# 差分更新に添える共有画面は 1 つの純粋なキューで扱い、選ぶことは状態を変えず、消費はログの `diff` の行を入力に 1 回だけ行う

差分更新に添える[共有画面](../../GLOSSARY.md)の扱い（受け取り・この回に添える画面の選び方・持ち越し・[一時停止](../../GLOSSARY.md)の後の追いつき）を、同期の純粋な module `ScreenQueue`（`server/src/core/screenQueue.ts`）1 つにする（仕様 [#1638](https://github.com/daiki-beppu/live-mindmap/issues/1638)、実装 [#1652](https://github.com/daiki-beppu/live-mindmap/issues/1652)・[#1653](https://github.com/daiki-beppu/live-mindmap/issues/1653)・[#1654](https://github.com/daiki-beppu/live-mindmap/issues/1654)）。これまでは、ライブ（`callUpdater`・`pushScreen`）と復元（`restoreState` の `replayScreens`）が同じ規則を別々に持っていた。突き合わせると違いが 8 つあり、4 つは偶然の食い違いだった（一時停止で終わるログの追いつきの印が戻らない、差分更新が止まった回に選んだ画面を消費したまま、`screenCount` が前の `screen` の行の数を超える、画像を添えない会議を復元すると添える）。

- **操作は「受け取る・選ぶ・消費する・一時停止の印を付ける・画像を添えないにする」の 5 つ。「確定する」「巻き戻す」は持たない**。選ぶことはキューを変えないので、一時停止や停止で終わった回に戻すものが無い
- **消費の入力は、書いた（復元では読んだ）`diff` の行そのもの**。受けた順の番号（`seq`）が行の `screenCount` より小さく、締め切りまでの画面だけを外す。呼び出し中に届いた画面は、回の結末にかかわらず残る。ライブと復元が同じ行を同じ関数に入れるので、「ライブ = 復元」は照合ではなく作りで成り立つ（[ADR 0024](0024-reflect-diff-row-in-one-pure-fold.md) の反映と同じ形）
- **復元は「選ぶ」を呼ばない**。添えた画面は `diff` の行の `input.screens` をそのまま使う。規則を変えても、過去のログは同じに戻る
- **`Result` を返し、Effect は返さない**。ライブは `Ref.modify` の中で、`reflectDiff` の隣で呼ぶ。消費は反映の中には入れない（ADR 0024 が共有画面の持ち越しを反映の外に置いている）。消費の失敗は、復元では行の位置つきの `InvalidLogEvent`、ライブでは defect
- **ライブは、ログの行を書くこととキューの操作を、Session ごとの 1 つの `Semaphore` で直列化する**。区間は 2 種類ある。1 つは `pushScreen` の「`screen` の行を書く → 受け取る」で、中断もできなくする。もう 1 つは呼び出しの結末の「消費する → `diff` の行」（成功の回とエラーの回）と「印を付ける → `diff-update-paused` の行」だ。選ぶこと・画像の読み戻し・応答の待ちは区間の外に置く
- **キューの外に残すもの**: 画像ファイルの名前の予約（`screenFiles`。受け取りより前に要る）、更新器の中の共有画面の状態（[#1313](https://github.com/daiki-beppu/live-mindmap/issues/1313) の決定どおり、それを使う DiffUpdater に置く）

## Considered Options

- **ライブと復元の写しを残し、規則ごとに「ライブ = 復元」の照合テストを重ねる（今までの作り）**: 照合テストを重ねても、偶然の食い違いが 4 つ残っていた
- **「選ぶ」でキューから外し、一時停止で巻き戻す（前のライブの作り）**: 巻き戻しのために、選ぶ前の数と残した数を覚えておく必要がある。復元はその手順を別に写すことになる
- **消費を `reflectDiff` の中に入れる**: ADR 0024 が反映の外に置くと決めた共有画面を、反映が知ることになる
- **`screen` の行を書いてから受け取る、の順にそろえるだけ（直列化しない）**: 仕様の formal-spec で、TLC が「行を書く → 一時停止 → 再試行の `diff` → 受け取る」の割り込みで、復元にだけ追いつきの印が残る反例を出した。受け取り側と結末側のどちらか片方だけを囲んでも、反例は残る
- **呼び出し全体を直列化する**: AI の応答を待つ間、画面を受け取れなくなる

## Consequences

- 共有画面の規則を変えるときは `screenQueue.ts` の 1 か所を直す。ライブと復元がそろって変わる。規則の中身は `screenQueue.test.ts` の期待値で確かめ、Session のテストには配線（行の書き込み・読み戻し・どの結末で消費するか・受け取りと結末の順）だけを残す
- 差分更新の呼び出しの TLA+ のモデル（`verify-diff-update-scheduler`）は、共有画面・ログ・復元を含まない。直列化の約束の証拠は `sessionScreenOrdering.test.ts` にある
- 更新器へ渡す画像の id は、helper の id ではなく画像のファイル名になった（復元と同じ形）
- ログの形は変えない。過去のログはそのまま読める
