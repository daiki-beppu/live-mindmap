# MVP のパイプラインはローカルの Node サーバーが持ち、ブラウザは表示と操作だけにする

MVP では、ヘルパーのイベントを受けて差分更新エンジン（Claude）と「いま話している」ノードの判定（Jev）を呼び、セッションの状態とログを持つ役を、ローカルで動く Node のサーバーに置く。ブラウザはサーバーから届くスナップショットを描き、操作を送り返すだけにする。ヘルパーはサーバーが子プロセスとして起動する。MVP の間はデプロイしない。

当初は、バックエンドが必要なら Convex を第一候補にしていた。しかしヘルパーは Mac 専用でローカルに常駐するため、Convex を使ってもヘルパーからの中継役がローカルに要る。Convex で得られる同期や共同編集は MVP の範囲外なので、サーバーが 1 つ増えるだけになる。ブラウザだけで完結させる案は、API キーがブラウザに出て、再読み込みで状態が消え、ログをファイルに書けないため外した。

Claude は、コストを抑えるため Agent SDK をサブスクリプションの認証で呼ぶ。API キーで直接呼ぶより応答が遅い（構造化出力が 2 ターンになる）が、2 発言ごと・同時に 1 つまでの呼び出しなら重ならない。

## Consequences

- MVP の後は何らかの形でアプリ化する。移しやすくするため、エンジン・状態・ログ・再生は WebSocket や Node の実行環境に依存しない TypeScript のモジュールにし、サーバーはそれを WebSocket につなぐ薄い層にとどめる
- サブスクの認証は、自分やチームで使う間だけ成り立つ。アプリとして配布するときは、差分操作の呼び出しを API キーで Anthropic API を直接呼ぶ実装に差し替える。そのため Claude の呼び出しは 1 つの関数の後ろに閉じておく
- 状態はサーバーのメモリにあり、同時に扱うセッションは 1 つ。サーバーが落ちたら、ログの差分操作を順に適用し直して復元する（LLM は呼び直さない）
