# 発言の確定の遅れ（Issue #97）の調査

実際の会議（2026-10-02、65 分）では、話し終わりから発言の確定まで p50 8.8 秒かかった（合成音声のデモは 0.3〜1.0 秒）。この文書は、合成音声で遅れを再現し、遅れる条件を切り分け、直し方の候補を比べた結果と、おすすめをまとめる。本番の挙動は変えていない（変更は `SpeechAnalyzerTranscriber.convert` の `public` 化だけ）。実会議の録音と本文は使っていない。実会議の数値は Issue #97 の集計値だけを使う。

## 測り方

- 道具: `helper/Sources/stt-bench`（`synth` で `say` から音声を合成、`run` で実時間のまま SpeechAnalyzer に流して JSONL を出す、`variants` で候補の一覧）、`server/bench/sttLatency.ts`（遅れの集計と、候補 b・c の計算）、`server/bench/sttReplay.ts`（本番の `createSession` と差分更新に流して、話し終わり → ノードと再現率を出す）。
- 認識は ja-JP、`.volatileResults` + `.fastResults`（現状の設定）。`相手` の流れ 1 本が基本で、`--load` を付けると、別の音声をもう 1 本同時に認識する（2 本同時の負荷）。
- 合成音声・計測の出力・実行用スクリプトは、リポジトリの外の `/tmp/stt97/m3` に置いた。リポジトリに音声は入っていない。
- 「遅れ」は、各文の話し終わり（台本の行の end）から、その文を覆う発言が届くまでの秒数。確定結果の end から数える方式は、確定が遅れても end が遅れるので遅れが見えなくなる（前回の調査で確認済み）。この文書は行の end から数える。
- 各条件 1 回ずつの計測。同じ条件の繰り返しによるばらつきは測っていない。同じ設定で比べられる組（下の「2 本同時」の 2 行）は 0.1 秒以内で一致した。件数が少ない条件（`long` は 4 行）の p90 は、実質最大値。
- 6 場面（`agree` / `brainstorm` / `chitchat` / `converge` / `monologue` / `rapid`）は、`helper/bench/scenarios/bench6.json`。

## 1. 再現

現状の設定（baseline）で、各文の話し終わり → 確定結果が届くまで（秒、p50 / p90）。

| 音声 | 行数 | p50 | p90 |
|---|---|---|---|
| `short`（10 行、短い文、gap 0.5〜0.6 秒、元の台本） | 10 | 5.5 | 9.3 |
| `long`（4 行、長い文） | 4 | 1.0 | 10.9 |
| `aizuchi`（相づちが重なる） | 6 | 5.0 | 9.9 |
| `gap 0`（`short`） | 10 | 10.8 | 16.9 |

`short` と `aizuchi` と `gap 0` で、実会議に近い、または超える遅れ（p50 5〜11 秒、p90 9〜17 秒）が再現した。デモ（0.3〜1.0 秒）の遅れは、文の間の無音が長い音声（下の `gap 2.0`）に近い。

## 2. 条件の切り分け

### 無音の長さ（文の間の gap、baseline、p50 / p90）

| gap | `short` | `long` |
|---|---|---|
| 0 秒 | 10.8 / 16.9 | 10.5 / 14.9 |
| 0.6 秒 | 4.4 / 9.3 | 0.7 / 11.2 |
| 1.0 秒 | 4.9 / 10.6 | 1.1 / 1.7 |
| 2.0 秒 | 3.4 / 6.6（9 件） | 0.9 / 1.6 |

gap が短いほど遅れる。gap 0 では `long` でも 10 秒以上になる。gap 1.0 秒以上で `long` は 2 秒以内に収まる。`short` は gap 2.0 秒でも 3〜7 秒かかる。`short` の gap 2.0 秒は、確定結果が 9 件で、1 行ぶんの確定結果は届かなかった。

### 発話の長さ

| 音声（gap は元の台本） | p50 / p90 |
|---|---|
| `short`（1 文が短い） | 5.5 / 9.3 |
| `long`（1 文が長い） | 1.0 / 10.9 |

`long` は p50 が小さく p90 が大きい。4 行しかなく、1 行だけが 10 秒以上遅れたことを表す。1 文が短いと、全体に遅れやすい。

### 2 本同時の認識の負荷

| 条件 | p50 / p90 |
|---|---|
| `short` 単独 | 5.5 / 9.3 |
| `short` + `long` を同時に認識 | 5.5 / 9.2 |
| `long` 単独 | 1.0 / 10.9 |
| `long` + `short` を同時に認識 | 1.0 / 10.9 |

2 本同時でも遅れは変わらない。負荷は原因ではない（この条件の範囲）。

結論: 遅れは、文の間の無音が短いほど大きく、1 文が短いほど全体に出やすい。認識の負荷には依存しない。

## 3. 直し方の候補

### 候補 a: SpeechAnalyzer の設定

13 候補を `short` / `long` で比べた（`stt-bench variants` の名前）。確定結果が届くまでの p50 / p90（秒）。

| 候補 | 内容 | `short` | `long` |
|---|---|---|---|
| baseline | 現状 | 5.5 / 9.3 | 1.0 / 10.9 |
| no-fast | `.volatileResults` のみ（`.fastResults` なし） | 12.5 / 19.9 | 6.3 / 13.8 |
| final-only | 途中結果なし（`.fastResults` のみ） | 5.5 / 9.2 | 1.0 / 10.8 |
| alternatives | `alternativeTranscriptions` を追加 | 5.5 / 9.2 | 1.0 / 10.9 |
| confidence | `attributeOptions` に `transcriptionConfidence` を追加 | 5.5 / 9.2 | 1.2 / 10.9 |
| preset-progressive | `Preset.timeIndexedProgressiveTranscription` | 5.5 / 9.2 | 1.0 / 10.9 |
| detector-low / medium / high | `SpeechDetector` の感度 | 6.1 / 9.2（3 つとも） | 1.0 / 10.9（`high` は 10.8） |
| finalize-1s / 2s / 3s | 更新が 1 / 2 / 3 秒なければ `finalize(through:)` を呼ぶ | 5.5 / 9.2（3 つとも） | 1.0 / 10.8〜10.9 |
| priority | `Options(priority: .userInitiated, modelRetention: .processLifetime)` | 5.5 / 9.2 | 1.0 / 10.9 |
| ignore-limits | `ignoresResourceLimits`（macOS 27 以降） | 5.5 / 9.2 | 1.0 / 10.9 |

確定までの遅れを縮めた候補はなかった。`no-fast` は悪化した（実装メモにある、`.fastResults` を外すと確定が塊で遅れるという事実と合う）。`finalize(through:)`（確定を促す API）を、更新が 1 / 2 / 3 秒途切れたときに呼ぶ候補は、上の表の数値では遅れが縮まらなかった（この表は、失敗を記録する修正の前の計測）。修正後の再実行では、呼び出しの失敗は 0 件だったが、呼び出しの回数は 0〜2 回と少なく、行ごとの遅れは表と照合していない。そのため、修正後の計測で finalize に効果がないことは未確認（件数は 6 章に書いた）。設定で直す手は、表の範囲では見つからなかった。

### 候補 b・c: 途中結果を使う

途中結果が T 秒変わらなければ、最後の本文を発言として出す（b）。確定結果が先に届けば確定結果を出す。出した後で確定が届いたときの扱いを `discard`（捨てる）と `correct`（訂正として流す）で比べた。baseline の JSONL からの計算（認識の出力は baseline と同じ）。

T の比較（`short` / `long` の `discard`、p50 / p90、秒。「現状」は確定結果）:

| 条件 | 現状 | T=1 | T=2 | T=3 |
|---|---|---|---|---|
| `short` | 5.5 / 9.3 | 5.5 / 9.3 | 5.5 / 9.3 | 5.5 / 9.3 |
| `long` | 1.0 / 10.9 | 0.5 / 1.0 | 1.0 / 10.9 | 1.0 / 10.9 |
| `aizuchi` | 5.0 / 9.9 | 2.5 / 5.1 | 5.0 / 9.9 | 5.0 / 9.9 |
| gap 0 `short` | 10.8 / 16.9 | 9.6 / 15.9 | 10.8 / 16.9 | 10.8 / 16.9 |
| gap 0 `long` | 10.5 / 14.9 | 0.2 / 10.5 | 10.5 / 14.9 | 10.5 / 14.9 |
| gap 1.0 `short` | 4.9 / 10.6 | 1.5 / 4.9 | 3.2 / 8.2 | 4.9 / 10.6 |
| gap 2.0 `short` | 3.4 / 6.6 | 1.8 / 3.8 | 2.6 / 4.8 | 3.7 / 6.6 |

T=1 秒だけが、すべての条件で現状以下になる。T が長いと、途中結果の更新が続く間は出せず、利得が消える。このため T は 1 秒にする。`discard` と `correct` の遅れは同じ（上書きの件数も同じ）。

出した後に確定結果が届いて本文が違った件数（上書き、T=1 秒）:

| 場面（6 場面） | 確定結果の件数 | 上書き |
|---|---|---|
| agree | 10 | 2 |
| brainstorm | 11 | 4 |
| chitchat | 12 | 1 |
| converge | 14 | 0 |
| monologue | 3 | 0 |
| rapid | 10 | 0 |
| 合計 | 60 | 7（約 12%） |

なお、gap を振った音声では、gap 2.0 `short` で上書きが 3 件（T=1）、gap 0.6 `long` で 1 件あった。

**後から届いた確定結果の規則（決定）**: `discard`（捨てる）を選ぶ。理由: 6 場面の再現率が `correct` と同じで（下の表）、遅れも同じ範囲だった（p50 は 6 場面中 3 つで `correct` が 0.2〜1.1 秒小さく、残り 3 つは同じ。p90 は 0.1〜1.6 秒の差で、向きは場面による）。この差は 1 回の計測の範囲で、`discard` を退けるほど大きくはないと判断した。`correct` は、本番に既知の発言を書き換える仕組みがない（`server/src/core/session.ts` は既知の ID を差分更新の対象から外す）ので、実装が増える。

**区間の一部だけが先に出ていた確定結果**（2 つの発話のうち片方だけが T 経過で出済み、もう片方は T 前）の扱いは、「出ていない方を、確定結果が届いた時刻に出す」と決めた。単体テスト（`server/test/sttLatency.test.ts`）で固定している。この状況が実際に何件起きたかの数は、集計の出力にないため未計測（空欄）。

### 候補 c: 途中結果で先に差分更新を呼び、確定で上書きする

c は、b の T を 0 に近づけた案。出せる時刻は b より早いが、先に出した発言を確定で書き換える仕組みが本番にない。そのため、上書き後の再現率は測れない（測るには、既知の発言の書き換えと、差分更新への再投入を実装する必要がある）。上書きの件数と割合は、上の b の表（約 12%）が目安になる。

## 5. おすすめ

**b を T=1 秒、後から届いた確定結果は `discard` で実装する。**

- a は、修正前の計測では遅れを縮められなかった（修正後の遅れは未照合）。この調査では設定の変更は採用しない。
- b は、6 場面の p50 を 3.8〜12.8 秒から 3.8〜7.1 秒へ縮め、再現率は 14/15 のまま。
- `correct` は `discard` と同じ再現率・遅れで、本番に書き換えの仕組みが要る。割に合わない。
- c は、上書きの再現率が測れず、仕組みも本番にない。b の後に、必要なら検討する。

実装 issue に引き継ぐ注意（未解決）:

- 本番の途中結果（`partial` イベント）は、本文だけで start / end がない（`helper/Sources/HelperCore/Events.swift:68-73`）。b は start を発話の識別に使うので、イベントの拡張が要る。
- `自分` の確定結果は、`相手` の確定結果との重複判定のため、最大 8 秒保留される（`Duplicates.swift`、出力先がスピーカーのとき）。b で `自分` の発言を途中結果から出すと、この重複判定を通らない。実装 issue で扱い方を決める必要がある。この 8 秒の保留は、本調査の遅れの数字（話し終わり → 確定結果が届くまで）には含まれない。実会議の遅れ（8.8 秒）のうち、`自分` トラックの分は、この保留が上乗せされている可能性がある（未確認）。
- 差分更新の `QUIET_MS`（1.5 秒）と、Claude の呼び出し（約 2 秒）は変わらないので、ノードが出る時間は、b でも 3.8 秒以上は残る。

## 6. 試した条件と、測れなかったもの

- OS: macOS 26 以降の SpeechAnalyzer（ja-JP）。音声は `say` の合成音声で、実会議の音声ではない。
- 各条件 1 回の計測。繰り返しのばらつきは未測定（空欄）。
- 6 場面の再生は、現状 / discard / correct を各 1 回。適用されなかった（`dropped` の）操作は、ノードに反映されたと数えない（`reflectedArrivals`）。同じ入力でも Claude の応答時間で p50 が数秒動く（現状の `converge` は、数え方を直す前後で 10.6 → 7.6）。
- 区間の一部だけが先に出ていた確定結果の件数: 未計測（空欄。集計の出力にない）。
- c の上書き後の再現率: 測れない（本番に上書きの仕組みがない）。
- 候補 a の 6 場面の再生: していない（遅れが縮まらなかったため）。
- 候補 a（`finalize-*`）の `finalize(through:)` の成否: 失敗を握りつぶす実装を直した後に、`short.wav` / `long.wav` で各 1 回再実行した。成功 / 失敗の件数は次のとおりで、失敗は 0 件。`finalize-1s` は short 1 / 0・long 2 / 0、`finalize-2s` は short 0 / 0・long 1 / 0、`finalize-3s` は short 0 / 0・long 0 / 0。呼び出しが 0 回の組み合わせは、この音声では finalize が試されていない。回数が少なく遅れも未照合なので、修正後の計測で「呼んでも変わらない」とは結論しない。それより長い音声や実会議の音声での成否は未確認。この再実行での行ごとの遅れの数値は、上の表と照合していない（未確認）。
