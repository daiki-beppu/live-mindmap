# Devin の環境をファイルで決める範囲

- 調査日: 2026-10-31
- issue: [#1790](https://github.com/daiki-beppu/live-mindmap/issues/1790)（map [#1784](https://github.com/daiki-beppu/live-mindmap/issues/1784)）
- 一次情報: docs.devin.ai（各節に URL）と Devin の 2026 年のリリースノート。ページはすべて 2026-10-31 に取得した `.md` 版を読んだ。

## 答え

Devin の環境は **blueprint**（YAML）で書き、**build** が blueprint を実行して **snapshot**（VM イメージ）を作り、各セッションは snapshot の新しいコピーから立ち上がる。blueprint はリポジトリの **`.devin/blueprint.yaml`** に置ける（git-backed blueprint）。ただし、ファイルを置いただけでは効かない。リポジトリを Devin につなぎ、環境に加える操作は UI でしか行えない。ファイルを変えた後の sync も、UI の操作・API・UI で入れる「既定ブランチの commit ごとに実行」の設定のどれかが要る。

| ファイル（repo）で決められる | UI（または API・Terraform）でしか決められない |
|---|---|
| `.devin/blueprint.yaml` の `initialize`・`maintenance`・`knowledge`・`clone`・`runs-on`・`includes` | GitHub 連携と、Devin が読める repo の選択（Settings > Connections） |
| ランタイムの版（`uses: github.com/actions/setup-node@…` や `nvm install`） | repo を環境に加える（Settings > Environment > Blueprints > Add） |
| 依存の入れ方（`pnpm install`）と、lint・test のコマンドを Devin に知らせる `knowledge` | sync と build の起動（Sync ボタン、sync API、または Advanced タブの「Run on every commit to default branch」） |
| エージェントへの常時の指示: `AGENTS.md`（先頭 16 KiB を自動で読む） | organization blueprint（全 repo 共通。`post-build` はここと enterprise のみ） |
| 手順の指示: `.agents/skills/<name>/SKILL.md` | secrets（blueprint エディタの Secrets タブ、Secrets ページ）とファイル添付 |
| | ネットワークの制限（Security Profiles）、snapshot の pin、Playbook |

## 1. 環境設定の仕組み

### blueprint・build・snapshot

- 環境は Linux の VM。設定は snapshot として保存され、各セッションはそこから起動する。セッション中の変更は snapshot へ戻らない。organization ごと・プラットフォームごとに有効な snapshot は 1 つ。<https://docs.devin.ai/onboard-devin/environment.md>
- blueprint は Dockerfile、build は `docker build`、snapshot は Docker イメージにあたる。<https://docs.devin.ai/onboard-devin/environment/blueprints.md>
- 設定の方法は 2 つ。セッションで「Set up your environment for this repo」と頼むと、Devin が blueprint を提案カードで出し、承認すると build が走る。手で書くなら宣言的な設定（blueprint の YAML）が推奨。<https://docs.devin.ai/onboard-devin/environment.md>
- 古い「Repo Setup」の対話型ウィザードのページ（`/onboard-devin/repo-setup`）は、いまは上の環境の説明ページと同じ内容を返す。設定は blueprint に一本化されている。

### 節と実行のタイミング

<https://docs.devin.ai/onboard-devin/environment/blueprints.md>、<https://docs.devin.ai/onboard-devin/environment/blueprint-reference.md>

| 節 | 用途 | いつ動くか |
|---|---|---|
| `initialize` | ランタイム・システムパッケージ・グローバルな CLI | build の時だけ。結果は snapshot に残る。differential build で引き継がれた workspace では飛ばされる |
| `maintenance` | 依存のインストール・更新 | build の時に動く。**セッション開始時には自動で実行されず**、コマンドがエージェントに文脈として渡されるだけ（依存が変わっていればエージェントが流し直す） |
| `knowledge` | lint・test・build のコマンドなど | 実行しない。セッション開始時にその repo の分が文脈に入る |
| `post-build` | 組み上がった環境の検証 | organization・enterprise の blueprint だけで使える。repo 単位では使えない。0 以外で終わると build は失敗する |
| `clone` | clone の ref・深さ・submodule・LFS | repo 単位の blueprint だけ |

build の順番: enterprise（`~` で initialize → maintenance）→ organization（同じ）→ 全 repo を clone → repo ごとに `~/repos/<repo-name>` で initialize → maintenance → post-build → health check → snapshot を保存。各ステップの上限は 3 時間。<https://docs.devin.ai/onboard-devin/environment/blueprints.md>

build が走るきっかけ: blueprint の保存、repo の追加・削除、repo secret の追加、手動の **Build snapshot**、**約 24 時間ごとの定期更新**、Devin の提案。<https://docs.devin.ai/onboard-devin/environment/blueprints.md>

セッション開始時の動き: 関係する repo の最新コードを pull する → maintenance のコマンドを（実行せず）渡す → その repo の knowledge を読み込む。<https://docs.devin.ai/onboard-devin/environment/blueprints.md>

`$ENVRC` に書いた変数は、後続のステップと、その build から作るセッションに引き継がれる（`$GITHUB_ENV` に近い）。`uses:` の action が足した PATH は自動で `$ENVRC` に入る。`run:` の中の `export PATH=` はそのステップでしか効かない。`$ENVRC` は build ごとに空に戻るので、`maintenance` が `initialize` の書いた値に頼ってはいけない（differential build で困る）。<https://docs.devin.ai/onboard-devin/environment/blueprint-reference.md>

### 宣言的な設定ファイル: `.devin/blueprint.yaml`

<https://docs.devin.ai/onboard-devin/environment/git-backed-blueprints>（リリースノートでは 2026-07-03 の「Git-Backed Blueprints」で入った。<https://docs.devin.ai/release-notes/2026.md>）

- repo を環境に**加えた時**、既定ブランチに `.devin/blueprint.yaml` があれば git-backed モードになる。無ければ UI で編集するデータベースモードになる（後からソースのドロップダウンで Git に切り替えられる）。
- **push しただけでは sync されない。** sync が走るのは次の 4 つの場合。
  1. sync API: `POST /v3beta1/organizations/{org_id}/snapshot-setup/sync`。その後に `POST /v3/.../snapshot-setup/builds` で build を起動する（API トークンが要る）
  2. UI の Sync ボタン（中身が変わっていれば build も走る）
  3. repo を環境に加えた時
  4. repo の Advanced タブで「Run on every commit to default branch」を有効にした時。GitHub.com の repo で、organization でこの設定が使える時だけ。「Report status checks for each commit」を有効にすると、build の結果が commit の check run として出る
- git-backed の間、UI のエディタからは直接保存できない。エディタの **Create PR** を押すと、Devin が `.devin/blueprint.yaml` を変える PR を作る。セッション中に Devin が出す blueprint の提案も PR になる。
- モノレポでは、ルートの blueprint に `includes: [server, web]` と書くと、各ディレクトリの `.devin/blueprint.yaml` を workspace の blueprint として読む（入れ子の includes は不可）。workspace の blueprint のコマンドは、そのディレクトリを作業ディレクトリにして動く。<https://docs.devin.ai/onboard-devin/environment/workspaces>
- `---` で区切った複数の文書と `runs-on:` で、プラットフォームごとに書き分けられる（既定は Linux。macOS・Windows はアカウントにマシンが登録されている場合だけ）。
- organization blueprint は git-backed にできない（git-backed は repo の `.devin/blueprint.yaml` の仕組み）。UI か API・Terraform provider で管理する（Terraform provider の blueprint リソースは 2026-10-14 のリリースノート）。

## 2. Node・pnpm の版

### 標準のイメージに入っているもの

- **base image の Node の既定の版は、公式ドキュメントに書かれていない**（2026-10-31 時点。docs.devin.ai の llms.txt・テンプレート集・リファレンスを探したが見つからなかった）。
- 書かれているのは次のとおり。**nvm は入っている**（「Use nvm (pre-installed) to switch Node.js versions per repository via `.nvmrc`」）。JDK 17・Rust（rustup）と Cargo・awscli も入っている。base image は Ubuntu 系で、ホームは `/home/ubuntu`。<https://docs.devin.ai/onboard-devin/environment/templates>、<https://docs.devin.ai/onboard-devin/environment/blueprint-reference.md>
- pnpm が入っている、という記述は無い。テンプレートはどれも `initialize` で `npm install -g pnpm` している。<https://docs.devin.ai/onboard-devin/environment/templates>

したがって Node 24 は blueprint で**明示して入れる**前提にする。

### Node 24 と `packageManager` の pnpm をそろえる方法

1. **Node 24**: `initialize` に CI（`.github/workflows/tests.yml` の `actions/setup-node` + `node-version: 24`）と同じ action を書く。

   ```yaml
   initialize:
     - name: Node 24
       uses: github.com/actions/setup-node@v4   # 参照の形は github.com/<owner>/<repo>@<ref>。repo の CI と同じタグにそろえてよい
       with:
         node-version: "24"
   ```

   - `uses` で使えるのは、Node の action（`node16`・`node20`・`node24`）と composite action。Docker の action は Linux の build だけで使える。`post` のステップは飛ばされる。GitHub のコンテキストは仮の値なので、GitHub API やイベントの情報に頼る action は動かないことがある。**`uses` は `maintenance` では使えない**（使うと build が失敗する）。<https://docs.devin.ai/onboard-devin/environment/github-actions>
   - action を使わず、入っている nvm で `nvm install 24 && nvm alias default 24` としてもよい（テンプレートに `nvm install 20` の例がある）。その場合、PATH を `$ENVRC` に書かないと後続のステップに引き継がれない点に注意する。

2. **pnpm**: 次のどちらかにする。
   - `npm install -g pnpm`（テンプレートどおり）の後に、repo で `pnpm install` を走らせる。pnpm 11 以降は `packageManager` の版と合わないとき、既定（`pmOnFail: download`）でその版を取ってきて使う。そのため、グローバルに入れる版を厳密に合わせなくても、repo の中の実行は `pnpm@12.11.2` にそろう（pnpm 11 のリリースノートより。<https://newreleases.io/project/npm/pnpm/release/11.0.0-rc.2>。pnpm の公式の changelog は未確認）。
   - CI と同じ `pnpm/setup` の action を `uses` で呼ぶ。`packageManager` を読む action だが、Devin の build で動くかは試していない（action の種類と GitHub コンテキストの制限に当たらないか、仕様の段階で確かめる）。
   - Node 24 に入っている corepack（`corepack enable`）でもそろえられる。ただし Node 25 から corepack は同梱されないので、Node を上げるときに困る。

3. **依存**: `maintenance` で `pnpm install --frozen-lockfile` を走らせる（pnpm のテンプレートと同じ）。
   - `npm install` のテンプレートには「`npm ci` は使わず差分で入れる」という注記がある。pnpm の `--frozen-lockfile` は `node_modules` を消さないので、この注記には当たらない。
   - maintenance は `initialize` の `$ENVRC` を当てにできない（differential build で困る）。そのため PATH を自分で通すか、`initialize` で `/usr/local/bin` 等に入れる。

この repo の手順を共通のセットアップスクリプトにまとめるなら、`maintenance: bash scripts/<共通スクリプト>` のように呼べる（`run` のステップは bash で動き、repo の blueprint は repo のルートで動く）。

## 3. ネットワークと secrets

### ネットワーク

- 制限は **Security Profiles** のネットワークポリシー（宛先の allowlist）でかける。設定するのは org・enterprise の管理者で、UI か v3 API から行う。リポジトリのファイルでは決められない。<https://docs.devin.ai/product-guides/security-profiles.md>
- 既定は「Inherit」で、どの階層も profile を結び付けていなければ制限は無い（「No profile — sessions at this level run unrestricted」）。個人や小さな org が何も設定しなければ、npm レジストリにも GitHub にも出られる。
- snapshot の build に効くのはネットワークポリシーだけ。build 用の既定 profile は別に設定できる。Devin が動くのに要る宛先（repo へ届く git のプロキシなど）は自動で許可される。

### secrets

- 置き場所は UI だけ: org・個人の Secrets ページ、blueprint エディタの Secrets タブ（org・repo）、セッション中に渡すセッション限りの secrets。<https://docs.devin.ai/product-guides/secrets.md>
- blueprint では `$NAME` で参照するだけで、宣言はしない。build の各ステップの前に注入され、snapshot を保存する前に消される。ただし、コマンドが設定ファイルに書き出した値は snapshot に残る。<https://docs.devin.ai/onboard-devin/environment/blueprint-reference.md>
- **secrets を何も渡さなくても動くか**: 動く。必須の secrets は無い。repo への読み書きは SCM 連携が担い、secrets ではない。この repo の `pnpm install`・`typecheck`・`test` は公開レジストリだけを使い、API キーも要らない。そのため blueprint は secrets を参照しない形で書ける（bench・eval・`test:external` は map で範囲外）。

## 4. エージェントへの指示の読ませ方

| 仕組み | 置き場所 | 読み方 | 一次情報 |
|---|---|---|---|
| `AGENTS.md` | repo（ルートほか） | 各ファイルの**先頭 16 KiB** を自動で文脈に入れる。超えた分は切り詰めの通知だけ出て、必要なら Devin が読みに行く。repo を設定する時にルートの `AGENTS.md` を読んで従う動きは 2026-10-09 のリリースで入った | <https://docs.devin.ai/onboard-devin/agents-md.md>、<https://docs.devin.ai/release-notes/2026.md> |
| blueprint の `knowledge` | `.devin/blueprint.yaml` | 実行しない。セッション開始時に、**作業する repo の分だけ**を読む。`lint`・`test`・`build` という名前を慣習として使い、Devin は自分の作業を確かめる時にこれを見る | <https://docs.devin.ai/onboard-devin/environment/blueprint-reference.md> |
| Skills | `.agents/skills/<name>/SKILL.md`（Agent Skills 標準） | つないだ repo 全体から自動で見つける。Customize ページ・plugin でも配れる | <https://docs.devin.ai/product-guides/skills.md> |
| Knowledge（製品の機能） | UI | **非推奨**で、Skills（plugin の中）へ自動で移している途中。`AGENTS.md`・`CLAUDE.md`・`.cursorrules` 等からも自動で取り込む | <https://docs.devin.ai/onboard-devin/knowledge-onboarding.md> |
| Playbook | UI | **Skills へ移行中**。2026-10-24 以降に作ったアカウントには Playbook が無い。`!macro` は移行後も、その Playbook から変わった skill を呼ぶ | <https://docs.devin.ai/product-guides/using-playbooks.md> |

この repo の今の状態に当てはめると、次のとおり。

- `AGENTS.md` は 9,287 バイトで 16 KiB に収まるので、全文が自動で入る。
- `.agents/skills/` にはすでに skill が 5 つあり（foldkit・verify-live-mindmap 等）、Devin も読む。Claude Code・Codex と同じファイルを共有できる。

## 5. 注意点（この repo で設定する時）

- **helper は Linux で通らない**。ルートの `pnpm typecheck` は `pnpm -r typecheck` なので helper の swift build まで走る。CI の `ts` job は `--filter @live-mindmap/server --filter @live-mindmap/web --filter @live-mindmap/e2e typecheck` と `pnpm fallow` に分けて流している。blueprint の `knowledge` には、この絞り込んだコマンドを書く必要がある（Linux で通るコマンドの決め方は別の ticket）。
- **セッション開始時に `pnpm install` は自動で走らない**。snapshot は最大で約 24 時間古い。セッションは最新コードを pull するが、lockfile が変わっていれば、エージェントが maintenance を流し直すかどうかに任される。`AGENTS.md` か `knowledge` に「lockfile が変わっていたら `pnpm install`」と書いておくと確実になる。
- **ファイルだけでは始まらない**。初回は UI で GitHub 連携 → repo を環境に追加（この時に `.devin/blueprint.yaml` を読み、git-backed になる）。以降に blueprint を変えたら、Sync を押すか、Advanced タブで commit ごとの sync を有効にする。API で sync するなら CI に Devin の API トークンを置くことになり、「API キーは渡さない」方針とぶつかるので、Advanced タブの設定を使う方がよい。
- Advanced タブの設定は「organization で使える時だけ」出る。使えない時は、変更のたびに Sync を押す。
- `uses` の action が Devin の build で動くかどうかは、action によって違う（GitHub コンテキストは仮の値）。`setup-node` は公式のテンプレートとリファレンスに例がある。`pnpm/setup` は未確認。
- 各ステップの上限は 3 時間。build 後のルートファイルシステムの空きが 2 GiB 未満なら失敗する（2026-09-25 のリリースノート）。

## 他の 2 つと比べる観点（#1785 Cursor・#1786 Claude cloud 向け）

- **設定ファイル**: `.devin/blueprint.yaml`（YAML。initialize・maintenance・knowledge）。
- **ファイルが効き始める条件**: repo を UI で環境に加えた時。以降は sync（UI・API・commit ごとの自動 sync）が要る。
- **イメージの作り方**: build して snapshot を作り、セッションはそのコピーから起動する。セッションの開始時には依存を入れ直さない。
- **ランタイムの版**: base image の Node の既定は書かれていない。`setup-node` の action か nvm で指定する。
- **指示**: `AGENTS.md`（先頭 16 KiB）・`.agents/skills`・blueprint の `knowledge`。Knowledge と Playbook は Skills へ移行中。
- **UI でしか決められないもの**: SCM 連携・repo の追加・sync の起動（または自動 sync の有効化）・org blueprint・secrets・ネットワーク（Security Profiles）・snapshot の pin。
