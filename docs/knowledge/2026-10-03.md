## 話し終わりから発言の確定までの 9 秒を、合成音声で再現して直し方を測り比べた話

実際の会議（65 分）で、話し終わりからマップのノードが出るまでが p50 12.5 秒かかっていたのを調べたときの学び。内訳は、話し終わり → **発言**（音声認識が確定させた文字起こしの 1 区切り）の確定が p50 8.8 秒、確定 → 差分更新の呼び出しの待ちが 1.5 秒、差分更新そのものが約 2 秒。合成音声で試したデモでは、確定までが 0.3〜1.0 秒だった。遅れの大半は、音声認識（macOS の SpeechAnalyzer、日本語）の確定待ちだった。takt に、合成音声での再現、条件の切り分け、直し方の比較までを調べさせた。

- 決定の記録: [実際の会議で、発言の確定が話し終わりから約 9 秒遅れる](https://github.com/daiki-beppu/live-mindmap/issues/97)、調査の結論 [`docs/investigations/2026-10-02-remark-finalization-latency.md`](../investigations/2026-10-02-remark-finalization-latency.md)

### 1. 遅れは、遅れて届いた結果の時刻ではなく、話し終わりの正解の時刻から測る

最初の計測では、確定結果が持つ区間の終わり（end）から、その結果が届くまでを測っていた。続けて話す短い文の音声（文の間の無音 0.3 秒）で、これは 0.4 秒だった。遅れは無いように見えた。

ところが、台本の各行の終わりから数え直すと、p50 5.5 秒・p90 9.3 秒だった。続けて話すと、音声認識は 1 文ずつではなく、約 11.5 秒ぶんの複数の文を 1 件にまとめて確定させる。まとめた結果の end は最後の文の終わりなので、そこから数えると届くまでは短い。しかし、最初の文の話し終わりからは 10 秒近く経っている。

元からあった計測の道具も、同じ形で遅れを測れていなかった。録音済みの文字起こしを流し直す再生は、発言を end の時刻に流していた。つまり、認識の遅れをゼロとして扱っていた。そこで、結果が実際に届いた時刻（arrival）で流し直す道具を新しく作った。

**遅れを測るときは、遅れる側が出した時刻ではなく、入力の側に持たせた正解の時刻から数える。** 合成音声なら、台本の各行の時刻がその正解になる。

### 2. 原因は文の間の無音の短さで、認識の負荷ではなかった

無音の長さ、1 文の長さ、2 本同時に認識する負荷の 3 つを、1 つずつ変えて測った（話し終わり → 確定、p50 / p90、秒）。

| 文の間の無音 | 短い文が 10 行 | 長い文が 4 行 |
|---|---|---|
| 0 秒 | 10.8 / 16.9 | 10.5 / 14.9 |
| 0.6 秒 | 4.4 / 9.3 | 0.7 / 11.2 |
| 1.0 秒 | 4.9 / 10.6 | 1.1 / 1.7 |
| 2.0 秒 | 3.4 / 6.6 | 0.9 / 1.6 |

2 本（相手と自分）を同時に認識させても、短い文は 5.5 / 9.3 → 5.5 / 9.2 で変わらなかった。実際の会議は、文の間に間を置かずに話し、相づちも重なる。デモの合成音声は文の切れ目に長い無音があったので、遅れが出なかった。

### 3. 設定で直す案は全部効かず、途中結果を使う案だけが効いた

直し方の候補は 3 系統だった。

- a: 音声認識の設定を変える（13 通り）
- b: 途中結果が T 秒変わらなければ、確定を待たずに発言にする
- c: 途中結果で先に差分更新を呼び、確定で上書きする

a は、13 通りのどれも遅れを縮めなかった。速さ優先の設定（`.fastResults`）を外すと、逆に p50 が 12.5 秒に悪化した。確定を促す API（`finalize(through:)`）を、更新が 1〜3 秒途切れたときに呼ぶ案も効かなかった。

b は T を 1・2・3 秒で比べた（短い文 / 長い文 / 相づちが重なる音声の p50 / p90、秒）。

| | 現状 | T=1 | T=2 | T=3 |
|---|---|---|---|---|
| 長い文 | 1.0 / 10.9 | 0.5 / 1.0 | 1.0 / 10.9 | 1.0 / 10.9 |
| 相づちが重なる | 5.0 / 9.9 | 2.5 / 5.1 | 5.0 / 9.9 | 5.0 / 9.9 |
| 無音 1.0 秒の短い文 | 4.9 / 10.6 | 1.5 / 4.9 | 3.2 / 8.2 | 4.9 / 10.6 |

T=1 だけが、すべての条件で現状以下になった。T を長くすると、途中結果の更新が続くあいだは発言にできず、短縮の効果が消える。6 つの場面を本物の差分更新に通すと、話し終わり → ノードの p50 は 3.8〜12.8 秒から 3.8〜7.1 秒に縮んだ。決定と TODO の再現率は 14/15 のままだった。

先に出した発言が、あとの確定結果と違っていたのは、60 件中 7 件（約 12%）だった。あとの確定を「捨てる」と「訂正として流す」で、遅れも再現率も同じだった。訂正には、すでに出した発言を書き換える仕組みが要る。差が出ないので、仕組みを増やさない「捨てる」を選んだ。c は、上書きした後の再現率を測る手段が無く、後回しにした。

**同じ結果になる 2 案なら、仕組みが少ないほうを選ぶ。** そのために、2 案を同じ入力で並べて測っておく。

### 4. 結論の文が、測った範囲を超えていないかを点検する

レビューで、確定を促す API を呼ぶ候補が、呼び出しの失敗を握りつぶしていたと指摘された（`try?` で捨てていた）。これでは「呼んでも変わらない」と「呼べていない」を区別できない。失敗を記録するよう直して計測し直すと、失敗は 0 件だった。ただし、呼ばれた回数は 0〜2 回と少なかった。

結論の文書は、この後も「呼んでも変わらない」と書いていた。修正の検証の工程が、修正後の遅れを照合していないのに断定していると差し戻し、「修正前の計測では縮まらなかった。修正後は未照合」に書き直された。同じ工程の最初の報告も「未確認と明記した」と書いていたが、明記できていない箇所が 5 つ残っていた。

**計測をやり直したら、結論の文がどの計測に支えられているかを 1 文ずつ確かめる。** 前の計測の結論が、新しい計測の結論の顔をして残りやすい。

## 長い処理が起動した側と一緒に止まるのを、3 回繰り返してから切り離した話

前のエントリの調査を takt に回していたあいだに、長い処理が、それを起動した側の寿命で止められた。この 2 日で 3 回目になる。takt の実行が 2 時間で止められ、止まった位置から積み直そうとして、もう一度はまった。

- 前に同じ形で止まった話: [AI エージェントのワークフローが、起動した側の時間の上限で止められ、止まった工程から積み直した話](./2026-10-02.md#takt-interrupted-requeue)

### 1. 起動した側の寿命は、上限を延ばすのではなく、切り離して外す

3 回は、どれも同じ形だった。

| 何が止まったか | 起動した側 | 止まった時点 |
|---|---|---|
| takt の実行（前日） | コーディング用エージェントのバックグラウンド実行（既定 30 分） | 30 分 |
| 実会議中の開発サーバー（前日） | 同じバックグラウンド実行（上限 2 時間） | 会議の 65 分目 |
| 今回の調査の takt の実行 | 同じバックグラウンド実行（上限 2 時間） | 1 時間 58 分、レビューの直前 |

前日は、takt の実行を上限の 2 時間にして起動し直して済ませた。調査の作業は、計測だけで 1 時間以上かかり、それを超えた。

今回は、takt の実行を `nohup` で切り離して起動し、プロセス番号を控えた。バックグラウンド実行には、そのプロセス番号の終了を待つループだけを載せた。

```sh
nohup takt run > takt.log 2>&1 < /dev/null & echo $! > takt.pid; disown
while kill -0 "$(cat takt.pid)" 2>/dev/null; do sleep 60; done   # これだけをバックグラウンド実行に載せる
```

待つループが上限で止まっても、takt は動き続ける。その後の 2 件の takt の実行は、これで最後まで回った。

**上限を延ばす対処は、次に長い処理が来たときにまた外れる。長い処理は、起動した側の寿命から切り離す。**

### 2. エージェントの 1 工程の中で起動したバックグラウンドの処理も、工程と一緒に止まる

調査の実装の工程は、計測をバックグラウンドで起動し、「計測の完了待ちです」と返して工程を終えた。工程が終わると、エージェントのプロセスと一緒に計測も止まった。結果は 1 本も残らなかった。その前の試みは、スクリプトに実行権限がなく、一度も起動していなかった。担当のエージェントは起動したと思い込んでいた。どちらの場合も、スクリプトの先頭で出力先を消していたので、途中から再開もできなかった。

再計画の工程が決めた対策は、次の 3 つだった。

- 前面のコマンドを 10 分以内に区切って流す
- 出力は一時ファイルに書き、成功したときだけ名前を変える
- 出力済みの組み合わせは飛ばす

これで、計測は途中で止まっても、続きから再開できる形になった。

**エージェントに長い計測を任せるときは、1 回の呼び出しで終わる大きさに区切り、どこまで終わったかを出力ファイルの有無で判断できるようにする。**

### 3. 「止まった位置から再開」は、いつも選べるとは限らない

前日は、止まったタスクを積み直すときに、始める位置の既定として「止まった位置から再開」（`resume-checkpoint`）が出た。今回、同じ手順で積み直すと、この選択肢が無いと言われて失敗した。

```text
Error: Unknown task retry start selection: resume-checkpoint
```

選択肢の一覧を出すと、既定は最初の計画の工程になっていた。そのまま積み直していたら、1 時間 45 分ぶんの計画・計測・実装を全部やり直すところだった。

takt のソースを読むと、止まった位置は、ワークフローの入れ子の経路と、各段の工程の種類の並びとして記録される。積み直すときは、その並びを今のワークフローの定義でたどり直し、たどれたときだけ「止まった位置から」を出す。今回止まったのは、入れ子の 4 段目のレビューの工程だった。レビュー担当の数が実行時に決まる並列の工程で、記録では種類が「並列」、定義の読み方では別の種類になり、照合が合わなかった。3 段目まではたどれた。

一覧から、止まったレビューの工程の頭を指定して積み直した。やり直したのは、途中まで進んでいたレビューの十数分だけだった。

**既定に任せて積み直す前に、選択肢の一覧と既定の位置を出して確かめる。** 前に既定だった選択肢が、止まった場所によっては出てこない。

## 音声認識の確定を待たず、1 秒変わらない途中結果を発言にした話

1 つ目のエントリの結論を、takt に実装させたときの学び。**途中結果**（音声認識が確定させる前に出す暫定の文字列と区間）が 1 秒更新されなければ、それを発言として差分更新に渡す。確定結果が先に届けば確定結果を使い、発言にした後に届いた確定結果は捨てる。takt の実行は 34 分、レビューは 2 回だった。

- 決定の記録: [途中結果が 1 秒変わらなければ発言として出す](https://github.com/daiki-beppu/live-mindmap/issues/99)、[ADR 0003 ローカルの Node サーバーがパイプラインを持つ](../adr/0003-local-node-server-owns-pipeline.md)

### 1. 前段の判定を通らない経路を足すときは、判定ごと持ってくるより、その経路を使わない

このアプリは、相手の声（会議アプリの音）と自分の声（マイク）を別々の**トラック**として認識する。スピーカーで会議を聞いていると、相手の声がマイクにも入る。そこで、自分の発言が相手の発言と同じ内容かを確かめ、同じなら印を付けている。この判定は確定結果にだけ行い、相手の確定を待つために自分の確定を最大 8 秒保留する。

途中結果から発言を作ると、この判定を通らない。選択肢は 2 つあった。

- 自分のトラックは途中結果から発言にしない（確定結果だけ）
- 途中結果から作った発言にも判定を通す

計画の工程は前者を選んだ。後者は、判定をサーバーへ移すか、保留の仕組みと組み合わせる必要があり、変更が大きい。調査で測った短縮の効果も、相手のトラックの値だった。速くなるのは相手の発言だけで、自分の発言の遅れは残る。

**前段で守っていた性質が、新しい経路で崩れるときは、まず新しい経路をその対象に使わない。** 守る仕組みを持ち込むのは、効果を測ってからでよい。

### 2. 同じ発話かどうかは、本文ではなく区間の始まりで決める

途中結果は、話しているあいだに本文が書き換わり続ける。本文で同じ発話かを判断すると、書き換わるたびに別の発話になる。そこで、同じトラックで区間の始まり（start）が同じ途中結果を、同じ発話の更新とした。本文が同じでも、start が違えば別の発話になる。

確定結果がどの発話を覆うかは、端の一致では決められない。実機の出力で、途中結果の start が 12.53 秒、確定結果の start が 12.71 秒とずれていた。発話の区間の中央が確定結果の区間に入るかで決めた。

### 3. 時間で動く規則は、時刻を受け取る純粋な部分と、タイマーを持つ部分に分ける

「1 秒経ったら出す」規則は、2 つのファイルに分けた。

- `core/settle.ts`: 現在時刻を引数で受け取り、出すべき発言を返す。タイマーを持たない
- `remarkSettling.ts`: 次に出す時刻に合わせて、タイマーを 1 本だけ張り直す

このリポジトリでは、中核のロジックが実行環境のタイマーに頼らない決まりにしている（ADR 0003）。おかげで、規則のテストは時刻を渡すだけで書け、実際に 1 秒待たずに済む。

レビューでは、このテストの穴を突かれた。「更新の間隔が 1 秒を超えたら別の発話にする」を確かめるテストが、次の途中結果を渡す前に「1 秒経った」処理を呼んでいた。そのため、間隔を比べる行は一度も実行されていなかった。その行を消しても、テストは通る状態だった。テストを 1 件足して、その行を通るようにした。

**守りたい行を消すとテストが落ちるかを確かめる。** 時刻を引数にした規則は、呼ぶ順番しだいで、守りたい分岐を通らずに済んでしまう。

### 4. 発言の番号は、捨てるかどうかが決まった後に振る

それまでは、ヘルパーからイベントが届いた時点で発言の番号（r1, r2, …）を振っていた。今回から、確定結果は捨てられることがある。届いた時点で番号を振ると、捨てた確定結果が番号を消費して、番号が飛ぶ。規則は番号の無い発言を返し、セッションに渡す直前に番号を振る形にした。

## 決めごとのない会議で話の 8 割が捨てられていたのを、「捨てる範囲」を閉じて直した話

実際の会議（65 分）は、決める会議ではなかった。ツールの紹介、体験談、おすすめ、質疑が中心だった。差分更新（AI が新しい発言を読み、マップへの変更だけを返す処理）は 350 回呼ばれ、そのうち 285 回が「マップを変えない」（noop）を返した。ノードが 10 分近く増えない区間が 2 回あった。その間も、発言は 5 分あたり 25〜40 件あった。この直しを takt に実装させたときの学び。

- 決定の記録: [雑談・共有が中心の会議でも、話題と要点が残るマップにする](https://github.com/daiki-beppu/live-mindmap/issues/98)

### 1. 捨てる条件を例で書くと、モデルは例に似たものまで捨てる

差分更新のプロンプトには、こう書いてあった。

```text
挨拶、進行の段取り、相づち、雑談、番組の解説のような、会議の中身でない発言は noop にする。
```

実会議での noop の理由は、「自作ツールのデモ説明であり、会議の議題・決定とは無関係」「お勧めと体験談で、新しい主張や決定はない」といったものだった。「雑談」「のような」という例の書き方が、決定につながらない話をまとめて捨てる根拠になっていた。

捨てる範囲を、4 つに閉じて定義し直した。

```text
noop にしてよいのは、新しい発言が次の 4 つだけでできているときに限る。
- 相づち / 進行の段取り / 聞き取れない断片 / 同じ内容の言い直し
これ以外（紹介、説明、体験談、おすすめ、質問と答え、脱線した話題など）は noop にせず、マップに残す。
```

あわせて、ノードの種類に「要点」（議題の中で共有された中身。紹介・体験談・おすすめ・質問とその答え）を足した。約 60 分の合成会議で、noop の割合は 29〜30% から 8〜10% に、ノードが増えない最長の時間は 5.1〜5.6 分から 4.1 分になった。決定と TODO の再現率は 100% のままだった。

**迷ったときの既定が「捨てる」になる書き方を避け、捨てる範囲を閉じたリストにする。** 閉じると、リストに無いものの既定が「残す」に反転する。

この線引きは、別の issue（Claude に渡す前に軽いモデルで雑談を振り分けて、呼び出しを減らす案）とも重なる。2 か所に別々の定義を持つと、片方だけ直したときに食い違う。プロンプトの定数 1 か所を正本にし、もう一方の issue はそれに従うと両方に書いた。

### 2. 言葉で粒度を絞っても効かないとき、数の上限を置く

捨てる範囲を閉じると、ノードが増えた。約 60 分の合成会議で 63〜64 だったのが 79〜84 になり、増えた分の大半は要点だった。「補足・値段・手順は新しい要点にせず、既存の要点を更新する」という基準を 1 行足しても、80・74 とほぼ変わらなかった。要点を 1 つずつ見ると、どれも「別の体験」として書かれていて、モデルから見れば基準に反していなかった。

再計画の工程は、言葉で絞る方法を繰り返さないと決め、2 案を比べた。

| 案 | ノード数 | ノードが増えない最長の時間 | 要点のある話題 |
|---|---|---|---|
| A: 1 つの議題の下の要点は 3 つまで。超えたら近い要点に統合する | 62・64 | 4.1 分 | 9/9 |
| B: ノード数が経過時間に比例した数を超えたら、要点を足さない | 56・60 | 6.1・5.6 分 | 6/9・9/9 |

B は数が少ないが、話題が 5〜7 分続く会議では、早くに頭打ちになって空白ができた。A を採った。

**言葉の基準が効かないのは、モデルが基準を守ったうえで、なお多いときがある。そのときは、言葉を強めるより、数で区切る。** 区切り方は、何を損なうか（ここでは空白の長さ）で比べる。

### 3. 評価の分母を、評価される側の出力から取らない

「話題ごとに要点が 1 つ以上あるか」を、最初はマップの議題を分母にして数えていた。テストのレビューが、これでは話題が丸ごと落ちても満点になると差し戻した。議題として立たなかった話題は、分母からも消えるからだ。

文字起こしの側に「あるべき話題」を定義して、分母にした。1 回目の直しは、要点の祖先にどれか 1 つ議題があれば成立と数えていて、別の話題の発言を 1 件だけ根拠に持つ議題でも数えてしまった。修正の検証の工程が差し戻し、議題ごとに、配下のノードの根拠の発言を多数決で分類して、対応する話題を決める形にした。

直した数え方で測り直すと、変更前のマップは、9 つの話題のうち 2 つを実際に落としていた。古い数え方では見えなかった。

**評価の正解は、生成物とは独立に、入力の側に持たせる。** 数え方を直したら、わざと話題を消したマップで点が下がることを確かめる。

### 4. 合成した会議が、実際の会議の症状を再現しているかを先に確かめる

評価のために合成した共有型の会議（約 10 分）では、変更前でも noop の割合は 30〜48%、空白は 3.2 分以下だった。実会議の 81%・10 分近くの空白は再現していなかった。直したかった症状が合成データで弱いと、改善の幅も小さく見える。今回の評価で差がはっきり出たのは、約 60 分の会議を合成し直してからだった。

**合成データで直し方を比べる前に、変更前の数字で、元の症状が出ているかを確かめる。**

## 遅い CI でだけ毎回違うテストが落ちたのを、つないだ直後のメッセージの取りこぼしまでたどった話

前のエントリの PR の CI が落ちた。調べると、その前にマージした 2 件の後から、main の CI も赤くなっていた。2 件とも、PR の時点では CI が通っていた。原因は、サーバーが音声認識のヘルパーに WebSocket でつないだ直後のイベントを、受け取る準備の前に取りこぼすことだった。

- 修正: [ヘルパーにつないだ直後のイベントを取りこぼさない](https://github.com/daiki-beppu/live-mindmap/pull/103)

### 1. マージした後の main の CI も見る

PR の CI が通ってもマージ後の main で落ちたのは、落ち方が毎回違ったからだ。1 回目は「途中結果が字幕として届く」テスト、2 回目は「終了後もマップが残る」テスト、3 回目は別の 2 件が落ちた。ローカルでは 3 回流して 3 回とも通った。PR ごとに 1 回しか流さないと、運よく通った回でマージしてしまう。今回は、次の PR が落ちるまで、main が赤いことに気づかなかった。

**PR の CI だけでなく、マージ後の main の CI の結果も確かめる。** 落ちるテストが毎回違うなら、テストの書き方ではなく、共通の前提を疑う。

### 2. `await` で接続を待ってから購読すると、その隙間に届いたメッセージが消える

落ちたテストに共通していたのは、テスト用の偽のヘルパーが、接続を受けた直後にイベントを全部送ることだった。サーバーの側は、接続の完了（`open`）を `await` してから、メッセージの受け取りを始めていた。

```ts
const ws = new WebSocket(url);
await new Promise((resolve) => ws.once("open", resolve));
ws.on("message", onMessage); // ここより前に届いたメッセージは誰も受け取らない
```

WebSocket のライブラリ（ws）は、ハンドシェイクの応答と同じ塊で届いたフレームを、`open` を出した直後に `process.nextTick` で流す。Node では、`process.nextTick` の処理が Promise の継続より先に走る。そのため、`await` の続きで購読を始める前に、メッセージが流れて消える。遅い CI では、応答とイベントが同じ塊で届きやすい。

推測を確かめるため、ハンドシェイクの応答と 2 つのフレームを 1 回の書き込みで返すサーバーを作った。上の書き方で受け取れたのは 0 件だった。

接続を作った時点からメッセージをためておき、購読を始めたときに、ためた分を届いた順に先に渡す形にした。同じサーバーで、2 件とも受け取れることをテストで固定した。

**接続のイベントを `await` してから購読する書き方は、その隙間に届くものを落とす。購読は接続を作った時点で始める。** 本番のヘルパーでも、接続の直後に話し始めていれば、最初の発言が落ちていた。

### 3. 偽物がイベントを送る時機は、本物より厳しい側に寄せる

偽のヘルパーが接続直後にイベントを全部送る作りは、前のエントリの実装の工程でも気づかれていた。「発言を出した後に届く確定結果」の場面を作れず、遅れて送るイベントを足して対応していた。そのときは「テストが書きにくい」という問題として扱われ、取りこぼしの問題には結びつかなかった。

本物のヘルパーは、モデルの準備に時間がかかり、接続直後にイベントを送ることは少ない。偽物のほうが厳しい時機で送っていたので、取りこぼしが表に出た。

**偽物の時機が本物と違うと気づいたら、テストの書きにくさとしてだけでなく、本物でも起こり得るかを考える。**

## 直した 2 つを合成音声のデモで確かめ、効いた直しと効かなかった直しを見分けた話

この日に入れた 2 つの直し（決めごとのない会議で話を残す直しと、確定を待たずに途中結果を発言にする直し）を、合成音声の会議で動かし、画面を録画して確かめたときの学び。会議は 96 秒・17 発言で、手書きメモアプリの紹介、朝の散歩の体験談、本のおすすめ、質疑が続き、最後に決定 1 件と TODO 1 件が入る。文と文の間は 0.3 秒にした。スピーカーで流したので、相手の声は自分のマイクにも入る。

- 決定の記録: [要点の色をスレートグレーにする](https://github.com/daiki-beppu/live-mindmap/pull/105)、[スピーカーで聞くとき、漏れた相手の声が自分の字幕に出る](https://github.com/daiki-beppu/live-mindmap/issues/106)

### 1. 直しが効いたかは、直しが前提にした条件をデモに入れて確かめる

紹介・体験談・おすすめは、3 つとも**要点**（議題の中で共有された中身を表すノード）として残った。差分更新は 7 回呼ばれ、マップを変えなかったのは最後の「それでいきましょう」の 1 回だけだった。前日の実会議では 350 回中 285 回がマップを変えていなかった。こちらの直しは効いた。

一方、確定を待たない直しは、ほとんど効かなかった。台本の各行の話し終わりから数えると、次のとおりだった。

| | 話し終わり → 発言 | 話し終わり → マップに反映 |
|---|---|---|
| p50 | 7.1 秒 | 10.3 秒 |
| 最大 | 17.6 秒 | 21.6 秒 |

相手の発言 8 件のうち、途中結果から出たのは 2 件だけだった。残りは、確定結果が 2〜4 文ぶんまとめて届いた。この直しは「途中結果が 1 秒変わらなければ」出す。文の間が 0.3 秒だと、話し続けているあいだ途中結果が更新され続け、1 秒止まる瞬間が来ない。調査の段階で、短い文が続く音声では縮まないと測れていた（[1 つ目のエントリ](#stt-finalization-latency) の 3 節の表）。直しの効果として目立って紹介されていたのは、6 つの場面の平均的な数字のほうだった。

**直しを確かめるデモは、直しが働く条件と働かない条件の両方を含める。** 調査で「この条件では効かない」と出ていたら、その条件をデモにそのまま入れる。実会議の話し方はこちらに近い。

### 2. 種別の色は、数が多いものほど引かせる

新しく足した要点は、鮮やかなピンクだった。デモでは 9 ノード中 3 つが要点で、マップ全体がピンクに見え、決定や TODO が埋もれた。

色を決めるとき、2 つのことを基準にした。

- 要点は、数が一番多く、会議のあとで行動や判断につながらない。少なくて大事な決定・TODO・論点ほど鮮やかにし、要点は一番引かせる
- 色相の空きがほとんど無い。青・黄・赤・紫・緑・青緑が使われ、残りの水色・黄緑・藍は隣の色と見分けにくい。新しい色相を探すより、色相を持たないグレーにする

候補は 3 つにした。ほかの種別は Tailwind の色見本の 500 番で揃っていたので、スレートグレーとストーン（温かいグレー）は 1 段薄い 400 番にした。くすんだローズは、ピンクの系統を残して彩度を落とした。利用者がスレートグレーを選んだ。

候補を比べるのに、コードは変えなかった。開いているマップのページの中で、要点の色の値だけを書き換えて撮った。色はノードの CSS 変数（`--kind-color: #ec4899`）と、線の `stroke: rgb(236, 72, 153)` の 2 か所にあり、16 進と rgb の両方の書き方を置き換える必要があった。

**見た目の候補は、動いている画面の値を書き換えて並べる。** ビルドも、データの作り直しも要らない。

### 3. 画面の撮影は、前面にある窓ではなくページを撮る

候補を並べる画像を、最初は OS の画面撮影で撮った。ところが、撮った瞬間に前面にあったのはブラウザではなく、別の作業をしていたアプリの窓だった。4 枚とも、関係のない作業の画面が写っていた。送る前に気づいて消し、ブラウザの DevTools でページそのものを撮り直した。

**人に渡す画像は、OS の画面撮影ではなく、対象のページや要素を指定して撮る。** 画面撮影は、その瞬間に前面にあるものを何でも写す。送る前に、1 枚は必ず自分で見る。

### 4. 受け取る側だけある仕組みは、送る側を探すと穴が見つかる

デモで、相手の声が自分の字幕にも出ていた。字幕は、音声認識の途中結果から作る。スピーカーから漏れた相手の声には、確定結果のほうでは重複の印が付く。

サーバーを読むと、途中結果に重複の印が付いていれば、そのトラックの字幕を空にする処理が、前からあった。ところが、音声認識のヘルパーを読むと、途中結果に印を付ける処理はどこにも無かった。自分の途中結果は、判定を通さずにそのまま流していた。受け取る側だけが作られ、送る側が無かった。受け取る側の単体テストは、印の付いた入力を自分で作って渡すので、通っていた。

直しの issue には、ヘルパーのイベントからサーバーの字幕までを通しで確かめるテストを、受け入れ基準として入れた。

**ある値を読む処理を見つけたら、その値を書く処理がどこにあるかも探す。** 読む側の単体テストだけでは、書く側が無いことに気づけない。

### 5. 起動したツールが別のアプリを操作すると、録画の画面に許可のダイアログが出る

これまで、デモの音声は QuickTime で流し、AppleScript で再生していた。今回は、コーディング用エージェントを別のアプリの中から動かしていた。AppleScript でブラウザやファインダーを操作すると、macOS の「このアプリが別のアプリを操作する許可」のダイアログが出て、処理が止まった。ダイアログは録画の画面にも映る。

許可を与えるかは利用者の判断なので、許可は押さなかった。代わりに、すでにつながっていたブラウザの DevTools で、音声ファイルを裏のタブで開いた。ブラウザの音声として認識でき、別のアプリを操作する許可も要らなかった。

**デモの段取りは、新しい許可を要らない経路で組む。** 操作する側のアプリが変わると、前に通った手順でも許可を求められる。
