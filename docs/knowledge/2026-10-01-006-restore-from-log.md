# サーバーが落ちても、ログを流し直して直前のマインドマップに戻す機能を作った話

live-mindmap（会議の音声から、AI がマインドマップを差分更新し続ける Web アプリ）の開発で、**ログからの復元**を作ったときの学び。ログからの復元とは、サーバーが落ちて再起動したときに、ログに残ったイベントを順に流し直し、落ちる直前のマップに戻すことをいう。LLM は呼び直さない。実装は、AI エージェントのワークフロー実行ツール takt に任せた。takt は計画・テスト作成・実装・複数観点のレビュー・指摘の採否判断・修正を順に回し、途中経過をレポートのファイルに残す。この記事は、そのレポートと差分を読み直して書いた。

- 決定の記録: [ログからの復元](https://github.com/daiki-beppu/live-mindmap/issues/40)、[ADR 0003 ローカルの Node サーバーがパイプラインを持つ](../adr/0003-local-node-server-owns-pipeline.md)
- 用語集: [`CONTEXT.md`](../../CONTEXT.md)（発言・差分操作・セッションの語彙）
- 前の記事: [LLM がマップを差分更新する中核を、テストファーストで本実装した話](./2026-10-01-002-core-module-tdd.md)

前提として、次のものがすでにあった。

- マップは会議をルートとする木。AI は毎回作り直さず、既存のマップへの**差分操作**（追加・更新・統合・移動・削除・何もしない）を返す
- **セッション**（1 つの会議を追う一続きの作業）は、イベントをログ（JSONL）に追記する。イベントは 2 種類で、`remark`（**発言**＝STT が確定させた 10〜15 秒程度の文字起こしの 1 区切りを受け取った）と `diff`（差分更新の入力の要約・返ってきた操作・捨てた操作・エラー）
- 差分操作を検証して適用する純粋関数 `applyOps` が、新しいノードに `n1`、`n2`… と ID を振る
- 受入条件は 4 つ。「再起動時にログのイベントを順に適用関数へ流してマップを戻す」「復元では LLM を呼ばない」「知らない種類のイベントは読み飛ばせる」「復元したマップが元と一致する（ノードの ID を含む）」

## 1. 復元に要る情報がログに全部あるかを、書く前に棚卸しする

計画の段階で、受入条件の「元のマップと一致する」を、一致させるべき項目に分解した。ノードの ID・親・種別・本文・根拠・状態に加えて、**ルートの本文**（会議のタイトル）も一致しなければならない。ところが、既存のログにタイトルは無かった。タイトルは文字起こしのファイル名から作っていて、ログにもどこにも残っていなかった。

候補は 3 つあった。

| 案 | 採否 | 理由 |
| --- | --- | --- |
| セッションの開始時に `{ type: "start", title }` を最初のイベントとして書く | 採用 | ログだけで戻せる |
| タイトルを書き出し済みの `export.json` から読む | 不採用 | ログだけからの復元にならない |
| ルートの本文を空文字で補う | 不採用 | 元と一致しない |

`start` が無いログはエラーにした。ルートの本文を推測で埋めると、一致しないマップが黙って出来上がる。

一方、ノードの ID はログに書き足さなくても戻せた。`applyOps` の採番は、初期のマップ・操作の列・処理済みの発言の集合が同じなら同じ ID になる。ID を保存するより、採番が決定的であることを確かめるほうが安い。

**イベントソーシング（状態を、起きたことの記録から組み立て直す方式）で復元を作るときは、最初に「一致させるべき項目」を並べ、それぞれがログから導けるかを確かめる**。抜けは、ログの形を決めた時点では気づきにくい。

## 2. 復元では記録された結果を信用せず、元と同じ順で適用関数を通し直す

ログの `diff` には、捨てた操作とその理由まで残っている。これを使えば、適用関数を通さずに結果を組み立てられそうに見える。しかし受入条件は「適用関数へ流す」と言っており、近道は採らなかった。

注意が要ったのは、適用関数が見る「処理済みの発言の集合」だ。根拠の検証（根拠に指定できるのは差分更新に渡した発言だけ）と採番は、この集合に左右される。元のセッションは、差分更新を**呼ぶ前に**渡す発言を集合に加えていた。呼び出しが失敗した回も加わっている。復元でも、`error` 付きの `diff` を含めて、同じ順で加えてから `applyOps` を呼ぶ。

```ts
case "diff": {
  if (!map) throw new Error("ログの diff より前に start がありません");
  for (const id of e.input.fresh) {
    const r = remarks.find((x) => x.id === id);
    if (!r) throw new Error(`ログに発言がありません: ${id}`);
    known.add(id);
    processed.push(r);
  }
  map = applyOps(map, e.ops, known).map;
  break;
}
```

テストの元になるセッションには、すべての種類の操作・捨てられる操作・差分更新の失敗・重複の印（スピーカーの音を自分のマイクが二重に拾った発言に付ける印）の付いた発言を、わざと起こさせた。そのうえで、ログを JSON に書いて読み直した形で復元し、`snapshot()`（その時点のマップ全体）を `toEqual` で比べる。実装の `known.add` を消すと、復元のテストが 4 本落ちることも確かめた。

**ログから状態を戻すときは、記録された結果ではなく、適用関数が見ていた入力を元と同じ順で組み立て直す**。失敗した回の副作用も、入力の一部になる。

## 3. 復元の結果は「止まったマップ」ではなく、続きを受け取れるセッションで返す

マップだけを戻せば、受入条件は満たせる。しかし、再起動の後も会議は続く。そこで、既存の `createSession` を、開始のイベントを書く部分と、状態を受け取ってセッションを組み立てる `openSession` に分けた。`restoreSession` はログから状態を組み立てて、同じ `openSession` に渡す。

戻す状態はマップだけではない。

- 受け取ったすべての発言（重複の印つきも含む）
- 差分更新に渡した発言（直前の発言として、最後の 3 つを次の呼び出しに渡すため）
- まだ渡していない発言（重複の印がなく、どの `diff` の入力にも含まれない発言）

最後のものの扱いが分かれ目だった。復元の終わりにすぐ差分更新を呼ぶと「復元では LLM を呼ばない」に反する。捨てると、会議の最後の発言を取りこぼす。たまった発言として戻しておき、次の発言が来たときに一緒に流すことにした。

テストでは、元のセッションをそのまま続けた場合と、途中で落として復元してから続けた場合で、次の差分更新に渡る入力（直前の発言・新しい発言・マップ）が `toEqual` で一致することを確かめた。

**復元の正しさは、戻した状態の見た目ではなく、「落ちなかった場合と同じ次の一手になるか」で確かめる**。

## 4. 読み飛ばすのは「読めて、種類を知らない行」だけにし、壊れた行では止める

「知らない種類のイベントを読み飛ばせる」は、後でイベントの種類を足すための条件だ。これを「読めないものは全部飛ばす」と広げると、ログの欠けに気づかないまま違うマップが出来上がる。

そこで、2 つを分けた。

- JSON として読めて、`type` が知らない値の行 → 読み飛ばす
- JSON として読めない行 → `log.jsonl の 2 行目が JSON として読めません` のように、行番号付きのエラーにする

読み飛ばしのテストには、知っている種類のフィールド名を持つ未知のイベントも混ぜた。`{ type: "future", remark: {…}, ops: [{ op: "delete", … }] }` のような行だ。`remark` や `ops` という欄があるかで解釈する実装なら、これを誤って適用してしまう。判別は `type` だけで行う。

**前方互換のための読み飛ばしは「種類を知らない」に限り、「形が壊れている」とは区別する**。

## 5. 生成の途中でイベントを書くようにすると、コールバックが戻り値より先に呼ばれる

`createSession` が開始のイベントを書くようにすると、既存の CLI が壊れることを、計画の段階で見つけていた。CLI はログのコールバックの中で、作ったセッションを参照してエクスポートを書き出していた。

```ts
// 変更前の CLI（要点だけ抜き出したもの）
const session = createSession({
  title, updater,
  log: (event) => {
    appendFileSync(logPath, JSON.stringify(event) + "\n");
    writeFileSync(exportPath, JSON.stringify(session.exportJson())); // start の時点では session がまだ無い
  },
});
```

`start` は `createSession` の中で書かれるので、`session` に代入される前にコールバックが走る。ログへの追記は常に行い、エクスポートの書き出しは代入の後だけにした。

**ファクトリの中でコールバックを呼ぶようにしたら、呼び出し側のコールバックが戻り値を参照していないかを確かめる**。外から見える関数の形は変わらないので、型チェックでは気づけない。

## 6. 理由を指定しない「例外が出ること」のテストは、実装が無くても通る

テストを先に書いた段階で、新しいテストのうち 10 本が想定どおり落ち、18 本が通った。通ったものの中に、「`start` が無いログはエラーにする」のテストがあった。

```ts
expect(() => restoreSession(withoutStart, options)).toThrow();
```

このとき `restoreSession` はまだ存在せず、呼ぶと `TypeError`（関数ではない）が出る。`toThrow()` は理由を問わないので、それで通っていた。テストを書いた側がこれを申し送り、実装の後に、意図したエラー文で例外が出ることをコードで確かめた。ほかのテストも、実装を 1 か所壊して落ちることを確かめている。

| 壊した箇所 | 結果 |
| --- | --- |
| 復元で処理済みの発言を集合に加える `known.add` を消す | 復元のテストが 4 本落ちる |
| 最新のセッションを選ぶ `.at(-1)` を `.at(0)`（最古）にする | 複数セッションのテストが落ちる |

**赤を経ずに緑になったテストは、何が投げられて通ったのかを確かめる**。例外のテストは、エラー文か型まで指定しておくと、この取り違えが起きない。

## 7. レビューの指摘は、守る契約が受入条件から来ているかで採否を分ける

実装の後、アーキテクチャ・テスト・コーディング・AI 特有の書き癖の 4 観点で、並行してレビューさせた。差し戻しは 2 件あった。

| 指摘 | 採否 | 理由 |
| --- | --- | --- |
| ログを持つ最新のセッションを選ぶ処理に、セッションが複数あるときのテストが無い | 採用 | 「進行中だったセッションのログを読む」という受入条件そのもの。今回、選ぶ処理を `export` と共用の関数に抜き出したことで生まれた、まだ誰も確かめていない契約だった |
| ログ全体を一度に読み込んでいる。長い会議でメモリを超えうるので、1 行ずつ流すべき | 不採用 | 復元したセッションは、エクスポートのためにすべての発言を持ち続ける。読み込みを 1 行ずつにしても、全体を持つことは避けられない。受入条件にもない |

1 件目は、テストだけを足して直した。新旧 2 つのセッションを作って新しい方が選ばれることと、ログの無い、より新しいフォルダがあっても飛ばされることを確かめる 2 本だ。

2 件目の指摘は、事実としては正しい。しかし採用すると、元の要求に無い「ログがメモリを超えても復元できる」という契約を新しく背負うことになる。

**「直すべきか」は指摘の正しさではなく、守ろうとしている契約がどこから来たかで決める**。共通の関数に抜き出したときは、呼び出し元ごとの契約が、それぞれテストされているかを見直す。

## 8. エージェントのワークフローは、途中経過をファイルに残しておくと、止まっても続きから回せる

最初の実行は、計画から修正まで進んだところで、使っていたコーディングエージェントの利用上限に当たって止まった。直後に 2 回再実行したが、どちらも 5 秒ほどで同じ理由で止まった。上限が戻るまで約 30 分待ち、修正の検証から再開した。

| 実行 | 時間 | 進んだところ |
| --- | --- | --- |
| 1 回目 | 約 29 分 | 計画 → テスト作成 → 実装 → レビュー 4 観点（ここだけで約 15 分）→ 指摘の採否 → 修正 → 修正の検証で停止 |
| 2・3 回目 | 各約 5 秒 | 利用上限のまま、すぐ停止 |
| 4 回目 | 約 9 分 | 修正の検証 → レビュー 5 観点（セキュリティを追加）→ 指摘の採否 → 最終確認で完了 |

再開できたのは、各段の結果（計画・テストの対応表・決定の記録・レビュー・採否）がレポートのファイルとして残っていて、次の段がそれを入力に読むからだ。止まって失ったのは待ち時間だけで、やり直した段はなかった。この記事の「判断が変わった瞬間」も、すべてこのレポートから拾えた。

**エージェントに長い手順を任せるときは、段ごとの結果を会話ではなくファイルに残させる**。利用上限で止まったときは、すぐに再実行せず、上限が戻るのを待ってから続きを回す。
