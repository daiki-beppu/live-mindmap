# LLM にマインドマップを差分更新させるプロンプトと、System One モデルの前段ゲートを実測した話

live-mindmap（会議の音声から、AI がマインドマップを差分更新し続ける Web アプリ）の開発で、差分更新エンジン（文字起こしを受け取り、既存のマップへの変更を LLM に出させる部分）を試作したときの学び。公開会議の録音 2 本（収束型のファシリテーター会議・発散型のアプリブレスト、各 60 分）を時間順に再生し、Claude Sonnet 5.5 に差分操作を出させて、マップの形・コスト・遅延を測った。あわせて、Claude の手前に System One モデル（選択肢から選ぶだけで文章を生成しない判断専用モデル）の Jev を置く案も試した。

- 決定の記録: [差分更新エンジン：操作スキーマ・プロンプト・更新タイミング](https://github.com/daiki-beppu/live-mindmap/issues/6)
- 用語集: [`CONTEXT.md`](../../CONTEXT.md)（ノード種別と差分操作の語彙）
- 前の記事: [LLM が差分更新するマインドマップの語彙を、「LLM が迷わない」基準で決めた話](./2026-09-30-002-map-domain-model-for-llm.md)

## 1. LLM には操作だけを出させ、規則の検証はマップ側で行う

LLM に毎回マップを作り直させると、ノードの id が変わって表示がちらつき、根拠（ノードの元になった発言）の対応も崩れる。そこで、既存のマップへの**差分操作**だけを返させた。操作は 6 種類で、`追加・更新・統合・移動・削除・何もしない`。構造化出力の JSON スキーマで、操作ごとの形を anyOf で縛った。

```text
{ ops: [
  { op: "add", ref: "a1", parent: "n3", kind: "論点", text: "…", evidence: ["s41"] },
  { op: "add", ref: "a2", parent: "a1", kind: "決定", text: "…", evidence: ["s42"] },   // 同じ応答で作った a1 を親にできる
  { op: "update", node: "n7", evidence: ["s43"] },
  { op: "noop", reason: "進行の段取りだけ" }
] }
```

受け取った操作は、マップ側の純粋な関数で 1 つずつ検証してから適用する。決定の親は論点に限る、決定と TODO は子を持たない、削除は子のないノードだけ、統合は同じ種別どうし、根拠は既に届いた発言だけ、といった規則を、プロンプトではなくコードで守らせる。

約 800 回の呼び出しで、規則違反は 2 件だった（空のマップで、存在しない親 `n1` を指定した）。プロンプトに「ルートの id は root」と 1 行足して消えた。**スキーマで形を縛り、規則はコードで弾き、弾いた理由を記録する**。この分担にすると、プロンプトは「何をどこに置くか」の判断に集中できる。

ただし、仮 id（`ref`）で同じ応答内の追加を親にできる設計には裏がある。先頭の追加が弾かれると、それを親にした後続の追加も連鎖して落ちる。

## 2. Agent SDK で試作するなら、まずユーザー設定の読み込みを切る

試作は Claude のサブスクリプションから呼ぶため、Claude Agent SDK を使った（API キーではなく Claude Code の認証で動く）。最初の 1 回は、20 トークンの入力に対して 16 万トークンのキャッシュが作られ、概算 $0.18・19 秒かかった。原因は、手元の Claude Code に入れていたプラグイン・MCP サーバー・スキルの定義が、毎回の前置きとして読み込まれていたことだった。

```ts
query({ prompt, options: {
  model: "claude-sonnet-5-5", systemPrompt: SYSTEM,
  tools: [], settingSources: [], persistSession: false,
  mcpServers: {}, strictMcpConfig: true, plugins: [], skills: [], agents: {},   // これを足すまで前置きが 16 万トークン
  outputFormat: { type: "json_schema", schema: SCHEMA },
}})
```

`settingSources: []` だけでは消えず、プラグイン・スキル・MCP を明示的に空にして、**1 回 $0.004・4 秒**になった。なお、SDK が返す費用は API の定価で見積もった値で、サブスク経由なら請求額ではない。構造化出力は内部で「StructuredOutput ツールの呼び出し → 結果」の 2 ターンになるので、API を直接呼ぶ本番より遅く高めに出る。

## 3. 操作の定義の一文が、マップの形を決める

同じ会議を、プロンプトだけ変えて 3 回流した（2 発言ごとに呼び出し、60 分）。

| | ノード数 | 本文の長さ p90 / 最大 | 深さ | 決定 / TODO | 概算費用 |
| --- | --- | --- | --- | --- | --- |
| v1 | 52 | 119 / 427 字 | 5 | 4 / 1 | $1.85 |
| v2 | 103 | 33 / 42 字 | 9 | 2 / 0 | $1.91 |
| v3 | 38 | 37 / 45 字 | 4 | 3 / 1 | $1.39 |

- **v1**: 用語集に書いた「同じ話題に戻ったときの続きも更新で表す」をそのままプロンプトに入れた。Claude はこれを「本文への追記」と読み、1 つの課題に 10 分ぶんの議論を書き足し続けた。1 ノードが 427 字、1 つの論点の直下に課題が 20 個並んだ
- **v2**: 本文を 40 字以内にし、「続きは本文に書き足さず子ノードにする」とした。今度は「課題の子の課題の子の課題…」と 9 段まで掘り下がり、ノードが倍増した。「本文に書き足さない」を「更新しない」と受け取り、更新が 28 回から 2 回に減った。決定と TODO も案として置かれた
- **v3**: 子にするのは**親と別の主張**（別の理由・懸念・派生した案）のときだけ、言い換えや具体例は根拠を足す更新にとどめる、と基準を言葉にした。決定と TODO は「〜を基準にする」「〜さんが〜する」のような言い方の例を添えた

v1 と v2 は、同じ緊張関係の両端だった。「同じ話題の続きをどこに置くか」を本文に寄せると肥大化し、子に寄せると増殖する。**操作の意味を 1 文変えるだけで、マップの形は振り子のように揺れる**。中間に止めるには、「どちらにするか」ではなく「何を基準に分けるか」を書く必要があった。

この結果に合わせて、用語集の「更新」も「本文を言い直す（書き足さず全文を置き換える）」に直した。

## 4. LLM には、マップ全体の予算を毎回見せる

v3 で一番効いたのは、毎回のプロンプトの先頭に足した 1 行だった。

```text
## マップの状態
経過 23 分・ノード 31・最大の深さ 4（目安: 60 分で 50 前後、深さ 4 まで）
```

各呼び出しで Claude が見ているのは「新しい 2 発言」なので、マップ全体がどれだけ膨らんだかを意識できない。予算に対する現在地が見えるようになると、新しいノードを足す代わりに既存ノードの更新を選ぶようになった（更新 2 回 → 31 回）。人が会議メモを取るときの「もう書きすぎたな」という感覚を、数字で渡している。

ノードが減ったぶん、毎回渡すマップのアウトラインも小さくなり、費用も 25% 下がった。

## 5. 後から組み替える操作は、指示しても使われない

v2 と v3 には「1 つの親の下に同じ種別が 6 つを超えそうなら、論点を立てて移動で束ねる」と書いたが、移動と統合は 2 本の会議を通して**一度も出なかった**。v3 でも、最初の論点の直下には課題が 11 個並んだ。

各呼び出しは「新しい発言をどう載せるか」に注意が向いていて、既存の構造を見直す動機がない。組み替えを効かせたいなら、数分おきに「整理だけをする呼び出し」を別に挟むのがよさそうだ。操作の種類を定義しても、それを使う場面を作らなければ使われない。

## 6. 構造化出力では、小さいモデルほど遅く高くなることがある

Haiku 4.5 でも同じ条件で流したところ、1 回 40〜70 秒かかり、費用は Sonnet 5.5 の約 4 倍になった。anyOf の入った JSON スキーマの検証に落ちて、SDK の中で再試行を繰り返していたと見ている。会議の 23 分目で打ち切った。

「安いモデルで回数を稼ぐ」は、出力の形が複雑だと成り立たない。モデルの単価ではなく、**完了した 1 回あたりの費用と時間**で比べる必要がある。

## 7. 反映の遅れは、発言の長さと呼び出しの間隔で決まる

発言（STT が返す文字起こしの 1 区切り）が終わってから、それがマップに載るまでの遅れを、呼び出しの間隔ごとに測った（ファシリテーター会議、Sonnet 5.5）。

| 呼び出しの間隔 | 発言が終わってから反映まで p50 / p95 | 話し始めてから反映まで p50 / p95 | 概算費用 / 60 分 |
| --- | --- | --- | --- |
| 1 発言ごと | 2.9 / 4.0 秒 | 20 / 32 秒 | $3.97 |
| 2 発言ごと | 10.6 / 30.6 秒 | 28 / 51 秒 | $1.85 |
| 4 発言ごと | 28.6 / 68.1 秒 | 46 / 89 秒 | $0.99 |

Claude の応答自体は約 3 秒で、間隔を変えてもほぼ変わらない。遅れの大半は、**発言そのものの長さ**（このサンプルでは平均 13〜17 秒）と、**次の発言が来るまで待つ時間**から来ている。リアルタイム性を上げたいなら、LLM を速くするより、発言を短く区切るか、呼び出しの間隔を詰めるのが先になる。間隔を半分にすると、費用はほぼ倍になる。

## 8. System One モデルの精度は、質問の設計で決まる

Jev（TypeSafe AI）は、状態（テキスト）と型付きの質問（yes/no・選択・スコア）を送ると、選択肢ごとの確率を約 0.2 秒で返す。これを Claude の手前に置き、発言ごとに「中身があるか」を判定して、雑談なら Claude を呼ばずに捨てるゲートを試した。

正解ラベルには、Claude を 1 発言ごとに呼んだランを使った。発言ごとに「マップを変えたか」が分かっているので、ゲートの判定と突き合わせられる（ラベルは人の判断ではなく Sonnet の判断なので、「Sonnet と同じ判断を安くできるか」の評価になる）。

最初の設計では、直前の 3 発言と新しい発言の文面だけを渡し、「会議の中身を述べているか」を yes/no で聞いた。収束型の会議では、冒頭の解説員の前置きをきれいに捨てた（捨てる 24%、取りこぼし 1%）。ところが**発散型のブレストでは、アイデアの 45% を雑談と判定して捨てた**。おバカアプリのアイデアは、会議の目的を知らずに文面だけ読めば冗談にしか見えない。

一度は「System One モデルは文脈に依存する判断に弱い」と結論づけかけた。だが、同じデータで別の質問（次の節の「どのノードの話か」）の結果を見ると、取りこぼしは 7% だった。**同じモデル・同じ発言でも、質問の立て方で 45% と 7% に分かれた**。失敗の主因はモデルではなく、質問の構造だった。

まず、判断に要る文脈を状態に入れ、判断の基準を選択肢の側に書き出した。

- 状態に**会議の目的**（「おバカなアプリのアイデアを 1 人ずつ発表し、周りが突っ込むブレスト会議」）と**現在のマップ**を入れる
- 「中身があるか」の yes/no をやめ、**役割を 8 択**で選ばせる（新しい案・課題・問い・決定・TODO・既存の話の補足・進行・雑談）

「中身があるか」は判断の基準をモデルに丸投げする質問で、8 択は基準を選択肢の側に書き出す質問になっている。これだけで、ブレストの役割の分布は「案」71 件、ファシリテーター会議は「補足」100 件・「課題」25 件と、会議の性質どおりになった。**System One モデルでは、質問の設計がそのままプロンプトエンジニアリングになる**。

一方、「話題が切り替わったか」は、どの設計でも判定できなかった。yes/no で聞くと確率が 0.18〜0.40 に固まり、関係するノードの変化から導くと 196 発言中 129 回も「切り替わり」になった。

## 9. ゲートには「拾うもの」ではなく「捨ててよいもの」を、マップに照らして判定させる

取りこぼしを 45% から 1〜2% まで下げたのは、質問の構造を 2 つの軸で反転させたことだった。

**1 つ目の反転: 発言を単体で判定するのをやめ、マップに照らして判定させる。** 「この発言は会議の中身か」という絶対的な問いは、会議の目的を知らないと答えられない。代わりに、選択肢にマップの全ノードと「どれにも関係しない」を並べ、「この発言はどのノードの話か」と聞いた。問いが「中身かどうか」から「既にある議論のどこに当たるか」に変わると、モデルは発言の文面と各ノードの本文を突き合わせるだけで済む。この質問は、Claude が実際に更新したノードとの一致が 86% で、それ自体が次の節の仮表示の材料にもなった。

**2 つ目の反転: 「拾う判定」をやめ、「捨てる判定」にする。** 最初の設計は「中身の確率が閾値より低ければ捨てる」、つまり**迷ったら捨てる**だった。これを、「役割が進行か雑談」**かつ**「どのノードにも関係しない」の両方が成り立つときだけ捨てる、**迷ったら通す**に変えた。

| 捨てる条件 | 収束型 捨てる / 取りこぼし | 発散型 捨てる / 取りこぼし |
| --- | --- | --- |
| 迷ったら捨てる: 文面だけで「中身があるか」< 0.3 | 24% / 1% | 61% / 45% |
| マップに照らす: どのノードにも関係しない | 18% / 1% | 20% / 6% |
| 役割で判定: 進行・雑談 | 29% / 5% | 29% / 5% |
| **迷ったら通す: 進行・雑談 かつ どのノードにも関係しない** | **14% / 1%** | **18% / 2%** |

反転させた理由は、誤りの重さが非対称だからだ。雑談を通してしまった場合の損失は、Claude の呼び出し 1 回ぶん（約 $0.01）で、Claude が「何もしない」を返せば済む。決定や TODO を捨ててしまった場合は、その発言はマップに二度と載らない。**高い処理の手前に置くフィルターは、既定を「通す」にして、捨てるには独立した 2 つの根拠を要求する**。2 つの質問は別々の観点（発言の役割と、マップとの関係）なので、片方の誤判定をもう片方が打ち消す。

代わりに、捨てられる量は 61% から 18% に減った。この試作では、節約は小さくなっても取りこぼしを減らすほうを取った。会議の種類ごとに閾値を較正しなくても、どちらの会議でも取りこぼしが 1〜2% に収まったのも、この構造の効果になる。

## 10. 前段ゲートの価値は、節約より速さにある

Jev の単価は入力 100 万トークンあたり $0.042（出力は無料）で、状態にマップを入れても 60 分で約 117 万トークン、**約 $0.05** だった。Claude（60 分で約 $1.4〜2）の約 1/40 になる。

それでも、差分更新のゲートとしては MVP に入れなかった。捨てられる発言は 14〜18% で、捨てられるのは前置きや雑談のように、もともと入力が小さい区間になる。60 分で浮くのは $0.3 程度で、反映の遅れも減らない（遅れは 7 節のとおり発言の長さで決まる）。1 発言ごとに呼ぶ（費用が倍になる）ときや、長い会議の費用対策として残した。

代わりに有望だったのは速さのほうだった。「どのノードに関係するか」の答えは、Claude が実際に更新したノードと 86% 一致し、しかも 0.2 秒で返る。Claude の 3 秒と待ち時間を待たずに、該当ノードを「いま話している」と光らせることができる。**0.2 秒と 3 秒という桁の違いは、LLM の手前ではなく、表示の即時フィードバックで活きる**。

## その後: 仮表示は採用され、発言の長さは STT 側で決まった

- 「マップの見せ方」を決めたチケットで、Jev による「いま話している」ノードの仮表示を MVP に入れると決めた。2 発言ごとに Claude を呼ぶ設計の反映待ち（p50 約 11 秒・p95 約 31 秒）を埋めるためで、差分更新の前段ゲートとして使うかは引き続き別の判断にしている（[マップの見せ方：描画ライブラリ選定・ノード種別の表現・更新アニメーション](https://github.com/daiki-beppu/live-mindmap/issues/7)）
- 音声取得と STT を決めたチケットで、STT は Apple の SpeechAnalyzer をストリーミングで使うことになった。発言は STT の確定結果そのもので、長さは p50 8.6〜13.4 秒。確定前の**途中結果**は 0.1 秒以内に届くが、書き換わるので差分更新には使わず、字幕と仮表示にだけ使う。音声の終わりから確定まで p50 6 秒かかり、Claude を足したマップへの反映は p50 18〜22 秒の見込み。7 節の「遅れの大半は発言の長さ」は、本番の STT でもそのまま当てはまった（[リアルタイム音声取得と STT の経路](https://github.com/daiki-beppu/live-mindmap/issues/9)、[ADR 0002](../adr/0002-local-stt-helper.md)）
