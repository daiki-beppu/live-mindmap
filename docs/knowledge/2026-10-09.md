## 過去のセッションから引き継いだ語彙の効き目を測ったら、引き継ぎは上限まで届いていて、低く見えた原因は英字の語の読みの崩れだった話

前のセッションの**語彙**を次のセッションに引き継いだとき、固有名詞の正解率がどこまで上がるかを測ったときの学び。語彙は、会議で話されそうな固有名詞・略語の正しい表記の集まりで、音声認識が崩した語を、発言（確定した文字起こしの 1 単位）にするときに読みで引いて直すのに使う。引き継ぐのは「前のセッションの発言に出た語と、利用者が足した語」だけ、と前のチケットで決めてあった（[過去のセッションを語彙の出どころに残すか決めた話](./2026-10-08.md#past-session-vocab)）。補正の形は、読みの近さで置き換え、ふつうの語の一覧（日本語の上位 5 万語）に載る区間は直さない、というもの（[語彙からふつうの語を除く手段を測った話](./2026-10-08.md#vocab-common-words)）。

- 決定の記録: チケット [過去のセッションから引き継いだ語彙の効き目を測る](https://github.com/daiki-beppu/live-mindmap/issues/526)、地図 [Kanary を手本に字幕の精度を上げる](https://github.com/daiki-beppu/live-mindmap/issues/386)
- 起こしたチケット: [英字の語の読みが FoundationModels で崩れる割合と、別の作り方を測る](https://github.com/daiki-beppu/live-mindmap/issues/577)

素材は、架空の地方スーパーのネットスーパー立ち上げの週次定例を、音声合成で 2 回分作った（各 8 分、同じ 4 人）。1 回目はスライド 6 枚を共有し、2 回目は共有なし。1 回目のスライドを macOS の Vision で OCR し、規則（カタカナ 3 字以上・漢字 3〜12 字・大文字を含む英字の語、と 3 画面以上に出る 2〜4 字の短い行）で語彙を取った。1 回目をその語彙で直し、直した後の発言に出た語だけを 2 回目に引き継いで、2 回目を直した。

| 2 回目に使った語彙 | 語数 | 固有名詞の正解率 | CER |
| --- | --- | --- | --- |
| 補正なし | – | 41.4%（41/99） | 13.6% |
| 引き継いだ語彙（1 回目の発言に出た語だけ） | 24 | 54.5% | 10.2% |
| 絞らずに 1 回目の語彙を全部 | 37 | 54.5% | 10.2% |
| 台本で 2 回とも出る語（引き継ぎで届く上限） | 18 | 54.5% | 10.3% |
| 2 回目の台本の語すべて（語彙で届く上限） | 24 | 74.7% | 4.3% |

置き換えの誤りは、どの行も 0 だった。英字の語の読みは、崩れた語を手で直した値で測っている（3 節）。

### 1. 出どころの効き目は、全体の上限ではなく「その出どころが持ちうる語」の上限と比べる

チケットは「台本の語彙（別の素材で 62.7%→96.8%）や共有画面の OCR の語彙にどれだけ届くか」という問いで立てていた。引き継ぎの 54.5% を台本の語すべての 74.7% と比べると、20 ポイント届いていない。引き継ぎの仕組みに取りこぼしがあるように見える。

上限を 2 つに分けると読み方が変わった。引き継ぎが持ちうるのは「前の回にも出た語」だけなので、台本で 2 回とも出る 18 語を語彙にした値が、引き継ぎの上限になる。これも 54.5% で、引き継ぎはもう上限に届いていた。20 ポイントの差は、2 回目に初めて出る語（新しい SaaS の名前や地名、2 回目の固有名詞の出現 99 回のうち 36 回）の分で、どう引き継いでも直らない。

前の日に「出どころを比べる前に、その素材で正しい語彙なら何点まで上がるかを先に出す」と書いた（[OCR の語彙の効き目を測った話](./2026-10-08.md#ocr-vocab-effect)）。今回はそれをもう一段分けた。素材全体の上限と、出どころが原理的に届く上限は別に出す。素材を作るとき、1 回目と同じ語・新しい語・話にだけ出る語（スライドに無い取引先の人名）を分けて台本に入れておいたので、この分け方がそのまま計算できた。

### 2. 次の段の入力を、その段自身の出力で絞ると、誤りが次の回へ持ち越される

「発言に出た語だけを引き継ぐ」は、使われない語で語彙が膨らまないための決まりだった。絞ると効き目が落ちるかもしれない、と思っていたが、絞らない場合と同じ 54.5% だった。絞って落ちたのは、参加者の名前（小窓の OCR で取れたが、音声認識が「6村」「遠野」のように崩したまま発言に残らなかった）と、スライドの見出しのかけら（先行店舗・審査待など）だった。名前は語彙に入れても 2 回目で直らないので、落としても値は変わらない。

代わりに穴が見えた。「発言に出たか」は補正をかけた後の本文で判定する。補正をかける前の本文で判定すると、「カゴラク」（音声認識は「過ご楽」と書く）のような、直して初めて現れる語が引き継がれない。ところが補正の後で判定すると、誤った置き換えで本文に入った語も「発言に出た語」になる。1 回目では「配達の時間帯→配達時間帯」「夕方の便→夕方便」の 2 件があり、どちらも引き継がれた。2 回目では害が出なかったが、同じ誤りを次の回でも繰り返せる形になっている。

この 2 件は、前の日に仕様へ入れると決めた「語の中のひらがなを落とす置き換えを止める守り」があれば、そもそも入らない。ある段の出力で次の段の入力を選ぶときは、その段の誤りがどう持ち越されるかを先に確かめる。

### 3. 上限が低すぎたら、直らなかった語を 1 つずつ見る。崩れていたのは別の段だった

最初に測ったとき、2 回目の台本の語すべての語彙で 58.6% だった。別の素材では台本の語彙で 95% まで上がっていたので、低すぎる。直らなかった語を見ると、Amplitude（8 回）・Figma（5 回）・Datadog（2 回）が、語彙に入っているのに 1 回も直っていなかった。

原因は英字の語の読みだった。補正は読みで引くので、英字の語には読みが要る。前のチケットで「英字の語の読みは、端末の中の LLM（Apple の FoundationModels）に 1 度だけ聞く」と決めていた。その読みを開くと、新しく聞いた 7 語のうち 3 語が崩れていた。

| 語 | FoundationModels の読み | 音声認識の書き方 |
| --- | --- | --- |
| Amplitude | アスペクト | アンプリチュード |
| Figma | ファイマ | フィグマ |
| Datadog | ダットドッグ | データドッグ |

3 語の読みを手で直すと、台本の語すべての語彙で 74.7% になった。引き継ぎの側にも響いていた。1 回目で Datadog が直らなかったので、「発言に出た語」にならず、引き継がれていなかった。手で直した読みで 1 回目からやり直すと Datadog も引き継がれ、引き継ぎの値は 52.5% から 54.5% に上がった。

引き継ぎの効き目と読みの質が、同じ数字に混ざっていた。読みを手で直した値と直さない値を両方出して、2 つを分けた。読みの作り方は、このチケットの範囲を超えるので、別のチケットに起こした。

### 4. 「OCR は 1 字も崩さない」は、前の素材の語での話だった。珍しい字は崩れる

前の日の測定では、OCR はスライドの名前・店名を 1 字も崩さずに読んだ。それを前提に「OCR は崩れないと仮定して、規則だけを測る」というやり方を取っていた。

今回は「雫石」を一度も正しく読まなかった。会議アプリの右の小窓に出る名前（13px）は 6 画面とも「栗石」、スライドの本文（24px）の「（雫石）」は「雲石」になった。同じ小窓の「鳴海」「六車」「東雲」は崩れていないので、文字の小ささより、「雫」という字の珍しさが効いている。小窓の名前は、繰り返し出る短い行として語彙に入れる決まりなので、誤った表記がそのまま語彙に入る。今回は「栗石」に読みの近い区間が無く、害は出なかった。前の日の素材の語（港南・葛西・野々村など）が崩れなかったのは、ありふれた字だったからで、OCR がいつも崩れないわけではない。

規則の側にも 1 つ穴があった。カタカナを Unicode の範囲（U+30A0〜U+30FF）で取っていて、中黒「・」（U+30FB）がこの範囲に入る。箇条書きの「・パン」や「・ピックナビ」が、中黒ごとカタカナの語として取れた。今回は前後の中黒を外して数えた。仕様では、中黒をカタカナから外す。

### 5. `LC_ALL=C` は `sort` にだけ付ける。`sed` に付けると日本語のバイトを壊す

前の日に、`sort -u` が UTF-8 のロケールで日本語の行をまとめてしまうことにはまり、`LC_ALL=C` を付けて直した。今回はそれを覚えていて、語彙を作るシェルの先頭で `export LC_ALL=C` にした。その後に行頭の中黒を外そうとして、`sed 's/^・*//'` を同じシェルで流した。

C ロケールでは、`・*` の `*` は「・」の 3 バイト（E3 83 BB）の最後の 1 バイトにしか掛からない。パターンは「E3 83 で始まり、BB が 0 回以上続く」になり、E3 83 で始まるカタカナ（「ピ」は E3 83 94）の頭の 2 バイトを削った。補正の道具は語彙のファイルを読めずに「ファイルの形式が正しくない」で落ち、`file` で見ると UTF-8 ではなくなっていた。

`sort` と `uniq` だけを `LC_ALL=C` で動かし、文字として扱う `sed` は UTF-8 のロケールで動かすと直った。

```sh
cat v1.rules.txt v1.repeat.txt | LC_ALL=en_US.UTF-8 sed 's/^・*//; s/・*$//' | LC_ALL=C sort -u > v1.vocab.txt
```

手元で同じように測るなら、素材は `~/live-mindmap-samples/synth/weekly-1`・`weekly-2`、道具と出力は `~/live-mindmap-samples/runs/carry-vocab/`（どちらもリポジトリの外の素材置き場）にある。音声認識は `helper` の `stt-bench run --variant baseline` に通し、補正は前の試作（`prototype/vocab-stoplist-491` ブランチの `helper/bench/proto-vocab-correct/main.swift`）を `--mode index --strict --min 0.8 --stop <上位5万語> --stop-scope latin` で回し、`server/bench/sttAccuracy.ts` で固有名詞の正解率と CER を出した。

[ローカルの LLM を回帰評価にかけた話](./2026-10-08.md#local-llm-eval)の続きで、試作のチケットを 1 件、利用者と相談しながら解いた。**差分更新**は、AI が会議の発言を読み、マインドマップへの操作（足す・直す・閉じるなど）だけを JSON で返す処理だ。今は Claude（Sonnet 5.5）が担っている。前の日の計測では、Apple Intelligence（macOS の端末内のモデル）も Qwen などのローカルのモデルも、Claude と同じプロンプトではマップを作れなかった。そこで今回は、Apple Intelligence に絞って、プロンプトと出力の形を作り直した。案を 5 つ試し、最後に同じプロンプトで Qwen3.5-4B を 1 回だけ流した。

### 1. 小さいモデルに id を正しく書かせたいなら、指示ではなく列挙型で縛り、新しい id はサーバーが振る

前の日の崩れ方は、すべて id だった。新しいノードに付ける仮 id にルートの id（`root`）を書く、存在しない `root` を書き換えようとする、といった誤りだ。指示を 1 行足すと崩れ方は変わったが、モデルごとに別の誤りへ移るだけだった。

今回は、指示で頼むのをやめて、出力のスキーマで縛った。呼び出しのたびに、その時点のマップにある id だけを JSON Schema の `enum` に書き込む。親の欄なら「今あるノードの id ＋ この応答で足すノードの番号（新1・新2 …）」、根拠の欄なら「新しい発言の id」だけが選べる。仮 id はモデルに書かせず、サーバーが add の順に振る。Apple Intelligence の構造化出力（Foundation Models の `GenerationSchema`）も、llama.cpp の `json_schema` も `enum` をそのまま守る。手で 1 回試したとき、Apple Intelligence は「予算」の下に置くなら親はどれ、という問いに、列挙した 4 つから正しい id を選んだ。

v1 では、捨てられた操作が 39 回の呼び出しで 11 個まで減った（前の日はほぼ全部）。残った 11 個も「TODO の下に子を足した」という種別の規則の違反で、id の誤りは 0 になった。前の日のエントリで「仮 id をなくせば失敗の元は消える」と見込んでいたが、そのとおりになった。スキーマが形しか保証しないなら、意味のある値の範囲まで毎回スキーマに書き込めばいい。

### 2. 文脈長が会話全体にかかるモデルでは、会話を続けず毎回 1 から呼び、見せるマップを絞る

Apple Intelligence の文脈長 8,192 トークンは、1 回の入力ではなく会話全体にかかる。Claude の形（同じ会話を使い回し、2 回目からはマップの変更だけを送る）では、最初の呼び出しだけで約 4,000 トークンあり、1 往復で約 1.4k 増えて数回で溢れていた。

そこで、ローカル向けは会話を続けず、毎回システムプロンプトと「話し中の部分のマップ」と新しい発言だけを送る形にした。システムプロンプトは、Claude 向けの長いものから、種別の定義と数行の規則だけの短いものに書き直した。v1 では入力が 1.0k〜3.8k に収まり、1 回の時間は 14 秒から 4 秒に縮んだ。開き直す回数を何回にするか、という悩みも消えた。

ただし、マップの全体を見せる形（v3）では、ノードが増えるにつれて入力が 7.9k まで膨らみ、後半の 14 回が文脈長の超過で失敗した。v4 からは、マップのうち議題（話題のまとまり）と論点（答えを出すべき問い）の行だけを見せ、要点や案は見せないことにした。こうすると入力は会議が進んでも 3k を超えなかった。Claude 側は、前置きをキャッシュに乗せる今の形のまま残した。キャッシュが効く Claude と、文脈長が窮屈な小さいモデルとでは、良い形が逆になる。

### 3. 小さいモデルに「あるか」を判断させる欄は、指示の向きで「全部なし」と「全部あり」に振れる。判断力は形では作れない

形が直ると、残った問題は中身だった。v1 では、Apple Intelligence は 39 回の呼び出しで一度も「何もしない」を返さなかった。TODO を 26 個作り、担当者まで作っていた。決定は 2 つだけだった。

そこで、判断を分類に置き換えた。v2 は新しい発言 1 つごとに、種類（相づち・進行 / 説明 / 問い / 提案 / 懸念 / 合意 / 作業の引き受け）を 1 つ選ばせる形だ。すると今度は、作業の引き受けが 1 個しか出なくなった。v3 では「作業 → 合意 → 中身」の順に、空にもできる配列で拾わせた。結果は作業 50・合意 43 だった。v4 では、各欄の前に「ある / ない」を答えさせる関門を置いた。Apple Intelligence は前から順に生成するので、先に「ない」を選べば配列を埋めないはずだった。ところが、最初の 5 回はすべて「ある」だった。v4 は決定 3/5 と数字では一番良かったが、決定を 43 個ばらまいた結果にすぎない。

指示や欄の作り方で動かせたのは、どちらに倒れるかだけだった。発言ごとに「これは合意か」を見分ける力そのものは、どの形でも出てこなかった。

### 4. 分類の単位は、モデルの入力の単位ではなく、判断の単位に合わせる

v2 で取りこぼした発言を、正解の時刻に重なる発言ごとに見ていった。すると、この素材の「発言」（音声認識が区切った 1 単位）は、複数の行為の塊だった。たとえば 1 つの発言の中に「見直し案を来週の水曜までに出します」「お願いします」「画面をもう一回お願いします」「出店の話に行きましょう」が続けて入っている。TODO と、相づちと、進行と、話題の切り替えが 1 つの単位にまとまっている。これに種類を 1 つだけ選ばせれば、TODO は「相づち・進行」に埋もれる。

v5 では、サーバーが新しい発言を「。」「？」「！」で文に切り、文の数と同じ長さの配列を返させた。配列の位置で文と対応させるので、モデルは文の id を書かなくていい。正解の TODO を含む 7 つの発言のうち、Apple Intelligence は 6 つ、Qwen3.5-4B は 7 つすべてで、その発言から TODO を作った。拾い漏れはほぼなくなった。ただし作った数が多すぎて、照合で当たったのは 3/7・4/7 にとどまった。決定はどちらのモデルも外し続けた。

この形には、もう 1 つ利点がある。「文に切る（サーバー）」「文ごとに種類を判定する」「要約して置き場所を決める」が分かれるので、判定の段だけを別のモデルに差し替えられる。結果を見た利用者からは、「こういうのは将来的に Jev などの system one のモデルでやらせる」と返ってきた（system one は、安く速い判定だけを担うモデルのことで、Jev はその 1 つ）。判定の段に向くモデルは、この地図の外の取り組みにした。

### 5. 構造化出力でも生成は止まらないことがある。上限はモデルの側で切る

v2 の 7 回目で、1 回の呼び出しが 190 秒かかり、`Content contains 8193 tokens` で失敗した。出力が止まらず、文脈長の上限まで伸びていた。スキーマで縛っていても、文字列の欄の中身はいくらでも長く書ける。同じ要求を送り直すと 117 トークンで終わったので、確率的に起きる。

困ったのは、詰まりが後ろに伝わったことだ。計測用のシムは Apple Intelligence への要求を 1 つずつ順に処理していた。そのため、呼ぶ側のタイムアウトで接続を切っても、モデルの生成は続き、次の要求が全部待たされた。Foundation Models の `GenerationOptions` に `maximumResponseTokens: 600` を渡してからは、暴走しても 600 トークンで止まり、JSON として読める形で返ってきた。39 回のうち 6〜10 回がこの上限に当たっていたので、まれな事故ではない。呼ぶ側のタイムアウトは、生成を止める手段にならない。

### 6. 速さの差は「読み込み」と「生成」に分けてから、改善で縮むかを見る

4B の v5 は 1 回 中央 21 秒で、内訳は生成が 16 秒（277 トークンを 14 トークン/秒）、読み込みが 4 秒（976 トークン）だった。前の日の 37.5 秒からは縮んだが、この会議で差分更新を呼ぶ間隔（中央 35 秒）とほぼ同じで、ほかのアプリとメモリを取り合えばすぐ溢れる。Apple Intelligence は 6.6 秒だった。利用者の感想は「さすがに apple しか使い物にならないね、速度的に」だった。

判定を system one のモデルに任せれば 4B も化けるか、とも聞かれた。品質は上がりうる。外しているのは判定なので、そこを別のモデルが担えば、4B に残るのは要約と置き場所だけになる。一方で速さは、ほとんど変わらない見込みだ。遅さの大半は要約を書く生成で、判定を外しても縮むのは作るノードが減る分だけになる（見込みで半分程度、10 秒前後）。しかも同じ改善は Apple Intelligence にも効くので、差は縮まらない。

利用者はさらに、品質はハードのスペックにも左右される、と続けた。手元で測れるのは M4・16GB の 1 台だけで、ほかの機種の数字は持っていない。そこで次のように決めた。

- 品質を保証するのは Apple Intelligence だけにする。
- ほかのモデルは、すでに決めてある OpenAI 互換の口をアダプターとして用意し、利用者が設定に書けば使えるようにする。品質は保証しない。
- そうした利用者の実行環境は、通常のモードでだけ使える。ローカルモード（会議の中身が Mac の外に一切出ないと約束するセッション）では選べない。Ollama や LM Studio は更新の確認で外に通信するので、約束の範囲から外す、という前の決定のままだ。

結果として、「何も外に出ない」と約束できる範囲と、品質を保証する範囲が、どちらも Apple Intelligence にそろった。Mac の中でモデルを動かす内蔵の仕組み（node-llama-cpp）も、作らないことにした。推奨のモデルを機種ごとに 2 段で案内する計画も消えた。

手元で同じように測るなら、試作は `prototype/local-llm-prompt` ブランチの `server/src/prototypeLocalUpdater.ts` にある。`LOCAL_LLM_SHAPE=stateless` と `LOCAL_LLM_VARIANT=v1`〜`v5` で案を切り替え、宛先は `LOCAL_LLM_URL` で渡す。Apple Intelligence は同じブランチの `server/bench/afm/main.swift` を `swiftc -O` でビルドし、`server/bench/afmServer.ts` で localhost の OpenAI 互換の口に包む。4B は llama.cpp の `llama-server --offline -c 16384 --reasoning off` で動かした。正解の時刻に重なる発言ごとに作ったノードの種別を出す道具は、`server/bench/truthHits.py` だ（本文は出さない）。

## 英字の語の読みを作り方ごとに 106 語で比べたら、端末の中の LLM は 4 語に 1 語を別の語に崩し、差分更新のモデルに聞く形に改めた話

[1 つ目のエントリ](#carry-vocab-effect)で見つけた「英字の語の読みの崩れ」を、語を増やして測り直したときの学び。字幕の補正は、音声認識が崩した語を、**語彙**（会議で話されそうな固有名詞・略語の正しい表記の集まり）から読みの近さで引いて直す。読みは OS のトークナイザが返すローマ字で比べるが、Figma のような英字の語はトークナイザが英字のまま返すので、カタカナの読みを別に作る必要がある。これまでは端末の中の LLM（Apple の FoundationModels）に 1 語ずつ聞いていた。測った結果、セッションの**差分更新のモデル**（会議の発言からマインドマップを更新し続ける AI。セッションの開始時に選ぶ）にまとめて聞く形に改めた。

- 決定の記録: チケット [英字の語の読みが FoundationModels で崩れる割合と、別の作り方を測る](https://github.com/daiki-beppu/live-mindmap/issues/577)、改めた ADR [語彙での補正はサーバーが発言を締めるときにかけ、読みはヘルパーが送る](../adr/0015-correct-remarks-in-server-readings-from-helper.md)、地図 [Kanary を手本に字幕の精度を上げる](https://github.com/daiki-beppu/live-mindmap/issues/386)

会議に出そうな英字の製品名・サービス名を 106 語集め（それまでの読みのキャッシュにあった 20 語を含む）、語ごとに正しい読みを書いた。作り方ごとに読みを出し、本番の補正と同じ照合の条件で正しい読みに届くかを数えた。

| 作り方 | 読みが正しい語 | 崩れ方の例 |
| --- | --- | --- |
| FoundationModels（それまでの形） | 79/106（75%） | Amplitude→アスペクト、MySQL→マイクロン、SharePoint→シャープポイント |
| FoundationModels＋手本 5 つのプロンプト | 76/106 | Gmail→グーグルメール、PayPal→ペイペイ |
| FoundationModels で候補を 3 つ | 83/106 | |
| FoundationModels で 5 回出して全部を読みにする | 90/106 | PowerPoint→プレゼンテーション が混ざる |
| ICU の字訳（ローマ字読み） | 47/106 | |
| 日本語の音声合成で読ませて音声認識にかける | 69/106 | Figma→ヒグマ、Asana→浅田 |
| Claude Haiku に 106 語をまとめて 1 度聞く | 103/106（97%） | Marketo→マーケト、Swagger→スウェガー |

実際の素材（音声合成で作った 8 分の会議 2 本）を台本の語の語彙で直すと、固有名詞の正解率は、新しい英字の語が多い会議で 58.6% から 74.7%、もう一方で 95.2% から 96.0% に上がった。誤った置き換えはどちらも 0 だった。74.7% は、前のエントリで読みを手で直したときの値と同じだ。

### 1. 正解の表記は、下流の段が実際に書く形から決める

正しい読みを書く前に、音声認識（Apple の SpeechAnalyzer）が英字の製品名をどう書いているかを素材で確かめた。台本の語の前後の時刻に重なる確定結果を並べると、フィグマ・アンプリチュード・ブレイズ・セールスフォース・ノーションのように、辞書どおりのカタカナで書いていた。GitHub や POC は英字のまま出ていた。

補正が引くのは、音声認識が書いたこの文字列だ。だから正しい読みは「英語の発音に近いカタカナ」ではなく「音声認識が書くカタカナ」になる。今回は両者がほぼ一致していたので、辞書どおりの表記を正解にできた。順番を逆にして、先に発音から正解を作っていたら、トゥイリオとツイリオのどちらを正解にするかで迷い、照合の数字が意味を持たなかった。

### 2. 採点は本番の照合の条件でする。照合の側のずれは、読みの崩れと分けて数える

読みが「正しいか」は見た目では決めず、本番の補正と同じ条件で数えた。読みをローマ字にして長音・促音などを潰したキーを作り、キーが 5 字以下なら完全一致、それより長ければ編集距離から出した似ている度合いが 0.8 以上なら、補正がその語を引ける。

数えている途中で、照合の側のずれが見つかった。スワガーとスワッガーが一致しない。トークナイザの返すローマ字を出すと、こうなっていた。

```
スワガー   ["suwa", "gā"]
スワッガー ["suwa~tsu", "gā"]
トゥイッチ ["to~uitchi"]
ツイッチ   ["tsu", "itchi"]
```

辞書に無いカタカナでは、小さいカナを `~tsu`（ッ）・`~u`（ゥ）と返す。キーは `~` を記号として落とすが、`tsu` は残るので、促音を含む読みが一致しにくい。これは読みの作り方とは関係が無く、音声認識がトゥイリオと書いたときにも効く。

採点を 2 通り出した。本番のままのキーと、`~tsu` を落として `~` を外したキーだ。どの作り方でも、後者で増えたのは 0〜2 語だった（FoundationModels は 78→79 語、Haiku は 103 語のまま）。表の値は、読みの作り方の差だけを見るために後者で数えている。照合の直しは、読みの作り方とは別の項目として仕様に入れた。混ぜて数えていたら、どちらが効いたかが分からなくなっていた。

### 3. 候補を増やすと当たりは増えるが、外れの候補が誤りの元になる

当たりの数だけを見ると、FoundationModels で 5 回出して全部を読みにする形が 90 語で、1 回だけの 79 語を大きく上回る。ただ、出てきた候補を開くと、PowerPoint にプレゼンテーション、パワポ、パワフォートが並んでいた。

補正は、語彙の語の読みに近い区間を見つけたら、その語に書き換える。読みにプレゼンテーションを持たせると、会議で「プレゼンテーション」と話した箇所が PowerPoint に書き換わる。ふつうの語の一覧に載る区間は直さない守りはあるが、英字の語への書き換えだけは通す決まりなので、この守りでは止まらない。

この補正では、読みが外れて取りこぼすより、誤って書き換えるほうが害が大きい。字幕が勝手に別の語に変わるからだ。候補を増やす形は、当たりの数を上げても採れなかった。読みは 1 語に 1 つと仕様に書いた。

### 4. 小さいモデルに手本を足したら、かえって悪くなった

最初に試したのは、プロンプトの言い換えだった。「綴りをローマ字読みせず、英語の発音をもとにした、日本で定着した呼び方にする」と書き、Microsoft→マイクロソフトのような手本を 5 つ付けた。79 語が 76 語に減った。

崩れ方が変わっていた。手本なしでは Amplitude→アスペクトのように、綴りの近い別の語に崩れていた。手本ありでは Gmail→グーグルメール、PayPal→ペイペイ、SharePoint→スポーティングのように、「日本で定着した呼び方」を「日本でよく聞く別の名前」と取ったような答えが出た。指示を足しても、小さいモデルが知らない語の読みは作れない。知らない語の前で、別の知っている語に寄せる向きが変わるだけだった。

### 5. 音声合成で読ませて音声認識にかける形は、声が英語を読めず使えなかった

「音声認識がどう書くか」が正解なら、音声認識そのものに書かせればよい、と考えた。macOS の日本語の声（Kyoko）に「12 番、次は Braze の話です。」のような文を 106 語ぶん読ませ、1 本の音声にして、同じ SpeechAnalyzer で文字起こしした。

```sh
cut -f1 truth.tsv | awk '{printf "%d番、次は%sの話です。[[slnc 900]]\n", NR, $0}' > script.txt
say -v Kyoko -f script.txt -o kyoko.aiff
afconvert -f m4af -d aac kyoko.aiff kyoko.m4a
```

Braze→ブレイズ、Stripe→ストライプのように正しく戻る語もあったが、Figma→ヒグマ、Asana→浅田、Claude→クロッドのように、日本語の声が英字の語を読めていなかった。照合が緩いので数字は 69 語になったが、エバーフロー（Airflow）のように崩れたまま通った語も含む。英語の声（Samantha）で読ませて日本語の音声認識にかけると、語は英字のまま返るか崩れ、番号まで崩れて照合できなかった。

英語の発音記号からカタカナを規則で作る形も考えた。macOS には英文の発音記号を返す `NSSpeechSynthesizer.phonemes(from:)` があるが、英語の声を指定しても空の文字列しか返さず、試せなかった。

### 6. 正解を書いた側と同じ系統のモデルは、有利に見えうる

一番よかったのは Claude Haiku だが、正しい読みの一覧を書いたのも Claude（この作業をしていたエージェント）だ。表記の揺れ（トレロかトレローか）を同じ癖で選んでいれば、Haiku は実力以上に当たって見える。

偏りが結論を変えるかは、崩れ方で見た。FoundationModels の外れは、表記の揺れではなく別の語（アスペクト、マイクロン、オンデーズ）が多い。正解の書き方を変えても、これは当たりにならない。差の大半は偏りでは説明できないと判断し、偏りがありうることは記録に残した。

### 7. 新しい外部呼び出しを足す前に、会議の中身をすでに渡している先に相乗りする

改めた形では、新しい英字の語が語彙に入るとき、サーバーがセッションの差分更新のモデルに語をまとめてカタカナを聞く。返ったカタカナは、これまでどおりヘルパー（音声認識を担う Swift の実行ファイル）のサブコマンドに渡し、ほかの語と同じトークナイザのローマ字にする。測った読みの形は変わらない。

読みのためだけに別のクラウドの API を呼ぶ形にはしなかった。語彙の語は共有画面や発言から取るので、会議の中身にあたる。差分更新のモデルには、もともと発言を渡している。そこに語を足しても、会議の中身の行き先は増えない。**ローカルモード**（会議の中身が Mac の外に一切出ないと約束するセッション）では、差分更新のモデルは Mac の中で動く Apple Intelligence だけ（[2 つ目のエントリ](#local-llm-prompt-shape)）なので、約束もそのまま守られる。

その代わり、ローカルモードの読みの質は FoundationModels のまま、4 語に 1 語が崩れる。ここは仕組みでは埋めず、残る弱さとして記録した。

手元で同じように測るなら、道具と出力は `~/live-mindmap-samples/runs/latin-readings/`（リポジトリの外の素材置き場）にある。`readings.swift` を `swiftc -O` でビルドし、`readings truth.tsv fm` のように作り方を渡すと、語ごとの読みと判定を出す。`FROM=<出力>` で読みを採点だけし直し、`FIX=1` で小さいカナの癖を外して採点する。素材での値は、前のエントリの補正の道具を、読みのキャッシュだけ差し替えて回した。

## Haiku 5.5 と Sonnet 5.5 を比べる地図を作ったら、比べる前に effort の既定値と、過去の試算の単価のずれが見つかった話

Claude Haiku 5.5 が出たので、差分更新に使っている Sonnet 5.5 と比べる計画を立てたときの学び。**差分更新**は、AI が会議の発言を読み、マインドマップへの操作だけを JSON で返す処理だ。このアプリで Claude を呼ぶのはこの 1 か所だけで、Claude Agent SDK を通して Sonnet 5.5 を呼んでいる。利用者は自分の API キーで払う。今回はコードを書かず、決めることを並べた地図（決めることを 1 つの issue に束ね、子のチケットに分けたもの）を作り、最初の調べ物を 1 件だけ片づけた。

- 決定の記録: 地図 [Haiku 5.5 を差分更新のモデルとして Sonnet 5.5 と比べる](https://github.com/daiki-beppu/live-mindmap/issues/612)、チケット [Haiku 5.5 と Sonnet 5.5 の公表値と、今の呼び方で Haiku 5.5 が使えるか](https://github.com/daiki-beppu/live-mindmap/issues/613)、注記の PR [ナレッジの Claude の費用に、キャッシュの読み出しの単価が公式と違うことを注記する](https://github.com/daiki-beppu/live-mindmap/pull/617)

### 1. 新しいモデルと比べるときは、評価を回す前に、目的地と物差しを決める

利用者の最初の一言は「haiku 5.5 が出たので既存の claude の設定と比較」だった。これだけでは、比べる対象（製品の差分更新か、開発に使う道具のモデルか）も、何が分かれば終わりかも決まらない。そこで、先に 4 つを決めた。

- 比べる範囲は、製品の差分更新だけにする。E2E のテストは記録を再生していてモデルを呼ばないので、比べても意味がない。
- 地図の終わりは 2 つの判断にする。1 つは、既定のモデルを Haiku 5.5 に替えるか。もう 1 つは、既定にしない場合でも、選べるモデルとして残すか。
- 物差しは「品質に下限、その上で遅れと料金」にする。下限は Sonnet 5.5 から落ちないこと。
- Haiku に向きそうな別の役目（文ごとの種類の分類）は、まだ実装が無いので範囲外にする。

チケットは、調べ物 → 評価 → 判断の順に、前のものが閉じるまで次に進めない形でつないだ。評価より先に調べ物を置いたのは、モデル名だけを替えて同じに動く保証が無いからだ。今の作りは、キャッシュに乗る最小の長さと、JSON スキーマでの構造化出力に頼っている。実際、次の節の 2 つの落とし穴は、評価を回す前の調べ物で見つかった。

**新しいモデルとの比較は、評価を回す前に、何が分かれば終わりかと、どの数字で比べるかを決める。** 決めずに回すと、出た数字を見てから基準を選ぶことになる。

### 2. Agent SDK で新しいモデルを呼ぶときの既定値は、API ではなく、同梱の CLI のモデル一覧で決まる

Agent SDK は、内部で Claude Code の CLI を子プロセスとして動かす。調べると、同梱の CLI は 2026-10-02 のビルドで、10-07 に出た Haiku 5.5 をモデルの一覧に持っていなかった。知らないモデルでも、ID はそのまま API に送る。Haiku 5.5 が受け付けない指定（temperature・thinking の予算・prefill）も送らないので、呼べる見込みは高い。

問題は effort（どれだけ考えるかの段階）の既定値だった。

| | API の既定 | 今の作りで実際に送る値 |
| --- | --- | --- |
| Sonnet 5.5 | `high` | `medium`（CLI の一覧の既定） |
| Haiku 5.5 | `medium` | `high`（一覧に無いので、CLI の最後の既定） |

コードで何も指定していないので、そのまま比べると「medium の Sonnet」と「high の Haiku」の比較になる。API の既定とも逆向きにずれる。評価のチケットには、両方の effort を `options.effort` で明示して揃える、と書き足した。

**SDK を通してモデルを呼ぶときは、既定値がどこで決まるかを、API のドキュメントではなく SDK の中身で確かめる。** 新しいモデルの直後は、SDK の版がモデルより古いことが多く、ずれが出やすい。

### 3. 要求ごとに単価が切り替わるモデルでは、会話を使い回す作りが境目に近づかないかを見る

Haiku 5.5 の単価は、Sonnet 5.5 のおよそ 1/20 だ（100 万トークンあたり入力 $0.10・出力 $0.50）。ただし、1 回の要求の入力が 10 万トークンを超えると、その要求は 5 倍の単価になる。入力にはキャッシュから読んだ分も含まれる。

この差分更新は、SDK の会話を開いたまま最大 14 回使い回す。キャッシュを効かせるためで、回を追うごとに会話の履歴が積もる。長い会議では、会話を開いたときに渡すマップ全体も大きくなる。そこで、評価のチケットに、入力の合計が 10 万を超える呼び出しの数を数える、と足した。

**料金が要求ごとの大きさで変わるモデルでは、キャッシュのために入力を大きく保つ作りが、そのまま単価の境目に近づく。** キャッシュで安くしたつもりの設計が、別の料金体系では逆に効くことがある。

### 4. 「SDK の値と一致した」は、単価が正しい証拠にならない。単価は料金表で確かめる

調べ物の途中で、別の誤りも見つかった。過去の開発ログでは、Sonnet 5.5 のキャッシュの読み出しを 100 万トークンあたり $0.20 として費用を数えていた。公式の料金表では $0.10（入力の 0.05 倍）だ。$0.20 は、1 つ前の Sonnet 5 の単価と同じだ。

[長い会議を測った話](./2026-10-04.md#long-meeting-eval) では、自分で計算した 1 回の費用が SDK の返す値と一致した（$0.00798 と $0.00799）。それで単価は合っていると考えていた。ただ、一致が示すのは「SDK と同じ数え方をした」ことだけで、その数え方が料金表と同じかどうかは示さない。SDK の内側も同じ単価で数えていたのだと見ている（確かめてはいない）。このアプリの費用は、キャッシュの読み出しが入力の大半を占める。そのため、長い会議ほど高めに出ていた。

**費用の物差しに使う単価は、SDK の値と照らすだけで済ませず、料金表の一次情報で一度確かめる。** 同じ表を見ている 2 つの数字は、一緒に外れる。

### 5. 生のトークン数を残していない記録は、推測で書き換えず、注記で直す

利用者からは「試算も公式の値で揃えて」と頼まれた。ところが、計算し直すのに要る呼び出しごとのトークン数が、どこにも残っていなかった。当時のセッションのフォルダは消えていた。開発ログには、表の金額しか書いていなかった。

読み出しの割合を仮定すれば、金額を縮めることはできる。ただ、それでは推測の数字を、測った値として書き換えることになる。利用者と相談して、日付の付いた記録は当時の値のまま残した。そのうえで、Claude の費用を載せた 4 日分の 9 節に注記を 1 行ずつ足した。中身は、どの単価で数えたか、公式の単価はいくらか、実際はどちらに外れるか。これからの評価は、トークン数に公式の単価を掛けて出すと、評価のチケットに書いた。

**費用を測ったら、金額だけでなく、呼び出しごとのトークン数の内訳も残す。** 単価が後で変わっても、間違いが見つかっても、内訳があれば計算し直せる。

## テストの層の子チケットを takt で流したら、takt の中で満たせない受け入れ条件で止まり、CI の判定と振り分けにも穴が 2 つ見つかった話

テストを unit・軽い IT・重い IT・E2E の層にそろえる親チケットの子 21 件を、takt（issue を渡すと、エージェントが計画・実装・レビューまで進めて PR を作る道具）に並列 3 で積み、終わった PR から順にマージした。子チケットの切り方は [前日のエントリ](./2026-10-08.md#test-layers-tickets) にある。takt は止まらずに通った件が多かったが、2 件は takt の中で止まり、2 件は CI の穴を通ってマージされ、そのうち 1 件は main を壊した。回す側の見張りの書き方は [前日のエントリ](./2026-10-08.md#takt-ops-watch) に書いたので、ここでは issue の書き方と CI の作りから見た学びを書く。

- 決定の記録: 親チケット [テストの層をそろえる](https://github.com/daiki-beppu/live-mindmap/issues/543)
- 途中で起こしたチケット: [`check` ジョブが runner を取れなかったジョブを見逃す](https://github.com/daiki-beppu/live-mindmap/issues/589)、[`helper/package.json` だけの変更で server のテストが走らない](https://github.com/daiki-beppu/live-mindmap/issues/599)

### 1. 受け入れ条件は「takt の中で確かめられるか」で分け、外の条件は「マージ後に人が」に回す

helper（Swift で書いた音声の取り込みの子プロセス）の unit のテストを速くするチケットは、受け入れ条件に「縮めても失敗を捕まえられる根拠を PR の本文に書く」を入れていた。takt は実装もレビューも通した（指摘 0 件）のに、最後の判定で止まった。takt は PR の本文を issue の本文から作るので、takt の中のエージェントは PR の本文に書けない。満たせない条件が 1 行あるだけで、全体が「未完了」になる。残った差分を手で PR にし、根拠は自分で本文に書いた（テストは約 7.5 秒から 0.98 秒になった）。

同じ形の条件は、ほかのチケットにもあった。CI のジョブを組み直すチケットの「実際の PR で 4 つの runner が回って通る」「どのジョブが落ちても `check` が落ちる」は、PR がマージされて CI が回るまで分からない。これらは、積む前に行頭へ「（マージ後に人が）」を付けて takt の条件から外し、代わりに takt の中で確かめられる条件を置いた。たとえば、ワークフローの YAML を読んで「`check` の `needs` が全ジョブを含む」ことを確かめるテストや、重い IT の割り振りのロジックを、テスト一覧に見立てた入力で走らせるテストだ。

**エージェントに渡す受け入れ条件は、エージェントの手の届く範囲（ファイルの中身・手元で回るコマンド）だけで書く。** PR の本文・実際の CI・人の目が要る条件は、別の印を付けて後に回し、代わりに手元で確かめられる形の条件を足す。

### 2. issue に書いた再現の例は、今の規則に照らしてから積む

議題（マインドマップの論点のまとまり）を統合したとき、根拠が増えていないのに「根拠が足された」の印が付く、というチケットは、takt の計画の段で「要件どうしが両立しない」と判定され、自動の積み直し 2 回を経て止まった。

食い違っていたのは、私が issue に書いた再現の例だった。例は「1 回目に作り、2 回目に統合して、同じ応答の中で閉じられる」。ところが今の規則では、直前の反映で根拠が足された議題は閉じられない。1 回目に作った根拠は、2 回目から見て「直前」だ。統合を直しても、この例は規則どおりに失敗する。例を規則と両立する 2 本（2 回目に統合して 3 回目に閉じる／3 回目に統合して同じ応答で閉じる）に書き直して積み直すと、APPROVE で通った。

takt の計画のエージェントは、例と規則を突き合わせて、矛盾をきちんと見つけた。止まったのは正しい振る舞いで、直すべきは issue のほうだった。

**再現の例は仕様の一部として読まれる。積む前に、例の 1 手ずつが今の規則で何を返すかをたどる。**

### 3. 必須のジョブの判定は「失敗を探す」ではなく「成功か飛ばしだけか」を確かめる

main へのマージには、CI の最後の `check` ジョブが通ることを必須にしている。`check` は、ほかのジョブの結果を見て落ちるか決める。そのステップの条件は次のとおりだった。

```yaml
- if: contains(needs.*.result, 'failure') || contains(needs.*.result, 'cancelled')
```

ある PR の CI で、helper のジョブが macOS の runner を 15 分取れずに終わった（「The job was not acquired by Runner」。ステップは 1 つも走っていない）。それでも `check` は success になった。runner を取れずに終わったジョブは、`failure` でも `cancelled` でもない結果で渡るらしい。この PR は、たまたま main との衝突でマージされずに済んだが、Swift のテストが一度も走らないままマージできる状態だった。

判定を逆にした。ステップを毎回走らせ、`needs` の結果を `jq` で読んで、`success`・`skipped` 以外が 1 つでもあれば、そのジョブ名と結果を出して落とす。

**取りうる値を全部知らないものを判定するときは、悪い値を列挙せず、良い値を列挙する。** 知らない値は、悪い側に倒れる。

### 4. 変更のパスでジョブを飛ばすなら、テストが読むファイルも振り分けに入れる

CI は、PR が変えたパスでジョブを選ぶ。`helper/` の下だけの変更なら、server と web のジョブ（ts のジョブ）は飛ばす。

helper の型検査（`typecheck` の script）の先頭に、テストの層の点検の script を足すチケットがマージされた。この PR は helper の下だけの変更なので、ts のジョブは飛ばされ、CI は通った。ところが server には、`helper/package.json` を読んで「AEC3（エコーキャンセラー）のライブラリを組む `build-apm` を、ビルドより先に呼ぶ」ことを確かめるテストがある。点検の script が先頭に来たので、このテストは落ちる。main の次の 2 回の CI で初めて落ち、手で順を直した（`build-apm` → 点検 → ビルド）。

直し方は 2 つあった。振り分けに `helper/package.json` を足すか、server のテストを helper の側へ移すか。テストは helper の script が server の期待を守っているかを見るもので、置き場所は正しい。振り分けのほうを直し、`helper/package.json` が変わったときは ts のジョブも走らせた。理由はワークフローのコメントに 1 行書いた。

**パスで振り分ける CI では、「このテストが何のファイルを読むか」がジョブの依存になる。** `grep -rn "helper/" server/test web/test` のように、別のディレクトリのファイルを読むテストを探して、振り分けに足す。

### 5. 依存が解けた子は、ブロッカーが閉じるたびに親から引き直す

子チケットには「この子が閉じてから着手」という依存（GitHub の blocked by）を張ってあった。回す側は、マージのたびに「これで解けた子」を手で数えて積んでいた。CI の helper のジョブを 1 回のビルドから 3 層に分けて回す子は、ブロッカーが閉じた時点で着手できたのに、ほかの子をマージした後まで積み忘れていた。気づいたのは、親の子が全部片付いたと報告しかけたときだった。

積み忘れた間に main は進んでいて、本文の前提（「ビルドを 1 回にする」）は別のチケットで済んでいた。残る作業は、テストを回すステップを 3 つに分けることだけだった。本文を今の main に合わせて直してから積んだ。

**手で数える代わりに、マージのたびに親の子の一覧を引き、「open で、ブロッカーが全部閉じていて、まだ積んでいない」子を機械的に出す。** 遅れて積む子ほど、本文が古くなっている。

### 6. 全員が書き足す 1 行は、並行の PR を毎回衝突させる

`AGENTS.md`（エージェントが毎回読むリポジトリの案内）の Checks の節は、検査の手順を 1 段落に詰めて書いていた。テストの層の子は、ほぼ全部がこの段落に 1 文を足す。並列 3 で流すと、先にマージされた PR の文と後の PR の文が同じ行でぶつかり、後の PR がほぼ毎回 DIRTY（衝突でマージできない）になった。そのたびに、takt の作業場所で `origin/main` に載せ直し、両方の文を残して push した。

衝突の解消は機械的だが、毎回人（回す側のセッション）の手が要り、そのぶんマージが遅れた。

**並行で書き足される文書は、1 項目 1 行の箇条にしておく。** 行が分かれていれば、別々の追記は衝突しない。

## 話者分離の回帰評価を決め、地図を仕様と形式仕様にまとめたら、人の声の素材は要らないと利用者に押し戻され、全探索は時相の性質で TLC に回すと 1 分で済んだ話

話者分離の地図（会議の `相手`（会議アプリの音）のトラックを声で区別し、「相手 A」のような**話者**のラベルを字幕とマップに出す取り組み。[前の日のエントリ](./2026-10-08.md#speaker-diarization-map)）の、最後のチケット「回帰評価の指標」を決めたときの学び。続けて、地図の 10 件の決定を 1 本の実装仕様にまとめ、仕様の「常に成り立つべき性質」を Quint と Alloy で形式化して検証器にかけた。

- 決定の記録: チケット [話者分離の回帰評価の指標](https://github.com/daiki-beppu/live-mindmap/issues/542)、仕様 [話者分離の実装仕様](https://github.com/daiki-beppu/live-mindmap/issues/610)（Formal Spec はそのコメント）、地図 [話者分離：字幕とマップで誰の発言か分かるようにする](https://github.com/daiki-beppu/live-mindmap/issues/367)

### 1. 人の声の素材が要るかは、「どの判定が声のばらつきに頼っているか」で切り分ける

チケットには「基準値を人の声の会議でどう確かめるか。素材をどう用意するか」という問いがあった。これまでの計測は、架空の台本を音声合成（Gemini TTS）で読ませた**合成会議**だけで行っている。TTS は 1 人に 1 つの声を当て、どの行も同じ調子で読むので、人より区別しやすいかもしれない、という心配が地図に書かれていた。

私はこれを素直に受け、人の声で注釈つきの会話コーパスを調べに行った。日本語で 5 人以上の会議があり、企業が使えるのは国語研の CEJC だけで、商業利用は 2 年・社内 10 人以内で 50 万円（税別）、契約は郵送と前払い、音声は CI に置けない。無料で今週中に手に入るのは英語・中国語の会議室の録音（AMI・NOTSOFAR-1 は CC BY 4.0、AISHELL-4 は CC BY-SA 4.0）だった。そこで「AMI と NOTSOFAR-1 を主にし、Opus に通し直して流す」と推した。

利用者の返事は「自作の音声で良くない？」だった。改めて、評価の項目ごとに、人の声で結果が変わりうるかを分けた。

| 測るもの | 人の声で変わりうるか |
| --- | --- |
| 発言ごとの話者の正解率 | 小さい。前の計測で、合成会議の DER（話者の誤りの時間の割合）は、NVIDIA が人の声で出した公開値と同じ水準だった（4 人で 7〜15%） |
| 案の出した人・TODO の担当者・名前 | 声ではなく、AI と規則の問題 |
| 5 人目の声の混入の検出 | 変わりうる。同じ人の声どうしの埋め込みが近いことに頼っており、TTS は同じ人のばらつきが小さい |

人の声が要るのは 3 行目だけだった。次に利用者は「実際に使った時のやつでいいんじゃないの？」と続けた。実際の会議には正解の注釈が無いが、「相手が何人いたか」さえ分かれば、混入の誤検出の回数やラベルの数は数えられる。最後に「TTS だけで問題ないと思うけどな」で決まった。人の声で誤検出しうることは既知の制限として仕様に書き、起きれば `log.jsonl` の検出の記録で気づける、という扱いにした。

外れたのは、地図にあった「TTS は区別しやすいかもしれない」を、項目を分けずに評価全体の前提にしたところだ。分けてみると、心配が当たるのは 1 つの判定だけで、そのために 50 万円のコーパスや英語の会議室の録音を持ち込むのは釣り合わなかった。素材の現実味を上げる前に、どの判定がその現実味に頼っているかを先に分ける。

その途中で利用者に「なんの話？」と聞き返された場面もあった。基準値を選ぶ素材と確かめる素材を分けるか、という問いを、コーパスの名前と cos の値で書いていた。問答が長くなったら、いま何を決めているのかを毎回 1 行で書き直す。

### 2. 「誤ったラベルよりラベルなし」を選んだ設計では、指標でも話者なしを取り違えと分ける

話者分離の地図は、決定のたびに「迷ったらラベルを付けない」を選んできた。確定したラベルが 3 秒待っても揃わない、声の混入を検出した、ヘルパー（音声を取り込んで認識する子プロセス）を作り直した後にまだ照らし合わせが済んでいない、のどれでも、発言をただの `相手` で出す。

正解率を 1 つの数にまとめると、この「意図して付けなかった」分が誤りに数えられる。規則が正しく働くほど、数字が悪化して見えることになる。そこで各**発言**（文字起こしの 1 区切り）を、正解 / 取り違え / 話者なし の 3 つに分けて数えることにした。誤ったラベルは人に結び付いたまま信じられるので、取り違えのほうを重く見る。

同じ考えで、ヘルパーを作り直した後のつなぎ直しは、正しくつないだ / 新しいラベル / 話者なし / 誤ってつないだ の 4 つに分け、誤ってつないだ数を最も重く見る。名前も、誤った名前の数を別に目立たせる。誤った名前は、名前がないより悪いからだ。

### 3. AI の誤りと音声側の誤りは、正しい入力を渡す段を挟んで切り分ける

案の出した人と TODO の担当者は、2 つの段を通って決まる。音声から話者を分ける段と、AI が根拠の発言や担当者を選ぶ段だ。全部を通した値だけを見ると、外れたときにどちらのせいか分からない。

そこで、正解の台本（`timeline.tsv`。行ごとの話者と時刻）から、正しい話者つきの発言を作って流す段を足した。この段で外れれば、差分更新のプロンプトか根拠の選び方の問題だと分かる。字幕の精度の計測で、認識の誤り（CER）を認識だけで測っているのと同じ切り分け方だ。

### 4. 「再生で測り直せるようにログに残す」と決めたら、読み直す経路が本当にあるかを確かめる

話者分離の ADR には、「発言に決まった話者と、ヘルパーから届いた生の話者の区間を両方ログに残す。規則を変えたら再生で測り直せるように」と書いてあった。仕様を書く前に、継ぎ目を調べるサブエージェントにコードを読ませた。すると、今の再生（`cli play`）は**締めた後の発言**だけを差分更新に流していて、発言を締める規則も、その手前の関所も通らないことが分かった。生の区間をいくら残しても、規則を変えて測り直す経路は無い。

仕様には「締める前の入力（`remark` / `partial` と話者のイベント）を、届いた時刻の順にもう一度流す経路を足す」と書き、Eval の切り出しもこの経路の上に組んだ。記録を残す決定は、それを読み直す側があって初めて意味を持つ。ADR を書いた時点では、そこまで確かめていなかった。

### 5. 全探索が時間切れになったら、性質を時相で書いて TLC に回し、動きの違う部分は別の検査器に分ける

仕様の性質を形式化した。ラベルは初めて話した順に振り、使い回さない。混入で戻したラベルは会議の最後まで戻したまま。出した発言は書き換えない。手入力の名前は AI が変えない。案の出した人は更新で変わらない。検証器は takt の `/verify` と同じもの（Quint は `--max-steps 20`、時相の性質が無ければ Apalache、あれば TLC。Alloy は全部の `run` / `check`）で、このスキルでは全探索の上限を 5 分にしている。

最初は、ラベル・発言・名前・案・TODO を 1 つの Quint のモジュールに入れ、「書き換えない」は 1 つ前の状態の控えを変数に持たせて不変条件で書いた。構文と模擬実行は通ったが、Apalache の全探索が 5 分で時間切れになった。ラベルを 4→3、発言を 6→4 に減らしても同じだった。

効いたのは書き方を変えることだった。

- 「書き換えない」「戻したまま」「つないだら替わらない」は `always(p implies always(p))` の時相の性質で書いた。控えの変数が要らなくなり、検証器は TLC に切り替わる。状態をラベル 3・発言 4・作り直し 1 回に抑えたモデルは、TLC の全探索が約 1 分で終わった
- 名前と案の出した人は、ラベルの動きと独立している。こちらは Alloy 6 の時間つきのモデル（`for 3 but 8 steps`）に移した

Alloy では 2 か所でつまずいた。`fact steps` は `steps` が Alloy 6 の予約語なので構文エラーになった。また、`some rs: set Remark | addPlan[p, rs]` のように集合を量化すると、「skolem 化できない高階の量化」で解けなかった。根拠は 1 つずつ足す形に直した。いちばん早い発言で追加し、残りを更新で足すのと同じなので、性質は変わらない。

12 の性質がすべて反例なしで通り、要件どうしの矛盾は見つからなかった。中には、仕様のどこにも直接は書いていない性質もある。「案の出した人は、更新や統合を経ても、いつもその案の根拠の発言のどれかの話者」は、「追加のときに決めて変えない」「統合では早いほうを残す」「根拠は増えるだけ」の 3 つを組み合わせて初めて言える。形式化して得をするのは、こうした組み合わせの性質を機械に確かめさせられるところだ。

<a id="managed-deps"></a>

## takt の「重い依存は使うときだけ入れる」を真似る地図を作ったら、確認を受け取るのは端末ではなく AI エージェントだった話

AI エージェントのワークフロー実行ツール takt の issue を手本に、live-mindmap の重い依存を「使うときだけ入れる」形にできるかを考え、決めることを並べた地図を作ったときの学び。地図は、決めることを 1 つの issue に束ね、子のチケットに分けたもの。今回はコードを書いていない。地図を作り、調べ物のチケット 3 件をサブエージェントに並行で片づけさせた。

- 決定の記録: 地図 [重い依存を使うときだけ入れ、start の前にそろえる](https://github.com/daiki-beppu/live-mindmap/issues/619)、チケット [Claude Agent SDK と node-llama-cpp を管理ディレクトリから読み込む方法](https://github.com/daiki-beppu/live-mindmap/issues/620)・[Playwright と Chromium を使うときだけ入れる方法](https://github.com/daiki-beppu/live-mindmap/issues/621)・[ヘルパーが開始前に確かめられること](https://github.com/daiki-beppu/live-mindmap/issues/622)
- 手本: [takt #1738](https://github.com/nrslib/takt/issues/1738)

手本の issue の中身はこうだ。`npm i takt` の node_modules は約 1GB あり、その大半はプロバイダの SDK が引き込む CLI のネイティブバイナリが占める。そこで SDK を通常の依存から外し、固定版の package.json と lock を本体に同梱する。使うときに、管理ディレクトリで `npm ci --omit=dev --ignore-scripts` を打って入れる。導入の確認は「実行を始める直前」にだけ出し、実行中は出さない。対話できる端末が無い入口では、未導入なら止まり、版が違うだけなら警告して動かす。

live-mindmap で同じ形に当たるものを測った。node_modules は 727MB で、重いものは次のとおり。

| もの | 大きさ | 使う場面 |
| --- | --- | --- |
| Claude Agent SDK の CLI バイナリ（darwin-arm64） | 219MB | 差分更新を Claude で行うとき。ローカルモードでは読み込みもしない |
| Playwright の Chromium | 手順どおりに入れると約 557MB | セッションの終わりに、マップの画像 map.png を撮るとき |
| node-llama-cpp と GGUF のモデル | 68MB と数 GB | 差分更新を Mac の中のモデルで行うとき（計画中） |

**差分更新**は、AI が会議の発言を読み、マインドマップへの操作だけを返す処理。**ローカルモード**は、会議の中身を Mac の外に出さないと約束するモードで、Claude を呼ばない。

### 1. よそのプロジェクトの設計を借りるときは、効き目を支える前提が自分の側にもあるかを先に見る

takt の狙いは容量だ。npm で配るツールなので、`npm i takt` を打つ全員が、使わないプロバイダの分まで入れている。ところが live-mindmap は `private: true` で、clone して `pnpm install` する形でしか動かない。容量を減らしても、得をするのは clone した人だけだ。

そこで、何を借りるのかを利用者に先に聞いた。答えは、容量と「開始前にそろえる流れ」の両方で、軸は後者に置く、だった。会議の途中で導入の確認に止まるのは、takt の step が止まるよりずっと痛い。このアプリでは、`start`（セッションを始めるコマンド）の直前に、そのセッションで要るものを一覧にしてそろえるほうに価値がある。容量は、その結果としてついてくる。配る形（npm・Mac アプリ・署名）は、それだけで地図 1 枚の大きさがあるので、別の地図に回した。

**設計を借りるときは、その設計が何に効いているのかと、その前提（ここでは「npm で配る」）が自分の側にもあるかを先に確かめる。** 前提が無ければ、借りる価値は別の場所にあることが多い。

### 2. CLI を呼ぶのが AI エージェントなら、確認は CLI ではなく、エージェントの向こうの人に届ける

最初の案は、takt と同じく、CLI が端末で y/N を聞くものだった。サーバーが「要るもの」と状態を返し、CLI が確認を出して、端末でなければ止める。利用者からは「AI エージェントが起動する前提なので留意」と返ってきた。ADR 0010（CLI の作りの判断の記録）にも、「呼ぶのは AI エージェントで、exit code と stderr で失敗に気付ける」と書いてあった。読んでいたのに、案に反映していなかった。

エージェントが Bash で打つコマンドには TTY が無い。takt の「端末あり／なし」で分けると、いつも「端末なし」の側に落ち、人に確認する場面が無くなる。実際には、人はエージェントの向こうにいる。そこで次のように組み直した。

- `start` は自分では導入しない。差分更新に欠かせないものが足りなければ、専用の exit code で止まる。stderr に、足りないもの・容量の目安・打つコマンド（`cli install claude` など）を出し、「利用者に確認してから入れる」と添える
- 導入は、明示の `cli install <名前>` だけで行う。`start --install` は作らない。導入が独立したコマンドなら、人はエージェントの権限確認の画面で「何を入れるか」を見られる
- 人が端末で打つときも、y/N は出さない。経路を 1 つにして、テストを 1 本で済ませる

もう 1 つ、利点が見つかった。導入はサーバーが行う。エージェントのサンドボックスがネットワークを塞いでいても、人が立ち上げたサーバーなら外から取ってこられる。

**呼び手がエージェントの CLI では、「対話できるか」を TTY で判定しない。** 止まる理由を exit code で区別できるように返し、人の承認が要る操作は独立したコマンドに切り出す。

### 3. 開始前の確かめは、本番と同じプロセスの経路で行う。macOS の許可は、起動したアプリのものになる

`start` の前に確かめたいものには、こちらからは入れられないものもある。音声認識（SpeechAnalyzer）の日本語モデル、画面収録とマイクの許可だ。これらを確かめるのは、会議の音声と画面を取り込む Swift の子プロセス（**ヘルパー**）になる。調べ物で 2 つの落とし穴が見つかった。

- **許可は、ヘルパーを起動したアプリのものとして扱われる。** ヘルパーには Info.plist が無いので、macOS は起動元（ターミナルなど）の許可で判断する。許可を一度も求めたことのない新しいプログラムでも、起動元の許可がそのまま使われた。CLI がヘルパーを自分で起動して確かめると、会議のとき（サーバーがヘルパーを起動する）と違う答えが返るおそれがある
- **日本語モデルの状態は、プログラムの署名の識別子ごとに違う。** 小さな試作のプログラムで `AssetInventory.status(forModules:)` を呼ぶと、ja_JP が Mac に入っているのに、新しい識別子では「ダウンロードが要る」が返った。識別子が `live-mindmap-helper` のときは「入っている」が返った。また、確かめのつもりで `assetInstallationRequest` を呼ぶと、言語の予約まで起きてしまう

画面収録とマイクの許可は、ダイアログを出さずに読める（`CGPreflightScreenCaptureAccess`、`AVCaptureDevice.authorizationStatus`）。ただし画面収録は「まだ聞いていない」と「拒否された」を見分けられない。システム音声の許可は、事前に確かめる公開の手段が見つからなかった。

**事前の確かめは、本番と同じ起動の経路・同じ署名のプログラムで行う。** 確かめるための別のプログラムは、本番と違う答えを返しうる。そのうえで、確かめの API に副作用（予約やダイアログ）が無いことも確かめる。

### 4. 読み込んだときに 1 度だけ読まれる設定は、動的な読み込みに変えて、読み込む前に渡す

Playwright の Chromium の置き場所は、環境変数 `PLAYWRIGHT_BROWSERS_PATH` で管理ディレクトリに向けられる。ただしこの値は、`playwright-core` を読み込んだときに 1 度だけ読まれる。サブエージェントが試すと、読み込んだ後に環境変数を設定しても既定のキャッシュを見続けた。いまの撮影のコードは静的 import なので、動的 import に変え、環境変数を設定してから読み込む必要がある。

管理ディレクトリから SDK を読み込む形とは、相性がよい。どのみち `createRequire` で場所を解決し、`import(pathToFileURL(...))` で動的に読むので、その前に環境変数を設定すれば済む。Claude Agent SDK も、CLI バイナリの場所を指定しなければ、自分のファイルの位置から探す。管理ディレクトリから読めば、バイナリもその中から見つかり、API に届くところまで動いた。

**ライブラリが設定をいつ読むかを確かめてから、置き場所を変える。** 読み込みの時点で固まる設定は、静的 import のままでは後から変えられない。

### 5. 容量は見積もらずに測る。見積もりは外れ、測ると別の削り方も見つかる

地図を作るとき、Chromium を「約 150MB」と書いた。測ると、`playwright-core` が 13MB、ヘッドレス専用の shell が 195MB、ffmpeg が 2.5MB で、合わせて約 211MB だった。一方、README の手順（`playwright install chromium`）には `--only-shell` が付いていない。そのため、使わないフルの Chromium まで入り、約 557MB になっていた。map.png の撮影は shell だけで足りることを、heavy IT（本物のブラウザを使う重いテスト）8 件が通ることで確かめた。この地図とは別に、手順に `--only-shell` を足すだけで約 360MB 減る。

ほかの実測も、見積もりと違う方向に外れた。

| 実測 | 分かったこと |
| --- | --- |
| Claude Agent SDK 224MiB（うちバイナリ 218.6MiB）、node-llama-cpp 68MiB | node-llama-cpp は `--ignore-scripts` で入れても、`getLlama({ build: "never" })` でビルド済みの Metal 版が使われ、GGUF の生成まで動く |
| Linux x64 で `npm ci` すると、node-llama-cpp だけで 670MB を超える | CUDA・Vulkan・arm 向けのバイナリまで入る。容量を減らす仕組みが、CI ではかえって容量を増やしうる |
| node-llama-cpp の初回の `getLlama` は 17 秒、2 回目は 0.25 秒 | 温めを導入の中で済ませるかを決める必要がある |

もう 1 つのはまりどころがある。型のために SDK を devDependencies に残すと、clone の形では `pnpm install` が devDependencies も入れるので、バイナリも残る。pnpm の `ignoredOptionalDependencies` でプラットフォーム別のパッケージを外せば、型だけが残り、`tsc` も通った。

**容量を減らす設計は、対象の全プラットフォームと開発者の手順で、実際に入れて測る。** 測ると、本題とは別の安い削り方や、逆に増える場所が見つかる。

## 利用者が語彙を足す UI が要るかを決めたら、足して効く語の幅は小さく、画面ではなく開始のコマンドの引数 1 つにした話

字幕の精度を上げる地図のうち、「利用者が語彙を足す UI は要るか、要るならいつ・どこで・どんな形か」を決めたときの学び。**語彙**は、会議で話されそうな固有名詞・略語の正しい表記の集まりで、音声認識が崩した語を、発言（確定した文字起こしの 1 単位）にするときに読みで引いて直すのに使う。語彙は利用者に入力を求めずに集めるのが本命で、出どころは**共有画面**（会議アプリに映る、相手が共有している画面）の OCR と、前のセッションから引き継いだ語彙。利用者の入力は任意の上乗せ、と地図を作ったときに決めてあった。今回はコードを書いていない。測った結果と今のコードを材料に、問いを 2 回に分けて利用者に出し、どちらも推奨どおりに決まった。

- 決定の記録: 地図 [Kanary を手本に字幕の精度を上げる](https://github.com/daiki-beppu/live-mindmap/issues/386)、チケット [利用者が語彙を足す UI の要否と形を決める](https://github.com/daiki-beppu/live-mindmap/issues/512)
- 材料: [共有画面の OCR から集めた語彙の効き目を測った話](./2026-10-08.md#ocr-vocab-effect)、[過去のセッションを語彙の出どころに残すか決めた話](./2026-10-08.md#past-session-vocab)

決まった形は、画面の UI を作らず、セッションを始めるコマンドに `cli start --vocab <file>`（1 行に 1 語）を足すだけ。足せるのは開始時だけで、会議の途中では足せない。

### 1. 入力の UI の要否は、「利用者が足して、初めて直る語」がどれだけ残るかで決める

自動で集めた語彙でも直らない語は、前のチケットの測定で 3 種類に分かれていた。

- (a) 共有画面に出ない語
- (b) 画面に出ても、候補を取る規則（カタカナ 3 字以上、漢字 3〜12 字、大文字を含む英字の語）で取れない語。2 字の人名・地名、「情シス」、「1on1」など
- (c) 音声認識が、ふつうの語に崩してしまう語。「港南」が「江南」に、「野々村」が「野村」になるなど

利用者が足して効くのは (a) と (b) だけで、(c) は足しても直らない。補正には「ふつうの語の一覧（日本語の上位 5 万語）に載る区間は直さない」という守りがあり、「江南」はそこで止まるからだ。

幅も数字で見た。固有名詞・略語の多い合成の会議（台本の語 39 語）で、語が全部スライドに出たと仮定すると、規則で取れる語だけで固有名詞の正解率は 87〜90% になる。台本の語を全部語彙に入れた上限は 95% だ。利用者の入力で埋まるのは、この差の 5〜8 ポイントになる。崩れていた語で数えると 5 語・13 回だった。

**入力の UI を足す前に、自動の手段の取りこぼしを種類に分け、入力で直る種類だけの幅を出す。** 幅が小さければ、凝った入力の UI は見合わない。

### 2. 入力の口の形は、今の使い方の入口に合わせる。新しい画面を足すと、別の制約まで背負う

問いを出しながら、今のセッションの始め方をサブエージェントに調べさせた。分かったことは 3 つ。

- セッションは CLI の `cli start --app <bundle id> [--title]` からしか始まらない。始める前の画面は無い
- Web の画面には、入力欄（`<input>`・`<textarea>`・`<select>`）が 1 つも無い。画面共有で参加者に見せる前提で作られている
- 利用者ごとの設定ファイルは無い。永続するのはセッションの保存先のフォルダだけ

画面に入力欄を置くと、部品だけでは済まない。このアプリには「共有画面に出る字幕・マップを、手元の操作で跳ばさない」という好みがある。入力欄は参加者から見えない手元の置き場に置く必要があり、その置き場がまだ無い。CLI の引数なら、会議が始まる前に済むので画面は動かない。足した語は次のセッションへ引き継がれるので、ファイルを書くのは初回の 1 度で済む。形は、計測用の道具がすでに持っていた `--vocab <file>`（1 行に 1 語）にそろえた。

**入力の口は、利用者がすでに通っている入口に足す。** 入口の無い場所に入力を足すと、その場所が満たすべき制約（ここでは共有画面）も一緒に背負う。

### 3. 前に決めた規則が入口を前提にしていたら、概念ごと消すより、最小の入口を作る

「UI は要らない」で終わらせなかった理由は、前のチケットの決定にある。過去のセッションから引き継ぐ語は、「発言に出た語」と「利用者が足した語（話されたかは問わない）」と決めてあった。用語集の「語彙」の定義にも「利用者が足すこともできる」と書いてある。入口を作らなければ、この規則の後半は空のまま残る。

入口ごと消して規則と定義を書き直す道もあった。だが (a)(b) の取りこぼしは小さくても 0 ではない。それに、利用者が入れた語が次の会議にも残るという性質は、引き継ぎと組み合わさって効く。そこで、入口は残して形を最小にした。会議の途中で足す `cli vocab add` も、`cli resume`（中断したセッションの続き）で語を足す口も作らなかった。途中で足す手段は、本番で「画面に出ない語が崩れ続ける」と分かってから別の取り組みにする。

**決めかけた「要らない」が、前の決定や用語集の定義とぶつからないかを見る。** ぶつかるなら、概念を消すより、規則を満たす最小の入口を作るほうが、書き直す範囲が小さい。

### 4. 利用者が入れた語でも、守りは外さない。誤りの出る先が共有画面だから

利用者が「野村は野々村のこと」と書いたなら、その語だけはふつうの語の区間でも置き換えたくなる。だがそうすると、補正の「誤りが 0」という性質が崩れる。守りを外したときの誤りは、1000 語の語彙で 36 件あった（守りを入れると 1 件）。会議に本当に「野村さん」がいれば、その名前は全部書き換わる。しかも書き換えた字幕は、共有画面で参加者に見える。

利用者が足した語の扱いは、次の 1 点を除いて自動の語とそろえた。

- 候補を取る規則はかけない（2 字の人名や「1on1」を足せることが、この口の意味だから）
- 読みの作り方と置き換えの守りは同じ
- 違いは、話されなくても次のセッションへ引き継ぐことだけ

**利用者の入力を信じて安全の仕組みを外すかは、誤ったときに誰に見えるかで決める。** 本人だけでなく相手にも見えるなら、外さない。

### 5. 「消す手段」は、減らす規則と一緒に決める

足す口を決めると、「誤って足した語を消す手段は」と続けて決めたくなる。だが同じ地図に「語彙の大きさの上限と、語彙を育てる・減らす規則を決める」チケットが残っていた。古い語が自動で減るなら、手で消す口は要らないかもしれない。順序を逆にすると、要らない口を先に作りかねない。そこで、消す手段はそのチケットの問いに書き足して回した。

**対になる操作（足す・消す）でも、片方が別の規則に左右されるなら、その規則と一緒に決める。** 決めずに回すときは、回した先のチケットの本文に書き足して、問いを落とさない。

<a id="chatgpt-subscription"></a>

## ローカルのモデルの開き直す回数を決めに行ったら問いが縮んでいて、話のついでに出た「ChatGPT もサブスクで」は、Claude と逆に公式に認められていた話

**差分更新のモデル**（会議の発言からマインドマップへの変更を作る LLM）を、Claude・Mac の中で動くモデル・その他のプロバイダから切り替えられるようにする地図で、「ローカルのモデルで開き直す回数と文脈長」を決めたときの学び。今の Claude は、Agent SDK の query を開いたまま 14 回使い回す。2 回目からはマップの変更だけを送り、14 回ごとに開き直す。ローカルのモデルでも同じ形を保つには、回数と文脈長をいくつにするか、というのがチケットを起こしたときの問いだった。決めている途中で、利用者が「ChatGPT も Claude みたいにサブスクで使えるようにしたい」と言った。そこから規約の調べに広がった。

- 決定の記録: 地図 [差分更新をローカルの LLM でも動かし、ローカルモードでは何も外に出さない](https://github.com/daiki-beppu/live-mindmap/issues/374)、チケット [ローカルのモデルで開き直す回数と文脈長](https://github.com/daiki-beppu/live-mindmap/issues/426)・[ChatGPT のサブスクで差分更新を呼べる経路](https://github.com/daiki-beppu/live-mindmap/issues/634)
- 起こしたチケット: [ChatGPT のサブスクで差分更新を回せるかを測る](https://github.com/daiki-beppu/live-mindmap/issues/635)、[ChatGPT のサブスクの経路のサインインと上限の扱い](https://github.com/daiki-beppu/live-mindmap/issues/636)
- 前提の決定: [小さいモデル向けに差分更新の出力の形を 5 通り試した話](#local-llm-prompt-shape)

### 1. 先に決まったことで問いが縮んでいたら、残った問いだけを聞く

チケットを起こしたのは、ローカルのモデルも Claude と同じく、会話を続けて変更だけを送る前提のときだった。その後の試作で、ローカルのモデルは会話を続けず、毎回 1 から呼ぶ形に決まった（入力は 3k トークン以下）。こうなると「ローカルで何回まで開いたまま使うか」という問いは消え、開き直すのは Claude だけになる。チケットの本文には、関連するチケットが閉じるたびに「残るのはこれ」という追記が溜まっていた。そこで、元の問いではなく残った 4 つだけを、推奨を添えて聞いた。

- OpenAI 互換の口（Ollama や GPT など、利用者が設定するモデル）は、どちらの形で呼ぶか
- Claude の開き直す回数を 14 のまま残すか
- 溜まった発言で 1 回が大きくなるときに、どうするか
- 互換の口の設定例に書く文脈長

決まったのは次のとおり。互換の口はすべて毎回 1 から呼び、会話を続ける形は Claude だけが持つ。Claude の回数は 14 のまま、モデルの設定から外してコードの定数にする（設定は 8 項目から 7 項目になる）。

**チケットの問いは、起こした時点の前提で書かれている。** 取りかかる前に、後から閉じたチケットの決定と突き合わせ、まだ意味のある問いだけに絞る。

### 2. 文ごとに分類する出力では、文脈長より先に出力の上限に当たる

溜まった発言の扱いでは、最初は文脈長（Apple Intelligence は 8192 トークンで固定）を超えるかが論点だと思っていた。だがローカル向けの形は、サーバーが発言を文に切り、モデルが文ごとに種類と 40 字以内の要約を返す。出力が文の数に比例して伸びる。試作では、出力が止まらなくなるのを防ぐために上限を 600 トークンにしていた。数分ぶんの発言が溜まると、先に当たるのはこちらになる。

そこで、ローカル向けの形でだけ、1 回に渡す文の数に上限を置いた。あふれた文は捨てずに、次の呼び出しに回す。この作りは「呼び出しは同時に 1 つまで、その間に溜まった発言は次の 1 回にまとめる」という今の仕組みにそのまま乗る。採らなかった案は 2 つ。1 回の中で何度も呼ぶと、その間は画面が止まる。あふれを失敗として扱うと、溜まった会議の中身が丸ごと落ちる。そのかわり、たくさん溜まった後は遅れの回復に時間がかかる。「遅れは 1 回の時間の 1〜2 倍で止まる」という前の見積もりは、溜まっていないときにだけ成り立つ、と書き添えた。

**出力の量が入力に比例する形を選んだら、文脈長と出力の上限の両方で、溜まった最大の 1 回を見積もる。**

### 3. サブスクで使ってよいかは、OSS かどうかではなく「誰が作ったアプリか」で分かれる

利用者は「Claude も ChatGPT もサブスク用の SDK で動く、と明記したい。書けない理由があったか」と聞き、続けて「今の OSS の状態でもダメか」と聞いた。リポジトリには、「Claude のサブスクの認証は案内しない」という決定が、規約を根拠にすでに残っていた。ただ、その記録は要約だったので、規約のページを読み直した。

規約は、商用かどうかや OSS かどうかでは分けていなかった。分けているのは、Anthropic のアプリか、開発者が作るアプリかだ。

> Developers building products or services that interact with Claude's capabilities, including those using the Agent SDK, should use API key authentication

MIT で公開していても、Agent SDK で作ったアプリはこれに当たる。

読み直すと、記録を書いた後に足されたらしい一文もあった。

> Nor does it prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription

改変していない Claude Code の CLI（`claude -p`）を子プロセスで呼べば、この例外に入る余地がある。そう伝えたところ、利用者は採らなかった。「`claude -p` はサブスクでは使えなくなる、というリリースが出たこともあった」からだ。例外の解釈に頼る経路は、規約の文面が変わると足場ごと消える。Claude は API キーのままにした。

**規約の判断を記録から引くときは、根拠のページを読み直す。** 要約は書いた日の文面で止まっていて、例外が足されていることもある。そのうえで、例外に乗るかは、文面がどれだけ明示か、取り消されたときに何を失うかで決める。

### 4. 先行する OSS は「動く」とは書いても「勧める」とは書いていない

利用者から「takt（複数の AI エージェントを YAML のワークフローで回す OSS）はどう書いているか」と聞かれ、README を読んだ。対応する経路として、Agent SDK・Codex SDK・Claude Code CLI などを並べている。規約については次の一文だけだった。

> **OAuth usage:** Whether OAuth is permitted varies by provider and use case. Check each provider's terms of service before using TAKT.

環境変数の例はどれも API キーだった。サブスクで動く経路は持っているが、勧めるかどうかは利用者に任せ、案内する例は API キーにそろえている。

**先行例を真似るときは、作りと案内の書き方を分けて見る。** 作りが同じでも、案内でどこまで言っているかは別に決まっている。

### 5. 同じ「サブスクで使いたい」でも、プロバイダごとに向きが逆のことがある。調べる前に決めつけない

ChatGPT については、調べる前に「Claude と同じく、第三者のアプリには認めていない可能性もある」と利用者に言った。調べはサブエージェントに任せ、途中で「規約を一番の論点に」と追加で伝えた。結果は逆だった。2026-09-29 の DevDay で出た Sign in with ChatGPT の「ChatGPT プラン利用」が、OSS とローカルで動くアプリにはっきり許していた。

> your open-source app can request permission to use the user's ChatGPT plan for eligible Responses API requests

有料のアプリやホスト型のアプリには申請が要るが、各自の Mac で動く MIT のアプリは対象に入る。意外だったので、サブエージェントの報告を受け取ったあと、引用元のページを自分でも開いて文言を確かめた。

経路の形も、思っていたのとは違った。利用者は「サブスク用の SDK」と考えていたが、Codex SDK は使わない。338MB と重く、中身がコーディングエージェントだからだ。代わりに、OAuth で受け取ったトークンで Responses API を直接呼ぶ。前の応答を引き継ぐ `previous_response_id` は使えないので、毎回 1 から呼ぶ形になる。節 1 で決めた「会話を続けるのは Claude だけ」とちょうど合った。利用者の「takt みたいに設定ファイルでプロバイダーを変えるだけで切り替えたい」という好みにも、設定の `route` の値を 1 つ増やすだけで乗る。

まだ確かめていないことが 4 つある。構造化出力が通るか、1 回の時間、Plus の 5 時間の上限（他のアプリと共有）をどれだけ使うか、品質だ。これはログインして測るタスクとして起こした。

**規約の調べは、1 社の結論を他社に当てはめずに、プロバイダごとに一次情報で確かめる。** 意外な結論は、報告を受け取った側でも引用元を開いて確かめてから、決定の材料にする。

## Haiku 5.5 と Sonnet 5.5 を同じ会議で比べたら、料金は 1/10 になったが、考える量が増えて速くはならず、SDK の返す使用量と費用もそのままでは数えられなかった話

[Haiku 5.5 と Sonnet 5.5 を比べる地図を作った話](#haiku-5-5-compare) の続きで、差分更新のモデルだけを Haiku 5.5 に差し替え、同じ素材で回帰評価にかけたときの学び。**差分更新**は、AI が会議の発言を読み、マインドマップへの操作だけを JSON で返す処理だ。素材は音声合成で作った架空の会議 2 本で、23 分の四半期レビュー（画面共有つき、正解は決定 5・TODO 7）と、55 分の社内会議（正解は決定 4・TODO 5）を使った。各モデル 2 本ずつ流し、出来たマップに正解の決定・TODO がどれだけ載ったか（再現率）を数えた。モデルの差し替えは評価用の一時的なパッチで行い、本体には入れていない。

- 決定の記録: チケット [Haiku 5.5 と Sonnet 5.5 を同じ素材で cli eval にかける](https://github.com/daiki-beppu/live-mindmap/issues/614)、地図 [Haiku 5.5 を差分更新のモデルとして Sonnet 5.5 と比べる](https://github.com/daiki-beppu/live-mindmap/issues/612)

| | Sonnet 5.5 | Haiku 5.5 |
| --- | --- | --- |
| 決定の再現率（23 分の会議） | 4/5・4/5 | 2/5・3/5 |
| TODO の再現率（55 分の会議） | 3/5・3/5 | 2/5・1/5 |
| 1 会議の料金（55 分の会議） | $1.12・$1.07 | $0.11・$0.11 |
| 発言から反映までの遅れ（23 分の会議を等速で、中央 / 最大） | 5.5 / 10.5 秒 | 7.0 / 23.7 秒 |

品質の下限は「Sonnet 5.5 から落ちないこと」と決めてあり、Haiku 5.5 はそれに届かなかった。既定を替えるか、選べるモデルとして足すかは、次のチケットで利用者と決める。

### 1. effort を揃えても、考える量は揃わない。小さいモデルが速いかは、出力の量まで含めて測る

前の調べ物で、effort（どれだけ考えるかの段階）の既定値がモデルでずれると分かっていた。そこで、両方とも `options.effort: "medium"` を明示して揃えた。それでも、Haiku 5.5 は thinking（答える前の思考）のトークンを Sonnet 5.5 の 8〜9 倍出した。23 分の会議の 1 会議分の合計で、7.0k に対し 59.6k だった。

公表の位置づけは、Haiku 5.5 が「Fastest」、Sonnet 5.5 が「Fast」だ。1 秒あたりに出すトークンは、たしかに Haiku が約 2 倍速かった（約 195 対 105 tok/s。出力の合計を呼び出しの秒数の合計で割った、粗い値）。ところが 1 回の出力が 3 倍前後あるので、待ち時間なしで流したときの 1 回の秒数は、中央で 5.1 秒に対し 10.3 秒になった。

**同じ effort の名前でも、どれだけ考えるかはモデルごとに違う。「速いモデル」は、自分の課題で 1 回の出力の量まで含めて測る。** 公表の速さは、トークンあたりの速さでしかない。

### 2. 料金の比は、単価の比どおりにはならない。出力と読み出しの量が変わる

単価だけを見れば、Haiku 5.5 は Sonnet 5.5 の 1/20（キャッシュの読み出しは 1/10）だ。実際の 1 会議の料金は 1/7〜1/10 だった。原因は 2 つある。出力が約 3.5 倍に増えたこと（thinking の分）と、キャッシュの読み出しが 1.2〜1.7 倍に増えたことだ。後者は、長い出力が会話の履歴に積もり、次の回にまた読まれるためだ。

**モデルを替えた料金の見積もりは、単価の比ではなく、そのモデルで実際に流したトークン数で出す。** このアプリのように会話を使い回す作りでは、出力の量が次の回の入力にも跳ね返る。

### 3. SDK の返す使用量は、1 回の呼び出しの最後の要求の分しか持たないことがある。合計の累計と突き合わせて数える

料金は、SDK が返す概算の費用（`total_cost_usd`）ではなく、トークン数に公式の単価を掛けて出すと決めてあった。そこで、呼び出しごとに結果の `usage` を記録した。1 本目を流した後、`usage` の数字から計算した費用を、会話ごとの概算の費用の増え方と突き合わせた。すると、合わない回があった。

調べると、構造化出力を一度やり直した回では、内部で API への要求が 2 回走っていた。ところが `usage`（とその中の `iterations`）には、最後の 1 回の分しか入っていなかった。そこで数え方を次のように変え、8 本を最初から流し直した。

- 合計は、会話ごとの累計である `modelUsage` の差分から取る
- 要求ごとの入力の大きさ（10 万トークンを超えたかの判定に使う）は、要求ごとの assistant メッセージの `usage` から取る
- 両者の入力の合計が一致するかを、全部の回で検算する

流し直した 1 本目では、検算が 3 回ずれた。原因は、SDK の中の Claude Code が会話を開くたびに、別のモデル（Haiku 4.5）で小さな補助の呼び出しを 1 回していたことだった（入力 1〜3k・出力 20 前後）。`modelUsage` にはモデルごとの累計が入るので、差分更新のモデルの分だけを取り、補助の分は別に数えた。これで、ずれは 0 になった。

概算の費用のほうは、Haiku 5.5 では実際の約 36 倍になった（23 分の会議で $2.75 対 $0.076）。同梱の CLI が、まだ Haiku 5.5 の単価を知らないためだと見ている。

**SDK の返す使用量で費用を出すときは、1 つの数字を信じず、要求ごとの値と累計の 2 通りで数えて突き合わせる。** 合わなかった差から、やり直しの要求や補助の呼び出しのような、見えていなかった呼び出しが見つかる。

### 4. 品質の落ち方は、失敗の数ではなく、捨てられた操作と再現率に出る

スキーマ違反と失敗は、両方のモデルとも 0 回だった。JSON スキーマでの構造化出力が効いているので、形は崩れない。差が出たのは中身だった。マップに当てられずに捨てられた操作（親が無い、などの理由）は、23 分の会議で Sonnet 5.5 が 2・5 件、Haiku 5.5 が 20・29 件だった。決定・TODO の再現率も、1〜2 件ずつ落ちた。

**構造化出力のある作りでは、小さいモデルへの差し替えで「エラーが出ないこと」を品質の証拠にしない。** 返した操作が実際に当たったかと、正解との照合で見る。

### 5. 待ち時間なしの再生で測った遅れと料金は、実際の会議と違う。見積もりではなく、等速で測る

回帰評価は、ふだん待ち時間なしで再生している。速く終わり、過去の計測とも同じ条件で比べられるからだ。利用者に「反映までにかかる時間は？」と聞かれ、この点を見落としていたことに気づいた。待ち時間なしでは、発言が一度に届くので、差分更新は 2 発言ずつの呼び出しになる。実際の会議では、発言の間隔（この会議で中央 17 秒）が、1 つでも呼ぶまでの無音の判定（1.5 秒）より長い。そのため、ほぼ 1 発言ずつの呼び出しになる。

最初は、発言の時刻と、待ち時間なしで測った 1 回の秒数を組み合わせて見積もった。Haiku 5.5 の遅れは、中央 12〜13 秒・最大 51 秒と出た。そのあと等速で流して実測すると、中央 7.0 秒・最大 23.7 秒だった。1 発言ずつだと 1 回の入力が小さく、Haiku 5.5 の 1 回の秒数が中央 10.3 秒から 5.4 秒に縮んだからだ。見積もりは、この変化を入れていなかった。

料金も変わった。呼び出しが 2 倍（39 回から 78 回）になり、Sonnet 5.5 の 1 会議の料金は $0.58〜0.64 から $0.89 に上がった。Haiku 5.5 との比（1/9.3）は、ほとんど変わらなかった。

**比べるだけなら、待ち時間なしの再生で足りる。利用者が体感する遅れと、実際に払う額を答えるときは、等速で流して実測する。** 呼び出しのまとめ方が変わると、1 回の大きさも回数も変わり、見積もりはそれを取りこぼす。

<a id="haiku-5-5-choice"></a>

## Haiku 5.5 を既定にするかを決めたら、下限を割っても料金の差で調べ直すことになり、プロンプトの持ち方は公式のガイドの作りがそのまま答えだった話

[Haiku 5.5 と Sonnet 5.5 を同じ会議で比べた話](#haiku-5-5-eval) の結果をもとに、利用者と 2 つのことを決めた。1 つは、差分更新のモデルの既定を Haiku 5.5 に替えるか。もう 1 つは、既定にしない場合でも、Haiku 5.5 を利用者が選べるモデルとして足すかだ。比べた結果は、Haiku 5.5 の決定・TODO の再現率が 1〜2 件ずつ落ち、1 会議の料金は約 1/9、発言から反映までの遅れは裾で約 2 倍、というものだった。このアプリの設定では、利用者は `~/.live-mindmap/config.json` に名前を付けたモデルを書いて選ぶ。`claude` など少数の名前だけは、設定に書かなくても組み込みで選べる。

- 決定の記録: チケット [差分更新の既定のモデルを替えるか、Haiku 5.5 を選べるモデルに足すか](https://github.com/daiki-beppu/live-mindmap/issues/615)、地図 [Haiku 5.5 を差分更新のモデルとして Sonnet 5.5 と比べる](https://github.com/daiki-beppu/live-mindmap/issues/612)
- 次の手: [Haiku 5.5 の effort を low と high にして cli eval にかける](https://github.com/daiki-beppu/live-mindmap/issues/654) → [Haiku 5.5 向けの SYSTEM の追記を作って cli eval にかける](https://github.com/daiki-beppu/live-mindmap/issues/655) → [チューニングした Haiku 5.5 を差分更新の既定にするか](https://github.com/daiki-beppu/live-mindmap/issues/656)

### 1. 品質の下限を割ったら終わり、ではない。差が一桁あるなら、届かせる手を先に試す

地図には、物差しを先に決めてあった。品質の下限は「Sonnet 5.5 から落ちないこと」で、それを満たした上で遅れと料金で決める、というものだ。私（エージェント）はこの物差しをそのまま当てはめた。下限を割り、速くもならないのだから、既定は替えず、これで閉じる案を推した。

利用者の答えは「チューニングでなんとかならないか調査。価格が安いのはデカすぎる」だった。物差しは「何で決めるか」の順番であって、1 回の測定で候補を捨てる規則ではなかった。比べたのは、プロンプトも effort（モデルがどれだけ考えるかの段階）も Sonnet 5.5 に合わせたままの Haiku 5.5 だ。料金の差が 1/9 もあるなら、Haiku 5.5 に合わせて調整した上で、もう一度測る価値がある。

結局、既定の判断は保留にした。調整の段を 2 つ（effort、次にプロンプト）チケットにし、その結果を見て決め直す。

**物差しで負けた候補でも、得るものが一桁違うなら、「そのまま比べた」のか「その候補に合わせて調整して比べた」のかを確かめてから捨てる。** 調整していない比較は、その候補の下限ではなく、今の作りに合うかを測っただけだ。

### 2. 保証しないモデルは、組み込みの名前にせず、設定に書けるだけにする。差は案内に書く

選べるようにする形には、3 つの案があった。組み込みの名前（`--model haiku` だけで選べる）にする、設定に書けば選べるだけにして README で案内する、案内しない、の 3 つだ。

選んだのは 2 つ目だった。組み込みの名前は、`claude` と同格の推奨に見えてしまう。案内しなければ、書けることを誰も知らない。README の設定例には、測った差（料金が約 1/9、決定・TODO が 1〜2 件落ちる、遅れの裾が約 2 倍）を添え、品質は保証しないと書く。

この逃げ道があるおかげで、既定に替える基準を緩めずに済んだ。既定は、何も選ばない全員が受け取る品質だ。安さを取りたい人は、設定に 1 行書けばよい。そこで、既定に替える基準は「Sonnet 5.5 から落ちない（2 本ずつ測って、差は 1 件まで）」のまま残した。遅れの基準は、等速で流したときの p90 が 12 秒以内（Sonnet 5.5 の 8.0 秒に、ばらつきの分を見込んだ 1.5 倍）とした。

**保証できるかで、見せ方の格を分ける。保証しないものにも選べる道を残しておくと、既定の基準を高いまま保てる。**

### 3. 評価で揃えた条件は、製品にも固定する。製品は effort を指定していなかった

前の評価では、両方のモデルに effort `medium` を明示して比べた。ところが製品のコードを読むと、モデル名の定数があるだけで、effort はどこでも指定していなかった。製品は、同梱の Claude Code の既定の effort で動いていたのだ。既定の値はモデルによってずれうる（Haiku 5.5 は high になりうる）し、SDK の更新でも変わりうる。そうなると、評価で出した速さと料金の数字は、製品の振る舞いを表さなくなる。

そこで、Claude の経路では `effort: "medium"` を定数として明示すると決めた。

**比べるときに明示した設定は、製品の側でも同じ値を明示する。** 評価の側だけで揃えても、製品が既定に任せている限り、その比較は製品の比較にならない。

### 4. モデルごとのプロンプトの持ち方は、公式のガイドの作りが答えになっていた

調整の段でプロンプトを直すとき、持ち方を 2 通り比べた。

1. Claude の 2 つのモデルで 1 つのプロンプトを共有し、直したら両方で測り直す
2. Haiku 5.5 専用のプロンプトを持つ

私は 1 を推した。プロンプトが増えると評価の組が増えるからだ。それに「Haiku 5.5 で崩れる箇所は、Sonnet 5.5 にとっても曖昧な指示だろう」と見込んでいた。利用者は「2 のほうがいいかも。公式のプロンプトガイドを見て判断」と返した。

[Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) は、全モデル共通の技法と、モデルごとのページに分かれていた。モデルごとのページは「この振る舞いを見たら、この文を足す」という形で書かれている。共通のページには「特定のモデルで測った技法は、別のモデルに使う前に、自分の評価で確かめ直す」とある。私の見込み（崩れる箇所は両方に効く）は、ガイドの前提と逆だった。

そこで持ち方は、2 つの案の間を取った。SYSTEM（システムプロンプト）の本体は共有し、Haiku 5.5 にだけ追記を足して、追記は Haiku 5.5 の評価でだけ確かめる。完全に別のプロンプトにすると、本体を直すたびに 2 箇所を直すことになる。

**モデルごとにプロンプトを分けるかは、推測で決めず、ベンダーのガイドの作りに合わせる。** Claude なら「共通の本体＋モデルごとの追記」で、追記はそのモデルでだけ確かめる。

### 5. 小さいモデルの調整は、effort が先。プロンプトの文では thinking は止まらない

[Prompting Claude Haiku 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-haiku-5-5) によると、Haiku 5.5 の主な調整手段は effort だ。ガイドには「プロンプトで『すぐ答えて』と書いても、thinking は止まらなかった」とあり、`high` は「指示に厳密に従わせる」用途に向くとされている。前の評価で見えた症状（thinking が 8〜9 倍、捨てられた操作が 4〜6 倍）は、プロンプトより先に effort で触るべきものだった。

ガイドには、Haiku 5.5 の既知の崩れ方も並んでいた（検索の抜け、自前のツールと JSON 出力の組み合わせ、長いエージェントでの早い停止、チャットボットでの指示の守り）。ただし、このアプリの症状（決定を落とす、当たらない操作を出す）に当たるものは無かった。そのため、プロンプトの追記は、ガイドの文をそのまま足すのではなく、評価で落ちた箇所を読んで作る。

順番は、手間の小さい順に決めた。まず effort の low と high を、23 分の会議で 1 本ずつ流して絞り込む。残った段だけを、2 本の会議で 2 本ずつ流して判定する。届かなければプロンプトの追記に進む。会話を開き直す回数を減らす案は、費用の計測をやり直すことになるので外した。

**モデルの調整は、コードの変更が 1 行で済む設定から試し、1 本の測定で見込みのない段を切ってから、判定の量を流す。**

## 開始前に何を確かめ、足りないときにどう返すかを決めたら、前提の半分が別の地図で削られていて、「確かめるだけ」のはずのものが「入れる」側に移った話

[takt の「重い依存は使うときだけ入れる」を真似る地図を作った話](#managed-deps)の続きで、地図の最初の決めるチケットを片づけたときの学び。問いは 2 つあった。セッション（会議 1 本分の作業）で要るものの一覧を何から決めるか。そして、`start` の前の確かめが、CLI を呼ぶ AI エージェントに何を返すか。今回もコードは書いていない。

- 決定の記録: チケット [セッションで要るものの決め方と、開始前の確かめの返し方](https://github.com/daiki-beppu/live-mindmap/issues/623)、地図 [重い依存を使うときだけ入れ、start の前にそろえる](https://github.com/daiki-beppu/live-mindmap/issues/619)
- 用語集に足した語: **開始前の確かめ**（[PR #650](https://github.com/daiki-beppu/live-mindmap/pull/650)）

### 1. 別の地図の前提に乗っているときは、問いを立てる前に、その地図の決定の一覧を読む

この地図の Notes（地図の冒頭に置く、合意の控え）には、「入れるところまで受け持つもの」が 4 つ並んでいた。Claude Agent SDK、node-llama-cpp、GGUF のモデル、Chromium だ。node-llama-cpp と GGUF は、Mac の中で LLM を動かす**内蔵**のモデルのためのもの。内蔵は、差分更新（AI が会議の発言からマインドマップへの変更を作る処理）をローカルで動かす別の地図で計画されていた。

質問を書く前に、その地図の決定の一覧を読んだ。すると内蔵は、もう削られていた。16GB の M4 で 1 回の推論が中央 21 秒かかり、発言の間隔（中央 35 秒）に追いつけない、という実測が理由だ。削られたのは同じ日の 14 時半ごろで、この地図を作ったのはその 2 時間後だった。地図を作ったときに相手の地図を読み直さなかったので、Notes は削られる前の前提のまま書かれていた。

そのまま質問していたら、「GGUF の pull を `cli install` に寄せるか」「内蔵とこの地図のどちらを先に実装するか」を利用者に聞くところだった。もう要らない判断だ。最初の質問を「内蔵を外すか」にした。外すと、管理ディレクトリ（`~/.live-mindmap/` の下の、重い依存を入れる場所）に入るものは半分になり、地図の未決の項目も 1 つ消えた。node-llama-cpp の読み込み方の調べの結果は、内蔵が戻ってきたときの資料として残した。

**地図どうしが前提を共有しているときは、相手の地図の決定の一覧を先に読み、消えた前提を最初の質問にする。** 同じ日に並行で進む地図では、作った時点ですでに古い前提が入りうる。地図を作るときにも、チケットを片づけるときにも読む。

### 2. 「入れるか、確かめるだけか」は、ファイルの持ち主ではなく、足りないときに誰が直せるかで分ける

最初の分け方では、音声認識（SpeechAnalyzer）の日本語モデルは「確かめるだけ」の側にいた。モデルは OS が持つもので、管理ディレクトリには入らないからだ。

ところが、足りないときの直し方を詰めると、行き場が無かった。システム設定から入れる道は無く、取りに行けるのは、こちらのヘルパー（音声と画面を取り込む Swift の子プロセス）が呼ぶ `assetInstallationRequest` だけだ。止めるだけで入れる道を案内しなければ、利用者は詰む。警告して始めれば、いまどおりヘルパーが開始時に取りに行き、会議の冒頭が止まる。この地図が避けたいことそのものだ。

そこで、日本語モデルを「入れるところまで受け持つもの」に移した。`cli install speech-ja` で、サーバーがヘルパーに予約と取得をさせる。Mac にはあるが、ヘルパーの署名の識別子でまだ予約していないだけの場合も、「未導入」に数える。直すのは同じコマンドで、すぐ終わる。

**管理の分け方は「どこに置くか」ではなく、「欠けたときに、このアプリのコマンドで直せるか」で切る。** 直せるのがこちらだけなら、置き場所が OS でも、入れる側に入れる。

### 3. 止めるのは、中心の出力が作れないときだけ。一部の出力が減るだけなら、知らせて始める

足りないものごとに、「開始しない」と「警告して開始する」を振り分けた。基準は 1 本にした。差分更新ができなければ、マップができない。だから止める。それ以外は、何が減るかを書いて始める。

| 足りないもの | 扱い | 減るもの |
| --- | --- | --- |
| 選んだモデルが使うもの（Claude なら Agent SDK）、ヘルパーのビルド、日本語モデル | 開始しない | マップそのもの |
| Chromium | 警告して開始 | map.png（マップの画像）だけ |
| SDK・Chromium の版違い | 警告して開始 | 無し（固定版とずれているだけ） |
| 画面収録の許可 | 警告して開始 | AI に渡す共有画面 |
| マイクの許可 | 警告して開始 | 自分の声。拒否のときは警告にそう書く |

許可を止める理由にしなかったのには、事情もある。画面収録は、ダイアログを出さずに読めるが、「まだ聞いていない」と「拒否された」を見分けられない。止めると、一度も聞かれていない人まで、始められずに詰む。始めれば、未決定の人には開始時にダイアログが 1 度だけ出る。システム音声の許可は事前に確かめる手段が無いので、確かめない。この利用者には、もともと「イヤホン必須のような使い方の前提を課さず、どのケースでも動く案を選ぶ」という好みがあり、それとも合う。

**開始を止める条件は、成果物の中心が作れないかどうかの 1 本にする。** 確かめられない状態（未決定と拒否の区別など）を止める理由にすると、確かめの精度の低さがそのまま利用者の詰みになる。

### 4. 確かめの経路は、入口ごとの本番の経路に合わせる。経路が違えば、確かめのコマンドも分かれる

要るものは、「入口」と「モデルの種類」の組み合わせで決めた。

- `start`・`resume`（ライブの会議）: ヘルパーの項目（ビルド・日本語モデル・許可）が要る
- `play`（録音済みの会議の再生。回帰評価に使う）: ヘルパーを使わないので要らない
- モデルの種類: Claude なら Agent SDK、Apple Intelligence なら使えること、ChatGPT ならサインイン済みであること、OpenAI 互換の口なら何も要らない
- Chromium は、どの入口でも任意

ここで、`cli check`（始めずに確かめるだけのコマンド）の行き先が問題になった。前の調べで、macOS の許可はヘルパーを起動したアプリのものとして扱われる、と分かっていた。ライブの会議では、サーバーがヘルパーを起動する。だから `start` 向けの確かめもサーバー経由で行い、サーバーにつながらなければ、ほかのコマンドと同じく止める。CLI が自分でヘルパーを起動して確かめるフォールバックは作らない。違う答えが返りうるからだ。

一方、`play` はサーバーを通らず、CLI のプロセスの中で差分更新を呼ぶ。こちらは `cli check --for play` として、CLI の中だけで確かめる。決める前は、確かめのコマンドは 1 つのつもりだった。コードを読んで `play` だけがサーバーを使わないと分かり、2 つに分かれた。

**確かめは、その入口が本番で通る経路と同じ経路で行う。** 入口ごとに経路が違うなら、確かめも入口ごとに分けたほうが、答えがずれない。

### 5. 呼び手が AI エージェントなら、「人の承認が要る」という止まり方に専用の exit code を割り当てる

エージェントは、止まった理由を stderr の文からも読める。ただし文は、言い回しを変えれば読み方が変わる。そこで「必須のものが足りない。入れれば進むが、入れるには利用者の承認が要る」という止まり方に、exit code 3 を割り当てた。1 は、いまの一般の失敗のまま残す。`cli check` も、足りなければ同じ 3 を返す。

止まるときは stdout に何も出さず、stderr に 3 行を出す。

```
開始しません。足りないもの: claude（Claude Agent SDK、約 224MB）、speech-ja（日本語の音声認識モデル）
入れるには: pnpm cli install claude speech-ja
利用者に確認してから入れてください
```

容量は、実測できたもの（SDK 224MB、Chromium 211MB）だけを書く。日本語モデルは、公開の API ではダウンロードの前に容量が分からない。実測値を固定で持つ案もあったが、OS の版で変わる値はすぐ古くなる。だから書かない。

**エージェントに返す失敗は、次に取る行動が違うものごとに exit code を分ける。** 文面は人の確認を促すために書き、行動の分岐は数字で渡す。確かめられない数字は、古くなった数字より害が大きいので、出さない。

<a id="managed-deps-install"></a>

## 重い依存の置き場所と `cli install` の振る舞いを決めたら、失敗したときの戻し方は入れ方から自然に決まり、進み具合の返し方はエージェントの Bash のタイムアウトで決まった話

[開始前の確かめの返し方を決めた話](#preflight-check)の次のチケットを片づけたときの学び。決めたのは 3 つ。重い依存（Claude Agent SDK のバイナリ込みで約 224MB、Playwright の Chromium で約 211MB）を `~/.live-mindmap/` の下にどう置くか。固定版をどこに持つか。それを入れる `cli install` / `cli update` がどう振る舞うか。今回もコードは書いていない。質問 8 つに推奨の答えを添えて出し、利用者はすべて推奨どおりで答えた。判断が割れなかったぶん、推奨を作るときに何を基準にしたかを残す。

- 決定の記録: チケット [管理ディレクトリと固定版、cli install / cli update の振る舞い](https://github.com/daiki-beppu/live-mindmap/issues/624)、地図 [重い依存を使うときだけ入れ、start の前にそろえる](https://github.com/daiki-beppu/live-mindmap/issues/619)
- 手本: takt の [#1738](https://github.com/nrslib/takt/issues/1738)（プロバイダの SDK を本体の依存から外し、同梱した lock に対して管理ディレクトリで `npm ci` する）

### 1. 入れ方を「作業用ディレクトリで入れてから rename」にすると、全体の manifest も、失敗したときの戻し方も要らなくなる

チケットの問いは「manifest の形（入れたものごとに、版と入れた時刻など）」から始まっていた。全体を 1 つの `manifest.json` にまとめる形が、最初に浮かぶ。

先に入れ方を決めた。takt と同じく、作業用ディレクトリに `npm ci --omit=dev --omit=peer --ignore-scripts` で入れる。ハッシュを確かめて、その中に `.ready.json`（版・入れた時刻・ハッシュ）を書く。そこまで済んだら `<版>-<uuid>/` へ rename し、`current` のリンクも一時リンクからの rename で差し替える。

```
~/.live-mindmap/deps/
  claude/
    current -> 0.3.288-<uuid>/
    0.3.288-<uuid>/   (node_modules と .ready.json)
    install.lock
  chromium/
    current -> ...
    browsers/         (PLAYWRIGHT_BROWSERS_PATH。版をまたいで共有)
```

こう入れると、`current` が指す先には必ず `.ready.json` がある。「準備ができているか」は「`current` の `.ready.json` の版が、同梱の固定版と一致するか」の 1 点で決まる。全体の manifest を別に持つと、実体と記録の 2 つを同時に書き換えることになり、その間で落ちたときの食い違いを考える羽目になる。

地図の未決の項目には、「導入が途中で失敗したときの戻し方」が別に立っていた。この入れ方なら、失敗したら作業用ディレクトリを捨てるだけで、`current` は前の版を指したまま残る。項目は、問いにする前に答えが出た。

**状態の記録は実体の中に置き、差し替えは rename 1 回で済ませる。** そうすれば、記録と実体の食い違いも、途中で落ちたときの戻し方も、設計の外に追い出せる。

### 2. 進み具合の返し方は、呼び手のツールの制限で決まる。エージェントの Bash は既定で 2 分で切れる

導入はサーバーが行い、CLI はそれを頼むだけ、と前のチケットで決めていた。残る問いは、CLI がいつ返るかだ。

- 終わるまで待つ。サーバーは応答を流し続け、CLI は段階（ダウンロード・展開・確認）を 1 行ずつ stderr に出す
- すぐ返して、裏で入れる。終わったかは `cli check` で見る

この CLI を呼ぶのは AI エージェントで、Claude Code の Bash ツールは既定で 2 分で切れる。224MB のダウンロードは、回線によっては 2 分を超える。ここだけを見ると、すぐ返す形がよく見える。

ただ、すぐ返す形にすると、開始前の確かめの状態（`ready`・`missing`・`outdated`・`absent`）に `installing` が加わる。`start` も `cli check` も、「入れている途中」を扱わなければならなくなる。待つ形のまま、stderr に「時間がかかるので run_in_background で呼んでよい」と添えれば、エージェントは自分で背景に回せる。同時に 2 件頼まれたら、2 件目は待たせず「導入中です」と exit 1 で返す。待たせると、2 件目も 2 分の壁に当たるからだ。

**長い処理の API は、呼び手のタイムアウトを先に調べてから形を選ぶ。** 呼び手の側に背景で走らせる手段があるなら、こちらの状態を増やすより、その手段を案内するほうが安い。

### 3. 固定版を 2 か所に書くなら、ずれを検査で落とす

依存から外しても、型は要る。SDK と `playwright-core` は、`import type` のために devDependencies に残す。管理ディレクトリに入れる版は、同梱の `server/managed/<名前>/package-lock.json`（npm の lock。利用者の手元に pnpm があるとは限らないので npm にした）が決める。版を書く場所が 2 つになる。

片方だけを上げると、型は新しい版で通り、実行は古い版で動く。どちらも単体では壊れないので、気づくのが遅れる。そこで、両者の版が一致するかを `server/scripts/check-managed-lock.ts` が確かめ、`pnpm typecheck` で落とすことにした。このリポジトリには、ソースを読んで規則違反を `path:line` で落とす `check-*.ts` がすでに並んでいて、その 1 つとして足す。

**同じ事実を 2 か所に書かざるを得ないときは、片方を正にして、もう片方とのずれを CI で落とす。** 手順書に「両方上げる」と書くだけでは守られない。

### 4. 「対象外」のものに名前を付けたら、エラーにせず、何もしないで 0 を返す

`cli install` の名前は `claude`・`chromium`・`speech-ja` の 3 つ。`speech-ja` は、OS が持つ日本語の音声認識モデルで、ヘルパー（音声を取り込む Swift の子プロセス）に予約と取得をさせるだけだ。管理ディレクトリにも固定版にも乗らない。だから「版違い」が起きず、`cli update` で直すものが無い。

`cli update speech-ja` をエラーにする案もあった。しかしエージェントは、`cli check` の出力を見て、名前を並べてそのまま渡すことがある。対象外の名前が 1 つ混ざっただけで全体が失敗すると、エージェントは原因を調べ直すことになる。「OS が更新するので不要」と 1 行出して exit 0 にした。逆に、未導入のものを `cli update` で指したら exit 1 にした。こちらは、`cli install` を打つという別の行動が要るからだ。

**exit code を 0 にするか 1 にするかは、呼び手が次に別の行動を取る必要があるかで決める。** 何もしなくてよい場合は、たとえ空振りでも 0 を返す。

### 5. 調べの結果が足した問いは、ほかの決定で消えていないかを確かめてから聞く

このチケットには、前の調べの結果から問いが 4 つ足されていた。そのうち 2 つは、node-llama-cpp（内蔵の LLM）のものだった。Linux x64 で `npm ci` すると CUDA・Vulkan 向けのバイナリまで入って 670MB を超える件と、初回の `getLlama` が 17 秒かかる件だ。

内蔵は、前のチケットの時点で別の地図で削られていた。この 2 つは聞かずに、「扱わない」と解決コメントに書いて閉じた。前のエントリで、別の地図の前提が消えていたのに気づくのが遅れた。そのときの教訓を、チケットの中の問いにも当てた形だ。

**チケットに後から足された問いは、足された時点の前提で書かれている。** 聞く前に、その前提がまだ生きているかを確かめる。

## ChatGPT のサブスクの上限の扱いを決め、地図を仕様・形式仕様・チケットにまとめたら、同じ日に別の地図で決めた「保証しないモデルは組み込みの名前にしない」と食い違っていた話

[ローカルのモデルの開き直す回数を決めた話](#chatgpt-subscription) で足すと決めた ChatGPT のサブスクの経路について、残っていたサインイン・トークン・利用上限の扱いを利用者と決めた。それで地図の最後の問いが閉じたので、同じセッションで地図を仕様にまとめ、形式仕様で検証し、実装のチケットに切った。地図とは、大きな取り組みの決定を 1 つの issue に索引として並べ、未決の問いを子の issue にしたもの。差分更新のモデル（マップを更新する AI）を Claude・OpenAI 互換の口・Apple Intelligence・ChatGPT から選べるようにし、ローカルモード（会議の中身が Mac の外に出ないと約束するセッションの設定）を足す取り組みだ。

- 決定の記録: チケット [ChatGPT のサブスクの経路のサインインと上限の扱い](https://github.com/daiki-beppu/live-mindmap/issues/636)、地図 [差分更新をローカルの LLM（WebGPU を含む）でも動かし、ローカルモードでは何も外に出さない](https://github.com/daiki-beppu/live-mindmap/issues/374)
- 仕様: [差分更新のモデルを切り替えられるようにし、ローカルモードを足す](https://github.com/daiki-beppu/live-mindmap/issues/660)（形式仕様はそのコメント）
- 実装の親: [差分更新のモデルの切り替えとローカルモードを実装する](https://github.com/daiki-beppu/live-mindmap/issues/661)（子 10 件）

### 1. 上限に当たったときの扱いは、今の失敗の扱いが「何を捨てるか」を読んでから決める

前のタスクで、Plus（月 $20）でも 2 時間の会議で 5 時間の枠の 3 割未満しか使わないと測っていた。ただ、枠は Codex など同じ ChatGPT のプランを使う他のアプリと共有で、残りは応答から分からない。分かるのは 429（`subscription_sharing_usage_limit_exceeded`）が来たときだけだ。

問いを立てる前に、今の core（パイプラインの中心）が差分更新の失敗をどう扱っているかを読んだ。「失敗した回の発言は処理済みとして扱い、マップは変えずに次へ進む」だった。1 回きりの失敗なら、これで困らない。だが 429 は上限が戻るまで何度でも返る。この扱いのままだと、その間の発言がすべて、黙ってマップから落ちる。

そこで、選択肢を 3 つ並べた。今のまま、会議の残りは止める、一時停止して発言を溜め 5 分ごとに試し直す、の 3 つだ。利用者は 3 つ目を選んだ。溜めた発言は、前の決定で置いていた「1 回に渡す文の数に上限を置き、あふれは次の呼び出しへ」の仕組みでそのまま流せる。新しい仕組みは要らなかった。

**「失敗」をひとまとめに扱っている作りに新しい失敗の種類を足すときは、その扱いが何を捨てるかを先に読む。** 一時的な失敗と、続けて返る失敗とでは、捨ててよいものが違う。

### 2. サインインを `start` に混ぜない理由は、共有画面だった

サインインの入口では、`start` がサインインしていないことに気づいたらブラウザを開く案もあった。手数は一番少ない。それでも、別のサブコマンド `login chatgpt` に分けた。`start` は会議の直前、多くは画面を共有し始めた後に打つ。そこで OpenAI のサインインの画面が開くと、相手に映りうる。待ち時間も読めない。

上限に当たったとき、Claude など別のモデルに自動で切り替える案も採らなかった。利用者が選んでいない事業者に、会議の中身を送ることになるからだ。ローカルモードを使えない Mac で「Claude に黙って回さず、開始を拒む」と前に決めていたのと、同じ理由で揃った。

**会議のツールでは、操作の置き場所を「その時点で画面が共有されているか」で決める。**

### 3. 地図の決定を並べ直すと、別々の日の決定どうしの食い違いが見える

仕様を書くために、地図の 13 件の決定を読み直した。すると、前の決定が後の決定の前提を壊している箇所が 1 つ見つかった。

モデルの選び方を決めたときに、「組み込みの名前（`claude`・`apple` など、設定に書かなくても選べる名前）は、設定に書けば上書きできる」としていた。その後、ローカルモードで選べるのは live-mindmap が起動する子プロセスだけ、と決めた。理由は、Ollama のように、宛先が localhost でもモデル名によっては外の事業者で推論する実行環境があり、宛先の検査では見抜けないことだった。

ところが `apple` を設定で上書きできると、宛先を書き換えられる。約束が、設定の書き方しだいになる。仕様では、`apple` は上書きさせず、設定に書けば誤りとして拒むことにした。この点は私（エージェント）が仕様を書く中で決めたので、利用者への報告で、自分で決めたこととして挙げた。

**決定は、それぞれのチケットの中では筋が通っている。食い違いは、全部を 1 か所に並べたときに初めて見える。** 仕様にまとめる段は、清書ではなく、決定どうしの検査として読む。

### 4. 形式仕様では、選び方と実行中の状態を 1 つのモデルに入れ、「捨てない」は直前の操作の幽霊変数で書く

仕様を Quint で書き、takt（AI エージェントのワークフローを回す OSS）が同梱する検証器にかけた。開始時のモデルの選び方は、`init` で一度だけ非決定的に選ぶ入力にした（`--model`・`--local`・`default: "local"`・Apple Intelligence が使えるか・サインイン済みか）。差分更新の状態（動いている／立ち上げ直している／一時停止／止まった）と発言の数は、`step` で動かす。こうすると、「ローカルモードなら Claude を読み込まない」「立ち上げ直しは Apple Intelligence だけ」のように、選び方と実行中の状態をまたぐ性質も 1 本の不変条件で書ける。

「429 では発言を捨てない」は、状態だけでは書きにくい。捨てたかは、遷移の前後の差だからだ。そこで、直前の操作の名前と、その操作で捨てた数を変数（幽霊変数）として持たせ、`lastAction == "rateLimited" implies lastDropDelta == 0` と書いた。あわせて、全体の保存則「届いた発言 ＝ 反映した数 ＋ 処理済みの失敗 ＋ 溜まっている数」も置いた。時相の性質は使わず、不変条件 18 個で 1 回で通った。

書く途中で、仕様の文の読み方を 1 つ決める必要が出た。設定が `default: "local"`（毎回ローカルモード）のときに `--model chatgpt` を付けたらどうなるか、だ。仕様の優先順位は「`--model`／`--local` ＞ 環境変数 ＞ 設定の `default`」なので、名前が勝ち、通常のモードで始まると読んだ。ただ、`default: "local"` は旗の付け忘れで外に送る事故を防ぐための設定だ。明示した名前でも外せないほうが、目的には合うかもしれない。これは利用者に確認として返した。

**形式化は、文で書いた優先順位が、ぶつかったときにどちらへ倒れるかを決めさせる。** 決めた側に倒れた理由を書き、目的と合うかを人に返す。

### 5. 同じ日に別の地図で決めた基準を、読まずに推した

チケットを切ったあと、このエントリを書くために同じ日の開発ログを読んだ。そこで、別の地図（Haiku 5.5 を差分更新のモデルとして比べる）で数時間前に決まった基準が見つかった。

> 保証できるかで、見せ方の格を分ける。保証しないものにも選べる道を残しておくと、既定の基準を高いまま保てる。

その地図では、Haiku 5.5 を組み込みの名前にせず、設定に書けば選べるだけにした。組み込みの名前は、`claude` と同格の推奨に見えるからだ。

一方で、この日の問答では、私が「`--model chatgpt` を設定に書かなくても選べる組み込みの名前にし、既定のモデルを `gpt-6-luna` にする」を推し、利用者は推奨のまま受けた。ChatGPT の品質は、3 分の区間で測っただけだ。この地図では品質を保証するのは Apple Intelligence だけと決めてあり、ChatGPT はその外にいる。基準に照らせば、`chatgpt` は組み込みの名前にしないほうが筋が通る。食い違ったまま、仕様にも実装のチケットにも入っている。

前提にしていたのは「同じ地図の決定だけ読めば足りる」だった。だが差分更新のモデルの見せ方という同じ主題を、2 つの地図が同じ日に並行して決めていた。どちらを正にするかは利用者の判断なので、このエントリを出すときに確認として返した。

**同じ主題を並行する地図が扱っているときは、推す前に、その日の他の地図の決定（開発ログでもよい）を読む。** 地図の境界は作業の都合で引いたもので、主題の境界ではない。
