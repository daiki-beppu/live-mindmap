## 過去のセッションから引き継いだ語彙の効き目を測ったら、引き継ぎは上限まで届いていて、低く見えた原因は英字の語の読みの崩れだった話

前のセッションの**語彙**を次のセッションに引き継いだとき、固有名詞の正解率がどこまで上がるかを測ったときの学び。語彙は、会議で話されそうな固有名詞・略語の正しい表記の集まりで、音声認識が崩した語を、発言（確定した文字起こしの 1 単位）にするときに読みで引いて直すのに使う。引き継ぐのは「前のセッションの発言に出た語と、利用者が足した語」だけ、と前のチケットで決めてあった（[過去のセッションを語彙の出どころに残すか決めた話](./2026-10-08.md#past-session-vocab)）。補正の形は、読みの近さで置き換え、ふつうの語の一覧（日本語の上位 5 万語）に載る区間は直さない、というもの（[語彙からふつうの語を除く手段を測った話](./2026-10-08.md#vocab-common-words)）。

- 決定の記録: チケット [過去のセッションから引き継いだ語彙の効き目を測る](https://github.com/daiki-beppu/live-mindmap/issues/526)、地図 [Kanary を手本に字幕の精度を上げる](https://github.com/daiki-beppu/live-mindmap/issues/386)
- 起こしたチケット: [英字の語の読みが FoundationModels で崩れる割合と、別の作り方を測る](https://github.com/daiki-beppu/live-mindmap/issues/577)

素材は、架空の地方スーパーのネットスーパー立ち上げの週次定例を、音声合成で 2 回分作った（各 8 分、同じ 4 人）。1 回目はスライド 6 枚を共有し、2 回目は共有なし。1 回目のスライドを macOS の Vision で OCR し、規則（カタカナ 3 字以上・漢字 3〜12 字・大文字を含む英字の語、と 3 画面以上に出る 2〜4 字の短い行）で語彙を取った。1 回目をその語彙で直し、直した後の発言に出た語だけを 2 回目に引き継いで、2 回目を直した。

| 2 回目に使った語彙 | 語数 | 固有名詞の正解率 | CER |
| --- | --- | --- | --- |
| 補正なし | – | 41.4%（41/99） | 13.6% |
| 引き継いだ語彙（1 回目の発言に出た語だけ） | 24 | 54.5% | 10.2% |
| 絞らずに 1 回目の語彙を全部 | 37 | 54.5% | 10.2% |
| 台本で 2 回とも出る語（引き継ぎで届く上限） | 18 | 54.5% | 10.3% |
| 2 回目の台本の語すべて（語彙で届く上限） | 24 | 74.7% | 4.3% |

置き換えの誤りは、どの行も 0 だった。英字の語の読みは、崩れた語を手で直した値で測っている（3 節）。

### 1. 出どころの効き目は、全体の上限ではなく「その出どころが持ちうる語」の上限と比べる

チケットは「台本の語彙（別の素材で 62.7%→96.8%）や共有画面の OCR の語彙にどれだけ届くか」という問いで立てていた。引き継ぎの 54.5% を台本の語すべての 74.7% と比べると、20 ポイント届いていない。引き継ぎの仕組みに取りこぼしがあるように見える。

上限を 2 つに分けると読み方が変わった。引き継ぎが持ちうるのは「前の回にも出た語」だけなので、台本で 2 回とも出る 18 語を語彙にした値が、引き継ぎの上限になる。これも 54.5% で、引き継ぎはもう上限に届いていた。20 ポイントの差は、2 回目に初めて出る語（新しい SaaS の名前や地名、2 回目の固有名詞の出現 99 回のうち 36 回）の分で、どう引き継いでも直らない。

前の日に「出どころを比べる前に、その素材で正しい語彙なら何点まで上がるかを先に出す」と書いた（[OCR の語彙の効き目を測った話](./2026-10-08.md#ocr-vocab-effect)）。今回はそれをもう一段分けた。素材全体の上限と、出どころが原理的に届く上限は別に出す。素材を作るとき、1 回目と同じ語・新しい語・話にだけ出る語（スライドに無い取引先の人名）を分けて台本に入れておいたので、この分け方がそのまま計算できた。

### 2. 次の段の入力を、その段自身の出力で絞ると、誤りが次の回へ持ち越される

「発言に出た語だけを引き継ぐ」は、使われない語で語彙が膨らまないための決まりだった。絞ると効き目が落ちるかもしれない、と思っていたが、絞らない場合と同じ 54.5% だった。絞って落ちたのは、参加者の名前（小窓の OCR で取れたが、音声認識が「6村」「遠野」のように崩したまま発言に残らなかった）と、スライドの見出しのかけら（先行店舗・審査待など）だった。名前は語彙に入れても 2 回目で直らないので、落としても値は変わらない。

代わりに穴が見えた。「発言に出たか」は補正をかけた後の本文で判定する。補正をかける前の本文で判定すると、「カゴラク」（音声認識は「過ご楽」と書く）のような、直して初めて現れる語が引き継がれない。ところが補正の後で判定すると、誤った置き換えで本文に入った語も「発言に出た語」になる。1 回目では「配達の時間帯→配達時間帯」「夕方の便→夕方便」の 2 件があり、どちらも引き継がれた。2 回目では害が出なかったが、同じ誤りを次の回でも繰り返せる形になっている。

この 2 件は、前の日に仕様へ入れると決めた「語の中のひらがなを落とす置き換えを止める守り」があれば、そもそも入らない。ある段の出力で次の段の入力を選ぶときは、その段の誤りがどう持ち越されるかを先に確かめる。

### 3. 上限が低すぎたら、直らなかった語を 1 つずつ見る。崩れていたのは別の段だった

最初に測ったとき、2 回目の台本の語すべての語彙で 58.6% だった。別の素材では台本の語彙で 95% まで上がっていたので、低すぎる。直らなかった語を見ると、Amplitude（8 回）・Figma（5 回）・Datadog（2 回）が、語彙に入っているのに 1 回も直っていなかった。

原因は英字の語の読みだった。補正は読みで引くので、英字の語には読みが要る。前のチケットで「英字の語の読みは、端末の中の LLM（Apple の FoundationModels）に 1 度だけ聞く」と決めていた。その読みを開くと、新しく聞いた 7 語のうち 3 語が崩れていた。

| 語 | FoundationModels の読み | 音声認識の書き方 |
| --- | --- | --- |
| Amplitude | アスペクト | アンプリチュード |
| Figma | ファイマ | フィグマ |
| Datadog | ダットドッグ | データドッグ |

3 語の読みを手で直すと、台本の語すべての語彙で 74.7% になった。引き継ぎの側にも響いていた。1 回目で Datadog が直らなかったので、「発言に出た語」にならず、引き継がれていなかった。手で直した読みで 1 回目からやり直すと Datadog も引き継がれ、引き継ぎの値は 52.5% から 54.5% に上がった。

引き継ぎの効き目と読みの質が、同じ数字に混ざっていた。読みを手で直した値と直さない値を両方出して、2 つを分けた。読みの作り方は、このチケットの範囲を超えるので、別のチケットに起こした。

### 4. 「OCR は 1 字も崩さない」は、前の素材の語での話だった。珍しい字は崩れる

前の日の測定では、OCR はスライドの名前・店名を 1 字も崩さずに読んだ。それを前提に「OCR は崩れないと仮定して、規則だけを測る」というやり方を取っていた。

今回は「雫石」を一度も正しく読まなかった。会議アプリの右の小窓に出る名前（13px）は 6 画面とも「栗石」、スライドの本文（24px）の「（雫石）」は「雲石」になった。同じ小窓の「鳴海」「六車」「東雲」は崩れていないので、文字の小ささより、「雫」という字の珍しさが効いている。小窓の名前は、繰り返し出る短い行として語彙に入れる決まりなので、誤った表記がそのまま語彙に入る。今回は「栗石」に読みの近い区間が無く、害は出なかった。前の日の素材の語（港南・葛西・野々村など）が崩れなかったのは、ありふれた字だったからで、OCR がいつも崩れないわけではない。

規則の側にも 1 つ穴があった。カタカナを Unicode の範囲（U+30A0〜U+30FF）で取っていて、中黒「・」（U+30FB）がこの範囲に入る。箇条書きの「・パン」や「・ピックナビ」が、中黒ごとカタカナの語として取れた。今回は前後の中黒を外して数えた。仕様では、中黒をカタカナから外す。

### 5. `LC_ALL=C` は `sort` にだけ付ける。`sed` に付けると日本語のバイトを壊す

前の日に、`sort -u` が UTF-8 のロケールで日本語の行をまとめてしまうことにはまり、`LC_ALL=C` を付けて直した。今回はそれを覚えていて、語彙を作るシェルの先頭で `export LC_ALL=C` にした。その後に行頭の中黒を外そうとして、`sed 's/^・*//'` を同じシェルで流した。

C ロケールでは、`・*` の `*` は「・」の 3 バイト（E3 83 BB）の最後の 1 バイトにしか掛からない。パターンは「E3 83 で始まり、BB が 0 回以上続く」になり、E3 83 で始まるカタカナ（「ピ」は E3 83 94）の頭の 2 バイトを削った。補正の道具は語彙のファイルを読めずに「ファイルの形式が正しくない」で落ち、`file` で見ると UTF-8 ではなくなっていた。

`sort` と `uniq` だけを `LC_ALL=C` で動かし、文字として扱う `sed` は UTF-8 のロケールで動かすと直った。

```sh
cat v1.rules.txt v1.repeat.txt | LC_ALL=en_US.UTF-8 sed 's/^・*//; s/・*$//' | LC_ALL=C sort -u > v1.vocab.txt
```

手元で同じように測るなら、素材は `~/live-mindmap-samples/synth/weekly-1`・`weekly-2`、道具と出力は `~/live-mindmap-samples/runs/carry-vocab/`（どちらもリポジトリの外の素材置き場）にある。音声認識は `helper` の `stt-bench run --variant baseline` に通し、補正は前の試作（`prototype/vocab-stoplist-491` ブランチの `helper/bench/proto-vocab-correct/main.swift`）を `--mode index --strict --min 0.8 --stop <上位5万語> --stop-scope latin` で回し、`server/bench/sttAccuracy.ts` で固有名詞の正解率と CER を出した。

## 小さいモデル向けに差分更新の出力の形を 5 通り試したら、形の崩れは列挙型と毎回 1 から呼ぶことで消えたが、判断の質は届かず、品質を保証するのは Apple Intelligence だけにした話

[ローカルの LLM を回帰評価にかけた話](./2026-10-08.md#local-llm-eval)の続きで、試作のチケットを 1 件、利用者と相談しながら解いた。**差分更新**は、AI が会議の発言を読み、マインドマップへの操作（足す・直す・閉じるなど）だけを JSON で返す処理だ。今は Claude（Sonnet 5.5）が担っている。前の日の計測では、Apple Intelligence（macOS の端末内のモデル）も Qwen などのローカルのモデルも、Claude と同じプロンプトではマップを作れなかった。そこで今回は、Apple Intelligence に絞って、プロンプトと出力の形を作り直した。案を 5 つ試し、最後に同じプロンプトで Qwen3.5-4B を 1 回だけ流した。

### 1. 小さいモデルに id を正しく書かせたいなら、指示ではなく列挙型で縛り、新しい id はサーバーが振る

前の日の崩れ方は、すべて id だった。新しいノードに付ける仮 id にルートの id（`root`）を書く、存在しない `root` を書き換えようとする、といった誤りだ。指示を 1 行足すと崩れ方は変わったが、モデルごとに別の誤りへ移るだけだった。

今回は、指示で頼むのをやめて、出力のスキーマで縛った。呼び出しのたびに、その時点のマップにある id だけを JSON Schema の `enum` に書き込む。親の欄なら「今あるノードの id ＋ この応答で足すノードの番号（新1・新2 …）」、根拠の欄なら「新しい発言の id」だけが選べる。仮 id はモデルに書かせず、サーバーが add の順に振る。Apple Intelligence の構造化出力（Foundation Models の `GenerationSchema`）も、llama.cpp の `json_schema` も `enum` をそのまま守る。手で 1 回試したとき、Apple Intelligence は「予算」の下に置くなら親はどれ、という問いに、列挙した 4 つから正しい id を選んだ。

v1 では、捨てられた操作が 39 回の呼び出しで 11 個まで減った（前の日はほぼ全部）。残った 11 個も「TODO の下に子を足した」という種別の規則の違反で、id の誤りは 0 になった。前の日のエントリで「仮 id をなくせば失敗の元は消える」と見込んでいたが、そのとおりになった。スキーマが形しか保証しないなら、意味のある値の範囲まで毎回スキーマに書き込めばいい。

### 2. 文脈長が会話全体にかかるモデルでは、会話を続けず毎回 1 から呼び、見せるマップを絞る

Apple Intelligence の文脈長 8,192 トークンは、1 回の入力ではなく会話全体にかかる。Claude の形（同じ会話を使い回し、2 回目からはマップの変更だけを送る）では、最初の呼び出しだけで約 4,000 トークンあり、1 往復で約 1.4k 増えて数回で溢れていた。

そこで、ローカル向けは会話を続けず、毎回システムプロンプトと「話し中の部分のマップ」と新しい発言だけを送る形にした。システムプロンプトは、Claude 向けの長いものから、種別の定義と数行の規則だけの短いものに書き直した。v1 では入力が 1.0k〜3.8k に収まり、1 回の時間は 14 秒から 4 秒に縮んだ。開き直す回数を何回にするか、という悩みも消えた。

ただし、マップの全体を見せる形（v3）では、ノードが増えるにつれて入力が 7.9k まで膨らみ、後半の 14 回が文脈長の超過で失敗した。v4 からは、マップのうち議題（話題のまとまり）と論点（答えを出すべき問い）の行だけを見せ、要点や案は見せないことにした。こうすると入力は会議が進んでも 3k を超えなかった。Claude 側は、前置きをキャッシュに乗せる今の形のまま残した。キャッシュが効く Claude と、文脈長が窮屈な小さいモデルとでは、良い形が逆になる。

### 3. 小さいモデルに「あるか」を判断させる欄は、指示の向きで「全部なし」と「全部あり」に振れる。判断力は形では作れない

形が直ると、残った問題は中身だった。v1 では、Apple Intelligence は 39 回の呼び出しで一度も「何もしない」を返さなかった。TODO を 26 個作り、担当者まで作っていた。決定は 2 つだけだった。

そこで、判断を分類に置き換えた。v2 は新しい発言 1 つごとに、種類（相づち・進行 / 説明 / 問い / 提案 / 懸念 / 合意 / 作業の引き受け）を 1 つ選ばせる形だ。すると今度は、作業の引き受けが 1 個しか出なくなった。v3 では「作業 → 合意 → 中身」の順に、空にもできる配列で拾わせた。結果は作業 50・合意 43 だった。v4 では、各欄の前に「ある / ない」を答えさせる関門を置いた。Apple Intelligence は前から順に生成するので、先に「ない」を選べば配列を埋めないはずだった。ところが、最初の 5 回はすべて「ある」だった。v4 は決定 3/5 と数字では一番良かったが、決定を 43 個ばらまいた結果にすぎない。

指示や欄の作り方で動かせたのは、どちらに倒れるかだけだった。発言ごとに「これは合意か」を見分ける力そのものは、どの形でも出てこなかった。

### 4. 分類の単位は、モデルの入力の単位ではなく、判断の単位に合わせる

v2 で取りこぼした発言を、正解の時刻に重なる発言ごとに見ていった。すると、この素材の「発言」（音声認識が区切った 1 単位）は、複数の行為の塊だった。たとえば 1 つの発言の中に「見直し案を来週の水曜までに出します」「お願いします」「画面をもう一回お願いします」「出店の話に行きましょう」が続けて入っている。TODO と、相づちと、進行と、話題の切り替えが 1 つの単位にまとまっている。これに種類を 1 つだけ選ばせれば、TODO は「相づち・進行」に埋もれる。

v5 では、サーバーが新しい発言を「。」「？」「！」で文に切り、文の数と同じ長さの配列を返させた。配列の位置で文と対応させるので、モデルは文の id を書かなくていい。正解の TODO を含む 7 つの発言のうち、Apple Intelligence は 6 つ、Qwen3.5-4B は 7 つすべてで、その発言から TODO を作った。拾い漏れはほぼなくなった。ただし作った数が多すぎて、照合で当たったのは 3/7・4/7 にとどまった。決定はどちらのモデルも外し続けた。

この形には、もう 1 つ利点がある。「文に切る（サーバー）」「文ごとに種類を判定する」「要約して置き場所を決める」が分かれるので、判定の段だけを別のモデルに差し替えられる。結果を見た利用者からは、「こういうのは将来的に Jev などの system one のモデルでやらせる」と返ってきた（system one は、安く速い判定だけを担うモデルのことで、Jev はその 1 つ）。判定の段に向くモデルは、この地図の外の取り組みにした。

### 5. 構造化出力でも生成は止まらないことがある。上限はモデルの側で切る

v2 の 7 回目で、1 回の呼び出しが 190 秒かかり、`Content contains 8193 tokens` で失敗した。出力が止まらず、文脈長の上限まで伸びていた。スキーマで縛っていても、文字列の欄の中身はいくらでも長く書ける。同じ要求を送り直すと 117 トークンで終わったので、確率的に起きる。

困ったのは、詰まりが後ろに伝わったことだ。計測用のシムは Apple Intelligence への要求を 1 つずつ順に処理していた。そのため、呼ぶ側のタイムアウトで接続を切っても、モデルの生成は続き、次の要求が全部待たされた。Foundation Models の `GenerationOptions` に `maximumResponseTokens: 600` を渡してからは、暴走しても 600 トークンで止まり、JSON として読める形で返ってきた。39 回のうち 6〜10 回がこの上限に当たっていたので、まれな事故ではない。呼ぶ側のタイムアウトは、生成を止める手段にならない。

### 6. 速さの差は「読み込み」と「生成」に分けてから、改善で縮むかを見る

4B の v5 は 1 回 中央 21 秒で、内訳は生成が 16 秒（277 トークンを 14 トークン/秒）、読み込みが 4 秒（976 トークン）だった。前の日の 37.5 秒からは縮んだが、この会議で差分更新を呼ぶ間隔（中央 35 秒）とほぼ同じで、ほかのアプリとメモリを取り合えばすぐ溢れる。Apple Intelligence は 6.6 秒だった。利用者の感想は「さすがに apple しか使い物にならないね、速度的に」だった。

判定を system one のモデルに任せれば 4B も化けるか、とも聞かれた。品質は上がりうる。外しているのは判定なので、そこを別のモデルが担えば、4B に残るのは要約と置き場所だけになる。一方で速さは、ほとんど変わらない見込みだ。遅さの大半は要約を書く生成で、判定を外しても縮むのは作るノードが減る分だけになる（見込みで半分程度、10 秒前後）。しかも同じ改善は Apple Intelligence にも効くので、差は縮まらない。

利用者はさらに、品質はハードのスペックにも左右される、と続けた。手元で測れるのは M4・16GB の 1 台だけで、ほかの機種の数字は持っていない。そこで次のように決めた。

- 品質を保証するのは Apple Intelligence だけにする。
- ほかのモデルは、すでに決めてある OpenAI 互換の口をアダプターとして用意し、利用者が設定に書けば使えるようにする。品質は保証しない。
- そうした利用者の実行環境は、通常のモードでだけ使える。ローカルモード（会議の中身が Mac の外に一切出ないと約束するセッション）では選べない。Ollama や LM Studio は更新の確認で外に通信するので、約束の範囲から外す、という前の決定のままだ。

結果として、「何も外に出ない」と約束できる範囲と、品質を保証する範囲が、どちらも Apple Intelligence にそろった。Mac の中でモデルを動かす内蔵の仕組み（node-llama-cpp）も、作らないことにした。推奨のモデルを機種ごとに 2 段で案内する計画も消えた。

手元で同じように測るなら、試作は `prototype/local-llm-prompt` ブランチの `server/src/prototypeLocalUpdater.ts` にある。`LOCAL_LLM_SHAPE=stateless` と `LOCAL_LLM_VARIANT=v1`〜`v5` で案を切り替え、宛先は `LOCAL_LLM_URL` で渡す。Apple Intelligence は同じブランチの `server/bench/afm/main.swift` を `swiftc -O` でビルドし、`server/bench/afmServer.ts` で localhost の OpenAI 互換の口に包む。4B は llama.cpp の `llama-server --offline -c 16384 --reasoning off` で動かした。正解の時刻に重なる発言ごとに作ったノードの種別を出す道具は、`server/bench/truthHits.py` だ（本文は出さない）。

## 英字の語の読みを作り方ごとに 106 語で比べたら、端末の中の LLM は 4 語に 1 語を別の語に崩し、差分更新のモデルに聞く形に改めた話

[1 つ目のエントリ](#carry-vocab-effect)で見つけた「英字の語の読みの崩れ」を、語を増やして測り直したときの学び。字幕の補正は、音声認識が崩した語を、**語彙**（会議で話されそうな固有名詞・略語の正しい表記の集まり）から読みの近さで引いて直す。読みは OS のトークナイザが返すローマ字で比べるが、Figma のような英字の語はトークナイザが英字のまま返すので、カタカナの読みを別に作る必要がある。これまでは端末の中の LLM（Apple の FoundationModels）に 1 語ずつ聞いていた。測った結果、セッションの**差分更新のモデル**（会議の発言からマインドマップを更新し続ける AI。セッションの開始時に選ぶ）にまとめて聞く形に改めた。

- 決定の記録: チケット [英字の語の読みが FoundationModels で崩れる割合と、別の作り方を測る](https://github.com/daiki-beppu/live-mindmap/issues/577)、改めた ADR [語彙での補正はサーバーが発言を締めるときにかけ、読みはヘルパーが送る](../adr/0015-correct-remarks-in-server-readings-from-helper.md)、地図 [Kanary を手本に字幕の精度を上げる](https://github.com/daiki-beppu/live-mindmap/issues/386)

会議に出そうな英字の製品名・サービス名を 106 語集め（それまでの読みのキャッシュにあった 20 語を含む）、語ごとに正しい読みを書いた。作り方ごとに読みを出し、本番の補正と同じ照合の条件で正しい読みに届くかを数えた。

| 作り方 | 読みが正しい語 | 崩れ方の例 |
| --- | --- | --- |
| FoundationModels（それまでの形） | 79/106（75%） | Amplitude→アスペクト、MySQL→マイクロン、SharePoint→シャープポイント |
| FoundationModels＋手本 5 つのプロンプト | 76/106 | Gmail→グーグルメール、PayPal→ペイペイ |
| FoundationModels で候補を 3 つ | 83/106 | |
| FoundationModels で 5 回出して全部を読みにする | 90/106 | PowerPoint→プレゼンテーション が混ざる |
| ICU の字訳（ローマ字読み） | 47/106 | |
| 日本語の音声合成で読ませて音声認識にかける | 69/106 | Figma→ヒグマ、Asana→浅田 |
| Claude Haiku に 106 語をまとめて 1 度聞く | 103/106（97%） | Marketo→マーケト、Swagger→スウェガー |

実際の素材（音声合成で作った 8 分の会議 2 本）を台本の語の語彙で直すと、固有名詞の正解率は、新しい英字の語が多い会議で 58.6% から 74.7%、もう一方で 95.2% から 96.0% に上がった。誤った置き換えはどちらも 0 だった。74.7% は、前のエントリで読みを手で直したときの値と同じだ。

### 1. 正解の表記は、下流の段が実際に書く形から決める

正しい読みを書く前に、音声認識（Apple の SpeechAnalyzer）が英字の製品名をどう書いているかを素材で確かめた。台本の語の前後の時刻に重なる確定結果を並べると、フィグマ・アンプリチュード・ブレイズ・セールスフォース・ノーションのように、辞書どおりのカタカナで書いていた。GitHub や POC は英字のまま出ていた。

補正が引くのは、音声認識が書いたこの文字列だ。だから正しい読みは「英語の発音に近いカタカナ」ではなく「音声認識が書くカタカナ」になる。今回は両者がほぼ一致していたので、辞書どおりの表記を正解にできた。順番を逆にして、先に発音から正解を作っていたら、トゥイリオとツイリオのどちらを正解にするかで迷い、照合の数字が意味を持たなかった。

### 2. 採点は本番の照合の条件でする。照合の側のずれは、読みの崩れと分けて数える

読みが「正しいか」は見た目では決めず、本番の補正と同じ条件で数えた。読みをローマ字にして長音・促音などを潰したキーを作り、キーが 5 字以下なら完全一致、それより長ければ編集距離から出した似ている度合いが 0.8 以上なら、補正がその語を引ける。

数えている途中で、照合の側のずれが見つかった。スワガーとスワッガーが一致しない。トークナイザの返すローマ字を出すと、こうなっていた。

```
スワガー   ["suwa", "gā"]
スワッガー ["suwa~tsu", "gā"]
トゥイッチ ["to~uitchi"]
ツイッチ   ["tsu", "itchi"]
```

辞書に無いカタカナでは、小さいカナを `~tsu`（ッ）・`~u`（ゥ）と返す。キーは `~` を記号として落とすが、`tsu` は残るので、促音を含む読みが一致しにくい。これは読みの作り方とは関係が無く、音声認識がトゥイリオと書いたときにも効く。

採点を 2 通り出した。本番のままのキーと、`~tsu` を落として `~` を外したキーだ。どの作り方でも、後者で増えたのは 0〜2 語だった（FoundationModels は 78→79 語、Haiku は 103 語のまま）。表の値は、読みの作り方の差だけを見るために後者で数えている。照合の直しは、読みの作り方とは別の項目として仕様に入れた。混ぜて数えていたら、どちらが効いたかが分からなくなっていた。

### 3. 候補を増やすと当たりは増えるが、外れの候補が誤りの元になる

当たりの数だけを見ると、FoundationModels で 5 回出して全部を読みにする形が 90 語で、1 回だけの 79 語を大きく上回る。ただ、出てきた候補を開くと、PowerPoint にプレゼンテーション、パワポ、パワフォートが並んでいた。

補正は、語彙の語の読みに近い区間を見つけたら、その語に書き換える。読みにプレゼンテーションを持たせると、会議で「プレゼンテーション」と話した箇所が PowerPoint に書き換わる。ふつうの語の一覧に載る区間は直さない守りはあるが、英字の語への書き換えだけは通す決まりなので、この守りでは止まらない。

この補正では、読みが外れて取りこぼすより、誤って書き換えるほうが害が大きい。字幕が勝手に別の語に変わるからだ。候補を増やす形は、当たりの数を上げても採れなかった。読みは 1 語に 1 つと仕様に書いた。

### 4. 小さいモデルに手本を足したら、かえって悪くなった

最初に試したのは、プロンプトの言い換えだった。「綴りをローマ字読みせず、英語の発音をもとにした、日本で定着した呼び方にする」と書き、Microsoft→マイクロソフトのような手本を 5 つ付けた。79 語が 76 語に減った。

崩れ方が変わっていた。手本なしでは Amplitude→アスペクトのように、綴りの近い別の語に崩れていた。手本ありでは Gmail→グーグルメール、PayPal→ペイペイ、SharePoint→スポーティングのように、「日本で定着した呼び方」を「日本でよく聞く別の名前」と取ったような答えが出た。指示を足しても、小さいモデルが知らない語の読みは作れない。知らない語の前で、別の知っている語に寄せる向きが変わるだけだった。

### 5. 音声合成で読ませて音声認識にかける形は、声が英語を読めず使えなかった

「音声認識がどう書くか」が正解なら、音声認識そのものに書かせればよい、と考えた。macOS の日本語の声（Kyoko）に「12 番、次は Braze の話です。」のような文を 106 語ぶん読ませ、1 本の音声にして、同じ SpeechAnalyzer で文字起こしした。

```sh
cut -f1 truth.tsv | awk '{printf "%d番、次は%sの話です。[[slnc 900]]\n", NR, $0}' > script.txt
say -v Kyoko -f script.txt -o kyoko.aiff
afconvert -f m4af -d aac kyoko.aiff kyoko.m4a
```

Braze→ブレイズ、Stripe→ストライプのように正しく戻る語もあったが、Figma→ヒグマ、Asana→浅田、Claude→クロッドのように、日本語の声が英字の語を読めていなかった。照合が緩いので数字は 69 語になったが、エバーフロー（Airflow）のように崩れたまま通った語も含む。英語の声（Samantha）で読ませて日本語の音声認識にかけると、語は英字のまま返るか崩れ、番号まで崩れて照合できなかった。

英語の発音記号からカタカナを規則で作る形も考えた。macOS には英文の発音記号を返す `NSSpeechSynthesizer.phonemes(from:)` があるが、英語の声を指定しても空の文字列しか返さず、試せなかった。

### 6. 正解を書いた側と同じ系統のモデルは、有利に見えうる

一番よかったのは Claude Haiku だが、正しい読みの一覧を書いたのも Claude（この作業をしていたエージェント）だ。表記の揺れ（トレロかトレローか）を同じ癖で選んでいれば、Haiku は実力以上に当たって見える。

偏りが結論を変えるかは、崩れ方で見た。FoundationModels の外れは、表記の揺れではなく別の語（アスペクト、マイクロン、オンデーズ）が多い。正解の書き方を変えても、これは当たりにならない。差の大半は偏りでは説明できないと判断し、偏りがありうることは記録に残した。

### 7. 新しい外部呼び出しを足す前に、会議の中身をすでに渡している先に相乗りする

改めた形では、新しい英字の語が語彙に入るとき、サーバーがセッションの差分更新のモデルに語をまとめてカタカナを聞く。返ったカタカナは、これまでどおりヘルパー（音声認識を担う Swift の実行ファイル）のサブコマンドに渡し、ほかの語と同じトークナイザのローマ字にする。測った読みの形は変わらない。

読みのためだけに別のクラウドの API を呼ぶ形にはしなかった。語彙の語は共有画面や発言から取るので、会議の中身にあたる。差分更新のモデルには、もともと発言を渡している。そこに語を足しても、会議の中身の行き先は増えない。**ローカルモード**（会議の中身が Mac の外に一切出ないと約束するセッション）では、差分更新のモデルは Mac の中で動く Apple Intelligence だけ（[2 つ目のエントリ](#local-llm-prompt-shape)）なので、約束もそのまま守られる。

その代わり、ローカルモードの読みの質は FoundationModels のまま、4 語に 1 語が崩れる。ここは仕組みでは埋めず、残る弱さとして記録した。

手元で同じように測るなら、道具と出力は `~/live-mindmap-samples/runs/latin-readings/`（リポジトリの外の素材置き場）にある。`readings.swift` を `swiftc -O` でビルドし、`readings truth.tsv fm` のように作り方を渡すと、語ごとの読みと判定を出す。`FROM=<出力>` で読みを採点だけし直し、`FIX=1` で小さいカナの癖を外して採点する。素材での値は、前のエントリの補正の道具を、読みのキャッシュだけ差し替えて回した。

## Haiku 5.5 と Sonnet 5.5 を比べる地図を作ったら、比べる前に effort の既定値と、過去の試算の単価のずれが見つかった話

Claude Haiku 5.5 が出たので、差分更新に使っている Sonnet 5.5 と比べる計画を立てたときの学び。**差分更新**は、AI が会議の発言を読み、マインドマップへの操作だけを JSON で返す処理だ。このアプリで Claude を呼ぶのはこの 1 か所だけで、Claude Agent SDK を通して Sonnet 5.5 を呼んでいる。利用者は自分の API キーで払う。今回はコードを書かず、決めることを並べた地図（決めることを 1 つの issue に束ね、子のチケットに分けたもの）を作り、最初の調べ物を 1 件だけ片づけた。

- 決定の記録: 地図 [Haiku 5.5 を差分更新のモデルとして Sonnet 5.5 と比べる](https://github.com/daiki-beppu/live-mindmap/issues/612)、チケット [Haiku 5.5 と Sonnet 5.5 の公表値と、今の呼び方で Haiku 5.5 が使えるか](https://github.com/daiki-beppu/live-mindmap/issues/613)、注記の PR [ナレッジの Claude の費用に、キャッシュの読み出しの単価が公式と違うことを注記する](https://github.com/daiki-beppu/live-mindmap/pull/617)

### 1. 新しいモデルと比べるときは、評価を回す前に、目的地と物差しを決める

利用者の最初の一言は「haiku 5.5 が出たので既存の claude の設定と比較」だった。これだけでは、比べる対象（製品の差分更新か、開発に使う道具のモデルか）も、何が分かれば終わりかも決まらない。そこで、先に 4 つを決めた。

- 比べる範囲は、製品の差分更新だけにする。E2E のテストは記録を再生していてモデルを呼ばないので、比べても意味がない。
- 地図の終わりは 2 つの判断にする。1 つは、既定のモデルを Haiku 5.5 に替えるか。もう 1 つは、既定にしない場合でも、選べるモデルとして残すか。
- 物差しは「品質に下限、その上で遅れと料金」にする。下限は Sonnet 5.5 から落ちないこと。
- Haiku に向きそうな別の役目（文ごとの種類の分類）は、まだ実装が無いので範囲外にする。

チケットは、調べ物 → 評価 → 判断の順に、前のものが閉じるまで次に進めない形でつないだ。評価より先に調べ物を置いたのは、モデル名だけを替えて同じに動く保証が無いからだ。今の作りは、キャッシュに乗る最小の長さと、JSON スキーマでの構造化出力に頼っている。実際、次の節の 2 つの落とし穴は、評価を回す前の調べ物で見つかった。

**新しいモデルとの比較は、評価を回す前に、何が分かれば終わりかと、どの数字で比べるかを決める。** 決めずに回すと、出た数字を見てから基準を選ぶことになる。

### 2. Agent SDK で新しいモデルを呼ぶときの既定値は、API ではなく、同梱の CLI のモデル一覧で決まる

Agent SDK は、内部で Claude Code の CLI を子プロセスとして動かす。調べると、同梱の CLI は 2026-10-02 のビルドで、10-07 に出た Haiku 5.5 をモデルの一覧に持っていなかった。知らないモデルでも、ID はそのまま API に送る。Haiku 5.5 が受け付けない指定（temperature・thinking の予算・prefill）も送らないので、呼べる見込みは高い。

問題は effort（どれだけ考えるかの段階）の既定値だった。

| | API の既定 | 今の作りで実際に送る値 |
| --- | --- | --- |
| Sonnet 5.5 | `high` | `medium`（CLI の一覧の既定） |
| Haiku 5.5 | `medium` | `high`（一覧に無いので、CLI の最後の既定） |

コードで何も指定していないので、そのまま比べると「medium の Sonnet」と「high の Haiku」の比較になる。API の既定とも逆向きにずれる。評価のチケットには、両方の effort を `options.effort` で明示して揃える、と書き足した。

**SDK を通してモデルを呼ぶときは、既定値がどこで決まるかを、API のドキュメントではなく SDK の中身で確かめる。** 新しいモデルの直後は、SDK の版がモデルより古いことが多く、ずれが出やすい。

### 3. 要求ごとに単価が切り替わるモデルでは、会話を使い回す作りが境目に近づかないかを見る

Haiku 5.5 の単価は、Sonnet 5.5 のおよそ 1/20 だ（100 万トークンあたり入力 $0.10・出力 $0.50）。ただし、1 回の要求の入力が 10 万トークンを超えると、その要求は 5 倍の単価になる。入力にはキャッシュから読んだ分も含まれる。

この差分更新は、SDK の会話を開いたまま最大 14 回使い回す。キャッシュを効かせるためで、回を追うごとに会話の履歴が積もる。長い会議では、会話を開いたときに渡すマップ全体も大きくなる。そこで、評価のチケットに、入力の合計が 10 万を超える呼び出しの数を数える、と足した。

**料金が要求ごとの大きさで変わるモデルでは、キャッシュのために入力を大きく保つ作りが、そのまま単価の境目に近づく。** キャッシュで安くしたつもりの設計が、別の料金体系では逆に効くことがある。

### 4. 「SDK の値と一致した」は、単価が正しい証拠にならない。単価は料金表で確かめる

調べ物の途中で、別の誤りも見つかった。過去の開発ログでは、Sonnet 5.5 のキャッシュの読み出しを 100 万トークンあたり $0.20 として費用を数えていた。公式の料金表では $0.10（入力の 0.05 倍）だ。$0.20 は、1 つ前の Sonnet 5 の単価と同じだ。

[長い会議を測った話](./2026-10-04.md#long-meeting-eval) では、自分で計算した 1 回の費用が SDK の返す値と一致した（$0.00798 と $0.00799）。それで単価は合っていると考えていた。ただ、一致が示すのは「SDK と同じ数え方をした」ことだけで、その数え方が料金表と同じかどうかは示さない。SDK の内側も同じ単価で数えていたのだと見ている（確かめてはいない）。このアプリの費用は、キャッシュの読み出しが入力の大半を占める。そのため、長い会議ほど高めに出ていた。

**費用の物差しに使う単価は、SDK の値と照らすだけで済ませず、料金表の一次情報で一度確かめる。** 同じ表を見ている 2 つの数字は、一緒に外れる。

### 5. 生のトークン数を残していない記録は、推測で書き換えず、注記で直す

利用者からは「試算も公式の値で揃えて」と頼まれた。ところが、計算し直すのに要る呼び出しごとのトークン数が、どこにも残っていなかった。当時のセッションのフォルダは消えていた。開発ログには、表の金額しか書いていなかった。

読み出しの割合を仮定すれば、金額を縮めることはできる。ただ、それでは推測の数字を、測った値として書き換えることになる。利用者と相談して、日付の付いた記録は当時の値のまま残した。そのうえで、Claude の費用を載せた 4 日分の 9 節に注記を 1 行ずつ足した。中身は、どの単価で数えたか、公式の単価はいくらか、実際はどちらに外れるか。これからの評価は、トークン数に公式の単価を掛けて出すと、評価のチケットに書いた。

**費用を測ったら、金額だけでなく、呼び出しごとのトークン数の内訳も残す。** 単価が後で変わっても、間違いが見つかっても、内訳があれば計算し直せる。

## テストの層の子チケットを takt で流したら、takt の中で満たせない受け入れ条件で止まり、CI の判定と振り分けにも穴が 2 つ見つかった話

テストを unit・軽い IT・重い IT・E2E の層にそろえる親チケットの子 21 件を、takt（issue を渡すと、エージェントが計画・実装・レビューまで進めて PR を作る道具）に並列 3 で積み、終わった PR から順にマージした。子チケットの切り方は [前日のエントリ](./2026-10-08.md#test-layers-tickets) にある。takt は止まらずに通った件が多かったが、2 件は takt の中で止まり、2 件は CI の穴を通ってマージされ、そのうち 1 件は main を壊した。回す側の見張りの書き方は [前日のエントリ](./2026-10-08.md#takt-ops-watch) に書いたので、ここでは issue の書き方と CI の作りから見た学びを書く。

- 決定の記録: 親チケット [テストの層をそろえる](https://github.com/daiki-beppu/live-mindmap/issues/543)
- 途中で起こしたチケット: [`check` ジョブが runner を取れなかったジョブを見逃す](https://github.com/daiki-beppu/live-mindmap/issues/589)、[`helper/package.json` だけの変更で server のテストが走らない](https://github.com/daiki-beppu/live-mindmap/issues/599)

### 1. 受け入れ条件は「takt の中で確かめられるか」で分け、外の条件は「マージ後に人が」に回す

helper（Swift で書いた音声の取り込みの子プロセス）の unit のテストを速くするチケットは、受け入れ条件に「縮めても失敗を捕まえられる根拠を PR の本文に書く」を入れていた。takt は実装もレビューも通した（指摘 0 件）のに、最後の判定で止まった。takt は PR の本文を issue の本文から作るので、takt の中のエージェントは PR の本文に書けない。満たせない条件が 1 行あるだけで、全体が「未完了」になる。残った差分を手で PR にし、根拠は自分で本文に書いた（テストは約 7.5 秒から 0.98 秒になった）。

同じ形の条件は、ほかのチケットにもあった。CI のジョブを組み直すチケットの「実際の PR で 4 つの runner が回って通る」「どのジョブが落ちても `check` が落ちる」は、PR がマージされて CI が回るまで分からない。これらは、積む前に行頭へ「（マージ後に人が）」を付けて takt の条件から外し、代わりに takt の中で確かめられる条件を置いた。たとえば、ワークフローの YAML を読んで「`check` の `needs` が全ジョブを含む」ことを確かめるテストや、重い IT の割り振りのロジックを、テスト一覧に見立てた入力で走らせるテストだ。

**エージェントに渡す受け入れ条件は、エージェントの手の届く範囲（ファイルの中身・手元で回るコマンド）だけで書く。** PR の本文・実際の CI・人の目が要る条件は、別の印を付けて後に回し、代わりに手元で確かめられる形の条件を足す。

### 2. issue に書いた再現の例は、今の規則に照らしてから積む

議題（マインドマップの論点のまとまり）を統合したとき、根拠が増えていないのに「根拠が足された」の印が付く、というチケットは、takt の計画の段で「要件どうしが両立しない」と判定され、自動の積み直し 2 回を経て止まった。

食い違っていたのは、私が issue に書いた再現の例だった。例は「1 回目に作り、2 回目に統合して、同じ応答の中で閉じられる」。ところが今の規則では、直前の反映で根拠が足された議題は閉じられない。1 回目に作った根拠は、2 回目から見て「直前」だ。統合を直しても、この例は規則どおりに失敗する。例を規則と両立する 2 本（2 回目に統合して 3 回目に閉じる／3 回目に統合して同じ応答で閉じる）に書き直して積み直すと、APPROVE で通った。

takt の計画のエージェントは、例と規則を突き合わせて、矛盾をきちんと見つけた。止まったのは正しい振る舞いで、直すべきは issue のほうだった。

**再現の例は仕様の一部として読まれる。積む前に、例の 1 手ずつが今の規則で何を返すかをたどる。**

### 3. 必須のジョブの判定は「失敗を探す」ではなく「成功か飛ばしだけか」を確かめる

main へのマージには、CI の最後の `check` ジョブが通ることを必須にしている。`check` は、ほかのジョブの結果を見て落ちるか決める。そのステップの条件は次のとおりだった。

```yaml
- if: contains(needs.*.result, 'failure') || contains(needs.*.result, 'cancelled')
```

ある PR の CI で、helper のジョブが macOS の runner を 15 分取れずに終わった（「The job was not acquired by Runner」。ステップは 1 つも走っていない）。それでも `check` は success になった。runner を取れずに終わったジョブは、`failure` でも `cancelled` でもない結果で渡るらしい。この PR は、たまたま main との衝突でマージされずに済んだが、Swift のテストが一度も走らないままマージできる状態だった。

判定を逆にした。ステップを毎回走らせ、`needs` の結果を `jq` で読んで、`success`・`skipped` 以外が 1 つでもあれば、そのジョブ名と結果を出して落とす。

**取りうる値を全部知らないものを判定するときは、悪い値を列挙せず、良い値を列挙する。** 知らない値は、悪い側に倒れる。

### 4. 変更のパスでジョブを飛ばすなら、テストが読むファイルも振り分けに入れる

CI は、PR が変えたパスでジョブを選ぶ。`helper/` の下だけの変更なら、server と web のジョブ（ts のジョブ）は飛ばす。

helper の型検査（`typecheck` の script）の先頭に、テストの層の点検の script を足すチケットがマージされた。この PR は helper の下だけの変更なので、ts のジョブは飛ばされ、CI は通った。ところが server には、`helper/package.json` を読んで「AEC3（エコーキャンセラー）のライブラリを組む `build-apm` を、ビルドより先に呼ぶ」ことを確かめるテストがある。点検の script が先頭に来たので、このテストは落ちる。main の次の 2 回の CI で初めて落ち、手で順を直した（`build-apm` → 点検 → ビルド）。

直し方は 2 つあった。振り分けに `helper/package.json` を足すか、server のテストを helper の側へ移すか。テストは helper の script が server の期待を守っているかを見るもので、置き場所は正しい。振り分けのほうを直し、`helper/package.json` が変わったときは ts のジョブも走らせた。理由はワークフローのコメントに 1 行書いた。

**パスで振り分ける CI では、「このテストが何のファイルを読むか」がジョブの依存になる。** `grep -rn "helper/" server/test web/test` のように、別のディレクトリのファイルを読むテストを探して、振り分けに足す。

### 5. 依存が解けた子は、ブロッカーが閉じるたびに親から引き直す

子チケットには「この子が閉じてから着手」という依存（GitHub の blocked by）を張ってあった。回す側は、マージのたびに「これで解けた子」を手で数えて積んでいた。CI の helper のジョブを 1 回のビルドから 3 層に分けて回す子は、ブロッカーが閉じた時点で着手できたのに、ほかの子をマージした後まで積み忘れていた。気づいたのは、親の子が全部片付いたと報告しかけたときだった。

積み忘れた間に main は進んでいて、本文の前提（「ビルドを 1 回にする」）は別のチケットで済んでいた。残る作業は、テストを回すステップを 3 つに分けることだけだった。本文を今の main に合わせて直してから積んだ。

**手で数える代わりに、マージのたびに親の子の一覧を引き、「open で、ブロッカーが全部閉じていて、まだ積んでいない」子を機械的に出す。** 遅れて積む子ほど、本文が古くなっている。

### 6. 全員が書き足す 1 行は、並行の PR を毎回衝突させる

`AGENTS.md`（エージェントが毎回読むリポジトリの案内）の Checks の節は、検査の手順を 1 段落に詰めて書いていた。テストの層の子は、ほぼ全部がこの段落に 1 文を足す。並列 3 で流すと、先にマージされた PR の文と後の PR の文が同じ行でぶつかり、後の PR がほぼ毎回 DIRTY（衝突でマージできない）になった。そのたびに、takt の作業場所で `origin/main` に載せ直し、両方の文を残して push した。

衝突の解消は機械的だが、毎回人（回す側のセッション）の手が要り、そのぶんマージが遅れた。

**並行で書き足される文書は、1 項目 1 行の箇条にしておく。** 行が分かれていれば、別々の追記は衝突しない。

## 話者分離の回帰評価を決め、地図を仕様と形式仕様にまとめたら、人の声の素材は要らないと利用者に押し戻され、全探索は時相の性質で TLC に回すと 1 分で済んだ話

話者分離の地図（会議の `相手`（会議アプリの音）のトラックを声で区別し、「相手 A」のような**話者**のラベルを字幕とマップに出す取り組み。[前の日のエントリ](./2026-10-08.md#speaker-diarization-map)）の、最後のチケット「回帰評価の指標」を決めたときの学び。続けて、地図の 10 件の決定を 1 本の実装仕様にまとめ、仕様の「常に成り立つべき性質」を Quint と Alloy で形式化して検証器にかけた。

- 決定の記録: チケット [話者分離の回帰評価の指標](https://github.com/daiki-beppu/live-mindmap/issues/542)、仕様 [話者分離の実装仕様](https://github.com/daiki-beppu/live-mindmap/issues/610)（Formal Spec はそのコメント）、地図 [話者分離：字幕とマップで誰の発言か分かるようにする](https://github.com/daiki-beppu/live-mindmap/issues/367)

### 1. 人の声の素材が要るかは、「どの判定が声のばらつきに頼っているか」で切り分ける

チケットには「基準値を人の声の会議でどう確かめるか。素材をどう用意するか」という問いがあった。これまでの計測は、架空の台本を音声合成（Gemini TTS）で読ませた**合成会議**だけで行っている。TTS は 1 人に 1 つの声を当て、どの行も同じ調子で読むので、人より区別しやすいかもしれない、という心配が地図に書かれていた。

私はこれを素直に受け、人の声で注釈つきの会話コーパスを調べに行った。日本語で 5 人以上の会議があり、企業が使えるのは国語研の CEJC だけで、商業利用は 2 年・社内 10 人以内で 50 万円（税別）、契約は郵送と前払い、音声は CI に置けない。無料で今週中に手に入るのは英語・中国語の会議室の録音（AMI・NOTSOFAR-1 は CC BY 4.0、AISHELL-4 は CC BY-SA 4.0）だった。そこで「AMI と NOTSOFAR-1 を主にし、Opus に通し直して流す」と推した。

利用者の返事は「自作の音声で良くない？」だった。改めて、評価の項目ごとに、人の声で結果が変わりうるかを分けた。

| 測るもの | 人の声で変わりうるか |
| --- | --- |
| 発言ごとの話者の正解率 | 小さい。前の計測で、合成会議の DER（話者の誤りの時間の割合）は、NVIDIA が人の声で出した公開値と同じ水準だった（4 人で 7〜15%） |
| 案の出した人・TODO の担当者・名前 | 声ではなく、AI と規則の問題 |
| 5 人目の声の混入の検出 | 変わりうる。同じ人の声どうしの埋め込みが近いことに頼っており、TTS は同じ人のばらつきが小さい |

人の声が要るのは 3 行目だけだった。次に利用者は「実際に使った時のやつでいいんじゃないの？」と続けた。実際の会議には正解の注釈が無いが、「相手が何人いたか」さえ分かれば、混入の誤検出の回数やラベルの数は数えられる。最後に「TTS だけで問題ないと思うけどな」で決まった。人の声で誤検出しうることは既知の制限として仕様に書き、起きれば `log.jsonl` の検出の記録で気づける、という扱いにした。

外れたのは、地図にあった「TTS は区別しやすいかもしれない」を、項目を分けずに評価全体の前提にしたところだ。分けてみると、心配が当たるのは 1 つの判定だけで、そのために 50 万円のコーパスや英語の会議室の録音を持ち込むのは釣り合わなかった。素材の現実味を上げる前に、どの判定がその現実味に頼っているかを先に分ける。

その途中で利用者に「なんの話？」と聞き返された場面もあった。基準値を選ぶ素材と確かめる素材を分けるか、という問いを、コーパスの名前と cos の値で書いていた。問答が長くなったら、いま何を決めているのかを毎回 1 行で書き直す。

### 2. 「誤ったラベルよりラベルなし」を選んだ設計では、指標でも話者なしを取り違えと分ける

話者分離の地図は、決定のたびに「迷ったらラベルを付けない」を選んできた。確定したラベルが 3 秒待っても揃わない、声の混入を検出した、ヘルパー（音声を取り込んで認識する子プロセス）を作り直した後にまだ照らし合わせが済んでいない、のどれでも、発言をただの `相手` で出す。

正解率を 1 つの数にまとめると、この「意図して付けなかった」分が誤りに数えられる。規則が正しく働くほど、数字が悪化して見えることになる。そこで各**発言**（文字起こしの 1 区切り）を、正解 / 取り違え / 話者なし の 3 つに分けて数えることにした。誤ったラベルは人に結び付いたまま信じられるので、取り違えのほうを重く見る。

同じ考えで、ヘルパーを作り直した後のつなぎ直しは、正しくつないだ / 新しいラベル / 話者なし / 誤ってつないだ の 4 つに分け、誤ってつないだ数を最も重く見る。名前も、誤った名前の数を別に目立たせる。誤った名前は、名前がないより悪いからだ。

### 3. AI の誤りと音声側の誤りは、正しい入力を渡す段を挟んで切り分ける

案の出した人と TODO の担当者は、2 つの段を通って決まる。音声から話者を分ける段と、AI が根拠の発言や担当者を選ぶ段だ。全部を通した値だけを見ると、外れたときにどちらのせいか分からない。

そこで、正解の台本（`timeline.tsv`。行ごとの話者と時刻）から、正しい話者つきの発言を作って流す段を足した。この段で外れれば、差分更新のプロンプトか根拠の選び方の問題だと分かる。字幕の精度の計測で、認識の誤り（CER）を認識だけで測っているのと同じ切り分け方だ。

### 4. 「再生で測り直せるようにログに残す」と決めたら、読み直す経路が本当にあるかを確かめる

話者分離の ADR には、「発言に決まった話者と、ヘルパーから届いた生の話者の区間を両方ログに残す。規則を変えたら再生で測り直せるように」と書いてあった。仕様を書く前に、継ぎ目を調べるサブエージェントにコードを読ませた。すると、今の再生（`cli play`）は**締めた後の発言**だけを差分更新に流していて、発言を締める規則も、その手前の関所も通らないことが分かった。生の区間をいくら残しても、規則を変えて測り直す経路は無い。

仕様には「締める前の入力（`remark` / `partial` と話者のイベント）を、届いた時刻の順にもう一度流す経路を足す」と書き、Eval の切り出しもこの経路の上に組んだ。記録を残す決定は、それを読み直す側があって初めて意味を持つ。ADR を書いた時点では、そこまで確かめていなかった。

### 5. 全探索が時間切れになったら、性質を時相で書いて TLC に回し、動きの違う部分は別の検査器に分ける

仕様の性質を形式化した。ラベルは初めて話した順に振り、使い回さない。混入で戻したラベルは会議の最後まで戻したまま。出した発言は書き換えない。手入力の名前は AI が変えない。案の出した人は更新で変わらない。検証器は takt の `/verify` と同じもの（Quint は `--max-steps 20`、時相の性質が無ければ Apalache、あれば TLC。Alloy は全部の `run` / `check`）で、このスキルでは全探索の上限を 5 分にしている。

最初は、ラベル・発言・名前・案・TODO を 1 つの Quint のモジュールに入れ、「書き換えない」は 1 つ前の状態の控えを変数に持たせて不変条件で書いた。構文と模擬実行は通ったが、Apalache の全探索が 5 分で時間切れになった。ラベルを 4→3、発言を 6→4 に減らしても同じだった。

効いたのは書き方を変えることだった。

- 「書き換えない」「戻したまま」「つないだら替わらない」は `always(p implies always(p))` の時相の性質で書いた。控えの変数が要らなくなり、検証器は TLC に切り替わる。状態をラベル 3・発言 4・作り直し 1 回に抑えたモデルは、TLC の全探索が約 1 分で終わった
- 名前と案の出した人は、ラベルの動きと独立している。こちらは Alloy 6 の時間つきのモデル（`for 3 but 8 steps`）に移した

Alloy では 2 か所でつまずいた。`fact steps` は `steps` が Alloy 6 の予約語なので構文エラーになった。また、`some rs: set Remark | addPlan[p, rs]` のように集合を量化すると、「skolem 化できない高階の量化」で解けなかった。根拠は 1 つずつ足す形に直した。いちばん早い発言で追加し、残りを更新で足すのと同じなので、性質は変わらない。

12 の性質がすべて反例なしで通り、要件どうしの矛盾は見つからなかった。中には、仕様のどこにも直接は書いていない性質もある。「案の出した人は、更新や統合を経ても、いつもその案の根拠の発言のどれかの話者」は、「追加のときに決めて変えない」「統合では早いほうを残す」「根拠は増えるだけ」の 3 つを組み合わせて初めて言える。形式化して得をするのは、こうした組み合わせの性質を機械に確かめさせられるところだ。
