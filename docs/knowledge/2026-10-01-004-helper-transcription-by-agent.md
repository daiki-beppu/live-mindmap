# 会議音声を文字起こしする Swift のヘルパーを、AI エージェントのワークフローに実装させた話

live-mindmap（会議の音声から、AI がマインドマップを差分更新し続ける Web アプリ）の開発で、会議アプリの音を取って文字にする Swift のヘルパー（常駐プロセス）を作ったときの学び。ヘルパーは、選んだ会議アプリの音を Core Audio のプロセスタップ（アプリ単位で出力音を横取りする macOS の API）で取り、Apple の SpeechAnalyzer（端末内の音声認識）に流し、結果を localhost の WebSocket に配る。実装は人が書かず、takt という AI エージェントのワークフロー実行ツールに任せた。takt は、計画 → テストを書く → 実装 → 観点別のレビュー（5 観点を並行）→ 指摘の裁定 → 修正 → 修正の検証 → 最終判定、という工程を順に回す。どの工程も別のエージェントが受け持ち、工程ごとに報告書を残す。この記事は、その報告書と差分から拾ったものだ。

- 決定の記録: [ヘルパー：会議の音声を文字起こしする](https://github.com/daiki-beppu/live-mindmap/issues/33)、[ADR 0002 音声取得と STT はローカルのヘルパーが行う](../adr/0002-local-stt-helper.md)
- 用語集: [`CONTEXT.md`](../../CONTEXT.md)（発言・途中結果・トラックの語彙）
- 前の記事: [LLM がマップを差分更新する中核を、テストファーストで本実装した話](./2026-10-01-002-core-module-tdd.md)

前提として、次のことが決まっていた（音の取り方を実測して決めた経緯は[別の記事](./2026-09-30-005-local-realtime-stt.md)にある）。

- **発言**は、STT（音声認識）が確定させた文字起こしの 1 区切り。**途中結果**は、確定前に届く暫定の文字列で、後で書き換わる
- **トラック**は音の出どころで、`相手`（選んだ会議アプリの音）と `自分`（マイク）の 2 つ。今回作るのは `相手` だけだが、`自分` も同じ形で流せるようにする
- Mac 全体の出力はタップしない。通知音や別のタブの動画まで拾うため
- 実機で会議を流して途中結果と発言が届くかは、人が確かめる

## 1. イベントの形は、受け取る側の型と「誰が何を採番するか」から決める

ヘルパーが WebSocket に流すイベントの形は、この作業で決めることになっていた。受け取る側のサーバーには、すでに発言の型があった。計画の工程は、項目名をその型に合わせたうえで、2 つの点で型をそのまま写さなかった。

```json
{"type":"partial","track":"相手","text":"こんに"}
{"type":"remark","track":"相手","start":1.5,"end":3.25,"text":"こんにちは","duplicate":false}
```

- **`id` を付けない。** サーバーの発言の型には `id` があるが、採番はサーバーが行う。ヘルパーでも振ると、ID の出どころが 2 つになる
- **途中結果に時刻と重複の印を付けない。** STT の途中結果にも時間範囲は付いてくる。だが、それを載せると途中結果と発言が同じ形になり、受け取る側が `type` だけで区別することになる。途中結果は 3 項目、発言は 6 項目と、キーの集合そのものを変えた

テストは値だけでなく、JSON のキーの集合が完全に一致することを確かめている。入力に時刻がある途中結果を渡しても、出力のキーは `type/track/text` の 3 つだけになる。

**境界のイベントは、受け取る側の型を写すのではなく、「その値を誰が決めるか」で項目を削る**。

## 2. 実機でしか動かない部分は、選ぶロジックと OS の呼び出しに分けて、選ぶほうだけを細かくテストする

プロセスタップと SpeechAnalyzer は、実機で音を出さないと動かない。そこで「どのプロセスをタップするか」を選ぶ純粋関数と、選んだプロセスでタップを作る部分を分けた。選ぶほうには、プロセスの一覧を偽物で渡すテストを並べた。そこで決まった規則が 3 つある。

| 場面 | 素直な実装で起きること | 決めた規則 |
| --- | --- | --- |
| Chrome を選ぶ | `hasPrefix("com.google.Chrome")` だと、`com.google.ChromeCanary.helper` まで一致する | 完全一致か、`appBundleID + "."` で始まるものだけ |
| ブラウザを選ぶ | 本体をタップしても音は来ない。音はヘルパーのプロセスから出る | 本体と `.helper`、`.helper.Renderer` を、無音のものも含めてすべて対象にする |
| 合うプロセスが 0 件 | 「全部をタップすれば何か取れる」と広げたくなる | エラーで終わる。Mac 全体のタップには切り替えない |

1 つのプロセスが複数の起動中アプリに一致するときは、最も長い bundle id のアプリに割り当てる。そうすれば、結果が起動中アプリの並び順に左右されない。

実際のタップの作成と文字起こしは、モックでテストしなかった。モックで通しても、実際の API がそう動くことの確認にはならないからだ。そちらは手順を README に書き、人の実機確認に回した。

**実機が要る処理は、判断の部分を純粋関数に切り出して細かくテストし、OS の呼び出しはモックせずに実機の確認へ回す**。

## 3. 実行ファイルの最上位に書いた配線はテストできないので、薄い関数に切り出す

最初の実装では、STT の結果をイベントにして WebSocket に流すループが `main.swift` に直接書かれていた。Swift の実行ターゲットの最上位のコードは、テストから呼べない。takt の伴走役（コンパニオン）が、ここを「テストできない経路」と指摘した。

対応は、ループを `HelperCore`（ライブラリ側）の関数に移すだけだった。

```swift
public func relay<Results: AsyncSequence>(
    _ results: Results, track: Track, to server: WebSocketServer
) async throws where Results.Element == TranscriptionResult {
    for try await result in results {
        await server.broadcast(try event(from: result, track: track).jsonString())
    }
}
```

テストは、結果の流れを直接渡し、本物の WebSocket クライアントに `partial`、`remark` の順で届くことを確かめる。STT 全体の偽物は作らなかった。確かめたい受け渡しが `relay` の内側に収まるからだ。`main.swift` が `relay` を呼んでいるかどうかだけは、自動テストの外に残る。

**テストできない場所に置いたコードは、偽物を作り込む前に、テストできる場所へ移せないかを考える**。

## 4. 観点を分けた並行レビューは、テストが通った後の「失敗の経路」を拾う

実装の工程が終わった時点で、テストは 23 件すべて通っていた。そのあと 5 つの観点（セキュリティ・コーディング・AI 生成コードの癖・アーキテクチャ・テスト）のレビューを並行で回すと、5 観点すべてが差し戻した。指摘は 9 件あり、裁定の工程がそれを 3 つの問題にまとめた。

| 問題 | どこで見つかったか | 中身 |
| --- | --- | --- |
| A | 3 観点が同じ箇所 | 音声形式の変換器を作れないと `guard let converter else { continue }` でバッファを捨て続ける。タップは動いているのに何も届かず、エラーにもならない |
| B | 2 観点 | 取得から認識までの 2 つのキューに上限がない。認識が遅れると、長い会議でメモリが増え続ける |
| C | 2 観点 | Ctrl-C のシグナルで呼ぶ `stop()` と、`start()` がロックなしで同じ資源を触る。開始の途中でシグナルが来ると、終了の要求が失われる |

どれも正常系のテストでは出てこない。問題 C は、一度 `SIG_IGN` に差し替えたシグナルを受け損なうと、Ctrl-C を押しても止まらなくなる、というところまで裁定に書かれていた。

裁定は、直さない指摘も 2 件決めた。

- **WebSocket に認証がない（セキュリティ）。** 現象は本当にある。`127.0.0.1` に束縛しても、同じ Mac の別ユーザーのプロセスはつなげる。しかし、仕様にも ADR にも「localhost の WebSocket に流す」としか書かれていない。裁定は認証を勝手に足さず、「必要以上の拡張」として別の要求に持ち越した
- **`自分` のトラックが転送で正しく届くかのテストがない（テスト）。** 指摘は「`relay` がトラックを `相手` に固定していたら」という仮定に立っていた。実際のコードはトラックを引数のまま渡している。そのため「根拠なし」として退けた

**レビューの指摘は、仕様に照らして「直す」「別の要求として持ち越す」「前提が成り立たない」に分ける**。現象が本当でも、仕様にない契約をレビューで足すと、作業の範囲が黙って広がる。

## 5. 音声のキューがあふれたら、捨てずにエラーで止める。時刻がずれるから

問題 B の直し方には、選択肢が 2 つあった。あふれた分を捨てて処理を続けるか、エラーで止めるか。リアルタイムの音声なら、古い分を捨てて追いつく案は自然に見える。

止めるほうを選んだ。SpeechAnalyzer が結果に付ける時刻は、「入力に流し込んだ音声の先頭から何秒か」で数えられる。途中でバッファを 1 つ捨てると、その後のすべての発言の時刻が、捨てた長さだけ黙って前にずれる。発言の時刻はマップのノードの根拠として残るので、ずれたまま動き続けるより、止まって気づけるほうがいい。

```swift
// 2048 個: 1 個あたり約 10 ms 前後の IO バッファを想定して約 22 秒分。通常の遅れは吸収し、処理が止まった場合だけ超える。
let (stream, continuation) = AsyncThrowingStream.makeStream(
    of: AVAudioPCMBuffer.self, throwing: Error.self, bufferingPolicy: .bufferingOldest(limit))
// …IOProc の中で
if case .dropped = continuation.yield(copy) {
    continuation.finish(throwing: ProcessTapError.backlogExceeded(limit: limit))
}
```

`AsyncStream` の `yield` には背圧（送り手を待たせる仕組み）がない。上限を決めない限り、既定のキューは無制限に溜まる。上限 2048 という値が実機の IO バッファの大きさに合っているかは、まだ測っていない。

**時刻を「入力の累積」で数える処理の前では、データを間引かない。あふれたらエラーで止める**。

## 6. テストを走らせるコマンドは 1 か所に固定する。工程が変わると、エージェントは素のコマンドに戻る

この Mac には Xcode がなく、Command Line Tools だけが入っている。その環境では、素の `swift test` が swift-testing のマクロを見つけられずに失敗する。

```text
plugin for module 'TestingMacros' not found
```

テストを書く工程のエージェントがこれに気づき、マクロのプラグインの場所を渡す引数を見つけた。実装の工程はそれを `package.json` の test スクリプトに入れ、23 件を通した。

```sh
swift test -Xswiftc -plugin-path -Xswiftc /Library/Developer/CommandLineTools/usr/lib/swift/host/plugins/testing
```

ところが、レビュー後の修正の工程は、素の `swift test` を叩いて同じエラーで失敗した。その結果、問題 C のために足した `stop()` のテストは、この作業の中では一度も実行されなかった。救いは、修正の検証の工程が、それを成功の証拠に数えなかったことだ。「テストは失敗、実行結果は得られていない」と書き、後続の確認に引き継いだ。

同じ引数の不足は、ほかにもあった。音声バッファの型（`AVAudioPCMBuffer`）がスレッド間で安全に渡せる印（`Sendable`）を持たないため、Swift 6 の言語モードではタスク間の受け渡しがエラーになる。これは `Package.swift` で言語モードを 5 にして避けた。テストを書く工程では、もう 1 つつまずきがあった。`stop()` の直後に同じポートで待ち受け直すテストが、OS の都合で不安定になった。そこで「`stop()` の後は新しい接続を受けない」という確かめ方に置き換えた。

**環境に合わせた実行コマンドは、スクリプトに 1 か所だけ書き、どの工程もそれを使うよう指示する**。工程ごとに別のエージェントが動く仕組みでは、前の工程の発見が次の工程に自動では伝わらない。

## 7. 利用上限で止まった実行は、すぐに再試行せず、止まった工程から再開する

最初の実行は 30 分ほど進み、修正の検証の工程で止まった。AI のサービス側の利用上限（rate limit）に当たったためだ。止まった直後に 2 回、再開が試みられた。だが、どちらも 5〜6 秒で同じ理由で失敗した。利用上限は、時間がたたないと解けない。

17 分ほど待ってから、止まった工程を起点に再開した。計画・テスト・実装・レビュー・修正をやり直さず、修正の検証から続けた。そこから 2 回目のレビュー（5 観点すべて承認）と最終判定まで、13 分で終わった。工程に使った時間は、合計で約 43 分だった。

工程ごとに報告書がファイルで残っているので、途中から再開しても、前の工程の判断を読み直せる。再開後の検証の工程は、前の実行の修正報告をそのまま読んでいる。

**利用上限による停止は、間を置いて、止まった工程から再開する**。すぐの再試行は、同じ失敗を重ねるだけだ。

## その後

この作業のあと、マイクを `自分` のトラックとして足す作業で、ここで決めたことのうち 2 つが変わった。

- **発言の時刻の起点。** この作業では「キャプチャ開始からの秒数」とし、SpeechAnalyzer が返す時刻をそのまま使った。トラックが 1 つならそれで足りる。しかし、`相手` と `自分` で SpeechAnalyzer を 2 本並べると、それぞれが自分の最初の入力を 0 秒として数える。そのため、同じ瞬間の発言でも時刻が揃わない。そこで、取得した音声のバッファに取得時点のホスト時刻（OS の単調な時計）を付けるようにした。そのうえで、`run` が取得を始める直前を 0 とする、2 トラック共通の秒数に補正している。5 節の「時刻は入力の累積で数えられる」という性質が、ここでも効いた
- **退けたテスト。** 4 節で「根拠なし」とされた `自分` のトラックの転送も、2 トラックを実際に流すようになった時点で、「自分と相手の結果が、トラック違いの同じ形のイベントとして 1 つの接続先に届く」というテストとして入った。指摘の前提は外れていても、確かめたい振る舞いそのものは、次の作業で必要になった

6 節で一度も実行されなかった `stop()` のテストは、いまの main で `package.json` のコマンドから流すと、ほかと合わせて 40 件すべて通る。
