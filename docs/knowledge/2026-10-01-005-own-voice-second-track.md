# 自分の声を 2 本目の音声認識で文字起こしし、2 トラックの時刻を揃えた話

live-mindmap（会議の音声から、AI がマインドマップを差分更新し続ける Web アプリ）の開発で、Mac 上で動く Swift のヘルパー（音声を取って文字起こしし、localhost の WebSocket でイベントを流す常駐プロセス）に、**自分の声**の文字起こしを足したときの学び。それまでのヘルパーは、会議アプリの音（相手の声）だけを Apple の SpeechAnalyzer（macOS 26 からの端末内の音声認識）で文字にしていた。今回、マイクの音を 2 本目の SpeechAnalyzer に流し、2 つの**トラック**（音声の出どころ。`自分` はマイク、`相手` は会議アプリの音）の結果を、同じ形・同じ時刻の基準で流すようにした。

実装は、AI エージェントのワークフロー実行ツール（takt）が、計画 → テスト → 実装 → 複数の観点のレビュー → 修正、の順に自動で進めた。下の学びのいくつかは、その途中でレビュー役が出した指摘と、計画のやり直しから来ている。

- 決定の記録: [ヘルパー：自分の声を別トラックで文字起こしする](https://github.com/daiki-beppu/live-mindmap/issues/34)、[ADR 0002 音声取得と STT はローカルのヘルパーが行う](../adr/0002-local-stt-helper.md)
- 用語集: [`CONTEXT.md`](../../CONTEXT.md)（発言・途中結果・トラックの語彙）
- 前の記事: [LLM がマップを差分更新する中核を、テストファーストで本実装した話](./2026-10-01-002-core-module-tdd.md)

前提として、次のことが決まっていた。

- ヘルパーが流すイベントは 2 種類。**途中結果**（確定前の暫定の文字列）と、**発言**（STT が確定させた 10〜15 秒程度の 1 区切り。トラック・開始と終了の秒数・本文を持つ）
- Apple のエコーキャンセル（音声処理）は使わない。同じプロセスで有効にすると、会議アプリの音を取るプロセスタップ（Core Audio の、特定のプロセスの音だけを取る仕組み）が止まるため
- スピーカーで聞くと相手の声が自分のマイクにも入る。この二重の文字起こしは、後でサーバー側が時刻と文字列の重なりで見分ける。そのため、2 トラックの `start` / `end` は同じ基準の秒数でなければならない

## 1. 認識器を 2 本にすると時刻の原点も 2 つになるので、共通の時計で先頭の差を 1 回だけ補正する

SpeechAnalyzer が返す結果の時刻は、「そのアナライザに最初に入れた音声を 0 とする秒数」で、入れたサンプル数から計算される。アナライザが 1 本なら、これがそのまま「キャプチャ開始からの秒数」になる。2 本にすると、原点が 2 つになる。プロセスタップとマイクは開始のタイミングが少しずれ、アナライザの準備が終わるまでの待ちもトラックごとに違うからだ。

計画の段階で比べた案は 3 つあった。

| 案 | 採否 | 理由 |
| --- | --- | --- |
| 音声の取得側がバッファに取得時のホスト時刻（Mac の単調な時計）を付け、`run` で 1 回だけ取った基準時刻との差を、結果の時刻に足す | 採用 | 差を足す計算は純粋関数になり、テストできる |
| SpeechAnalyzer の入力に、バッファの開始時刻を渡す API（`AnalyzerInput(buffer:bufferStartTime:)`）を使う | 不採用 | API はあるが、渡した値が結果の時刻にどう反映されるかは、実機でないと確かめられない |
| 補正しない（同時に始めるので差は小さいとみなす） | 不採用 | 準備の待ちがトラックごとに違い、ずれが残る |

採った方式は、次の形になった。

```swift
// main.swift: 2 トラック共通の基準。音声取得を始める直前に 1 回だけ取る
let origin = AudioGetCurrentHostTime()
let theirResults = try await theirTranscriber.transcribe(tap.start(), origin: origin)
let myResults = try await myTranscriber.transcribe(microphone.start(), origin: origin)
```

各トラックは、最初に届いたバッファの取得時刻と `origin` の差を 1 回だけ記録し、以後のすべての結果の `start` と `end` に同じ量を足す。トラックの中の時刻は、これまでどおり SpeechAnalyzer のサンプル数から出る値を使う。補正するのは先頭の差だけで、60 分の間に生じるデバイスのクロックのずれは補正しない（要求にないため）。

テストでは、取得の開始が相手 0.5 秒・自分 1.2 秒とずれた 2 トラックに、共通の基準で 3.0〜4.0 秒にあたる発言を流した。アナライザから見ると、相手は 2.5〜3.5 秒、自分は 1.8〜2.8 秒になる。補正後はどちらも 3.0〜4.0 秒になることを確かめている。

**音声認識を並べるときは、結果の時刻が何を原点にしているかを先に確かめ、共通の時計への変換を 1 か所に置く**。

## 2. 時刻は「読み出した時点」ではなく「取得した時点」のタイムスタンプから取る

補正量を決める「最初のバッファの時刻」には、2 通りの取り方がある。バッファを読み出したときに時計を見るか、取得したときに付いたタイムスタンプを使うかだ。

ヘルパーでは、取得したバッファはいったん上限 2048 個のキューにためてから、文字起こしの側が読み出す。プロセスタップは `transcribe` を呼ぶ前に動き始めるので、最初の数個のバッファは、読み出されるまでキューで待つ。読み出した時刻を使うと、その待ちの分だけ基準がずれる。

そこで、取得のコールバックが受け取るタイムスタンプを使った。

- プロセスタップ: IOProc の第 3 引数 `inInputTime` の `mHostTime`（`mFlags` に `hostTimeValid` があるとき）
- マイク（AVAudioEngine）: `installTap` のブロックが受け取る `AVAudioTime` の `hostTime`（`isHostTimeValid` のとき）

どちらも有効でないときだけ、その場で `AudioGetCurrentHostTime()` を使う。2 つの出どころは同じホスト時刻の時計なので、そのまま比べられる。

**バッファをためて後で処理する経路では、時刻を処理の側で取らず、取得のコールバックで付けて運ぶ**。

## 3. 並行タスクの「最初のエラーで全体を止める」は、`waitForAll()` では書けない

2 トラックの結果は、Swift の `withThrowingTaskGroup` で並行して WebSocket に流す。決めた振る舞いは次の 2 つだった。

- どちらかのトラックがエラーで終わったら、そのエラーを返し、もう一方も止める
- 片方が正常に終わっても、もう一方は止めない

最初の実装は、グループの最後で `try await group.waitForAll()` を呼んでいた。すると、「一方がエラーで終わり、もう一方は終わらない流れ」を渡すテスト 2 件が、どちらも 60 秒のタイムアウトで失敗した。`waitForAll()` は、子のタスクが投げたエラーを受け取ってもグループをキャンセルせず、残りのタスクが終わるまで待つ。会議の音声のように終わらない流れが残っていると、エラーが起きても戻らない。

グループの結果を 1 つずつ受け取る形に直すと、通った。

```swift
try await withThrowingTaskGroup(of: Void.self) { group in
    for (track, results) in tracks {
        group.addTask { try await relay(results, track: track, to: server) }
    }
    // 最初のエラーで抜ける。グループを抜けるときに、残りのタスクはキャンセルされる
    for try await _ in group {}
}
```

テストでは、終わらない側の流れの `onTermination` が呼ばれることまで見ている。キャンセルが伝わって、マイクやプロセスタップの読み出しが本当に止まることの確認になる。

**終わらない流れを並行に扱うときは、「片方が失敗したらもう片方は止まるか」を、終わらない偽の流れでテストする**。

## 4. 規則を確かめていないテストは、規則を private から出して型にすれば書ける

1 の補正には、「補正量は最初のバッファで 1 回だけ決め、2 本目以降で上書きしない」「記録した補正量をすべての結果に足す」という規則がある。最初の実装では、この規則が文字起こしクラスの中の `private` な小さな型と、2 か所の呼び出しに分かれていた。テストは、秒数を出す関数と、時刻をずらす関数に、手で計算した値を渡しているだけだった。

テストを担当するレビュー役が、ここを指摘した。

> 共通時刻のテストは同じ `offsetSeconds` 呼び出しを 2 回比較するだけです。（中略）既存テストはその補正を外しても成功します。

実装役は最初、規則のテストには SpeechAnalyzer を差し替える層の新設が要るとして、テストを純粋関数の組み合わせに書き換えるところで止めた。その後の再計画で、この想定が崩れた。SpeechAnalyzer に依存しているのは結果の流れの元だけで、補正の規則そのものは SpeechAnalyzer がなくても成り立つ。テストできなかった本当の理由は、規則が `private` の中に散らばっていたことだった。

規則を `internal` の型 `TrackTimeline`（`record` で最初の 1 回だけ記録し、`align` で結果をずらす）にまとめ、テストを `@testable import` にした。足したテストは、それぞれ 1 つの誤実装を落とすように選んだ。

| テスト | 落とす誤実装 |
| --- | --- |
| 0.5 秒後のバッファを記録し、2.5〜3.5 秒の結果をずらすと 3.0〜4.0 秒になる | 補正量を結果に足さない |
| 0.5 秒後の次に 0.9 秒後のバッファを記録しても、結果は 3.0〜4.0 秒のまま | 2 本目以降で上書きする（3.4 秒になる） |
| 相手 0.5 秒・自分 1.2 秒の 2 トラックで、同じ瞬間の発言が両方 3.0〜4.0 秒になる | 2 トラックで補正量を共用する |

その後のアーキテクチャのレビューで、秒数を出す関数と時刻をずらす関数に `public` が付いたままだと指摘され、`internal` に戻した。テストは `@testable` で内部の型を呼べるので、公開する必要はなかった。

**「外部への依存があるからテストできない」と判断する前に、確かめたい規則が依存の外で成り立つかを見る。成り立つなら、規則を内部の型に切り出して、公開せずにテストする**。

## 5. 文字列で比較するテストが揺れたら、出力の順序を固定する

イベントは JSON の文字列にして WebSocket に流し、テストは受け取った文字列を期待値と比べている。2 トラックのテストを足したところ、`JSONEncoder` の出力のキーの並びが呼び出しごとに変わり、テストがときどき落ちた。既存のテストの 1 件も、同じ理由で潜在的に不安定だった。

テスト側で JSON を解析して比べる案もあったが、エンコーダに `.sortedKeys` を指定した。キーと値は変わらず、並びだけが決まる。変更後、テストを 3 回続けて流し、38 件すべてが通ることを確かめた。

あわせて、2 トラックの到着順そのものは決まらないので、テストでは「全体の集合が一致すること」と「同じトラックの中の順序が保たれること」を分けて確かめている。

**並行に届くものを比べるテストは、決まらない順序（キーの並び、トラック間の到着順）を、出力の側で固定するか、比較の側で無視するかを、1 つずつ決める**。

## 6. localhost の WebSocket でも、ブラウザの別のサイトからは接続できる

セキュリティのレビュー役は、マイクの文字起こしが流れる WebSocket が、接続元（`Origin`）を確かめていないことを指摘した。待ち受けは `127.0.0.1` に限っているが、それはネットワークの外からの接続を防ぐだけで、利用者のブラウザで開いた別のサイトのページは `ws://127.0.0.1:8765` につなげる。ヘルパーが動いている間、そのページは利用者の発言を受け取れることになる。

自分の声を足したことで、流れる内容は「会議アプリの音」から「マイクに入ったすべての音」に広がった。それでも、今回の修正では扱わず、範囲外とした。接続を受ける部分は今回の変更の対象外のファイルにあり、許可する `Origin` や認証の方式は、まだつないでいないサーバー側の設計と一緒に決める必要があるためだ。この判断は、レビューの裁定として記録に残した。

**localhost で待ち受けるサーバーは「外から届かない」と思いがちだが、ブラウザからは届く。流す内容が広がる変更のときに、接続元の確認があるかを見直す**。

## 7. 自動で確かめられない前提は、人が実機で確かめる手順として残す

今回のテストは、偽の結果の流れと、手で作ったホスト時刻で通している。次のことは、単体テストでは確かめられない。

- 会議アプリの音とマイクを同時に流したとき、2 トラックの発言が実際に届くこと
- SpeechAnalyzer の結果の時刻が「最初に入れた音声を 0 とする秒数」であるという、1 の方式の前提
- 2 本の SpeechAnalyzer を 60 分同時に動かしても止まらないこと、そのときの CPU の負荷

ワークフローの中では実行できないので、ヘルパーの README に手順として書いた。2 つ目の前提は、「2 トラックの近い時刻の発言が、近い `start` / `end` になること」を見ることで確かめる。CPU は、次のコマンドで 1 分ごとに記録する。

```sh
top -pid $(pgrep -f live-mindmap-helper | head -1) -l 0 -s 60 -stats pid,cpu,mem | tee helper-cpu.log
```

自動の実装では、こうした項目は「確認済み」ではなく「環境のため未実証」として報告させ、どの確認で補うかを一緒に書かせた。テストが全部通っても、マイクから `自分` として流れる配線の誤りは検出できない、と報告に明記されている。

**自動で確かめられない受け入れ条件は、確かめ方（見る値とコマンド）まで書いた手順にして、人に渡す**。
