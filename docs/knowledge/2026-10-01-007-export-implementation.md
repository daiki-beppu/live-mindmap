# 会議のマップを md・json・Drawnix に書き出す処理を、AI エージェントのワークフローに実装させた話

live-mindmap（会議の音声から、AI がマインドマップを差分更新し続ける Web アプリ）の開発で、**エクスポート**を実装したときの学び。エクスポートとは、その時点のマップを、人とエージェントが使える形でセッションの外へ書き出すことをいう。何をどの形式で出すかは、[前の記事](./2026-10-01-001-export-formats.md)で決めてあった。今回は、その決定どおりに作ったときに分かったことを書く。決定どおりにはいかなかった点や、決定には書かれていなかった点、はまりどころが中心になる。実装は、AI エージェントのワークフロー実行ツール takt に任せた。takt は、計画 → テストを書く → 実装 → 観点別のレビュー → 指摘の裁定 → 修正 → 再レビュー → 最終確認、という手順でエージェントを順に動かす。手順は全部で 16 段になった。途中で利用上限に当たって約 45 分止まり、再開してから完了した。

- 決定の記録: [エクスポート（md・json・drawnix）](https://github.com/daiki-beppu/live-mindmap/issues/41)、[エクスポート：会議の後に何をどの形式で取り出すか](https://github.com/daiki-beppu/live-mindmap/issues/23)
- 用語集: [`CONTEXT.md`](../../CONTEXT.md)（ノードの種別・根拠・セッション・再生の語彙）
- 形式を決めたときの記事: [会議のマインドマップを会議の後に何の形で取り出すか決めた話](./2026-10-01-001-export-formats.md)

前提として、次のことが決まっていた。

- 出力は、人が読む `map.md`、エージェントが加工する `map.json`、Drawnix（ブラウザで動くホワイトボード・マインドマップのツール）で開いて直す `map.drawnix`、マップの画像 `map.png` の 4 つ。すべて同じスナップショット（その時点のマップ全体）から作る。今回の範囲は画像を除く 3 つ
- **セッション**（1 つの会議を追う一続きの作業）の終了時には、ログと同じフォルダに自動で書き出す。会議の途中の `export` は、ファイルにせず標準出力に出す
- `map.md` の根拠（ノードの元になった発言への参照）は、会議の中の時刻だけで示す。却下した案は取り消し線で元の位置に残す
- 同じ時間帯に、ブラウザの表示・ログからの復元・回帰評価も、別のエージェントが並行して実装していた

## 1. 「同じスナップショットから作る」は、スナップショットを 1 回だけ取る書き出し口を 1 つ置いて守る

「4 つの出力はすべて同じスナップショットから作る」は、形式ごとに書き出し関数を作ると簡単に崩れる。形式ごとにセッションからマップを取り直すと、その間に差分更新が入ったとき、md と json の中身が食い違う。

実装では、書き出しの入口を 1 つの関数にまとめた。スナップショットを 1 回だけ取り、3 形式すべてに同じ値を渡す。

```ts
// セッション終了時の書き出し。スナップショットは 1 回だけ取り、3 形式に同じものを渡す。
export function writeSessionExports(dir: string, exp: JsonExport): string[] {
  return Object.entries(exportFiles(exp)).map(([name, content]) => {
    const path = join(dir, name);
    writeFileSync(path, content.endsWith("\n") ? content : content + "\n");
    return path;
  });
}
```

形式への変換（`exportFiles`）は Node に依存しない中核に置き、ファイルに書くのは CLI の側だけにした。中核に `node:*` の import が無いことは、中核だけを対象にした型チェックで確かめている。

この 1 か所にまとめる形は、後から別の理由でも効いた。受入条件には「再生・ライブの**両方**の終了時に書き出す」とあった。しかし、ライブのセッションはまだ作られていなかった（後続のチケットの範囲）。最初のレビューでは、4 観点のうち 3 観点がライブ側が無いことを、そのうち 2 観点は画像が無いことも、差し戻しの理由に挙げた。裁定の段はこれらを範囲外と判断し、人も「ライブと画像は後続のチケットで作る。そのとき同じスナップショットから出力を足せるよう、書き出しの入口は 1 か所にしておく」と範囲を補足した。ライブの終了処理は、後でこの関数を呼ぶだけでよい。

**「全部を同じ元から作る」という決定は、元を取る場所を 1 つの関数に閉じ込めて守る**。まだ無い呼び出し元があっても、入口が 1 つなら後から足せる。

## 2. 「時刻だけ付ける」と決めても、根拠が複数あるときと 1 時間を超えるときの表記は、実装で初めて決まる

形式を決めたときは「ノードごとに会議の中の時刻を付ける（例：`（12:34）`）」と決めた。実装に入ると、決めていない場合が 2 つ出てきた。

- 根拠の発言が複数あるノードは、どの時刻を出すか
- 会議が 1 時間を超えたとき、`1:01:40` と書くか、`61:40` と書くか

前者は「最も早い発言の開始時刻」にした。ノードの話が最初に出た時刻なので、録音をたどる起点になる。後者は分を 60 以上のまま出し、`61:40` とした。書式が 1 種類で済み、並べたときに桁が揃う。

ほかにも、決めていなかった細部をテストで固定した。項目の無い一覧は見出しだけにせず `- なし` と書く。TODO の担当者と期限は、あるものだけを出す。冒頭の決定の一覧は、どの論点への決定かが分かるよう `面接は何回か → 2 回にする` の形にする。テストは、全部の状態を含むマップを 1 つ組み、`map.md` の全文と一致するかを見た。根拠が 3725 秒と 3700 秒の 2 つある TODO が `（61:40）` になる行も、その中に入れた。

```text
## TODO
- 求人票を直す（担当：佐藤・期限：来週）（00:28）
- 日程を決める（61:40）
```

**「時刻を付ける」「件数を出す」のような表記の決定は、値が複数あるとき・空のとき・桁が上がるときの 3 つを、実装の前に決めておく**。決めていなければ、全文一致のテストに入れて、実装の判断を見える形で残す。

## 3. 「同じ内容」を文字列で比べるなら、末尾の改行を足す場所を 1 か所に決める

テストを書く段のエージェントは、次の 2 つのテストを書いた。

- `map.json` のファイルの中身は、直後の `export --format json` の標準出力と文字列で一致する（標準出力は末尾に改行が付く）
- 中核の `exportFiles` が返す `map.json` の文字列は、`JSON.stringify` の結果そのもの（末尾に改行が無い）

どちらも単独では正しい。しかし、同じものを片方は改行あり、片方は改行なしで求めている。実装の段のエージェントは、ファイルに書く直前に「末尾に改行が無ければ足す」ことで両立させた（1 節のコードの `content.endsWith("\n")`）。

これで動くが、改行を付ける場所が、標準出力の側とファイルの側の 2 か所に分かれた。後で 3 か所目の出力を足すときにも、同じ判断をもう一度することになる。

**出力どうしを文字列一致で比べる契約を置くなら、末尾の改行を付ける層を 1 つに決めてから書く**。中身を作る関数は改行を付けず、ファイルや標準出力に書く層で付ける、のように揃える。

## 4. 「途中で」の契約は、途中で止めた状態を作ってテストする

`export` は会議の途中に呼ばれる。CLI の再生は、ログを書くたびに `export.json` へ最新のマップを書いておき、別のプロセスの `export` がそれを読む。最初のテストは、どれも再生が終わってから `export` を呼んでいた。

テストのレビューが、これを差し戻した。再生の終わった後は、`export.json` と終了時に書く `map.*` の中身が一致する。そのため、`export` が誤って `map.md` を読むように変わっても、完了後のテストでは気づけない。

直したテストは、2 回目の差分更新の中で処理を止め、その間に `export` を呼ぶ。止めるのに固定の待ち時間は使わず、Promise を 2 つ使った。1 つは止まった所に着いたことを知らせ、もう 1 つは止まった処理を再開させる。

```ts
let reachedSecond!: () => void;
const secondCallReached = new Promise<void>((resolve) => (reachedSecond = resolve));
let release!: () => void;
const released = new Promise<void>((resolve) => (release = resolve));
const updater = async () => {
  const ops = script[calls++] ?? [];
  if (calls === 2) {
    reachedSecond();
    await released; // 2 回目の更新が終わらない、進行中の状態で止める
  }
  return { ops };
};
const playing = runCli(["play", fixture], { updater, sessionsDir, ... });
await secondCallReached;
// ここで export を呼ぶ。論点は（未決）のままで、「→ 決定」はまだ出ない
release();
await playing;
```

止めている間に見るのは 3 つ。Markdown に `面接は何回か（未決）` があって `→ 決定` が無いこと、JSON の論点の子が空であること、フォルダのファイルが `export.json` と `log.jsonl` の 2 つのまま増えないことだ。`map.md` を読む実装にすると、この時点ではまだファイルが無いので落ちる。

**「途中でも」「完了する前に」という契約は、完了後の状態では区別がつかない。処理を止める口を差し替え口に作り、その状態でテストする**。

## 5. 読み込みの検査を通ることと、ツールで描けることは別

形式を決めたときに Drawnix のソースを読み、ファイルを開くときに確かめられるのは `type` が `"drawnix"`・`elements` が配列・`viewport` がオブジェクトの 3 点だけだと分かっていた。受入条件のテストも、この 3 点と木の形を見る。

しかし、この 3 点は開けるかどうかの検査で、マインドマップとして描けるかは別の話だった。計画の段のエージェントは、描画を担うライブラリ（Plait）のソースまで読んだ。そして、次の形に合わせる必要があると判断した。

- ルートの要素は `type: "mindmap"` で、置く位置の `points` と、枝を伸ばす向きの `layout` を持つ
- 子の要素は `mindmap` ではなく `type: "mind_child"`
- 本文は `data.topic.children[0].text` に入れる

3 点の検査だけを満たすなら、子の型が違っていても、テストは通ってファイルも開ける。描けるかどうかは、実際に drawnix.com で開くまで分からない。この確認は人の手作業として受入条件に残したが、自動でマージされたときにはまだ済んでいなかった（人の作業が閉じた issue に取り残される話は、[回帰評価の記事](./2026-10-01-008-regression-eval-recall.md)の 7 節を参照）。

**ファイルの形式を自前で組むときは、読み込みの検査と描画が要求する形を分けて調べる**。自動テストで確かめられるのは前者だけなので、後者は実物で開く手順として残す。

## 6. 並行の作業が使っている出力の形を変えると、マージで壊れる

再生のコマンド `play` は、終わるとセッションのフォルダのパスを 1 行だけ標準出力に出していた。今回、受入条件に従って、書き出した 3 ファイルのパスを 1 行ずつ出す形に変えた。

```text
変更前: <セッションのフォルダ>
変更後: <セッションのフォルダ>/map.md
        <セッションのフォルダ>/map.json
        <セッションのフォルダ>/map.drawnix
```

エージェントが作業している間に、ブラウザへの配信・ログからの復元・回帰評価の 3 つが先に main に入っていた。どれも、テストで `play` の出力をそのままセッションのフォルダとして使っていた。takt の作業ブランチは古い main から切られていたので、レビューも最終確認も通った。マージの前に main を取り込むと、CLI 本体とそのテストのファイルが衝突した。衝突を解いたうえで、3 か所のテストを「1 行目のパスの親フォルダを使う」形に直した。

```ts
const dir = dirname(out.join("").split("\n")[0]!); // play は書き出したファイルのパスを出す
```

CLI の標準出力は、エージェントが Bash から読む前提の出力なので、テストや別の機能も同じように頼る。並行するチケットのどれかが形を変えると、残りはマージのときに初めて気づく。

**並行して作業させるときは、CLI の標準出力のような「みんなが読む出力」の形を変えるチケットを、先に入れるか単独で回す**。出力を読む処理を 1 つの関数にまとめておけば、直す場所も 1 か所で済む。

## 7. エージェントに渡すのはそのチケットだけなので、別のチケットに書かれた共有の値は見えない

Drawnix の要素には、表示と揃えた種別の色を付ける決まりだった。ところが計画の段のエージェントは、「表示はまだ作られていない」と判断した。作業ブランチの起点の main には表示が無かったからだ。表示は、この作業の途中で main に入っていた。

エージェントが参照できたのは、自分のチケットと過去の記事だけだった。過去の記事から読み取れた「議題 青・論点 黄・課題 赤・案 紫・決定 緑」の 5 色はそのまま使った。しかし TODO の色はどこにも書かれていなかったので、自分で橙を選んだ。TODO を青緑と決めていたのは、表示のチケットの本文だった。

| 種別 | 表示（ブラウザ） | `map.drawnix` |
| --- | --- | --- |
| 議題・論点・課題・案・決定 | 同じ 5 色 | 同じ 5 色 |
| TODO | `#14b8a6`（青緑） | `#f97316`（橙） |

この記事を書いた時点でも、main の 2 つの色の表は別々に定義されていて、TODO の色は食い違ったままだ。エージェントは「表示との一致は、表示を作るときに確かめる」と未確認の項目に書き残していた。しかし、表示のほうが先に入ったので、確かめる場面が来なかった。

**複数のチケットで使う値（色・ラベル・ファイル名）は、どちらかのチケットの本文ではなく、コードの 1 か所に置いて両方から参照させる**。エージェントは自分のチケットの外を読まないので、「別のチケットで決まっている」は伝わらない。
