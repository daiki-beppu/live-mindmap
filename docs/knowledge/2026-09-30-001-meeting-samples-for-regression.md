# 会議 AI の回帰評価用に、公開会議の音声サンプルを 1 時間で揃えた話

live-mindmap（会議の音声から、AI がマインドマップを差分更新し続ける Web アプリ）の開発で、差分更新エンジンの試作と回帰評価に使う「会議の録音と文字起こし」を用意したときの学び。

- 決定の記録: [回帰評価用の会議録音サンプルを用意する](https://github.com/daiki-beppu/live-mindmap/issues/4)
- 前提の調査: [Kanary で準リアルタイムの文字起こしを取れるか](https://github.com/daiki-beppu/live-mindmap/issues/3)

## 1. 自分の会議が無くても、公開会議で評価は始められる

手元に録音が 1 件も無かった。「次の会議を録る」のを待つと日数がかかるので、YouTube で公開されている会議で代用した。

公開会議には次の利点がある。

- **社外秘の問題が起きない**。会議内容を LLM に渡してよいかの確認が不要になる。このプロジェクトでは、社外秘の会議は LLM に渡さないと決めた
- **すぐ手に入る**。検索して、切り出して、文字起こしするまで 1 時間かからない
- **他人も同じ素材で再現できる**。出典の URL と切り出し区間を書いておけば、音声を配らなくても同じサンプルを作り直せる（音声は第三者の著作物なので git には入れない）

欠点は、全員の声が 1 本に混ざったミックス音声なこと。自分の声（マイク）と相手の声（システム音声）を分けて扱う処理は、公開会議では評価できない。そこは自分の会議で後から録る。

## 2. サンプルは「性質が逆の会議」を組み合わせる

1 本だけだと、その会議に合わせてプロンプトを調整してしまう。性質が逆の 2 本を選んだ。

| サンプル | 性質 | 何の試験になるか |
| --- | --- | --- |
| [プロのファシリテーター同士の会議](https://www.youtube.com/watch?v=5qf4nsARKcg)（先頭 60 分） | 収束型。1 つのテーマで論点を整理し、対立意見を扱い、途中で前の論点に戻る | 同じ話題に戻ったときに、新しいノードを増やさず「統合」できるか。解説員の割り込みに「何もしない」を返せるか |
| [おばかアプリブレスト会議 後編](https://www.youtube.com/watch?v=ogtvHpmuYiU)（先頭 60 分） | 発散型。1 人ずつ案を発表し、周りが突っ込む | 案が大量に出ても、マップが破綻しないか |

収束型では統合が、発散型では追加が主な操作になる。両極端を押さえておくと、片方に最適化したときの劣化に気づける。

途中に入る「会議ではない発言」（解説員のコメントや司会の段取り）は雑音ではなく、試験項目として価値がある。実際の会議でも雑談や脱線は必ず起きるからだ。

## 3. タイトルを信じず、数カ所を試し起こししてから選ぶ

「おばかアプリブレスト会議 **前編**」を選んだら、60 分のほぼすべてが技術セッションの発表で、ブレストは 1 秒も無かった。タイトルに「会議」とあっても、中身が会議とは限らない。

全文を文字起こしする前に、**数カ所を 1 分ずつ切り出して試し起こし**すると安く確かめられる。

```sh
for m in 0 10 20 30 45 60 75 90 105; do
  ffmpeg -loglevel error -y -ss $((m*60)) -t 60 -i full.webm -ac 1 probe-$m.wav
  echo "## ${m}min: $(kanary transcribe probe-$m.wav --lang ja | jq -r '[.transcript.segments[].text]|join("")' | cut -c1-160)"
done
```

110 分の後編でも、9 カ所・合計 9 分の試し起こしで「全編が案の発表と突っ込みで、使える」と判断できた。

## 4. yt-dlp は JavaScript ランタイムが無いと 403 になることがある

`uvx yt-dlp` でインストールせずに使えるが、JavaScript ランタイムが無いと YouTube の音声取得が `HTTP Error 403: Forbidden` で失敗することがあった（既定で有効なのは deno だけ）。node があるなら指定すれば通る。

```sh
uvx yt-dlp --js-runtimes node -f bestaudio -o "full.%(ext)s" "https://www.youtube.com/watch?v=<id>"
ffmpeg -i full.webm -t 3600 -ac 1 -c:a aac -b:a 96k sample.m4a   # 先頭 60 分・モノラル
```

## 5. ローカル STT（Kanary）で 60 分を丸ごと文字起こしした結果

Mac のローカル文字起こしアプリ Kanary の `kanary transcribe`（ライブラリに登録しない使い捨ての文字起こし）で、60 分の音声を 1 ファイルのまま処理した。

- **60 分は Pro なしで通った**。制限は「1 ファイル 75 分超は Pro が必要」なので、それより長い会議は先に切り出す
- **segment は粗い**。60 分で 196〜220 segment、1 segment あたり平均約 17 秒。発言単位の細かい時刻が欲しいなら、自前で短く区切って渡す必要がある
- **話者は分かれない**。ミックス音声なので、結果の track はすべて `speaker` になる
- **略語や固有名詞は崩れる**。「OJT」が「OT」「OP」に、人名も別の字になった。差分更新のプロンプトは、文字起こしに誤りがある前提で作る必要がある
- `--lang ja` で言語を固定した（自動判定に任せない）

## 6. 「サンプルを用意する」も、判断の塊だった

作業チケットのつもりで着手したが、実際には人が決めることが 3 つあった。

1. どこから用意するか（実会議を録る / 手元の録画 / 公開会議 / 台本で模擬会議）
2. 社外秘を LLM に渡してよいか
3. どの会議を選ぶか

エージェントは候補を探して並べ、試し起こしで中身を確かめるところまでを担い、選ぶのは人にした。この分担だと、人が関わるのは選択肢を選ぶ 3 回だけで済み、残りの作業は待たずに進んだ。
