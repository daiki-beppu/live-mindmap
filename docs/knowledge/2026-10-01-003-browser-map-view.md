# 会議のマップをブラウザに描く部分を、AI エージェントのワークフローに実装させた話

live-mindmap（会議の音声から、AI がマインドマップを差分更新し続ける Web アプリ）の開発で、マップをブラウザに描く部分を作ったときの学び。サーバーは差分更新が反映されるたびに、マップ全体を WebSocket で送る。ブラウザは受け取ったものを React Flow で描くだけにした。実装は、AI エージェントのワークフロー実行ツール takt に任せた。takt は、計画 → テストを書く → 実装 → 6 観点のレビュー → 指摘の裁定 → 修正 → 再レビュー、という手順でエージェントを順に動かす。途中で API の利用上限に当たって 1 度止まり、再開してから完了した。

- 決定の記録: [ブラウザにマップが表示される](https://github.com/daiki-beppu/live-mindmap/issues/32)、[ADR 0003 ローカルの Node サーバーがパイプラインを持つ](../adr/0003-local-node-server-owns-pipeline.md)
- 用語集: [`CONTEXT.md`](../../CONTEXT.md)（ノードの種別・差分操作・発言・再生の語彙）
- 前の記事: [LLM がマップを差分更新する中核を、テストファーストで本実装した話](./2026-10-01-002-core-module-tdd.md)

前提として、次のことが決まっていた。

- マップは会議をルートとする木。AI は毎回作り直さず、既存のマップに**差分操作**（追加・更新・統合・移動・削除）を当てる
- 描画には React Flow を使い、見た目は Drawnix 風に描き直す。左から右への木で、兄弟は作られた順に上から積み、親は子の範囲の中央に置く。描画ライブラリを比べた試作で、この形に決まっていた
- **再生**は、録音済みの会議の文字起こしを、発言の流れとしてもう一度流すこと。今回の作業で、CLI の再生に「等速」と「待ち時間なし」の 2 つのモードを持たせる

## 1. 表示専用のブラウザには、差分ではなく全体を送り、サーバーは最新の 1 つだけを持つ

差分操作を WebSocket で送り、ブラウザ側でも適用する案は、計画の段階で外した。ブラウザに適用の仕組みを持たせると、取りこぼした差分があったときに、サーバーとマップがずれる。全体を送るなら、ブラウザは届いたものを描き直すだけで済む。

この形だと、つなぎ直しもほぼ何もせずに済む。配信の側は、最後に送ったスナップショット（その時点のマップ全体）を 1 つ持っておく。新しくつないできたクライアントには、それをすぐ送るだけでよい。

```ts
wss.on("connection", (client) => {
  if (latest !== undefined) client.send(latest);
});
// publish: latest を更新し、OPEN のクライアント全員に送る
```

疎通のテストでは、送る → つなぐ → 切る → 切っている間に送る → つなぎ直す、までを同じサーバーで続けて行った。そして、つなぎ直したクライアントに最新の 1 つだけが届くことを確かめた。ブラウザの側は、切れたら 1 秒後につなぎ直し、その間も最後に受け取ったマップを出し続ける。配信のサーバーを止めて立ち上げ直すと、同じ画面が自動でつなぎ直して最新のマップを描いた。

差分更新が失敗した回は送らない。マップが変わっていないので、反映ではないからだ。

**ブラウザが描くだけなら、送るのは全体にする。そうすれば、つなぎ直しは「最新を 1 つ持っておく」だけで済む**。

## 2. 等速の再生は発言の時刻の差だけ待ち、処理の終わりは待たない

前の記事で、待ち時間なしの再生は「1 発言流すたびに、差分更新の呼び出しが終わるのを待つ」ようにした。そうしないと、呼び出し中にたまった発言が 1 回にまとめて渡され、ライブとは別の呼び出し方になる。

等速の再生は逆で、呼び出しの終わりを待ってはいけない。等速の目的は、会議の流れどおりにマップが組み上がる様子をブラウザで見ることだ。ライブでは、話している人は LLM の応答を待たずに次の発言をする。そこで等速では、前の発言との終了時刻の差だけ待ってから次の発言を流し、呼び出しの終わりは待たないようにした。

| 再生のモード | 1 発言ごとに待つもの | 揃えたい相手 |
| --- | --- | --- |
| 待ち時間なし（既定） | 差分更新の呼び出しの終わり | ライブと同じ呼び出しの区切り（回帰評価用） |
| 等速（`--realtime`） | 前の発言との終了時刻の差 | ライブと同じ時間の流れ（見た目の確認用） |

待つ処理は、中核のモジュールに `sleep(ms)` という引数で渡した。中核は Node に依存させない方針なので、`setTimeout` を直接呼ばない。テストでは、記録するだけの `sleep` を渡して、引数が `[9800, 9400, 8800]`（発言の終了時刻の差）になることと、`sleep → push` の順に呼ばれることを確かめた。「呼び出しの終わりを待つ」誤った実装だと、偽物の差分更新が返らないあいだ 3 回目の `sleep` に進めず、テストが落ちる。

**同じ「再生」でも、何に揃えたいかで、待つ対象が変わる。呼び出しの区切りを揃えるなら処理の終わりを、時間の流れを揃えるなら時刻を待つ**。

## 3. 「追加しても上は動かない」は、高さが揃ったテストでは崩れない

描画ライブラリを比べた試作で、次の配置の規則にしていた。

- 兄弟は、作られた順に上から積む
- 親は、子の範囲の上下の中央に置く

この規則なら、追加で動くのは追加位置より下のノードだけになる、と考えていた。実装には、この性質を確かめるテストが 3 本あった。先頭・途中・末尾に子を足し、上のノードの座標が変わらないことを見るものだ。どれも通っていた。

ところが、レビューの段で 2 人のレビュアーが、同じ反例を独立に見つけた。**親が子の並びより高いとき**だ。

```text
親の高さ 200、子 A の高さ 40
  追加前: A.y = 80
  末尾に高さ 40 の子 B を足す
  追加後: A.y = 54   ← 追加位置より上の A が動いた
```

原因は、親の上端がはみ出す分の補正にあった。最初の実装は、子を上端 0 から積み、親が子の範囲より高ければ、はみ出し分 `(親の高さ − 子の範囲の高さ) / 2` だけ部分木全体を下げていた。子が増えると子の範囲が伸び、補正の量が変わるので、既存の子まで動く。

直し方は、補正を後から全体に足すのをやめることだった。最初の子を置く位置を、最初の子の高さだけで先に決める。

```ts
// 親が最初の子より高いと、親の上端が部分木の上にはみ出す。
// 最初の子の開始位置を、最初の子の高さだけで先に決めておく。
let offset = Math.max(0, (h - firstKidHeight) / 2);
```

こうすると、子をいくつ足しても最初の子の位置は変わらない。親は子の範囲の中央に置かれたまま、子が増えるにつれて下がっていく。

テストが見逃した理由は、高さの与え方にあった。性質を確かめる 3 本は、すべてのノードを同じ高さにしていた。高さが揃っていれば、親は子の範囲より高くならない。このアプリでは、会議のタイトルや長い論点のように、親のほうが文字が多く高くなる場面が普通にある。回帰テストは、根が高い場合と、根以外の親が高い場合の 2 本を足した。

**「追加しても上は動かない」のような性質のテストは、大小の関係が逆になる入力（親のほうが大きい、など）を必ず 1 つ混ぜる**。

## 4. 「反映のたびに全体を収める」は、最後の画面では確かめられない

カメラは、反映のたびにマップ全体が画面に収まるようにする。実装は、ノードが変わるたびに React Flow の `fitView` を呼ぶだけだ。

最初の動作確認は、スナップショットをいくつか流し、最後の画面で全ノードが画面内にあることを見ていた。しかし、「最初の 1 回だけ収める」という誤った実装でも、最後の画面が同じになることはある。ワークフローは、この確認を「未完了」と判断し、実装の段に差し戻した。

やり直しでは、本物の配信サーバーを一時スクリプトから起動し、1 → 3 → 8 → 12 ノードと段階的に送った。そして段階ごとに、ブラウザの画面の拡大率と位置、画面内に収まったノードの数を記録した。

| ノード数 | viewport（React Flow の表示位置） | 画面内に収まった数 |
| --- | --- | --- |
| 3 | `translate(66px, 432.3px) scale(1.858)` | 3 / 3 |
| 8 | `translate(66px, 284.2px) scale(1.365)` | 8 / 8 |
| 12 | `translate(66px, 144.9px) scale(1.365)` | 12 / 12 |

反映のたびに viewport が変わっているので、「初回だけ」の実装ではないと言える。

この観測では、最初にルートの `parent: null` を付け忘れて送り、全ノードが原点に重なった。配置の側に「親のないノードもルートとして扱う」処理を足す案もあったが、取らなかった。スナップショットの型ではルートの `parent` は `null` と決まっていて、本物のセッションはそのとおりに出す。型に反する入力を黙って受け入れる分岐は、本物の不具合を隠す。直したのは送るデータの側だった。

**途中の状態に関する振る舞い（反映のたびに〜する）は、最後の状態を見ても確かめられない。段階的に流して、段階ごとに記録する**。

## 5. 127.0.0.1 で待ち受けても、ブラウザで開いた任意のページからつながる

配信のサーバーは、実装の段で `127.0.0.1` だけで待ち受けるようにしていた。決定の記録には「ローカル専用なので」とある。セキュリティのレビュアーは、これを重大度 High で差し戻した。

`127.0.0.1` で待ち受けると、ほかのマシンからはつながらない。しかし、同じマシンのブラウザで開いたページなら、どのサイトのものでも `ws://127.0.0.1:4319` につなげる。WebSocket の接続には、ブラウザの同一オリジンの制限がかからないからだ。再生中に悪意のあるページを開いていると、そのページが会議の議題・決定・TODO をそのまま読み取れる。

ブラウザは、WebSocket の接続時に必ず `Origin` ヘッダーを付ける。そこで、サーバーの側で `Origin` を見るようにした。

```ts
const LOCAL_HOSTNAMES = new Set(["localhost", "127.0.0.1", "[::1]"]);
const isLocalOrigin = (origin: string) =>
  URL.canParse(origin) && LOCAL_HOSTNAMES.has(new URL(origin).hostname);

new WebSocketServer({
  host: "127.0.0.1",
  verifyClient: ({ origin }) => origin === undefined || isLocalOrigin(origin),
});
```

`Origin` のない接続は受け入れる。ブラウザ以外のクライアント（テストや CLI）は `Origin` を付けないし、ブラウザは必ず付けるので、ブラウザ上のページを締め出す目的には影響しない。テストは、許可する 4 通り（`localhost`・`127.0.0.1`・`[::1]` の各ポート付き、`Origin` なし）と、拒否する 3 通りにした。

| 拒否する `Origin` | 確かめたいこと |
| --- | --- |
| `https://evil.example` | 外部のサイト |
| `null` | サンドボックス化された iframe やファイルから開いたページ |
| `http://localhost.evil.example` | 文字列の前方一致で判定してしまう誤り |

3 つ目は、`origin.startsWith("http://localhost")` のような判定を弾くためのものだ。ホスト名を `URL` で取り出し、完全一致で比べているので通らない。ブラウザは開発サーバー（Vite）の `/ws` 経由でつなぐ。そのため、本来の `Origin`（`http://localhost:5173`）がプロキシを通って届く想定でいる。ただし、実際のブラウザでプロキシ越しに確かめるところまでは、まだしていない。

**ローカルのサーバーを「127.0.0.1 で待ち受けているから安全」と考えない。ブラウザから読めるものを配信するなら、`Origin` を完全一致で見る**。

## 6. 実装したエージェントのテストは、実装と同じ思い込みを持つ

1 回目のレビューでは、6 観点（フロントエンド、AI 生成コード、設計、コーディング、セキュリティ、テスト）のレビュアーから 4 件の指摘が出た。同じ原因のものをまとめると、直す問題は 3 つになった。

| 問題 | 見つけた観点 | 実装の側にあった思い込み |
| --- | --- | --- |
| 親が子より高いと、上のノードが動く（3 節） | 設計、コーディング | ノードの高さは揃っている |
| WebSocket が接続元を見ない（5 節） | セキュリティ | 127.0.0.1 ならローカルだけ |
| README の起動例のパスが存在しない | AI 生成コード | コマンドはリポジトリのルートで動く |

3 つ目は、`pnpm --filter <パッケージ> <スクリプト>` がスクリプトをパッケージのフォルダで動かすことを見落としていた。そのため、起動例が `server/server/test/...` という存在しないパスを指していた。

3 つとも、実装と一緒に書かれたテストはすべて通っていた（server 28 件、web 20 件）。テストを書いたのも実装したのもエージェントで、テストは実装と同じ前提の上に立っていた。一方、テストの観点のレビュアーは、1 回目に「指摘なし」を出していた。しかし、裁定の段は 3 節の見逃しをテストの観点の見落としとみなし、回帰テストの追加を修正の条件に含めた。

修正の後、2 回目のレビューでは 6 観点すべてが通した。テストは web 22 件、server 35 件になった。

**エージェントに実装させるときは、実装とテストを書いた側とは別の観点から見るレビューを挟む。テストが全部通ることは、前提が正しいことの証拠にはならない**。

## 7. 回帰テストを古いコードで落とすには、直す前の状態が履歴に残っている必要がある

前の記事では、「赤を経ずに緑になったテストは、実装を 1 か所壊して、落ちることを見てから残す」と書いた。3 節の回帰テストでも、修正の段のエージェントは、直す前のコードで落ちることを確かめようとした。しかし、できなかった。`layout.ts` はまだ一度もコミットされていない新しいファイルで、直す前の版を取り出す先がなかったからだ。比べようとする途中で、ファイルが一時的に空になる事故も起きた。退避しておいた新しい版を書き戻し、テストと型チェックが通ることで元に戻ったことを確かめた。

結局、直す前のコードで落ちることは、手計算（A の y が 80 から 54 に動く）で示すにとどまった。

**修正の前に、レビューを受けた状態を 1 度コミットしておく。そうすれば、回帰テストが古いコードで落ちることを `git stash` や `git checkout` で確かめられる**。

## 8. 段ごとに成果物をファイルに残すワークフローは、利用上限で止まっても続きから再開できる

今回の実行の時間の流れは次のとおり。

| 実行 | 内容 | 所要 |
| --- | --- | --- |
| 1 回目 | 計画 → テスト → 実装 → 実装のやり直し → レビュー（約 13 分） → 裁定 → 修正の計画 → 修正 → 修正の検証 → 2 回目のレビューの途中で利用上限 | 約 43 分 |
| 2・3 回目 | 2 回目のレビューから再開したが、まだ上限が解けておらず即座に停止 | 各 約 20 秒 |
| 4 回目（約 10 分後） | 2 回目のレビュー → 裁定 → 最終確認 → 完了 | 約 7.5 分 |

takt は、各段の成果物（計画・実装の報告・レビュー・裁定）をファイルとして残す。再開のときは、それを新しい実行に引き継いで、止まった段からやり直す。そのため、4 回目は計画や実装をやり直さずに、2 回目のレビューから始められた。2・3 回目の失敗は、上限が解ける前にすぐ再開したためで、成果物は何も失われていない。

**エージェントのワークフローは、段の区切りで成果物をファイルに書き出す形にしておく。利用上限で止まったら、上限が解けるのを待ってから、止まった段から再開する**。
