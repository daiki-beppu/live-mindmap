# LLM が組み立てたマップを、正解の決定・TODO と時刻で突き合わせて採点した話

live-mindmap（会議の音声から、AI がマインドマップを差分更新し続ける Web アプリ）の開発で、プロンプトやモデルを変えたときにマップの出来が良くなったか悪くなったかを比べる**回帰評価**の仕組みを作ったときの学び。作ったのは、録音サンプルを流し直した結果を読んで、ノード数・深さ・種別ごとの数と、人が書いた正解の決定・TODO に対する再現率を、1 ラン 1 行の表で出す CLI のコマンドだ。実装は、AI エージェントのワークフロー実行ツール takt が、計画・テスト作成・実装・4 観点のレビュー・修正までを約 25 分で自動で回した。

- 決定の記録: [回帰評価](https://github.com/daiki-beppu/live-mindmap/issues/44)、[ADR 0003 ローカルの Node サーバーがパイプラインを持つ](../adr/0003-local-node-server-owns-pipeline.md)
- 用語集: [`CONTEXT.md`](../../CONTEXT.md)
- 評価に使う録音サンプルを選んだ話: [会議 AI の回帰評価用に、公開会議の音声サンプルを 1 時間で揃えた話](./2026-09-30-001-meeting-samples-for-regression.md)
- 前の記事: [LLM がマップを差分更新する中核を、テストファーストで本実装した話](./2026-10-01-002-core-module-tdd.md)

前提として、次のものが揃っていた。

- **再生**: 録音済みの会議の文字起こしを、発言の流れとして待ち時間なしで流し直す CLI の `play`。終わるとセッションのフォルダにその時点のマップ（JSON）を書き出す
- マップの**ノード**は議題・論点・案・決定・課題・TODO の 6 種別のどれかで、**根拠**として元になった**発言**（STT が確定させた文字起こしの 1 区切り）を 1 つ以上持つ。発言は会議の中の開始・終了の秒を持つ
- 録音サンプルは、収束型と発散型の公開会議 2 本（各 60 分）。第三者の著作物なので、リポジトリの外に置く

## 1. 正解との照合は、本文ではなく「種別 + 時刻の区間」で行う

再現率を出すには、AI が作ったノードと人が書いた正解を対応付ける規則が要る。候補は 3 つあった。

| 照合の方法 | 採否 | 理由 |
| --- | --- | --- |
| 本文の類似度 | 不採用 | 日本語の言い回しはランごとに変わる。同じ決定でも、ランが変われば別の言葉で書かれる |
| LLM に判定させる | 不採用 | 判定そのものがぶれ、評価のたびに費用がかかる。評価の物差しが評価対象と同じくらい揺れる |
| 同じ種別のノードの根拠の発言が、正解の時刻の区間と重なるか | 採用 | 同じ入力からは必ず同じ結果が出る |

正解のファイルは、種別名をキーにした JSON にした。

```text
{ "決定": [{ text, from, to }], "TODO": [{ text, from, to }] }
```

`from` / `to` は会議の中の秒で、発言の開始・終了と同じ単位にした。変換せずにそのまま比べられる。`text` は人が読み返すための欄で、照合には使わない。判定は「同じ種別のノードの根拠のどれか 1 つが区間と重なれば再現できた」で、端が接するのも重なりとして数える（`r.start <= to && r.end >= from`）。

**採点を毎回同じにしたいなら、言葉ではなく、入力の側にある動かない座標（ここでは時刻）で突き合わせる**。

## 2. 時刻で照合した再現率は「当たりの上限」なので、ノード数と同じ行に並べる

この照合規則には弱点がある。自動レビューでは、4 つの観点のうち 3 つが同じ点を指摘して差し戻した。

- 正解と違う内容の決定でも、同じ時間帯の発言を根拠にしていれば当たりになる
- 根拠の発言 1 つが複数の正解の区間に重なれば、1 つのノードで複数の正解を満たす

後者は、このプロジェクトでは特に起きやすい。録音サンプルの文字起こしは、60 分で 196〜220 発言、1 発言あたり平均約 17 秒と粗い。17 秒のあいだに決まったことが 2 つあれば、どちらの正解も 1 つのノードで当たりになる。

それでも照合規則は変えなかった。内容まで照合するには、結局 1. で捨てた本文の類似度か LLM の判定が要るからだ。代わりに、この再現率を「取りこぼしていないか」を見る指標として扱い、誤りや水増しは同じ行の別の列で見る。

```text
| ラン | 会議 | ノード | 深さ | 議題 | 論点 | 案 | 決定 | 課題 | TODO | 決定の再現率 | TODO の再現率 |
```

何でも決定にしてしまうプロンプトは再現率が上がるが、同じ行の「決定」の数も跳ね上がるので気づける。

**安く決定的に測れる指標は、甘く出る方向を自覚して、それを打ち消す数と同じ行に並べる**。

## 3. 比較は統計値を出さず、1 ラン 1 行の表を標準出力に出すだけにする

「複数回の結果を並べて、ランごとのぶれを見る」という要求には、次の形で応えた。

```sh
node src/cli.ts eval [--truth <正解ファイル>] <セッションのフォルダ>...
```

- 渡した順に 1 ラン 1 行の Markdown の表を出す。行を並べればぶれは見えるので、平均や標準偏差は出さない
- 結果はファイルに書かず、標準出力だけに出す。評価結果には第三者の会議の内容が入りうるので、リポジトリの中に何も書かなければ、誤って git に入れることがない
- モデル名やプロンプトの版をセッションに記録する仕組みも作らない。比べたいランのフォルダを並べて渡せば比較は成り立つ

計算（指標・再現率・表の整形）は Node に依存しない中核のモジュールに純粋関数として置き、ファイルの読み込みは CLI の側に置いた。前の記事で書いた「実行環境に触る出口は中核の外に出す」という分け方に、そのまま乗っている。

1 つだけ、レビューの指摘で直した。会議名は文字起こしのファイル名から、ランの名前はフォルダ名から来るので、`|` や改行が入りうる。そのまま ` | ` で連結すると、指標が隣の列にずれ、1 ラン 1 行も崩れる。セルごとに `\` と `|` をエスケープし、改行を空白 1 つにしてから連結した。テストでは、会議名 `会議|A\B<改行>C`、ランの名前 `run|x\` という意地の悪い名前で流し、各行のセル数が見出しと一致することを確かめている。

**人が後で目で比べる出力は、集計を足すより、1 行 1 件で並べてそのまま貼れる形にする。そして、外から来る名前は表の区切りを壊すものとして扱う**。

## 4. 人が書く入力は、照合に使う欄だけを厳しく検証する

正解は人が手で書くので、形が崩れていても計算が黙って進むと、再現率が気づかないうちに誤る。読み込みの境界で検証し、不正ならファイルのパスを含むエラーで止めるようにした。テストでは次の 8 通りを止めている。

- JSON として読めない / オブジェクトでない
- `決定` か `TODO` のキーが無い / 配列でない
- `from` か `to` が数でない
- `from` が `to` より大きい

一方、`text` は検証せず、文字列でなければ空文字にした。自動レビューは「必須の欄なのに書き忘れを通す」と指摘したが、`text` は照合にも出力にも使わない。書き忘れで止めても人の手間が増えるだけで、再現率の正しさは `from` / `to` の検証で守れている。

**入力の検証の厳しさは、その欄が結果にどう効くかで決める**。結果に効かない欄で止めるのは、正しさではなく手間を増やす。

## 5. 自動レビューの指摘は「元の要求にある契約か」で採否を分ける

takt のワークフローでは、4 つの観点（コーディング・アーキテクチャ・テスト・AI 生成コードにありがちな問題）のレビューが並行に走り、その後で裁定の担当が指摘ごとに直すかどうかを決める。1 回目は 3 観点が差し戻し、指摘は重複を除いて 3 件だった。

| 指摘 | 裁定 | 理由 |
| --- | --- | --- |
| 再現率が内容を照合しない（2. の弱点） | 直さない | 要求は「正解の形を決め、再現率を出す」まで。内容の照合や 1 対 1 の対応は要求にない契約の追加になる |
| 正解の `text` の書き忘れを通す（4.） | 直さない | 照合にも出力にも使わず、観測できる誤った結果がない |
| 表のセルに `|` や改行が入ると崩れる（3.） | 直す | 要求の「1 ラン 1 行で並べて比べる」が実際に破れる |

2 回目のレビューは 4 観点とも承認し、直さなかった 2 件は「要求が変わる、新しい証拠が出る、などの条件を満たせば再び開く」として残った。

レビューの担当は、親切心から要求を広げる方向に指摘を出しがちだ。どれも筋は通っているので、全部直すと、要求にない照合規則や入力制約が積み上がる。**指摘は「元の要求のどの条件が破れるか」を示せたものだけ直し、示せなかったものは既知の限界として記録に残す**。2. の弱点がこの記事に書けているのは、それが捨てられずに記録に残っていたからだ。

## 6. テストを先に別の担当が書くと、計画の細部まで契約になる

ワークフローでは、テストを書く担当と実装する担当が分かれている。テストの担当は計画にあった列の見出し `決定の再現率` / `TODO の再現率` をそのまま期待値にした。実装の担当が見出しを `${種別}の再現率` と組み立てたところ、`TODOの再現率`（空白なし）になり、テストが 3 件落ちた。

実装は、種別ごとに見出しを持つ対応表に直した（テストの側を合わせるのではなく）。対応表にしておくと、正解の種別を増やしたときに型検査で見出しの書き漏れに気づける。

テストを先に書くのは、同じ人がやっても別の担当がやっても、計画の文字列を固定する効果がある。別の担当だと、実装の担当が「このくらい揃っていればいい」と丸めた細部が、そのまま落ちたテストとして返ってくる。**表示の文字列は、組み立てずに表として持つ**。

## 7. 人がやる受け入れ条件は、自動でマージされると閉じた issue の中に取り残される

要求には「サンプル 2 本分の正解（決定・TODO の一覧）を人が作る」という条件があった。エージェントは計画の段階でこれを自分の範囲外と判断し、レビューもマージを止める理由にはしなかった。それ自体は正しい。

ところが、PR の本文に issue を閉じる記述（`Closes #44`）が入っていたので、マージと同時に issue も閉じた。人がやる条件のチェックボックスは未チェックのまま閉じている。この記事を書いた時点でも、サンプルの置き場に正解のファイルはまだない。つまり、指標の表は出せるが、再現率の列はまだ一度も実データで埋まっていない。

**エージェントに渡す issue に人の作業が混ざるなら、人の作業は別の issue に切り出してから渡す**。同じ issue に入れておくと、コードの完了がそのまま issue の完了として扱われる。
