# LLM がマップを差分更新する中核を、テストファーストで本実装した話

live-mindmap（会議の音声から、AI がマインドマップを差分更新し続ける Web アプリ）の開発で、試作から本実装に移る最初の 1 本を、テストファースト（失敗するテストを書いてから、通すだけのコードを書く繰り返し）で作ったときの学び。作ったのは、文字起こしのファイルを流すと Claude がマップを組み立て、CLI でその時点のマップを JSON で取り出せるところまで。音声・画面はまだない。テストは 15 本になり、最後に本物の Claude（Sonnet 5.5）で録音サンプルの一部を流して確かめた。

- 決定の記録: [文字起こしのファイルを流すと、AI がマップを組み立てる](https://github.com/daiki-beppu/live-mindmap/issues/31)、[ADR 0003 ローカルの Node サーバーがパイプラインを持つ](../adr/0003-local-node-server-owns-pipeline.md)
- 用語集: [`CONTEXT.md`](../../CONTEXT.md)（ノードの種別・差分操作・発言・セッションの語彙）
- 前の記事: [会議のマインドマップを会議の後に何の形で取り出すか決めた話](./2026-10-01-001-export-formats.md)

前提として、次のことが決まっていた。

- マップは会議をルートとする木で、AI は毎回作り直さず、既存のマップへの**差分操作**（追加・更新・統合・移動・削除・何もしない）を返す
- **発言**は、STT（音声認識）が確定させた 10〜15 秒程度の文字起こしの 1 区切り。スピーカーで聞くと相手の声が自分のマイクにも入るので、二重に拾った発言には**重複の印**を付け、差分更新に使わない
- 差分更新は、重複の印がない発言が 2 つたまるごとに呼ぶ。同時に呼ぶのは 1 つまでで、呼び出し中にたまった発言は次の 1 回にまとめる
- 中核のモジュールは、WebSocket・CLI・Node の実行環境に依存しない TypeScript で書く（後でアプリに移しやすくするため）

## 1. テストを置く場所は、書く前に 2 か所に絞って合意する

試作には、操作を検証して適用する純粋関数 `applyOps` がすでにあった。純粋関数はテストしやすいので、ここに検証のテストを細かく並べたくなる。しかし、仕様のテスト方針は「入力は発言の流れ、見るのはスナップショット（その時点のマップ全体）とログ」だった。`applyOps` を直接叩くテストは、適用関数の引数の形が変わるたびに壊れる。

そこで、テストを書く前に、置く場所（継ぎ目）を次の 2 つに絞り、人と合意した。

| 継ぎ目 | 入れるもの | 差し替えるもの | 見るもの |
| --- | --- | --- | --- |
| セッション | 発言を 1 つずつ | 差分更新（台本どおりに操作を返す偽物） | スナップショット、ログのイベント |
| CLI | `replay <ファイル>` → `export --format json` | 差分更新、セッションの置き場 | 標準出力の JSON |

検証の規則（決定の親は論点だけ、削除は葉だけ、統合は同じ種別どうし、など）も、すべてセッションの外から確かめた。偽物の差分更新に規則違反の操作を返させ、スナップショットにノードが無いことと、ログに捨てた理由が残ることを見る。結果は、セッションに 14 本、CLI に 1 本になった。

**テストの置き場所は「どこが一番テストしやすいか」ではなく、「仕様が何を観察すると言っているか」で決める**。

## 2. 「N 個ごとに呼ぶ」という規則には、余りの扱いが書かれていない

「2 つたまるごとに呼ぶ」と「呼び出し中にたまった分は次の 1 回にまとめる」を実装すると、仕様に書かれていない場合が出てきた。**呼び出しが終わった時点で、発言が 1 つしかたまっていないとき**だ。すぐ呼べば反映は速いが、1 発言ずつの呼び出しが続いて回数が増える。2 つ目を待てば規則どおりだが、会議の最後の 1 発言が反映されないまま残る。

2 つ目を待つことにした。理由は 3 つある。

- 試作でプロンプトの出来を測ったのは「2 発言ごと」の入力だった。1 発言だけの入力は、まだ評価していない形になる
- ライブでは差が小さい。発言は 1 つ 10〜15 秒、応答は試作の計測で中央値 約 3 秒（今回の 6 発言の確認では 1 回 約 7 秒）なので、呼び出しの最中に発言がたまる場面そのものが少ない
- 呼ぶかどうかが発言の数だけで決まると、録音を流し直したときに同じ呼び出しが再現できる

残った 1 発言は、セッションの終わりに明示的に流す `flush()` で拾う。ライブで話が途切れたときの扱い（一定時間で流すか）は、ライブのセッションを作るときに決める。

**「N 個ごと」「N 秒ごと」の規則を実装するときは、余りと終わりの扱いを先に決める**。

## 3. 待ち時間なしの再生は、1 つ流すたびに呼び出しの終わりを待つ

録音済みの会議の文字起こしを流し直す**再生**は、回帰評価のために待ち時間なしで流したい。素直に全発言を一気にセッションへ入れると、次のことが起きる。

```text
push(u1), push(u2)          → 1 回目の呼び出しが始まる
push(u3) … push(u200)       → 1 回目の最中なので、全部たまる
1 回目が終わる               → 2 回目に 198 発言がまとめて渡される
```

「呼び出し中にたまった分はまとめる」という、ライブでは正しい規則が、流す速さが変わっただけで別物になる。仕様には「待ち時間なしで流しても、ライブと同じ順で同じ呼び出しが起きる」と書かれていた。

再生の側で、1 つ流すたびに呼び出しの終わりを待つようにした。

```ts
for (const u of utterances) {
  session.push(u);
  await session.idle();  // 呼び出し中なら終わるまで待つ
}
await session.flush();
```

こうすると、呼び出しの区切りは応答の速さによらず「2 発言ごと」になり、呼び出しが重ならないライブと同じになる。

**流す速さを変えて再現させたいときは、時刻ではなく処理の終わりで同期する**。

## 4. 実行環境に依存しない中核は、出口を引数で受け取る

中核を Node に依存させないために、ファイルへの書き込みは中核の外に出した。セッションはログのイベントを `log: (event) => void` という引数に渡すだけで、JSONL に追記するのは CLI の側だ。差分更新も `updater: (input) => Promise<{ ops }>` という引数で受け取る。

この形は、そのままテストの差し替え口になった。

- セッションのテストは、`log` に配列への追加を、`updater` に台本を返す関数を渡す
- CLI も `runCli(argv, { updater, sessionsDir, stdout })` という関数として書き出した。テストは子プロセスを立てずに同じプロセスで呼び、一時フォルダと偽物の差分更新を渡す
- 本物の差分更新（Agent SDK を使う）は、`updater` が渡されなかったときだけ `import()` で読み込む。テストでは SDK を読み込まない

ログの差分操作のイベントには、入力の要約（渡した発言の ID、その時点のノード数）・返ってきた操作・捨てた操作とその理由を残す。差分更新が例外を投げたときも `error` を残し、マップは変えずに次の呼び出しへ進む。

**実行環境に触る出口（ログの書き先、外部の呼び出し）を引数にすると、移植性とテストの差し替え口が同時に手に入る**。

## 5. 最初から通ったテストは、一度わざと落として確かめる

テストファーストでは、テストは失敗してから通るのが普通だ。しかし「直前の発言として、処理済みのうち最後の 3 つを渡す」のテストは、書いた時点で通った。前のスライスで、呼び出しの制御を作るついでに実装していたからだ。

最初から通るテストは、何も確かめていない可能性がある。そこで、実装の `RECENT = 3` を一時的に `4` に変えて流し、このテストだけが落ちることを確かめてから戻した。

```text
RECENT = 4 → × 直前の発言として、処理済みのうち最後の 3 つを渡す（1 failed | 13 passed）
RECENT = 3 → 14 passed
```

**赤を経ずに緑になったテストは、実装を 1 か所壊して落ちることを見てから残す**。

## 6. 本物の LLM での確認は、サンプルを数発言に切って 1 回だけ流す

テストは偽物の差分更新で通しているので、本物の Claude とつながっているかは別に確かめる必要がある。60 分の録音サンプルを全部流すと時間も費用もかかるので、`jq` で 6 発言だけ切り出して流した。

```sh
jq '.transcript.segments |= .[10:16]' facilitators-meeting.transcript.json > head.transcript.json
node src/cli.ts replay head.transcript.json
node src/cli.ts export --format json
```

結果は、呼び出し 3 回（2 発言ずつ）、全体で約 22 秒、捨てた操作 0、エラー 0。ログを見ると、1・2 回目でノードを 2 つずつ追加し（議題 3 つと、その下の 1 つ）、3 回目は新しいノードを作らず既存のノードを更新していた。言い換えは根拠を足す更新で表す、という試作のプロンプトの方針どおりに動いている。

Node 26 は `.ts` を型の除去だけで直接実行できるので、CLI はビルドせずに `node src/cli.ts` で動かしている。`tsconfig.json` に `erasableSyntaxOnly`（型の除去だけで動く構文に限る）と `allowImportingTsExtensions` を入れておくと、型チェックと直接実行が食い違わない。

**偽物で振る舞いを固めたら、本物との接続は小さく切ったサンプルで 1 回だけ確かめる**。出来の評価は、テストではなく回帰評価で行う。
