## 「ブランチが古い」で止まる PR を揃える方式を決めて仕様にしたとき、調査どうしの食い違いは前提の違いで、仕様の前提は依存先を読み直して外れが見つかり、形式仕様で「CI が緑」と「マージされた」の隙間に穴が見つかった話

前日の地図（[2026-10-15 の地図のエントリ](./2026-10-15.md#behind-prs-map)、[数えたエントリ](./2026-10-15.md#behind-prs-count)）の最後のチケットとして、方式を決めて ADR にした。続けて仕様を書き、形式仕様で検証し、実装のチケットに分けた。用語をおさらいする。strict は、PR のブランチが main の最新を含んでいないと（BEHIND）、CI が緑でもマージさせない ruleset の設定だ。DIRTY は main と衝突している状態を指す。自動マージの予約は `gh pr merge --auto` のことで、条件がそろうと GitHub がマージする。揃えるは `gh pr update-branch` で、main を PR のブランチにマージして最新にする。そのたびに CI が流れ直す。takt は issue をエージェントに実装させる仕組みで、takt-sequence はそれを順に回し、自分が予約した PR だけを揃えてきたスクリプトだ。決めた方式は、strict は残し、GitHub Actions のワークフローが自作の GitHub App のトークンで、予約済みで BEHIND の PR を予約の古い順に 1 件ずつ揃える、というものだ。

- 決定の記録: チケット [BEHIND の PR を揃える方式を決め、ADR にする](https://github.com/daiki-beppu/live-mindmap/issues/1182)、[ADR 0021](../adr/0021-align-behind-prs-one-at-a-time-with-app-token.md)、仕様 [自動マージを予約した BEHIND の PR を、Actions が 1 件ずつ揃える](https://github.com/daiki-beppu/live-mindmap/issues/1188)、実装の親 [#1190](https://github.com/daiki-beppu/live-mindmap/issues/1190)

### 1. 調査どうしの推奨が食い違ったら、どちらが正しいかより先に、それぞれが何を前提にしていたかを見る

閉じた調査を並べると、起動するイベントで推奨が割れていた。方式を比べた調査は「CI の完了（`workflow_run`）も引き金にする」と書いていた。トークンと起動イベントを調べた調査は「`workflow_run` は要らない」と書いていた。

食い違いの元は、揃え方の前提だった。全部を一斉に揃えるなら、どれかが入るたびに main への push が来るので、push だけで足りる。1 件ずつ揃えるなら、揃えた 1 件の CI が落ちたとき、main への push は来ない。その PR は入らないからだ。次の 10 分おきの schedule まで、待っている PR がすべて止まる。2 本目の調査は一斉に揃える前提で書かれていた。**同じ問いへの答えが割れたら、片方を誤りとみなす前に、その答えが置いていた前提を書き出す。** 前提を決めれば、答えは自動的に決まる。ここでは「1 件ずつ」が先に決まっていたので、`workflow_run` を入れ、ADR にその理由まで書いた。後で読む人が 2 本目の調査を見て外さないようにするためだ。

### 2. 仕様に「今はこう動いている」と書いたら、依存先のコードをその日に読み直す

仕様には、takt-sequence から揃えを外す手順も書いた。最初の版では「takt-sequence は `update-branch` の失敗で衝突を見分けているので、揃えを外すと衝突でも止まらなくなる。だから判定を書き換える」と書いた。チャートのときに読んだコードの記憶で書いていた。

利用者から「dotfiles 側を変えてるが再度確認」と言われて読み直すと、前日に別の PR（レビューを済ませてから予約する変更）が入っていた。揃える分岐より前で `mergeable === "CONFLICTING"` を見て止める判定が、すでにあった。書き換えは要らず、外すのは分岐 1 つで済む。続けて「takt のマージ機能を使うようにしてるはず」とも言われた。確かめると、takt のマージ機能（base と同期し、衝突は AI で解く）が動くのは予約の前だけだった。予約の後の BEHIND は、まだ `update-branch` で揃えていた。予約を境に、前は takt、後はワークフローと担当が分かれるので、ぶつからない。これも仕様に書いた。

**仕様の中で「今のコードはこう動く」と書く文は、仕様のなかで一番古くなりやすい。** 別のリポジトリにあるコードなら、なおさらだ。書く前に、その日の main の該当行を開いて確かめる。

### 3. 「CI が緑」と「マージされた」の間には隙間がある。CI の完了で起動する仕組みは、ちょうどその隙間で動く

仕様の判定の規則 1 は、最初「最新の main を含む予約済みの PR の CI が実行中なら、ほかは揃えずに待つ」だった。これを Quint（状態遷移を書いて、到達しうる状態を機械で調べる言語）で書いて検証にかけると、7 手の反例が出た。

1. PR A と PR B が、どちらも予約済みで BEHIND
2. ワークフローが A を揃え、A の CI が走り始める
3. A の CI が緑になり、`workflow_run` でワークフローが起動する
4. GitHub の自動マージは、まだ A をマージしていない。実行中の CI が無いので、ワークフローは B も揃える
5. A が入ると B はまた BEHIND になり、B の CI は空回りになる

ADR には「揃えた 1 件の CI が終わる（マージされる、または落ちる）まで次を揃えない」と書いていた。規則に写すときに「終わる」を「実行中でない」と読み替えて、緑でマージ待ちの状態を落としていた。しかも 1. で入れた `workflow_run` は、CI が緑になった直後、つまりこの隙間にちょうど起動する。まれな競合ではなく、揃えるたびに起きる。規則を「最新の main を含み、CI が落ちていない（実行中か緑）PR があれば待つ」に直すと、検証が通った。**「完了」を条件にするときは、完了の後に別の主体（ここでは GitHub の自動マージ）が動くまでの状態を、名前を付けて数える。**

検証では、ほかに 2 つ、仕様の書き方の誤りも見つかった。

- GitHub Actions の `concurrency` は、同じ group で待てる run を 1 本しか持たない。新しい run が来ると、待っていた run は取り消される。仕様には「後から来た run は取り消されずに待つ」と書いていたが、正しくない。どの run も今の状態を読み直すので、出来事は落とさない。そう書き直した。
- 衝突したままの PR に作者が push しても、check は走らず `workflow_run` も来ない。新しい head への衝突の知らせは、次の schedule まで遅れる。これも仕様に「わかっている動き」として足した。

### 4. 形式仕様の性質は、判定の定義を使わずに書く。そうしないと、検査が自分自身を確かめるだけになる

3. の反例は、最初は出なかった。モデルでは、判定の「待つ」を `inFlight` という定義で書いていた。不変条件（どの状態でも成り立つべき性質）の「揃えた PR のうち、マージ待ちはたかだか 1 件」も、同じ `inFlight` で書いていた。規則 1 を元に戻すと、性質の側も一緒に「実行中だけを数える」に変わる。だから反例が出なかった。性質の側で「最新の main を含み、DIRTY でなく、CI が落ちていない」を書き直し、判定から切り離した。すると、元の規則で反例が出た。**性質は、仕様の言葉（ADR の「マージされるまで」）から直接書く。実装側の定義を借りない。**

ほかにもはまりどころがあった。

- **最初の反例は、モデルの書き違いだった。** 作者の push で、最新の main を含む PR が新しく衝突できるように書いていた。main が進んでいないのに衝突は起きない。反例が出たら、要件どうしの矛盾か、モデルが現実より自由すぎるかを、まず見分ける。
- **ランダムなシミュレーションは、3. の反例を見つけなかった。** 2 万本のトレースを流しても出なかった。「A の CI が緑になった直後、マージの前にワークフローが動く」という狭い順番が要るからだ。
- **探索の範囲は、性質を試すのに要る最小にする。** Apalache（記号的なモデル検査器）は 7 手でも 10 分で終わらなかった。TLC（状態を 1 つずつ数え上げる検査器）も、PR 3 件では 2,000 万状態を超えて止まらなかった。「1 件ずつ」と「古い順」を試すのに要るのは PR 2 件だけだ。2 件・main は 2 回まで・作者の push は 1 回までに絞ると、反例も passed もすぐ出た。
- **一時ディレクトリに置いたモデルは、日付が変わったときに消えた。** 検証器が run ごとに残していた控えから、通ったモデルを戻した。通ったモデルは、すぐ issue のコメントに残す。

### 5. チケットは、人にしかできない作業と、待ちが要る作業を、ラベルで分けて切り出す

実装は 5 件に分けた。GitHub App の作成は、設定画面での操作なので人のチケットにした。本文に手順のチェックリストを書いた。takt-sequence から揃えを外すチケットも人のチケットにした。変更先が別のリポジトリ（dotfiles）で、しかも「ワークフローが 1 日動いて漏れが無い」のを確かめてから始める必要があるからだ。エージェント向けのラベルは「依存が閉じたら、いつ誰が拾ってもよい」という印なので、「1 日待つ」という条件を表せない。**「始めてよい条件」が依存の閉じ方で表せないチケットは、エージェントに拾わせない。**

## 会議の後にマップを URL で見せる機能の地図を作ったとき、引き継ぎの問いの半分はもう作ってあり、手で出した公開は音声だけ外して発言の文字は出しており、気になった新製品は肝心の仕組みが当てはまらなかった話

ある技術イベントの配信を取り込んで作ったマップを、Discord で参加者に見せたくなった。そこで、書き出した見返し用の HTML（`map.html`）を手で Cloudflare Pages に置いた。期限を過ぎたら 410 を返し、AI のクローラーは拒んだ。録音入りの版（`map-audio.html`）は、登壇者の声を配り直すことになるので出さなかった。これを製品の機能にするかを決めるため、wayfinder で地図を作った。wayfinder は、霧の多い大きな問いを、決めるチケットの集まり（地図）に分けて 1 枚ずつ解く進め方だ。地図を作るセッションでは、行き先を決め、チケットを起票し、調べるチケットだけをサブエージェントに並行で解かせた。

- 決定の記録: 地図 [会議の後にエクスポートを期限つきで公開する（エクスポートの公開）](https://github.com/daiki-beppu/live-mindmap/issues/1206)、調査 [Cloudflare の方式](https://github.com/daiki-beppu/live-mindmap/issues/1207)・[同意と権利の実務](https://github.com/daiki-beppu/live-mindmap/issues/1208)・[Cloudflare OS](https://github.com/daiki-beppu/live-mindmap/issues/1214)、アイデア [live-mindmap を Cloudflare OS のアプリとして載せる](https://github.com/daiki-beppu/live-mindmap/issues/1216)

### 1. 引き継ぎの問いは、起票の前に過去の地図と仕様に当てる。問いの前提が古いことがある

引き継ぎには 3 つの問いがあった。会議の後の共有、会議中のライブ共有、相手の発言を外に出す同意だ。2 つ目には「Cloudflare Tunnel で今の dev サーバーを出すと、操作の API（ポート 4319）も外に出る。読み取り専用の配信口が先に要る」という見立てが付いていた。

起票の前に、同じ主題の過去の地図を検索した。すると、会議中の共有は 6 日前の地図で決め、仕様にし、実装まで済んでいた。**閲覧の共有**と呼んでいる機能で、セッション中の画面を、許した人にだけ見るだけの形で Mac の外へ開く。中身は次のとおりだ。

- `cli share` で quick tunnel を開く
- メール・ドメインで絞るか、誰でもを明示する
- 操作の口とは別のポートに閲覧の口を立て、`/session/*` は断る

引き継ぎが心配していた穴は、もう塞がっていた。

その仕様には「会議の後に見せるときは、エクスポートを渡す」と書かれ、見返しを閲覧の共有で開くことは対象外とされていた。今回の地図は、ちょうどこの境界の先、つまり「渡す」をどうするかを扱えばよいと分かった。行き先がそれだけ小さく、はっきりした。**引き継ぎの文面は、書いた人がその時点で思い出せた範囲の見立てにすぎない。** 地図の行き先を決める前に、過去の地図と仕様の「対象外」の行を読むと、どこから始めればよいかが分かる。

### 2. 用語の「避ける語」は、その機能での理由で避けている。別の機能では、その理由がむしろ正確になることがある

用語集は、閲覧の共有の言い換えとして「公開」を避けていた。理由は「誰にでも開くように読める」からだ。閲覧の共有は、許した人だけに開く機能なので、この理由は正しい。

会議の後に URL で見せる機能の名前を決めるとき、候補は「見返しの共有」「会議後の共有」「エクスポートの公開」だった。選んだのは「**エクスポートの公開**」だ。URL を知る人なら誰でも見られる形になりうるので、「誰にでも開くように読める」はむしろ正確だった。閲覧の共有とは、「生きた画面を開く」か「書き出した物を置く」かで区別できる。後で届いた同意と権利の調査も、この選択を裏づけた。URL を知る人なら誰でも見られる状態は、著作権法では「公衆」への送信に当たる。

ある機能で避けた語を、別の機能でも機械的に避けると、実際の見え方を和らげた名前になる。**語を避けた理由まで読み、その理由が新しい機能にも当てはまるかを確かめる。**

### 3. 「何を外に出すか」は、ファイルの名前ではなく中身で数える。手で出した公開は、音声だけ外して発言の文字は出していた

手で公開したときは、録音入りの `map-audio.html` を外し、`map.html` を出した。声を配り直すのは重いが、マップなら軽い、という判断だった。

地図の最初の質問を作るために書き出しのコードを読むと、`map.html` は見返し用で、マップに加えてセッションのログを埋め込んでいた。手で公開したファイルを数えると、ログの発言の行が 1,100 件入っていた。つまり、登壇者の話の文字起こしは、そのまま外に出ていた。外したのは声だけだった。

同意と権利の調査では、重さは「マップ（要約）＜発言の文字＜音声」の順だった。講演は原稿が無くても著作物で、文字に起こして URL に置けば、複製と公衆送信に当たる。マップは、元の言い回しを残さない限り、事実やアイデアの整理に近い。そこで、地図では「既定はマップだけ、発言の文字と音声は選んだときだけ」と決めた。

**ファイルの名前（「音声つき」かどうか）で重さを判断すると、名前に出ていない中身を見落とす。** 外に出す前に、そのファイルに何が入っているかを数える。

### 4. ある機能で選んだ方針が、似た機能に持ち越せるとは限らない。持ち越せないと分かったら、黙って破らずに決めるチケットにする

閲覧の共有では、「アカウントやドメインを前提にしない」を選んでいた。quick tunnel はアカウント無しで開けるからだ。会議の後の公開でも同じにしたかった。

Cloudflare の調査では、アカウント無しで置ける一時の置き場は 60 分で消え、1 ファイル 5 MiB までだった。数 MB〜25 MB の HTML を数日置く用途には使えない。結論は「利用者の Cloudflare アカウントは要る」で、権限は Workers の Admin 1 つで足りる。置き方は REST API だけで済み、180 MB を超える wrangler は要らない。

この食い違いは、調査を待つ決めるチケット（誰に、どう見せるか）の問いとして、地図を作る時点で書いておいた。**似た機能の方針を前提にすると、調査の結果で静かに破ることになる。** 食い違いうると分かった時点で、それを決める場所を地図に作っておく。

### 5. 知らない新製品は、魅力に感じた仕組みが自分の用途に効くかを調べる。今回は、その仕組みが効かない範囲だった

途中で「Cloudflare OS に載せるのも面白そう」という案が出た。モデルの知識の後に出た製品だったので、推測で話さずに検索した。2026 年 8 月に出た、会社向けのオープンソースの AI ワークスペースで、権限の扱いに特徴がある。エージェントが読んだものを記録し、元のデータを読めない同僚には、その成果物も見せない。会議のマップを社内の読める人にだけ見せる用途に、合いそうに見えた。

範囲は 2 つに分けた。

- 公開先の候補として調べる。行き先の範囲に入るので、調べるチケットにした
- live-mindmap 自体を載せる。配布の形が変わる話なので、地図の対象外にし、アイデアの issue に分けた

ソースを読んだ調査の結論は、公開先には使えない、だった。

- 外からファイルを置く公開の口（API・CLI・MCP）が無い
- 期限を付けられない
- 中のアプリは外と通信できず、HTML をそのまま置けない
- 魅力に感じた権限の仕組みは、Cloudflare OS の接続を通して読んだデータにしか効かない。外から置いた HTML には効かない

**新製品の売りの機能が、自分の置き方にも効くとは限らない。** 発表の言葉ではなく、その機能がどのデータの経路にかかるのかを、ソースで確かめる。

範囲を先に分けておいたので、地図の行き先は動かなかった。大きな案は、アイデアの issue に壁と成り立ちそうな分け方を書いて残した。

## 会議の後にマップを URL で見せる相手を決めたとき、見る人を絞る仕組みは置き場ではなく中身に持たせ、「指定が無ければ止まる」の理由を確かめて止まらない既定にした話

前のエントリで作った地図の、最初の決めるチケットを利用者と対話で解いた。問いは「書き出したマップを Mac の外の置き場に置いたとき、誰に、どう見せるか」だ。調べるチケットで分かっていた事実は 3 つあった。置き場には利用者の Cloudflare アカウントが要る。Workers に静的な HTML を置けば、期限を過ぎたら 410 を返せる。URL を知る人なら誰でも見られる状態は、著作権法の「公衆」への送信に当たる。決めたのは次のことだ。既定では、製品が作る**合言葉**（置いた物を開くための文字列）で HTML を暗号化して置く。URL を知る誰にでも見せるのは、`--anyone` を明示したときだけにする。

- 決定の記録: チケット [エクスポートの公開を、誰に、どう見せるか](https://github.com/daiki-beppu/live-mindmap/issues/1209)、地図 [会議の後にエクスポートを期限つきで公開する](https://github.com/daiki-beppu/live-mindmap/issues/1206)、調査 [エクスポートの公開を Alchemy で置き・消しできるかを調べる](https://github.com/daiki-beppu/live-mindmap/issues/1218)

### 1. 手元を離れた物の見せる相手は、置き場で絞るか、中身で絞るかしかない。中身で絞れば、置き場に前提を足さずに済む

会議中の画面を開く**閲覧の共有**では、メールアドレスで見る人を絞っている。Cloudflare の quick tunnel を開くコマンド（`cloudflared`）に許すメールを渡すと、相手はメールに届く PIN で入れる。アカウントは要らない。認証は、Mac から伸びる tunnel の側が持っている。

書き出した物を置き場に置くと、Mac はもう手を離れている。絞る仕組みを持てる場所は 2 つしかない。

- **置き場で絞る**: Cloudflare Access でメールの PIN を求める。無料枠（Zero Trust Free、50 人まで）で使える。ただし、組織を作るときに支払い情報を入れる必要があり、メールの PIN によるログインも自分で足す必要がある。API トークンにも、Access の権限を足すことになる
- **中身で絞る**: HTML を合言葉で暗号化して置き、ブラウザで合言葉を入れたら復号する（StatiCrypt と同じ方式）。置き場は、ただのファイル置き場のままで済む。権限は Workers の Admin 1 つのままで、置いた中身は Cloudflare からも読めない

使い方の前提を増やさない方を選び、置き場で絞る案は地図の対象外にした。Discord の閉じたチャンネルなら URL と合言葉を一緒に貼ればよく、社内向けも同じ形で足りるからだ。**絞る仕組みを置き場に持たせると、置き場の設定が利用者の宿題になる。** 中身が自分の手元で作る 1 枚のファイルなら、中身の側で絞る方が軽い。

用語集で合言葉の「避ける語」に PIN を入れたのも、この違いを残すためだ。PIN はメールに届く使い捨ての番号で、合言葉は置いた物にずっとついている鍵だ。

### 2. 「指定が無ければ止まる」は、なぜ止まるのかを読む。製品が安全な値を作れるなら、止めずにその値を既定にする

閲覧の共有は、絞る相手も `--anyone` も渡さないと、開かずに理由を示して止まる。最初は、エクスポートの公開も同じにするつもりで考えていた。

止まる理由を読み直すと、閲覧の共有では、許す相手（メールアドレス）を利用者しか決められないからだった。製品には分からない値なので、聞くしかない。合言葉は違う。製品が作れる。そこで、何も指定しなければ製品が合言葉を作って暗号化し、URL と合言葉を出力する形にした。止まらないうえに、うっかり誰にでも見せることもない。**「止まる」も「聞く」も、製品が決められない値があるときの手段だ。** 似た機能の既定を持ち込むときは、その既定が何を理由にしているかまで確かめる。

### 3. 暗号文を誰でも取れる置き方では、合言葉の強さだけが守りになる。だから利用者には選ばせない

利用者が合言葉を決められる `--passphrase` も考えた。しかし、暗号化した HTML は URL を知れば誰でも取れる。取った人は、手元で好きなだけ合言葉を試せる。置き場で回数を制限する仕組みは働かない。

そのため、合言葉は製品が作るものだけにした。長さを十分にとり、鍵の導出には時間のかかる方式（PBKDF2 の回数を多くする）を使う。利用者が決める形をやめた理由はほかにも 2 つある。弱い合言葉を選べてしまうことと、コマンドの引数に渡すとシェルの履歴に残ることだ。

**暗号化で守るなら、相手が何回でも試せるかを先に考える。** 試せる置き方なら、秘密の強さを利用者の判断に任せない。

### 4. リンクのプレビューは、貼った場所の外に中身を出す

Discord は、URL を貼るとそのページを取りに行き、タイトルや画像をプレビューとして表示する。`--anyone` で置いたページのタイトルに会議名が入っていると、URL を開かない人にも、プレビューで会議名が見える。プレビューは転送や引用で、チャンネルの外にも出ていく。

合言葉で置いたときは、暗号化の外にあるのが入力画面だけなので、決まった文しか出ない。`--anyone` のときもこれにそろえて、プレビューには中身を出さないことにした。**「誰に見せるか」を決めるときは、URL を開いた人だけでなく、URL を取りに来るボットに何が見えるかも数える。** 一方で、AI のクローラーを拒む仕組みが Discord のボットまで弾くと、プレビューそのものが出なくなる。この兼ね合いは、既定値を決める別のチケットに回した。

### 5. 推奨に「A か B」と書いた枝は、決まっていない。閉じる前に拾い直す

対話では、質問ごとに推奨を添えて答えてもらった。絞り方の質問には「メールで絞る案は、地図の後で決める欄に置くか、見送る」と、2 つの道を並べた推奨を書いた。利用者は「推奨どおりで」と答えたが、どちらを選んだかは決まっていない。

まとめに入る前に枝を数え直して、この曖昧さに気づいた。改めて「後で決めるか、対象外か」を聞き、対象外に決めた。地図では、この 2 つの扱いがまったく違う。後で決める欄の物は、いずれチケットになる。対象外の物は、行き先を描き直さない限り戻らない。**「推奨どおり」で受けた答えは、推奨そのものが 1 つに決まっているときにしか決定にならない。**

### 6. 対話の途中の思いつきは、その場の問いに答える物か、別の問いかを分ける

途中で利用者から「Alchemy も使えればいい」という一言があった。Alchemy は TypeScript でインフラを書く道具で、この地図より前に、将来サーバー本体を Cloudflare に置くときの道具として決めてあった。

この一言は、「誰に、どう見せるか」の答えを変えない。変わるのは「どう置くか、どう消すか」だ。調査では、REST API を直接叩けば依存なしで置けると分かっていた。そこで、Alchemy で置けるかを別の調べるチケットに切り出した。後片付けを決めるチケットが、その結果を待つように結んだ。**今の問いの答えを変えない思いつきは、その場で決めずに、答えを変える問いの前に置く。**

## 会議の後に URL で見せる物の既定値を決めたとき、「マップだけ」の物はまだ無く、見返しの HTML は画面に出さない発言までデータとして抱えていた話

同じ地図の、2 枚目の決めるチケットを利用者と対話で解いた。問いは、**エクスポートの公開**（書き出したマップを Mac の外に期限つきで置き、URL で見せること）の既定値だ。何を出すか、期限を何日にするか、AI のクローラーを拒むかを決める。決めたことは次のとおり。既定では、**見返し**（会議の後に時刻を動かしてマップの組み上がりを見直す HTML）から字幕を抜いた版を出す。発言の文字と録音は、積み上げ式で足せるようにする。期限は既定 7 日、上限 30 日で、無期限は許さない。AI の拒否は常に付け、外すスイッチは持たない。

- 決定の記録: チケット [エクスポートの公開の既定値（中身・期限・AI の拒否）を決める](https://github.com/daiki-beppu/live-mindmap/issues/1210)、地図 [会議の後にエクスポートを期限つきで公開する](https://github.com/daiki-beppu/live-mindmap/issues/1206)

### 1. 「既定は X だけ」と決めたら、X だけを持つ物が今あるかを確かめる

地図を作ったときに、「出す中身の既定はマップだけ」と合意していた。チケットに入る前に、書き出しのコードを読んだ。セッションの終わりに書くのは、Markdown・JSON・Drawnix（ホワイトボードの形式）・PNG と、見返し用の `map.html` だ。録音があれば `map-audio.html` も書く。**マップだけの HTML は無かった。** `map.html` には字幕が入っているからだ。

「マップだけ」を何で実現するかで、選択肢は 3 つあった。

- 見返しの HTML から字幕を抜いた版。時刻を動かすと、マップの組み上がりが見える
- 最後の時点のマップだけを載せた HTML。時刻は動かせない
- `map.png` をそのまま置く

1 つめを選んだ。見返しの価値が残り、作る HTML の種類も増えないからだ。合意の言葉は短くても、その言葉に合う物があるとは限らない。**既定を決める前に、その既定に当たる物が今あるか、無ければ既存の物から引くか新しく作るかを決める。**

### 2. 画面に出さないことと、ファイルから抜くことは違う。単一ファイルの HTML は、表示しないデータも抱えている

チケットを閉じた後、この開発ログを書くために `map.html` の作り方を読み直した。`map.html` は、セッションのログ（`log.jsonl`）の出来事を丸ごと JSON にして、HTML の中に埋め込んでいた。見返しの画面は、その出来事を再生して組み上がる。つまり、字幕を画面に出さないようにしても、発言の文字は HTML のソースに残る。開発者ツールを開けば読める。

埋め込まれていたのは発言だけではなかった。

- `remark`: 発言の文字
- `screen` の `lines`: 共有画面から読み取った文字
- `start` の会議名: 前のチケットで、URL とプレビューには出さないと決めた物

決定は「字幕を抜いた見返し」の一行で閉じていた。しかし実際に要るのは、埋め込むデータから出来事を選んで抜くことだ。さらに、マップを組み直す処理は `remark` も読んでいる。抜いた列で見返しが組み上がるかも確かめる必要がある。これらはチケットに追記し、仕様で決める材料にした。**「何を出すか」を画面で数えると、データとして運ばれる物を見落とす。** 自己完結の HTML を外に出すときは、表示ではなく、埋め込んだデータで数える。

### 3. 出す中身の選択肢は、重さの順に積み上げる形にすると、意味の無い組み合わせが消える

中身の段は、マップだけ → ＋発言の文字 → ＋録音の積み上げ式にした。録音は、文字なしでは選べない。別々に選べる形と比べた。

調べるチケットで、法的な重さの順は、要約 < 逐語の文字 < 録音だと分かっていた。録音は複製・公衆送信に加えて、声が個人情報になる。積み上げ式にすると、選択肢の並びがそのままリスクの順になる。「録音だけ出して字幕は出さない」のような、使い道が見当たらないうえに重い方だけを出す組み合わせも消える。既存の `map.html` と `map-audio.html` の分け方とも合う。**独立に見える選択肢でも、重さに順があるなら積み上げにする。**

### 4. 上限は、仕組みと用語の定義から決める。無期限は、期限を焼き込む仕組みと「期限つき」という定義の両方を壊す

期限は、既定 7 日、上限 30 日にした。Discord で「この会議のまとめ」を見てもらうには 1 週間あれば足りる。対話では「Fireflies の上限も 30 日」と推奨の根拠に挙げた。しかし、ログを書くときに調査の記録を読み直すと、Fireflies の期限は「24 時間〜30 日」に加えて「無期限」も選べた。期限を数字で区切る中では最長が 30 日、というのが正確で、上限を 30 日で止めている前例ではなかった。決定は変わらないが、根拠の一つは言い過ぎだった。

無期限を許さなかった理由は、使い勝手ではない。置き場は Cloudflare の Worker で、期限の日時を Worker に焼き込み、過ぎたら 410 を返す。無期限にすると、この仕組みの前提が無くなる。用語集でも、エクスポートの公開は「期限つきで置く」と定義してある。延ばしたいときは公開し直してもらう。**ある値を許すかどうかは、仕組みと定義を壊さないかで先に絞り、好みの議論はその内側でする。**

### 5. 外すスイッチは、外したい使い道が無いなら持たない。前の決定で漏れる物が減っていれば、拒否の範囲も狭くできる

AI の拒否（robots.txt の全拒否・`x-robots-tag`・主な AI クローラーの User-Agent への 403）は常に付け、外すスイッチは持たない。会議の中身を AI に読ませたい使い道が思い当たらず、スイッチは誤って外す余地を増やすだけだからだ。

前のエントリで残していた兼ね合いも、ここで解けた。AI の拒否が Discord のボットまで弾くと、リンクのプレビューが出なくなる。ただ、前のチケットで、プレビューには決まった文しか出さないと決めてあった。プレビュー用のボットを通しても中身は漏れないので、拒否する対象を AI のクローラーに絞れた。既定では合言葉で暗号化しているので、クローラーが取れるのは暗号文だけでもある。AI の拒否が実際に効くのは `--anyone` のときだ。**先に「何が見えるか」を減らしておくと、後の「誰を拒むか」は細かく分けずに済む。**

### 6. 推奨を 1 つに絞って出すと、「推奨」の一言が決定になる

前のチケットでは、「A か B」と 2 つの道を並べた推奨に「推奨どおり」と答えてもらい、枝が決まっていなかった。今回は 4 つの質問のどれにも、推奨を 1 つだけ書いた。利用者の答えは「推奨」の一言で、そのまま 4 つの決定になった。**推奨は、受け入れられたらそのまま決定として書ける形で出す。**

## 会議の後に相手の発言を URL で出すときの確認を決めたとき、CLI の出力を読むのはエージェントだと指摘されて、置いた後の注意文から置く前に止める形に変えた話

同じ地図の、3 枚目の決めるチケットを利用者と対話で解いた。問いは、**エクスポートの公開**（書き出したマップを Mac の外に期限つきで置き、URL で見せること）で、相手の発言を外に出すときの同意と権利の扱いを、製品の振る舞いにどう落とすかだ。前のチケットで、出す中身は「マップだけ」（既定）→「＋発言の文字」→「＋録音」の積み上げ式と決めていた。調べるチケットでは、法的な重さは要約 < 逐語の文字 < 録音で、「URL を知る誰でも」見られる状態は著作権法の「公衆」向けに当たると分かっていた（法的な助言ではなく、製品の既定値を決める材料として調べたもの）。決めたことは次のとおり。発言の文字か録音を含む公開は、何も置かずに専用の終了コードで止める。そして、利用者に相手の了解やイベントの規約を確かめさせてから、確認済みを示すフラグを付けて実行し直させる。

- 決定の記録: チケット [相手の発言を外に出すときの同意・権利の扱いを、製品の振る舞いに落とす](https://github.com/daiki-beppu/live-mindmap/issues/1211)、地図 [会議の後にエクスポートを期限つきで公開する](https://github.com/daiki-beppu/live-mindmap/issues/1206)

### 1. 確認の形は、出力を誰が読むかで決まる。読むのがエージェントなら、置いた後の注意文は誰にも届かない

最初の推奨は、確認のフラグを足さない案だった。中身の段を選ぶフラグ（`--transcript` のようなもの）を付けること自体を意思の表明とみなし、公開した後の出力と help に「相手の了解を確かめるのは利用者の責任」と書く。了解を示す別のフラグを要求する案も比べたが、退けた。理由は「エージェントが機械的に付けるだけになり、守るものが増えない」というものだ。CLI は対話の確認（y/N）を一つも持たず、エージェントが叩くことも多い。そこまでは前提に入れていた。

続けて、「注意文は公開が終わった後に出るので、読んだときにはもう置かれている」という問いを出した。利用者の返事は「人が叩く前提で作ってない、それも踏まえてどうするのがいいかな？」だった。

これで推奨がひっくり返った。live-mindmap の CLI は、会議の取り込みを始める・止める・書き出すなどを、利用者がエージェント（Claude Code など）に頼み、エージェントが叩く前提で作ってある。出力を読むのはエージェントで、利用者ではない。公開した後に注意文を出しても、エージェントが読んで終わる。利用者には届かず、届いたとしても置いた後だ。確認を意味のあるものにするには、**置く前に止めて、エージェントに利用者へ聞かせる**しかない。

最初の推奨は「エージェントが叩く」という事実を、「了解のフラグはエージェントが付けるだけ」という否定の理由にだけ使っていた。「では注意文は誰が読むのか」には当てていなかった。**確認や警告を設計するときは、まずその文を最初に読むのは誰かを決める。** 人が読む前提の注意文は、間にエージェントが入ると、届かない文になる。

### 2. 同じ形の問題は、製品の中に前例があることが多い。依存の導入の「止まって、エージェントに聞かせる」にそろえた

止める形を一から考える前に、README を探した。必須の依存（音声認識のモデルなど）が足りないときの振る舞いが、すでにこう書かれていた。

> 開始時に必須の依存が足りないときは、CLI は不足内容と導入コマンドを表示し、終了コード3（exit 3）で止まります。エージェントはこの案内を受けたら利用者に確認し、同意を得てから導入してください。

これは今回と同じ形の問題だ。製品が勝手に進めてはいけないことがあり、決めるのは利用者で、間にエージェントがいる。これに合わせて、次のように決めた。

- 発言の文字か録音を含む公開は、専用の終了コードで止まる。出力はエージェントに向けて書き、何を利用者に聞くかを渡す（閉じた会議なら相手の了解、イベントなら規約と登壇者の許可）
- 了解を得たら、確認済みを示すフラグを付けて実行し直す
- help にも「実行する前に利用者に確かめる」と書く。help を先に読んだエージェントは、最初から聞いてから付けられる
- 聞く中身は段で重くする。録音なら「声は話し手を特定できれば個人情報にもなる」を足す。`--anyone`（合言葉なしで誰でも見られるようにするフラグ）と組み合わせるなら「公衆への送信に当たる」を足す。マップだけなら止めない

1 つめの推奨で退けた「了解を示す別のフラグ」は、こうして戻ってきた。違いは、フラグそのものではなく、**止めたときの出力が、エージェントに次の手を指示していること**だ。フラグ単体なら、エージェントは機械的に付けるだけになる。「止まる → 何を聞くかが渡される → 聞いてから付ける」の流れがあって、初めて確認になる。

### 3. 製品が確かめられないことは、聞きも記録もしない。聞けば手間が、記録すれば偽の証拠が増える

残りの 2 つの枝も、同じ基準で切った。

- **会議の種類（社内・社外・公開のイベント）は聞かない。** 調べた結果では、種類によって効く法や規約が違う。しかし `--event` のように種類を指定させても、それが本当かを製品は確かめられない。確かめられるものは増えず、指定の手間だけが増える。確認の文言に、閉じた会議の場合とイベントの場合の両方を並べることにした
- **同意は記録しない。** 記録するのは、公開した事実（いつ・どの段か・合言葉か `--anyone` か・期限・URL）だけにした。「誰がいつ了解した」と記録すると、製品が同意を取った証拠のように見える。実際には、製品は確かめていない

**製品が持つ情報は、製品が確かめた物だけにする。** 確かめていない値を入力させたり残したりすると、それらしい形をしているぶん、無いより誤解を生む。

### 4. 仕組みで防げないことは、防げないと決定に書いておく

止めて聞かせる形にしても、エージェントが確かめずに最初から確認済みのフラグを付けることは防げない。依存の導入でも同じだ。これは解決のコメントに「防げないこと」として書いた。製品にできるのは、聞く場面を必ず作り、何を聞くかを渡すところまでだ。

書いておくのは、後で仕様や実装を見た人が「これで同意を担保している」と読み違えないためだ。**確認の仕組みは、何を保証し、何を保証しないかを並べて書く。** 保証しない側を書いておかないと、仕組みの強さが実際より大きく伝わる。

### 5. 推奨の前提が崩れたら、崩れた枝だけを出し直す

利用者の指摘を受けて出し直したのは、確認の形の問い 1 つだけだった。会議の種類・記録・`--anyone` との組み合わせの答えは、この形でも変わらない。そこで「この 3 つは変わらない」と書き添え、置いた後の注意文をいつ出すかという問いは「止めるので要らなくなった」と消した。利用者の返事は「推奨」の一言で、すべての枝がそろって閉じた。**前提が変わったときは、全部を聞き直さず、どの枝が影響を受けてどの枝が受けないかを分けて示す。**
