# 会議のマインドマップを会議の後に何の形で取り出すか決めた話

live-mindmap（会議の音声から、AI がマインドマップを差分更新し続ける Web アプリ）の開発で、会議の後にマップを取り出す**エクスポート**の形を決めたときの学び。エクスポートとは、その時点のマップを、人とエージェントが使える形でセッションの外へ書き出すことをいう。取り出すものと形式、根拠の含め方、取り出すきっかけを順に決めた。コードは書かず、候補を並べて 1 つずつ決めた。形式の事実は、サブエージェントに公式ドキュメントとソースを調べさせた。

- 決定の記録: [エクスポート：会議の後に何をどの形式で取り出すか](https://github.com/daiki-beppu/live-mindmap/issues/23)
- 用語集: [`CONTEXT.md`](../../CONTEXT.md)（ノードの種別・根拠・セッションの語彙）
- 前の記事: [AI が組み立てるマップを人が直す機能を詰めきってから、MVP では入れないと決めた話](./2026-09-30-007-defer-human-edits.md)

前提として、次のことが決まっていた。

- マップは会議をルートとする木で、ノードの種別は 議題・論点・案・決定・課題・TODO。論点は `未決` か `決定済み`、案は `検討中` か `却下` の状態を持つ
- 各ノードは**根拠**（ノードの元になった発言への参照）を 1 つ以上持つ。発言は STT が確定させた 10〜15 秒程度の文字起こしの 1 区切りで、開始・終了時刻を持つ
- 状態を持つのはローカルの Node サーバーだけで、ログはセッション（1 つの会議を追う一続きの作業）ごとの JSONL に追記する
- 基本操作（開始・終了・エクスポート・再生）は、AI エージェントがサーバーの CLI から行う。ブラウザは表示専用

## 1. 形式より先に「誰が何に使うか」を決め、出力を役割で分ける

最初の問いは形式ではなく、読み手にした。候補は「人が読む議事録」「エージェントが加工する材料」「両方」の 3 つで、両方を選んだ。基本操作をエージェントが行う前提なので、「議事録を Notion に貼って」「TODO を起票して」とエージェントに頼むのが自然な使い方になる。その場合、エージェントが人向けの Markdown を解釈し直すより、構造化データから組み立てるほうが確実だ。

この答えに、次の一言が付いた。

> 手軽に mindmap のスクショとかもいいかも
> できれば編集可能なマインドマップが理想

これで出力は 4 つになり、それぞれに役割を 1 つずつ割り当てた。

| ファイル | 役割 | 中身 |
| --- | --- | --- |
| `map.md` | 人が読む | 決定・TODO・未決の論点の一覧と、マップの木 |
| `map.json` | エージェントが加工する | 最後のマップのスナップショット |
| `map.drawnix` | 人が開いて直す | Drawnix で編集できるマインドマップ |
| `map.png` | 人が見る | マップ全体の画像 |

4 つとも同じスナップショットから作るので、中身が食い違うことはない。

**エクスポートの形式を選ぶ前に、読み手と使い道を並べ、1 つの出力に 1 つの役割を割り当てる**。

## 2. 同じ事実を複数の出力に書かず、派生は読み手の側で導く

エージェント向けのデータには、3 つの候補があった。

- 何も足さず、エージェントにログ（JSONL）を読ませる
- 最後のマップのスナップショットを JSON で出す
- スナップショットに加えて、TODO 一覧や決定一覧も JSON で出す

2 つ目を選んだ。ログは「起きたことの流れ」なので、最後のマップを知るには差分操作を順に適用し直す必要がある。その適用関数を持たないエージェントに、ログを読ませるのは重い。一方、TODO 一覧や決定一覧はマップの木から導ける。それを JSON に重ねて持つと、同じ事実が 2 か所に書かれることになる。

同じ考えで、`map.md` の冒頭に置く 3 つの一覧（決定・TODO・未決の論点）も、書き出すときに木から導く。論点の `決定済み` という状態も、保存せず「子に決定を持つか」から導く状態なので、出力でもそのまま `→ 決定：…` と子を並べて表した。

**派生できる情報は出力に重ねて持たず、読み手（エージェント、または書き出し処理）の側で導く**。

## 3. 根拠は、読み手ごとに見せる粒度を変える

根拠の発言をどこまで出すかは、読み手によって答えが違った。

- `map.md`: ノードごとに会議の中の時刻だけ付ける（例：`（12:34）`）
- `map.json`: 発言の ID に加えて、本文と時刻も持つ
- `map.drawnix`: 含めない

議事録に発言の本文を抜粋すると長くなるうえ、STT の誤認識がそのまま人の目に触れる。時刻があれば、録音や JSON の本文にたどれる。後で調べたところ、Drawnix の形式にはメモ欄がなかった。しかし根拠は md と json に置き場があるので、編集用のファイルで失っても困らない。

**根拠のような補助情報は、すべての出力に同じ粒度で入れず、置き場を 1 つ確保したうえで読み手ごとに削る**。

## 4. 却下した案は消さず、元の位置に取り消し線で残す

却下した案の扱いには、「含めない」「取り消し線で元の位置に残す」「末尾にまとめる」の 3 つの候補があった。取り消し線を選んだ。何を検討して捨てたかは、議事録として価値がある。元の位置にあれば、どの論点に対する案だったかも分かる。一方、案の `検討中` にはあえて印を付けていない。普通の状態に印を付けると、印だらけの議事録になるからだ。

**状態の表し方は、例外の状態にだけ印を付ける**。

## 5. 「編集できる形式」は、読み込み側の実装を見て選ぶ

編集できる形式は、開くツールで決まる。候補を調べた結果が次の表だ。

| 形式 | 開いて編集できるツール | 種別の色 | メモ（根拠） |
| --- | --- | --- | --- |
| XMind（`.xmind`） | XMind、MindNode | 可（ノードごとの指定は公式で未確認） | 可 |
| Drawnix（`.drawnix` の JSON） | drawnix.com | 可 | 不可 |
| FreeMind / Freeplane（`.mm`） | Freeplane、XMind、MindNode | 可 | 可 |
| Markdown の箇条書き | XMind、MindNode、Drawnix、markmap、Whimsical | 不可 | 不可 |
| Mermaid mindmap | テキストとして直すだけ | ほぼ不可 | 不可 |

Drawnix を選んだ。画面の見た目が Drawnix 風なので、書き出したマップが表示と揃う。Drawnix のファイル形式は公式ドキュメントにはまとまっていなかった。そこで、ソースの読み込み処理を読んだ。確認されるのは次の 3 点だけだった。

- `type` が `"drawnix"` であること
- `elements` が配列であること
- `viewport` がオブジェクトであること

マインドマップは `type:'mindmap'` の要素で、`children` の入れ子で木を表し、色は `fill` / `strokeColor` / `branchColor` で指定できる。こちらのマップも木なので、サーバーでそのまま組める。XMind は色もメモも持てるが、ノードごとの色の付け方を公式で確認できなかったので、必要になったら足すことにした。

**「このツールで開けるか」は、ドキュメントより先に読み込み処理のソースで確かめる**。確認項目が少なければ、自前で組んでも壊れにくい。

## 6. 画像の撮り方は、「いつ撮るか」の決定から逆算する

画像の撮り方には 3 つの候補があった。

| 案 | 長所 | 短所 |
| --- | --- | --- |
| ブラウザ側で html-to-image | 依存が 1 つで最も軽い | ブラウザを開いているときしか撮れない |
| サーバーが Playwright で自分の表示ページを撮る | ブラウザを開いていなくても撮れる | ブラウザ本体で数百 MB の依存 |
| サーバーで SVG を直接組む | 依存がない | 配置計算を二重に持ち、見た目が表示とずれる |

軽さだけなら html-to-image だ（React Flow の公式の画像出力例も、これを使っている）。しかし、その前に「セッションの終了時に自動で書き出す」と決めていた。エージェントに export を呼び忘れさせないためだ。終了時にブラウザが開いている保証はないので、撮れないことがある。そこで Playwright を開発用の依存に入れ、サーバーが自分の表示ページを開いて、全体を収めた状態で撮ることにした。更新を知らせる赤い枠や「変わったこと」の一覧は写さない。この仕組みは、再生（録音済みの会議を流し直す回帰評価）の結果を画像で残すのにもそのまま使える。

なお、html-to-image は、公式の例では版を 1.11.11 に固定している。それより新しい版は画像が正しく出ない不具合があり、この記事を書いた時点では未解決だった。

**手段の軽さで選ぶ前に、先に決めた「いつ・誰が起動するか」と矛盾しないかを見る**。自動で動く処理に、人の画面を前提にする手段は組み合わせない。
