## エコーキャンセルを実機で確かめ、出力先ごとの扱いをその場で決めた話

エコーキャンセルを組み込んだヘルパー（Mac で会議の音を取り、文字にして送る Swift の常駐プログラム）を、MacBook Air の内蔵スピーカーと AirPods Pro で試した。会議の録音を Chrome で流しながら、利用者に決まった 2 文（「来週の金曜日までに見積もりを先方へ送ります」「予算は三百万円で、来月から着手したいと考えています」）を読んでもらい、`自分` のトラック（マイクの音から作る発言の出どころ。会議アプリの音は `相手`）に何が残るかを見た。画面は Cap で録画した。

- 決定の記録: [MVP の実機確認](https://github.com/daiki-beppu/live-mindmap/issues/89)、[Bluetooth にもかける](https://github.com/daiki-beppu/live-mindmap/issues/116)

### 1. 漏れが消えたかと、自分の声が残るかは、同じ回で一緒に見る

| 出力先 | エコーキャンセル | 会議の文言の `自分` への漏れ | 読んだ 2 文 |
| --- | --- | --- | --- |
| 内蔵スピーカー（音量 50） | あり | なし（95 秒の間、`自分` の発言 0 件） | 残った。誤認識 2 か所（「予算は」→「さんは」、「着手」→「拍手」） |
| AirPods Pro | なし | なし | 正確 |
| AirPods Pro | あり | なし | 開始 7 秒からの 1 回目は崩れた。45 秒からの 2 回目は正確 |

前日の調査では、同じ内蔵スピーカー・音量 50 で、エコーキャンセルなしだと会議の文言がほぼ全文 `自分` に出ていた。漏れを消す働きは、実機でもはっきり出た。文字列の重なりで漏れに印を付ける仕組み（重複の印）は、どの回も 1 件も付かなかった。漏れが文字になる前に消えているので、印は保険の役割になった。

一方で、「漏れが無い」だけを見ていたら、AirPods にエコーキャンセルをかけた回の 1 回目が崩れたことには気づかなかった。

**エコーキャンセルの実機確認では、消したい音と残したい音を同じ回に入れる。** 片方だけ見ると、消しすぎも消し残しも見落とす。

### 2. 扱いを決める質問は、実機の前で、選んだ結果をすぐ試せるときにする

確認項目の中に、「Bluetooth スピーカーを判定の対象にするか決める」「USB ヘッドセットの扱いを決める」が残っていた。作りでは、Bluetooth はイヤホンと同じ扱いで、エコーキャンセルも重複の印もかけていなかった。AirPods には正しいが、Bluetooth スピーカーで聞くと漏れが残る。

利用者には、選択肢と、それぞれで何が起きるかを並べて聞いた。利用者は「Bluetooth もかける」「USB は今のまま」を選んだ。変更は判定の 1 行とテストと README だけだったので、takt に回さずにその場で直した。直したヘルパーを開発サーバーが使う場所に一時的に差し替え、AirPods で同じことをもう一度やった。起動のログに `echo cancellation: enabled (… output: bluetooth)` が出て、漏れも出なかった。

途中で AirPods の接続が切れ、出力が内蔵スピーカーに戻ったまま始めてしまった回があった。起動のログの `output: builtInSpeaker` ですぐ気づいて止めた。

**出力先で振る舞いを変える機能は、起動のログに判定結果を出す。** 実機確認で「何として判定されたか」を毎回確かめられ、機器の接続が切れたことにも気づける。

### 3. 確かめられない項目は、何で代わりに確かめたかを書いてチェックする

「イヤホンで聞いたときは印が付かないこと」は、有線のイヤホンが手元に無く、実機では確かめられなかった。変更後、印もエコーキャンセルもかけないのは、本体のヘッドフォン端子につないだ有線のイヤホンだけになっている。AirPods（変更前、かけない扱い）で自分の声が崩れないことは確かめた。有線を見分ける判定は単体テストが受け持つ。この 2 つを注記して、項目をチェックした。

**実機で確かめられない項目は、未確認のまま放置せず、代わりの根拠と確かめていない範囲を書いて閉じる。** 後から読む人が、どこまで信じてよいかを判断できる。

## 開始直後に自分の声が削られる疑いを合成音声で測り、結論の言い過ぎを 2 回直された話

前のエントリの AirPods の回で、開始 7 秒からの読み上げだけが崩れた。これを、AI エージェントのワークフロー実行ツール takt に調べさせた。takt は、計画 → テストを書く → 実装 → 観点別のレビュー → 指摘の裁定 → 修正 → 修正の確認 → 最終判定、という工程を、別々のエージェントに順に受け持たせる。今回は 16 工程で 72 分かかった。

- 決定の記録: [調査の issue](https://github.com/daiki-beppu/live-mindmap/issues/118)、[調査の PR](https://github.com/daiki-beppu/live-mindmap/pull/120)、[直す issue](https://github.com/daiki-beppu/live-mindmap/issues/119)

### 1. 実機で 1 回見えた現象は、合成音声で条件を振って再現してから原因を語る

実機の結果を見たときの見立ては、「AEC3 は開始直後、参照（スピーカーに出す音）とマイクのずれを推定し終わるまで、話している声まで抑えることがある。Bluetooth は遅れが 0.1〜0.3 秒と大きいので、推定に時間がかかる」だった。

takt は、開発者向けの計測の道具に `echo` を足した。会議の音に遅れ（40・200・300 ms）と減衰（−10 dB）をかけた漏れを作り、そこへ読み上げの 2 文を開始 5・30・60 秒に足して、AEC3 に通す。発話の残り方は、出力のうち元の発話と同じ向きの成分のエネルギーを、元の発話と比べた値（dB）で測った。漏れを入れない対照も並べた。

| 条件 | 開始 5 秒 | 30 秒 | 60 秒 |
| --- | --- | --- | --- |
| 漏れ −10 dB（遅れ 40・200・300 ms） | −7.6〜−8.2 dB | −7.2〜−8.1 dB | −7.5〜−8.2 dB |
| 漏れ無し（遅れによらず同じ） | −9.8 dB | −4.95 dB | −4.52 dB |

漏れがある条件では、開始直後でも削られ方は変わらなかった。削られたのは、**漏れが無い**条件の開始直後だった。1〜7 秒の発話は定常より 2.3〜9.5 dB 余計に削られ、10 秒で定常に戻った。結果は遅れによらなかった。

見立ての「遅れの推定」は外れていた。AirPods の回の崩れは、Bluetooth の遅れのせいではなく、「参照は鳴っているのにマイクには漏れていない」という条件のせいだった。内蔵スピーカーの回（漏れあり）の誤認識は、この計測では開始直後の問題として説明できない。

**実機で 1 回見えた現象の原因は、条件を振った再現で確かめるまで仮説として扱う。** 対照（ここでは漏れ無し）を置くと、仮説が想定していなかった条件で現象が出ることがある。

### 2. 判定の基準を先に書くときは、どの条件に当てはめるかまで書く

計画の工程は、計測の前に判定の基準を書いていた。「いずれかの遅れで、開始 5 秒の残り方が、30 秒と 60 秒の両方より 3 dB 以上小さければ『削られる』」。結果を見てから基準を決めないためだ。

それでも、最初の結論は「削られない」になった。調査文書の初稿が、基準を漏れ −10 dB の条件にだけ当てはめ、漏れ無しの対照を基準の外に置いたからだ。漏れ無しの 5 秒は、30 秒より 4.82 dB 小さく、基準を満たしていた。レビューの工程（AI が書きがちな誤りを探す観点）が、文書の前半で開始直後に 5〜9 dB 余計に削られたと書きながら、結論が「削られない」になっている矛盾を指摘して差し戻した。

修正後の文書は、初稿がどこで条件を狭めたかを「判定基準」の節に残している。基準を後から変えたのではなく、当てはめる条件を誤って狭めていた、という書き方にした。

**基準を事前に決めても、当てはめる条件を後から選べば、結論は動かせる。** 基準と一緒に、どの条件に当てはめるかも計測の前に書く。

### 3. 退けた案の理由は、測った範囲を超えて一般化しない

直し方の候補の 1 つは、「開始から N 秒は AEC の出力を使わず、素通しにする（bypass）」だった。3 秒版と 5 秒版を測ると、漏れ無しの 5 秒の発話の残り方は、どちらでも −9.8 dB のまま変わらなかった。漏れがある条件では、漏れを消す量が減った（開始 2 秒で 19.6 dB → 12.2 / 8.2 dB）。それで、この案は退けた。

1 回目の修正は、修正の確認の工程で差し戻された。理由はこうだった。

> 測定した `bypass-3` と `bypass-5` は 5 秒の発話開始時には終了します。…記録済みの数値が示すのは、測定した二つの設定では改善しなかったことまでです。

要約と GitHub のコメントでは、「bypass 方式は 5 秒の削られ方を直さない」と方式全体に広げて書いていた。2 回目の修正で、測った 2 つの設定の結果として書き直した。直す issue には、bypass を候補として残したまま、漏れを消す量とのトレードオフの数字を並べた。

この調査では、takt が途中で issue へのコメントと、直す issue の作成まで行っていた。結論を直すたびに、訂正のコメントが足された。外に出した文章は、リポジトリの文書と違ってその場で書き換わらない。

**退けた案の理由は、測った設定の範囲で書く。** 一般化した理由は、条件を変えれば効く案まで候補から消してしまう。

## 開始直後の削られ方を AEC3 の設定 1 項目で直し、レビュー役の利用上限を工程の途中から越えた話

前のエントリの調査で、漏れの無い条件（参照は鳴っているが、マイクには漏れない。イヤホン相当）では、開始 1〜7 秒の発話が定常より最大 9.5 dB 余計に削られると分かった。これを、AEC3 の設定を変えて直すよう takt に実装させた。受入条件は「漏れ無しの開始 1〜5 秒で、定常（30・60 秒）との差が 3 dB 未満」「漏れ −10 dB の遅れ 3 通り × 5・30・60 秒の 9 セルで、発話の残り方と漏れの低下量が今より悪くならない」の 2 つ。

- 決定の記録: [直す issue](https://github.com/daiki-beppu/live-mindmap/issues/119)、[PR](https://github.com/daiki-beppu/live-mindmap/pull/122)

### 1. 設定で直すときは、候補を 1 項目ずつ、直したい条件と壊したくない条件の両方で測る

AEC3 には、開始直後の振る舞いに関わりそうな設定がいくつもある。takt の実装役は、それぞれを一時的に C の薄い層（Swift から AEC3 を呼ぶための層）へ通し、計測の道具で 1 項目ずつ測った。

| 変えた設定 | 漏れ無しの開始直後 | 漏れ −10 dB の 9 セル |
| --- | --- | --- |
| 初期の遅れの見積もり（`delay.default_delay`） | 直らない（2 秒で 9〜10 dB） | 漏れの低下量が 4〜7 dB 悪化 |
| 初期状態の長さ（`filter.initial_state_seconds`） | 直らない（2 秒で 9 dB） | 漏れの低下量が最大 15 dB 悪化 |
| 慎重な初期段階（`filter.conservative_initial_phase`） | 直らない | 悪化 |
| エコー経路の強さの初期値（`ep_strength.default_gain`）を 0.5〜10 | 直らない | 変わらない |
| 同じ初期値を 0.05 / 0.02 / 0.01 | 直る（最大 2.3 / 1.3 / 1.0 dB） | 変わらない（差 0.00 dB） |

前の調査で直し方の候補に挙げていたのは「初期の遅れの見積もり」と「初期化の設定」だった。前者は効かず、後者のうち効いたのは、候補の文に名前の出ていなかった `ep_strength.default_gain` 1 つだった。名前のとおりなら、AEC3 はエコー経路がどれくらい強いかを最初は既定値（1）と仮定して抑え、学習が進むと実際の値に置き換える。漏れが無いと、最初の仮定の分だけ発話が削られていた、と見ている（AEC3 の中までは確かめていない）。初期値を小さくすると、開始直後の状態にだけ効き、収束した後（5 秒以降）の値は全桁で変わらなかった。

値は 0.01 にした。基準を満たす 0.05・0.02・0.01・0.001・0 のうち、0.05・0.02 より差が小さく、0.001・0 のように下限に張り付かないもの、という理由だ。根拠は各条件 1 回の計測だけだと、文書に書いてある。

探索で層に通した設定のうち、採用しなかったものは、測定後にコードから消した。調査文書には、表の値を再現するには一時的に通し直す必要があると書いた。1 回目のレビューでは、使っていない `#include` が 1 つ残っていることを指摘されて直した。

**設定で直すときは、効いてほしい条件と、変わってほしくない条件を同じ表に並べて、1 項目ずつ測る。** 名前から効きそうに見える設定ほど、変わってほしくない条件を壊していた。

### 2. 受入条件の外で悪くなった数字も、表に残してから判断する

受入条件は「5 秒以降の 9 セルが悪くならない」だった。実装役は、条件の外の開始 1〜3 秒も測って、参考の表に残した。漏れ −10 dB の開始 1 秒では、漏れの低下量が最大 9.2 dB 下がっていた（遅れ 40 ms で 23.7 → 14.5 dB）。発話の残り方は、同じ 1 秒で逆に良くなっていた。2 秒では 1〜2 dB の低下、3 秒からは差が無い。

最初の 1〜2 秒は、会議を始めた直後の数秒にあたる。そこで漏れが少し残っても、重複の印（文字列の重なりで漏れに印を付ける仕組み）が保険として拾う。マージの前にこのトレードオフを確かめて、受け入れた。実会議の字幕にどう出るかは、まだ確かめていない。

**受入条件の外で悪くなった数字は、隠さずに表に残す。** 条件を満たしたかどうかだけでは、マージの判断に要るトレードオフが見えない。

### 3. レビュー役が利用上限で止まったら、止まった工程から再開する

takt は実装までを 27 分で終えた。ところが、観点別のレビューの工程で、レビュー役に割り当てていた Codex（OpenAI のコーディングエージェント）が利用上限に達した。

```
codex usage limit reached — retry after 3:01 AM: You've hit your usage limit.
```

takt は自動で 2 回積み直したが、どちらも十数秒で同じ理由で失敗し、タスクは `failed` になった。

実装をやり直す必要はないので、takt の内部の API で、レビューの工程（`restart:0.4.0.0`）を開始位置にして積み直した。最初は、上限が解ける 3:05 に `takt run` を起動する待ちを仕掛けた。利用者から「Claude の opus にオーバーライドして」と言われたので、レビュー役の割り当て（`~/.takt/runtime.yaml` の 15 か所）を一時的に opus に書き換えて、すぐに再開した。再開後は、レビュー → 裁定 → 修正 → 2 回目のレビュー → 最終判定が 8 分で終わった。書き換えは、元のファイルを取っておいて、終わった直後に戻した。

Codex のセッションの記録には、上限の種類が `limit_id: "premium"`（上位モデル用の枠）と残っていた。takt が使っていたモデル（`gpt-6-sol`）は、Codex の既定の設定のモデル（`gpt-6.1-sol`）と違った。利用者は「ほかのプロジェクトでは問題なく動いている」と言っていて、枠がモデルごとに分かれている可能性がある。ただ、確かめきれていない。

**外部のサービスの上限で工程が止まったら、止まった工程から再開する。** 自動の積み直しは、上限が解ける前に回数を使い切る。割り当てを一時的に変えるときは、元に戻す手順まで決めてから変える。

### 4. API の上限は、同じアカウントで動くほかのセッションと分け合っている

同じころ、GitHub の API が 1 時間の上限（5,000 回）に達したと警告が出た。このセッションが 1 時間に使ったのは、PR の作成・マージ、CI の待ち、takt の中の issue の取得やコメントを合わせて、数百回ほどだった。

調べると、別のプロジェクトのセッションが `gh pr checks --watch --interval 20` を回していた。20 秒ごとに CI の状態を問い合わせ続ける呼び出しで、1 回の問い合わせで API を数回呼ぶ。複数の作業場所で同時に回ると、すぐに上限に届く。

**API の上限は、同じアカウントで並行に動くすべてのエージェントと分け合う。** CI の待ちは、CI にかかる時間（ここでは 3〜5 分）に合わせて、問い合わせの間隔を広げる。
