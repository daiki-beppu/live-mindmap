## 同じ音声認識を使う別のアプリを手本に、字幕の精度を上げる地図を作った話

「Kanary の実装を参考に字幕の精度を上げたい」という一言から、決めることを並べた地図（親 issue と、判断ごとの子 issue）を作った。Kanary は同じ Mac で動く録音・文字起こしのアプリで、ソースは無く、アプリ本体だけが手元にある。字幕は、まだマップに入っていない話をマップの下に重ねて出す表示だ。中身は、音声認識（STT）の途中結果（確定前の暫定の文字列）と、発言（確定した文字起こしの 1 区切り。一度出したら書き換えない）でできている。地図を作る中で、調べるだけで答えが出る調査のチケット 2 件をサブエージェントに解かせた。その結果を見て、チケットを 1 件足し、試作の着手順を入れ替えた。

- 決定の記録: 地図 [Kanary を手本に字幕の精度を上げる](https://github.com/daiki-beppu/live-mindmap/issues/386)、調査 [FoundationModels で語彙の補正をする条件と使い方、Kanary の作り方](https://github.com/daiki-beppu/live-mindmap/issues/389)、[共有画面と過去のセッションから語彙の候補を取り出す手段](https://github.com/daiki-beppu/live-mindmap/issues/391)、[ADR 0002](../adr/0002-local-stt-helper.md)

### 1. 手本が同じエンジンを使っているなら、差はエンジンの設定ではなく、その前後の処理にある

最初の見立ては「Kanary は SpeechAnalyzer（Apple の端末内の音声認識）に語彙を渡して、固有名詞を当てているのだろう」だった。SpeechAnalyzer には、語のヒントを渡す口（`AnalysisContext.contextualStrings`）がある。しかし、以前の比較（ADR 0002）で、Kanary とこちらが直接 SpeechAnalyzer を使った結果の文字の一致率は、60 分の会議 2 本で 98.9% だった。エンジンが同じで、結果もほぼ同じなら、精度の差はエンジンの設定ではなく、前後の処理から来ているはずだ。

ソースが無いので、アプリの中のバイナリが何を import しているかを `dyld_info -imports` で、埋め込まれた文字列を `strings` で見た。この方法では、「使っている API」と同じくらい「使っていない API」もはっきり分かる。Kanary は `contextualStrings` も `DictationTranscriber` も import していなかった。最初の見立ては外れていた。代わりに見つかったのは、STT の外側にある 3 つの処理だ。

- 文字起こしの後に、端末内の LLM（FoundationModels）で語を用語の一覧の表記に置き換える（`KanaryGlossary` / `LiveGlossaryCorrector`）
- 音量（RMS）がしきい値を下回るときだけ、文字起こしに渡す音のゲインを上げる（録音そのものは変えない）
- 無音が続いたときや、途中結果が落ち着いたときに、確定（`finalize`）を促す

こちらのヘルパー（音声を取って STT に流す Swift の常駐プロセス）には、3 つとも無かった。

### 2. 「書き換えない」と決めた記録を直すなら、表示の段ではなく確定する瞬間に入れる

直す段の候補は 2 つあった。STT の段で直して字幕も発言も良くする案と、字幕の表示だけを後から直す案だ。用語集で、発言は「出したら書き換えない」と決まっている。そのため、表示だけを直すと、字幕では正しい表記なのに、マップの根拠（ノードの元になった発言）では崩れたまま、という食い違いが残る。

一方、Kanary 式の補正は STT の後で行う処理なので、「STT の段で直す」とは字面がぶつかる。解いたのは、補正を入れる瞬間をずらす考え方だ。途中結果はそのまま速く出す。補正は、途中結果から発言を作る瞬間にだけかける。途中結果はもともと後で書き換わる前提なので、話しているそばの速さを落とさずに、確定した字幕とマップの根拠を同じ表記に揃えられる。この方針は、用語集の新しい語「語彙」（セッションで話されそうな語の正しい表記の集まり）の定義に、「途中結果は語彙で直さない」と書き込んだ。

### 3. 端末内の小さいモデルには読みの判断をさせず、決定的に絞った候補から選ばせるだけにする

FoundationModels を調べて分かった数字は次のとおりだ。

- 文脈の上限は、手元の macOS 27.0.1 で 8192 トークン、26.x では 4096 トークン。日本語はほぼ 1 文字 1 トークンなので、語彙を全部渡すことはできない
- 1 回の呼び出しは、Apple M4 で 0.4〜0.7 秒。最初の 1 回だけ 1〜3.8 秒かかる
- 4 例を 2 回ずつ試しただけでも、文脈に合わない候補を選ぶ誤りが出た（「サーバー」→「Server Components」、「じぇぶ」→「Jest」）

Kanary の作りは、この弱さに合わせてあった。まず語彙の索引（表記のキーと、読みをローマ字にしたキー）から、区間ごとに最大 50 件の候補をモデルを使わずに引く。モデルには、括弧で括った出現ごとに「候補の番号か、どれでもないか」だけを選ばせる。本文の書き換えはさせない。こちらで組むなら、`DynamicGenerationSchema` の `anyOf`（その出現の候補と NONE）で返り値を縛れば、提示していない語はそもそも返せない。

はまりどころが 1 つあった。ヘルパーは Xcode なしの Command Line Tools でビルドする前提になっている。この環境では、型から返り値の形を作る `@Generable` マクロのプラグインが無く、ビルドが通らない。動的スキーマなら組めて、実際に動いた。

使えない環境の扱いも、ここで決まった。FoundationModels は、M1 以降・macOS 26 以上・Apple Intelligence が有効でないと動かない。ただし、使えるかどうかは `availability` で事前に判定できるので、使えない Mac では補正だけを飛ばしてそのまま動かせる。利用者に「Apple Intelligence を有効にしてください」という前提を課さずに済む。

### 4. 後から直す補正は、崩れ方が大きい語には届かない。語彙の出どころを調べると、手の順番が変わる

語彙をどこから集めるかについて、地図を作る段階では「共有画面の文字と、過去のセッションから」を推奨し、利用者もそれに同意していた。調査で、このうち過去のセッションは外れだと分かった。

- 過去のセッションの発言は、文字起こしの結果そのものだ。崩れる語は崩れたまま残る。合成会議（架空の台本を TTS で読ませた評価用の会議）では、台本に 35 回出る「ソウタ」が文字起こしで正しく出たのは 0 回、「ユズ」は 55 回中 0 回、「大槻」は 11 回中 0 回だった
- 日本語の文から固有名詞を拾う標準の機能（NaturalLanguage の `NLTagger` の人名・地名・組織名）は、日本語の文で 0 件だった。英語の `Tim Cook` などは取れる。候補は「カタカナ 3 字以上」「漢字 3〜12 字」「英字」のような単純な規則で取るしかなく、Kanary の候補抽出も同じ作りだった
- 共有画面には、文字起こしが崩した「港南店」「廃棄率」が正しく映っていた。ただし、規則で取った候補 30 件のうち約 7 割は、一般語などのノイズだった

一度も正しく出ない語は、後からの補正で候補を引けないおそれがある。発言の側に、手がかりになる文字が残っていないからだ。そこで、Kanary が使っていなかった口、つまり語彙を STT に直接渡す `contextualStrings` が効くかを測るチケットを足した。補正の試作は、その結果も待ってから着手する順に入れ替えた。1 で外れた「エンジンに語彙を渡す」案が、手本に無い手として戻ってきた形だ。手本の作りを写すのが目的ではなく、手本が持っていない手も比べる。

### 5. 精度を上げる地図では、測る道具を最初のチケットにする

調べてみると、このリポジトリには文字誤り率（CER）を出す道具が無かった。ADR 0002 にある 98.9% を出したときのスクリプトも残っていなかった。改善したかどうかは「CER と固有名詞の正解率で判断する」と先に決めたので、残りのチケットはすべて、測る道具のチケットの後ろに並んだ。語の抜けを測る、`contextualStrings` を試す、補正を試作する、のどれも、同じ素材で今の値（基準線）と比べないと判断できない。

全体の CER だけを指標にしなかったのは、固有名詞の誤りが数語あっても、全体の CER は 1〜2% しか動かないことが多いからだ。不満の中心は固有名詞にあるので、固有名詞の正解率を別に数える。台本がある合成会議の素材なら、台本を正解として両方とも出せる。

## データを外に出さないことを売りにするため、差分更新をローカルの LLM でも動かす地図を作った話

「データ安全性を売りにするために、Claude だけでなくローカル LLM（WebGPU で動くものを含む）でも動かせるようにしたい」という一言から、決めることを並べた地図（親 issue と、判断ごとの子 issue）を作った。live-mindmap では、AI が会議の発言を読んで、マップに足す・直す・まとめるといった操作だけを返し、既存のマップに当てていく。これを**差分更新**と呼ぶ。今は Claude（Sonnet 5.5）が担っている。地図の目的地は、差分更新を担うモデルを Claude・Mac で動くローカルのサーバー・ブラウザ内の WebGPU から切り替えられるようにし、さらに**ローカルモード**（発言・マップ・共有画面のどれも Mac の外に出ない設定）を約束する仕様だ。調べるだけで答えが出る調査のチケット 3 件はサブエージェントに解かせ、その結果を地図とチケットに戻した。

- 決定の記録: 地図 [差分更新をローカルの LLM（WebGPU を含む）でも動かし、ローカルモードでは何も外に出さない](https://github.com/daiki-beppu/live-mindmap/issues/374)、調査 [ネイティブのローカル LLM で差分操作をスキーマどおりに出せるか](https://github.com/daiki-beppu/live-mindmap/issues/375)、[ブラウザ内の WebGPU で動く LLM の現状](https://github.com/daiki-beppu/live-mindmap/issues/376)、[ローカルで画像を読めるモデルで共有画面を渡せるか](https://github.com/daiki-beppu/live-mindmap/issues/377)、[ADR 0003](../adr/0003-local-node-server-owns-pipeline.md)、[ADR 0006](../adr/0006-send-map-changes-within-a-query.md)

### 1. 「外に出ない」を売りにする前に、今どこから外に出ているかを数える

最初にコードを読んで、外部に送っているものを数えた。音声認識は、もとから Mac の中で動いている（Apple の SpeechAnalyzer）。外に出ているのは、差分更新で Claude に送る発言とマップだけだった。地図 #179 で進めている共有画面の取り込みが入ると、画像もそこに加わる。

出口が 1 か所に絞れていたのは、以前の判断（ADR 0003）で「Claude の呼び出しは 1 つの関数の後ろに閉じる」と決めていたからだ。当時は、サブスクリプションの認証から API キーに差し替えるための備えだった。それが、モデルそのものを差し替える口として使える。ただし、閉じていたのは呼び出しの場所だけで、呼び出し方は Claude の Agent SDK に寄っていた。開いた query を 14 回使い回し、2 回目からはマップの変更だけを送り、5 分のキャッシュに乗せる（ADR 0006）。この作りをローカルでどう再現するかが、モデル選びより大きな山場になる。そのため、口の形を決めるチケットは、実行環境の調査の後ろに置いた。

### 2. 宛先が localhost かを確かめるだけでは、「何も外に出ない」は約束できない

最初の案は、ローカルモードではサーバーが差分更新の宛先を検査し、localhost かブラウザ内でなければセッションの開始を拒む、というものだった。調査の結果、これでは足りないと分かった。

- Ollama のデスクトップアプリは、自動更新を切っていても、1 時間ごとに ollama.com へ更新を確認し、端末 ID を送る
- Ollama で `:cloud` の付いたモデル名を指定すると、要求の宛先は localhost なのに、推論は ollama.com で行われる
- LM Studio は、起動時に更新を確認する（版・OS・IP）。切る手段は文書に無い
- llama.cpp server は推論中に通信せず、`--offline` を付ければ通信をすべて塞げる
- ブラウザ内で推論するなら、モデルとランタイムをローカルの Node サーバーから配り、CSP の `connect-src 'self'` を付ければ、ブラウザが外への通信を拒む

ここから、宛先の検査より前に、約束の範囲を決める必要が出てきた。「会議の中身（発言・マップ・共有画面）が出ない」なのか、「更新の確認も含めて通信が一切ない」なのか。後者なら、完全に約束できるのは llama.cpp と、Node から配る WebGPU だけになる。この判断は、人と決めるチケットに、事実を添えて渡した。売りにする言葉は、実行環境の通信の挙動を調べてから選ぶ。

### 3. ローカルのモデルでも、メッセージを足していく形ならプレフィックスキャッシュで ADR 0006 の作りが残る

Agent SDK は会話の状態を持ってくれるが、OpenAI 互換の API では会話の履歴をこちらで持ち、毎回すべて送ることになる。それでも、llama.cpp server・Ollama・LM Studio・mlx-lm の 4 つは、前回と同じ先頭部分（プレフィックス）の計算を使い回せる。メッセージの配列を書き換えずに末尾へ足していけば、「2 回目からは変更だけ送る」形のまま、前置きの再計算を避けられる。

はまりどころが 3 つある。

- 思考モード（thinking）は切る。オンのままだと、チャットのテンプレートが過去の応答を書き換え、先頭が一致しなくなってキャッシュが外れる
- Ollama は、文脈長の既定が 4,096 トークンで、OpenAI 互換の API からは変えられない。`OLLAMA_CONTEXT_LENGTH` で上げる。5 分使わないとモデルを下ろし、キャッシュも消えるので、`keep_alive: -1` にする
- mlx-lm server には構造化出力（`response_format`）が無い。差分操作は JSON Schema で形を縛っているので、候補から外した。llama.cpp server・Ollama・LM Studio は、スキーマで使っている `anyOf`・`const`・`enum`・`minItems`・`additionalProperties: false` をすべて扱える

### 4. 動機を確かめると、技術の候補が「主役」か「脇役」かが決まる

WebGPU を挙げた理由を聞くと、「何もインストールせずに試せるから」だった。そこで、ネイティブのローカルサーバー（Ollama など）を第 1 の経路にし、WebGPU は試すための入口として第 2 の経路に置いた。

WebGPU には、この作りとぶつかる点がある。ADR 0003 では、パイプライン（差分更新の呼び出し・状態・ログ）は Node のサーバーが持ち、ブラウザは表示だけにしている。WebGPU はブラウザでしか動かないので、推論を入れるとこの前提が変わる。そこで、「推論をどこで動かすか」を独立した判断のチケットに切り出した。調査では、ほかの弱点も見つかった。

- WebLLM に組み込みのモデルは、ほぼすべて文脈長が 4,096 トークンだった。差分更新 1 回の入力（指示文・スキーマ・50 ノードのマップ）は 5,000〜6,000 字あり、収まらないと見積もった
- ブラウザを会議アプリの裏に回したとき、WebGPU の処理が遅くなるかどうかは、一次情報が見つからなかった。表示のタブは、ふつう会議アプリの裏にある

### 5. 検証できない段は、地図に「未検証」と書いておく

推奨のモデルを、Apple Silicon の 16GB と 32GB 以上の 2 段に分けたかった。しかし、手元の検証機は M4・16GB の 1 台だけだ。そこで、実測は 16GB の段だけにし、32GB 以上の段は公開情報から選んで「未検証」と書く、と地図の Notes に残した。後でこの地図を読む人が、数字の重みを取り違えないようにするためだ。

16GB の段の見積もりは厳しかった。GPU が使えるメモリは約 10.7GB で、テキスト用と画像用の 2 つのモデルは同時に載らない。1 つのモデル（第一候補は Qwen3.5-9B の 4bit）で、差分更新と共有画面の読み取りを兼ねることになる。差分更新 1 回は 15〜25 秒、画像 1 枚の読み取りは 5〜10 秒と見積もった。今の「2 発言ごとに、同時に 1 つまで呼ぶ」間隔では詰まりそうだ。この遅さへの対応は、地図を作った時点では「まだチケットにできない論点」に置いていた。見積もりが出て問いが絞れたので、計測の後ろに並ぶチケットにした。

### 6. 置き換える対象の呼び名は、一番遠い候補にも当てはまる語にする

切り替える対象を何と呼ぶかで、「プロバイダ」「接続先」「バックエンド」が候補に挙がった。ブラウザ内の WebGPU を入れると、どこにも接続しないので「接続先」は合わない。「プロバイダ」は Claude や OpenAI のような会社を連想させる。そこで、用語集には「**差分更新のモデル**」（どこで動くかも含めて、差分更新を担う AI を指す）を足した。合わせて「ローカルモード」も足し、避ける語に「オフラインモード」を挙げた。ネットワークを切ることではなく、会議の中身を Mac の外に出さないことだからだ。

## 字幕とマップで「誰の発言か」を分かるようにするため、話者分離の地図を作った話

「字幕、マップのコンテキストに渡すために話者分離をしたい」という一言から、決めることを並べた地図（親 issue と、判断ごとの子 issue）を作った。live-mindmap は音声を 2 本の**トラック**（音声の出どころ）で取っている。`自分` はマイク、`相手` は会議アプリの音で、相手が何人いても 1 本に混ざる。話者分離は、この `相手` の中を声で分けることだ。地図の目的地は、まず匿名のラベル（相手 A / 相手 B）で分け、最後は名前を付けるところまでを含めた実装仕様にした。調べるだけで答えが出る調査のチケット 1 件は、サブエージェントに解かせた。

- 決定の記録: 地図 [話者分離：字幕とマップで誰の発言か分かるようにする](https://github.com/daiki-beppu/live-mindmap/issues/367)、調査 [ローカルで動く話者分離の方式の候補](https://github.com/daiki-beppu/live-mindmap/issues/368)、[ADR 0002](../adr/0002-local-stt-helper.md)

### 1. 用語集が「避ける」と書いていた語を立てるときは、避けていた理由ごと書き換える

用語集の「トラック」の項には、避ける語として「話者（話者の識別はしない）」と書いてあった。トラックを「話者」と呼ぶと、人を区別しているように読めてしまうからだ。今回はその「識別しない」を覆す。避ける語の欄をそのまま残すと、後から読む人やエージェントが「話者は扱わない」と読み取ってしまう。

そこで、この欄を「話者（トラックの中の一人ひとりは話者）」に書き換え、**話者**を新しい語として立てた。定義は「`自分` のトラックは 1 人の話者、`相手` のトラックは声で区別してラベルで呼ぶ」とした。避ける語には、話さない人も含む「参加者」と、音を出す機器の「スピーカー」を挙げた。「スピーカー」は、このプロジェクトではすでにエコーの文脈（スピーカーから漏れた相手の声）で使っている。人の意味で使い始めると、読み違えが起きる。

### 2. 「誰の TODO か」は、言い出した人と担当者の 2 つの軸に分かれる

マップで一番知りたいことを聞くと、「誰の案か、誰の TODO か」だった。案のほうは、言い出した人がそのまま「出した人」になる。TODO は違う。用語集では、TODO はすでに担当者（会話に出た名前）を持っている。「じゃあ B さんお願いします」と A が言えば、言い出したのは A でも、担当者は B だ。

話者分離の精度がどれだけ上がっても、担当者は決まらない。話者は、担当者を推定する手がかりの 1 つにしかならない。そこで用語集の TODO の項に「担当者は、その TODO を言い出した話者とは限らない」と足した。差分更新（AI が発言を読んでマップに足す・直す操作を返すこと）へどう渡すかは、案の出した人と合わせて 1 枚のチケットにした。人を結び付けるノードは案と TODO だけに絞り、論点・課題・決定には持たせない。画面の上で、人の印が増えすぎないようにするためだ。

### 3. 台本から合成した評価素材は、話者の正解をただで持っている

評価に使う会議の音声は、架空の台本を TTS で読ませて作ったものだ。この素材には、台本の行ごとに話者・開始秒・終了秒を書き出した `timeline.tsv` が付いている。話者分離の正解を、人が聞いて付け直す手間がない。人数も 4 人・5 人・6 人・14 人とそろっている。話者の上限が 4 人の方式の弱点（次の節）も、同じ素材で確かめられる。

ただし、TTS の声は人の声より互いに離れていて、分けやすすぎるかもしれない。計測のチケットには、数字がよすぎたら声の近い話者の組で確かめる、と書いておいた。合成した素材の正解は便利だが、合成した素材ならではの甘さも一緒に持ち込む。

### 4. 候補は「同じ道具で測れるか」でも絞る

条件は、端末の中だけで、ほぼリアルタイムに動くこと。調査では、これを満たす方式を一次情報で比べた。Apple の SpeechAnalyzer（いま使っている端末内の音声認識）は、話者の情報を返さない。外の方式を足すことになる。

残った 3 つは、どれも Swift のライブラリ FluidAudio（Apache-2.0）の同じ呼び出し方で動く。

| 方式 | 日本語・会議の公開値 | ラベルの遅れと書き換え | 人数 |
| --- | --- | --- | --- |
| Sortformer v2.1 | CALLHOME 日本語の DER 12.7%（同じ論文の pyannote 3.1 は 28.8%） | 約 1.04 秒で確定。それより新しい部分は仮のラベルで、後から変わる | 4 人まで |
| LS-EEND | 日本語単独の値は無い。AMI（英語の会議）で DER 20.76% | 0.1 秒刻みで確定し、書き換えない | 型によって 10 人まで |
| pyannote の逐次処理 | AMI で DER 38〜56% | 3〜10 秒の塊ごと | 上限なし |

DER は、話者の付け間違い・取りこぼし・余計な検出を合わせた誤りの割合だ。落とした候補もある。sherpa-onnx と SpeakerKit のオープンソース版は、ファイル全体をまとめて処理する方式しか持たない。diart は Python が要る。この 3 つが同じライブラリに収まったので、次の計測は道具 1 つで済む。ヘルパー（音声を取って STT に流す Swift の常駐プロセス）にとっても、依存は 1 つで足りる。別言語のランタイムや C++ のシムは要らない。

### 5. 方式が「ラベルを書き換えるか」は、既存の「書き換えない」決まりとぶつかる

このプロジェクトでは、**発言**（文字起こしの 1 区切り）は一度出したら書き換えない、と決めている。Sortformer は速い代わりに、直近の音声に仮のラベルを付け、後から変える。LS-EEND は一度付けたら変えないが、学習データの大半が合成音声で、60 分を超えて同じ人に同じラベルを保てるかは分かっていない。

どちらを採るかは、精度の数字だけでは決まらない。仮のラベルの間は発言を出すのを待つのか、発言を出してから話者だけ後で足すのか。その組み合わせで決まる。そこで、発言と話者の対応を決めるチケットは、計測の後ろに置いた。調べる前は「話者が替わったら発言を切る」に気持ちが寄っていた。調査で書き換えの有無が見えてから、それが計測の結果しだいだと分かった。

### 6. GitHub の書き込みが 500 を返すときは、作れたかを確かめてから繰り返す

地図の issue を作ろうとすると、`gh issue create` が GraphQL のエラーを返し、REST API で作っても HTTP 500 が続いた。GitHub の状態ページは「All Systems Operational」のままで、読み出しは通った。30 秒おきに繰り返すと、10 回目（約 5 分後）で通った。

繰り返すときは、毎回の前に、同じタイトルの issue がもうできていないかを一覧で確かめた。500 でも裏では作れていることがあり、確かめずに繰り返すと重複する。子のチケット 5 件も、同じ確認つきの繰り返しで作った。

もう 1 つ、はまりどころがあった。依存（blocked by）を張るループで、`for e in "369 368" ...; do set -- $e` と書いた。zsh は bash と違い、引用しない変数を空白で分けない。そのため 4 本とも、存在しない URL への要求になって失敗した。失敗に気づけたのは、張った後に依存の数を読み直したからだ。書き込みの後は、結果を読み直して確かめる。さらに、張れたはずの 1 本が数え直しで 0 のままに見え、張り直すと「Target issue has already been taken」が返ってきた。依存の集計は、書き込みより少し遅れて変わる。

## 差分更新のモデルを差し替える口を、プロンプト・会話・運び手の 3 層に分けた話

[差分更新をローカルの LLM でも動かす地図](#local-llm-map)の判断のチケットを 1 件、人との問答（grilling）で解いた。**差分更新**は、AI が会議の発言を読み、マップへの操作（足す・直す・まとめる）だけを返す処理だ。今は Claude（Sonnet 5.5）が担っている。このチケットで決めたのは、差分更新を担うモデルを Claude・OpenAI 互換の API を持つローカルのサーバー（Ollama や llama.cpp server）・ブラウザ内の WebGPU から切り替えるための口の形だ。質問は 2 回に分けて 9 問出し、利用者はすべて推奨の答えを選んだ。

- 決定の記録: [差分更新のモデルを差し替える口の形](https://github.com/daiki-beppu/live-mindmap/issues/378)、地図 [差分更新をローカルの LLM（WebGPU を含む）でも動かし、ローカルモードでは何も外に出さない](https://github.com/daiki-beppu/live-mindmap/issues/374)、[ADR 0003](../adr/0003-local-node-server-owns-pipeline.md)、[ADR 0006](../adr/0006-send-map-changes-within-a-query.md)

### 1. 口を設計する前に、もうある口を探す。問いは「口を作るか」から「口の下を何層にするか」に変わる

チケットの問いは「差し替える口をどういう形にするか」だった。コードを読むと、口はもうあった。パイプラインの中核（core）は `DiffUpdater` というサービスを通して差分更新を呼ぶ。`update(入力) → 差分操作` だけの形で、Claude のことは知らない。Claude の実装は、起動時に Layer として差し込まれているだけだった。

同じように、Claude 用のファイルの中も、プロンプトを組み立てる関数（指示文、マップのアウトライン、前回からの変更、出力の JSON Schema）は、どれも Agent SDK に依存しない純粋な関数だった。Claude に固有なのは、「開いた query を使い回し、何回目かを数え、失敗したら捨てる」という会話の状態の持ち方だけだ。違いがそこだけだと分かったので、決める問いが「新しい口を作るか」から「既存の口の下に、何を共通の層として置くか」に絞れた。

### 2. 経路ごとの違いを「会話の状態の持ち方」と「要求の運び方」に分けると、新しい経路が運び手 1 つに縮む

口の下は 3 層にした。

1. **プロンプト**: 指示文・組み立て・スキーマ。モデルに依らず、Claude も同じものを使う
2. **messages の会話**: 履歴の配列、前回送ったマップ（2 回目からは変更だけ送るため）、回数で開き直す、失敗したら捨てる
3. **運び手**: OpenAI 互換の要求を 1 つ送り、応答を受け取る

効いたのは、ブラウザ内の推論ライブラリ WebLLM の API が OpenAI と同じ形（`engine.chat.completions.create`）で、`response_format: json_schema` も受けることだった。これで WebGPU は、新しい経路ではなく「互換の要求を、HTTP ではなくブラウザへ運ぶもの」になる。会話の層を作り直さずに済む。残る難しさ（ブラウザで推論すると、パイプラインは Node のサーバーが持ち、ブラウザは表示だけ、という前提が崩れる）は、運び手の中身の問題として、別のチケットに閉じ込められた。

### 3. 実績のある経路を、揃えるためだけに作り直さない。非対称でも、後から揃えられるなら ADR にしない

Claude も Messages API を直接呼ぶ形にすれば、3 つの経路を 1 つの会話の層に揃えられる。しかし、今の Agent SDK の作りは、14 回まで使い回して品質が落ちないことを計測で確かめた経路だ。揃えれば回帰評価をやり直すことになり、ローカルで動かすという目的地には要らない。そこで Claude は Agent SDK のままにした。

この「Claude だけ非対称」な作りは、後から読む人が「なぜ揃えないのか」と思う所だ。それでも ADR は書かなかった。ADR は「取り返しにくい」「文脈が無いと意外」「本当の比較の結果」の 3 つが揃ったときに書く、と決めている。これは 2 つ目と 3 つ目には当てはまるが、後から揃えられるので 1 つ目に当たらない。理由はチケットの解決のコメントに残し、ADR にするかは、もっと重い判断（ブラウザでの推論）とまとめて決めることにした。

### 4. 遅いモデルでは、失敗したときのやり直しが遅れを倍にする。扱いは 1 つに揃え、失敗の元を断つ

今は、差分更新が失敗すると、やり直さずにその回の発言を処理済みにし、マップは変えずに先へ進む。ローカルのモデルは、Claude より構造化出力を崩しやすいかもしれない。そこで「ローカルだけ 1 回やり直す」案も出した。しかし、16GB の M4 で 9B のモデルを動かすと、1 回 15〜25 秒かかる見込みだ。やり直すと、字幕とマップの遅れが倍になる。

結論は、扱いをモデルごとに変えないことにした。その代わり、崩れる原因の側を断つ。ローカルのランタイムは文法でトークンを制約するので、JSON の形は崩れにくい。残る崩れ方は、出力のトークン数の上限で途中で切れることだ。互換の口では `max_tokens` を十分大きく明示する。失敗率は 16GB の機械での計測で数え、多ければ見直す。

### 5. ランタイムごとの癖は、名前で分岐せず、設定に載せるデータで吸収する

ローカルのランタイムには癖がある。思考モードを切るには、要求の body に `chat_template_kwargs: {"enable_thinking": false}` を載せる。Ollama の文脈長（既定 4,096 トークン）とモデルを保つ時間（`keep_alive`）は、OpenAI 互換の API からは変えられず、ランタイム側の環境変数でしか変わらない。

コードで「Ollama ならこうする」と分岐させる案はとらなかった。モデルの設定に「追加で body に載せる項目」を持たせ、body で済む癖はそこで吸収する。ランタイム側でしか変えられないものは、README の導入手順に書く。こうすると、新しいランタイムを足すときは設定例を 1 つ足すだけで済む。モデルの設定の項目は 8 つにした。経路、モデル名、宛先の URL、API キーを読む環境変数の名前、画像を読めるか、開き直す回数（既定 14）、`max_tokens`、追加の body だ。

### 6. 「まだチケットにできない論点」に晴れる条件を書いておくと、晴れた瞬間に迷わずチケットに上げられる

地図には、問いがまだ絞れない論点を置く「まだ決めていないこと」の欄がある。その中の「長い会議と文脈長」には、「差し替えの口の形が決まってから詰める」と条件を書いておいた。このチケットで、開き直す回数をモデルごとの設定にすると決まった。条件が満たされたので、「ローカルのモデルで開き直す回数と文脈長」というチケットに上げ、計測のチケットの後ろにつないだ。晴れる条件を書いておかないと、論点がいつ問いとして立つのかを、毎回読み直して判断することになる。

### 7. 人と決めるチケットを別のセッションに渡すときは、中継せず、人が直接話す場所を用意する

このチケットを閉じた後、「別のワークツリーで次を回す」と頼まれた。以前、人と決めるチケットを並行のワーカーに解かせ、ワーカーの質問をまとめ役のエージェントが中継したことがある。このときは、利用者が途中で止めた。中継を挟むと、問答の往復の質が落ちたからだ。そこで今回は、新しいワークツリーでエージェントを起動し、地図の URL を渡して、画面を利用者に開いた。こちらからは見張りも中継もしない。並行させてよいのは、調べるだけで答えが出るチケットに限る。

## 字幕の精度を測る道具を作り、今の値を出したら、CER より固有名詞の正解率で判断することになった話

字幕の精度を上げる地図（[同じ日の最初のエントリ](#subtitle-accuracy-map)）で、最初に置いた計測のチケットを解いた。発言（確定した文字起こしの 1 区切り）を、合成会議の台本と突き合わせて、文字誤り率（CER）と固有名詞・略語の正解率を出す道具を作り、今の設定での値（基準線）を 5 本の素材で出した。合成会議は、架空の台本を TTS で読ませて作った評価用の会議の音声で、台本と行ごとの時刻がそのまま正解になる。手本の Kanary（同じ Mac で動く、同じ音声認識エンジンを使う文字起こしのアプリ）の文字起こしも同じ道具で採点し、参考値にした。

- 決定の記録: [字幕の精度を測る道具を作り、今の値を出す](https://github.com/daiki-beppu/live-mindmap/issues/390)、道具の PR [#423](https://github.com/daiki-beppu/live-mindmap/pull/423)、地図 [Kanary を手本に字幕の精度を上げる](https://github.com/daiki-beppu/live-mindmap/issues/386)

出た基準線は次のとおり。音声は本番のヘルパー（会議の音を取って文字起こしする Swift の CLI）と同じ設定で、実時間で流した。

| 素材 | 台本の文字数 | CER | 固有名詞の正解率 | Kanary の文字起こし（CER・正解率） |
| --- | --- | --- | --- | --- |
| 略語と製品名の会議（新規、8 分） | 2,500 | 11.0% | 62.7%（79/126） | 10.5%・61.9% |
| 画面共有つきの四半期レビュー | 7,056 | 3.0% | 61.2%（30/49） | 2.6%・63.3% |
| 社内の公開会議 | 18,862 | 4.2% | 67.4%（29/43） | 3.9%・67.4% |
| アイデア出しのブレスト | 22,805 | 4.5% | 0.0%（0/22） | 4.4%・4.5% |
| 劇場の記録集の編集会議 | 45,744 | 5.5% | 1.0%（2/208） | 5.3%・1.4% |

### 1. 測りたい誤りが少ない素材しか無ければ、その誤りを濃く詰めた素材を先に足す

手元の合成会議 4 本は、会議の流れを測るために作ったものだ。固有名詞として数えられたのは参加者の名前と地名くらいで、困りごとの代表例だった「OJT が OT になる」のような略語は 1 つも入っていなかった。そこで、新人の OJT を見直す 8 分の会議の台本を書き足した。OJT・KPI・1on1・SLA のような略語、Notion・Zendesk・Salesforce のような製品名、読みの紛らわしい姓（宍戸・久我）と地名を、39 語・延べ 126 回詰め込んだ。各素材には、正しい表記を 1 行 1 語で並べた `terms.txt` を置いた。

足した素材がいちばん役に立った。英字の製品名はほぼ必ずカタカナで出る（Notion→ノーション が 8 回中 8 回、Zoom→ズーム）。読みの合う別の語にもなる（Zendesk→全デスク、1on1→オンワン、情シス→上質）。一方、OJT は 13 回中 13 回、KPI・CS・AWS・GitHub はすべて正しかった。英字のまま読み上げる略語は強く、カタカナ語として定着した製品名は弱い。この区別は、元の 4 本からは見えなかった。

素材を作る段でも 2 つつまずいた。1 つ目は、合成スクリプトが呼ぶ TTS の API キーが、前払いの残高切れで 402 を返したことだ。同じモデルを別の窓口（Vertex AI）から呼ぶように書き換えた。そこでは音声が WAV ではなく生の PCM（24 kHz・16 bit）で返るので、頭を付けてから変換に渡す。2 つ目は、TTS 自身が読み違える語だ。「柊」は発言で「ひ」「ギ」になっていて、TTS が正しく読んだのかを耳で確かめていない。台本を正解にする素材では、読みの珍しい語は、採点の前に TTS の読みを確かめる必要がある。

### 2. 台本を正解にした CER は表記の揺れで埋まる。数字は両側でそろえ、判断は固有名詞の正解率で行う

最初に採点したとき、食い違いの上位は「一→1」（16 件）、「三→3」「十→10」のような数字の書き方だった。台本は漢数字で書き、音声認識は算用数字で出すからだ。そこで、比べる前に漢数字の並びを算用数字に変える処理（「九十日」→「90日」、「四千八百二十万円」→「48200000円」）を、台本と発言の両方にかけた。両側に同じ変換をかけるので、「一緒」が「1緒」になるような語の中の誤変換も、両側で一致して誤りに数えない。これで新しい素材の CER は 12.4% から 10.5% に下がった。

数字をそろえても、上位は表記の揺れのままだった。社内の公開会議の素材では、「分→わ」（分かる→わかる）が 34 件、「ほう→方」が 30 件、「だ→出」が 25 件ある。音声認識がひらがなと漢字のどちらで書くかの違いで、字幕を読む人には誤りに見えない。固有名詞の崩れ（大槻→大月 の 11 件）は、この中に埋もれる。地図を作ったときに「全体の CER は固有名詞では 1〜2% しか動かない」と見込み、固有名詞の正解率を別に数えると決めていた。実際の値を見て、判断の主役は固有名詞の正解率で、CER は悪くなっていないかの確認に回すと決めた。

### 3. 正解率が 0〜1% と出たら、崩れ方の内訳を見る。読みは合っていて表記だけ違うものが混ざっている

Kanary の文字起こしで既存の 4 本を採点すると、ブレストの素材は 4.5%、劇場の素材は 1.4% と出た。認識がまるで駄目に見えたが、崩れ方の一覧を見ると、劇場の素材の「ユズ」55 回のうち 53 回は「ゆず」だった。台本では登場人物の名前をカタカナで書いているのに、音声認識はひらがなや漢字で書く（ハル→春、ダイスケ→大輔）。読みは合っていて、表記だけが違う。

そこで、正解ではないがひらがなとカタカナの違いだけのものを「かな違い」として別に数えた（劇場の素材で 89 件）。正解には入れない。語彙（セッションで話されそうな語の正しい表記の集まり）で直す目的からすると、「ゆず」も直すべき崩れだからだ。ただ、別に数えておけば、「ゆず」のように候補を引きやすい崩れと、「伊豆」「な」のような崩れを分けて見られる。「春」「大輔」のような漢字の書き分けは、読みを引く辞書が無いと分けられないので、今回は数えていない。

### 4. 手本の文字起こしを同じ道具で採点すると、差がどの段にあるかを数字で確かめられる

地図を作ったときの見立ては、「Kanary と同じエンジンを使っているので、差はエンジンの前後の処理（語彙での補正など）にある」だった。今回、Kanary がファイルから起こした文字起こしと、こちらが実時間で流した結果を同じ道具で採点した。CER の差は 5 本とも 0.1〜0.5 ポイント、固有名詞の正解率の差は 4.5 ポイント以内だった。音声認識の段では、ほぼ互角だ。

見立てが数字で裏づけられたので、Kanary との差を詰める手は、語彙での補正のように音声認識の後に入れる処理から試すことになる。どの手も、この基準線と比べて判断する。

### 5. 長い会議を編集距離で突き合わせるときは、発言がまたがない行の間で区切る

いちばん長い素材は台本が 4.6 万字ある。1 回で編集距離を取ると、表が 20 億マスを超える。そこで約 30 秒ごとに区切って突き合わせた。区切りは台本の行と行の間に置き、どの発言（音声認識の確定結果）の区間もまたがない所だけを選ぶ。発言は、区間の中央が入る区切りに入れる。

時刻で機械的に切ると、1 つの発言が前後の区切りに割れ、片側で脱落、もう片側で挿入として数えられる。音声認識の確定結果は話の切れ目で終わるので、またがない切れ目はすぐ見つかる。固有名詞の採点では、台本の語の位置に並んだ発言の文字列を見る。前後の誤りで並びが 1〜2 文字ずれることがあるので、前後に 2 文字の余裕を持たせて、正しい表記が含まれるかを判定した。

### 6. 実時間で流す計測を並べるなら、1 本を単独で流し直して結果が同じかを確かめる

計測は、本番と同じ条件にするため、音声を 100 ms ずつ実時間のペースで音声認識に渡す。5 本を順に流すと合計で 5 時間を超えるので、4 本を同時に流した。同時に流すと、音声認識の負荷で結果が変わるかもしれない。そこで最後に、新しい素材だけを単独で流し直した。置換・脱落・挿入・正解の件数まで、同時に流したときと一致した。長い素材は並べて流してよい。

道具は、テストとは別の所でも引っかかった。このリポジトリには、「プロセスを走らせる入口は、決まったファイルだけが持つ」ことを確かめるテストがある。入口の一覧に新しいスクリプトを足し忘れ、CI で落ちた。手元では新しいファイルのテストしか回していなかった。入口を足す変更では、全体のテストを手元で一度回す。

## 話者分離の候補を合成会議で測ったら、短い会議で良かった設定が、長い会議の休憩の後で崩れた話

話者分離の地図（[上のエントリ](#speaker-diarization-map)）で調べて絞った 3 つの方式を、合成会議（架空の台本を TTS で読ませた評価用の会議）の音声で実際に動かした。3 つとは、Sortformer、LS-EEND、pyannote の逐次処理で、どれも Swift のライブラリ FluidAudio に入っている。live-mindmap は、音声を 2 本の**トラック**（音声の出どころ）で取る。`自分` はマイク、`相手` は会議アプリの音で、相手が何人いても 1 本に混ざる。話者分離は、この `相手` の中を声で分けることだ。結論は Sortformer の低遅延の設定（`fastV2_1`）にした。ただ、そこに至る途中で、短い会議の数字で選びかけた設定が長い会議で崩れた。

- 決定の記録: 地図 [話者分離：字幕とマップで誰の発言か分かるようにする](https://github.com/daiki-beppu/live-mindmap/issues/367)、計測 [話者分離の候補を合成会議で測る](https://github.com/daiki-beppu/live-mindmap/issues/369)、新しい問い [相手が 5 人以上の会議での話者ラベル](https://github.com/daiki-beppu/live-mindmap/issues/470)

### 1. 製品が実際に分ける音を作ってから測る。全員が入った音声で測ると、方式を 1 段悪く見積もる

合成会議の音声には、参加者全員の声が入っている。製品では、利用者本人の声は `自分` のトラックに別に入るので、話者分離が分けるのは残りの人だけだ。そこで、台本の行ごとの話者と時刻を書いた正解（`timeline.tsv`）を使い、進行役（いちばん多く話す人）の行を無音にした「`相手` だけ」の音声を作って、主にそちらを測った。

違いは大きかった。Sortformer は枠が 4 つの方式で、5 人の会議（全員）では DER（付け間違い・取りこぼし・余計な検出を合わせた誤りの割合）が 33.9% だった。1 人を消した 4 人では 7.1% になる。上限が 4 人の方式は、5 人の会議でも、利用者を除けば上限に収まる。全員入りの音声だけで測っていたら、この方式を捨てていたかもしれない。

会議アプリを通った音の代わりに、`相手` だけの音声を Opus 24 kbps で符号化し直したものも測った。採った設定では、台本の 1 行ごとに話者の多数決が当たった割合（以下、行の正解率）が 97.5% から 90.4% に下がった。

### 2. 長い会議の評価は、会議全体で 1 つの対応を取り、15 分ごとの推移で見る。平均だけでは、途中で枠が入れ替わったことに気づけない

推定した話者は「枠 0」「枠 1」のような番号で返る。採点では、正解の話者と枠を、重なりが最大になる 1 対 1 で対応させる。この対応を会議全体で 1 つだけ取ると、途中で枠が入れ替わったときに、それ以降の正解率が下がって見える。それを 15 分ごとに並べた。

Sortformer には、遅れが同じで、過去の音を長く持つ `balancedV2_1` という設定がある。短い会議ではこちらが少し良く、23 分の会議の DER は低遅延の 15.2% に対して 7.5% だった。そのまま採りかけたが、161 分の会議（`相手` 4 人）で 15 分ごとの行の正解率を並べると、次のようになった。

| 設定 | 0〜75 分 | 75〜90 分 | 90〜161 分 |
| --- | --- | --- | --- |
| 低遅延（`fastV2_1`） | 95〜99% | 91% | 89〜97% |
| balanced（`balancedV2_1`） | 92〜97% | 36% | 25〜46% |

75〜82 分には、台本に 7 分の休憩（無音）がある。balanced は、休憩の後で女性 3 人の枠が入れ替わり、最後まで戻らなかった。低遅延の設定は、同じ休憩の後も同じ人を同じ枠に戻した。会議全体の DER は 36.3% と 12.7% で差は見えるが、それだけでは「全体に少し悪い」のか「途中から壊れた」のかが分からない。長い会議と、途中の長い無音を含む素材を用意していたのが効いた。製品では、会議アプリの音が途切れることも、休憩もある。

### 3. 遅れの公開値は、設定の名前ではなく設定の中身で確かめる

調査の段階では、FluidAudio の文書をもとに「balanced は確定まで約 1.5 秒」と書いていた。測ると、低遅延の設定と同じく、確定まで中央値 0.82 秒、95% で 1.04 秒だった。ライブラリの設定を読むと、どちらも 1 回に処理する長さ 6 フレーム、先読み 7 フレーム（1 フレーム 80 ms）で、違うのは過去を覚えておく長さだけだった。遅れを決めるのは先読みの長さで、名前の「balanced」から連想した遅れは外れていた。

遅れは、音声を実時間と同じく 0.1 秒ずつ渡し、各フレームのラベルが確定した時点で何秒分の音声を渡していたかで測った。計算は実時間の 7〜17 倍の速さなので、計算時間は足しても 0.15 秒以下だ。Sortformer は確定の前に仮のラベルも出す。仮のラベルの多数決が確定で変わった行は 0.6〜2.6% だった。10〜15 秒ある**発言**（文字起こしの確定した 1 区切り）よりずっと前に、話者は決まる。

### 4. 結果が悪すぎるときは、ライブラリ自身の経路で同じ結果が出るかを先に確かめる

LS-EEND は、性別の違う声も含めて、4〜5 人をほぼ 1 つの枠にまとめた（4 人の会議で行の正解率 29%）。調査では「10 人まで扱える受け皿」としていた方式なので、まずこちらの渡し方を疑った。

切り分けは、ライブラリが用意している別の経路で行った。音声ファイルを丸ごと渡す一括処理（`processComplete`）、FluidAudio のコマンドラインの既定の型（`ami`）、処理の刻み（0.1 秒と 0.5 秒）を試し、どれも 1〜2 枠に潰れた。自分で書いた逐次の渡し方を通らない経路でも同じなので、渡し方の誤りではなく、この音声とモデルの相性だと判断した。pyannote の逐次処理（10 秒の塊ごと）も、同性の女性 2 人を 1 つの枠にまとめ、4 人以下でも行の正解率は 44〜66% だった。

### 5. 合成音声が「分けやすすぎる」かは、公開値との比較と、崩れ方が声の近さに沿うかで見る

TTS の声は 1 人に 1 つの声で、話し方もそろっているので、人の声より区別しやすいかもしれない。計測のチケットには「数字がよすぎたら声の近い組で確かめる」と書いていた。確かめたのは 2 点だ。

- 水準: 採った設定の `相手` 4 人の DER 7〜13% は、NVIDIA の公開値（電話会話の CALLHOME で 4 人 12.4%、日本語 12.7%）と同じ水準だった
- 崩れ方: 正解の話者ごとに、どの枠に何割振られたかを出した。4 人以下なら、同性の組（男性 2 人、女性 3 人）も 87〜100% を別の枠に分けた。5 人になると、5 人目は声の近い同性の枠に混ざった

崩れ方が声の近さに沿っているので、合成音声でも区別の難しさは残っていると見た。ただ、台本では話者が順番に話し、重なる場面が無い。割り込みや相づちの重なりは、この素材では測れない。

### 6. Swift Package のバイナリ依存の取得が止まったら、手元に複製して `path:` で参照する

道具の準備でも 3 つはまった。

- FluidAudio の最新のタグ（v0.9.1）は 1 月のもので、Sortformer も LS-EEND も入っていなかった。`main` のコミットを固定して使った
- `swift build` が CPU 0% のまま進まなくなった。FluidAudio は、テキスト処理のバイナリ（約 87 MB の xcframework の zip）を依存に持つ。同じ URL を `curl` で落とすと数秒で取れ、チェックサムも一致した。止まっていたのは SwiftPM 側だ。手前で走らせた `swift package resolve` が止まったままロックを握っていたこともあり、止めて再実行しても同じだった。FluidAudio を手元に複製し、`Package.swift` と `Package@swift-6.2.swift` の `binaryTarget` を、`curl` で落として展開したフォルダの `path:` に書き換えて、`.package(path:)` で参照したら通った。複製したチェックアウトは読み取り専用なので、先に `chmod -R u+w` が要る
- zsh で `for p in "screen 大河内" ...; do set -- $p` と書き、引数が分かれずに失敗した。zsh は引用しない変数を空白で分けない。同じ日の地図づくりでも同じ間違いをしていた。`m=${p%%:*}` のように 1 語にまとめて区切る書き方に変えた

## 語の抜けを測りに行ったら、抜けは小さく、本番の発言で同じ本文が二重に出ていた話

字幕の精度を上げる地図（[同じ日の最初のエントリ](#subtitle-accuracy-map)）で、語の抜けを測るチケットを解いた。語の抜けは、発言の出だし・言い終わり・区切りの境目で語が落ちることだ。どこで・どれだけ落ちているかを数えてから、手を選ぶつもりだった。候補の手は 3 つあった。小さい音のときだけ文字起こしに渡す音を上げるゲイン（手本の Kanary が持つ）、エコーキャンセル（AEC）の自動音量調整（AGC）とノイズ抑制、確定を促す処理だ。測った道具と素材は、[基準線を出したエントリ](#subtitle-accuracy-baseline)のものを使った。結論は「抜けは小さく、どの手も採らない」になった。その代わりに、本番の発言で同じ本文が二重に出る不具合が見つかった。抜けよりはるかに大きい。

- 決定の記録: [語の抜けがどこで・どれだけ起きているかを測る](https://github.com/daiki-beppu/live-mindmap/issues/392)、不具合 [途中結果から作った相手の発言に、前に出した本文がもう一度入る](https://github.com/daiki-beppu/live-mindmap/issues/458)、地図 [Kanary を手本に字幕の精度を上げる](https://github.com/daiki-beppu/live-mindmap/issues/386)

### 1. 精度の基準線は、本番が発言を作るのと同じ経路で採る。別の経路で採ると、その間にある不具合が数字に出ない

基準線は、音声認識（STT）の確定結果だけを発言とみなして採点していた。ところが本番の `相手` のトラック（会議アプリの音）では、発言のもう 1 つの作り方が先に効く。途中結果（確定前の暫定の文字列）が 1 秒更新されなければ、その本文で発言にし、後から届いた確定結果は捨てる。確定の遅れ（実会議で約 9 秒）を縮めるために入れた規則だ。発言は一度出したら書き換えないので、続きが延びて届いたときは、出した分の後ろだけを新しい発言にする。その切り分けは、出す直前の関所（重なりを切る処理）がする。

抜けを数える前に、計測の結果（届いた時刻つきの途中結果と確定結果）を、本番の関所つきの処理に届いた時刻どおりに通した。台本と突き合わせると、挿入が桁違いに増えた。

| 素材 | 確定結果だけ: CER（挿入の字数） | 本番の作り方: CER（挿入の字数） |
| --- | --- | --- |
| 略語と製品名の会議（8 分） | 11.0%（28） | 46.2%（921） |
| 画面共有つきの四半期レビュー（23 分） | 3.0%（17） | 26.3%（1,675） |
| 社内の公開会議（55 分） | 4.2%（37） | 56.6%（9,971） |
| アイデア出しのブレスト（75 分） | 4.5%（39） | 62.3%（13,317） |
| 劇場の記録集の編集会議（161 分） | 5.5%（236） | 64.0%（27,181） |

並べて読むと、「開発の久我です。」の後に、同じ文から始まる発言がもう一度出ていた。基準線を確定結果だけで採ったので、この不具合はどの数字にも出ていなかった。計測の道具は、本番のどの段まで通した結果を測っているのかを決めてから使う。

### 2. 送り直し型のストリームから重なりを切るなら、比べる相手は「切る前の本文」で覚える

原因はコードで確かめた。STT の途中結果は、区間の始まりを変えずに、始まりからの全文を毎回送り直してくる（始まり 14.10 秒のまま、本文が 23 秒まで伸び続ける）。関所は、直前に出した発言の本文と比べて頭の重なりを切る。ところが、覚えていたのは**切った後の残り**だった。次の全文の頭は「残り」と合わない。重なりが 0 とみなされ、全文がもう一度出る。

関所の写しを 1 行だけ直し、切る前の本文を覚えるようにした。それで二重の大半は消えた（上の表の順に CER 12.1%・4.1%・5.9%・8.3%・9.4%）。それでも、確定結果だけのときより挿入は多い。途中結果が前の部分を書き換える（「C」→「CS」、表記の揺れ）と、前の全文で始まらず、重なりも見つからないからだ。直しは不具合の issue に回し、完了条件に「計測の道具でも本番の作り方で測れるようにする」を入れた。

この関所を入れた issue には「間を空けずに話す合成会議では起きない」と書いてあった。合成会議では、途中結果が 1 秒止まらないので、この経路を通らないという見立てだ。実際には、行の間の 0.45 秒の無音でも、途中結果の更新は 1 秒以上止まることがあった。合成会議でも経路は通っていた。実会議で起きているかは、残っているセッションが 1 件（相手の発言 7 件、重なり 0 件）しかなく確かめられていない。issue にもそう書いた。

### 3. 「語の抜け」は、脱落の字数ではなく、前後が合っていて間だけ消えたものを数える

確定結果だけで数えると、脱落は 5 素材で計 1,227 字あった。ただし、6〜9 割は 1〜2 字で、行の途中にある。誤認識（置換）に混じって、発言が台本より短くなった分だ。前後が合っていて、語がまるごと消えたものだけを数えると 308 字だった。台本は計約 97,000 字なので 0.3% にあたる。

まとまって落ちていたのは 2 種類だった。

- 同じ短い文が続くと、1 回にまとめられる（会議の終わりの「ありがとうございました」×3、「お疲れさまでした」×2）
- 確定結果の区切りの前後で、1〜3 秒ぶん消える（「お疲れさまでした。あ、次回の日程ですけど、十一月の第二週」が「お疲れ様でし」「1週の水で」になる）。途中結果にも出ていないので、本番の作り方でも落ちる

どちらも、上の 3 つの手が狙っていた「出だしと言い終わり」の抜けとは違う。

### 4. 小さい音が原因かは、素材を下げて流し直せば安く確かめられる。実録音の音量は、話している窓の分位で見る

実会議の録音を件数と音量だけで見ると、`自分`（マイク）の平均は -46.4 dB、`相手` は -22.3 dB だった。平均は無音の区間で下がるので、1 秒ごとの RMS の分位も取った。`自分` は上位 10%・1% の窓で -43〜-38 dB だった。`相手` と合成素材は -18〜-16 dB で、20〜25 dB の差がある。ゲインが効くなら、この差の分だ。

そこで、合成素材を 24 dB・30 dB 下げて流し直した。3 字以上落ちた部分の音量も、その行の平均とほぼ同じ（中央値 -0.5〜+1.0 dB）だった。

| 条件 | 略語の会議: CER・脱落の字数・固有名詞の正解 | 四半期レビュー: CER・脱落の字数・固有名詞の正解 |
| --- | --- | --- |
| 本番の設定 | 11.0%・60・79/126 | 3.0%・84・30/49 |
| 音を -30 dB | 10.7%・55・80/126 | 3.2%・97・31/49 |
| 1 秒更新がなければ確定を促す | 11.5%・68・76/126 | 3.2%・88・30/49 |

30 dB 下げても CER の差は ±0.3 ポイント以内で、向きも素材でそろわない。ただし、これは雑音の無い TTS の音を下げただけで、雑音の床が相対的に高い実際のマイクの小さい音とは違う。ゲインは SN 比を上げないので、雑音のある音でも効くとは考えにくい。この但し書きはチケットにも書いた。AEC の前後の比較は、素材が `相手` として流れて AEC を通らないので、この素材では測れなかった。

### 5. 効かなかった手は、どう悪くなったかまで見る

確定を促す処理は、途中結果が 1 秒更新されなければ、STT にそこまでの確定を求める。抜けが区切りで起きるなら効くかもしれない、と考えていた。結果は逆で、略語の会議では区切りの境目の脱落が 2 字から 14 字に増え、置換も増えた。区切りを増やせば、区切りで落ちる機会も増える。2 秒にすると、本番の設定と同じ数字になった。確定の遅れを扱った調査でも、この処理で遅れは縮まなかった。「効かない」だけでなく「区切りを増やすと悪くなる」まで分かったので、採らない理由がはっきりした。

計測では、また zsh の単語分割で失敗した。`for s in "screen 1350 1371" ...; do set -- $s` は、zsh では引用しない変数を空白で分けないので、素材の名前が「screen 1350 1371」のまま渡る。同じ日に 2 度目なので、引数を分けたいときは関数に渡す（`show screen 1350 1371`）と決めた。

### 1. 口頭で認めた例外は、issue の本文に書くまで、検証役に「計画の誤り」と判定される

段 2 の issue は、「HTTP は Effect の `NodeHttpServer` で受ける」と「Node の `node:http` に直接依存しない」の 2 つを求めていた。ところが `NodeHttpServer` の Layer は、`layer`・`layerServer`・`layerConfig`・`layerTest` のどれも、`node:http` の `createServer` を渡すことを必須にしている。実装はこの import を 1 行残し、レビューはそれを差し戻した。裁定は「指定の API では両立できず、要求を直す権限も無い」として、この指摘を範囲外にした。

途中で利用者が「`createServer` の import 1 か所は認める」と takt に伝え、修正の計画はそれを根拠に組まれた。しかし、修正を検証する役（別のモデル）は、計画を `plan_invalid` と判定した。理由は「計画が『要求の正本で例外が確定』とした条件は、order.md に存在しない」。order.md は、takt が issue の本文から作る作業の指示書だ。計画のやり直しは「両立しない条件で、外部の決定が要る」として決定案を 4 つ並べ、run は 3 時間 2 分で打ち切られた。order.md にこの例外を書き足したのは打ち切りの 4 分前で、間に合わなかった。結局、差分を手で引き取って PR にした。

段 4 では逆の形になった。計画は、ライブラリのソースを根拠に、issue の指定（正解ファイルを `Flag.FileSchema` で読む）を別の書き方に読み替えた。`Flag.FileSchema` は読み込みに失敗すると、使い方の説明を標準出力に出してから失敗する。そのため「失敗は標準エラーの 1 行で、今と同じ」という約束と両立しない。レビューの 3 つの観点は「承認の無い読み替え」として差し戻した。そこで、run の途中で issue の本文を「`Flag.FileSchema` は使わない」に書き換えた。修正の計画は本文を読み直し、3 件の指摘を誤検知として取り下げた。

takt の各工程が正本として読むのは、issue から作った指示書だけだ。会話で決めたことは、指示書の元になる issue の本文に書いてはじめて、後ろの工程に効く。

### 2. 仕様に書き写したライブラリの振る舞いは、実装の段でソースと食い違うことがある

段 3 の issue には、起票のときにソースを読んで書いた一文があった。「ヘルパーがシグナルで終わると、Effect は文面に `receipt of signal` を埋めた失敗（`PlatformError`）を返す。シグナルの名前はその文面から読む」。段 3 の計画が effect 4.0.1 のソースを読み直すと、`PlatformError.message` は `Unknown: ChildProcess.exitCode (…)` だった。シグナルの名前があるのは、その中の `cause.message` のほうだった。実装は `cause.message` に正規表現を当てる形になった。仕様のとおりに書いていたら、シグナルは常に「読めない」になる。SIGKILL で止めたときの「録音が不完全かもしれない」という警告も、黙って出なくなっていた。

段 4 でも、計画が仕様の前提を 1 つ外した。ポートの環境変数を `Config.Port` で読むと、0 が拒まれる。このプロジェクトのテストは、`LIVE_MINDMAP_PORT=0` で空いているポートを選ばせている。計画は `Config.Int` に替えた。

どちらも、仕様を書いた時点ではソースを読んでいた。それでも、どの層の値を読むか（外側の文面か、包まれた原因か）や、境界の値（0）で外れた。起票のときにライブラリの振る舞いを書き写すなら、「どのファイルの何行目で確かめたか」まで書いておくと、実装する側が読み直す場所がわかる。

### 3. 「入れ替えてよい」とした段は、混ざる間の継ぎ目の向きまで入れ替わる

置き換えの順番は「外側（入口）から内側へ」と決めていた。Effect の新しいコードから古い Promise のコードを呼ぶのは `Effect.tryPromise` の 1 行で済む。逆に、古いコードから新しいコードを呼ぶには `runPromise` が要るので、その向きを作らないための順番だった。そのうえで、段 2・3 の組（サーバー）と段 4・5 の組（CLI・計測）は互いに依存しないので、どちらを先にしてもよいとしていた。

実際には、段 4 が段 3 より先にマージされた。段 4 は、マップの画像を撮る処理を Effect の Service `MapCapture` に書き換えた。ところが、その撮影を終了時に呼ぶのは、段 3 でまだ置き換えていない `server.ts` の Promise のコードだった。古いコードから新しいコードを呼ぶ向きになったので、段 4 は `server.ts` の main で Service を `Effect.runPromise` で Promise に変える口（`PromiseMapCapture`）を作った。並行して入った見返し用 HTML の機能も、同じ形の口（`PromiseReviewPages`）を足した。

段 3 は、この口を外さなかった。セッションの後始末を受け持つ新しい `SessionSinks` の中で、Promise の口を `fromPromise` で Effect に戻した。

```ts
const fromPromise = <A>(run: () => Promise<A>): Effect.Effect<A> =>
  Effect.tryPromise({ try: run, catch: (error) => { throw error; } });
```

段 6 の issue には「`SessionSinks` がこの 2 つの Service を直接使う形にしてよい」と書いてあった。計画は「直接使う形には変えない」と決め、往復は最後まで残った。依存の線を張らなかった 2 つの組は、どちらが先に入るかで、継ぎ目の向きが変わる。「入れ替えてよい」と決めるときは、先に入ったほうが、まだ古い側から呼ばれるものを書き換えないかを見ておく。また、継ぎ目を外す作業は「してよい」ではなく、どこかの段の完了条件に入れる。

### 4. 入口だけに置く約束を検査で守るなら、許す単位を関数の呼び出しにする。ファイル単位で許すと、許した理由と別の呼び出しも通る

親 issue の完了条件には「`runMain` と `runPromise` は入口（`server.ts` の main・`cli.ts`・計測用スクリプト）にだけある」があった。段 6・7 の後で、これをテストで守るようにした。`server/test/entrypoints.test.ts` が `src` と `bench` のソースを読み、コメント行を除いて呼び出しの場所を確かめる。

最初の版は、`runPromise` を `src/server.ts` にファイル単位で許した。理由は、テストが使う Promise の入口 `startServerWithLayers` が `runPromise` を使っていたからだ。この許しで、同じファイルの main にある 3 節の往復も通ってしまった。`runSync` も「`core/review.ts` が使っている」として対象から外していた。

段ごとのレビューも、入口の確認は `runPromise` と `runMain` の grep に頼っていた。段 2 では、古いコールバックから `Effect.runSync` で配信へ渡す箇所を AI のレビューが「懸念」として挙げた。しかし裁定は「指示書が禁じているのは `runPromise` だ」として退けた。往復と `runSync` は、どのレビューの観点にも入っていなかった。

点検の後に直した版では、`runPromise` を許すファイルは無い（空の一覧）。`runSync` は `core/review.ts` だけに許す（5 節）。検査で約束を守るときは、許す例外を「この関数のこの呼び出し」まで絞る。絞れないなら、例外そのものを消す作業を先にする。

### 5. 同期の呼び出し元が残る境界は、Service も非同期も要らない部分を切り出して、`runSync` を 1 か所にする

見返し用の HTML は、保存したログからマップを組み立てて表示する。その関数 `reviewSnapshot` は、ブラウザ側の同期のコードから呼ばれる。段 6 より前は、古い `restoreSession` に「呼ばれたら投げる」偽の差分更新を渡して使っていた。段 6 で `restoreSession` は、Scope・差分更新・ログの 3 つを要る Effect に変わる。

段 6 の計画は、復元を 3 つに分けた。ログから状態を組み立てる `restoreState` は、要る Service が無く（`R = never`）、待ちも無い。状態からスナップショットを作る `snapshotOf` は普通の関数だ。セッションを開く `openSession` だけが Service を要る。`reviewSnapshot` は前の 2 つだけを使うので、`runSync` は必ず同期で終わる。

```ts
export function reviewSnapshot(events: readonly unknown[]): Snapshot {
  return Effect.runSync(Effect.map(restoreState(events), snapshotOf));
}
```

最新の main に載せ直すとき、`core/review.ts` が衝突した。並行して入った見返しの機能が、同じ関数の隣に、同梱ライブラリのライセンスの文言を埋め込む関数を足していたためだ。両方の変更を残して解いた。点検でも、この `runSync` は「Effect を知らないコードとの境界で、必ず同期で終わる」として、このままでよいと判定された。ブラウザ側の呼び出し元を Effect にする必要は無かった。

### 6. 「stop は中断しない」は、stop を走らせる Fiber の持ち主まで決めないと守れない

ヘルパーの stop は、中断ではなく「止めて」という印で止めると決めていた（[試作の話](./2026-10-06.md#helper-lifecycle-effect)）。段 3 の 1 周目のレビューで、それが守れていないと差し戻された。stop の本体は、HTTP の要求を処理する Fiber（Effect の軽量な実行単位）の上で動いていた。Effect の HTTP サーバーは、クライアントが接続を切ると、その要求の Fiber を中断する。CLI が応答を待たずに切れば、stop の途中で書き出しが飛ぶ。

直し方は、stop の本体をサーバーの Scope に属する Fiber として立て、要求の Fiber はその終わりを待つだけにすることだった。

```ts
const running = yield* Effect.forkIn(Effect.interruptible(body), serverScope);
yield* Effect.interruptible(Fiber.join(running));
```

段 7 のテストでも、同じ形の誤りで 20 秒の時間切れが出た。応答待ちの差分更新を `forkChild`（今の Fiber の子）で立てたため、セッションの Scope を閉じても止まらなかった。`forkIn(…, scope)` で、閉じたい Scope の持ち物にして直った。Effect で「何が止めるか」を決めるときは、処理を書く場所ではなく、その Fiber がどの Scope に属するかで決まる。

### 7. 終了まわりの既定値は Effect の下の層が持っていて、測ると秒の単位で出る

段 2 の実装とテストで、終了にかかわる既定値に 4 回つまずいた。どれも、Effect の上の書き方ではなく、その下の層の既定値だった。

| 症状 | 原因 | 直し方 |
|---|---|---|
| SIGINT で止めたサーバーが終了コード 130 を返し、テストが落ちる | `runMain` の既定の後始末は、中断だけで終わっても 130 を返す | 中断だけなら 0 を返す後始末を渡す |
| Scope を閉じるのに 20,009ms かかる | `NodeHttpServer` が接続の終わりを最大 20 秒待つ | `disablePreemptiveShutdown: true` で 4〜5ms |
| close に応答しない接続があると終了が 30 秒延びる | WebSocket のライブラリ `ws` の既定の待ち（30,000ms） | `closeTimeout: 3_000`。旧コードは `terminate()` で即座に切っていた |
| 終了の直前に送ったマップが届かない（期待 `[1,3,4]` に対して `[1,3]`） | Scope を閉じると、配信を待つ Fiber ごと消える | 配信を `PubSub.end` で閉じ、送り終わるまで `FiberSet.awaitEmpty` で待つ |

置き換えで「振る舞いを変えない」と決めていても、終わり方の振る舞いは新しい層の既定値に入れ替わる。旧コードが自分で書いていた止め方（`terminate()` など）を、一覧にしてから移すとよい。

### 8. 段ごとのレビューは差分しか見ないので、前から残っていた書き方は、置き換えた後に全体で点検する

6 段とも、レビューを通ってマージされた。翌日、利用者の依頼で、置き換えた後のサーバー全体を、effect 4.0.1 に同梱の書き方の手引きと型定義に突き合わせた。型検査は 0 エラーで、Effect 3 の API は 1 つも残っていなかった。そのうえで「直すべき」が 4 件見つかった。

- 3 節の、終了時の書き出しの Effect → Promise → Effect の往復
- 判断の記録（ADR）で「状態は Effect の可変の入れ物 `Ref` で持つ」と決めたのに、閉包の `let` やオブジェクトの書き換えのままの状態（差分更新の `let closed`、発言の ID の採番の `let count` など）
- 常駐サーバーのポートとセッションのフォルダを、Effect の設定の読み方 `Config` を通さず、`Number(process.env.LIVE_MINDMAP_PORT)` で検証せずに読んでいる。`LIVE_MINDMAP_PORT=abc` なら NaN がサーバーまで届く。CLI の側は同じ変数を `Config` で読んで弾くので、扱いが分かれている
- 正解ファイルの手書きの検証 `parseTruth` が、Schema（Effect の型と検証の定義）と二重に残っている。本番は Schema で読み、テストだけが手書きの検証を確かめていた

段ごとの記録をたどると、4 件とも、どのレビューも指摘していなかった。理由は 2 つあった。1 つは、置き換えの前からあったコードだったこと。`let closed` は置き換えの 5 日前、ポートの直読みは 6 日前のコードで、段 7 と段 4 はそれぞれの周りを書き直したが、その行は差分に入らなかった。もう 1 つは、残す理由がその場では正しかったこと。ポートの直読みは「まだ置き換えていない `server.ts` が使う」、`parseTruth` は「既存のテストが使う」という理由で残した。段 4 のレビューは、二重化を指摘するどころか、Schema の失敗の文面と検査の順番を `parseTruth` に寄せるよう求めた。どちらの理由も、後の段で消えたのに、残したものを外す役はどこにも割り当てられていなかった。

点検の指摘は、直すべき 4 件、直すと良い 12 件、好みの範囲 8 件だった。これを 16 件の issue（#436〜#451）に分けて起票した。段ごとのレビューの和は、置き換えの完了を意味しない。段で「残す」と決めたものには、外す段を書いておくか、最後に全体の点検を置く。

### 9. 利用上限で落ちた run は、すぐの自動の再投入では戻らない

段 2 と段 4 は同じ時刻に投入した。どちらも計画の工程で、Claude の 5 時間の利用上限に当たった（`rateLimitType=five_hour`）。takt は失敗した run を自動で 2 回まで投げ直す。だがその 2 回は数秒おきに走り、上限が戻るまでの約 2 時間を待たずに使い切った。段 4 の 3 つの run は、13 秒・4 秒・5 秒で終わっている。

その後、上限が戻るまでの間だけ別のモデル（Codex）に替えて再開した。だが段 2 は計画が「issue の指定が曖昧で確認が要る」として打ち切った。段 4 は、テストを書く工程が「計画に Service の公開名が無い」として計画へ 2 回差し戻し、そのまま takt のプロセスごと止まった。結局、どちらも翌朝 Claude に戻して投げ直した。段 3 と段 5 も、別の日中に takt のプロセスごと止まって run が中断し、手で投げ直した。段 3 は中断した時点の計画とテストを引き継いで、実装から再開した。

利用上限の失敗は、時間が解決するまで何度投げ直しても同じ結果になる。自動の再投入は、上限が戻る時刻（ログの `resetsAt`）まで待つ形でないと役に立たない。

### 10. 別のモデルの最終確認は、5 つのレビューと裁定がそろって見落としたものを拾う

takt の最後の工程（final-gate）は、レビューとは別のモデルが行う。この工程が、全員の承認を 2 回覆した。

- 段 2: レビューは `Sessions` に Layer を持たせるよう指摘したが、裁定は「`http.ts` から `server.ts` を import すると循環依存になる」として退けた。最終確認は「`Layer.ts:1041` は実装の値から Layer を作れる」と、裁定の前提をソースの行で否定した
- 段 3: 2 周目のレビューは 5 つとも承認した。最終確認は、テストの一部がまだ偽の時計（TestClock）ではなく実時間で待っていること（`helperSocket.test.ts` の `Effect.sleep(50)`、`server.test.ts` の 6 本が素の vitest の `it`）を差し戻した

一方で、どの工程も品質ゲートを自分では走らせず、実装の報告にある結果を引用していた。段 5 では、修正の後に全体のテストを走らせ直さないまま承認された。段 3 では、テストを書く工程が書いたテストが、実装に一度も当てられていなかった。実装の工程が「先に書かれたテストは、実装に対して一度も実行されていなかった」と記録し、検査する偽物と Layer に渡す偽物が別のインスタンスだった、などの誤りを直している。工程の数が多くても、「誰が実際に走らせたか」はどの工程の承認とも別に確かめる。

8 節の 16 件のうち、往復をなくす #436 と、`parseTruth` を消す #439 は、takt で直して main に入った。#436 で、`entrypoints.test.ts` の `runPromise` を許すファイルの一覧は空になり、`runSync` は `core/review.ts` だけに許す検査が足された。往復の口（`PromiseMapCapture`・`PromiseReviewPages`・`fromPromise`）と、テストのためだけの Promise の入口 `startServerWithLayers` も消えた。`Config` と `Ref` の 2 件を含む残りは、2026-10-08 の時点で未着手だ。

## 長い会議への対応を takt で 9 本続けて実装し、人が確かめる条件を takt の外に出した話

長い会議（60 分超・上限なし）への対応は、先に地図と試作で中身を決めてあった（[費用を時間に比例させる入力](./2026-10-04.md#long-meeting-input)、[議題の済みと畳む](./2026-10-04.md#close-topics)、[議題の入れ子](./2026-10-05.md#topic-nesting) など）。その実装を、仕様 issue 1 本と 7 本の sub-issue に切り、AI エージェントのワークフロー実行ツール takt に 1 本ずつ直列で実装させた。あわせて、講演形式の会議でマップが崩れる不具合 1 本と、そのマージ後の評価から出た 1 本も、同じ流れで takt に渡した。ここでは、決めた中身ではなく、takt に渡して実装させたときに分かったことを書く。

- 決定の記録: [長い会議への対応の実装仕様](https://github.com/daiki-beppu/live-mindmap/issues/166)、親 [長い会議への対応の実装](https://github.com/daiki-beppu/live-mindmap/issues/167)、子 [#168](https://github.com/daiki-beppu/live-mindmap/issues/168)・[#169](https://github.com/daiki-beppu/live-mindmap/issues/169)・[#170](https://github.com/daiki-beppu/live-mindmap/issues/170)・[#171](https://github.com/daiki-beppu/live-mindmap/issues/171)・[#172](https://github.com/daiki-beppu/live-mindmap/issues/172)・[#173](https://github.com/daiki-beppu/live-mindmap/issues/173)・[#174](https://github.com/daiki-beppu/live-mindmap/issues/174)、講演形式の [#162](https://github.com/daiki-beppu/live-mindmap/issues/162) と [#420](https://github.com/daiki-beppu/live-mindmap/issues/420)

### 1. 層ごとの issue に切ると、1 本は 20〜45 分で終わり、そのほとんどはレビューと検問に使われる

2 日前、サーバー・ヘルパー・画面にまたがる issue を 1 本で渡して、takt が 6 時間 50 分かかった（[止まったヘルパーの起動し直し](./2026-10-06.md#helper-restart)）。そのときに「次からは層ごとに issue を分けて渡す」と決めていた。今回は、1 本が 1 つの層の 1 つの約束になるように切った。

| issue | 中身 | 所要 | 差し戻し |

| #170 | 開いた会話の中では、マップの変更分だけを AI に送る | 23 分 | 0 回 |
| #173 | 画面のカメラを今の議題に寄せる | 74 分（止まった。2 節） | 1 回 |
| #168 | ノードに「最後に触れた時刻」を持たせる | 34 分 | 1 回 |
| #169 | 議題・論点の済みと、操作「閉じる」 | 44 分 | 1 回 |
| #171 | 済みの議題を畳んで AI に渡す | 37 分 | 1 回 |
| #174 | 済み・古い議題を画面で畳む | 24 分 | 0 回（指摘 3 件はすべて裁定で退けた） |

コードを書く段は、どの run でも数分だった。#171 は合わせて約 4 分、#172 は約 1 分半で、#168 の修正は 37 秒だった。残りは、計画（3〜5 分）、レビュー 1 周（4〜7 分）、最後の検問（4〜8 分）に使われた。差し戻しが 1 回あると、裁定・修正の計画・修正・確認・2 周目のレビューで 15〜20 分が足される。

**1 本の所要は、変更の量ではなく、レビューを何周するかで決まる。** 層で切って約束を 1 つに絞ると、指摘の数が減り、周回が 1 回で収まる。

### 2. 人が目で確かめる条件を受け入れ条件に混ぜると、全員が APPROVE でも takt は閉じない

#173 の受け入れ条件の最後に、「手で確かめる: 長い会議のログを再生し、1920×1080 で今の議題が 0.75〜1.1 倍で映る。撮影用の map.png は今どおり全体」が残っていた。2 周目のレビューは 5 人とも APPROVE だったが、最後の検問は、実画面の目視はコードの計算で代わりにならないとして、この条件を「判定不能」にし、run は止まった。自動の積み直しも同じ結論で止まり、差分は人が引き取って PR にした。止まり方と、そこで失った時間は、[takt を回した側のエントリ](#takt-ops-day) の 4 節に書いた。

以後、takt に渡す本文では、手の確認と本物の API での評価を「（マージ後に人が）」と書き、「takt の条件には含めない」と添えて、takt の受け入れ条件から外した。#174・#162・#420 の本文は、この形で渡した。どれも最後の検問で止まらず、検問はそれらの条件を「範囲外」として判定から外した。

**takt の受け入れ条件には、takt の手元で確かめられることだけを書く。** 画面を見る・本物の API で流すといった確認は、条件の外に出し、外に出したことを本文に明記する。

### 3. 外に出した確認は、結果を書く場所まで決めておかないと消える

外に出した確認には、行われたものと行われなかったものがあった。分かれ目は、本文が結果の置き場所を指定していたかだった。

- #170・#172・#162・#420 の本物の API の評価は、本文に「変更前後を表にして、この issue にコメントする」と書いた。4 本とも、合成会議の素材で変更前後を 2 回ずつ流した表が issue に残っている
- #174 の画面の確認は「手順は PR の本文に書く」としていた。takt が作った PR の本文は、渡した本文の写しと実行の報告だけで、手順は書かれなかった
- #173 は人が PR にしたときに「マージ後に人が確かめる」に移したが、確かめた記録は issue にも PR にも無い

#420 の本文は、画面の確認も「講演のマップが約 200 ノードに増えたことについて、画面（1920×1080）で読めるかを確かめ、所見を同じコメントに書く」と書いた。評価のコメントには、畳んだ後に画面に出るノード数と縮尺まで残っている。

**takt の外に出した条件は、誰がいつ行い、結果をどこに書くかまで本文に書く。** 「PR に書く」は、PR を作るのが takt なら当てにならない。

### 4. takt の作業場所から見えない素材は、本文に写しておく

takt の作業場所は、元のリポジトリとは別のクローンだった。ローカルにしか無いブランチは見えず、`git fetch` は承認が要るので走らない。依存も入っていない。そのため、計画が「未確認」のまま進んだものが 3 つあった。

- #172: 議題の入れ子を試した試作のプロンプト（v6）は、試作ブランチにしか無かった。計画もレビューも「未確認、本文を正とする」で通し、プロンプトは issue の本文の言い回しをほぼ写した形になった。試作に入れていた具体的な場面の例は、入らなかった
- #173: 画面のライブラリ（React Flow）の、範囲から倍率を出す関数を確かめられず、倍率の計算を自前で書いた
- #170: Agent SDK の型定義も見えなかった。ただし本文に、SDK の `env` は子プロセスの環境を丸ごと置き換えて `process.env` と混ぜないこと、を型定義の行番号つきで写し、`{ ...process.env, … }` と書くこと、`PATH` が引き継がれることをテストで確かめることまで書いていた。#170 は差し戻し 0 回で通った

本文の書き換えは、ほかの issue にも効いた。#169 の issue には「#244 が先に入っていれば…／まだなら…」という分岐が残っていた。takt に渡した本文では「どちらもマージ済み」と解決してあり、計画は分岐を考えずに済んだ。#171 は、サーバーを Effect に置き換える段が先に入ったので、投入の 1 分前に本文を新しいコードの形に合わせた。#168 は、並行で走っていた Effect の段と同じテストファイルを触ったが、本文で「このファイルは呼び出しの引数だけを直し、ほかは触らない」と絞っていたので、衝突しなかった。

**実装するエージェントが読めるのは本文だけだと考え、判断に要る外の素材（ライブラリの型、試作の文面、先に入る変更の形）は本文に写す。** 写さなかった素材は、エージェントが黙って本文から作り直す。

### 5. テストの入力が 2 つの条件を同時に満たしていると、片方の実装漏れを捕まえられない

差し戻しの多くは、実装の誤りではなく、テストの検出力の不足だった。形は 4 本とも同じだった。

| issue | テストの入力 | 見逃す誤り |
|---|---|---|
| #168 | 本文の変更と根拠の追加を、1 回の update で同時に行う | 「両方変わったときだけ時刻を進める」実装 |
| #169 | 名前は「既存の根拠を再指定」だが、本文も変わっていた | 「値が変わったときだけ開き直す」実装 |
| #172 | 済みの論点の下には案しか無く、議題を置いていなかった | 済みの論点の下の議題まで一覧から消す実装（実際にそうなっていた） |
| #420 | 行のどこかに数字の 5 があれば通る | 数の欠落（行に「上限 5」と書いてあるので常に通る） |

#172 は、テストではなく実装が誤っていた。議題の一覧を作る関数が、ノードを数える走査と子の議題を探す走査を同じ再帰でしていた。済みの論点に当たると両方が止まり、その下の話し中の議題が一覧から消えた。本文は「数えない条件」（済みの論点の下は数えない）と「一覧から外す条件」（済みの議題とその下を外す）を別々に書き、計画も「済みの論点の下の議題は外さない」と書いていた。4 人のレビュアー全員が、同じ欠陥で REJECT した。テストに「済みの論点の下にある議題」という組み合わせが無かったので、テストを書く段でも実装の段でも気づかなかった。

修正の確認にも穴があった。どの修正でも、「条件を外すと新しいテストが落ちる」ことは実行して確かめていない。#172 では確かめようとして、まだコミットしていない実装ファイルを丸ごと戻したので、ほかのテストまで 16 件落ち、切り分けにならなかった。

**条件が 2 つある振る舞いは、片方だけを満たす入力で 1 本ずつテストする。** 数を確かめるテストは、その数がどこに書かれているかまで絞って取り出す。

### 6. 計画で比べて選んだ案は、実装の途中で正しく指摘されても覆らず、レビューを 1 周使う

#173 の計画は、「最後に変わったノード」を、反映の前後のマップを比べた結果の末尾から取ると決めた。操作の順から決める案は「仮の ID の解決や捨てた操作の扱いを別に持つ必要がある」として退けていた。比べた結果の並びは作られた順なので、議題 n1・n2 の順に作り、n2 → n1 の順に更新すると、最後に変わったのは n1 なのに n2 を選ぶ。

実装の段に並走していたレビュアー（takt の companion）が、実装の途中でこの例をそのまま挙げて直すよう求めた。実装担当は事実を認めたうえで、「計画が採用した方式で、実装担当の範囲を超える」として残した。続くレビューでは 5 人全員が REJECT し、そのうち 4 人がこの点を挙げた。修正の計画は、退けた理由を 1 つずつ崩した。仮 ID の解決と捨てた操作の扱いを両方持っている適用の関数の中で、変わった順を記録すればよい。直るまでに、レビュー 1 周と修正 2 回（約 40 分）かかった。

2 回目の修正は、修正の確認で「計画の外を変えた」と差し戻された。修正担当は、計画が「変えない範囲」としたカメラを動かす条件まで、正しく直していた。ただしテストが無かった。再計画はテストを 1 本足すだけだったが、それでもう 1 周走った。

#174 でも、companion が実装の途中で前提の誤りを見つけた。計画は「ノードの並びは親が子より先」としていたが、移動や統合は並びを変えないので、後から作った親へ動かした子は親より前に来る。こちらは計画が比べて選んだ案ではなかったので、実装担当がその場で取り込み、レビューの前に直った。

**takt の実装担当は、計画が比べて選んだことを覆さない。** 計画に「比べて退けた案」を書かせるなら、その退けた理由が本当に成り立つかを、計画の段で確かめさせる。

### 7. 裁定で「範囲外」になった本当の欠けは、起票しない限り残らない

レビュアーの指摘は、裁定の段が採るか退けるかを決める。退ける理由は、受け入れ条件に書いていない、前の issue の約束を変えることになる、のどちらかが多かった。退けられた中に、事実としては正しい欠けが 2 つあった。

- #169: 2 つの議題を統合すると、根拠が 1 件も増えていなくても統合先に「根拠が足された」の番号を付ける。そのため、統合の直後の 2 回は、その議題を閉じられない。裁定は追跡を「正確」と認めたうえで、#168 の約束とそのテストを理由に退け、「別チケットで #168 の仕様を決める前提」とした
- #171: 済みで畳まれた議題の中のノードを、移動や統合で外に出すと、その下のノードは AI に一度も渡らない。裁定は「仕様の側で扱う課題として持ち越す」とした

どちらも、持ち越し先の issue は作られていない。takt は issue を起票しないので、「持ち越す」と書かれた報告は、作業場所と一緒に消える。この開発ログを書くために報告を読み直して、初めて拾えた。

**takt の裁定が「範囲外」「持ち越し」とした指摘は、マージの後に人が報告から拾って起票する。** 読むのは裁定の報告の、退けた指摘の表だけでよい。

### 8. 新しい指示を足すときは、それとぶつかる古い禁止が残っていないかを探す

#162 は、講演の補足（具体例・数字・経緯）を、親の要点の言い直しではなく、子の要点として足すように指示を変えた。レビューで、同じプロンプトに「例や経緯は本文に書かない」という無条件の禁止が残っていると指摘された。そのままでは、補足を子に足せと言いながら、子の本文に補足を書くことを禁じている。禁止は「親の要点に書き足さない」に絞り、矛盾が残っていれば落ちるテストを足した。

[議題の入れ子を決めたとき](./2026-10-05.md#topic-nesting) にも、否定の一文が別の規則を打ち消していた。そのときは試走の数字で気づいた。今回は、本物の API を流す前に、レビューが文面の突き合わせで見つけた。

**プロンプトに「〜する」を足したら、同じ対象についての「〜しない」を検索して、範囲を絞るか消す。**

### 9. 指標を数える道具は takt に作らせ、測るのは人がマージ後に行う。その数字が次の 1 本になる

#162 では、本物の API で流す比較を takt の条件から外した。代わりに、セッションのログから数える指標を 3 つ、回帰評価の出力に足すところまでを takt の範囲にした。本文の書き換えの回数 ÷ 発言の数、1 つのノードへの書き換えの最多回数、話し中（済みでない）の兄弟の最多数、の 3 つだ。それまでの評価は最後のマップしか見ていなかったので、途中で同じノードを書き換え続けることも、途中で兄弟が増えすぎることも、数字に出なかった。

マージ後に、講演の合成会議（約 28 分・発言 97）と、短い 2 本（決める会議・共有の会議）を、変更前後で 2 回ずつ流した。

| 本文の書き換え ÷ 発言 | 0.19・0.20 | 0.01・0.01 | 0.00・0.01 |
| 1 ノードの書き換えの最多 | 2・2 | 1・1 | 0・1 |

#162 は 5 つの条件のうち 4 つを満たし、兄弟の上限だけが満たせなかった。数えた道具がそのまま、どこで外れたかも示した。1 回の再生で 79〜103 個ある親のうち 6 以上になったのは 2 個で、親の種別は要点（議題の中で共有された紹介・体験談などの記述）と議題だった。一度超えると最後まで減らず、49 回の差分更新のうち 30 回・42 回の時点で 6 以上だった。この数字を事実として本文に書いた #420 を起票し、同じ夜に takt に渡した。決める会議の決定・TODO の再現率（2/2・3/3）と、講演・共有の誤検出 0 件は、#162・#420 の前後とも変わらなかった。

**本物の API の評価を takt から外しても、評価に要る指標の実装は takt の範囲に残す。** そうすると、人がマージ後にするのは流すことと読むことだけになり、外れた条件はそのまま次の issue の「事実」の節になる。

### 10. 上限を守らせるには、上限の値を変えるより、どこが上限に近いかを毎回見せる

#420 では、上限の 5 を 6 に緩める案も考えた。測った値で退けた。超えた親は 6 で止まらず、ちょうど 7 まで跳んでいた。一方、上限ちょうどの 5 に達した親は、1 回の再生に 9〜12 個あった。値を変えても、超える親はやはり超える。問題は値ではなく、AI が上限に近づいたことに気づけない点にあった。

原因は 2 つあった。毎回のメッセージに添える議題の一覧は、議題しか並べないので、要点の下で増えた兄弟は AI に見えない。また、「閉じる」が使えるのは議題と論点だけなので、親が要点のときは、指示にある「話の移ったものを閉じる」が使えない。指示は 3 つの手を並べていただけで、要点では閉じられないことを書いていなかった。

直し方は 2 つ入れた。

- 毎回の議題の一覧に、話し中の子が 5 つ以上ある親を、種別によらず id・本文・子の数つきで名指しする。すべての親は並べない（メッセージを長くしない）
- system プロンプトに、名指しされた親が要点なら、閉じられないので、新しい要点を最も近い兄弟の要点の子として足す、と書く

親ごとの数を system プロンプトに入れなかったのは、system プロンプトを毎回同じ文字列にしてキャッシュに乗せているからだ。毎回変わる値は、毎回のメッセージの側に出す。

#420 の後、講演の兄弟の最多は 2 回とも 5 になり、6 に進んだ親は無かった。上限ちょうどの 5 に達した親は 6 個と 4 個に減った。会議の直下の議題は 12 から 4〜5 に減り、深さは 10 になった。ノード数は約 200 のまま変わらず、増えた分は縦ではなく右に伸びた。利用者は講演形式のセミナーで、子が右に増えるのはよいが、縦に積みすぎるとどれがどの話につながるか分からない、と評していた。その好みどおりの形になった。1920×1080 の画面では、済みの議題が件数つきの 1 ノードに畳まれる。2 回目は縮尺 0.94 で 1 画面に収まり、1 回目は縮尺 0.75 で縦に約 1.8 画面分になった。

なお、#420 の変更前として測り直した版の最多は 6 で、#162 の評価で測った 7 とずれた。同じ指示でも、回によって 1 つ前後する。差が 1 の比較は、2 回ずつの再生では言い切れない。

**LLM に数の上限を守らせるときは、上限の値を調整する前に、AI がその時点で上限に近い場所を見えているかを確かめる。** 見えていなければ、毎回の入力で名指しし、その場所で使える手を書く。

### 1. 並行に走らせた 2 件が同じ型を別々に作り変えると、rebase の衝突は設計の判断になる

#276（開き直し・復元で直前の画面を送り直す）と #278（ライブの取り込み）は、どちらも #274 の後に、同じ main のコミットから 30 秒違いで走り出した。2 件とも、サーバーの中核の `server/src/core/session.ts` で、まだ AI に添えていない画面を持つ型 `HeldScreen` を書き換えた。

- #276 は `{ change, file }` とし、画像のバイト列をメモリに持った。復元では、呼ぶ側が渡す読み手（`restoreSession(events, readScreen?)`）でファイルを読んだ
- #278 は `{ start, image: { id, file } | null }` とし、ファイル名だけを持った。添えるときに、ログを書く口 `SessionLog` に足した `readScreen` で読み戻した

#278 がファイル名だけにしたのは、自分の run の設計のレビューで「差分更新まで受信した全 JPEG をメモリに保持する」と差し戻されたからだ。発言が来ない間、画像は際限なく溜まる。同じ指摘は、先に入った #274（合成会議の再生）でも「全 JPEG を再生前に溜め、使い終わっても持ち続ける」として出ていた。一方、同じ時間に走っていた #276 のレビューは、バイト列を持つことを指摘しなかった。同じ方針が、並行する 2 つの run の片方でだけ適用された。

#276 が先にマージされ、#278 を rebase すると `session.ts` が衝突した。衝突は、takt を回しているまとめ役のセッションがサブエージェントに解かせ、約 6 分で終わった。指示は「#278 のメモリに持たない形を保ち、#276 の送り直しと復元の働きも保つ」だった。結果は、`HeldScreen` をファイル名だけの形に寄せ、#276 の「最後に添えた 2 件」も同じ型で持った。復元の読み手と `SessionLog.readScreen` は同じ役なので 1 つにまとめ、`restoreSession` から第 2 引数を消した。

**同じ型を触る 2 件を並行させると、衝突の解決は行の取捨ではなく「どちらの表現に寄せるか」の判断になる。** 先に入った側に寄せるとは限らない。今回は、後から入る #278 の側が、レビューで 2 度出た方針に沿っていた。

### 2. 衝突を解くときに決めた振る舞いは、レビューを通らずに main に入る

表現を寄せると、振る舞いも 2 つ変わった。

- **送り直す画面が読めないときは、黙って外して送る。** 解いた直後、#278 のテスト「読み戻しが失敗しても次の呼び出しへ進む」が落ちた。読めなかった画面も「最後に添えた 2 件」に残るので、送り直しの読み戻しを呼び出しの失敗にすると、以後の呼び出しがすべて失敗する。送り直しは文脈の補いなので、読めなければ外すことにした。今の添える画面が読めないときは、これまでどおり呼び出しの失敗としてログに残す
- **復元の時点では画像を読まなくなった。** #276 では「画像が読めなければ復元が失敗する」だったが、「復元はでき、続きの呼び出しが失敗としてログに残る」に変わった。#276 のテストもそう書き換えた

どちらも筋は通っている。ただ、この 2 つを決めたのは衝突を解いたサブエージェントで、takt の観点別のレビューは通っていない。サブエージェント自身も、気になる点として「外したことがどこにも記録されない」「#276 の『読めなければ復元が失敗する』が消えた」を報告に挙げていた。PR は検査（型と全テスト）が通ったところで push し、自動でマージされた。PR の本文は takt が書いた #278 の説明のままで、この 2 つの決定は書かれていない。決定が残っているのは、コードのコメントと、まとめ役のセッションへの報告だけだ。

検査で見つかったこともある。#278 の takt の作業場所には、ヘルパー（会議の音と画面を取る Swift のプログラム）のビルドに要る WebRTC のライブラリが無く、run の中で Swift のテストは一度も走っていなかった。rebase の後に全部の検査を流して初めて、テストの 1 行（`#expect(sent == [11 * 0.25, …])`）が Swift の型検査の時間切れでビルドに落ちると分かり、期待値を `let expected: [Double]` に分けて直した。レビューはどの観点も、Swift の実行を「未確認」としたまま判定していた。

**rebase の衝突を解いて振る舞いが変わったら、その決定を PR の本文に書き足す。** takt のレビューは run の中でしか動かないので、run の後に入った変更を見る目は、マージ前の検査だけになる。

### 3. 同じファイルを触る issue は blocked by で直列にし、積む直前に本文を今の main に合わせる

1 の衝突の後は、同じファイルを触る issue を並べないようにした。

- #277（フォルダの流し直し）は、ログの `screen-off`（共有画面を使わない・使えない、の行）を元の時刻と理由のまま流す。その行の形と、中核に入れる口は #280 で入る。そこで #277 を #280 の blocked by にした
- #421（探し直し）は、#278 のマージ後に、#279・#280 の本文を #278 のコードと突き合わせていたサブエージェントが見つけた穴（開始時にウィンドウが無いと、そのセッションの間は二度と探さない）から起票した。取り込みの `ScreenCapture.swift` を触る。#280 も #279 も同じファイルを触るので、#280 の blocked by にし、さらに #279 のマージを待ってから積んだ

積む直前には、本文を今の main と突き合わせて書き足した。#277 には「画像はメモリに持たず、読み戻す形にそろえる」（#278 の形）を、#421 には「許可が無いときは探し直さない」（#280）と「見つけ直したウィンドウでもタイトルの読み直しを効かせる」（#279）を足した。takt は issue の本文しか読まないので、main に何が入ったかは、本文に書かない限り伝わらない（同じ日にほかの束でも続けたこの手順は、[takt を回した側のエントリ](#takt-ops-day) の 3 節と 5 節）。

その後の 4 件（#280・#279・#277・#421）では衝突は起きなかった。#277 と #279 は同時に走ったが、サーバーと Swift のヘルパーで触るファイルが分かれていた。代わりに、#421 は #279 のマージ（10 時 15 分）まで待つことになった。

**並行させてよいかは、issue の主題ではなく、触るファイルで決める。** 直列にするなら、待つ側の本文を、待った相手が入った後の main に合わせてから積む。

### 4. 一度きりの処理をループにすると、それまで起きなかった競合が出る

#421 は、開始時に会議のウィンドウが無いと二度と探さなかった取り込みを、見つかるまで 2 秒おきに探し直すように変えた。撮っていたウィンドウが消えたときも、探し直しに戻る。

実装の途中で、実装の工程に付いて走る AI らしい誤りの観点のレビューが 1 件見つけた。ウィンドウのタイトルを読み直すタスクは、取り込みを始め直すたびに作り直す。前のタスクは取り消すだけで終わりを待たないので、遅れて返った古い読み取りが、新しいウィンドウのタイトルを上書きしうる。takt はこれを直し、取り消し済みか、撮るウィンドウの ID が変わっていたら書き込まないようにした。

1 回目のレビューでは、AI らしい誤り・設計・テストの 3 観点が、そろって同じ欠陥で差し戻した。探し直しの待ちは、2 秒のタイマーを起動してから、待ちを登録していた。登録より先にタイマーが満了すると、起こす相手がいないので満了が捨てられ、その後に登録した待ちは二度と起こされない。直し方は、登録した後にタイマーを起動する、という順番の入れ替えだけだった。

2 つの競合には、同じ原因がある。レビューの言葉では「再開前は、1 回の `run()` につきタイトル読み直しタスクが 1 本だけだったため、この競合は起きなかった」。1 回しか通らない処理には、前の回の後始末と次の回の始まりが重なる瞬間が無い。ループにした途端、それが生まれる。

**一度きりの処理をループにするときは、回ごとに作り直すもの（タスク、タイマー、ID）を並べ、前の回の残りが次の回に届かないかを確かめる。**

### 5. 判断を純粋な関数に切り出して試しても、待ちと順番の誤りは試せない

#421 の本文は、「探し直しの判断」を純粋な関数に切り出して試すよう求めていた。CI の Mac には画面収録の許可が無く、ScreenCaptureKit（macOS の画面取り込みの API）を呼ぶテストは書けないからだ。takt は、ウィンドウの候補と今の状態（未開始・撮っている・無くなった）から次の行動（取り込みを始める・探し直す・何もしない）を返す関数を作り、11 件のテストを足した。

4 の 2 つの競合は、どちらもこの関数の外、待ちとタスクの順番にあった。テストの観点のレビューは、「`retryHasNoLimit()` は純粋関数の戻り値だけを検証し、この経路を通らない」と書いた。それでも、競合の回帰テストは足さなかった。待ちは private で、それを呼ぶ `run()` が ScreenCaptureKit を呼ぶので、最小の試す層が無い。裁定は回帰テストを任意とし、修正はコードを読んで確かめただけで通った。

**ScreenCaptureKit のように CI で呼べない API の周りでは、判断を切り出したテストが守るのは判断だけだ。** 待ちや順番は、コードを読むレビューが最後の網になる。次に同じ形を作るなら、待ちの仕組み（タイマーと登録）も ScreenCaptureKit から離して、時計を差し替えて試せる形にしておく。

修正の工程では、`swift test` を直接流して「`TestingMacros` のプラグインが見つからない」でテストのビルドが落ち、テストは 1 件も走らなかった。このリポジトリのヘルパーのテストは、Command Line Tools だけで動かすため、`pnpm test` のスクリプトがテストのプラグインのパスを渡している。素の `swift test` では通らない。修正の確認は「因果は未確認」として先へ送られ、全テストが通ったのは、PR の CI でだった。

### 6. 計画が自分で書いた「限界」は、仕様が除外していなければ差し戻される

#276 の計画には、「限界: 等速再生で呼び出しの途中に受けた画面は、ログからは区別できません」と書いてあった。復元は、ログの「この呼び出しは何秒までの発言を扱った」を区切りに、それ以前に映り始めた画面を「添えた」とみなしていた。ところが、AI の応答を待つ間に 18 秒の画面を受けると、元のセッションでは次の回に添えるのに、21 秒で区切った復元では添えたことになって消える。

1 回目のレビューでは、4 観点がそろってこれを差し戻した。裁定は「仕様の完了条件は、並行する場合を除外していない」として採った。直し方は、呼び出しの時点で受け取っていた画面の数（`screenCount`）をログに足し、復元では「受け取った順の番号が `screenCount` より小さく、かつ区切り以前」の画面だけを外す形にした。

**計画に「ここは区別できない」と書いたら、それは仕様に対する未達の宣言だ。** 仕様が除外していないなら、計画の段で記録を足して区別できるようにする。書いて先に進むと、レビューの 1 周分の時間で同じことをすることになる。

### 7. 読み込み先の検査は、正規化した後の場所だけでなく、正規化する前の文字列でも行う

#277 は、過去のセッションのログの `screen` の行に書かれたファイル名で、`screens/` の画像を読む。1 回目のレビューで、セキュリティとコードの観点が、ログに `../../private.jpg` と書けば `screens/` の外のファイルを読み、AI に送れると差し戻した。

最初の修正は、`resolve(screensDir, image)` の親が `screensDir` と一致するかを見た。修正の確認の工程がこれを通さなかった。`image` が絶対パスだと `resolve` はそれをそのまま返すので、`<フォルダ>/screens/x.jpg` という絶対パスは親が一致して通る。`../screens/x.jpg` や `./x.jpg` も通る。2 回目の修正で、「`basename(image) === image`（区切り文字を含まない）」も条件に足した。

**ログの中のファイル名は、外から来た入力として扱い、正規化の前の文字列でも検査する。** 正規化した後の場所だけを見ると、正規化が吸収してくれる書き方（絶対パス、`./`、戻ってくる `../`）がすり抜ける。1 で画面をファイル名だけで持つ形にしたので、ファイル名が画像を読む鍵になっている。

### 8. テストを先に書く工程の期待値は、実装と同じくらい間違える。間違え方は 2 通りある

takt は、実装の前にテストを書く。8 件のうち 4 件で、テストの期待値の誤りが見つかった。

- **テストが間違い、実装が正しい（#275・#276・#279）**: 実装の後にテストが落ち、原因はテストの側だった。#275 は表の見出しの数を、種類が 7 つのところ 6 つで数えていた。#279 は、テストの中の時刻の計算を誤っていた（動いた割合が除外のしきい値を超えることや、中央値が中央 2 つの平均になることを見落とした）。どれも、coder が実装ではなくテストを直した
- **テストと実装が同じに間違う（#274）**: 共有が終わったときの見出しは `## 共有画面：なし（[12:34] から）` と決めてあったが、実装もテストも角括弧の無い `（00:03 から）` にしていた。計画には正しく書いてあった。テストが通るので、実装の報告は「確認済み」だった。見つけたのは、仕様と突き合わせた AI らしい誤りのレビューだ

前者は、落ちたテストを見れば分かる。後者は、テストが通るので見えない。

**テストが落ちたら、実装より先に期待値の計算を確かめる。テストが通っても、仕様の文字列そのものと突き合わせる観点を別に持つ。** #280 では逆に、テストが仕様より細かいもの（JSON のキーの順番、オブジェクトの参照の同一性、`box-shadow: none` の書き方）を固定していて、テストの観点のレビューで外された。期待値は、仕様が決めた形だけを書く。

## 画面を人が動かす操作を 11 件のチケットに分け、同じ reducer を触るものを takt で 1 件ずつ実装した話

[前の日に地図と試作で決めた](./2026-10-07.md#human-view-ops-map)「画面を人が動かす操作」を、仕様 1 枚と実装のチケット 11 件にして、takt（issue の本文を渡すと、計画・テスト・実装・4 観点のレビュー・修正・最終確認・PR までを AI エージェントに回させるツール）で実装した。操作は、スクロール・ドラッグ・ズームでの移動、キーでの移動と全体表示、日本語入力がオンでも効くキー、キー一覧、画面の外の変化を知らせる縁の点、右の列と字幕の出し入れ、矢印キーでのノード選択、人による議題の開閉だ。どれもマップのデータを変えないので、ブラウザの中だけで完結させた。中心は見る状態の **reducer**（今の見る状態と出来事 1 つを受け取り、次の状態とカメラへの指示を返す純粋な関数 `reduceViewing`。`web/src/viewing.ts`）で、11 件のほとんどがこのファイルを触る。takt の 1 件の実行は 25〜84 分（合計で約 8 時間半）、最初の実行の開始から最後のマージまでは約 12 時間だった。

- 決定の記録: 仕様 [画面を人が動かす操作の実装仕様](https://github.com/daiki-beppu/live-mindmap/issues/309)、親 [#310](https://github.com/daiki-beppu/live-mindmap/issues/310)、実装は [#311](https://github.com/daiki-beppu/live-mindmap/issues/311)〜[#321](https://github.com/daiki-beppu/live-mindmap/issues/321)。決めた側のエントリは [自動のカメラへ戻る条件の試作](./2026-10-07.md#camera-return-prototype)・[ショートカットキーのライブラリの調査](./2026-10-07.md#hotkeys-library-research)・[ショートカットキーの一覧](./2026-10-07.md#hotkeys-list)

この画面では、**自動のカメラ**（反映のたびに**今の議題**、つまり直近の更新が当たった議題へ寄る動き）が普段の見え方を決める。人が動かすとそれが止まり、今の議題が変わるか `Esc` で戻る。済んだ議題は子孫を隠して 1 つのノードに**畳み**、畳んだ議題が同じ親の下に続くと「議題 N 件」という 1 つの**まとめ**にする。ノードを選ぶと、右の列にそのノードの**根拠**（元になった発言）が出る。

### 1. 同じファイルを触るチケットは、依存の線が無くても 1 件ずつ流し、積む前に「今のコード」を本文に書き足す

チケットの依存（blocked by）は、仕様の順番だけで張っていた。キーでの移動（#312）、⌘＋クリックと軸を固定するスクロール（#314）、縁の点（#316）は、どれも最初の 1 件（#311）だけを待つ。右の列と字幕（#317）と矢印での選択（#318）も、同じ 1 件だけを待つ。線のとおりなら並行に流せる。ただ、どれも同じ reducer の状態・出来事・指示の型に足していく。並行に流すと、それぞれが同じ型に別の名前で同じものを足し、後に入る側が作り直しになる。

そこで、#312→#314→#316 と #317→#318→#319→#320→#321 を直列にした。前の PR がマージされてから数分で次を流した（#319 の終わりが 0:15:49、#320 の開始が 0:18:59）。並行にしたのは、新しいファイル 2 つと、画面の部品からの呼び出しを足すだけで済む日本語入力のチケット（#313）だけだ。

直列にしても、takt は issue の本文しか読まず、仕様を書いた時点のコードには前のチケットが足した名前がまだ無い。そこで、積む直前に毎回、本文に「確定した細部」の節を足し、その時点の main にある関数の形（`reduceViewing(state, event, tree, scope)` が `{ state, camera }` を返す）や出来事・指示の一覧を写して、「先に main に入った名前や型はそのまま使い、別の名前で作り直さない」と書いた（同じ日にほかの束でも続けたこの手順は、[takt を回した側のエントリ](#takt-ops-day) の 3 節）。

11 件の実行の中で、rebase の衝突は 1 度も起きなかった。#314 の実行中には、別のチケットのコミットが 7 つ main に入っていた（`web/src` の 4 ファイル）。それでも乗せ直さずに squash でマージできた。

**依存の線は「どちらの答えが先に要るか」を表し、「同じ場所を書き換えるか」は表さない。** 同じ型に足していくチケットは、線とは別に直列にする。そのうえで、積むたびに今のコードの名前を本文に写す。

### 2. 本文に細部を書き足すと、仕様の決まりどうしの食い違いが、積む前に出てくる

選択と畳む見せ方をつなぐチケット（#319）の細部を書いていて、仕様の決まりが両立しないことに気づいた。仕様には「選んだノードとその祖先は畳まない」とあった。一方で、「畳んだ議題も選べる」「畳んだ議題では `→` で中へ入らない」「開くのは `Enter` だけ」とも決めていた。選んだノード自身を畳まないと、矢印で畳んだ議題に乗っただけで、その議題が開く。選ぶことが開くことになり、`Enter` の意味が無くなる。

利用者に聞き、「選んだノードの祖先だけを畳まない」に読み替えた。選んだノード自身は畳まれうるが、祖先が開いているので、畳んだノードとして見えたまま残る。#319 は、この読み替えを本文に書いてから流した。

同じ確認で、別の地図から来た古いチケット（#175）も閉じた。「変わったこと」から畳んだ議題の中を指したら一時的に開き、次の反映で畳み直す、というチケットだ。後から書いた仕様（#309・#321）は、同じ操作を「指したノードを選び、`Esc` まで開いたまま」に置き換えていた。先に作ると、作り直しになる。このチケットを待っていた別のチケットは、待ち先を #321 に付け替えた。

**「今のコードではこう書く」まで書き下すと、決まりどうしの矛盾が見える。** 仕様の文のままでは、1 つずつはもっともらしく読める。後の仕様が同じ振る舞いを決め直したときは、まだ作っていない古いチケットを探して閉じる。

### 3. ライブラリの挙動は、前の調査の記録ではなく、入れた版の dist で確かめる。外れた前提が 2 つあった

キーには TanStack Hotkeys（ショートカットキーのライブラリ）を使った。前の日の調査の記録には、「`=` の登録は、US 配列の `+`（`Shift`＋`=`）でも、`code` からの拾い直しで発火する」と書いていた（[ショートカットキーの一覧](./2026-10-07.md#hotkeys-list)の 2 節）。キーでの移動のチケット（#312）の計画は、これを根拠にした。計画を立てた作業場所には `node_modules` が無く、dist を読めなかったからだ。計画にも「dist は未確認」と書かれていた。

実装の途中で dist（`_match.js`）を読んだレビュー役が、これは誤りだと指摘した。`code` からの拾い直しは、修飾キーが登録と一致するときにしか試されない。`+` は `Shift` を押しているので、`Shift` なしの `=` の登録とは一致しない。実装役は `Shift+=` の登録を足した。そのとき「`=` の登録と二重に発火する」と考え、`Shift+=` の処理の中で `e.key === "="` なら何もしないようにした。

これが 2 つ目の誤りだった。JIS 配列で `Shift`＋`-` を押すと、`key` が `=` で `Shift` 付きのイベントになる。ライブラリはこれを、`=` の登録には点数 2、`Shift+=` の登録には点数 3 で一致させる。そして、点数がいちばん高い 1 件だけを実行する（`hotkey-manager.js`）。選ばれた `Shift+=` の処理が何もせずに戻るので、拡大が効かなかった。最初のレビューで 2 人がこれを指摘し、その分岐を消した。

人が議題を開閉する `Enter`（#320）でも、同じ形で前提が外れた。ライブラリは既定で、コールバックを呼ぶ**前に** `preventDefault()` を呼ぶ。入力欄を除外する既定はあるが、除外されるのは `input`・`textarea`・`select`・contentEditable だけで、`button` は入らない。そのため、見返しの再生ボタンにフォーカスして `Enter` を押しても、ボタンが押されなくなっていた。コールバックの中で早めに戻っても、取り消しはもう済んでいる。登録に `{ preventDefault: false }` を渡し、フォーカスのある要素を見て、マップの開閉に使うときだけ自分で `preventDefault()` を呼ぶ形にした。計画では、これは「参考（要件にはしない）」として持ち越していた。

**前の調査の記録は、書いた時点の仮説として読む。** 実装の前に、入れた版の dist で「何を一致とみなすか」「一致が複数あったらどれを実行するか」「既定の取り消しがコールバックの前か後か」を確かめる。計画を立てる場所に依存が入っていないなら、その確認を計画の最初の作業にする。

### 4. DOM の無いテストでは、判断を純粋な関数に寄せ、残りは「登録を記録する置き換え」と provider で観測する

web の vitest は DOM を持たない（jsdom も testing-library も入れていない）。そこで、判断はできるだけ純粋な関数に置いた。reducer のテストは、出来事の列を流して、指示の列と最後の状態を並べて比べる。最後のチケットの時点で `viewing.test.ts` は 2,162 行、テストは 222 件になった。カメラの計算（全体を収める箱、選んだノードを最小限ずらす量、縁の点の位置）も、`camera.ts` の純粋な関数として値で確かめた。

React の部品の中にしか無いものは、次の 3 つのやり方で観測した。

- 日本語入力のキーを送り直す層（#313）: `react` の `useEffect` を「その場で実行する」置き換えにし、`window` と `KeyboardEvent` を最小の代役にした。登録された監視に偽のイベントを渡し、止めたか、何を送り直したかを見る
- `Enter` の登録（#320）: `useHotkey` を「登録を記録するだけ」の置き換えにして、画面全体を `renderToStaticMarkup` で一度描く。記録された `Enter` のコールバックに、ボタンの中か外かを `closest` で答える偽の要素を渡し、reducer に `enter` の出来事が届くかを見る
- まとめを開いた後に位置を保つ基準のノード（#321）: `MapView` の中に書いていた置き換えを、純粋な関数 `keepTargetOf` に切り出して、開く前と後を値で比べた

判断が外れた場面もある。矢印での選択（#318）で、実装役は選んだノードの見た目を `renderToStaticMarkup` で確かめず、部品を関数として呼んで class を見た。理由は「React Flow の provider が無いと描画できない」で、既存のテストも同じ理由で関数として呼んでいた。レビュアー 3 人がこれを差し戻した。インストール済みのライブラリには `ReactFlowProvider` がある。包んで描くと、例外なく描けた。既存のテストの先例が、確かめていない前提をそのまま次に渡していた。

**「この環境では描けない・動かせない」は、試してから書く。** 試すと 1 行で済むことがある。描けないものは、判断を純粋な関数に出すか、外との境目（キーの登録・`useEffect`）を記録する置き換えにして観測する。

### 5. テストに映らない effect の誤りは、依存の参照が何で変わるかを読むレビューでしか捕まらない

右の列を出し入れする `E`（#317）では、「列の出し入れだけでは見る位置を変えない」と決めていた。実装は、自動のカメラに寄せ直させる番号（`refitSeq`）を `E` では進めないようにした。テストは 519 件すべて通った。

それでも、最初のレビューで 2 人が同じ欠陥を見つけた。自動のカメラの effect は、依存に `nodes` を持っていた。`nodes` は、補間アニメーション中の位置から `useMemo` で作る。その位置は、表示済みのノードが 1 つでもあると、描画のたびに新しいオブジェクトで返ってくる。`E` で描き直すだけで `nodes` の参照が変わり、effect が走り直して、今の議題へ寄せ直していた。番号を据え置いた意図は、この依存で無効になっていた。直し方は、依存から `nodes` を外し、議題が無いときだけ位置を値で比べて追うことだった。

テスト担当のレビュアーは、`MapView` を実際に動かす結合テストを求めた。これは裁定で却下した。DOM の環境が無く、足すには新しい依存が要るからだ。直した後の確認も、コードを追うことしかできなかった。手での確認はマージ後に人が行うと、本文に書いてあった。

キーでの移動（#312）にも、似た見落としがあった。人が縮められるのは 0.5 倍までだが、全体を見る `F` の間だけ下限を 0.02 倍に下げる。実装は、`F` の後に `Shift`＋矢印で人の状態へ移るときだけ、倍率を 0.5 倍に戻していた。ドラッグやスクロールで移る経路が抜けていた。React Flow の `setViewport` は `minZoom` で切られず、`setMinZoom` も今の倍率を直さない。そのため、0.5 倍未満のまま人の状態に残っていた。

**effect の依存を書き換えたら、依存の 1 つずつに「何がこの参照を変えるか」を書き出す。** 倍率の範囲のような不変条件は、状態が変わる入口のすべてで収め直す。キーで直したら、ポインターの経路も同じ表に並べる。

### 6. 同じ見せ方を 2 か所で計算するなら、入力を省略できない引数にして揃える

畳む見せ方の関数 `foldView` は、マップの描画と、右の列の根拠の取得の両方から呼ばれる。根拠の取得は、表示中の木を持たず、スナップショットから見せ方を計算し直して、選んだノードを探す。

#319 で、マップは選んだノードを `foldView` に渡すようになった。ところが根拠の取得は、選択なし（`null`）で計算し続けていた。5 件の済んだ議題が並ぶまとめで、真ん中の議題を選ぶと、前の 2 件と後ろの 2 件が別々の「議題 2 件」に分かれる。矢印で後ろのまとめに移ると、マップには見えているのに、根拠の側では 5 件の 1 つのまとめのままだった。右の列には「選んだノードは今のマップにありません」と出た。同じレビューで、もう 1 つ見つかった。まとめの ID（`run:` ＋最初の議題の ID）はスナップショットに無い。そのため、まとめを選ぶと祖先を守る処理が働かず、選んだまとめごと畳まれて消えていた。

次の 2 件は、これを型で防いだ。#320 は人が畳んだ集合を、#321 はまとめを解いた集合を、`foldView` と根拠の取得の両方に、省略できない引数として足した。#321 の決定ログには、「既定値を置くと、呼び出し元で渡し忘れても型検査で見つからない」とある。それでも、同じ型の集合を並べた引数は取り違えやすい。#320 のテストの道具は、人が畳んだ集合を「開く集合」の位置に渡していた。修正の確認役が見つけた。

#320 では、規則を足したことで、別の場所の前提も崩れた。「人が畳んだものは、選んだノードの祖先を守ることより優先する」と決めた。その結果、選んだノードが隠れることがありうるようになった。ところが、選んだノードが削除・統合されたときに選択を移す処理は、見えているノードしか見ていなかった。隠れた選択は移らず、消えたノードを指したまま残っていた。

**同じ計算を 2 か所でするなら、入力の追加を必須の引数にして、片方への渡し忘れを型で止める。** 「A は B より優先する」という規則を足したら、B が保証していた性質（ここでは「選んだノードは見えている」）に頼っている場所を探す。

### 7. レビューの裁定は、元の要求に無い検証手段や作りの指摘を落とす。落とした指摘のうち、人に聞くべきものは別に残す

11 件とも、最初のレビューでは誰か 1 人以上が差し戻した。takt のレビューには、レビュアーたちの指摘を元の要求と照らして「直す・直さない」を決める裁定の段がある。直すと決めた 10 件は、修正の後の 2 回目のレビューで全員が通した。残る 1 件（#316）は、唯一の指摘を裁定で落とし、修正なしで通った。

直したものの多くは、テストが観測できる値ではなく作りを固定していた指摘だった。結果が別のオブジェクトであること（`not.toBe`）を確かめるテスト（#316・#318）、タグ名とボタンの数を固定するテスト（#320）、案内文の全文一致（#311）だ。ほかに、直下の関数名を言い換えるだけのコメント（#313・#321）、呼び出し元が保証している条件への `?? []`（#321）もあった。

落としたのは、元の要求に無い検証手段や作りを求める指摘だった。`MapView` を動かす結合テスト（#311・#317。DOM の環境を足す必要がある）、縁の点のボタンの名前に移動先のノードの本文を入れること（#316）がそうだ。開閉の丸を `<span role="button">` から本物のボタンにして、Tab で届くようにすること（#320・#321）も落とした。

最後の 1 つは、2 回とも同じ理由で落とした。キーでは矢印で選んで `Enter` を押せば同じ開閉ができ、丸へのキー操作は要求に書かれていない、という理由だ。要求に照らした判断としては筋が通る。裁定も「必要なら別の課題にする」と書いていた。ただ、別の課題は作られず、「丸に Tab で届かなくてよいか」は、誰も利用者に聞いていない。裁定は要求の範囲を守る役なので、要求そのものが足りないかもしれない、という問いは拾わない。

逆の失敗も 1 つあった。#311 の実装役は、決定ログに「ボタンの外へ出てから戻して離すと、ドラッグの判定を抜ける。実害は小さい」と書いて残した。最初のレビューで 2 人がその穴を指摘し、差し戻しになった。直すのはポインターを固定する 1 行だった。

**裁定が「範囲外」として落とした指摘は、要求の外にある問いとして並べ、人に渡す。** 自分で穴を認めて残すときは、その場で塞ぐ手間と比べる。決定ログに書いた穴は、レビュアーも読む。

### 1. 同じファイルを触る並行のチケットには「先に main に入った名前を使う」と書く。それでも改名とファイル末尾の追記はぶつかるので、rebase の後は型検査とテストを回し直す

見返しのチケットは、`SessionView.tsx`（ライブと見返しが共有する画面）、`viewing.ts`（見る状態の reducer）、`ReviewControls.tsx`（操作の行）を何枚もが触る。そこで各チケットの本文に「作業の途中で main が変わっていたら、その時点の main の形に合わせる。先に main に入った出来事・指示・状態・props の名前や型はそのまま使い、別の名前で作り直さない」と書き、触るファイルと、同じファイルを触る他のチケットの番号を並べた。#341 のように「#337 のキーが main にあれば、それも同じに数える」と、相手の有無で振る舞いを分ける書き方もした（積む前に本文を今の main に合わせる手順は、[takt を回した側のエントリ](#takt-ops-day) の 3 節）。

それでもカメラの自動復帰（#338）は、PR を出した時点で main とぶつかった。同じ時間帯に、画面を人が動かす操作の側のキー一覧のチケット（#315）がマージされていたからだ。手で rebase したとき、2 つの壊れ方が出た。

- #338 は `SessionView.tsx` の中の関数 `keyTree` を、用途が広がったので `treeNow` に改名していた。#315 は、同じ `keyTree()` を呼ぶ行を新しく足していた。テキストとしては衝突せず、rebase は通るが、`keyTree` はもう無い。呼び出しを `treeNow()` に直して amend した。
- `viewing.test.ts` の末尾には、両方が `describe` の塊を足していた。衝突の両側をつなげたとき、片側の閉じの `});` と `});` が抜け、次の `describe` が前の塊の中に入った。これも amend で足した。

どちらも、rebase の成否では分からず、型検査とテストで分かる壊れ方だ。並行の変更を rebase したら、衝突の無かった所も含めて型検査とテストを回し直してから push する。本文の「先に入った名前を使う」は、まだ main に無い名前（このときの改名）には効かない。

### 2. 同じ更新の中で出来事が 2 つ続くと、まだ描画されていない指示を後の指示が上書きする。指示に通し番号を付け、描画済みの番号と比べる

#338 は、見返しで人が画面を動かした後、「触らずに 10 秒たつ」か「時刻を動かす（▶・シーク・コマ送り）」の早い方で、自動のカメラに戻す変更だ。reducer に `idle` と `timeMoved` の 2 つの出来事を足し、それぞれは単独のテストで通った。

フロントエンドのレビューが、出来事が続いたときの穴を指摘した。シークすると、子の `MapView` が新しい時点のマップを受けて `reflect`（反映が来た）を送り、親の `SessionView` が `timeMoved` を送る。React では子の effect が親の effect より先に走る。`reflect` で議題が変わると、状態は自動に戻り、カメラへの指示は `refocus`（今の議題へ寄せ直す）になる。続く `timeMoved` は、もう自動の状態で受けるので、指示は `follow`（何もしない）になり、まだマップが受け取っていない `refocus` を上書きする。レビュアーが挙げた失敗の条件は、反映 1 で議題 A、反映 2 は変化なし、反映 3 で議題 B のログで、反映 3 で人の状態に入ってから反映 2 へシークする場合だ。カメラは議題 A に寄らない。

直し方は、カメラへの指示を `{ command, seq }` の組にし、マップが最後に受け取った番号を持たせることにした。`nextCameraOrder` は、今の指示が `refocus` で、まだ描画されていない（番号が描画済みの番号と違う）なら、後から来た `follow` で上書きしない。テストには、2 つの出来事を両方の順で続けて流す場合と、描画の後は上書きされる場合を足した。reducer のテストを出来事 1 つずつ書いていると、この種の穴は見えない。出来事が同じ更新で続く経路を数え、続けて流すテストを置く。

### 3. 背景のタブでは requestAnimationFrame が止まる。「終わりで止める」判定を rAF だけに載せない

音声つきの版（#341）では、時刻の元を `<audio>` の `currentTime` だけにする（前の日に決めた）。表示を滑らかにするため、`currentTime` は `requestAnimationFrame` ごとに読む（`timeupdate` は間隔が粗い）。録音が会議より長いときは、会議の長さで止める。

フロントエンドのレビューは、止める判定の入口が rAF しか無いことを指摘した。背景のタブでは rAF が呼ばれない。会議 100 秒・録音 130 秒で、再生中に別のタブへ移ると、会議の終わりを越えて録音の終わりまで鳴り続ける。`<audio>` の `ended` は録音そのものの終わりでしか来ない。直し方は、`timeupdate` でも同じ `currentTime` を同じ口に通知することにした。前面では rAF が滑らかさを受け持ち、背景では粗い `timeupdate` が止める判定だけを受け持つ。時計を 2 つ持たないという決定は崩さずに済んだ。

### 4. エンコーダは単純な入力には目標より少ないビットしか使わない。ビットレートを確かめるテストには雑音を入れる

ヘルパーの `mix`（#339）は、相手と自分の録音を 0 秒の位置から重ね、AAC 16 kbps・モノラルの m4a を 1 本書く。ffmpeg は使わず AVFoundation の `AVAssetWriter` で書き、`canApply(outputSettings:)` で設定が受け付けられるかを確かめてから書く。

計画のテストは「出力のビットレートが 12〜20 kbps」だった。テスト用の録音を 440 Hz の純音で作ったところ、出力は約 10.3 kbps になった。エンコーダは、純音なら目標より少ないビットで足りるからだ。実装の欠陥ではないので、テストを 2 つに分けた。純音のテストは下限を 8 kbps に緩め、上限 20 kbps で「入力の 64 kbps のまま書いてしまう」実装を落とす。雑音を入れた録音のテストで、12〜20 kbps に入ること、つまり 16 kbps の指定が効いていることを確かめる。目標値を確かめるテストは、エンコーダが目標まで使い切る入力で書く。

### 5. 1 ファイルの HTML にまとめるビルドは、プラグインの組み合わせで黙って中身が欠ける。本物のビルドを走らせ、出力を開いて確かめる

`map.html` は、web の画面を Vite でビルドし、`vite-plugin-singlefile` で JS と CSS を 1 つの HTML にインライン化して作る。書き出すたびに一時フォルダへビルドし、会議のログを `<script type="application/json">` で埋め込む。偽のビルドを使うテストとは別に、本物の Vite でビルドし、Chromium で `file://` から開いて最後のマップが出るかを見るテストを 1 本置いた。この 1 本が、3 つの穴を見つけた。

- **HTML 全体への正規表現が、インライン化したコードの中の文字列に当たった**（#331）。「外部の CSS を読みにいかない」ことを確かめる正規表現が、インライン化した React の開発版のコードに含まれる `<link rel="stylesheet"` という文字列に当たって落ちた。1 ファイルにまとめた HTML では、`<script>` と `<style>` の中身はただの文字列なので、それを除いてから検査するように直した。
- **ライセンスの一覧が 1 行になった**（#332）。同梱したライブラリのライセンス文を残すため、Vite の `build.license: true` を有効にした。出てきた `.vite/license.md` は「The app does not bundle any dependencies」の 1 行だけだった。single-file のプラグインが、インライン化した後の chunk を bundle から消すので、Vite が同梱したモジュールを集められなかった。`viteSingleFile({ deleteInlinedFiles: false })` にして直した。エラーも警告も出ないので、出力の中身を見ないと気づけない。
- **中断されると、ビルドが終わる前に一時フォルダが消える**（#331、設計のレビュー）。ビルドは Effect の `acquireRelease`（取得と解放を対にする仕組み）で一時フォルダを作り、終われば消す。Vite の `build()` は中断の合図を受けないので、`play` が Ctrl-C で中断されると、解放の `rm` が、まだビルドが書いている出力先を先に消す。ビルドの区間を `Effect.uninterruptible` にして、終わるまで中断を待たせた。

### 6. 位置を自分で計算する部品は、CSS では動かせない。計画で CSS を書く前に、部品の実装を読む

議題で区切ったシークバー（#335）では、ポインタの位置に吹き出しを出す。シークバーは前の日に決めた Video.js 10 の部品（`@videojs/react`）で、計画は吹き出しの CSS に `left: var(--media-slider-pointer)` と `transform: translateX(-50%)` を書く方針だった。

実装の担当が、書く前に `@videojs/react` 10.0.1 の中を読んだ。`Slider.Preview` は、`position`・`left`・`width` をインラインの style で付けていた。`left` はポインタを中心にし、両端では内側に収める式だ。インラインの `left` は CSS より強いので、計画の CSS は効かない。`translateX(-50%)` を足せば、部品が中心に合わせた位置から、さらに半分ずれる。CSS には `bottom: 100%` と見た目だけを書き、横の位置は部品に任せた。端での見切れも部品が防ぐ。

同じ日、キーのチケット（#337）では、操作の行のツールチップを一律に `right: 0` で揃えていた。いちばん左の「反映 1 つ戻る」は左端から 12px しか離れておらず、名前の大部分が画面の左外に出ると、レビューで指摘された。既定を `left: 0` にし、右端のグループ（字幕・速さ・右の列）だけ `right: 0` に上書きした。どちらも、DOM を持たないテストでは見えない位置の問題で、最後は人が `map.html` を開いて確かめる項目に回した。

### 7. DOM の無いテスト環境では、開いたときにだけ描かれる分岐を純粋な関数に出す

web のテスト（vitest）は DOM を持たず、部品は `renderToStaticMarkup` で静的に描いて確かめる。最初の部品の切り出し（#330）で、すでにこれにぶつかった。実装の途中で、テストの指摘役が「クリックで選んだノードが、マップが更新されても選ばれたままか」のテストを求めた。静的な描画では確かめられず、`useState` をモックすれば確かめたい配線そのものを迂回する。計画を立て直し、テストの基盤を足すのは範囲外と明記した。速さのメニューの項目は、開いたときにだけ描かれる。音声つきの版（#342）で、項目の文言を「音声つきは倍率だけ（`0.5 倍`）、音声なしは所要時間つき（`60 倍（161 分を 2.7 分で）`）」と分けたとき、この分岐は静的な描画では観測できなかった。

DOM のテストを新しく入れるのは範囲を超えるので、文言を決める分岐を `rateItemLabel` という純粋な関数に出して export し、両方の文言をテストで固定した。メニューに正しいモードを渡しているかの 1 行は、テストのためだけに本番の部品へ prop を足すことになるので、自動のテストにはせず、人が確かめる手順に書いた。前の #336 では、同じ所の文言の関数を、DOM の無い環境で読み込めるか分からないとして単体テストにせず、node で式を実行して値を確かめるだけにしていた。#342 で関数を切り出したことで、そこも固定された。

### 8. レビューの指摘は、仕様の文言で裁く。却下や持ち越しの理由を残しておくと、後のチケットで拾える

takt のレビューは、複数のレビュアー（AI らしさ・設計・テスト・フロントエンド・バックエンド・セキュリティ）の指摘を、裁定の役が「直す・直さない」に振り分ける。今回、直さない側に回った指摘が多く、その理由がどれも仕様の文言に結びついていた。

- **参照が同じかを確かめるテストは、内部の固定ではなく契約だった**（#334）。時刻 t のマップを返す関数は、同じ反映の区間の t には同じオブジェクトを返す。テストは `toBe` でそれを確かめている。テストのレビュアーは「同じ内容を別のオブジェクトで返す正しい実装でも落ちる、内部の固定だ」と削除を求めた。実装の担当は残した。マップの部品は `snapshot.nodes` の参照が変わるたびに補間とカメラの寄せ直しをやり直すので、▶ の再生中に毎フレーム新しいオブジェクトを渡すと、マップが落ち着かない。計画の要件にも「`toBe` で確かめる」と書いてあった。参照の同一性に依存する利用側があるなら、`toBe` のテストは契約の証拠になる。
- **「バーの上の点」は、バーより上にも、バーに重ねてにも読める**（#335）。決定・TODO の点が、シークバーの中央に重なっていると、設計とフロントエンドの 2 人が指摘した。裁定は、仕様が縦の位置を決めていないとして直さなかった。競合する読みを推測で選ばず、見た目はマージ後に人が確かめることにした。
- **メニューの矢印キーでの移動や、開いた直後のフォーカス**（#336）は、仕様に無いとして「言い過ぎ」に分類した。
- **セッション終了時の書き出しが、サーバーの終了処理とつながらない独立した Promise で走る**（#341、バックエンドのレビュー）は、仕様が決めた形と既存の書き出しの形から来る問題として、範囲外で持ち越した。

直す側に回った指摘で中身があったのは、上の節で書いたもののほか、`review` の「失敗したら標準エラーに 1 行」の約束が、改行を含むパスを表示に埋め込むと 2 行になる、という指摘（#333）だった。利用者の入力を埋め込む表示の出口で改行を潰した。残りの多くは、処理をそのまま言い換えたコメント（#334 で 4 行、#342 で 2 か所）と、届かない代替値（#335 の `?? ""`。`noUncheckedIndexedAccess` で型を絞るために書いたもの）だった。実装のエージェントはこのどちらかを書きがちで、レビューの往復の多くはここに使われた。

### 9. 実装の外の失敗は、ワークフローの外で拾う

takt の run の外で、3 つの失敗があった。

- **作業場所が古い main から切られた。** `map.html` の書き出し（#331）は、依存する部品の切り出し（#330）がマージされた 2 分後に積んだのに、#330 を含まない手元の main から切られた。実装の前に早送りして間に合ったが、レビューに渡る差分には #330 の 3 ファイルが毎回入った。原因と、以後の手順は [takt を回した側のエントリ](#takt-ops-day) の 2 節に書いた。
- **本物のビルドのテストが、ブラウザの無い CI のジョブで落ちた。** #331 のテスト（`reviewBuild.test.ts`）は、実物の Vite で 1 ファイルの HTML を作り、Chromium で `file://` から開いて最後のマップが出るかを見る。手元では通ったが、CI ではサーバーのテストを「Chromium を入れるジョブ（撮影のテスト用）」と「入れないジョブ」に分けており、新しいテストは入れない側で走って落ちた。`.github/workflows/check.yml` で、撮影のジョブの対象に足し、もう片方の除外に足した。ブラウザを起動するテストを足すときは、CI のどのジョブで走るかを一緒に決める。
- **PR の作成が、push の 500 で落ちた。** #336 は実装もレビューも終わった後、`git push` が GitHub の `Internal Server Error` で拒否され、takt のタスクが `pr_failed` で止まった。作業場所のブランチにはコミットが残っているので、push と PR の作成だけを手でやり直した（[takt を回した側のエントリ](#takt-ops-day) の 6 節）。takt の外で作った PR は、タイトルの形がほかと違う（`feat: …（issue #336）`）。

### その後

#341 で持ち越した「セッション終了時の書き出しが独立した Promise で走る」は、翌日、Effect（サーバーが使う関数型の効果ライブラリ）の使い方の点検で「直すべき」に入り、[#436](https://github.com/daiki-beppu/live-mindmap/issues/436) で書き出しを Effect のまま流し、サーバーの入口以外の `Effect.runPromise` をなくした。見返しの書き出しのファイル操作も、その前に Effect の FileSystem に移した。そのときも、ビルドの区間の `Effect.uninterruptible` は残っている。#338 で足したカメラの指示の通し番号と `scope` の引数は、その後の、画面を人が動かす操作のチケット（議題の開閉など）で reducer が広がった今も、同じ形で残っている。

## Bluetooth のイヤホンで「構成の変化」が続いて取り込みが止まる件を、専用の終了コードと別の歯止めで直した話

ヘルパー（会議の音を取り、文字にしてサーバーへ送る Swift の常駐プログラム。サーバーが子プロセスとして起動する）は、前日の修正で、入力の機器が変わったら止まり、サーバーの起動し直しに任せるようになっていた。マージ後に実機で確かめると、AirPods をつないで耳に着けるあいだに、マイクの「構成の変化」の通知が短い間に何度も届いた。そのたびにヘルパーが終わり、サーバーは「60 秒以内に 3 回続けて終わったら諦める」という上限に当たって、取り込みを「止まった」にした。利用者が手で再開するまで、自分・相手の両方の字幕が止まる。直し方の候補を実機の記録と照らして比べ、方針と細部を issue の本文に書いてから、AI エージェントのワークフロー実行ツール takt に実装させた。takt は 32 分で、レビューの差し戻しなしに通った。

- 決定の記録: [Bluetooth のイヤホンをつなぐと構成の変化が続けて届き、起動し直しを諦めて取り込みが止まる](https://github.com/daiki-beppu/live-mindmap/issues/396)（実装は [PR #454](https://github.com/daiki-beppu/live-mindmap/pull/454)）、前段の [入力の機器を切り替えると、自分のマイクの取り込みが黙って止まる](https://github.com/daiki-beppu/live-mindmap/issues/232)
- 前段の判断: [ヘルパーを止めて起動し直しに任せると決めたトリアージ](./2026-10-07.md#triage-helper-stops)、[起動し直しと 60 秒・3 回の上限を入れた話](./2026-10-06.md#helper-restart)

実機の記録は次のとおりだった。

| 場面 | 届いた通知 |
|---|---|
| 内蔵マイク → AirPods の切り替え 1 回 | 1 回。0.2 秒後に起動し直し、自分の字幕は戻った |
| AirPods の接続と、サウンド設定の入力音量の調整 | 18 秒の間に 4 回。各起動は 2〜9 秒で終わり、4 回目で諦めて「止まった」 |
| AirPods を耳に着けた・入力音量のスライダーを動かした | 1 回ずつ（スライダーは、もう 1 回動かしたときは届かなかった） |
| 何も触らない 3 分 35 秒・11 分・29 分 | 0 回 |

### 1. 性質の違う終わり方を、同じ失敗の数に混ぜない。理由ごとに別の数え方と歯止めを持つ

60 秒・3 回の上限は、「壊れてすぐ落ちる」ヘルパーを起動し直し続けないための歯止めだ。構成の変化による終了は、ヘルパーが壊れたのではなく、外の機器が変わったという出来事で、起動し直せば新しい機器で取り込める。これを同じ数に入れていたので、正常な出来事が 4 回続いただけで、壊れたときと同じ扱いになった。

上限を 3 回から増やす手は取らなかった。壊れて落ちる場合の検出が、その分だけ遅れるからだ。代わりに、構成の変化による終了は失敗の数（`failures`）に数えず、別に「60 秒の間に 10 回を超えたら諦める」という歯止めを持たせた。観測した最大の連続（18 秒に 4 回）の倍以上の余裕を取りつつ、通知が止まらずに起動し直しを繰り返す場合は止まる。

2 つの数が干渉しないことも、本文で決めた。構成の変化の回は、`failures` を増やさず、0 にも戻さない。壊れて落ちる回の連続を、構成の変化で帳消しにも水増しにもしないためだ。テストでは、「1 → 75 → 1 → 75 → 1」（1 は壊れた終了、75 は構成の変化）の順に終わると、5 回目（壊れた終了の 3 回目）で諦め、理由が `failures` になることを確かめた。諦めたときのログにも理由（`failures` か `configuration-changes`）を残し、後から数えられるようにした。

**1 つの上限に当たったとき、「上限を上げる」前に、数えている中身が 1 種類かを見る。** 中身が 2 種類なら、それぞれに数え方と歯止めを持たせる。

### 2. 「まとめてから起動し直す」案は、実測の間隔で外れる

候補はほかに 2 つあった。

- **まとめてから起動し直す**: 通知を受けたら 1〜2 秒待ち、続く通知を 1 回にまとめてから終わる。ところが、実測の通知の間隔は 2〜9 秒だった。1〜2 秒の待ちではまとめきれない。9 秒を超えて待てば、いちばん多い「切り替え 1 回」の場面で、0.2 秒で戻っていた字幕が 9 秒以上止まる
- **ヘルパーの中で作り直す**: ヘルパーを終わらせずに、音声のエンジンを作り直す。前段のトリアージで、録音ファイルの形式やエコーキャンセルの参照が開始時の機器に依存していると分かり、作り直しはプロセスごと起動し直す経路に任せると決めていた。これを覆す新しい事実はなかった

**待ってまとめる案は、待ち時間を実測の間隔と、いちばん多い場面の戻りの速さの両方に当てて決める。** 両方を満たす値が無ければ、まとめずに数え方を変える。

### 3. 見分ける印は、既に境界を素通りしている値から選ぶ

サーバーが「構成の変化による終了」を見分ける印の候補は、標準エラーの文面、専用の終了コード、ヘルパーから送るイベントの 3 つだった。

- 標準エラーの文面は、サーバーが末尾 5 行だけを受け取る。文言を直すと、見分けが黙って壊れる
- イベントは、ヘルパーとサーバーの間の取り決めを増やす。終わる直前に送るので、届く前に接続が切れる場合も考えることになる
- 終了コードは、ヘルパーの `exit(...)` から、サーバーで子プロセスを起動する層（`helpers.ts`）を、数のまま素通りして判断の関数まで届いていた。サーバーの起動の層は変えなくてよい

値は 75 にした。BSD の `sysexits.h` の `EX_TEMPFAIL`（一時的な失敗。やり直すよう促す）で、「起動し直せば取り込める」という意味に合う。ヘルパーの今の終了コード（0・1・2）とも、シェルが使う 126・127 とも、シグナルによる 128+n とも被らない。Swift の実行時のクラッシュはシグナルで終わり、サーバーでは `code: null` になるので、これとも被らない。念のため、判断の側は「コードが 75 で、かつシグナルが無い」ときだけ構成の変化と見なす。

**新しい区別を足すときは、既に境界を通っている値で表せないかを先に見る。** 通っている値なら、間の層を変えずに済む。

### 4. 言語をまたぐ定数は、両側のテストで同じ値に固定する

75 は、Swift のヘルパー（`microphoneConfigurationChangedExitCode`）と、TypeScript のサーバー（`HELPER_EXIT_CONFIGURATION_CHANGED`）の両方に定数として置いた。2 つの言語をまたいで、同じ値かを機械的に照合する仕組みは無い。そこで、両側のテストで値 75 を固定し、どちらのコメントにも「もう片方と合わせる」と書いた。片方だけを変えると、変えた側のテストが落ちる。

takt の実装の報告も、この点を「未確認の範囲」に挙げ、代わりの検証として両側のテストを示していた。本物のヘルパーの `exit(75)` がサーバーに届くまでを通すテストは足していない。終了コードを数のまま渡すことは、既存の「予期せぬ終了」のテストが code 1 で確かめているからだ。

**1 つの値を 2 つの言語で持つときは、照合の仕組みを作るより先に、両側のテストで値を固定する。** 安く、片方だけの変更を確実に止められる。

### 5. 名前・境界・テストの台本まで本文に書いた issue は、takt を 32 分で、差し戻しなしに通った

takt に渡す前に、issue の本文に「確定した細部」の節を足した。方針、終了コードの受け渡しの経路（今のコードの関数名と型の名前で）、判断の規則と窓の境界（ちょうど 60 000 ms 前は窓の中）、テストを書くファイルと場面、書き直す説明、そして「受け入れ条件の実機の確認はマージ後に人が行い、takt の条件に含めない」を書いた。

| 工程 | 時間 |
|---|---|
| 計画 | 2 分 24 秒 |
| テストを書く | 6 分 38 秒 |
| 実装 | 4 分 33 秒 |
| 実装のやり直し（次節） | 20 秒 |
| 観点別のレビュー 3 つ（並行） | 3 分 50 秒 |
| 指摘の裁定 | 1 分 26 秒 |
| 最終の判定 | 3 分 14 秒 |
| 全体（工程の間の待ちを含む） | 32 分 |

レビューは 3 つとも 1 回目で APPROVE で、裁定が採った指摘は 0 件、修正の工程は 1 回も回らなかった。変えたのは 10 ファイル・543 行の追加で、うち 403 行がサーバーのテストだった。

2 日前の起動し直しの実装（[#161](./2026-10-06.md#helper-restart)）は 6 時間 50 分かかり、計画だけで 27 分、レビューと修正が 4 周した。あちらはサーバー・ヘルパー・画面の 3 か所にまたがり、規模が違うので、同じ物差しでは比べられない。それでも、計画の工程が 27 分から 2 分半になったのは、要件を探す仕事が本文の側で済んでいたからだ。

**エージェントに渡す本文には、決めたことだけでなく、今のコードの名前と、確かめ方まで書く。** 計画とレビューの工程が、探すことではなく照らすことになる。

### 6. 「確かめるだけ」の項目も完了の約束になる。読み直さないと、実装の工程がもう一度回る

本文には「エラーが途中の段で別のエラーに置き換わっていないことを確かめる」と書いていた。マイクのエラーが、エコーキャンセル・録音・文字起こし・送り出しの段を通るうちに別のエラーに包まれると、終了コードは 75 ではなく 1 になる。計画の工程は、該当の箇所を読んで「変更不要（確認だけ）」と記録した。

ところが、実装の工程の報告では、この項目が「未完了」になった。実装の工程が、対象のファイルを自分で読み直していなかったからだ。takt は、計画が立てた約束の一覧を 1 つずつ実装の報告で埋めさせ、埋まっていない項目があると実装をやり直させる。やり直しの工程は、各段の `catch` を `grep` で並べて読み直し、どれも受け取ったエラーをそのまま流していると確かめただけで、コードは変えずに終わった。前の工程の「確認済み」の記録をそのまま信用する選択肢は、それでは今回の確認にならないとして、やり直しの工程自身が退けていた。

ロスは 5 分ほどだった。**「変更なし、確認だけ」の項目は、本文で「どのファイルの何を読めば確認になるか」まで書いておく。** 計画と実装の工程が同じ確認を 2 回することになっても、約束の一覧が埋まる。

この記録の時点で、マージ後の実機の確認（AirPods をつないで耳に着けても、取り込みが止まらない）は、まだ issue に記録が無い。

## takt を並列 3 で半日回して 45 件を通し、積む前と通った後に人がやることを決めた話

2026-10-07 の夜から 10-08 の昼まで（日本時間で約 15 時間）、AI エージェントのワークフロー実行ツール takt に、issue を次々に積んで実装させた。takt は、1 件の issue を、計画 → テストを書く → 実装 → 観点別のレビュー → 指摘の裁定 → 修正 → 最終の判定の工程に分け、工程ごとに別のエージェントに受け持たせる。1 件ごとにリポジトリの clone（作業場所）を作り、通れば PR を作る。この間に 50 件を始め（2 件はこの記録の時点でまだ実行中）、45 件が通り、takt のブランチの PR が 48 本マージされた。止まった 3 件は、clone に残った作業を人が引き取って PR にした。回す側（人と、それを手伝うエージェント）がやったことと、そこで分かったことをまとめる。

- 決定の記録（回した issue の主な束）: [画面を人が動かす操作の実装](https://github.com/daiki-beppu/live-mindmap/issues/310)、[見返しの実装](https://github.com/daiki-beppu/live-mindmap/issues/328)、[共有画面を発言の文脈として使う実装](https://github.com/daiki-beppu/live-mindmap/issues/273)、[サーバーを Effect 4 へ置き換える実装](https://github.com/daiki-beppu/live-mindmap/issues/237)
- 前に、外から止められた run を積み直した話: [2026-10-02 のエントリ](./2026-10-02.md#takt-interrupted-requeue)

### 1. 並列の数は、マシンのメモリで決めて 3 にした

takt は既定では 1 件ずつ直列に回している。2026-10-01 に 5 件を並列で回したとき、レビューを受け持つ Codex の利用上限に当たり 4 件が失敗し、進み具合を見る `gh` の呼び出しも重なって GitHub の API の上限にも当たったからだ。今回は、触るファイルが重ならない issue だけを並べる前提で、並列の数を一時的に上げた（設定ファイルは変えず、`TAKT_CONCURRENCY=3 takt watch` で起動）。

4 にはしなかった。マシンのメモリは 16GB で、1 件ごとに Node と Swift のビルド・テスト、複数のエージェントが動く。3 件で動かしているときのメモリの使われ方を見て、4 件目を足す余裕は無いと判断した。

結果は、`tasks.yaml` の開始・終了の時刻から次のとおりだった。

| 同時に動いていた数 | 時間 |
|---|---|
| 3 | 7.3 時間 |
| 2 | 6.2 時間 |
| 1 | 1.6 時間 |

通った 45 件の 1 件あたりの時間は、中央値 44 分（11〜147 分）、合計 33.6 時間だった。並列 3 でも、3 件が同時に動いていたのは半分ほどにとどまる。5 節のとおり、同じファイルを触る issue を直列にしたので、並べられる issue が尽きる時間があったからだ。

**並列の数は、外の API の上限と、手元のマシンの資源の両方を見て、小さいほうで決める。** 上げても、並べられる issue が無ければ埋まらない。

### 2. takt の作業場所は手元の main から切られる。積む前に手元の main を最新にする

takt の clone は、`origin/main` ではなく、手元のリポジトリの `main` から切られる。手元の `main` は、マージを重ねても自動では進まない。2 件で、古い main から切られたことに気づいた。clone の `git reflog` に、そのときの記録が残っている。

```text
# #331（見返し用の HTML を書き出す）
9b9d2bb HEAD@{2026-10-07 22:37:09 +0900}: merge 9b9d2bb...: Fast-forward
a19f49b HEAD@{2026-10-07 22:36:57 +0900}: checkout: moving from main to takt/331/...

# #316（画面の外で変わったノードを縁の点で知らせる）
7a36690 HEAD@{2026-10-08 02:44:41 +0900}: merge 7a36690...: Fast-forward
3042911 HEAD@{2026-10-08 02:44:15 +0900}: checkout: moving from main to takt/316/...
```

#331 は、直前にマージされた #330（ライブと同じ画面の部品）を使う issue なのに、その 1 つ前のコミットから切られていた。#316 は、同じ 3 ファイルを触る #314 がマージされる前の、35 分古い main から切られていた。どちらも、切られた 12〜26 秒後に手で fast-forward して、実装が始まる前に間に合った。気づかずに進めば、マージ済みの変更を作り直すか、PR の段階で衝突していた。間に合っても、takt がレビューに渡す差分の起点は、切ったときの古いコミットのまま残った。#331 では #330 の 3 ファイルが毎回レビューの対象に入り、レビュアーはそのたびに「前のチケットの変更なので対象外」と除外していた。

それからは、積む直前に手元の main を `git pull --ff-only` で進めるのを手順にした。

**作業場所を作るツールが、どの版から切るかを確かめる。** 手元の版から切るなら、積む操作の前に必ず手元を最新にする。

### 3. 積む前に、issue の本文を今のコードと突き合わせる

issue の多くは、前日以前に仕様から切り出したものだった。その後、ほかの issue のマージで、関数名や型や、テストの差し替え方が変わっている。例えば #331 の本文は「CLI の `runCli` の `deps` に、ビルドを差し替えられる口を足す」と書いていたが、その間にサーバーの CLI が Effect の CLI モジュールに置き換わり、`deps` はもう無かった。

そこで、積む前に 1 件ずつ、サブエージェントに本文と今の main を突き合わせさせ、「確定した細部」の節を本文に足した。食い違った名前は今の名前に直し、迷いそうな点（境界の値、テストを書くファイル、触らない範囲）を決めて書いた。書き換える前の本文は、issue のコメントに退避した。この間に始めた 50 件のうち 44 件で、この書き換えをした（残る 6 件のうち 4 件は、この間に今のコードを見ながら起票したばかりの issue だった）。

本文には、次の一文も入れた。

> 作業の途中で main が変わっていたら、その時点の main の形に合わせる（ファイル名・関数名・型が変わっていれば、この節の名前ではなく main の名前で同じことを行う）。

並列で回すと、本文を書いた後にも main は動く。名前を書き込むほど、その名前が古くなったときにエージェントが本文に従って作り直してしまうので、「main が正」と明記した。

この書き換えの効き目は、[同じ日の #396](#bluetooth-config-change-exit-code) で見えた。名前・境界・テストの場面まで書いた issue は、計画の工程が 2 分半で終わり、差し戻しなしで通った。

**本文を書いた日と、エージェントが読む日の間に main が動いているなら、積む前に今のコードと突き合わせる。** 書いた名前より main が正しいことも、本文に書いておく。

### 4. 「手で確かめる」が受け入れ条件に残っていると、最後の判定で止まる

#173（画面のカメラを今の議題とその祖先に寄せる）は、本文を書き換えた後も、受け入れ条件に「手で確かめる: 長い会議のログを再生し、1920×1080 で今の議題が 0.75〜1.1 倍で映る」が残っていた。

takt は、レビュー 2 周と修正を経て、すべての観点で APPROVE まで進んだ。ところが、最後の判定の工程は、21 件の要件のうち 19 件を充足とし、手の確認にあたる 2 件を「判定不能」として、結果を「BLOCKED」にした。理由は「コード上の実装要件は充足し、未解消の指摘もない。受入条件の手動確認は未確認のため、人による確認待ち」。エージェントは画面を目で見られないので、何度やり直しても満たせない。takt は計画のやり直しに戻り、「外の操作か回答を待つだけが残る」として止まった。自動の積み直しも 2 回走ったが、どちらも計画のやり直しだけで同じ結論を出して止まった（2 回目は「リポジトリに長い会議のログは無い」とも書いていた）。最初の run の 67 分のうち最後の判定からの 7 分と、積み直し 2 回の約 7 分・出力 4.6 万トークンが無駄になった。

差分は clone に残っていたので、人が最新の main に乗せ直し、テストを通して PR にした。PR の本文には「マージ後に人が確かめること」として、その手順を移した。

次の issue からは、本文の「確定した細部」に「受け入れ条件の『手で確かめる』は、マージ後に人が行い、takt の条件に含めない」と書き、受け入れ条件の行頭にも「（マージ後に人が）」と付けた。それ以降、この理由で止まった run は無い。外に出した確認は、誰がいつ行い、結果をどこに書くかまで本文に書かないと消える。その話は [長い会議のエントリ](#long-meetings-takt) の 3 節に書いた。

**エージェントに渡す受け入れ条件は、エージェントが満たせるものだけにする。** 人の確認は消さずに、「マージ後に人が」と担い手を書いて残す。

### 5. 同じファイルを触る issue は、blocked by で直列にする。それでも DIRTY は出る

並列で回せるのは、触るファイルが重ならない issue だけだ。重なる issue は、GitHub の issue の依存（blocked by）でつなぎ、先の issue が main に入るまで積まなかった。依存の線が無くても同じ型に足していく issue は、線とは別に直列にした（[画面を人が動かす操作のエントリ](#human-view-ops-takt) の 1 節、[共有画面のエントリ](#shared-screen-takt-impl) の 3 節）。

極端だったのは、サーバーの Effect 4 の使い方を点検した報告から起票した 16 件だ。16 件のうち 14 件の本文が CLI の入口（`server/src/cli.ts`）に触れていた。依存でつなぐと、いちばん長い鎖は 11 件になり、16 件はほぼ直列にしか流せなかった。点検の指摘を「直す場所」ではなく「直す観点」（設定の読み方、ファイル操作、Schema の当て方など）で分けたので、どの観点も入口を触る。並列にしたいなら、切り方を入口の側から決める必要があった。

依存でつないでも、PR が DIRTY（main と衝突してマージできない）になることはあった。依存を張っていない issue どうしでも、同じファイルの近い行を触ることがあるからだ。4 本（#240・#243・#278・#338 の PR）は、takt の clone の中で最新の main に rebase して push し直した。4 本とも衝突があり（clone の reflog に `rebase (continue)` が残っている）、#240 と #278 は解くのに 4〜6 分かかった。#278 と #338 の衝突の中身は、[共有画面](#shared-screen-takt-impl) と [見返し](#review-view-takt) のエントリの 1 節にある。takt の PR は `gh pr merge --squash --auto` でマージを予約しているので、DIRTY のまま放っておくと、CI が通ってもマージされずに残る。

**並列にする前に、issue の切り方が同じ入口に集まっていないかを見る。** 集まっているなら、並列の数を上げても速くならない。

### 6. push や PR の作成が GitHub の 500 で落ちても、作業は clone に残っている

2 件（#311・#336）は、takt の工程はすべて通ったのに、最後の push で GitHub が `Internal Server Error` を返し、状態が `pr_failed` になった。

```text
PR creation failed: Failed to push branch to origin. Command failed: git push origin takt/311/...
remote: Internal Server Error
 ! [remote rejected] takt/311/... -> takt/311/... (Internal Server Error)
```

takt はこの失敗を自動では積み直さない。ただ、実装とレビューの結果は clone のブランチにコミットとして残っている。人が clone に入り、最新の main に rebase し、push して、`Closes #311` 付きの PR を作った。#311 は失敗から 3 分、#336 も 3 分で PR になった。`tasks.yaml` の状態は `pr_failed` のまま残るので、後で数えるときは、PR の有無と合わせて読む必要がある。

**ワークフローの最後の外部呼び出しで落ちたら、ワークフローを積み直さず、残った成果物から最後の一歩だけをやり直す。** 積み直すと、通った工程を全部やり直すことになる。

### 7. 工程ごとのモデルを替えるときは、runner を起動し直し、止めた run を同じ工程から積み直す

takt は、工程ごとにどのモデルを使うかを設定で持つ。この半日の始めに、設定を 2 つ変えた（理由は次節）。設定を確実に効かせるため、runner（積まれた issue を拾って回す常駐のプロセス）を起動し直した。

そのとき動いていた 2 件（#240・#242）は、run の途中で止まった。次の runner は、それらを「この run が始まる前に中断された。明示的に積み直せ」として拾わなかった。そこで、止まった工程から積み直した。#240 は実装の工程から、#242 はレビューの工程から再開し、どちらも通った。ただし #240 は、止める前に実装の工程を 1 時間回していた。その工程は頭からやり直しになり、1 時間分のエージェントの会話は引き継がれなかった。

**runner の設定を変えるときは、動いている run の工程の切れ目を待つか、捨てる時間を見積もってから止める。** 止めた run は、自動では拾われないので、止まった工程から積み直す。

### 8. モデルの速さは、設定の別名ではなく、実際に応答したモデルの ID で測る

takt のレビューには、観点別のレビュアーが出した指摘を、採るか退けるかを裁く役（review-adjudicator）がある。裁定を誤ると、指摘の見落としか、余計な手戻りになる。そこで 10-06 に、この役のモデルを Sonnet から Opus に上げた。すると 1 回 1 分ほどだった裁定が、9 分前後かかるようになった。run 1 本の平均も 19 分から 86 分に伸びたので、10-07 に Sonnet に戻した（同時に、実装の工程の振り分けからも Opus を外した）。

この判断の前提が外れていた。設定の `opus` は、takt の中で Claude Code を呼ぶときに、takt の依存に固定された古い版の Claude Code を通っていた。その版では、`opus` は Opus 5.5 ではなく一世代前の Opus 5 に、`sonnet` も Sonnet 5 に解決されていた。各エージェントのセッションの記録（`~/.claude/projects` の下の JSONL）の `message.model` を数えて分かった。例えば 10-06 の Effect の段 2 の run は、`claude-opus-5` が 852 件、`claude-sonnet-5` が 242 件で、5.5 は 1 件も無かった。自動で更新される Claude Code を使うように直し（10-07 の夜。前節の runner の起動し直しで効いた）、10-08 に裁定役を Opus（5.5）に戻して測り直した。

裁定 1 回の時間を、各 run のログ（`logs/*.jsonl` の `step_start`・`step_complete` の時刻と、`*-usage-events.jsonl` の `provider_model`）から出した。このリポジトリの run だけを数えた（takt の作業場所のフォルダには、ほかのリポジトリの run も混ざっている）。

| 実際のモデル | 期間 | 回数 | 1 回の時間（中央値） | 範囲 |
|---|---|---|---|---|
| Opus 5（設定は `opus`） | 10-06〜07 | 12 | 620 秒 | 247〜1737 秒 |
| Sonnet 5.5 | 10-01〜03、10-07〜08 | 104 | 54 秒 | 20〜167 秒 |
| Opus 5.5 | 10-08 | 6 | 104 秒 | 86〜203 秒 |

Opus 5.5 は Sonnet 5.5 の中央値の 2 倍ほどだが、Opus 5 の 6 分の 1 で、1 回 2〜3 分に収まった。比べた run は issue が違う。ただ、Opus 5 の 12 回のうち 7 回と、Opus 5.5 の 6 回のうち 5 回は、どちらもサーバーを Effect 4 に置き換える系統の issue だった。裁定役は Opus 5.5 のまま回している。

1 回の時間を出した jq は次のとおり（1 つの run のログについて、裁定の工程の開始と終了の組から秒を出す）。

```sh
jq -rs '(map(select(.type=="step_start"    and .persona=="review-adjudicator"))) as $s
      | (map(select(.type=="step_complete" and .persona=="review-adjudicator"))) as $c
      | range(0; [$s, $c] | map(length) | min) as $i
      | (($c[$i].timestamp | sub("\\.[0-9]+Z$"; "Z") | fromdate)
         - ($s[$i].timestamp | sub("\\.[0-9]+Z$"; "Z") | fromdate))' \
  .takt/runs/<run>/logs/<run>.jsonl
```

**「このモデルは遅い」と判断する前に、実際に応答したモデルの ID を数える。** 別名（`opus`・`sonnet`）は、呼び出す道具の版によって別のモデルに解決される。道具の版が固定されていると、新しいモデルが出ても、気づかないまま古いモデルで測ることになる。

## テストを unit・軽い IT・重い IT・E2E の層にそろえるため、先に今のテストを測ってから地図を作った話

別のプロジェクトで使っているテストの層の表（unit・軽い IT・重い IT・E2E と、それとは別に回す prompt eval）を貼り、「テストがこれに沿っているか調べて」と頼まれたのが始まりだった。表での層の分け方は、unit が直接の依存を偽物（test double）に置き換えたロジック、軽い IT が本物のファイルシステムや複数の部品の結合、重い IT が本物の子プロセスや全体のエンジン、E2E が公開の入口から利用者に見える結果まで、というものだ。回し方も層ごとに違い、重い IT は自分で変えたファイルだけ手元で回し、全件は PR の CI に任せる。調べた結果をもとに、決めることを並べた地図（親 issue と、判断ごとの子 issue）を作った。調べるだけで答えが出る調査のチケット 2 件はサブエージェントに解かせ、その結果を地図に戻した。

- 決定の記録: 地図 [テストを unit / 軽い IT / 重い IT / E2E の層に分け、層ごとに回す](https://github.com/daiki-beppu/live-mindmap/issues/459)、調査 [各テストファイルが使う本物の資源と所要時間を一覧にする](https://github.com/daiki-beppu/live-mindmap/issues/460)、[e2e（tester-army/e2e）で何ができるかを調べる](https://github.com/daiki-beppu/live-mindmap/issues/466)

### 1. 層の表に照らすときは、テストの中身より先に「層ごとに回す入口があるか」を見る

live-mindmap のテストは 3 か所にある。Node のサーバー（server、Effect で組んでいる）と Web 画面（web）は vitest で、Mac で会議の音を取るヘルパー（helper）は Swift のテストだ。中身を見ると、層の考え方はもうあった。server の部品は Effect の Layer（依存を差し替える単位）で組まれていて、本物の Layer を偽物に入れ替えるだけで unit 寄りのテストになる。本物の子プロセスを使うテストを契約の 6 本に絞った跡も、テストのコメントに残っていた。

足りなかったのは、層ごとに回す入口だった。server も web も `"test": "vitest run"` の 1 本だけで、unit も重い IT も同じコマンドで流れる。CI は一番遅いファイル（`server.test.ts`）をテスト単位で 4 つに割っていたが、手元の決まり（AGENTS.md の Checks）は「全件回す」だった。表とは逆だ。「沿っているか」を問われたときは、書き方が沿っているかと、回し方が沿っているかを分けて答えるとよい。直すべきなのはたいてい後者で、テストを書き直す話にはならない。

### 2. 前提をひっくり返す決定は、チケットに切る前の、目的地を決める段で決める

地図を作る最初の段では、層の定義より先に「重い IT を手元で全件回さない」を前提として受け入れるかを聞いた。今の Checks と逆なので、ここが決まらないと、後のチケットの問い（何をいつ回すか）がどれも宙に浮く。決め手は、main にはもう必須の CI のジョブがあり、全件が通らないとマージできないことだった。全件を通す保証が CI にあるなら、手元で全件回すのは同じ保証を二度取っていることになる。

### 3. ファイル単位の grep では、どのファイルで層が混ざっているかは分からない。テスト単位で読む

最初の調査は、ファイルごとに `mkdtemp`（一時ディレクトリ）、`child_process`、`chromium`、`listen`・`fetch`・`WebSocket`、`vi.mock` が出てくるかを grep して、使う資源を当てた。その結果から、「本物の子プロセスを使う `server.test.ts` などが unit と混ざっている」と報告し、地図の文面にもそう書いた。

これは外れていた。テストを 1 件ずつ読ませた調査では、`server.test.ts` の 6 件はどれも本物の子プロセス・HTTP・WebSocket を使っていて、混ざっていなかった。混ざっていたのは別のファイルだ。

- `http.test.ts`: どのテストも本物の HTTP サーバーを立てる。そのうち 36 件は偽のヘルパーを子プロセスで起動し、13 件は偽の Layer で済ませている
- `cli.test.ts`: 51 件は同じプロセスの中で一時ディレクトリを使い、1 件だけが本物の WebSocket を使う

grep で分かるのは「そのファイルのどこかで使っている」までだ。層の境目を決める材料にするなら、テスト単位で何を使うかを書いた一覧が要る。

### 4. 層の基準を決める前に所要時間を測る。遅さは数ファイルに偏り、資源の種類だけでは決まらない

この Mac（M4）で、各スイートを 1 回ずつ流して測った。

| 対象 | 件数 | 時間 | 目立ったもの |
| --- | --- | --- | --- |
| server | 1,099 | 59.6 秒 | `cliProcess.test.ts` が 54.2 秒（45 件すべてが node を子プロセスで起動）。次が `http` 26.1 秒、`server` 19.8 秒（うち SIGKILL を待つ 1 件が 12.8 秒）、`capture` 16.4 秒（Vite と Chromium）。残りの 39 ファイルは合わせて 17.7 秒 |
| web | 932 | 2.7 秒 | すべて unit。DOM も通信も使わない |
| helper | 319 | テストだけで 52〜76 秒 | 本物のエコー除去（WebRTC の AEC3）を動かすスイートが 60.8 秒。偽物しか使わないのに計算が重いスイートが 17.3 秒 |

server の遅さは、ほぼ 1 ファイルで決まっていた。層を分けなくても、このファイルを重い IT に回すだけで、手元の往復はほとんど軽くなる。

helper の数字は、資源の種類だけで層を決めると取りこぼすことも示した。エコー除去は子プロセスも通信も使わず、プロセスの中の計算だけで 1 分かかる。「本物の重いエンジンやモデルを動かすものは重い IT」のように、資源の種類に計算の重さを足す必要がある。

Swift のテストはスイートが並列に走るので、全体を流したときの各スイートの時間は、重いスイートに CPU を取られて 7〜20 秒に揃って見えた。スイートごとの時間は、`swift test --skip-build --filter <スイート>` で 1 つずつ流し直して測った。測っている途中で、層とは別の問題も 3 つ見つかった。

- ソースを変えていない 2 回目でも、ビルドが走り直して 102 秒かかった
- WebSocket の 1 件が、6 回中 1 回、5 秒の待ちを超えて落ちた
- スイートを 1 つずつ流した合計は 349 件、まとめて流すと 319 件で、件数が合わない

### 5. 一般名詞に見える道具の名前は、まずパッケージとして引く

「E2E は後から e2e というテストフレームワークを入れる」と聞いて、最初は「E2E 用の何かの道具」という意味に読んだ。`npm view e2e` を引くと、`e2e` という名前のパッケージがあった。AI エージェントが自然言語のシナリオで画面を操作する、E2E の SDK・runner・CLI（tester-army/e2e）だ。ふつうの E2E の道具とは性質が違う（次の節）ので、読み違えたまま進めていたら、地図の枝の切り方がずれていた。

### 6. AI が操作する E2E は、再生できる「操作」と、毎回ぶれうる「判定」に分かれる。層に置けるかは判定の側で決まる

e2e の調査で分かった、層の判断に効く事実は次のとおり。

- 操作（act）は、後の確認が通ったら記録され、次からはモデルを呼ばずに `.e2e/cache/` から再生される。記録はコミットでき、`--strict-cache` を付けると再生できなくなったときに落とせる
- 判定（assert・waitFor・extract）は毎回モデルを呼ぶ。温度も指定しないので、同じ画面でも判定がぶれうる。CI では落ちたテストを 1 回やり直し、通れば flaky として報告する
- モデルは AI SDK の provider なら何でもよいが、Claude はサブスクリプションには対応しておらず API キーが要る。公式の例（Claude Sonnet 4.5）で、操作 1 回が 0.020 ドル、判定 1 回が 0.011 ドル
- Web の画面は Playwright で操作できるが、CLI を操作する仕組みは無い
- モデルを呼ばない実行器（`StepExecutor`）と、AI SDK の mock のモデル（`MockLanguageModelV4`）で、API キーなしに通ることは試せた。ただ、操作を mock のモデルで通すには e2e の内部の呼び出し形式を真似る必要があり、そこは公開された約束ではない

ここから、「AI が操作する E2E を、落ちたら PR を止める決定的な層に置くか、prompt eval のように手で回す別枠にするか」を独立したチケットにした。操作は再生で決定的にできるので、問いは判定の扱いに絞られる。CLI の流れ（録音の再生や書き出し）を E2E の対象にするかも、e2e では操作できないという事実を前提に決めることになった。

### 7. 回し方を共有する層は、「後で入れる」ものでも同じ地図に入れる

最初は E2E を地図の範囲外にしていた。道具を後から決めると聞いていたので、今は層の整理に絞るつもりだった。そこで「これも合わせて地図にしよう」と言われ、範囲に戻した。範囲に戻すと、地図の目的地そのものを書き直すことになる。

戻してみると、つながりがはっきりした。層ごとの回し方を決めるチケット（手元・takt・CI・AGENTS.md の Checks）は、E2E の smoke をいつ回すかも決めることになり、E2E を決定的な層に置くかのチケットが閉じるまで待つようにつないだ（takt は、issue を渡すとエージェントが実装まで進める道具）。E2E を外したまま回し方を決めていたら、E2E を入れるときにもう一度同じ議論をすることになっていた。範囲を切るときは、道具が決まっているかではなく、決めることを共有しているかで切る。

調査の 2 件は、人と話しながら地図を作っている間にサブエージェントで並行に流した。2 つのエージェントが同じ地図の本文に 1 行ずつ書き足すので、「書き換える直前に本文を取り直し、自分の節だけを変え、書いた後に他の行が消えていないかを差分で確かめる」と両方に指示した。2 行ともそのまま残った。

## ブラウザの WebGPU で推論する場所を決めに行ったら、WebGPU をやめて、Apple Intelligence と Node の子プロセスで推論することになった話

[差分更新をローカルの LLM でも動かす地図](#local-llm-map)の判断のチケットを 1 件、人との問答（grilling）で解いた。**差分更新**は、AI が会議の発言を読んで、マップへの操作（足す・直す・まとめる）だけを返す処理だ。チケットの問いは「ブラウザ内の WebGPU で推論するなら、推論をどこで動かし、Node のサーバーが持つパイプラインとどうつなぐか」だった。答えは、問いの前提を外すものになった。ブラウザでは推論しない。ローカルの推論は、サーバーが起動する子プロセスに任せる。子プロセスは 2 種類で、1 つは Apple Intelligence（macOS の端末内のモデル）を呼ぶ Swift の実行ファイル、もう 1 つは node-llama-cpp で GGUF のモデルを Metal で動かす Node のプロセスだ。質問は 4 回に分けて 8 問出した。利用者は 7 問で推奨の答えを選び、1 問は「Apple Intelligence を既定にできるか」という別案で返した。

- 決定の記録: [WebGPU で推論する場所とパイプラインのつなぎ方](https://github.com/daiki-beppu/live-mindmap/issues/379)、[ADR 0012](../adr/0012-local-inference-in-child-process.md)、地図 [差分更新をローカルの LLM（WebGPU を含む）でも動かし、ローカルモードでは何も外に出さない](https://github.com/daiki-beppu/live-mindmap/issues/374)、[ADR 0003](../adr/0003-local-node-server-owns-pipeline.md)

### 1. 動機を聞いただけでは足りない。動機の「線引き」まで聞くと、候補そのものが要らなくなることがある

地図を作った日に、WebGPU を挙げた理由を聞いていた。答えは「何もインストールせずに試せるから」で、そこから WebGPU を「試すための第 2 の経路」に置いた（[その日のエントリ](#local-llm-map)の 4 節）。しかし、この読み方は一段浅かった。live-mindmap は、もともとリポジトリを取ってきて `pnpm install` し、Node のサーバーを動かして使う。だから「インストール」がすでにゼロではない。

そこで、避けたいインストールが何かを選択肢で聞いた。(a) Ollama や LM Studio のような、アプリとは別のものを入れて起動すること（npm の依存とモデルのダウンロードは数に入れない）。(b) ネイティブのバイナリ全般。答えは (a) だった。(a) なら、npm で Apple Silicon 向けの Metal 版がビルド済みで配られている node-llama-cpp で、同じ目的を果たせる。

WebGPU には、ほかの道に無い故障の型がある。推論するタブを閉じる、再読み込みする、裏に回すと、差分更新が止まる。会議中は会議アプリが前に出て、ブラウザは裏に回るのが普通だ。それなのに、隠れたタブで WebGPU が間引かれるかは一次情報が見つからなかった。さらに、ブラウザで推論するなら、「パイプラインは Node のサーバーが持ち、ブラウザは表示だけ」という以前の判断（ADR 0003）も見直す必要があった。チケットに並んでいた問い（タブが複数あるときにどれが推論するか、閉じたらどうするか）は、どれもこの故障の型への対策だった。線引きを聞いたら、問いごと消えた。

チケットの問いには「Node で WebGPU を使う道（Dawn のバインディング）は現実的か」もあった。調べると、バインディング自体は Node で動く。ただ、WebLLM はモデルの保存先を Cache API・IndexedDB・OPFS からしか選べず、Node で動いたという例も公式の回答も無かった。

### 2. 推論を子プロセスに置いて localhost に OpenAI 互換の HTTP を出させると、予定外の経路も運び手を変えずに入る

node-llama-cpp をサーバーと同じプロセスで動かすのが、いちばん単純だ。しかし、ネイティブのアドオンがメモリ不足などで落ちると、プロセスごと落ちる。16GB の機械では、会議アプリ・Chrome・音声認識のヘルパーとメモリを取り合う。プロセスが落ちれば、セッションの状態も字幕も CLI も止まる。子プロセスに分ければ、失うのは差分更新だけになる。字幕とログを続けながら、子を立ち上げ直せる。

子との話し方は、localhost の OpenAI 互換の HTTP にした。その前のチケットで、差分更新の口の下を「プロンプト・messages の会話・運び手」の 3 層に分け、運び手は「OpenAI 互換の要求を 1 つ送って応答を受け取るもの」と決めていた（[口を 3 層に分けた話](#diff-updater-seam)）。子が互換の HTTP を出せば、運び手は外部の Ollama を呼ぶものとまったく同じでよい。ローカルモード（会議の中身を Mac の外に出さない設定）でサーバーが宛先を検査するときも、「localhost だけ」という規則にそのまま通る。

この形が効いたのは、問答の途中で利用者が「Apple Intelligence を既定にしたい」と言ったときだ。計画に無かった経路だが、Swift の実行ファイルを 1 つ足し、それに互換の HTTP を出させれば収まる。経路の違いは「どの実行ファイルを起動するか」と、JSON Schema をその実行環境向けに写す処理だけに縮んだ。

### 3. 新しい API が使えるかは、文書を読むより先に、手元の機械で小さく呼んでみる

Apple Intelligence について覚えていたのは「文脈長が 4,096 トークン」だった。それだと、指示文だけで埋まって使えない。そこで、手元の M4・16GB・macOS 27 で、署名の無い小さな Swift のプログラムからサブエージェントに呼ばせた。分かったことは次のとおり。

| 確かめたこと | 結果 |
| --- | --- |
| 文脈長（`contextSize`） | 8,192 トークン（macOS 26 では 4,096） |
| 1 回の時間 | 2 回目以降は約 3〜5 秒、31〜42 トークン/秒 |
| 前の部分の再利用 | 同じ session を続けると、2 回目の入力 2,848 トークンのうち 2,775 がキャッシュに当たった |
| スキーマでの出力の制約 | `DynamicGenerationSchema` で、anyOf の和・enum・minItems・入れ子を組めた |
| JSON Schema をそのまま渡せるか | 専用の API は無い。`GenerationSchema` が Codable なので decode はできる。ただし、各オブジェクトに `x-order`、anyOf の各要素に `title` が無いと失敗する |
| Command Line Tools だけで作れるか | フレームワークは使える。マクロの `@Generable` は、プラグインが入っていないので使えない |

速さは、Qwen3.5-9B の見込み（1 回 15〜25 秒）よりかなり上だった。一方で 8,192 は窮屈だ。いまの指示文は UTF-8 で約 12KB（日本語で約 4,000 字）あり、これだけで 3,000〜4,000 トークンになる見込みだ。いま Claude でやっている「14 回分の履歴を積む」形は入らない。開き直す回数をモデルごとに決めるチケットに、この制約を足した。

node-llama-cpp でも、同じく手元で確かめて引っかかりが見つかった。ドキュメントには「JSON Schema で出力を縛れる」とある。ところが、対応している語の一覧に `anyOf` が無かった。差分操作のスキーマ（Effect の Schema から生成している）を実際に JSON Schema に書き出し、使っている語を数えた。出てきたのは `anyOf`・`enum`・`minItems`・`required` の 4 つだった。差分操作の和は判別できる形なので、`oneOf` に写せば済む見込みだ。ただ、これは「対応している」とだけ読んでいたら、実装の段で初めて気づくことだった。対応表と突き合わせるときは、想像で書いたスキーマではなく、実際に送るスキーマから語を出す。

### 4. 既定を OS の機能に寄せるときは、使えない環境への受け皿を自動で用意する

Apple Intelligence を既定にすると、モデルのダウンロードもメモリの確保も OS が持ってくれる。16GB の機械では大きな利点だ。ただ、Apple Intelligence は利用者か管理者が有効にしないと使えない。会社の MDM（端末の一括管理）で無効にされていることもある。この地図が狙っているのは「社内規程で外部の AI に会議を送れない人」だ。そういう人の Mac こそ、無効にされている見込みが高い。

そこで既定は自動で決めることにした。Apple Intelligence が使えればそれを使い、使えなければ（無効、対象外の機種、モデルを準備中）内蔵の node-llama-cpp に回す。利用者に「Apple Intelligence を有効にしてください」という前提は課さない。もう 1 つ、品質の条件を足した。Apple Intelligence を既定にするのは、16GB の機械での回帰評価で品質の下限を満たした場合だけにする。速さと手軽さは測れたが、20B の疎なモデル（1 回に動くのは 1〜4B）が差分更新をこなせるかは、まだ誰も測っていない。

### 5. 「セッション中に外へ出ない」は、取得を明示のコマンドに分けると、構造で守れる

内蔵のモデルは 2.5〜5GB ある。セッションを始める `start` の初回に自動で取れば手軽だ。しかし、ローカルモードの約束は「セッション中に会議の中身が Mac の外に出ない」ことだ。`start` がダウンロードしうると、セッションの始まりに外への通信が混ざる。そのたびに「中身は送っていない」と説明することになる。

モデルは `models pull` のような明示のコマンドでだけ取ることにした。`start` は決してダウンロードせず、モデルが無ければ開始を拒んで pull を案内する。live-mindmap は人ではなく AI エージェントが CLI で操作する前提なので（ADR 0003）、エラーの案内に従って pull を挟むのは手間にならない。「外に出ない」を検査で守るより、外に出る操作をセッションの外にしか置かない方が、約束として確かめやすい。

## テストの層の境目を決めに行き、所要時間を基準に入れる案を取り下げて、依存の境界だけで切ることにした話

[前のエントリ](#test-layers-map)で作った地図の最初の判断として、unit・軽い IT・重い IT の境目を、利用者と問答して決めた。材料は、同じ日に測った「各テストが使う本物の資源と所要時間」の一覧だ。最初は所要時間も基準に入れる案を勧めたが、利用者が別のプロジェクト（takt。issue を渡すとエージェントが実装まで進める道具で、このプロジェクトの実装にも使っている）のテスト方針の要約を貼ったのを受けて、その原文を読み、案を組み直した。

- 決定の記録: [unit / 軽い IT / 重い IT の定義と境目の基準を決める](https://github.com/daiki-beppu/live-mindmap/issues/461)、地図 [テストを unit / 軽い IT / 重い IT / E2E の層に分け、層ごとに回す](https://github.com/daiki-beppu/live-mindmap/issues/459)

### 1. 層は、実際に通る依存の境界だけで決める。時間を基準に入れると、遅い unit を IT に逃がす抜け道になる

最初に勧めたのは「基本は資源の種類で決め、資源から見れば軽いのに遅いものは、時間で重い IT に上げる」という案だった。念頭にあったのは helper（Mac で会議の音を取る Swift のヘルパー）の `WindowResultsTests` だ。偽物しか使わないのに、長い合成信号の相関を計算するので 17.3 秒かかる。資源の種類だけで決めると unit に入り、実装中に何度も回す層が重くなる。

利用者が貼った takt の方針は、ここを逆に決めていた。「遅いという理由だけでレイヤーを変更」は REJECT と明記し、禁止事項にも「速度基準だけの分類（遅い unit と実境界を通る IT を混同する）」を挙げている。言われてみると、時間を基準にすると 2 つ困ることがある。

- 層がマシンで変わる。手元の M4 で 0.9 秒のテストは、遅い CI のランナーでは 1 秒を超えうる
- 遅い unit を速くする代わりに、IT に移して済ませられてしまう。層の表が、遅いテストの置き場になる

`WindowResultsTests` は unit のままにして、入力を縮めるなどで速くすることにした。層の境目は「テストを書く前に分かるもの」にしておくと、新しいテストを書くエージェントへの指針にもそのまま使える。

### 2. 計算の重い本物のエンジンは、時間の線ではなく「本物の何を動かすか」という種類で拾う

前のエントリでは、「エコー除去（WebRTC の AEC3）は子プロセスも通信も使わずに 1 分かかるので、資源の種類だけでは取りこぼす」と書いた。時間を基準から外すと、これをどう拾うかが問題になる。

takt の方針の原文を手元のリポジトリで開くと、重い IT の定義は「実 child process、Git、完全な workflow engine、**計測済み高負荷処理**」だった。貼られた要約には無かった語だ。重い処理を本物で動かすこと自体を、境界の 1 つとして数えている。これに倣い、本物の AEC3（単独で 60.8 秒と 10.7 秒）と、OS の音声認識モデルを本物で動かす SpeechAnalyzer を重い IT にした。どちらも「本物の何を動かすか」で決まるので、測らなくても書く前に分かる。

一方、偽物で計算が重い `WindowResultsTests` は、この語に当てはめない。重いのは本物のエンジンではなく、テストが作った入力の大きさだからだ。

### 3. unit の境目は、組んでいる部品の数ではなく、テストの対象が直接頼るものがすべて偽物かで決める

もう 1 つ迷ったのは、server（Node のサーバー。部品を Effect の Layer という差し替えの単位で組んでいる）の `sessions.test.ts` だった。セッション全体を組んで 70 件を流すが、ヘルパー・保存先・時計はすべて偽の Layer で、本物の資源は何も使わない。時間は 0.96 秒だ。最初に使った層の表は「複数の部品の結合」を軽い IT としていたので、表のとおりなら軽い IT になる。

最初は「本物の資源を使わなければ、何個組んでも unit」と、表からずれる答えを勧めた。takt の原文の unit は「**直接依存**を test double に置き換えた個別ロジック」で、この言い方なら表とずれずに済む。セッションが直接頼るものはすべて偽物なので unit だ。本物の部品どうしを 2 つ以上つないだときに、初めて軽い IT になる。「結合」を「部品の数」と読むと、Layer で組む作りほど unit が減ってしまう。

同じ考えで、偽のヘルパーを子プロセスで起動するテストは重い IT にした。takt の原文の「実 process を使うが内部 client から偽 CLI を呼ぶのは重い IT。E2E ではない」に当たる。偽物でも、プロセスの境界は本物だからだ。

### 4. 境界で決めると決めたら、例外を作らない。読むだけのファイルも軽い IT にする

最初の案では、「リポジトリのファイルを読むだけのテストは unit、一時ディレクトリに書くテストは軽い IT」と分けていた。読むだけなら決定的で、後片付けも要らないからだ。

時間を外して境界だけで決めることにすると、この区別は理由が弱くなる。読むのも本物の filesystem という境界を通る。読むだけのテストの中身を見直すと、ソースを読んで呼び出しの数を数えるもの（`entrypoints.test.ts`）や、README の文言を読むもの（`coreSchema.test.ts` の一部）が混ざっていた。takt の方針は、こうした「内部構造や、実行されない資産を契約にする」テストを、足すべきでないものとしている。読むだけを unit として特別扱いしていたら、消すかどうかを考えるべきテストを、一番よく回す層で守ることになっていた。読むだけのものも軽い IT とし、こうしたテストの扱いは、テストの書き方の指針を決める段に回した。

### 5. 手本の方針を要約で渡されたら、原文を手元で開く。要約に無い語が、判断を 1 つ決める

利用者が貼ったのは、takt の方針の要約だった。そのまま使っても大筋は合っていた。ただ、手元にあった takt のリポジトリで原文（`builtins/ja/facets/policies/takt-testing.md`）と分類表（`scripts/test-classification.mjs`）を開くと、要約に無いことが 2 つ見つかった。

- 重い IT の定義に「計測済み高負荷処理」が入っていた（2 節の AEC3 を決めた）
- 「実 process だが内部 client から偽 CLI を呼ぶもの」の判定が明記されていた（3 節の子プロセスのテストを決めた）

要約は「遅いから分けない」という結論を伝えていたが、それだと AEC3 は unit になる。原文の 1 語で、時間を使わずに AEC3 を重い IT に置けた。

貼られた方針には、このチケットでは決めない話も多かった。分類のルールをテストで守る仕組み、重い IT を同じランナーの中で並列にしないこと、テストを足すときに求める 5 つの証拠、プロンプトの評価を 3 回回して率で見ること、だ。これらは捨てずに、地図の中で決める場所（層に分ける仕組み、回し方、書き方の指針、プロンプトの評価）を 1 つずつ名指しして、解決のコメントに書いた。1 回の問答で 1 つのチケットしか閉じないので、手本の残りはこうして行き先を付けておかないと、次のセッションで読み直すことになる。

## 音声認識に語彙を渡す口を測ったら、本番の部品はその口を無視していて、補正は発言にした後でやるしかなくなった話

字幕の精度を上げる地図（[同じ日の最初のエントリ](#subtitle-accuracy-map)）で、語彙を音声認識に直接渡すと効くかを測るチケットを解いた。語彙は、会議に出てくる固有名詞・略語の正しい表記の集まりだ。Apple の音声認識（SpeechAnalyzer）には、`AnalysisContext.contextualStrings` という、語彙を渡して認識を寄せる口がある。手本の Kanary は使っていない口だ。効けば、文字起こしの段で直せる。後から LLM で直すより前で、崩れる前に正しい表記が出る。測った道具と素材は、[基準線を出したエントリ](#subtitle-accuracy-baseline)のものを使った。結論は「本番で使っている部品（SpeechTranscriber）はこの口を無視する」だった。

- 決定の記録: [語彙を SpeechAnalyzer の contextualStrings に渡して効くかを測る](https://github.com/daiki-beppu/live-mindmap/issues/399)、地図 [Kanary を手本に字幕の精度を上げる](https://github.com/daiki-beppu/live-mindmap/issues/386)、道具 [PR #478](https://github.com/daiki-beppu/live-mindmap/pull/478)

### 1. API が値を受け取っても、使うかは下の部品次第。結果が 1 文字も変わらなければ、まず「無視されている」を疑う

SpeechAnalyzer は、文字起こしを担う部品（module）を差し込んで使う。本番は長い音声向けの SpeechTranscriber で、短い口述向けの DictationTranscriber も差し込める。語彙を渡す `setContext` は analyzer 側のメソッドで、どの部品を差し込んでも型の上では通る。SDK のインターフェースにも、どの部品が語彙を使うかは書いていない。

計測の道具（`stt-bench`）に、語彙を渡す候補を足して流した。略語と製品名の会議（8 分、固有名詞・略語が 126 回出る）に台本から作った 39 語を渡すと、CER（文字誤り率）も固有名詞の正解率も、語彙なしと件数まで同じだった。並べてみると、確定結果どころか途中結果まで、バイト単位で一致していた。

効きが小さいなら、どこかで 1 文字は動く。まったく動かないのは、効きが小さいのではなく、どこにも届いていないサインだ。そこから次の 2 つを分けた。

- **渡せていないのか**: analyzer から語彙を読み戻して、stderr に件数を出した（`context: 39 語`）。入っている
- **渡し方の問題か**: 途中で `setContext` する代わりに、analyzer を作るときの引数で渡す候補を足した。これも同じ

ここで Apple の開発者フォーラムを探すと、「contextualStrings が効くのは DictationTranscriber だけで、SpeechTranscriber は考慮しない」という回答が 2 件あった。公式のドキュメントには書かれていない。測った結果と一致したので、結論にした。

| 条件（略語と製品名の会議） | CER | 固有名詞の正解率 |
| --- | --- | --- |
| 本番の設定（語彙なし） | 11.0% | 62.7%（79/126） |
| 語彙 39 語 / 139 語 / 339 語 / 1,039 語、途中の 250 秒目に渡す、作るときに渡す | 11.0% | 62.7%（確定結果が 1 文字も変わらない） |

画面共有つきの四半期レビュー（23 分）でも、語彙ありの確定結果は語彙なしと 1 文字も違わなかった。

### 2. 効くかどうかを、一番短い素材 1 本で先に確かめる。測る項目を並べるのは、その後でいい

チケットには、測る点が 4 つ並んでいた。語彙の量を増やしたときの効き方、一般語が語彙の語に寄る副作用、途中結果の速さへの影響、セッション中の差し替えだ。どれも、効くことが前提の問いだった。

最初の判断はここで外れた。5 つの素材すべてに語彙を渡して、実時間で同時に流し始めた（一番長い素材は 161 分）。並べて流しても結果が変わらないことは、基準線のときに確かめてあった。8 分の素材が終わった時点で「1 文字も変わらない」と分かり、残りの 3 本（55・75・161 分）は途中で止めた。結果は捨てた。

効くと分かる前に、測る項目を広げる必要はなかった。量・副作用・速さ・差し替えは、効かない以上、測る意味がない。量と差し替えは、8 分の素材で流すだけで済むので、念のため流した（全部同じだった）。順番を逆にして、短い素材 1 本で効くかを見てから、ほかの素材と項目に広げればよかった。

### 3. 代わりの部品が「語彙で上がる」ことは、素の値と並べてから判断する

語彙が効く DictationTranscriber も、同じ素材で流した。

| 部品 | 語彙 | CER（脱落の字数） | 固有名詞の正解率 |
| --- | --- | --- | --- |
| SpeechTranscriber（本番） | なし | 11.0%（60） | 62.7% |
| DictationTranscriber | なし | 16.7%（260） | 48.4% |
| DictationTranscriber | 39 語 | 16.2%（255） | 55.6% |

語彙で 9 語ぶん（48%→56%）上がるが、本番の部品の素の値（63%）に届かない。脱落は 4 倍あった。語ごとに見ると、得手不得手が逆だった。DictationTranscriber は、英字の製品名を英字で書ける（Notion 6/8、Zoom・Excel・PowerPoint は全部）。本番の部品は、これらを全部カタカナにする。代わりに、略語が崩れる（OJT が 13 回中 2 回しか合わず、「大jt」になる）。「語彙で上がる」だけを見れば乗り換えたくなるが、素の値と並べると乗り換える理由にはならない。

DictationTranscriber には、発音つきの独自語彙を学習させる口（`customizedLanguage`）もある。これも DictationTranscriber 専用で、素の精度が低いので試していない。

### 4. 補正を前の段でできないと分かると、後ろの段の設計の前提が決まる

文字起こしの段で直せないので、語彙での補正は、発言（確定した文字起こしの 1 区切り）にした後の段でやるしかない。そこで直す相手は、崩れた後の表記だ。基準線のとき、崩れ方は表記が合わないものばかりだった。「ユズ」は「ゆず」に、「大槻」は「大月」に、「Notion」は「ノーション」に、「ハコビズ」は「運び図」になる。どれも、表記の近さでは候補を引けないが、読みはほぼ合っている。

なので、次の試作（端末内の LLM で発言を語彙で直す）は、崩れた表記から**読みで**候補を引く前提で比べることになった。このチケットの結論は「効かない」だが、その結論で、次のチケットの比べる軸が 1 つ決まった。

## 話者を発言にどう結び付けるかを決めに行ったら、遅れの数字を並べただけで「待つか、後から足すか」の問いが消えた話

話者分離の地図（[上のエントリ](#speaker-diarization-map)）で、方式を Sortformer に決めた（[上のエントリ](#diarization-measurement)）次の問いを解いた。推定した話者を、**発言**（文字起こしの 1 区切り。10〜15 秒程度で、一度出したら書き換えない）にどう対応させるか、その処理をどこに置くかだ。live-mindmap は、Swift で書いたヘルパー（常駐プロセス）が音声を取って文字起こしし、Node のサーバーが発言を受けてマップを組み立てる。チケットには、待つか後から足すか、1 発言に話者を 1 人にするか、ヘルパーとサーバーのどちらで決めるか、が並んでいた。答えはどれも推奨のとおりに決まった。決め手になったのは議論ではなく、問いを出す前にコードと計測から拾った 3 つの事実だった。

- 決定の記録: チケット [発言と話者の対応と、話者を決める場所](https://github.com/daiki-beppu/live-mindmap/issues/370)、[ADR 0013](../adr/0013-diarize-in-helper-split-remarks-by-speaker.md)、[ADR 0002](../adr/0002-local-stt-helper.md)、新しい問い [ヘルパーを作り直したときの話者のつなぎ方](https://github.com/daiki-beppu/live-mindmap/issues/483)

### 1. 「待つか、後から足すか」は、新しい信号の遅れと、今ある待ちの長さを並べてから問う

話者のラベルは文字より遅れて届く。チケットは、これを「発言を出すのを待つか、出してから話者を足すか」という二択で書いていた。後から足すなら、「出した発言は書き換えない」という今の決まりに例外を作ることになる。

ところが数字を並べると、二択はほとんど消えた。Sortformer の確定ラベルは、音声から中央値 0.82 秒、95% で 1.04 秒遅れて届く。一方、サーバーは今でも、途中結果（確定前の暫定の文字列）が 1 秒更新されなければ発言にしている。つまり、発言はもともと約 1 秒待ってから出ている。ラベルを待っても、増える待ちは長くてもコンマ数秒だ。そこで、発言は終わりまでの確定ラベルが揃ってから出し、3 秒待っても揃わなければ話者なしで出す、と決めた。書き換えない決まりは、例外なしで保てた。

新しい信号の遅れは、それ単体で見ると「遅い」と感じやすい。比べるのは 0 秒ではなく、パイプラインがすでに払っている待ちだ。

### 2. 新しい信号は既存のイベントに混ぜず、別のイベントで流す。結び付けるのは、相手のデータが出来上がる場所でやる

ヘルパーとサーバーの間のイベントには、ADR 0002 の約束がある。「クラウドの STT に差し替えても、サーバー側のイベントの形は変えない」だ。話者を STT の結果（`remark` / `partial`）に載せると、STT を差し替えるたびに話者の載せ方にも触ることになる。

話者を STT とは別の `speaker` イベント（トラック・区間・ラベル・仮か確定か）にすれば、約束はそのまま守れる。では、発言と話者を結び付けるのはどちらか。コードを読むと、発言はヘルパーではなくサーバーで作られていた（`server/src/core/settle.ts`）。途中結果が 1 秒更新されなかったときにも発言を作るので、ヘルパーが話者を載せても、結局サーバーで合わせ直すことになる。結び付けは、発言が出来上がる場所、つまりサーバーに置いた。テストも TypeScript の側だけで書ける。

### 3. 細かい情報が要るときは、上流がもう返しているのに境界で捨てていないかを先に見る

「1 つの発言に話者は 1 人」にするには、話者が替わったところで発言を切る必要がある。10〜15 秒の発言のどこで切るかを決めるには、語ごとの時刻が要る。新しく取りに行く仕組みが要るかと思ったが、ヘルパーのコードを見ると、SpeechAnalyzer にはすでに `attributeOptions: [.audioTimeRange]` を頼んでいた。語ごとの区間は手元にあり、イベントにするときに発言全体の start / end だけ残して捨てていただけだった。

足すのは「イベントに語の区間を載せる」ことだけで、クラウドの STT も語の時刻は返すので、ADR 0002 とも両立する。

### 4. 下流の判断を AI に任せたくなければ、上流のデータの単位をそろえる

発言を切らずに「話者の区間を複数持たせる」案もあった。しかしその場合、マップの**案**（論点への答えの候補。出した人を持つ）について「誰が出したか」を決めるには、発言のどの部分が誰の話かを差分更新の AI が読み解くことになる。1 発言 1 話者にしておけば、案の根拠の発言から出した人が機械的に決まる。

これは語の定義の変更でもあった。用語集の**発言**には「複数人の話が 1 つの発言に混ざることがある」と書いてあり、これを外した。書き換えの途中で、一度「話者を 1 人持つ」と書いた。ところが同じ決定の中に、声で区別できなかった発言は「話者なし」で出す、という決まりもある。読み返して矛盾に気づき、「話者は 1 人まで」に直した。用語の定義は、決めたことを全部並べて照らし合わせないと、例外の扱いで食い違う。

### 5. 調整しそうな規則は、その入力の生のデータもログに残す

発言への対応付けには、細かい規則がいくつか付いた。語の区間に 2 人分のラベルが重なれば、最も長く重なる話者にする。誰とも判定されない区間は、前後の話者に寄せる。0.5 秒未満の話者の区間は、相づちで細切れにならないよう前後に寄せる。合成会議の台本には話し声の重なりが無かったので、これらの値は測れていない。実際の会議で直すことになりそうだ。

そこで、ログ（`log.jsonl`）には、発言に決まった話者だけでなく、`speaker` イベントの生の区間も残すことにした。規則を変えたときに、録音から音声処理をやり直さなくても、ログを**再生**（記録した発言の流れをもう一度流す回帰評価）すれば測り直せる。

### 6. 前提が決まると、霧の中の問いは「立てられる」か「半分消える」かのどちらかになる

地図には、まだ問いにできない項目（霧）を書いておく欄がある。今回の決定で、そのうち 2 つが動いた。

- 「ヘルパーの作り直しをまたぐ話者」には、もともと「話者を決める場所が決まってから」と書いてあった。場所が決まったので、問いを正確に書けるようになり、チケットにした（作り直した後の枠を、前の「相手 A」に対応させるか、新しいラベルにするか）
- 「話者の取り違えへの備え」は、「推定が後から変わるときに、マップや字幕を書き換えるか」という問いだった。発言の話者は後から変えないと決めたので、半分は答えが出た。残りは「誤ったラベルが案の出した人に載ったとき、人が直せるようにするか」に絞った

霧に「何が決まったら問いにできるか」を書いておくと、決定のたびに、どの霧を見直せばよいかがすぐ分かる。

## ローカルの LLM を回帰評価にかけたら、どれもマップを作れず、速さを優先して Apple Intelligence に絞って調整することにした話

[差分更新をローカルの LLM でも動かす地図](#local-llm-map)の作業のチケットを 1 件、エージェントだけで解いた。**差分更新**は、AI が会議の発言を読み、マップへの操作（足す・直す・まとめるなど）だけを JSON で返す処理だ。今は Claude（Sonnet 5.5）で動いている。チケットの中身は、ローカルの候補モデルを手元の M4・16GB に差し込み、既存の**回帰評価**（録音済みの会議の文字起こしを流し直し、できたマップを人が書いた正解の決定・TODO と照らす仕組み）にかけて、推奨の下限を決める材料を出すことだった。結果は、今のプロンプトのままでは候補のどれもマップを作れない、だった。その後、利用者と話して、調整の対象を Apple Intelligence に絞った。

- 決定の記録: チケット [ローカルの候補モデルを 16GB の M4 で回帰評価にかける](https://github.com/daiki-beppu/live-mindmap/issues/380)、新しい問い [Apple Intelligence でも差分操作を当てられるプロンプトと出力の形](https://github.com/daiki-beppu/live-mindmap/issues/487)、地図 [差分更新をローカルの LLM（WebGPU を含む）でも動かし、ローカルモードでは何も外に出さない](https://github.com/daiki-beppu/live-mindmap/issues/374)

計測のために、使い捨ての接続を 2 つ書いた。1 つは、差分更新を OpenAI 互換の chat completions に送る実装で、プロンプトは Claude と同じものを使い、`response_format` に今の出力のスキーマを渡す。もう 1 つは、Apple Intelligence（macOS の端末内のモデル）を Swift の小さな実行ファイルで呼び、Node で互換の HTTP に包むシムだ。ほかのモデルは llama.cpp の `llama-server` で動かした。素材は、架空の会議の台本を音声合成した 23 分の会議（78 発言、スライド 8 枚、正解は決定 5・TODO 7）にした。

| ラン | 決定 | TODO | 適用できた操作 | 1 回の時間（中央 / p90） |
| --- | --- | --- | --- | --- |
| Claude Sonnet 5.5 | 4/5 | 5/7 | — | 5.8 / 9.4 秒 |
| Apple Intelligence | 0/5 | 0/7 | ほぼ 0 | 14.2 / 22.4 秒 |
| Qwen3.5-9B（4bit） | 0/5 | 0/7 | 0/144 | 61.3 / 122.5 秒 |
| Gemma 4 12B（4bit、最初の 6 回） | — | — | 0/20 | 96.1 / 104.6 秒 |
| Qwen3.5-4B（4bit）＋指示 1 行 | 1/5 | 2/7 | 132/140 | 37.5 / 66.6 秒 |

### 1. 出力をスキーマで縛っても、意味の誤りは防げない。最初の 1 つの誤りが、以後をすべて巻き込む

事前の調査では「llama.cpp も Apple Intelligence も、JSON Schema で出力を縛れる」と確かめていた。そのとおり、スキーマ違反は 1 件も出なかった。それでもマップは空のままだった。

ログで捨てられた理由を数えると、崩れ方は id の扱いだった。差分操作の add は、新しいノードに仮 id（`ref`）を付けて、同じ応答の後ろの操作から親として指せる。Qwen3.5-9B と Gemma 4 12B は、最初の add の仮 id に、ルートの id そのもの（`root`）を書いた。これは「既存の id と重なる」で弾かれる。最初の議題ができないので、その下に足そうとした add は全部「親が存在しない」で捨てられる。モデルに次に届く「前回からのマップの変更」は「（変更なし）」なので、モデルは自分の操作が捨てられたことに気づかず、同じ誤りを繰り返す。9B は 39 回の呼び出しで 144 操作を出し、当たったのは 0 だった。Apple Intelligence は、存在しない `root` を update する操作を繰り返した。

スキーマが保証するのは形だけで、「その id が今のマップにあるか」は保証しない。そして差分を積み上げる設計では、最初の誤りが後ろの全部を巻き込む。「構造化出力に対応している」は、使えることの証拠にはならなかった。

### 2. 全員が同じところで崩れたら、1 行足して「浅い問題か、力の問題か」を切り分ける

3 つのモデルがそろって id で崩れたので、プロンプトの浅い問題なのか、モデルの力の問題なのかを分けたかった。そこで、システムプロンプトの末尾に 1 行だけ足した。「add の ref には a1, a2 … のような、この応答で新しく付ける仮 id を書く。root や既存ノードの id を ref にしない」。

| モデル | 指示なし | 指示 1 行あり（最初の 8 回） |
| --- | --- | --- |
| Qwen3.5-9B | 当たった操作 0 | 41 操作中 14 |
| Qwen3.5-4B | （測っていない） | 28 操作中 28 |

ここで予想が外れた。大きい 9B の方が指示に従うと思っていたが、9B は別の誤り方に移っただけだった。発言の id（`r2`）を仮 id に使ったり、同じ仮 id を何度も付けたりした。小さい 4B は素直に従い、全編を流しても 140 操作中 132 が当たった。ただし当たるようになっても、決定は 1/5・TODO は 2/7 で、Claude（4/5・5/7）には遠い。1 つの親の下で話し中の子は最多 26 になり、5 つまでという目安はほとんど効かなかった。

1 行で崩れ方が変わったので、プロンプトか出力の形を作り直す余地はある。一方で、同じ 1 行への反応はモデルごとに違う。これが後で、調整の対象を絞るときの判断材料になった（6 節）。

### 3. 速さの見込みは、空いた機械ではなく、普段のアプリを開いたままの機械で測る

事前の調査は、16GB の機械で Qwen3.5-9B が 1 回 15〜25 秒（読み込み 150 トークン/秒、生成 13〜16 トークン/秒）と見込んでいた。実測の最初の 3 回は、ほぼそのとおりだった（読み込み 139、生成 15.6）。4 回目から落ちた。

計測した Mac では、Orca・Chrome・複数のエージェントのセッションが動いたままで、メモリの空きは 12〜29%、スワップは最大 10GB 近くまで増えた。ほかのアプリとメモリを取り合うと、9B の生成は 6〜8 トークン/秒に、読み込みは 46〜57 に落ちた。しかも出力は 1 回 250〜450 トークンと長く、生成だけで 30 秒を超えた。

| モデル | 1 回の時間（中央） | 生成（中央） | 等速で流したときの、会議の終わりでの遅れ |
| --- | --- | --- | --- |
| Claude | 5.8 秒 | — | 2 秒 |
| Apple Intelligence | 14.2 秒 | — | 21 秒 |
| Qwen3.5-4B | 37.5 秒 | 11.9 トークン/秒 | 567 秒 |
| Qwen3.5-9B | 61.3 秒 | 6.2 トークン/秒 | 1,529 秒 |

この会議で差分更新を呼ぶ間隔（2 発言ごと）は、中央 35 秒だった。1 回がそれより長いと、遅れは会議の終わりまで溜まり続ける。遅れは、各呼び出しの時間を元の会議の時刻に当てはめて計算した（待ち時間なしで流したので、実際に詰まらせてはいない）。会議中に使う道具の速さは、会議アプリやブラウザを開いた、利用者の普段の状態で測らないと、楽観に倒れる。

### 4. 速さは、本番の長さのプロンプトで測る。短い指示で測った数字は、窮屈さを隠す

Apple Intelligence は、前のチケットで「1 回約 3〜5 秒」と測っていた。今回は中央 14 秒だった。前の計測は 2.7k トークンの指示で行ったもので、本番のプロンプトでは最初の呼び出しだけで約 4,000 トークンになる（システムプロンプトとスキーマとマップ）。さらに、会話を続けると 1 往復で約 1.4k トークン増えた。

Apple Intelligence の文脈長は 8,192 トークンで、これは 1 回の入力ではなく会話全体にかかる。Claude と同じ「14 回まで同じ会話を使い回す」設定では、4 回目に `Content contains 8387 tokens, which exceeds the maximum allowed context size of 8192.` で失敗した。3 回ごとに開き直す設定に変えても、長い回で 1 回超えた。失敗した回の発言は差分更新に反映されないので、文脈長の超過はそのまま取りこぼしになる。

### 5. 全編を流す前に、最初の数回で「速さ」と「当たるか」を見る

最初は、候補ごとに全編を流すつもりだった。しかし 9B の 1 本で 48 分かかった。Gemma 4 12B は 1 回 90〜130 秒で、全編なら 1 時間を超える。

そこで、残りの候補は最初の 6〜8 回だけを流し、「1 回の時間」と「操作が当たるか」の 2 つを見てから、全編に進むかを決めることにした。Gemma は 6 回で止めた（20 操作中 0 が当たり、1 回 96 秒）。指示 1 行の 9B も 8 回で止めた。この切り替えの後で全編まで流したのは、8 回で 28 操作すべてが当たった 4B だけだ。崩れ方が序盤で決まる失敗（1 節）は、数回で見分けがつく。

### 6. 計測の道具が機械を壊しかけた。出力先と空き容量に、先に柵を立てる

途中で 2 回、計測そのものでつまずいた。

1 つは、走っている Claude の計測のセッションのフォルダを、整理のつもりで別の場所に動かしたことだ。ログはパスで追記されていたので、次の書き込みで `ENOENT` になり、計測が落ちた。以後は、ランごとにセッションの置き場を分け（環境変数で親のフォルダを変える）、走っている間は触らないようにした。

もう 1 つはディスクだ。モデル（9B は 5.7GB、画像用の部品が 0.9GB、12B は 7.0GB）に加えて、スワップが同じボリュームで増え、空きが 155MB まで落ちた。スワップを増やせなくなると Mac 全体が不安定になるので、計測を止め、利用者に容量を空けてもらった。再開するときは、空きが 2GB を切ったら推論のサーバーと再生を止める見張りを、先に立てた。ローカルのモデルを利用者に勧めるときも、モデルの大きさだけでなく、スワップを見込んだ空き容量の目安が要る。これは地図の「案内」の霧に書き足した。

### 7. 調整の対象を 1 つに絞るときは、変更がモデルに依らない部分かを見る。残りの候補は「同じプロンプトで 1 回」で確かめる

結果を見た利用者から、「時間が大事なので、Apple Intelligence だけに絞って調整するか」と聞かれた。会議に追いつく見込みがあるのは Apple Intelligence だけ（14 秒。4B は 37 秒、9B 以上は 60 秒超）で、ダウンロードもディスクも要らない。プロンプトを削れば、文脈長に収まると同時に速くもなるので、2 つの調整が 1 つの作業で済む。

ただし絞ると、Apple Intelligence が使えない Mac（無効にしている、対象外の機種、会社の端末管理で止められている）ではローカルモードを出せなくなる。前のチケットでは、そういう Mac では Node で動かす内蔵のモデルに回すと決めていた。また macOS 26 では文脈長が 4,096 なので、実質 macOS 27 以上が対象になる。この 2 点を示して、利用者に確認した。

続けて、「Apple Intelligence を調整すれば、Qwen3.5-4B なども使い物になるのでは」とも聞かれた。答えは半分だった。考えている変更は、システムプロンプトを短くする、id をサーバーが振って仮 id を書かせない、出力を短くする、の 3 つで、どれもモデルに依らない作り方の変更だ。今回の失敗はすべて id で起きていたので、仮 id をなくせば失敗の元は消える。出力が短くなれば、4B の生成時間も縮む。一方で、2 節のとおり同じ指示への反応はモデルごとに違い、メモリの取り合いによる遅さはプロンプトでは直らない。

そこで、調整は Apple Intelligence だけで行い、最後に同じプロンプトで Qwen3.5-4B を 1 回だけ流して確かめることにした。4B 向けの調整はしない。4B も下限に届けば、Apple Intelligence が使えない Mac の代わりとして残し、届かなければ、そういう Mac ではローカルモードを出さない。調整に時間の区切りを置き、区切りまでに下限の見込みが立たなければ、そこで決め直す。候補を捨てるか残すかを、調整の副産物で判断できるようにした。

## 端末内の LLM で発言を語彙で直す試作を測ったら、LLM を外して読みの索引だけで置き換えることになった話

字幕の精度を上げる地図（[同じ日の最初のエントリ](#subtitle-accuracy-map)）で、発言を語彙で直す形を決めるチケットを解いた。発言は確定した文字起こしの 1 区切りで、語彙は会議に出てくる固有名詞・略語の正しい表記の集まりだ。[前のエントリ](#contextual-strings)で、音声認識に語彙を渡す口は効かないと分かったので、直すのは発言にした後の段になる。地図では最初から、手本の Kanary と同じ作りにするつもりだった。読みと表記の索引で候補を絞り、Mac の中で動く LLM（Apple の FoundationModels。Apple Intelligence のモデルをアプリから呼ぶ API）に「候補の番号か、どれでもない」を選ばせる作りだ。測ってみると、LLM は外すことになった。

- 決定の記録: [FoundationModels で発言を語彙で直す試作を測り、補正の形を決める](https://github.com/daiki-beppu/live-mindmap/issues/393)、地図 [Kanary を手本に字幕の精度を上げる](https://github.com/daiki-beppu/live-mindmap/issues/386)、用語の更新 [PR #489](https://github.com/daiki-beppu/live-mindmap/pull/489)

### 1. 読みは OS のトークナイザで取れる。崩れた表記どうしでも、ローマ字のキーにそろえれば候補を引ける

崩れ方は表記が合わないものばかりだ。「宍戸」は「シ子度」に、「情シス」は「上質」に、「Notion」は「ノーション」に、「ハコビズ」は「運び図」になる。表記の近さでは引けないが、読みはほぼ合っている。

読みには、macOS の `CFStringTokenizer` を使った。日本語を語に切り、語ごとのローマ字（`kCFStringTokenizerAttributeLatinTranscription`）を返す。「シ子度」は `shi/shi/do` になり、つなげると「宍戸」の `shishido` と同じになる。辞書を持ち込む必要はない。ローマ字は、長音・促音・`shi`/`si`・`ou`/`o` の揺れを潰したキーにそろえた。そのうえで、発言の中の 1〜5 語の区間と、語彙の語のキーを編集距離で比べた。

英字の語は、このトークナイザでは英字のまま返る（`Notion` は `Notion`）。そこで、語彙に入ったときに 1 度だけ、FoundationModels にカタカナの読みを聞いた。「ノーション」「ズーム」は合ったが、崩れたものもあった（PoC→ポック、PowerPoint→パワープーイント、UiPath→ユーパース、Slack→スラク）。崩れた読みに近い区間はまず無いので、その語が直らないだけで、誤って直す方向には働かなかった。OJT・KPI のような大文字だけの略語は、トークナイザが字ごとに読む（`ōjētī`）。

### 2. 正解率だけを見ると、壊した数が見えない。語彙の語が出てこない会議にもかけて、誤って直した数を数える

最初に、読みが近ければ置き換える形を、略語と製品名の会議（8 分、固有名詞・略語が 126 回出る）に、台本から作った 39 語の語彙でかけた。固有名詞の正解率は 62.7% から 96.0% に、CER（文字誤り率）は 11.0% から 2.4% になった。数字だけを見れば、もう決まりに見えた。

試作には、置き換えた語が台本の同じ時間帯に出ているかを数える機能を入れてあった。これで見ると、最初の版は「で相模原」を「相模原」に置き換えて、助詞の「で」を消していた。すでに正しい語に助詞がくっついた区間を、別の出現として拾っていた。

さらに、語彙の語がほとんど出てこない他の 4 つの合成会議にも、同じ 39 語の語彙をかけた。ここでは、置き換えはすべて誤りになる。誤りは会議ごとに 7〜71 件あった。語彙を 1,000 語に増やすと（会議から規則で取った語が多く混ざる）、どの会議でも CER が 20〜26% まで悪化した。正解率を測る素材だけでは、この側が見えない。

| 形（略語と製品名の会議） | 語彙 | 固有名詞の正解率 | CER | 誤って直した数 |
| --- | --- | --- | --- | --- |
| 補正なし | – | 62.7% | 11.0% | – |
| 読みが近ければ置き換え | 39 語 | 96.0% | 2.4% | 1（他の会議で 7〜71） |
| 同じ | 1,039 語 | 92.9% | 20.1% | 196 |

### 3. 決定的な規則の守りは、誤りの中身を並べて、型ごとに 1 つずつ足す

誤りを「区間→置き換えた語」で数えて並べると、型がはっきりしていた。

- 区間が助詞で始まる・終わる: 「の本→Notion」が 39 件
- 1 文字の区間: 「間→芦田」「一→位置」「客→契約」「今→居間」
- 送り仮名で終わる: 「開い→柊」「暗く→Slack」
- 読みが短い語に、たまたま近い: 「月→大槻」

それぞれに 1 つずつ守りを足した。区間の最初か最後の文字がひらがななら候補にしない。1 文字の区間は候補にしない。読みが 5 字以下の語は、読みの完全一致だけにする。

| 形 | 語彙 | 固有名詞の正解率 | CER | 誤って直した数 |
| --- | --- | --- | --- | --- |
| 守りあり | 39 語 | 96.8% | 2.1% | 0（他の会議で 0〜2） |
| 守りあり | 139 / 339 / 1,039 語 | 96.8% | 2.2 / 3.1 / 4.4% | 2 / 18 / 36 |

守りで落とした正しい置き換えは、ほとんど無かった（正解率はかえって上がった）。残った誤りは「開発→改札」「仮設→解説」「半信→本心」で、どれも語彙に混ざったふつうの語と、発言の中のふつうの語の取り違えだった。

### 4. LLM に「はっきり言えるときだけ選べ」と頼むと、取りこぼしも誤りも両方出る

残った誤りを止めるのが、LLM の役目のはずだった。Kanary と同じ形にした。区間を `[番号:区間]` で括り、出現ごとに「候補か NONE」だけを選べる型（`DynamicGenerationSchema` の `anyOf`）で答えさせる。指示も Kanary に倣い、文脈からはっきり言えるときだけ候補を選ばせた。

| 形 | 語彙 | 固有名詞の正解率 | CER | 誤って直した数 |
| --- | --- | --- | --- | --- |
| 守りあり（LLM なし） | 39 語 | 96.8% | 2.1% | 0 |
| 守りあり + LLM が選ぶ | 39 語 | 88.1% | 3.7% | 0 |
| 守りあり（LLM なし） | 1,039 語 | 96.8% | 4.4% | 36 |
| 守りあり + LLM が選ぶ | 1,039 語 | 94.4% | 4.1% | 22 |

語彙が正しいとき、LLM は正しい置き換えを 10 件捨てた（ノーション→Notion、ジラ→Jira、運び図→ハコビズ など）。語彙が大きいときは、「開発→改札」の 15 件を止めた。一方で、索引だけでは起きていなかった「前回→全体」を 22 件、自分から選んだ。候補を 3 件まで渡したので、2 番手以下の候補を拾ったのだ。

LLM には、遅れと動く環境の制約もある。1 回 0.4〜0.7 秒（静かなときの調査の値）で、Apple Intelligence が有効な Mac でしか動かない。索引だけなら数ミリ秒で、どの Mac でも同じに動く。両方を並べて、補正の段からは LLM を外した。FoundationModels は、英字の語の読みを 1 度聞くのにだけ使う。

地図の Notes には、最初から「補正の LLM は FoundationModels を使う（Kanary と同じ）」と書いてあった。手本の作りを前提にしていたが、手本の作りが自分の素材で効くかは、測るまで分からなかった。

### 5. 誤りの原因が入力の質なら、守りは入力の側に置く

残った誤りは、すべて語彙にふつうの語が混ざったときに出ていた。台本どおりの 39 語なら誤りは 0 で、ふつうの語が増えるほど誤りも増える（2 → 18 → 36）。補正の側で LLM を足して止めるより、語彙にふつうの語を入れなければ、誤りの元が無くなる。

用語集の「語彙」を「固有名詞・略語・社内の造語の正しい表記の集まり。ふつうの語は入れない」に改めた。会議から規則で取った語彙の候補は約 7 割がノイズなので、そこからふつうの語を除く手段を測るチケットを、地図に足した。

### 6. 端末内のモデルが一斉に失敗し始めたら、API を疑う前に、ディスクと負荷を見る

測っている途中で、FoundationModels の呼び出しが、どれも 0.1 秒以内に `com.apple.SensitiveContentAnalysisML error 15` で失敗し始めた。モデルの出力を検査する安全判定の段のエラーだ。Kanary と同じ guardrail の設定（`permissiveContentTransformations`）に変えても同じだった。

原因は別の所にあった。次に打ったコマンドが `no space left on device` で落ちて、ディスクが満杯だと分かった。並行して動く別の作業が埋めていて、load average は 24〜50 まで上がっていた。空きを作ると呼び出しは通るようになった。それでも、空きが減るにつれてまた失敗が出て、1 回が 2〜20 秒（最大 548 秒）かかった。このため、この日の遅れの数字は判断に使わず、静かなときの調査の値を使った。

試作は、判定に失敗したら直さずに出し、3 秒おいて 3 回まで試し直す形にした。製品でも、失敗したら直さずに出すのが前提になる。

手元で同じように測るなら、試作（`prototype/vocab-correction-393` ブランチ）を次のように使う。

```sh
swiftc -O helper/bench/proto-vocab-correct/main.swift -o /tmp/vocab-correct
/tmp/vocab-correct <確定結果.jsonl> --vocab <語彙.txt> --mode index --strict --min 0.8 \
  --readings <読みのキャッシュ.tsv> --timeline <台本の timeline.tsv> --out <直した.jsonl> --log <変更.jsonl>
node server/bench/sttAccuracy.ts <台本の timeline.tsv> <直した.jsonl> --terms <語彙.txt>
```
