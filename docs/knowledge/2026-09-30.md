## 会議 AI の回帰評価用に、公開会議の音声サンプルを 1 時間で揃えた話

差分更新エンジンの試作と回帰評価に使う「会議の録音と文字起こし」を用意したときの学び。

- 決定の記録: [回帰評価用の会議録音サンプルを用意する](https://github.com/daiki-beppu/live-mindmap/issues/4)
- 前提の調査: [Kanary で準リアルタイムの文字起こしを取れるか](https://github.com/daiki-beppu/live-mindmap/issues/3)

### 1. 自分の会議が無くても、公開会議で評価は始められる

手元に録音が 1 件も無かった。「次の会議を録る」のを待つと日数がかかるので、動画サイトで公開されている会議で代用した。この素材は後に、内容を書き換えて合成した会議に置き換えた（[その後](#meeting-samples-afterwards)）。

公開会議には次の利点がある。

- **社外秘の問題が起きない**。会議内容を LLM に渡してよいかの確認が不要になる。このプロジェクトでは、社外秘の会議は LLM に渡さないと決めた
- **すぐ手に入る**。検索して、切り出して、文字起こしするまで 1 時間かからない

欠点は、全員の声が 1 本に混ざったミックス音声なこと。自分の声（マイク）と相手の声（システム音声）を分けて扱う処理は、公開会議では評価できない。そこは自分の会議で後から録る。

### 2. サンプルは「性質が逆の会議」を組み合わせる

1 本だけだと、その会議に合わせてプロンプトを調整してしまう。性質が逆の 2 本を選んだ。

| サンプル | 性質 | 何の試験になるか |
| --- | --- | --- |
| ファシリテーター同士の会議（先頭 60 分） | 収束型。1 つのテーマで論点を整理し、対立意見を扱い、途中で前の論点に戻る | 同じ話題に戻ったときに、新しいノードを増やさず「統合」できるか。解説員の割り込みに「何もしない」を返せるか |
| アプリのアイデアを出し合うブレスト（先頭 60 分） | 発散型。1 人ずつ案を発表し、周りが突っ込む | 案が大量に出ても、マップが破綻しないか |

収束型では統合が、発散型では追加が主な操作になる。両極端を押さえておくと、片方に最適化したときの劣化に気づける。

途中に入る「会議ではない発言」（解説員のコメントや司会の段取り）は雑音ではなく、試験項目として価値がある。実際の会議でも雑談や脱線は必ず起きるからだ。

### 3. タイトルを信じず、数カ所を試し起こししてから選ぶ

同じブレストのシリーズの **前編** を選んだら、60 分のほぼすべてが技術セッションの発表で、ブレストは 1 秒も無かった。タイトルに「会議」とあっても、中身が会議とは限らない。

全文を文字起こしする前に、**数カ所を 1 分ずつ切り出して試し起こし**すると安く確かめられる。

```sh
for m in 0 10 20 30 45 60 75 90 105; do
  ffmpeg -loglevel error -y -ss $((m*60)) -t 60 -i full.m4a -ac 1 probe-$m.wav
  echo "## ${m}min: $(kanary transcribe probe-$m.wav --lang ja | jq -r '[.transcript.segments[].text]|join("")' | cut -c1-160)"
done
```

110 分の後編でも、9 カ所・合計 9 分の試し起こしで「全編が案の発表と突っ込みで、使える」と判断できた。

### 4. ローカル STT（Kanary）で 60 分を丸ごと文字起こしした結果

Mac のローカル文字起こしアプリ Kanary の `kanary transcribe`（ライブラリに登録しない使い捨ての文字起こし）で、60 分の音声を 1 ファイルのまま処理した。

- **60 分は Pro なしで通った**。制限は「1 ファイル 75 分超は Pro が必要」なので、それより長い会議は先に切り出す
- **segment は粗い**。60 分で 196〜220 segment、1 segment あたり平均約 17 秒。発言単位の細かい時刻が欲しいなら、自前で短く区切って渡す必要がある
- **話者は分かれない**。ミックス音声なので、結果の track はすべて `speaker` になる
- **略語や固有名詞は崩れる**。「OJT」が「OT」「OP」に、人名も別の字になった。差分更新のプロンプトは、文字起こしに誤りがある前提で作る必要がある
- `--lang ja` で言語を固定した（自動判定に任せない）

### 5. 「サンプルを用意する」も、判断の塊だった

作業チケットのつもりで着手したが、実際には人が決めることが 3 つあった。

1. どこから用意するか（実会議を録る / 手元の録画 / 公開会議 / 台本で模擬会議）
2. 社外秘を LLM に渡してよいか
3. どの会議を選ぶか

エージェントは候補を探して並べ、試し起こしで中身を確かめるところまでを担い、選ぶのは人にした。この分担だと、人が関わるのは選択肢を選ぶ 3 回だけで済み、残りの作業は待たずに進んだ。

## LLM が差分更新するマインドマップの語彙を、「LLM が迷わない」基準で決めた話

マップのノード種別・関係・根拠・差分操作を決めたときの学び。コードを書く前に、エージェントとの問答（grilling）で 2 往復半かけて決め、`CONTEXT.md` の用語集に書き起こした。

- 決定の記録: [マップのドメインモデル：ノード種別・関係・根拠の単位](https://github.com/daiki-beppu/live-mindmap/issues/5)
- 用語集: [`CONTEXT.md`](../../CONTEXT.md)、判断の記録: [ADR 0001 マップのノード同士の関係は親子だけにする](../adr/0001-map-is-a-tree.md)

### 1. 出発点は README の 7 つの要素だった

README には「マップで扱う要素」として、議題・論点 / アイデア / 選択肢 / 決定事項 / 未決事項 / 課題 / TODO / 担当者 が並んでいた。人が読む分にはこれで伝わるが、LLM に「この発言はどの種別か」を選ばせる語彙としては曖昧すぎた。

最終的には 6 つの種別になった。

| 種別 | 意味 | 状態・属性 |
| --- | --- | --- |
| 議題 | 話題のまとまり。答えを出す対象ではない | なし |
| 論点 | 答えを出すべき問い | `未決` / `決定済み` |
| 案 | 論点への答えの候補、または自由なアイデア | `検討中` / `却下` |
| 決定 | 論点への答え。論点の子に置く | なし |
| 課題 | 問題や懸念。答えを出す対象ではない | なし |
| TODO | 後で行う作業 | 任意の担当者・期限 |

以下は、この形にたどり着くまでに使った判断の基準。

### 2. 種別は「答えを出す対象か」という 1 本の軸で切る

「議題」「論点」「課題」は、どれも「話していること」なので区別がぼやける。そこで「会議の中で答えを出す対象か」で切った。

- **論点**: 答えを出す問い（「どの施策を試すか」）。未決 / 決定済みの状態を持つ
- **議題**: 答えを出さない話題のまとまり（「OJT 受け入れ」）
- **課題**: 答えを出さない問題の記述（「現場の 2 人が問題意識を持っていない」）。答えを出すべき問いになった時点で、別の論点として立てる

軸が 1 本だと、LLM への指示も「答えを出すものか？」の一問で済む。種別の定義が「何であるか」の説明だけだと、境界の事例で判断が揺れる。

### 3. LLM が安定して見分けられない区別は、まとめる

「アイデア」と「選択肢」は分けなかった。ブレストのアイデアは「どんなアプリを作るか」という論点への選択肢とも言え、収束型の会議の「施策案」はどちらとも呼べる。人間でも迷う区別を LLM にさせると、同じ内容が回ごとに違う種別になる。

まとめた「**案**」は、親が論点なら答えの候補、親が議題なら自由なアイデア、と**位置**で意味が決まる。種別を増やす代わりに構造に意味を持たせると、LLM が選ぶものが減る。

同じ理由で、AI の差分操作からは**種別の変更をなくした**。自動更新されるマップで種別が変わると、見た目がちらつく。種別の誤りを直す手段は、人がマップを修正できるようにするかどうかとまとめて後で決める。

### 4. 状態は、持たせるより構造から導く

「未決事項」は種別にせず、論点の状態にした。さらにその状態も LLM に書かせず、「決定の子を持つかどうか」から**自動で決まる**ようにした。

- 論点に決定を追加すると、その論点は `決定済み` になる
- 決定を削除すると、その論点は `未決` に戻る

これで README にあった「解決」という操作が不要になった。解決は「論点に決定を追加する」ことと同じ意味だからだ。操作が 1 つ減るうえに、「決定があるのに論点が未決のまま」という食い違いが起こり得なくなる。

決定を論点の状態や属性にせず、独立したノードにしたのは、実際の決定が「案 A と案 B を組み合わせて、まず 1 か月試す」のように、1 つの案と一致しないことが多いからだ。

### 5. 根拠の単位は、STT が返す区切りに合わせる

「ノードをクリックすると元の発言が見える」ために、ノードと文字起こしをどの単位で結ぶかを決めた。

- **採用**: STT の 1 区切り（これを「発言」と呼ぶ）の参照を、ノードが複数持つ
- **見送り**: 発言の中の文字の範囲まで持つ

文字の範囲まで持つと、LLM に文字の位置を正確に返させる必要がある。STT の誤認識もあるので不安定になる。発言は複数人の話が混ざった十数秒の塊だが、クリックしたときに全文を見せれば根拠としては十分だった。

あわせて「**すべてのノードは根拠を 1 つ以上持つ**」を必須にした。根拠のないノードは AI の推測なので作らせない。この制約 1 つで、根拠を表示する機能がすべてのノードで成り立つ。

### 6. 「何もしない」も操作として出させる

新しい発言を見てマップを変えない場合も、「何もしない」を明示的な操作として返させ、ログに残す。操作を 1 つも返さないことで表すと、回帰評価のときに「発言を見落とした」のか「見たうえで変えなかった」のかを区別できない。

録音サンプルには、解説員の割り込みのような「会議ではない発言」が入っている。これに「何もしない」を返せたかどうかが、そのまま試験項目になる。

### 7. 用語集に書き起こすと、決めたことどうしの矛盾が見つかる

問答で「更新は本文と根拠だけを変える（種別は変えない）」と決め、別の問いで「却下された案は削除せず `却下` の状態にする」と決めた。どちらもその場では妥当だったが、`CONTEXT.md` に書き起こしてみると、案を `却下` にする操作がどこにもなかった。

問答の答えを一覧に並べ直す段階で初めて矛盾が見えた。決めたそばから用語集に書くと、この種の穴が問答の中で埋まる（ここでは「更新で案の状態も切り替えられる」にした）。

### 8. ADR は「元に戻しにくいもの」だけに絞る

判断はたくさんしたが、ADR にしたのは「ノード同士の関係は親子だけ（木をまたぐリンクは持たない）」の 1 つだけ。リンクを後から加えると、差分操作・操作ログ・描画のすべてに手を入れることになるうえ、描画ライブラリの候補も変わる（markmap はリンクを描けない）。

「根拠は発言の単位」は、後から細かい単位に変えても既存のデータと両立するので ADR にしなかった。意外に見えるか、実際に比べて選んだか、元に戻しにくいか、の 3 つがそろったものだけを残すと、ADR が読まれる量に収まる。

### その後: 用語の定義は試作で直される

この回で決めた「更新」は、その後の差分更新エンジンの試作で「本文を**言い直す**（書き足さず、全文を置き換える）」と定義し直した。同じ話題に戻ったとき、同じ主張の繰り返しは更新で根拠を足すだけにし、別の主張は子の追加で表す、という線引きも加わった（[差分更新エンジン：操作スキーマ・プロンプト・更新タイミング](https://github.com/daiki-beppu/live-mindmap/issues/6)）。

問答で決めた語彙は出発点で、実際の会議を流すと境界が動く。用語集が 1 か所にあると、直すときもその 1 か所で済む。

## LLM にマインドマップを差分更新させるプロンプトと、System One モデルの前段ゲートを実測した話

差分更新エンジン（文字起こしを受け取り、既存のマップへの変更を LLM に出させる部分）を試作したときの学び。公開会議の録音 2 本（収束型のファシリテーター会議・発散型のアプリブレスト、各 60 分）を時間順に再生し、Claude Sonnet 5.5 に差分操作を出させて、マップの形・コスト・遅延を測った。あわせて、Claude の手前に System One モデル（選択肢から選ぶだけで文章を生成しない判断専用モデル）の Jev を置く案も試した。

- 決定の記録: [差分更新エンジン：操作スキーマ・プロンプト・更新タイミング](https://github.com/daiki-beppu/live-mindmap/issues/6)
- 用語集: [`CONTEXT.md`](../../CONTEXT.md)（ノード種別と差分操作の語彙）

### 1. LLM には操作だけを出させ、規則の検証はマップ側で行う

LLM に毎回マップを作り直させると、ノードの id が変わって表示がちらつき、根拠（ノードの元になった発言）の対応も崩れる。そこで、既存のマップへの**差分操作**だけを返させた。操作は 6 種類で、`追加・更新・統合・移動・削除・何もしない`。構造化出力の JSON スキーマで、操作ごとの形を anyOf で縛った。

```text
{ ops: [
  { op: "add", ref: "a1", parent: "n3", kind: "論点", text: "…", evidence: ["s41"] },
  { op: "add", ref: "a2", parent: "a1", kind: "決定", text: "…", evidence: ["s42"] },   // 同じ応答で作った a1 を親にできる
  { op: "update", node: "n7", evidence: ["s43"] },
  { op: "noop", reason: "進行の段取りだけ" }
] }
```

受け取った操作は、マップ側の純粋な関数で 1 つずつ検証してから適用する。決定の親は論点に限る、決定と TODO は子を持たない、削除は子のないノードだけ、統合は同じ種別どうし、根拠は既に届いた発言だけ、といった規則を、プロンプトではなくコードで守らせる。

約 800 回の呼び出しで、規則違反は 2 件だった（空のマップで、存在しない親 `n1` を指定した）。プロンプトに「ルートの id は root」と 1 行足して消えた。**スキーマで形を縛り、規則はコードで弾き、弾いた理由を記録する**。この分担にすると、プロンプトは「何をどこに置くか」の判断に集中できる。

ただし、仮 id（`ref`）で同じ応答内の追加を親にできる設計には裏がある。先頭の追加が弾かれると、それを親にした後続の追加も連鎖して落ちる。

### 2. Agent SDK で試作するなら、まずユーザー設定の読み込みを切る

試作は Claude のサブスクリプションから呼ぶため、Claude Agent SDK を使った（API キーではなく Claude Code の認証で動く）。最初の 1 回は、20 トークンの入力に対して 16 万トークンのキャッシュが作られ、概算 $0.18・19 秒かかった。原因は、手元の Claude Code に入れていたプラグイン・MCP サーバー・スキルの定義が、毎回の前置きとして読み込まれていたことだった。

```ts
query({ prompt, options: {
  model: "claude-sonnet-5-5", systemPrompt: SYSTEM,
  tools: [], settingSources: [], persistSession: false,
  mcpServers: {}, strictMcpConfig: true, plugins: [], skills: [], agents: {},   // これを足すまで前置きが 16 万トークン
  outputFormat: { type: "json_schema", schema: SCHEMA },
}})
```

`settingSources: []` だけでは消えず、プラグイン・スキル・MCP を明示的に空にして、**1 回 $0.004・4 秒**になった。なお、SDK が返す費用は API の定価で見積もった値で、サブスク経由なら請求額ではない。構造化出力は内部で「StructuredOutput ツールの呼び出し → 結果」の 2 ターンになるので、API を直接呼ぶ本番より遅く高めに出る。

### 3. 操作の定義の一文が、マップの形を決める

同じ会議を、プロンプトだけ変えて 3 回流した（2 発言ごとに呼び出し、60 分）。

| | ノード数 | 本文の長さ p90 / 最大 | 深さ | 決定 / TODO | 概算費用 |
| --- | --- | --- | --- | --- | --- |
| v1 | 52 | 119 / 427 字 | 5 | 4 / 1 | $1.85 |
| v2 | 103 | 33 / 42 字 | 9 | 2 / 0 | $1.91 |
| v3 | 38 | 37 / 45 字 | 4 | 3 / 1 | $1.39 |

- **v1**: 用語集に書いた「同じ話題に戻ったときの続きも更新で表す」をそのままプロンプトに入れた。Claude はこれを「本文への追記」と読み、1 つの課題に 10 分ぶんの議論を書き足し続けた。1 ノードが 427 字、1 つの論点の直下に課題が 20 個並んだ
- **v2**: 本文を 40 字以内にし、「続きは本文に書き足さず子ノードにする」とした。今度は「課題の子の課題の子の課題…」と 9 段まで掘り下がり、ノードが倍増した。「本文に書き足さない」を「更新しない」と受け取り、更新が 28 回から 2 回に減った。決定と TODO も案として置かれた
- **v3**: 子にするのは**親と別の主張**（別の理由・懸念・派生した案）のときだけ、言い換えや具体例は根拠を足す更新にとどめる、と基準を言葉にした。決定と TODO は「〜を基準にする」「〜さんが〜する」のような言い方の例を添えた

v1 と v2 は、同じ緊張関係の両端だった。「同じ話題の続きをどこに置くか」を本文に寄せると肥大化し、子に寄せると増殖する。**操作の意味を 1 文変えるだけで、マップの形は振り子のように揺れる**。中間に止めるには、「どちらにするか」ではなく「何を基準に分けるか」を書く必要があった。

この結果に合わせて、用語集の「更新」も「本文を言い直す（書き足さず全文を置き換える）」に直した。

### 4. LLM には、マップ全体の予算を毎回見せる

v3 で一番効いたのは、毎回のプロンプトの先頭に足した 1 行だった。

```text
## マップの状態
経過 23 分・ノード 31・最大の深さ 4（目安: 60 分で 50 前後、深さ 4 まで）
```

各呼び出しで Claude が見ているのは「新しい 2 発言」なので、マップ全体がどれだけ膨らんだかを意識できない。予算に対する現在地が見えるようになると、新しいノードを足す代わりに既存ノードの更新を選ぶようになった（更新 2 回 → 31 回）。人が会議メモを取るときの「もう書きすぎたな」という感覚を、数字で渡している。

ノードが減ったぶん、毎回渡すマップのアウトラインも小さくなり、費用も 25% 下がった。

### 5. 後から組み替える操作は、指示しても使われない

v2 と v3 には「1 つの親の下に同じ種別が 6 つを超えそうなら、論点を立てて移動で束ねる」と書いたが、移動と統合は 2 本の会議を通して**一度も出なかった**。v3 でも、最初の論点の直下には課題が 11 個並んだ。

各呼び出しは「新しい発言をどう載せるか」に注意が向いていて、既存の構造を見直す動機がない。組み替えを効かせたいなら、数分おきに「整理だけをする呼び出し」を別に挟むのがよさそうだ。操作の種類を定義しても、それを使う場面を作らなければ使われない。

### 6. 構造化出力では、小さいモデルほど遅く高くなることがある

Haiku 4.5 でも同じ条件で流したところ、1 回 40〜70 秒かかり、費用は Sonnet 5.5 の約 4 倍になった。anyOf の入った JSON スキーマの検証に落ちて、SDK の中で再試行を繰り返していたと見ている。会議の 23 分目で打ち切った。

「安いモデルで回数を稼ぐ」は、出力の形が複雑だと成り立たない。モデルの単価ではなく、**完了した 1 回あたりの費用と時間**で比べる必要がある。

### 7. 反映の遅れは、発言の長さと呼び出しの間隔で決まる

発言（STT が返す文字起こしの 1 区切り）が終わってから、それがマップに載るまでの遅れを、呼び出しの間隔ごとに測った（ファシリテーター会議、Sonnet 5.5）。

| 呼び出しの間隔 | 発言が終わってから反映まで p50 / p95 | 話し始めてから反映まで p50 / p95 | 概算費用 / 60 分 |
| --- | --- | --- | --- |
| 1 発言ごと | 2.9 / 4.0 秒 | 20 / 32 秒 | $3.97 |
| 2 発言ごと | 10.6 / 30.6 秒 | 28 / 51 秒 | $1.85 |
| 4 発言ごと | 28.6 / 68.1 秒 | 46 / 89 秒 | $0.99 |

Claude の応答自体は約 3 秒で、間隔を変えてもほぼ変わらない。遅れの大半は、**発言そのものの長さ**（このサンプルでは平均 13〜17 秒）と、**次の発言が来るまで待つ時間**から来ている。リアルタイム性を上げたいなら、LLM を速くするより、発言を短く区切るか、呼び出しの間隔を詰めるのが先になる。間隔を半分にすると、費用はほぼ倍になる。

### 8. System One モデルの精度は、質問の設計で決まる

Jev（TypeSafe AI）は、状態（テキスト）と型付きの質問（yes/no・選択・スコア）を送ると、選択肢ごとの確率を約 0.2 秒で返す。これを Claude の手前に置き、発言ごとに「中身があるか」を判定して、雑談なら Claude を呼ばずに捨てるゲートを試した。

正解ラベルには、Claude を 1 発言ごとに呼んだランを使った。発言ごとに「マップを変えたか」が分かっているので、ゲートの判定と突き合わせられる（ラベルは人の判断ではなく Sonnet の判断なので、「Sonnet と同じ判断を安くできるか」の評価になる）。

最初の設計では、直前の 3 発言と新しい発言の文面だけを渡し、「会議の中身を述べているか」を yes/no で聞いた。収束型の会議では、冒頭の解説員の前置きをきれいに捨てた（捨てる 24%、取りこぼし 1%）。ところが**発散型のブレストでは、アイデアの 45% を雑談と判定して捨てた**。おバカアプリのアイデアは、会議の目的を知らずに文面だけ読めば冗談にしか見えない。

一度は「System One モデルは文脈に依存する判断に弱い」と結論づけかけた。だが、同じデータで別の質問（次の節の「どのノードの話か」）の結果を見ると、取りこぼしは 7% だった。**同じモデル・同じ発言でも、質問の立て方で 45% と 7% に分かれた**。失敗の主因はモデルではなく、質問の構造だった。

まず、判断に要る文脈を状態に入れ、判断の基準を選択肢の側に書き出した。

- 状態に**会議の目的**（「おバカなアプリのアイデアを 1 人ずつ発表し、周りが突っ込むブレスト会議」）と**現在のマップ**を入れる
- 「中身があるか」の yes/no をやめ、**役割を 8 択**で選ばせる（新しい案・課題・問い・決定・TODO・既存の話の補足・進行・雑談）

「中身があるか」は判断の基準をモデルに丸投げする質問で、8 択は基準を選択肢の側に書き出す質問になっている。これだけで、ブレストの役割の分布は「案」71 件、ファシリテーター会議は「補足」100 件・「課題」25 件と、会議の性質どおりになった。**System One モデルでは、質問の設計がそのままプロンプトエンジニアリングになる**。

一方、「話題が切り替わったか」は、どの設計でも判定できなかった。yes/no で聞くと確率が 0.18〜0.40 に固まり、関係するノードの変化から導くと 196 発言中 129 回も「切り替わり」になった。

### 9. ゲートには「拾うもの」ではなく「捨ててよいもの」を、マップに照らして判定させる

取りこぼしを 45% から 1〜2% まで下げたのは、質問の構造を 2 つの軸で反転させたことだった。

**1 つ目の反転: 発言を単体で判定するのをやめ、マップに照らして判定させる。** 「この発言は会議の中身か」という絶対的な問いは、会議の目的を知らないと答えられない。代わりに、選択肢にマップの全ノードと「どれにも関係しない」を並べ、「この発言はどのノードの話か」と聞いた。問いが「中身かどうか」から「既にある議論のどこに当たるか」に変わると、モデルは発言の文面と各ノードの本文を突き合わせるだけで済む。この質問は、Claude が実際に更新したノードとの一致が 86% で、それ自体が次の節の仮表示の材料にもなった。

**2 つ目の反転: 「拾う判定」をやめ、「捨てる判定」にする。** 最初の設計は「中身の確率が閾値より低ければ捨てる」、つまり**迷ったら捨てる**だった。これを、「役割が進行か雑談」**かつ**「どのノードにも関係しない」の両方が成り立つときだけ捨てる、**迷ったら通す**に変えた。

| 捨てる条件 | 収束型 捨てる / 取りこぼし | 発散型 捨てる / 取りこぼし |
| --- | --- | --- |
| 迷ったら捨てる: 文面だけで「中身があるか」< 0.3 | 24% / 1% | 61% / 45% |
| マップに照らす: どのノードにも関係しない | 18% / 1% | 20% / 6% |
| 役割で判定: 進行・雑談 | 29% / 5% | 29% / 5% |
| **迷ったら通す: 進行・雑談 かつ どのノードにも関係しない** | **14% / 1%** | **18% / 2%** |

反転させた理由は、誤りの重さが非対称だからだ。雑談を通してしまった場合の損失は、Claude の呼び出し 1 回ぶん（約 $0.01）で、Claude が「何もしない」を返せば済む。決定や TODO を捨ててしまった場合は、その発言はマップに二度と載らない。**高い処理の手前に置くフィルターは、既定を「通す」にして、捨てるには独立した 2 つの根拠を要求する**。2 つの質問は別々の観点（発言の役割と、マップとの関係）なので、片方の誤判定をもう片方が打ち消す。

代わりに、捨てられる量は 61% から 18% に減った。この試作では、節約は小さくなっても取りこぼしを減らすほうを取った。会議の種類ごとに閾値を較正しなくても、どちらの会議でも取りこぼしが 1〜2% に収まったのも、この構造の効果になる。

### 10. 前段ゲートの価値は、節約より速さにある

Jev の単価は入力 100 万トークンあたり $0.042（出力は無料）で、状態にマップを入れても 60 分で約 117 万トークン、**約 $0.05** だった。Claude（60 分で約 $1.4〜2）の約 1/40 になる。

それでも、差分更新のゲートとしては MVP に入れなかった。捨てられる発言は 14〜18% で、捨てられるのは前置きや雑談のように、もともと入力が小さい区間になる。60 分で浮くのは $0.3 程度で、反映の遅れも減らない（遅れは 7 節のとおり発言の長さで決まる）。1 発言ごとに呼ぶ（費用が倍になる）ときや、長い会議の費用対策として残した。

代わりに有望だったのは速さのほうだった。「どのノードに関係するか」の答えは、Claude が実際に更新したノードと 86% 一致し、しかも 0.2 秒で返る。Claude の 3 秒と待ち時間を待たずに、該当ノードを「いま話している」と光らせることができる。**0.2 秒と 3 秒という桁の違いは、LLM の手前ではなく、表示の即時フィードバックで活きる**。

### その後: 仮表示は採用され、発言の長さは STT 側で決まった

- 「マップの見せ方」を決めたチケットで、Jev による「いま話している」ノードの仮表示を MVP に入れると決めた。2 発言ごとに Claude を呼ぶ設計の反映待ち（p50 約 11 秒・p95 約 31 秒）を埋めるためで、差分更新の前段ゲートとして使うかは引き続き別の判断にしている（[マップの見せ方：描画ライブラリ選定・ノード種別の表現・更新アニメーション](https://github.com/daiki-beppu/live-mindmap/issues/7)）
- 音声取得と STT を決めたチケットで、STT は Apple の SpeechAnalyzer をストリーミングで使うことになった。発言は STT の確定結果そのもので、長さは p50 8.6〜13.4 秒。確定前の**途中結果**は 0.1 秒以内に届くが、書き換わるので差分更新には使わず、字幕と仮表示にだけ使う。音声の終わりから確定まで p50 6 秒かかり、Claude を足したマップへの反映は p50 18〜22 秒の見込み。7 節の「遅れの大半は発言の長さ」は、本番の STT でもそのまま当てはまった（[リアルタイム音声取得と STT の経路](https://github.com/daiki-beppu/live-mindmap/issues/9)、[ADR 0002](../adr/0002-local-stt-helper.md)）

## 数秒ごとに育つマインドマップの描画ライブラリを、実データの再生で見比べて選んだ話

マップを描く部分を決めたときの学び。React Flow・markmap・Plait（Drawnix の中身）の 3 つで、同じマップを描く試作を作った。差分更新エンジンの試作で記録したラン結果（60 分の会議 2 本ぶんの、30 秒ごとの差分操作とマップ）を時間順に再生して見比べ、最後は 4 つ目の案として、React Flow で Plait 風に描き直したものを選んだ。

- 決定の記録: [マップの見せ方：描画ライブラリ選定・ノード種別の表現・更新アニメーション](https://github.com/daiki-beppu/live-mindmap/issues/7)
- 用語集: [`CONTEXT.md`](../../CONTEXT.md)（ノード種別と差分操作の語彙）

### 1. 架空のデータではなく、LLM が実際に出した差分を再生して比べる

描画ライブラリの比較は、サンプルの木を 1 つ描けば済みそうに見える。だが、このアプリで難しいのは静止画ではなく、**30 秒ごとに外からマップが書き換わること**だ。そこで、差分更新エンジンの試作が残したラン結果をそのまま再生した。

```text
steps[i] = {
  at,        // 会議の中の秒。Claude を呼んだ時刻
  applyAt,   // at + Claude の応答時間。マップに反映される時刻
  results,   // 適用した操作（追加・更新…）と、対象ノードの id
  map,       // 適用後のマップ全体
}
```

再生の画面には、再生速度（×1〜×180）、時刻のスライダー、「次の変化へ飛ぶ」ボタンを置き、`?variant=A|B|C|D` で描画だけを差し替えられるようにした。Claude は呼び直さないので、60 分の会議を ×60 で 1 分で見られる。

実データならではの発見が 2 つあった。

- 実際のランでは、統合と移動（ノードを後から組み替える操作）が 1 回も出ない。そのままでは、それらの見せ方を試せない。そこで、ある反映以降のすべてのマップに「このノードを移す」「このノードをまとめる」という変形を手でかけて混ぜた。変更の一覧には `*` を付け、手で混ぜた操作だと分かるようにした
- 1 本だけ見ていたら気づかない偏りがあった。収束型の会議は課題が多く（38 ノード中 17）、発散型のブレストは案が大半（58 ノード中 45）だった。種別の色分けは、この両方で読めるかを見る必要がある（5 節）

### 2. 差分更新との相性は、ライブラリがノードの同一性をどう決めるかで決まる

「何が変わったか」を目で追えるかは、アニメーションの有無より手前で決まっていた。**更新の前と後で、同じノードを同じものと認識できるか**である。

| ライブラリ | ノードの同一性 | 差分更新で起きたこと |
| --- | --- | --- |
| React Flow | 渡した `id` | 位置の変化を CSS の transition で滑らかに動かせた |
| markmap | 親の連番 + 自分の連番 + 本文のハッシュ | 追加のたびに、後ろのノードがすべて作り直された |
| Plait | 要素の木を丸ごと渡し直す | 渡すたびに全体を画面に収め直し、アニメーションは無い |

markmap は、ノードのキーを木をたどる順の連番で作る。

```js
// markmap-view の _initializeData（整形済み）
node.state.id  = ++i;   // 木をたどる順の連番
node.state.key = [parent?.state.id, node.state.id].join(".") + hash(node.content);
```

途中にノードが 1 つ増えると、それより後ろの連番がすべてずれる。キーが変わったノードは、d3 から見ると「消えて新しく現れた」ことになる。内部メソッドを上書きしてキーを `id + 本文` にすれば直せたが、本文を差し替える経路はそもそも無く、本文が変わったノードは作り直しになる。

**差分更新するマップの描画ライブラリは、まず「外から渡したノードの id をそのまま同一性に使えるか」で選ぶ**。アニメーションの滑らかさは、その上に乗る話だった。

### 3. 「綺麗さ」はライブラリではなく描き方から来る

4 つの案を並べたところ、見た目の評価は次のようになった。

- A（React Flow、種別の色帯つきカード＋バッジ＋影）は「AI 臭すぎる」
- C（Plait）は、ぱっと見で一番綺麗

ここで C に決めかけたが、C の見た目の要素を分解すると、どれも Plait でなければ描けないものではなかった。

- 種別ごとに 1 色だけを使い、ノードの淡い塗り・枠・親からの枝をその色で揃える
- 枝は太い曲線で、根元ほど太い
- 種別の名前やバッジを文字で出さない

そこで、A と同じ React Flow の仕組みのまま、描き方だけを C に寄せた案 D を作った。約 120 行で、見比べた結果は「この見た目で OK」だった。

A が AI 臭く見えた理由は、情報を足しすぎたことだった。種別の文字ラベル、状態のバッジ、変化のバッジ、影、色帯を 1 つのノードに重ねていた。**見た目の好みで描画ライブラリを選ぶ前に、描き方だけを入れ替えた案を 1 つ作る**。見た目は後から CSS で寄せられるが、ノードの同一性（2 節）とエコシステムの寿命（4 節）は、後から変えられない。

### 4. 保守性は、本体ではなくフレームワーク向けの部品まで見る

Plait の本体（`@plait/core`）は、調べた日の数日前にも更新されていた。本体だけを見れば活発に見える。問題は、React から使うための部品のほうだった。

| | 週あたりのダウンロード | 最後の更新 |
| --- | --- | --- |
| `@xyflow/react`（React Flow） | 約 1,408 万 | 数日前 |
| `markmap-view` | 約 16 万 | 2025 年 6 月 |
| `@plait/core` | 約 1,200 | 数日前 |
| `@plait-board/react-board`（Plait の React 部品） | 約 350 | 2025 年 12 月（0.4.0 のプレリリース） |

React 部品は `@plait/*` の 0.89 系に依存したまま止まっていて、本体の最新は 0.94 だった。何も考えずに入れると、本体の 0.94 と、部品が抱える 0.89 が二重に入り、`PlaitBoard` の型が噛み合わずにビルドが通らない。すべてを 0.89.2 に固定して、ようやく動いた。部品の CSS も package の `exports` に入っておらず、`node_modules` のパスを直接書いて読み込んだ。

本家の Drawnix（GitHub のスター約 1.5 万）は、この React 部品を npm からではなく、自分のリポジトリの中のソースで使っている。つまり Plait を React から使うなら、この部品を自分たちで抱えて、本体の更新に追従し続けることになる。**「本家のアプリが使っている」と「npm の部品が保守されている」は別の事実**で、確かめるには本家の `package.json` と、部品の公開日を並べて見るのが早い。

### 5. 種別の色が効くのは、同じ段に違う種別が混ざるとき

種別（議題・論点・案・決定・課題・TODO）ごとに 1 色を割り当てた。案 D で見ていると、「青・黄・赤の違いは深さ？」と聞かれた。

収束型の会議のマップは「会議 → 議題 → 論点 → 課題」とほぼ段ごとに種別が揃っていて、**色が深さを繰り返しているだけ**に見えていた。色から新しい情報が読めるのは、論点の下に 課題（赤）・案（紫）・決定（緑）が並ぶような、同じ段に違う種別が混ざる場面だけだった。発散型のブレストは、逆にほぼ紫（案）一色になる。

「決定・TODO・未決の論点だけ目立たせ、残りは控えめにする」という、重要度で色を絞る案も出た。ひとまず 6 色のままにしたが、**種別の色分けの価値は、マップの形（どれだけ種別が混ざるか）で変わる**ので、種別の数だけ色を用意すれば済むわけではない。

### 6. 「何が変わったか」は、操作ログではなく前後のマップの比較から導く

変化の見せ方は、LLM が返した操作ではなく、**反映の前後のマップをノードごとに比べて**導いた。

| 変化 | 判定 |
| --- | --- |
| 追加 | 前のマップに無い id |
| 決定済みに | 論点の子に決定が現れた |
| 却下 | 案の状態が `却下` に変わった |
| 移動 | 親が変わった |
| 統合 | 別のノードの根拠と子を引き取った |
| 更新 | 本文か根拠が変わった |

この方式にしたのは、手で混ぜた統合と移動（1 節）も、LLM の操作と区別なく同じ判定で拾えるからだ。論点の「決定済み」のように、保存せずに子から導く状態もそのまま扱える。

見せ方は、次の 3 つを試して 2 つを残した。

- 残した: **今回の反映で変わったノードの赤い枠**（新しい枝は根元から伸びる）
- 残した: **右側の「変わったこと」一覧**（時刻・変化の種類・種別・本文。クリックでそのノードの根拠を表示）
- 落とした: 数回前までに変わったノードの薄いオレンジの枠

画面共有越しに見るので、強調の段階は少ないほうが読める。

### 7. 外から書き換わる React Flow では、測った寸法をノードに戻す

案 D を ×60 で再生すると、マップが何も表示されなくなった。止めてスライダーで動かしたときは表示されていたので、気づくのが遅れた。DevTools でノードの数を数えると、要素は存在していて、すべて `visibility: hidden` になっていた。

React Flow v12 は、ノードの実寸を測り終えるまでノードを隠す。測った寸法は `onNodesChange` で `dimensions` の変更として届くので、それを受け取ってノードに戻す必要がある。試作はそれをしておらず、しかも再生中は毎フレーム新しいノードの配列を渡していた。そのため測った寸法が捨てられ続け、ノードが表示されないままになっていた。

```tsx
const [dims, setDims] = useState<Record<string, { width: number; height: number }>>({});
const onNodesChange = (changes: NodeChange[]) => {
  const upd = changes.filter((c): c is NodeDimensionChange => c.type === "dimensions" && !!c.dimensions);
  if (upd.length) setDims((d) => { const n = { ...d }; for (const c of upd) n[c.id] = c.dimensions!; return n; });
};
// ノードを作るときに measured: dims[id] を渡し、配置の計算にも dims[id].height を使う
<ReactFlow nodes={nodes} edges={edges} onNodesChange={onNodesChange} … />
```

直したあとは、×180 でも全ノードが表示された。受け取った寸法は、配置の計算にもそのまま使える。文字数から高さを見積もっていた案 A ではノードが重なっていたが、実寸を使う案 D では重ならなくなった。

**外からマップが書き換わる使い方は、止めた状態では壊れ方が見えない**。表示のテストは、実際の更新の速さか、それより速く再生して行う。

### 8. 配置の安定は、作られた順に積むだけで足りる

自動レイアウトのたびに配置が大きく動くと、画面共有で見ている人が迷子になる。左から右への木を、次の規則で配置した。

- 兄弟は、作られた順に上から積む
- 親は、子の範囲の上下の中央に置く

この規則なら、追加で動くのは、追加されたノードより下にあるものだけになる。上にあるものは動かない。ELK や dagre のような汎用のレイアウトエンジンは要らなかった。差分更新のマップは、ほぼ追加と更新でしか育たない（統合と移動は実データで 0 回）ので、「新しいものは下に足される」という前提が崩れにくい。

カメラは、反映のたびに全体を画面に収める方式にした。40〜60 ノードでも、読める大きさに収まった。

### 9. 仮表示の価値は、LLM を呼ぶ間隔で決まる

差分更新エンジンの試作で、System One モデルの Jev（選択肢から選ぶだけの判断専用モデル）なら、発言ごとに「いまどのノードの話か」を約 0.2 秒で返せると分かっていた。これを使って、Claude の反映を待たずに該当ノードを点滅させる仮表示を試した。試作では Jev を呼ばず、次の呼び出しで Claude が実際に触ったノードを光らせて代用した。

入れるかどうかは、Claude をどれだけ間を空けて呼ぶかで決まる。

| Claude の呼び方 | 発言が終わってから反映まで（p50） | 60 分の概算費用 | 仮表示の価値 |
| --- | --- | --- | --- |
| 2 発言ごと（採用） | 約 11 秒 | 約 $1.4〜1.6 | 大きい（反映待ちの空白を埋める） |
| 1 発言ごと | 約 2.9 秒 | 約 2 倍 | 小さい（空白がほぼ無い） |

光らせられるのは既にあるノードの話をしているときだけで、Claude の更新先との一致は 86% になる。それでも MVP に入れた。Jev はこの日の試用全体で約 $0.2、60 分の会議で約 $0.05 と、構成が 1 つ増えることを除けばほぼ負担にならないからだ。**反映の遅れへの対策は「LLM を速く・頻繁に呼ぶ」だけでなく、「安くて速い別のモデルで、仮の答えを先に見せる」もある**。

### その後: 仮表示は STT の途中結果で、さらに早く出せる

- 音声取得と STT を決めたチケットで、STT が確定前に出す**途中結果**（話しているそばから届くが、後で書き換わる暫定の文字列）を、字幕と「いま話している」ノードの仮表示に使うと決まった。途中結果は 0.1 秒以内に届く一方、確定した発言がマップに反映されるのは p50 18〜22 秒の見込みになった。9 節の表の「約 11 秒」は STT の遅れを含まない値で、実際の空白はもっと大きい。仮表示を入れた判断は、その後の結果でむしろ強まった（[リアルタイム音声取得と STT の経路](https://github.com/daiki-beppu/live-mindmap/issues/9)、[ADR 0002](../adr/0002-local-stt-helper.md)）
- 会議中に人がマップを直せるようにするか（削除・固定・種別の変更など）は、別のチケットで決める。候補だった Plait は編集器なので人の修正には強かったが、4 節の保守性の理由で外した（[会議中の人によるマップの修正：操作の範囲と AI の差分更新との両立](https://github.com/daiki-beppu/live-mindmap/issues/12)）

## 会議音声のリアルタイム文字起こしを、Mac の中だけで組んで実測した話

会議の音声を取って文字にする経路を、音声を外に送らない**ローカル完結**で決めたときの学び。候補は 2 つだった。Apple の SpeechAnalyzer（macOS 26 からの端末内の音声認識）を直接使う案と、文字起こしアプリ Kanary の CLI にチャンク（短く切った音声）を渡す案である。60 分の公開会議 2 本を実時間で流して比べた。あわせて、Zoom で流れているセミナーを相手に、実際の音の取り方を試した。

- 決定の記録: [リアルタイム音声取得と STT の経路（ローカル完結）](https://github.com/daiki-beppu/live-mindmap/issues/9)、[ADR 0002](../adr/0002-local-stt-helper.md)
- 用語集: [`CONTEXT.md`](../../CONTEXT.md)（発言・途中結果・トラックの語彙）

### 1. ラッパーを比べる前に、中で動いている認識エンジンを確かめる

Kanary を候補にしたのは、手元に入っていて、CLI もあったからだ。ただ、事前の調査でアプリの中のフレームワークに含まれる文字列を見ると、`SpeechAnalyzerLocaleUsageTracker` などの名前が並んでいた。Kanary も中では Apple の SpeechAnalyzer を使っていると読めた。

そこで、同じ 60 分の音声を 2 通りで文字にし、5 分ごとの窓で文字の一致率を出した。

| | ファシリテーター会議 | ブレスト |
| --- | --- | --- |
| SpeechAnalyzer を直接使った結果と、Kanary の全文の文字一致率 | 98.9% | 98.9% |

精度は同じだった。一方で、Kanary に 10 秒のチャンクを順に渡すと、チャンクの境界で語が抜けた。「結局どちら。」と「安定的に…」の間にあった「の方が」が、どちらのチャンクにも残らなかった。途中結果（確定前の暫定の文字列）も CLI からは取れない。

**同じエンジンの上に乗ったラッパーは、精度を足さずに制約だけを足すことがある**。候補を比べる前に中身のエンジンを確かめ、同じなら、直接使った場合と並べて測る。

### 2. リアルタイム STT の遅れは、区切りの長さと確定待ちで決まる

SpeechAnalyzer は、話しているそばから途中結果を出し、区切りごとに確定結果を出す。LLM に渡すのは確定結果（このプロジェクトでは**発言**と呼ぶ）なので、マップへの反映の遅れは確定結果の届き方で決まる。

測るには、音声ファイルを**実時間のペースで**流し込む必要がある。速く流すと、認識が音声に追いつくまでの待ちが測れない。100 ms ずつ読み、壁時計が音声の時刻に追いつくまで待ってから渡した。

```swift
while file.framePosition < file.length {   // 終わりで read を呼ぶと、0 フレームではなく eofErr が投げられる
  try file.read(into: inBuf, frameCount: chunk)       // 100 ms ぶん
  // …analyzer の形式（16 kHz・モノラル・Int16）に変換…
  fed += Double(inBuf.frameLength) / src.sampleRate
  let wait = fed - now()                               // 音声の時刻に壁時計が追いつくまで待つ
  if wait > 0 { try await Task.sleep(for: .seconds(wait)) }
  cont.yield(AnalyzerInput(buffer: outBuf))
}
```

結果ごとに、結果が付けてくる音声の時間範囲と到着時刻を並べると、遅れが出る。

| | ファシリテーター会議 | ブレスト |
| --- | --- | --- |
| 確定結果 1 つの長さ p50 / p95 | 13.4 / 22.0 秒 | 8.6 / 16.9 秒 |
| 音声の終わり → 確定が届くまで p50 / p95 | 6.1 / 11.4 秒 | 6.5 / 11.2 秒 |
| 話し始め → 確定が届くまで p50 / p95 | 19.2 / 29.7 秒 | 15.2 / 24.4 秒 |
| 途中結果の遅れ p50 / p95 | 0.07 / 0.11 秒 | 0.07 / 0.11 秒 |

LLM（Claude）の応答は約 3 秒なので、**反映の遅れの大半は LLM ではなく STT の区切り方から来ていた**。確定は、音声が終わってからさらに約 6 秒待つ。続きを聞いて区切りを決めているからだ。発散型のブレストは短いやりとりが多く、区切りも短い。

なお、Xcode を入れていなくても、Command Line Tools の `swiftc` だけで SpeechAnalyzer は動いた。日本語のモデルは `AssetInventory` で初回に取得される。

```sh
swiftc -O -swift-version 5 analyzer-bench.swift -o /tmp/analyzer-bench
/tmp/analyzer-bench meeting.m4a --volatile > out.jsonl   # 1 行 1 結果の JSON Lines
```

### 3. 途中結果は「速さが要る表示」に、確定結果は「正しさが要る更新」に分けて使う

途中結果は 0.1 秒以内に届く。これを「。」で切って先に LLM へ渡せば、反映を早められないかを試した。途中結果が文を閉じた瞬間に切り出し、最終的な確定結果と比べた。

| | ファシリテーター会議 | ブレスト |
| --- | --- | --- |
| 切り出した文のうち、確定結果と一致した割合 | 74% | 74% |
| 確定結果より早く出せた時間 p50 | 0.2 秒 | 11.4 秒 |

不一致の多くは、句読点や 1 字の違いだった（「弾いてる」→「引いてる」など）。それでも、LLM に渡したあとに書き換わる文を扱うには、「言い直された発言」を差分更新でどう扱うかという仕組みが別に要る。そのわりに、早まる幅は会議によって 0.2 秒から 11 秒までばらついた。

そこで、使い道を分けた。途中結果は字幕と「いま話している」ノードの仮表示だけに使い、差分更新とマップの根拠には確定結果だけを使う。**書き換わる暫定の値は、間違っても実害のない表示にだけ使い、状態を変える処理には確定した値だけを渡す**。

### 4. 相手の声は、Mac 全体ではなく会議アプリ単位で取る

相手の声は、Core Audio のプロセスタップ（macOS 14.4 から、アプリの出力音を横取りする API）で取った。最初は Mac 全体の出力をタップした。すると、流れてきた文字は、再生したテスト音声ではなく、同じ Mac で流れていた別の音声のものだった。Mac 全体のタップは、通知音も、別のタブの動画も拾う。

アプリを指定してタップするには、音を出しうるプロセスの一覧から bundle id で選ぶ。

```swift
// kAudioHardwarePropertyProcessObjectList で全プロセスを取り、bundle id の前方一致で選ぶ
let procs = ids.filter { (bundleID(of: $0) as String).hasPrefix("us.zoom.xos") }
let desc = CATapDescription(stereoMixdownOfProcesses: procs)
AudioHardwareCreateProcessTap(desc, &tapID)   // あとは集約デバイスに載せて IOProc で受ける
```

ここでもう 1 つつまずいた。「Chrome で再生している」と聞いて Chrome をタップしたところ、150 秒間、1 フレームも届かなかった。プロセスごとに `kAudioProcessPropertyIsRunningOutput`（いま音を出しているか）を出すと、音を出していたのは Zoom だけだった。実際には Zoom のセミナーを聞いていた。**どのアプリの音かは、利用者の記憶ではなく「いま出力しているプロセス」から選ばせる**ほうが確実だ。ブラウザは、音を本体ではなくヘルパーのプロセスから出す。そのため、ブラウザを選ぶと、ヘルパーも含めたブラウザ全体の音になる（Meet のタブだけには絞れない）。

権限の許可ダイアログはマイクでだけ出た。システム音声のタップは、起動したターミナルの権限で動いた。

### 5. Apple のエコーキャンセルとプロセスタップは、同じプロセスで両立しない

スピーカーで会議を聞くと、相手の声がマイクにも入る。自分のマイクのトラックに、相手の発言がほぼそのまま二重に文字になった。対策の定番は、AVAudioEngine の `setVoiceProcessingEnabled(true)`（Apple の音声処理。エコーキャンセルを含む）だ。これを試すと、別の問題が出た。

| 条件 | 相手（Zoom のタップ） | 自分（マイク） |
| --- | --- | --- |
| エコーキャンセルなし | 届く | 相手の声がほぼそのまま二重に文字になる |
| エコーキャンセルあり、同じプロセス | **最初の 1 回で止まる** | 漏れは「あ」の 1 語だけ |
| 同上、マイクを先に開始 | 止まる | 同上 |
| 同上、ダッキングを最小（`duckingLevel: .min`） | 止まる | 同上 |
| エコーキャンセルあり、タップとマイクを別プロセス | 届くが、音量が約 1/3 に下がる | 漏れは「あ」の 1 語だけ |

別プロセスにすると両立はした。ただ、タップで取れる Zoom の音のピークは 0.55 から 0.16〜0.22 に落ちた。これは利用者の耳にも同じで、ダッキング（音声処理が他のアプリの音を下げる動き）は最小の設定でも止まらなかった。会議の相手の声が小さくなるのは、会議の道具としては受け入れにくい。

**音声処理（Voice Processing）を有効にすると、同じ出力デバイスまわりに副作用が出る**。タップと組み合わせるなら、開始順や設定を変えて粘るより、まずプロセスを分けて副作用を測る。

### 6. スピーカーからの漏れは、区切りではなく時間窓の文字列で見分ける

「MVP はイヤホン前提にする」という案も出した。だが、決めたのは「スピーカーでもイヤホンでも、ストレスなく使える」ことだった。自分たちの実会議で使う道具なので、使う前の準備が要ると使われなくなる。

そこで、エコーキャンセルの代わりに、文字の重なりで漏れを捨てることにした。前提は、**相手のトラックには自分の声が入らない**ことだ（会議アプリは自分の声を再生しない）。漏れた発言は相手のトラックと重なり、自分の発言は重ならないはずである。

見分け方には注意が要った。2 つのトラックの確定結果は、区切りの位置が揃わない。自分のトラックの 1 つの確定結果が、相手のトラックの 2 つにまたがる。そこで、確定結果どうしを突き合わせるのではなく、**マイクの確定結果の文字 3-gram のうち、前後 8 秒の相手の文字列に現れる割合**（被覆率）を出した。スピーカーから漏れた 12 件では、被覆率は 0.68〜1.00 だった。認識が 2 回別々に走るので、英字とカタカナのように表記が揺れ、1.00 にはならないものが多い。

出力先がスピーカーかイヤホンかは、Core Audio で判定できる。既定の出力デバイスの `kAudioDevicePropertyTransportType` と `kAudioDevicePropertyDataSource` を読むと、内蔵スピーカーでは `bltn`（内蔵）と `ispk`（スピーカー）が返った。スピーカーのときだけこの判定をかければ、イヤホンのときに誤って捨てることもない。イヤホン（有線・Bluetooth）で返る値は、今回はまだ確かめていない。

まだ確かめていないことが 2 つある。自分の発言の被覆率が本当にほぼ 0 になるか。自分と相手が同時に話したとき、自分の発言まで捨てないか。しきい値は、この 2 つを実装時の回帰評価で測ってから決める。

## 会議音声からマインドマップまでのパイプラインを、どこで動かし状態をどこに持つか決めた話

MVP のシステム構成を決めたときの学び。この時点で両端は決まっていた。入り口は、Mac のローカルで常駐する Swift のヘルパーで、会議の音声を文字にして localhost の WebSocket でイベントを流す。出口は、ブラウザの React Flow で描くマップである。このとき決めたのは、その間の役割の置き場所だった。LLM（Claude）を呼んでマップを差分更新する役、「いま話している」ノードを判定する別のモデル（Jev）を呼ぶ役、状態を持つ役、回帰評価用のログを書く役である。コードは書かず、候補を並べて 1 つずつ決めた。

- 決定の記録: [MVP のシステム構成：パイプライン・実行場所・状態管理](https://github.com/daiki-beppu/live-mindmap/issues/8)、[ADR 0003](../adr/0003-local-node-server-owns-pipeline.md)
- 用語集: [`CONTEXT.md`](../../CONTEXT.md)（セッション・再生・発言・途中結果の語彙）

決まった構成は次のとおり。

```
[Swift ヘルパー] ──WS(途中結果 / 発言+重複の印)──▶ [ローカル Node サーバー] ──WS(スナップショット / いま話しているノード / 反映待ち)──▶ [ブラウザ: 表示だけ]
                                                   ├ Claude: 2 発言ごと、同時に 1 つまで
                                                   ├ Jev: 途中結果を約 3 秒ごと
                                                   ├ 状態: メモリ（セッションは 1 つ）
                                                   └ ログ: セッションごとの JSONL に追記
                                                   ◀── AI エージェントが CLI で操作（開始・終了・エクスポート・再生）
```

### 1. バックエンドの候補は、入り口がどこに縛られているかで絞る

プロジェクトの最初のメモでは、バックエンドが要るなら Convex（状態をクラウドに置き、ブラウザがリアクティブに購読できるサービス）を第一候補にしていた。候補を並べ直すと、次の 3 つになった。

| 案 | 引っかかった点 |
| --- | --- |
| ブラウザだけ（ヘルパーに直接つなぎ、LLM もブラウザから呼ぶ） | API キーがブラウザに出る。再読み込みで状態が消える。ログをファイルに書けない |
| ローカルの Node サーバー | なし |
| Convex | ヘルパーは Mac のローカルにしかいないので、ヘルパーから Convex へ送る中継役がローカルに要る |

Convex にしても、ローカルのサーバーは結局要る。Convex で得られるもの（複数のブラウザでの同期、共同編集）は、MVP では範囲外と決めていた。つまり Convex は、サーバーを 1 つ増やすだけになる。

**入り口（ここでは音声を取るヘルパー）が特定の場所に縛られているなら、中心もそこに寄せるのが最小の構成になる**。クラウドのバックエンドを候補に入れるのは、その利点が今の範囲の機能に効くときだけでよい。

### 2. 仮表示の入力は、届くまでの遅れを表示の目的に照らして選ぶ

前のチケットでは、Jev（選択肢から選ぶだけの判断専用モデル）に**発言ごと**に「いまどのノードの話か」を判定させ、該当ノードを点滅させると決めていた。発言は、STT（音声認識）が確定させた文字起こしの 1 区切りである。ところが構成を詰めると、発言がサーバーに届くのは話し始めから p50 15〜19 秒後だった。15 秒前の話を「いま話している」とは呼べない。

一方で、確定前の暫定の文字列（**途中結果**）は 0.1 秒以内に届く。後で書き換わるので、マップの更新や根拠には使わない。それでも、「どのノードの話か」を当てる材料としては十分だ。

| Jev の入力 | 表示の遅れ | 60 分の費用 |
| --- | --- | --- |
| 発言ごと | 15 秒以上 | 約 $0.05（試作での実測から） |
| 途中結果を約 3 秒ごとに間引く | 数秒 | 約 $0.2（呼び出し回数からの見積もり） |

仮表示を入れた目的は、Claude の反映待ちを埋めることだった。15 秒遅れては、その目的をほとんど果たせない。そこで途中結果に切り替えた。**速さのための仕組みに渡す入力は、「正しい入力はどれか」ではなく「その入力はいつ届くか」で選ぶ**。

### 3. 捨てる判定をしても、捨てずに印を付けて流す

スピーカーで会議を聞くと、相手の声がマイクにも入り、`自分` のトラック（マイクの音）でも文字になる。これを、`相手` のトラック（会議アプリの音）の前後 8 秒の文字列と比べて、重複として除く。除く場所の候補は 3 つだった。

- ヘルパーで判定して捨てる
- ヘルパーは判定だけ行い、発言に「重複」の印を付けて全件流す
- 下流のサーバーで判定する

前のエントリの ADR には、「自分と相手が同時に話したとき、自分の発言まで捨てないかは、実装時に回帰評価で確かめる」と書いてあった。ヘルパーで捨てると、捨てた発言がどこにも残らず、この確認ができない。

そこで、**判定は音の出どころを知っているヘルパーに置き、扱い（差分更新に使わない）とログは下流に置いた**。しきい値がまだ決まっていない判定ほど、誤りを後から数えられるように、捨てずに印を付けて流しておく。

### 4. 状態の持ち主が 1 つなら、ブラウザにはスナップショットを送る

ブラウザへの届け方は、次の 2 案から選んだ。

- 反映のたびに**マップ全体**を送る
- **差分操作**を送り、ブラウザでも適用する

後者では、マップに操作を適用するロジックが、サーバーとブラウザの 2 か所に要る。60 分の会議でノードは数十〜百数十なので、全体を送っても軽い。スナップショットなら、ブラウザを再読み込みしたときも、最新を 1 つ送り直すだけで済む。

この構成では、ブラウザは表示だけになった（6 節）。**状態の持ち主が 1 つで、受け手が描くだけなら、受け手に適用のロジックを持たせない**。「何が変わったか」の一覧も、受け手ではなく持ち主の側で導いて一緒に送る。

### 5. 1 本のイベントログで、復元と回帰評価を兼ねる

回帰評価用の JSON ログは、セッション（1 つの会議について、開始から終了までマップを組み立てる一続きの作業）ごとに 1 ファイルの JSONL にした。イベントが起きるたびに追記する。記録するのは次の 4 種類である。

- 発言（重複の印を含む）
- 差分操作（Claude への入力の要約と出力）
- Jev の判定
- 人の修正

状態はサーバーのメモリにしか無い。サーバーが落ちたら、ログの差分操作を順に適用し直してマップを復元する。LLM を呼び直さないので、費用も時間もかからない。

回帰評価では、同じログから発言だけを取り出し、エンジンに流し直す（**再生**）。そのため、エンジンの入力は「発言の流れ」という形に揃えた。出どころは、ライブ（ヘルパー）とファイルの 2 つである。ファイルは、過去のセッションのログでも、録音済みの会議の文字起こしでもよい。再生の速さは 2 通り用意する。

- **等速**: 見た目の確認用
- **待ち時間なし**: 評価用。前の Claude の呼び出しが終わりしだい次に進む

**ログを「何が起きたか」の順序付きの記録にしておけば、復元と評価は同じ再生の仕組みで賄える**。どこから再生するか（差分操作か、発言か）が違うだけである。

### 6. 基本操作をエージェントが行うなら、操作の入り口は CLI にする

最初の案では、ブラウザで会議アプリを選び、「開始」ボタンを押すつもりだった。決定を記録している途中で、利用者から前提が 1 つ足された。「基本操作は、MVP でも本番でも AI エージェントがする」。

そうなると、操作の入り口はボタンではなく、エージェントが呼べる形であるべきだ。サーバーの操作を CLI として出すことにした。対象は、セッションの開始・終了、会議アプリの一覧、エクスポート、再生である。エージェントは Bash から呼べる。MCP は、アプリ化の段階で必要になってから、同じ操作の上に被せる。ブラウザは表示専用になり、サーバーとブラウザの間の通信も、サーバーからブラウザへの一方向だけになった。

**誰が操作するかは、UI の問題ではなく構成の問題だ**。人がクリックする前提か、エージェントがコマンドを打つ前提かで、どこに入り口を作るか、ブラウザに何を持たせるかが変わる。

### 7. 安い経路を選ぶときは、成り立つ条件と差し替え先を一緒に書く

Claude の呼び方は、次の 2 案から選んだ。

- API キーで Anthropic API を直接呼ぶ
- Claude Agent SDK を Claude のサブスクリプションの認証で呼ぶ

試作の段階で、Agent SDK は構造化出力が 2 ターンになり、遅く出ることが分かっていた。それでも、利用者の希望（なるべく安く）に合わせて後者を選んだ。2 発言ごと（約 25 秒間隔）に呼び、同時に呼ぶのは 1 つまでにする。呼び出し中にたまった発言は、次の 1 回にまとめて渡す。この条件なら、応答が数秒遅れても呼び出しは重ならない。

ただし、サブスクの認証が成り立つのは、自分とチームで使う間だけだ。「MVP の後は何らかの形でアプリ化する」という前提も、同じ時期に足された。そこで ADR には、成り立つ条件と差し替え先を一緒に書いた。

- アプリとして配布するときは、API キーで直接呼ぶ実装に差し替える
- 差し替えられるように、Claude の呼び出しは 1 つの関数の後ろに閉じておく
- エンジン・状態・ログ・再生は、WebSocket や Node に依存しない TypeScript のモジュールにする。サーバーは、それを WebSocket と CLI につなぐ薄い層にとどめる

**今は安い経路を選んでいい。ただし、それが崩れる条件を先に書いておけば、後で「なぜこうなっているのか」を掘り起こさずに済む**。

### 8. 全体図を見せてから確定すると、前提の追加が出てくる

問いは 2 ラウンドに分け、各ラウンドの答えを受けて次の問いを立てた。9 問すべてが推奨どおりに決まった。ところが、構成の全体図を 1 枚にして「この理解で合っているか」と確かめた後に、前提が 2 つ足された。「MVP が終わったらアプリ化する」と「基本操作は AI エージェントがする」である。どちらも、個別の問い（Claude の呼び方、ヘルパーの起動方法）への答えを書き換えるものではない。構成全体にかかる条件だった。

個別の問いには、その問いの範囲でしか答えが返ってこない。**全体にかかる前提は、全体図を見せたときに初めて出てくる**。決定を記録する前に、図で全体を見せて確認する手順を省かない。

## AI が組み立てるマップを人が直す機能を詰めきってから、MVP では入れないと決めた話

会議中に人がマップを直せるようにするかを決めたときの学び。AI の誤りを会議中に直したい場面はありうる。例えば誤認識で、存在しない論点のノードができて、画面共有で参加者全員に見えてしまう場合だ。修正の入口、操作の種類、AI の更新とぶつかったときの扱い、ログへの残し方を順に決めた。そのうえで最後に、MVP では入れないと決めた。コードは書かず、候補を並べて 1 つずつ決めた。

- 決定の記録: [会議中の人によるマップの修正：操作の範囲と AI の差分更新との両立](https://github.com/daiki-beppu/live-mindmap/issues/12)
- 用語集: [`CONTEXT.md`](../../CONTEXT.md)（ノードの種別と差分操作の語彙）

前提として、次のことが決まっていた。

- マップの状態を持つのは、ローカルの Node サーバーだけ。ブラウザは、サーバーから届くスナップショット（マップ全体）を描くだけ
- 基本操作（開始・終了・エクスポート・再生）は、AI エージェントがサーバーの CLI から行う
- AI（Claude）は約 25 秒ごとに呼ばれ、1 回の応答に約 3 秒かかる。返すのは、既存のマップに当てる**差分操作**（追加・更新・統合・移動・削除・何もしない）
- 同時に呼ぶのは 1 つまで

### 1. 「修正させるか」と「どこから修正させるか」は、1 つの問いとして決める

最初に、修正の入口の候補を 3 つ並べた。

| 案 | 引っかかった点 |
| --- | --- |
| 入れない | 誤ったノードが残り、AI がそれを前提に子を足し続ける |
| エージェントに頼み、CLI から直す | 操作者が別のウィンドウで指示する手間がある。反映まで 10〜30 秒かかる（見積もり） |
| ブラウザでノードを右クリックして直す | 「ブラウザは表示だけ」という構成の原則に、初めての例外を作る |

入れるかどうかだけを先に決めると、次の問いでブラウザの案が自然に出てくる。そして、構成の原則が「機能のついで」に崩れる。そこで、入口まで含めて 1 つの問いにした。エージェント経由を選べば、原則は保たれる。後で MCP を被せるときも、同じ操作をそのまま使える。エージェントは本文からノードを特定できるので、操作者がノードの ID を知る必要もない。

**表示専用と決めた画面に操作を足す話が出たら、機能の有無と入口を一緒に決める**。

### 2. 入口がもともと遅いなら、衝突は「待たせる」だけで消せる

一番重く見えた問いは、AI の差分更新との衝突だった。AI の呼び出し中に人が論点 X を消し、返ってきた操作が「X に案を追加」だった場合、どうするか。候補は 3 つあった。

- 返ってきた操作を今のマップに 1 つずつ当て、成り立たないものだけ捨てる
- 結果を丸ごと捨てて、AI を呼び直す
- 呼び出し中は人の修正を待たせ、AI の結果を当ててから修正を当てる

3 つ目を選んだ。エージェント経由の修正は、もともと 10〜30 秒かかる。AI の応答の約 3 秒をさらに待たせても、体感はほとんど変わらない。サーバーは、AI の結果と人の修正を 1 本のキューで順に処理するだけになり、同時編集の問題そのものが消える。

残る衝突は、待っている間に修正の対象を AI が統合・削除していた場合だけだ。そのときは修正を拒否し、エージェントに理由を返す。エージェントはマップを取り直して、もう一度指示できる。

**衝突の扱いを考える前に、入口の遅さを測る**。人の操作がもともと遅い経路を通るなら、ロックや再計算ではなく「待たせる」で済む。

### 3. 人の修正を AI から守るのは、プロンプトではなくサーバーの検証に任せる

修正の後も、AI は同じ発言の流れを見続ける。すると、直した内容を AI が元に戻しうる。

- 人が消したノードを、直前 3 発言から AI がもう一度追加する
- 人が直した本文を、AI の「更新」（本文を全文で言い直す操作）が上書きする

候補の操作には「固定」（AI に動かさせない）もあった。しかし固定は、人が「ここは固定しておこう」と覚えていないと効かない。そこで、人が直したノードを自動で守る方針にした。

- アウトラインで「人が修正」の印を付ける
- サーバーの検証で、そのノードを AI の削除・統合・移動・本文の書き換えから守る
- AI の「更新」が来たら、根拠（ノードの元になった発言への参照）だけを足し、本文は人のものを残す
- 人が消したノードの本文は、直近数回の呼び出しに「人が消したもの」として渡す

守りの基本はサーバーの検証に置き、プロンプトは補助にとどめた。LLM が指示を守らなくても、人の修正は戻らない。

**人の判断を AI の上書きから守る仕組みは、人に操作を覚えさせるより、自動で効くほうを選ぶ**。LLM への指示ではなく、決定的に動く検証の側に置く。

### 4. 人の修正は、評価の場では適用せず「AI が誤った印」として使う

ログはセッション（1 つの会議について、開始から終了までマップを組み立てる一続きの作業）ごとの JSONL で、2 つの使い道がある。

- **復元**: サーバーが落ちたとき、記録した操作を順に適用し直してマップを戻す
- **再生**: 発言だけを取り出してエンジンに流し直し、回帰評価に使う

人の修正は、復元ではそのまま適用し直せる。しかし再生では、AI が毎回違う操作を返す。そのため、記録した修正の対象がそもそも存在しない。

そこで再生では、人の修正を適用せず、「AI がここを誤った」という正解ラベルとして使うことにした。例えば、人が消したノードに近いものを、再生で AI がまた作ったかを数える。そのために、修正の記録には対象ノードの ID だけでなく本文も残す。ID は再生のたびに変わっても、本文なら照合できる。

**人の介入のログは、同じ入力を流し直す評価では「やり直し」ではなく「採点の材料」になる**。

### 5. 答えが前の答えと食い違ったら、その 1 点だけを聞き直す

ここまでの 5 問への答えは、すべて推奨どおりだった。ただし同じ返事に、次の一言が付いていた。

> mvp では人が修正する前提で作らなくてもいいかも

これは、最初の問い（CLI から直せるようにする）への答えと食い違う。どちらかを勝手に採らず、この 1 点だけを 3 択にして聞き直した。

- MVP では入れない。詰めた内容はチケットに残すだけ
- MVP では入れないが、後で足すための欄（「誰の変更か」の欄、「人が修正」の印）だけ先に作る
- やはり入れる

推奨は 1 つ目にした。MVP の目的は「AI だけでどこまで使えるマップになるか」を確かめることだ。人の修正が混ざると、AI の出来を判断しにくくなる。返事は「推奨でいいが、後から修正したときに破綻しない作りが前提」だった。

細部を詰めると、キュー、保護の規則、ログの新しいイベント、評価での扱いと、この機能に要るものが並んだ。どれも MVP の目的には効かない。それが見えたことが、入れない判断につながったと考えている。詰めた内容は無駄にしていない。後で入れるときの方針として、そのままチケットに残した。

**細部を詰めた後でも、範囲の判断は覆してよい。詰めた内容は捨てずに、後で入れるときの方針として残す**。

### 6. 後で入れる機能には、欄ではなく変更の経路で備える

「後から修正を足しても破綻しない作り」を、仕様の約束事に落とした。候補にあった「誰の変更か」の欄や「人が修正」の印は、先回りして作らないことにした。代わりに入れたのは、構造の約束だけである。

- マップの変更は、すべて 1 つの適用関数を通る。AI の差分操作も例外にせず、状態を直接書き換える経路を作らない
- 検証は「適用する時点のマップ」に対して行う。成り立たない操作は捨てて理由をログに残す
- ログのイベントは種類で区別し、後から種類を足せる形にする。復元は、イベントを順に適用関数へ流す
- ノードの ID はサーバーが振り、更新・移動では変わらない

後から入る機能で破綻しやすいのは、欄が足りないことより、変更の経路が複数あることだ。経路が 1 本なら、人の修正は入口を 1 つ足すだけで済む。「AI の操作は、呼び出したときのマップにそのまま当たる」という前提を置かなければ、人の修正が割り込んでも、既存の検証が衝突を吸収する。この 2 つは人の修正がなくても役に立つ。例えば、1 回の応答の中で同じノードを 2 回統合するような食い違いも、同じ検証で捨てられる。

なお、前のエントリではログに記録するイベントの 1 つに「人の修正」を挙げていた。MVP では修正を入れないので、このイベントは MVP のログには現れない。後で入れるときに、種類を 1 つ足す。

**入れないと決めた機能への備えは、データの欄ではなく、変更が必ず通る 1 本の経路と、その場で検証する規則で行う**。
