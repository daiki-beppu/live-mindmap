## 案・課題・要点を名指しする規則で測り直したら、山は名指しの前に散って溜まらなくなったが、溜まり先はまた論点への答えに戻り、残った不合格は子 13 の判定の 1 件分だった話

マップが右に伸びすぎる問題を直す地図で、[今ある案の下に溜まる具体化をどう扱うかを決めた](./2026-10-10.md#pile-under-plan)規則をプロンプトに書き、測り直したときの学び。マップは会議をルートとする木で、**議題**（話題のまとまり）の下に、**論点**（答えを出すべき問い）・**案**（答えの候補やアイデア）・**課題**（問題や懸念）・**要点**（共有された中身）が付く。前回は、第三者が入った 92 分の会議を再生したもの（以下、実会議の再生）で、1 つの案の下に 66、1 つの要点の下に 73 のノードが溜まった。そこで今回は 2 つの規則を足した。案・課題・要点の配下が目安の 20 を超えたら、毎回モデルに添える「議題の一覧」でそのノードを名指しする。名指ししたノードの下には足さず、続きは一番近い議題の下に子の議題（議題の下に立てる議題）を立てて置く。

- 決定の記録: チケット [案・課題・要点を名指しする規則に書き換え、合成会議と実会議の再生で形を比べる](https://github.com/daiki-beppu/live-mindmap/issues/785)、次のチケット [子の少ない親で揺れる兄弟の判定と、論点への答えの溜まりをどう扱うか](https://github.com/daiki-beppu/live-mindmap/issues/791)、地図 [マップが右に伸びすぎないよう、議題の切り出しと鎖の作り方を直す](https://github.com/daiki-beppu/live-mindmap/issues/689)

### 1. 一律の禁止は、守られる前に、目安の文だけで山を散らした

実会議の再生を 2 回、合成会議（TTS で作った架空の会議）の facilitators（55 分）を 2 回流し、案・課題・要点の下の山を数えた。

| 素材 | 前回の最大の山 | 今回の最大の山 | 名指しされた山 | 名指しの後にその下へ足された数（前回 → 今回） |
|---|---|---|---|---|
| 実会議の再生 1 回目 | 73 | 22 | 4 → 1 | 52・9・7・0 → 0 |
| 実会議の再生 2 回目 | 66 | 19 | 1 → 0 | 45 → — |
| facilitators 1 回目 | — | 21 | 0 → 1 | — → 0 |

名指しされた山には、その後 1 つも足されなかった。前の規則の振り返りで「一律の禁止は守られる」と書いたとおりだ。ただ、効き方の大半はそこではなかった。名指しまで育った山は 4 本の再生で 2 つしかなく、ほかの山は 20 に届く前に止まった。SYSTEM プロンプト（毎回同じ前置きの指示）に「案・課題・要点の配下も 20 が目安」と書いただけで、モデルは早めに別の場所へ置くようになった。

前回の山は 45〜52 が名指しの後に足されていた。名指しの合図が効いたかを確かめるつもりで測ると、合図が出る前の変化を見落とす。名指しされた数と、名指しの後に足された数を、両方出しておく。

### 2. 「名指しの後」は、何が名指しされた後かを数えるたびに確かめる

前回の集計スクリプトにも「名指し後に足された数」という列があった。そのまま今回のセッションにかけると、案の山に 17 や 13 と出る。ところがこれは、山を囲む議題・論点が名指しされた後の数で、山そのものが名指しされた後の数ではない。今回の規則が止めるのは後者だ。

セッションのログ（差分ごとに記録したもの）を頭から 1 差分ずつ組み直し、各差分の直前のマップで、プロンプトと同じ数え方をした。どの山が 20 を超えていたか（名指しされたか）を決め、その差分で生まれたノードがどの山の中に入ったかを数えるスクリプトを書き直した。同じ名前の列でも、規則が変われば測る対象が変わる。前の回のスクリプトを流用するときは、列の定義が今回の規則の言葉と一致しているかを先に読む。

### 3. 1 か所を塞ぐと、溜まりはまだ許している場所へ移る

最大の**まとまり**（物差しで数える単位で、議題か論点の配下のノード数。目標は 40 以下）は、実会議の再生で 89・42 だった。どちらも論点 1 つの下で、1 回目は直下に 25（案 18・課題 6・要点 1）が付き、目安を超えた後に 69 が足されていた。

この地図では、溜まり先が 3 回移っている。最初は名指しされた議題の直下だった。それを禁じると論点への答えに移り、論点を独立に数えると案・要点の具体化に移った。今回それを塞ぐと、論点への答えに戻った。論点の規則には今も「派生の問いが無く、同じ問いへの別々の案や答えが続くだけなら、そのまま兄弟として並べてよい」という許可がある。派生の論点（元の問いの一部を別に問う論点）は 4 本の再生で計 5 しか立たない。

モデルは、禁止されていない一番近い置き場所を選ぶ。規則を 1 つ足して測るたびに、「次に溜まるのは、まだ許可が残っている場所」と予想して、その場所の数も先に出しておくと、結果を読む時間が短くなる。

### 4. 子が少ない親の判定は、揺れが物差しの幅より大きい

まとまりが 40 を超えた回は、その直下の兄弟を LLM で判定し、「別でない」（ほかの兄弟の具体化・重なり・外れ）の割合を、同じセッション全体の割合と比べる。1 回目の 89（直下 25）は 20.0%・20.0% で、セッション全体の 23.0〜24.5% より良く、通った。2 回目の 42（直下 13）は 30.8%・0.0% で、セッション全体は 19.2% だった。

同じ 13 の子への判定が、4 件と 0 件に分かれた。揺れを見るためにあと 3 回流すと、3 回とも 3 件（23.1%）だった。13 の子では 1 件が 7.7 ポイントに当たり、19.2% は 2.5 件にあたる。つまり 1 件分の差で不合格になっている。

合否には最初の 2 回をそのまま使い、×と記録した。不合格を見てから回数を足し、通る読み方を探すと、物差しを結果に合わせることになる。足した 3 回は揺れの幅を示す材料として別に書き、比べ方を変えるかは次のチケットで人と決める。前回の振り返りでも、直下の子 8 つの判定が不合格の決め手になっていた。子の数が少ない親を判定するときは、1 件が何ポイントに当たるかを先に計算しておく。

### 5. 本文を読まない約束は、伏せる側ではなく、出す側で守る

実会議は第三者が入った会議なので、本文は読まず、id・種別・数だけを見る約束にしている。名指しの行が正しく出るかを確かめるとき、プロンプトの「議題の一覧」の行から本文を伏せようとして、`「.*?」` を `「…」` に置き換えた。本文の中に「」が入っていたので、最初の 」で置き換えが止まり、残りの本文が画面に出た。

直し方は、伏せる正規表現を強くすることではない。出力を、id と数だけを拾って組み立てる形に変えた。

```ts
l.replace(/^(- \S+ n\d+).*: (話し中\S* \d+ ノード).*$/, "$1 $2")
```

伏せる方式は、本文の形を予想できる範囲でしか効かない。拾う方式なら、予想しない本文が来ても何も出ない。読んではいけないデータを扱うスクリプトは、最初から拾う形で書く。

## 反映の遅れを区間に分けて測り直したら、確定待ちの中央値は縮んでいたが、長い尾は「発言の途中の行が後ろを待つ」形で残っていた話

判定だけを受け持つ軽いモデル（System One モデル）で、マップへの反映を速くする地図の最初の計測の学び。いまのコードで、話し終わりからノード（マップの 1 要素）が出るまでの遅れを区間に分けて測り直した。ここでいう**発言**は、音声認識（STT）の結果を差分更新に渡す 1 区切りで、確定結果か、1 秒更新されなかった途中結果（確定前の暫定の文字列）のどちらか早いほうから作る。**差分更新**は、新しい発言を Claude に渡してマップへの変更を返させる呼び出しで、発言が 2 つたまるか、最後の発言から 1.5 秒次が来なければ呼ぶ。10/03 の実会議では、話し終わりからノードまで p50 12.5 秒、うち STT の確定待ちが 8.8 秒だった。この数字は「1 秒更新されなかった途中結果から発言を作る」規則が入る前のもので、いまどれだけ残っているかを知りたかった。

- 決定の記録: チケット [いまの反映の遅れの内訳を測り直す](https://github.com/daiki-beppu/live-mindmap/issues/761)、この結果を前提にするチケット [発言にする区切りを判定で早め、差分更新を早く呼ぶ](https://github.com/daiki-beppu/live-mindmap/issues/763)、地図 [System One モデル（Jev・OpenAI Decisions・Clef）で反映を速くし、費用を下げる](https://github.com/daiki-beppu/live-mindmap/issues/757)

### 1. 区間に分けるには、呼び出しの始まりを自分で記録する

既存の道具は、音声を等速で STT に流す `stt-bench run`、その結果から本番と同じ規則で発言を作る `sttLatency.ts --emit discard`、発言を届いた時刻のまま本番のセッションと Claude に流す `sttReplay.ts` の 3 段だった。`sttReplay` が出すのは「話し終わり → ノード」の 1 本だけで、セッションのログにも差分更新の時刻が無い。

そこで、差分更新の役（`DiffUpdater` という Effect の Service）を包む Layer を一時的に書き、呼び出しの始まり・終わりと渡した発言の ID を記録した。差分更新の役は Service として差し込む作りなので、本番のコードには手を入れずに済んだ。

```ts
const timed = Layer.effect(DiffUpdater)(Effect.gen(function* () {
  const inner = yield* DiffUpdater;
  return { update: (input) => /* 始まりと終わりの時刻、input.fresh の ID を記録して inner.update を呼ぶ */ };
})).pipe(Layer.provide(claudeUpdaterLayer(defaultClaude)));
```

合成会議（TTS で作った架空の会議）2 本を流した結果（各 1 回、p50 / p90、秒）:

| 区間 | screen（23 分・230 行） | facilitators（55 分・455 行） |
|---|---|---|
| 話し終わり → 発言 | 2.0 / 8.6 | 2.1 / 10.7 |
| 発言 → 差分更新の呼び出し開始 | 2.0 / 2.3 | 2.4 / 3.3 |
| 呼び出し → 応答 | 2.8 / 4.6 | 2.8 / 4.7 |
| 話し終わり → ノード | 7.4 / 14.7 | 8.6 / 18.7 |

「発言 → 呼び出し開始」が 1.5 秒の待ちより長いのは、前の呼び出しが終わるのを待つ分が乗るから。「呼び出し → 応答」の 2.8 秒は差分更新そのものなので、前段に判定を足しても縮まない。区間に分けたことで、判定の段で狙える場所と狙えない場所が分かれた。

### 2. 規則で縮んだのは中央値で、長い尾は残っていた

確定結果だけで発言を作った場合の「話し終わり → 発言」は 6.3 / 14.2 秒と 7.3 / 17.6 秒だった。途中結果の規則で p50 は約 5 秒縮んだが、p90 はまだ 8.6〜10.7 秒ある。中央値だけを見ていたら「確定待ちはもう小さい。発言の区切りを早める案は見送り」と判断していた。そのチケットには、まさに「確定待ちが小さければ見送る」と書いてあった。

尾の中身を見るため、台本の各行を、それを含む発言の中の位置で分けた。

| 行の位置 | screen p50 / p90 | facilitators p50 / p90 |
|---|---|---|
| 発言の最後の行 | 1.1 / 2.1（73 行） | 1.1 / 2.1（138 行） |
| 発言の途中の行 | 3.5 / 9.1（156 行） | 4.1 / 12.2（317 行） |

発言の最後の行は 1 秒の規則どおり約 1 秒で発言になる。遅いのは途中の行で、1 つの発言が 2〜5 行（p50 で長さ 14 秒）をまとめるため、前のほうの行は後ろの行が言い終わるまで待つ。途中結果が 1 秒止まらないかぎり発言が切れないので、行の間が短いと区切りが来ない。遅れを「発言ごと」に数えると、この待ちは見えない。行（人が言い終わった単位）から数えると、待ちが尾として現れる。

### 3. 素材の作りが尾を大きく見せている可能性を、数字と一緒に書く

合成会議は行の間が一律約 0.45 秒で、1.5 秒以上空いた行は 2 本で 14 行しかなかった。TTS は笑いも間も入れずに続けて読むので、実会議より区切りが来にくい。p90 の大きさの一部は素材の作りから来ているかもしれない。この注意は、結果の表と同じコメントに書いた。後で「合成会議で p90 10 秒」という数字だけが一人歩きすると、実会議の改善幅を見誤る。

### 4. 計測を推奨に変える前に、決まっていて未実装のものを確かめる

最初の報告では、遅れの原因を「話者の交代をまたいで 2〜5 行が 1 発言にまとまること」と書き、区切りを判定で早める案の根拠にした。この記録を書く段になって用語集を読み直すと、発言の定義に「`相手` のトラックでは話者が替わったところで区切る」とあった。話者で区切ることはすでに決まっていて、実装（話者分離の実装仕様）がまだ入っていないだけだった。

計測そのものは、いまのコードの姿として正しい。外れていたのは解釈のほうだ。話者分離が入れば、話者をまたいだまとまりは判定の段がなくても縮む。判定で区切りを早める案の利得は、その後に残る部分（同じ話者の文の切れ目）で見積もる必要がある。両方のチケットに補足を書き足した。

測った数字から「次にこれをやるべき」と言う前に、用語集と判断の記録を読み、決まっていて未実装のものが同じ遅れを消さないかを確かめる。コードだけを読むと、未実装の決定は見えない。

## takt の回し手を Claude から Codex へ、また Claude へ引き継いだら、記録の「実行中」は runner が消えても残り、人の確認を書いたチェックボックスは査読が全部通っても止め、設定は動いている run には届かなかった話

### 1. 人が確かめる項目は、「（マージ後に人が）」と書いてもチェックボックスに残すと止まる。別の節に移す

前の日に、人の目でしか確かめられない完了条件は何周しても満たされない、と書いた（[前の日の 4 節](./2026-10-10.md#takt-codex-batch)）。この日はそれを踏まえて、#713（Chromium の更新の後に、古いリビジョンを Playwright に消させる）の本文に、人の確認だとはっきり書いておいた。

```md
- [ ] （マージ後に人が）次に `playwright-core` の固定版を上げたとき、`cli update chromium` の後に `browsers/` に新しいリビジョンだけが残ること
```

それでも止まった。査読の 5 つの観点（コード・AI 特有の書き方・セキュリティ・設計・テスト）はすべて APPROVE で、指摘は 0 件だった。最後の判定だけが BLOCKED で、理由は「実装要件は充足しており、finding と修正対象はない。ただし、元仕様が明示したマージ後の人による受入条件は未完了である」。最後の判定は、本文のチェックボックスを全部埋めることを合格の条件にしている。括弧の中の注記は、その条件を緩めなかった。takt の自動の積み直しが 2 回走り、どちらも同じ判定に戻った。3 本の run で 46 分を使った。

差分を引き取って PR にし、人の確認は PR 本文の「## マージ後に人が確かめること」に書いた。この後に積んだ #841・#843 では、本物のモデルで測る条件を、積む前にチェックボックスから本文の別の節へ移した。

**エージェントが合否を付ける欄には、エージェントが満たせることだけを置く。** 注記で「これは人の分」と伝えるより、欄から外すほうが確実だ。

### 2. 開始の前に確かめる項目を足すと、その入口を通るテストがすべて巻き込まれる。巻き込まれるのは CI でしか流さない層だった

#706 は、会議を始める前に、要る依存（Claude Agent SDK など）が入っているかを確かめ、欠けていれば exit 3 で止める変更だった。takt の run は、型・unit・light IT・E2E の smoke をすべて通して PR にした。ところが CI の heavy IT（本物の Chromium や外部プロセスを使う重い結合テスト）が落ちた。heavy IT は、テストごとに一時の管理ディレクトリ（重い依存を入れておく場所）を作り、本物の依存の確かめ（`ManagedDeps`）でサーバーを立てていた。その一時のディレクトリには Claude Agent SDK が入っていないので、新しい確かめが会議の開始を 503 で断っていた。

takt の run は heavy IT を流さない。リポジトリの約束で、heavy は CI に任せているからだ。そのため、この落ち方は CI で初めて見えた。直し方は、heavy IT のサーバーを「Claude Agent SDK は入っている」と答える偽物で包むことだった（`withFakeClaude`）。heavy IT が確かめたいのは Chromium の側で、Claude の有無ではないからだ。

同じ形は手元でも出た。#713 の heavy IT を手元で流したとき、一時のディレクトリに Chromium だけを入れると、`play`（録音を流し直して会議を再現するコマンド）が依存の欠けを知らせる 3 行を出して exit 3 で落ちた。CI は Claude も入れているので落ちない。手元では `deps:install claude` も足して流した。

**入口に確かめを足すチケットは、その入口を通るテストの層を全部数えてから流す。** takt に任せる層と CI に任せる層が分かれていると、片方だけが通った状態で PR ができる。それ以来、管理依存や heavy IT に触る PR は、マージの前に関係する heavy IT だけを手元で流してから auto-merge を予約している。

### 3. 記録の「実行中」は、runner が消えても残る。プロセスとログの時刻で確かめてから引き継ぐ

Codex が引き継いだとき、Claude Code の側で立てた runner のプロセスは消えていた。消えた原因は分かっていない。タスクの記録（`.takt/tasks.yaml`）には、#840 と #842 が `running` のまま残っていた。実際に調べると、#842 は終わっていて、PR [#854](https://github.com/daiki-beppu/live-mindmap/pull/854) は CI が通ってマージ済みだった。#840 と、その後に積んだ #831 は、何も動かないまま `running` と書かれていた。

takt の記録の `running` は、「runner がこのタスクを始めた」という書き込みで、「今も動いている」ことは保証しない。runner が後片付けをせずに消えると、その書き込みだけが残る。引き継ぎの資料に「実行中: #840・#842」と書いてあっても、それは書いた時点の写しだ。

引き継いだ側は、次の 3 つを見てから動いた。

- runner のプロセスがあり、作業ディレクトリがこのリポジトリか（`pgrep` と `lsof -d cwd`）
- 各タスクの作業用のクローンで、run のログ（`.takt/runs/*/logs/*.jsonl`）が数分以内に伸びているか
- 記録が `running` のタスクに、もう PR ができていないか

runner を新しく立てると、takt は起動のときに `running` のタスクを中断されたとして `failed` に書き換える。止まった 2 本は、作業用のクローンと差分とレポートを残したまま、止まった位置（`resume-checkpoint`）から積み直した。#840 は修正の検証の工程から、#831 は計画から続きに入った。

### 4. 消えた記録が 1 件でもあると、一覧の道具ごと使えなくなる。片付けの道具が何を対象にするかを読む

状態を読む道具の 1 つ（takt の MCP の `takt_list_tasks`）が、`Worktree directory does not exist` で一覧を返さなくなっていた。数日前に失敗したタスクのうち 6 件（`failed`・`pr_failed`）の記録が、もう消した作業用のクローンを指していた。1 件の記録の先が無いだけで、一覧の全体が出ない。

片付けのスクリプトには、先の無い記録を消すオプション（`--missing`）がある。流すと「対象なし」で終わった。読むと、対象は `completed` の記録だけだった。失敗した記録は、何がどこまで進んだかの手がかりなので、勝手には消さない作りになっている。この 6 件も、関係する作業の所在を確かめるまでは消していない。代わりに、CLI の `takt list --non-interactive --format json` をいったんファイルに書いてから読んで、状態を取った（出力をパイプに直接流すと 64KB で切れることは、[前の日の 5 節](./2026-10-10.md#takt-codex-only)に書いた）。

**片付けの道具が「対象なし」と言ったら、壊れた記録が無いのか、その状態が対象外なのかを分ける。** 今回は後者だった。

### 5. 設定を戻すときは、動いている run に届かない前提で、空になるのを待って runner を立て直す

利用者の指示は、takt の工程を全部 Codex にしていた一時の上書き（リポジトリの `.takt/runtime.yaml`）を戻し、今の 2 本が終わったら回し直す、だった。上書きのファイルは 20 時 33 分に消した。#840 の査読の工程は 20 時 35 分に始まり、ログには `"provider":"codex"`、`"model":"gpt-6.1-sol"` と出ていた。ファイルを消した後に始まった工程でも、上書きの設定のまま動いている。少なくともこの run では、設定は run が始まったときに読まれていて、途中の変更は届かなかった。

元の設定に戻すには、runner を立て直す必要がある。前の日に、外から SIGINT を送ると実行中のタスクごと止まることを学んでいた。そこで、立て直しの手順を、待つ小さなスクリプトに書いて、runner とは別のタブで動かした。

- 15 秒おきにタスクの記録を読み、`running` と `pending` がどちらも 0 になるまで待つ。`pending` も数えるのは、残っていれば今の runner が古い設定のまま拾ってしまうからだ。そのため、立て直しが終わるまでは新しいタスクを積まない
- SIGINT を送る直前に、その PID のコマンドが `takt watch` で、作業ディレクトリがこのリポジトリかを確かめる。待っている間に runner が終わって、PID が別のプロセスに使い回されていても、それを止めないためだ
- 止めた後に runner が 60 秒以内に終わらなければ、例外で止まる。2 本目の runner は立てない。2 本目は、1 本目が持っているタスクを `failed` に書き換えるからだ
- 終わったのを確かめてから、同じタブで `exec` して新しい runner に入れ替える。利用者が見ているタブがそのまま新しい runner になる

**常駐のプロセスを入れ替える段取りは、「止めてよい条件」と「止めた相手が本物か」を、止める直前にもう一度確かめる形にする。** 待つ時間が長いほど、待ち始めたときの前提は崩れやすい。

### 6. 依存の版を固定するハッシュは、実際に落とすファイルから取る

#831（会議を外に見せる Tunnel のための `cloudflared` を、管理ディレクトリに入れる）を積む前に、固定する版 `2026.9.2` の tgz のハッシュを本文に書き写した。Codex は、GitHub のリリース API が返すファイルごとの digest と、同じ API から落としたファイルの SHA256 を比べ、arm64・amd64 の両方で一致することを確かめた。一方で、リリースの本文に書かれているチェックサムは、これと違う値だった。本文の値が何のハッシュなのか（tgz の中の実行ファイルか、別の版か）は確かめていない。

本文の値を写していたら、本物の tgz を落とす導入は、ハッシュの不一致で必ず失敗する。テストは偽のダウンロードで通るので、その失敗は利用者が初めて入れるまで見えなかったはずだ。**固定するハッシュは、説明の文ではなく、実際に落とすバイト列から取り、どこで取ったかを一緒に書く。** #831 のコメントには、照合した日と API の URL も書いた。

### 7. 一時的な失敗には自動の積み直しが効く

前の日は、自動の積み直しが環境の失敗に同じ結論を 2 回買うだけだったことを書いた。この日の #705 は逆の例だった。修正計画の工程で、Codex の API 呼び出しが `401 Unauthorized: Missing bearer or basic authentication in header` で落ちた。自動の積み直しで 2 回目に入り、そのまま完了して PR [#806](https://github.com/daiki-beppu/live-mindmap/pull/806) になった。認証のヘッダーが落ちたのは一度きりで、コードにも本文にも原因が無い。

この日 2 回止まった理由（401 と BLOCKED）を比べると、自動の積み直しに任せてよいかは、止まった理由がもう一度起きるかで分かれる。認証や通信の一度きりの失敗なら、積み直しで進む。本文に書いた条件で止まったなら、同じ本文を読み直すだけなので、何度でも同じ判定に戻る。

## 判定だけを任せる System One モデルの口を決めたら、口の形は計測を待たずに決まり、速さのための足しは「無くても同じに進む」と定義に書き、ローカルモードの約束とぶつかる一言は約束の側から形を変えた話

live-mindmap では、発言のたびに Claude（Sonnet 5.5）が**差分更新**（マップへの追加・更新・移動などの操作を出すこと）を行う。これを速く・安くするために、選択肢から選ぶだけの判断専用のモデル（System One モデル。TypeSafe の Jev、Cloudflare Workers AI の Clef など）に一部の判断を任せる地図を進めている。その中で、判断を任せる段の口と設定、既定のモデルを利用者と対話で決めたときの学び。

- 決定の記録: チケット [判定の段をアダプター形式で切り、既定のプロバイダーを決める](https://github.com/daiki-beppu/live-mindmap/issues/762)、ADR [0020 判定は判定のモデルを差し替えられる口の後ろに置き、無くても動くようにする](../adr/0020-judge-behind-swappable-port-optional.md)、次のチケット [Jev と Clef（flash・本体）を同じ条件で測る](https://github.com/daiki-beppu/live-mindmap/issues/857)、地図 [System One モデル（Jev・OpenAI Decisions・Clef）で反映を速くし、費用を下げる](https://github.com/daiki-beppu/live-mindmap/issues/757)

### 1. 決める前に測ることが並んでいても、その結果で変わる部分だけを後ろに回す

チケットには「既定を決める前に測ること」が 5 つ並んでいた。日本語の精度、日本からの応答時間の p50/p90、各社の `usage` で数え直した費用、選択肢の順による偏り、範囲外の発言の判定だ。これを全部このチケットで測ってから決めると、1 回の対話では終わらず、その後ろで待っている試作 5 件（発言の区切りを早める、話しているノードを光らせる、Haiku と Sonnet に振り分ける、など）も止まったままになる。

測った結果で変わるのは、どのモデルを既定にするかだけだった。Jev と Clef は同じ System One API（`state` と質問の束を渡し、質問ごとに確率の分布を受け取る形）で、違うのは宛先・モデル名・鍵だけだ。どちらが勝っても口の形は変わらない。そこで、口・設定・失敗時の振る舞いはこの場で決め、既定はいったん `jev` にして試作もそれで進めることにした。同じ条件で測る作業は別のチケットに切り出し、既定の見直しはその後ろに置いた。**「決める前に測る」と書かれた項目は、測った結果でどの決定が変わるかを一つずつ確かめ、変わらない部分は先に決めて後続を止めない。**

### 2. 判定ごとの関数ではなく、汎用の口を 1 つにする

口の切り方には 2 案あった。判定ごとの関数（「どのノードの話か」「発言の難しさ」など）をモデルごとに実装する案と、モデルは汎用の口（choice・score・yes-no の質問を受ける）だけを持ち、判定はその上で質問を組み立てる案だ。前者では、判定を 1 つ足すたびにモデルの数だけ書くことになる。OpenAI の Decisions API は別の API だが、`predicate`（真である確率）を yes-no に、`refusal`（答えの拒否）を「判定できなかった」に写せば、同じ口に収まる。

設定も新しく考えず、差分更新のモデルを選ぶ既存の設定（`~/.live-mindmap/config.json` の `models` と `default`、上書きは `--model`）に形をそろえ、`judges` と `judge`、`--judge` にした。`--judge off` で判定を使わない。**差し替えたい相手どうしが同じ API を持っているなら、口はその API の形にそろえ、設定は既存の似た設定の形を写す。** 利用者が覚えることが増えない。

### 3. 速さのための足しは、「無くても同じに進む」を定義に書く

前に、Jev で雑談を判定して Claude の呼び出しを減らす案を試して見送っている。6 場面で費用は $0.31 から $0.26 に下がっただけで、後回しにした発言の反映は最大 31 秒遅れた。判定を通らないと先に進めない作りにすると、判定の失敗や遅れがそのまま会議の遅れになる。

今回は、鍵が無ければ 1 行知らせて判定なしで始め、会議中に 1 回の判定が失敗・時間切れになったら、その発言は判定が無いときの流れ（いまの動き）で処理する、と決めた。これを個々の機能の約束にとどめず、用語集の「判定」の定義に「判定が無くてもセッションは同じように進む」と書いた。こうしておくと、後で判定を使う機能を作るときに、判定が無いときの動きを持つのが前提になる。**速くするための部品は、無くても同じ結果になることを、実装の注意ではなく言葉の定義に入れておく。**

### 4. 利用者の一言が既存の約束とぶつかったら、約束の側から両立する形を示す

質問に「すべて推奨」と答えてもらった直後、利用者から「ローカルモードでも品質向上に繋がるなら使う」と追加があった。**ローカルモード**は、会議の中身が利用者の Mac の外に一切出ないことを約束するセッションの設定だ。差分更新のモデルも、live-mindmap が自分で起動する子プロセス（Apple Intelligence）に限っている。Jev も Clef もクラウドなので、そのまま受けると発言が外に出て、規程で外部の AI を禁じられている人が使える唯一の道が無くなる。

一言をそのまま設計に入れず、用語集と ADR を読み直してぶつかる点を示し、3 案を出した。約束を守ったまま、Mac の中で動く判定のモデルだけを許す案。約束を変えてクラウドを許す案。前日に見送った端末内の Clef-flash を復活させる案だ。利用者は 1 つ目を選んだ。「品質が上がるなら使う」という意図は、約束を崩さない形でも満たせた。**要望が既存の約束とぶつかったら、要望と約束のどちらかを捨てる前に、約束の内側で要望を満たす形があるかを探して示す。**

### 5. 新しい語を提案する前に、用語集の「避ける語」まで読む

判定を担うモデルを指す語として、最初は「判定のプロバイダー」を提案し、利用者も了承した。ところが、用語集に書き込む段になって読み直すと、「差分更新のモデル」の項が「プロバイダ」を避ける語にしていた。どこで動くか（クラウドか Mac の中か）まで含めてモデルを指すためで、宛先や会社名だけではどのモデルかが決まらない、という理由だった。同じ会社の Clef と Clef-flash を選び分ける判定でも、この理由はそのまま当てはまる。

提案を出す前に読んでいたのは、用語集の見出しの一覧と「判定」が既にあるかだけで、近い項の _Avoid_ までは読んでいなかった。食い違いを示して聞き直し、「判定のモデル」に改め、「プロバイダー」を避ける語にした。**新しい語を提案するときは、同じ並びにある既存の語の定義と避ける語を先に読み、並びをそろえる。** 了承された後でも、書き込む前に食い違いに気づいたら聞き直す方が、用語集に 2 つの流儀が残るより安い。

## 発言の区切りを判定で早める試作をしたら、判定はモデルなしの句読点の規則に勝てず、早く切った分は差分更新の呼び出しの詰まりに移った話

[反映の遅れを区間に分けて測り直した](#latency-breakdown-remeasure)結果、話し終わりからマップに出るまでの遅れの長い尾は、1 つの**発言**（STT の結果を差分更新に渡す 1 区切り。いまは途中結果が 1 秒変わらなければ作る）が 2〜5 行をまとめ、前のほうの行が後ろの行を待つことから来ていた。そこで、話しているそばから届く**途中結果**（STT が確定させる前の暫定の文字列）を見て「ここで言い終わったか」を**判定**（選択肢から選ぶだけの軽いモデルの答え。ここでは TypeSafe の Jev）させ、早く発言にできるかを試作した。結論は「区切りに判定は使わない」で、モデルを使わない句読点の規則は別の問いとして地図の外に出した。

- 決定の記録: チケット [発言にする区切りを判定で早め、差分更新を早く呼ぶ](https://github.com/daiki-beppu/live-mindmap/issues/763)、地図の外に出した問い [途中結果の文の終わりで発言にし、差分更新の呼び方と合わせて決める](https://github.com/daiki-beppu/live-mindmap/issues/869)、地図 [System One モデル（Jev・OpenAI Decisions・Clef）で反映を速くし、費用を下げる](https://github.com/daiki-beppu/live-mindmap/issues/757)

### 1. モデルに判断させる案は、モデルなしの一番素朴な規則と並べて測る

前回の計測で使った途中結果の記録（合成会議 screen 23 分・facilitators 55 分）を、発言を切る規則だけ差し替えて流し直す使い捨てのシミュレーターを書いた。比べたのは、いまの規則、話者が替わったところで切る規則、Jev に「ここで言い終わったか」を聞いて切る規則だ。途中結果を眺めると、SpeechAnalyzer（macOS の音声認識）は確定前から「。」「？」を付けていた。そこで、途中結果に文の終わりが出たら即座に切る、モデルを使わない規則も加えた。

話し終わり → 発言（p50 / p90、秒。screen / facilitators）:

| 規則 | p50 | p90 | 発言の数 |
|---|---|---|---|
| いま（途中結果が 1 秒変わらなければ） | 3.1 / 3.7 | 9.6 / 12.2 | 221 / 448 |
| 文の終わり（。？！）が出たら切る | 0.6 / 0.7 | 1.5 / 2.2 | 772 / 1361 |
| 話者の交代で切る | 1.2 / 1.5 | 3.3 / 9.3 | 488 / 796 |
| 話者の交代 ＋ 文の終わりで切るかを Jev が決める | 0.8 / 1.2 | 1.6 / 6.8 | 604 / 950 |

Jev への問いは「｜より前は、話し手が言い終えたひとまとまりの話か」の yes-no で、直前の発言と候補の前後を渡した。1 回は約 0.17 秒、23 分で入力 13 万トークンと費用は無視できる。ただ、答えの 82% が 0.3〜0.7 に集まり、0.9 を超えたものは 1 件も無かった。モデルは迷っていて、切る位置の手がかりになっていない。切るのを見送った分だけ遅れ、細切れは句読点の規則より 1〜2 割減っただけだった。

試作を始めたときは「判定を使うとどこまで速くなるか」を測るつもりで、いまの規則としか比べない計画だった。それだと Jev は「p90 を 9.6 秒から 1.6 秒に縮めた」と見え、採る方向に傾いていたはずだ。**モデルに判断させる案を測るときは、同じ情報で動くモデルなしの一番素朴な規則を対照に入れる。** 勝てなければ、そのモデルは何も足していない。

句読点で切る規則は判定ではないので、判定を主題にしたこの地図には入れず、別の issue に出して地図の「範囲外」に指し先を残した。地図の主題から外れた発見でも、捨てずに、主題の合う場所へ渡す。

### 2. 1 つの区間を縮めたら、終わりまで流して詰まりの移り先を見る

発言までの p90 が 9.6 秒から 1.5 秒になるなら、マップに出るまでも同じだけ縮むと思っていた。screen を Claude（Sonnet 5.5）まで流すと、そうはならなかった（各 1 回）。

| 規則 | 話し終わり → ノード p50 / p90 | 差分更新の呼び出し | 1 回に渡す新しい発言の最大 | 費用 | 決定 | TODO |
|---|---|---|---|---|---|---|
| いま | 7.9 / 15.3 | 202 | 2 | $2.11 | 3/5 | 6/7 |
| 文の終わりで切る | 5.4 / 8.0 | 385 | 13 | $3.59 | 4/5 | 4/7 |
| 話者 ＋ Jev | 5.3 / 8.8 | 355 | 25 | $2.99 | 2/5 | 5/7 |

p90 はほぼ半分になったが、p50 は 2.5 秒しか縮まなかった。**差分更新**（新しい発言を Claude に渡し、マップへの変更を返させる呼び出し）は、発言が 2 つたまるか 1.5 秒次が来なければ呼び、前の呼び出しが終わるまで次を待つ。発言が 3.5 倍に増えると呼び出しも約 1.9 倍になり、待つ間に発言が最大 13〜25 件たまった。費用は呼び出しごとのキャッシュの書き込みが効いて 1.4〜1.7 倍になった。表の費用は差分更新の Claude の分で、Sonnet 5.5 の定価（100 万トークンあたり入力 $2・書き込み $4・読み出し $0.10・出力 $10）で数えた。Jev の分は含まず、23 分で約 $0.005 だった。決定・TODO の再現率は 1 回ずつでは揺れと区別できない。

詰まりは「発言にするまで」から「差分更新の呼び方」に移った。**ある区間を縮める案は、その区間の数字で判断せず、終わりまで流して、次にどこが詰まるかと費用を見る。** 地図の外に出した問いは、区切りと呼び方を同じ素材で一緒に測る前提で書いた。

### 3. 数え方を変えたら、まず前の計測の数字を再現する

シミュレーターの最初の版は、前回の計測の数え方（台本の各行について、行の区間の中央を含む最初の発言が届いた時刻 − 行の話し終わり）を写した。いまの規則では前回と同じ 2.0 / 8.6 秒・2.1 / 10.7 秒が出たので、シミュレーターが本番の規則を写せていることは確かめられた。

ところが句読点の規則では p50 が −0.6 秒になった。1 行に文が 2 つある行では、最初の文の発言が行の中央を覆い、行の話し終わりより前に届いたことになっていた。中央で数える方法は、発言が行より長い前提でしか成り立たない。数え方を「行の話し終わりの 0.3 秒前を含む発言」に変えた。いまの規則の値は 3.1 / 9.6 秒・3.7 / 12.2 秒に上がった（前回の数え方は途中の行の待ちを少し短く数えていた）。

**新しい道具は、まず前の計測の数字を再現してから使い、比べる対象が変わったら、数え方の前提（発言が行より長い、など）がまだ成り立つかを確かめる。** 負の遅れのような、ありえない値は数え方の前提が崩れた印になる。

### 4. 本番の規則を写すときは、出す直前の関所まで通す

句読点の規則の発言を作ってみると、同じ文が 2 つの発言に重複して入っていた。途中結果は同じ発話の中では本文が先頭から積み上がるので、1 秒の規則で一度出した後に続きが届くと、先頭からの本文がもう一度出る。前回の計測の道具が作った発言にも同じ重なりがあった。

本番のコードを読むと、発言を出す直前に関所（`remarkGate`）があり、直前に出した本文と重なる分を落としていた。前回の道具はこの関所を通さずに Claude へ流していた。そのため、前回書いた「発言の長さ p50 14 秒」は本番より長い。関所を通すと約 5 秒だった。シミュレーターはどの規則も関所を通すように直した。

**本番の規則を写した道具で測るときは、規則の本体だけでなく、出す直前の後処理まで同じものを通す。** 本体だけ写した道具は、本番に無い入力を後段に渡している。

### 5. 使い捨ての道具は、前日のものでも main の変化で動かなくなる

前日の計測の道具を差分更新まで流そうとすると、2 回止まった。1 回目は、差分更新の Layer が新しく必要とするサービス（管理下の依存を置く場所）を誰も渡していないというエラーだった。2 回目は、管理下の Claude の SDK がこの worktree に入っていないというエラーだった。どちらも前日から main に入った変更で、本番の入口（`sttReplay.ts`）は追従していたが、ブランチに置いた使い捨ての道具は追従していなかった。約 25 分の流し直しを 2 回失った。

また、Jev の鍵を 1Password から渡す `op run` を背景で回したとき、ロック解除を待って黙って止まった。Jev の答えを問いと一緒にファイルへ貯め、2 回目からは鍵なしで発言を作り直せるようにした（貯めた答えは会議の本文を含むので、コミットからは外した）。

**長く流す計測は、本番の入口と同じ組み立てを使っているかを先に読み、数十秒の試運転でエラーが出ないのを確かめてから流す。** 外部のモデルの答えは貯めておけば、数え方を直すたびに呼び直さずに済む。
