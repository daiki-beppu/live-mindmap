## 会議のマインドマップを会議の後に何の形で取り出すか決めた話

会議の後にマップを取り出す**エクスポート**の形を決めたときの学び。エクスポートとは、その時点のマップを、人とエージェントが使える形でセッションの外へ書き出すことをいう。取り出すものと形式、根拠の含め方、取り出すきっかけを順に決めた。コードは書かず、候補を並べて 1 つずつ決めた。形式の事実は、サブエージェントに公式ドキュメントとソースを調べさせた。

- 決定の記録: [エクスポート：会議の後に何をどの形式で取り出すか](https://github.com/daiki-beppu/live-mindmap/issues/23)
- 用語集: [`CONTEXT.md`](../../CONTEXT.md)（ノードの種別・根拠・セッションの語彙）

前提として、次のことが決まっていた。

- マップは会議をルートとする木で、ノードの種別は 議題・論点・案・決定・課題・TODO。論点は `未決` か `決定済み`、案は `検討中` か `却下` の状態を持つ
- 各ノードは**根拠**（ノードの元になった発言への参照）を 1 つ以上持つ。発言は STT が確定させた 10〜15 秒程度の文字起こしの 1 区切りで、開始・終了時刻を持つ
- 状態を持つのはローカルの Node サーバーだけで、ログはセッション（1 つの会議を追う一続きの作業）ごとの JSONL に追記する
- 基本操作（開始・終了・エクスポート・再生）は、AI エージェントがサーバーの CLI から行う。ブラウザは表示専用

### 1. 形式より先に「誰が何に使うか」を決め、出力を役割で分ける

最初の問いは形式ではなく、読み手にした。候補は「人が読む議事録」「エージェントが加工する材料」「両方」の 3 つで、両方を選んだ。基本操作をエージェントが行う前提なので、「議事録を Notion に貼って」「TODO を起票して」とエージェントに頼むのが自然な使い方になる。その場合、エージェントが人向けの Markdown を解釈し直すより、構造化データから組み立てるほうが確実だ。

この答えに、次の一言が付いた。

> 手軽に mindmap のスクショとかもいいかも
> できれば編集可能なマインドマップが理想

これで出力は 4 つになり、それぞれに役割を 1 つずつ割り当てた。

| ファイル | 役割 | 中身 |
| --- | --- | --- |
| `map.md` | 人が読む | 決定・TODO・未決の論点の一覧と、マップの木 |
| `map.json` | エージェントが加工する | 最後のマップのスナップショット |
| `map.drawnix` | 人が開いて直す | Drawnix で編集できるマインドマップ |
| `map.png` | 人が見る | マップ全体の画像 |

4 つとも同じスナップショットから作るので、中身が食い違うことはない。

**エクスポートの形式を選ぶ前に、読み手と使い道を並べ、1 つの出力に 1 つの役割を割り当てる**。

### 2. 同じ事実を複数の出力に書かず、派生は読み手の側で導く

エージェント向けのデータには、3 つの候補があった。

- 何も足さず、エージェントにログ（JSONL）を読ませる
- 最後のマップのスナップショットを JSON で出す
- スナップショットに加えて、TODO 一覧や決定一覧も JSON で出す

2 つ目を選んだ。ログは「起きたことの流れ」なので、最後のマップを知るには差分操作を順に適用し直す必要がある。その適用関数を持たないエージェントに、ログを読ませるのは重い。一方、TODO 一覧や決定一覧はマップの木から導ける。それを JSON に重ねて持つと、同じ事実が 2 か所に書かれることになる。

同じ考えで、`map.md` の冒頭に置く 3 つの一覧（決定・TODO・未決の論点）も、書き出すときに木から導く。論点の `決定済み` という状態も、保存せず「子に決定を持つか」から導く状態なので、出力でもそのまま `→ 決定：…` と子を並べて表した。

**派生できる情報は出力に重ねて持たず、読み手（エージェント、または書き出し処理）の側で導く**。

### 3. 根拠は、読み手ごとに見せる粒度を変える

根拠の発言をどこまで出すかは、読み手によって答えが違った。

- `map.md`: ノードごとに会議の中の時刻だけ付ける（例：`（12:34）`）
- `map.json`: 発言の ID に加えて、本文と時刻も持つ
- `map.drawnix`: 含めない

議事録に発言の本文を抜粋すると長くなるうえ、STT の誤認識がそのまま人の目に触れる。時刻があれば、録音や JSON の本文にたどれる。後で調べたところ、Drawnix の形式にはメモ欄がなかった。しかし根拠は md と json に置き場があるので、編集用のファイルで失っても困らない。

**根拠のような補助情報は、すべての出力に同じ粒度で入れず、置き場を 1 つ確保したうえで読み手ごとに削る**。

### 4. 却下した案は消さず、元の位置に取り消し線で残す

却下した案の扱いには、「含めない」「取り消し線で元の位置に残す」「末尾にまとめる」の 3 つの候補があった。取り消し線を選んだ。何を検討して捨てたかは、議事録として価値がある。元の位置にあれば、どの論点に対する案だったかも分かる。一方、案の `検討中` にはあえて印を付けていない。普通の状態に印を付けると、印だらけの議事録になるからだ。

**状態の表し方は、例外の状態にだけ印を付ける**。

### 5. 「編集できる形式」は、読み込み側の実装を見て選ぶ

編集できる形式は、開くツールで決まる。候補を調べた結果が次の表だ。

| 形式 | 開いて編集できるツール | 種別の色 | メモ（根拠） |
| --- | --- | --- | --- |
| XMind（`.xmind`） | XMind、MindNode | 可（ノードごとの指定は公式で未確認） | 可 |
| Drawnix（`.drawnix` の JSON） | drawnix.com | 可 | 不可 |
| FreeMind / Freeplane（`.mm`） | Freeplane、XMind、MindNode | 可 | 可 |
| Markdown の箇条書き | XMind、MindNode、Drawnix、markmap、Whimsical | 不可 | 不可 |
| Mermaid mindmap | テキストとして直すだけ | ほぼ不可 | 不可 |

Drawnix を選んだ。画面の見た目が Drawnix 風なので、書き出したマップが表示と揃う。Drawnix のファイル形式は公式ドキュメントにはまとまっていなかった。そこで、ソースの読み込み処理を読んだ。確認されるのは次の 3 点だけだった。

- `type` が `"drawnix"` であること
- `elements` が配列であること
- `viewport` がオブジェクトであること

マインドマップは `type:'mindmap'` の要素で、`children` の入れ子で木を表し、色は `fill` / `strokeColor` / `branchColor` で指定できる。こちらのマップも木なので、サーバーでそのまま組める。XMind は色もメモも持てるが、ノードごとの色の付け方を公式で確認できなかったので、必要になったら足すことにした。

**「このツールで開けるか」は、ドキュメントより先に読み込み処理のソースで確かめる**。確認項目が少なければ、自前で組んでも壊れにくい。

### 6. 画像の撮り方は、「いつ撮るか」の決定から逆算する

画像の撮り方には 3 つの候補があった。

| 案 | 長所 | 短所 |
| --- | --- | --- |
| ブラウザ側で html-to-image | 依存が 1 つで最も軽い | ブラウザを開いているときしか撮れない |
| サーバーが Playwright で自分の表示ページを撮る | ブラウザを開いていなくても撮れる | ブラウザ本体で数百 MB の依存 |
| サーバーで SVG を直接組む | 依存がない | 配置計算を二重に持ち、見た目が表示とずれる |

軽さだけなら html-to-image だ（React Flow の公式の画像出力例も、これを使っている）。しかし、その前に「セッションの終了時に自動で書き出す」と決めていた。エージェントに export を呼び忘れさせないためだ。終了時にブラウザが開いている保証はないので、撮れないことがある。そこで Playwright を開発用の依存に入れ、サーバーが自分の表示ページを開いて、全体を収めた状態で撮ることにした。更新を知らせる赤い枠や「変わったこと」の一覧は写さない。この仕組みは、再生（録音済みの会議を流し直す回帰評価）の結果を画像で残すのにもそのまま使える。

なお、html-to-image は、公式の例では版を 1.11.11 に固定している。それより新しい版は画像が正しく出ない不具合があり、このエントリを書いた時点では未解決だった。

**手段の軽さで選ぶ前に、先に決めた「いつ・誰が起動するか」と矛盾しないかを見る**。自動で動く処理に、人の画面を前提にする手段は組み合わせない。

## LLM がマップを差分更新する中核を、テストファーストで本実装した話

試作から本実装に移る最初の 1 本を、テストファースト（失敗するテストを書いてから、通すだけのコードを書く繰り返し）で作ったときの学び。作ったのは、文字起こしのファイルを流すと Claude がマップを組み立て、CLI でその時点のマップを JSON で取り出せるところまで。音声・画面はまだない。テストは 15 本になり、最後に本物の Claude（Sonnet 5.5）で録音サンプルの一部を流して確かめた。

- 決定の記録: [文字起こしのファイルを流すと、AI がマップを組み立てる](https://github.com/daiki-beppu/live-mindmap/issues/31)、[ADR 0003 ローカルの Node サーバーがパイプラインを持つ](../adr/0003-local-node-server-owns-pipeline.md)
- 用語集: [`CONTEXT.md`](../../CONTEXT.md)（ノードの種別・差分操作・発言・セッションの語彙）

前提として、次のことが決まっていた。

- マップは会議をルートとする木で、AI は毎回作り直さず、既存のマップへの**差分操作**（追加・更新・統合・移動・削除・何もしない）を返す
- **発言**は、STT（音声認識）が確定させた 10〜15 秒程度の文字起こしの 1 区切り。スピーカーで聞くと相手の声が自分のマイクにも入るので、二重に拾った発言には**重複の印**を付け、差分更新に使わない
- 差分更新は、重複の印がない発言が 2 つたまるごとに呼ぶ。同時に呼ぶのは 1 つまでで、呼び出し中にたまった発言は次の 1 回にまとめる
- 中核のモジュールは、WebSocket・CLI・Node の実行環境に依存しない TypeScript で書く（後でアプリに移しやすくするため）

### 1. テストを置く場所は、書く前に 2 か所に絞って合意する

試作には、操作を検証して適用する純粋関数 `applyOps` がすでにあった。純粋関数はテストしやすいので、ここに検証のテストを細かく並べたくなる。しかし、仕様のテスト方針は「入力は発言の流れ、見るのはスナップショット（その時点のマップ全体）とログ」だった。`applyOps` を直接叩くテストは、適用関数の引数の形が変わるたびに壊れる。

そこで、テストを書く前に、置く場所（継ぎ目）を次の 2 つに絞り、人と合意した。

| 継ぎ目 | 入れるもの | 差し替えるもの | 見るもの |
| --- | --- | --- | --- |
| セッション | 発言を 1 つずつ | 差分更新（台本どおりに操作を返す偽物） | スナップショット、ログのイベント |
| CLI | `replay <ファイル>` → `export --format json` | 差分更新、セッションの置き場 | 標準出力の JSON |

検証の規則（決定の親は論点だけ、削除は葉だけ、統合は同じ種別どうし、など）も、すべてセッションの外から確かめた。偽物の差分更新に規則違反の操作を返させ、スナップショットにノードが無いことと、ログに捨てた理由が残ることを見る。結果は、セッションに 14 本、CLI に 1 本になった。

**テストの置き場所は「どこが一番テストしやすいか」ではなく、「仕様が何を観察すると言っているか」で決める**。

### 2. 「N 個ごとに呼ぶ」という規則には、余りの扱いが書かれていない

「2 つたまるごとに呼ぶ」と「呼び出し中にたまった分は次の 1 回にまとめる」を実装すると、仕様に書かれていない場合が出てきた。**呼び出しが終わった時点で、発言が 1 つしかたまっていないとき**だ。すぐ呼べば反映は速いが、1 発言ずつの呼び出しが続いて回数が増える。2 つ目を待てば規則どおりだが、会議の最後の 1 発言が反映されないまま残る。

2 つ目を待つことにした。理由は 3 つある。

- 試作でプロンプトの出来を測ったのは「2 発言ごと」の入力だった。1 発言だけの入力は、まだ評価していない形になる
- ライブでは差が小さい。発言は 1 つ 10〜15 秒、応答は試作の計測で中央値 約 3 秒（今回の 6 発言の確認では 1 回 約 7 秒）なので、呼び出しの最中に発言がたまる場面そのものが少ない
- 呼ぶかどうかが発言の数だけで決まると、録音を流し直したときに同じ呼び出しが再現できる

残った 1 発言は、セッションの終わりに明示的に流す `flush()` で拾う。ライブで話が途切れたときの扱い（一定時間で流すか）は、ライブのセッションを作るときに決める。

**「N 個ごと」「N 秒ごと」の規則を実装するときは、余りと終わりの扱いを先に決める**。

### 3. 待ち時間なしの再生は、1 つ流すたびに呼び出しの終わりを待つ

録音済みの会議の文字起こしを流し直す**再生**は、回帰評価のために待ち時間なしで流したい。素直に全発言を一気にセッションへ入れると、次のことが起きる。

```text
push(u1), push(u2)          → 1 回目の呼び出しが始まる
push(u3) … push(u200)       → 1 回目の最中なので、全部たまる
1 回目が終わる               → 2 回目に 198 発言がまとめて渡される
```

「呼び出し中にたまった分はまとめる」という、ライブでは正しい規則が、流す速さが変わっただけで別物になる。仕様には「待ち時間なしで流しても、ライブと同じ順で同じ呼び出しが起きる」と書かれていた。

再生の側で、1 つ流すたびに呼び出しの終わりを待つようにした。

```ts
for (const u of utterances) {
  session.push(u);
  await session.idle();  // 呼び出し中なら終わるまで待つ
}
await session.flush();
```

こうすると、呼び出しの区切りは応答の速さによらず「2 発言ごと」になり、呼び出しが重ならないライブと同じになる。

**流す速さを変えて再現させたいときは、時刻ではなく処理の終わりで同期する**。

### 4. 実行環境に依存しない中核は、出口を引数で受け取る

中核を Node に依存させないために、ファイルへの書き込みは中核の外に出した。セッションはログのイベントを `log: (event) => void` という引数に渡すだけで、JSONL に追記するのは CLI の側だ。差分更新も `updater: (input) => Promise<{ ops }>` という引数で受け取る。

この形は、そのままテストの差し替え口になった。

- セッションのテストは、`log` に配列への追加を、`updater` に台本を返す関数を渡す
- CLI も `runCli(argv, { updater, sessionsDir, stdout })` という関数として書き出した。テストは子プロセスを立てずに同じプロセスで呼び、一時フォルダと偽物の差分更新を渡す
- 本物の差分更新（Agent SDK を使う）は、`updater` が渡されなかったときだけ `import()` で読み込む。テストでは SDK を読み込まない

ログの差分操作のイベントには、入力の要約（渡した発言の ID、その時点のノード数）・返ってきた操作・捨てた操作とその理由を残す。差分更新が例外を投げたときも `error` を残し、マップは変えずに次の呼び出しへ進む。

**実行環境に触る出口（ログの書き先、外部の呼び出し）を引数にすると、移植性とテストの差し替え口が同時に手に入る**。

### 5. 最初から通ったテストは、一度わざと落として確かめる

テストファーストでは、テストは失敗してから通るのが普通だ。しかし「直前の発言として、処理済みのうち最後の 3 つを渡す」のテストは、書いた時点で通った。前のスライスで、呼び出しの制御を作るついでに実装していたからだ。

最初から通るテストは、何も確かめていない可能性がある。そこで、実装の `RECENT = 3` を一時的に `4` に変えて流し、このテストだけが落ちることを確かめてから戻した。

```text
RECENT = 4 → × 直前の発言として、処理済みのうち最後の 3 つを渡す（1 failed | 13 passed）
RECENT = 3 → 14 passed
```

**赤を経ずに緑になったテストは、実装を 1 か所壊して落ちることを見てから残す**。

### 6. 本物の LLM での確認は、サンプルを数発言に切って 1 回だけ流す

テストは偽物の差分更新で通しているので、本物の Claude とつながっているかは別に確かめる必要がある。60 分の録音サンプルを全部流すと時間も費用もかかるので、`jq` で 6 発言だけ切り出して流した。

```sh
jq '.transcript.segments |= .[10:16]' facilitators-meeting.transcript.json > head.transcript.json
node src/cli.ts replay head.transcript.json
node src/cli.ts export --format json
```

結果は、呼び出し 3 回（2 発言ずつ）、全体で約 22 秒、捨てた操作 0、エラー 0。ログを見ると、1・2 回目でノードを 2 つずつ追加し（議題 3 つと、その下の 1 つ）、3 回目は新しいノードを作らず既存のノードを更新していた。言い換えは根拠を足す更新で表す、という試作のプロンプトの方針どおりに動いている。

Node 26 は `.ts` を型の除去だけで直接実行できるので、CLI はビルドせずに `node src/cli.ts` で動かしている。`tsconfig.json` に `erasableSyntaxOnly`（型の除去だけで動く構文に限る）と `allowImportingTsExtensions` を入れておくと、型チェックと直接実行が食い違わない。

**偽物で振る舞いを固めたら、本物との接続は小さく切ったサンプルで 1 回だけ確かめる**。出来の評価は、テストではなく回帰評価で行う。

## 会議のマップをブラウザに描く部分を、AI エージェントのワークフローに実装させた話

マップをブラウザに描く部分を作ったときの学び。サーバーは差分更新が反映されるたびに、マップ全体を WebSocket で送る。ブラウザは受け取ったものを React Flow で描くだけにした。実装は、AI エージェントのワークフロー実行ツール takt に任せた。takt は、計画 → テストを書く → 実装 → 6 観点のレビュー → 指摘の裁定 → 修正 → 再レビュー、という手順でエージェントを順に動かす。途中で API の利用上限に当たって 1 度止まり、再開してから完了した。

- 決定の記録: [ブラウザにマップが表示される](https://github.com/daiki-beppu/live-mindmap/issues/32)、[ADR 0003 ローカルの Node サーバーがパイプラインを持つ](../adr/0003-local-node-server-owns-pipeline.md)
- 用語集: [`CONTEXT.md`](../../CONTEXT.md)（ノードの種別・差分操作・発言・再生の語彙）

前提として、次のことが決まっていた。

- マップは会議をルートとする木。AI は毎回作り直さず、既存のマップに**差分操作**（追加・更新・統合・移動・削除）を当てる
- 描画には React Flow を使い、見た目は Drawnix 風に描き直す。左から右への木で、兄弟は作られた順に上から積み、親は子の範囲の中央に置く。描画ライブラリを比べた試作で、この形に決まっていた
- **再生**は、録音済みの会議の文字起こしを、発言の流れとしてもう一度流すこと。今回の作業で、CLI の再生に「等速」と「待ち時間なし」の 2 つのモードを持たせる

### 1. 表示専用のブラウザには、差分ではなく全体を送り、サーバーは最新の 1 つだけを持つ

差分操作を WebSocket で送り、ブラウザ側でも適用する案は、計画の段階で外した。ブラウザに適用の仕組みを持たせると、取りこぼした差分があったときに、サーバーとマップがずれる。全体を送るなら、ブラウザは届いたものを描き直すだけで済む。

この形だと、つなぎ直しもほぼ何もせずに済む。配信の側は、最後に送ったスナップショット（その時点のマップ全体）を 1 つ持っておく。新しくつないできたクライアントには、それをすぐ送るだけでよい。

```ts
wss.on("connection", (client) => {
  if (latest !== undefined) client.send(latest);
});
// publish: latest を更新し、OPEN のクライアント全員に送る
```

疎通のテストでは、送る → つなぐ → 切る → 切っている間に送る → つなぎ直す、までを同じサーバーで続けて行った。そして、つなぎ直したクライアントに最新の 1 つだけが届くことを確かめた。ブラウザの側は、切れたら 1 秒後につなぎ直し、その間も最後に受け取ったマップを出し続ける。配信のサーバーを止めて立ち上げ直すと、同じ画面が自動でつなぎ直して最新のマップを描いた。

差分更新が失敗した回は送らない。マップが変わっていないので、反映ではないからだ。

**ブラウザが描くだけなら、送るのは全体にする。そうすれば、つなぎ直しは「最新を 1 つ持っておく」だけで済む**。

### 2. 等速の再生は発言の時刻の差だけ待ち、処理の終わりは待たない

前のエントリで、待ち時間なしの再生は「1 発言流すたびに、差分更新の呼び出しが終わるのを待つ」ようにした。そうしないと、呼び出し中にたまった発言が 1 回にまとめて渡され、ライブとは別の呼び出し方になる。

等速の再生は逆で、呼び出しの終わりを待ってはいけない。等速の目的は、会議の流れどおりにマップが組み上がる様子をブラウザで見ることだ。ライブでは、話している人は LLM の応答を待たずに次の発言をする。そこで等速では、前の発言との終了時刻の差だけ待ってから次の発言を流し、呼び出しの終わりは待たないようにした。

| 再生のモード | 1 発言ごとに待つもの | 揃えたい相手 |
| --- | --- | --- |
| 待ち時間なし（既定） | 差分更新の呼び出しの終わり | ライブと同じ呼び出しの区切り（回帰評価用） |
| 等速（`--realtime`） | 前の発言との終了時刻の差 | ライブと同じ時間の流れ（見た目の確認用） |

待つ処理は、中核のモジュールに `sleep(ms)` という引数で渡した。中核は Node に依存させない方針なので、`setTimeout` を直接呼ばない。テストでは、記録するだけの `sleep` を渡して、引数が `[9800, 9400, 8800]`（発言の終了時刻の差）になることと、`sleep → push` の順に呼ばれることを確かめた。「呼び出しの終わりを待つ」誤った実装だと、偽物の差分更新が返らないあいだ 3 回目の `sleep` に進めず、テストが落ちる。

**同じ「再生」でも、何に揃えたいかで、待つ対象が変わる。呼び出しの区切りを揃えるなら処理の終わりを、時間の流れを揃えるなら時刻を待つ**。

### 3. 「追加しても上は動かない」は、高さが揃ったテストでは崩れない

描画ライブラリを比べた試作で、次の配置の規則にしていた。

- 兄弟は、作られた順に上から積む
- 親は、子の範囲の上下の中央に置く

この規則なら、追加で動くのは追加位置より下のノードだけになる、と考えていた。実装には、この性質を確かめるテストが 3 本あった。先頭・途中・末尾に子を足し、上のノードの座標が変わらないことを見るものだ。どれも通っていた。

ところが、レビューの段で 2 人のレビュアーが、同じ反例を独立に見つけた。**親が子の並びより高いとき**だ。

```text
親の高さ 200、子 A の高さ 40
  追加前: A.y = 80
  末尾に高さ 40 の子 B を足す
  追加後: A.y = 54   ← 追加位置より上の A が動いた
```

原因は、親の上端がはみ出す分の補正にあった。最初の実装は、子を上端 0 から積み、親が子の範囲より高ければ、はみ出し分 `(親の高さ − 子の範囲の高さ) / 2` だけ部分木全体を下げていた。子が増えると子の範囲が伸び、補正の量が変わるので、既存の子まで動く。

直し方は、補正を後から全体に足すのをやめることだった。最初の子を置く位置を、最初の子の高さだけで先に決める。

```ts
// 親が最初の子より高いと、親の上端が部分木の上にはみ出す。
// 最初の子の開始位置を、最初の子の高さだけで先に決めておく。
let offset = Math.max(0, (h - firstKidHeight) / 2);
```

こうすると、子をいくつ足しても最初の子の位置は変わらない。親は子の範囲の中央に置かれたまま、子が増えるにつれて下がっていく。

テストが見逃した理由は、高さの与え方にあった。性質を確かめる 3 本は、すべてのノードを同じ高さにしていた。高さが揃っていれば、親は子の範囲より高くならない。このアプリでは、会議のタイトルや長い論点のように、親のほうが文字が多く高くなる場面が普通にある。回帰テストは、根が高い場合と、根以外の親が高い場合の 2 本を足した。

**「追加しても上は動かない」のような性質のテストは、大小の関係が逆になる入力（親のほうが大きい、など）を必ず 1 つ混ぜる**。

### 4. 「反映のたびに全体を収める」は、最後の画面では確かめられない

カメラは、反映のたびにマップ全体が画面に収まるようにする。実装は、ノードが変わるたびに React Flow の `fitView` を呼ぶだけだ。

最初の動作確認は、スナップショットをいくつか流し、最後の画面で全ノードが画面内にあることを見ていた。しかし、「最初の 1 回だけ収める」という誤った実装でも、最後の画面が同じになることはある。ワークフローは、この確認を「未完了」と判断し、実装の段に差し戻した。

やり直しでは、本物の配信サーバーを一時スクリプトから起動し、1 → 3 → 8 → 12 ノードと段階的に送った。そして段階ごとに、ブラウザの画面の拡大率と位置、画面内に収まったノードの数を記録した。

| ノード数 | viewport（React Flow の表示位置） | 画面内に収まった数 |
| --- | --- | --- |
| 3 | `translate(66px, 432.3px) scale(1.858)` | 3 / 3 |
| 8 | `translate(66px, 284.2px) scale(1.365)` | 8 / 8 |
| 12 | `translate(66px, 144.9px) scale(1.365)` | 12 / 12 |

反映のたびに viewport が変わっているので、「初回だけ」の実装ではないと言える。

この観測では、最初にルートの `parent: null` を付け忘れて送り、全ノードが原点に重なった。配置の側に「親のないノードもルートとして扱う」処理を足す案もあったが、取らなかった。スナップショットの型ではルートの `parent` は `null` と決まっていて、本物のセッションはそのとおりに出す。型に反する入力を黙って受け入れる分岐は、本物の不具合を隠す。直したのは送るデータの側だった。

**途中の状態に関する振る舞い（反映のたびに〜する）は、最後の状態を見ても確かめられない。段階的に流して、段階ごとに記録する**。

### 5. 127.0.0.1 で待ち受けても、ブラウザで開いた任意のページからつながる

配信のサーバーは、実装の段で `127.0.0.1` だけで待ち受けるようにしていた。決定の記録には「ローカル専用なので」とある。セキュリティのレビュアーは、これを重大度 High で差し戻した。

`127.0.0.1` で待ち受けると、ほかのマシンからはつながらない。しかし、同じマシンのブラウザで開いたページなら、どのサイトのものでも `ws://127.0.0.1:4319` につなげる。WebSocket の接続には、ブラウザの同一オリジンの制限がかからないからだ。再生中に悪意のあるページを開いていると、そのページが会議の議題・決定・TODO をそのまま読み取れる。

ブラウザは、WebSocket の接続時に必ず `Origin` ヘッダーを付ける。そこで、サーバーの側で `Origin` を見るようにした。

```ts
const LOCAL_HOSTNAMES = new Set(["localhost", "127.0.0.1", "[::1]"]);
const isLocalOrigin = (origin: string) =>
  URL.canParse(origin) && LOCAL_HOSTNAMES.has(new URL(origin).hostname);

new WebSocketServer({
  host: "127.0.0.1",
  verifyClient: ({ origin }) => origin === undefined || isLocalOrigin(origin),
});
```

`Origin` のない接続は受け入れる。ブラウザ以外のクライアント（テストや CLI）は `Origin` を付けないし、ブラウザは必ず付けるので、ブラウザ上のページを締め出す目的には影響しない。テストは、許可する 4 通り（`localhost`・`127.0.0.1`・`[::1]` の各ポート付き、`Origin` なし）と、拒否する 3 通りにした。

| 拒否する `Origin` | 確かめたいこと |
| --- | --- |
| `https://evil.example` | 外部のサイト |
| `null` | サンドボックス化された iframe やファイルから開いたページ |
| `http://localhost.evil.example` | 文字列の前方一致で判定してしまう誤り |

3 つ目は、`origin.startsWith("http://localhost")` のような判定を弾くためのものだ。ホスト名を `URL` で取り出し、完全一致で比べているので通らない。ブラウザは開発サーバー（Vite）の `/ws` 経由でつなぐ。そのため、本来の `Origin`（`http://localhost:5173`）がプロキシを通って届く想定でいる。ただし、実際のブラウザでプロキシ越しに確かめるところまでは、まだしていない。

**ローカルのサーバーを「127.0.0.1 で待ち受けているから安全」と考えない。ブラウザから読めるものを配信するなら、`Origin` を完全一致で見る**。

### 6. 実装したエージェントのテストは、実装と同じ思い込みを持つ

1 回目のレビューでは、6 観点（フロントエンド、AI 生成コード、設計、コーディング、セキュリティ、テスト）のレビュアーから 4 件の指摘が出た。同じ原因のものをまとめると、直す問題は 3 つになった。

| 問題 | 見つけた観点 | 実装の側にあった思い込み |
| --- | --- | --- |
| 親が子より高いと、上のノードが動く（3 節） | 設計、コーディング | ノードの高さは揃っている |
| WebSocket が接続元を見ない（5 節） | セキュリティ | 127.0.0.1 ならローカルだけ |
| README の起動例のパスが存在しない | AI 生成コード | コマンドはリポジトリのルートで動く |

3 つ目は、`pnpm --filter <パッケージ> <スクリプト>` がスクリプトをパッケージのフォルダで動かすことを見落としていた。そのため、起動例が `server/server/test/...` という存在しないパスを指していた。

3 つとも、実装と一緒に書かれたテストはすべて通っていた（server 28 件、web 20 件）。テストを書いたのも実装したのもエージェントで、テストは実装と同じ前提の上に立っていた。一方、テストの観点のレビュアーは、1 回目に「指摘なし」を出していた。しかし、裁定の段は 3 節の見逃しをテストの観点の見落としとみなし、回帰テストの追加を修正の条件に含めた。

修正の後、2 回目のレビューでは 6 観点すべてが通した。テストは web 22 件、server 35 件になった。

**エージェントに実装させるときは、実装とテストを書いた側とは別の観点から見るレビューを挟む。テストが全部通ることは、前提が正しいことの証拠にはならない**。

### 7. 回帰テストを古いコードで落とすには、直す前の状態が履歴に残っている必要がある

前のエントリでは、「赤を経ずに緑になったテストは、実装を 1 か所壊して、落ちることを見てから残す」と書いた。3 節の回帰テストでも、修正の段のエージェントは、直す前のコードで落ちることを確かめようとした。しかし、できなかった。`layout.ts` はまだ一度もコミットされていない新しいファイルで、直す前の版を取り出す先がなかったからだ。比べようとする途中で、ファイルが一時的に空になる事故も起きた。退避しておいた新しい版を書き戻し、テストと型チェックが通ることで元に戻ったことを確かめた。

結局、直す前のコードで落ちることは、手計算（A の y が 80 から 54 に動く）で示すにとどまった。

**修正の前に、レビューを受けた状態を 1 度コミットしておく。そうすれば、回帰テストが古いコードで落ちることを `git stash` や `git checkout` で確かめられる**。

### 8. 段ごとに成果物をファイルに残すワークフローは、利用上限で止まっても続きから再開できる

今回の実行の時間の流れは次のとおり。

| 実行 | 内容 | 所要 |
| --- | --- | --- |
| 1 回目 | 計画 → テスト → 実装 → 実装のやり直し → レビュー（約 13 分） → 裁定 → 修正の計画 → 修正 → 修正の検証 → 2 回目のレビューの途中で利用上限 | 約 43 分 |
| 2・3 回目 | 2 回目のレビューから再開したが、まだ上限が解けておらず即座に停止 | 各 約 20 秒 |
| 4 回目（約 10 分後） | 2 回目のレビュー → 裁定 → 最終確認 → 完了 | 約 7.5 分 |

takt は、各段の成果物（計画・実装の報告・レビュー・裁定）をファイルとして残す。再開のときは、それを新しい実行に引き継いで、止まった段からやり直す。そのため、4 回目は計画や実装をやり直さずに、2 回目のレビューから始められた。2・3 回目の失敗は、上限が解ける前にすぐ再開したためで、成果物は何も失われていない。

**エージェントのワークフローは、段の区切りで成果物をファイルに書き出す形にしておく。利用上限で止まったら、上限が解けるのを待ってから、止まった段から再開する**。

## 会議音声を文字起こしする Swift のヘルパーを、AI エージェントのワークフローに実装させた話

会議アプリの音を取って文字にする Swift のヘルパー（常駐プロセス）を作ったときの学び。ヘルパーは、選んだ会議アプリの音を Core Audio のプロセスタップ（アプリ単位で出力音を横取りする macOS の API）で取り、Apple の SpeechAnalyzer（端末内の音声認識）に流し、結果を localhost の WebSocket に配る。実装は人が書かず、takt という AI エージェントのワークフロー実行ツールに任せた。takt は、計画 → テストを書く → 実装 → 観点別のレビュー（5 観点を並行）→ 指摘の裁定 → 修正 → 修正の検証 → 最終判定、という工程を順に回す。どの工程も別のエージェントが受け持ち、工程ごとに報告書を残す。このエントリは、その報告書と差分から拾ったものだ。

- 決定の記録: [ヘルパー：会議の音声を文字起こしする](https://github.com/daiki-beppu/live-mindmap/issues/33)、[ADR 0002 音声取得と STT はローカルのヘルパーが行う](../adr/0002-local-stt-helper.md)
- 用語集: [`CONTEXT.md`](../../CONTEXT.md)（発言・途中結果・トラックの語彙）

前提として、次のことが決まっていた（音の取り方を実測して決めた経緯は[別のエントリ](./2026-09-30.md#local-realtime-stt)にある）。

- **発言**は、STT（音声認識）が確定させた文字起こしの 1 区切り。**途中結果**は、確定前に届く暫定の文字列で、後で書き換わる
- **トラック**は音の出どころで、`相手`（選んだ会議アプリの音）と `自分`（マイク）の 2 つ。今回作るのは `相手` だけだが、`自分` も同じ形で流せるようにする
- Mac 全体の出力はタップしない。通知音や別のタブの動画まで拾うため
- 実機で会議を流して途中結果と発言が届くかは、人が確かめる

### 1. イベントの形は、受け取る側の型と「誰が何を採番するか」から決める

ヘルパーが WebSocket に流すイベントの形は、この作業で決めることになっていた。受け取る側のサーバーには、すでに発言の型があった。計画の工程は、項目名をその型に合わせたうえで、2 つの点で型をそのまま写さなかった。

```json
{"type":"partial","track":"相手","text":"こんに"}
{"type":"remark","track":"相手","start":1.5,"end":3.25,"text":"こんにちは","duplicate":false}
```

- **`id` を付けない。** サーバーの発言の型には `id` があるが、採番はサーバーが行う。ヘルパーでも振ると、ID の出どころが 2 つになる
- **途中結果に時刻と重複の印を付けない。** STT の途中結果にも時間範囲は付いてくる。だが、それを載せると途中結果と発言が同じ形になり、受け取る側が `type` だけで区別することになる。途中結果は 3 項目、発言は 6 項目と、キーの集合そのものを変えた

テストは値だけでなく、JSON のキーの集合が完全に一致することを確かめている。入力に時刻がある途中結果を渡しても、出力のキーは `type/track/text` の 3 つだけになる。

**境界のイベントは、受け取る側の型を写すのではなく、「その値を誰が決めるか」で項目を削る**。

### 2. 実機でしか動かない部分は、選ぶロジックと OS の呼び出しに分けて、選ぶほうだけを細かくテストする

プロセスタップと SpeechAnalyzer は、実機で音を出さないと動かない。そこで「どのプロセスをタップするか」を選ぶ純粋関数と、選んだプロセスでタップを作る部分を分けた。選ぶほうには、プロセスの一覧を偽物で渡すテストを並べた。そこで決まった規則が 3 つある。

| 場面 | 素直な実装で起きること | 決めた規則 |
| --- | --- | --- |
| Chrome を選ぶ | `hasPrefix("com.google.Chrome")` だと、`com.google.ChromeCanary.helper` まで一致する | 完全一致か、`appBundleID + "."` で始まるものだけ |
| ブラウザを選ぶ | 本体をタップしても音は来ない。音はヘルパーのプロセスから出る | 本体と `.helper`、`.helper.Renderer` を、無音のものも含めてすべて対象にする |
| 合うプロセスが 0 件 | 「全部をタップすれば何か取れる」と広げたくなる | エラーで終わる。Mac 全体のタップには切り替えない |

1 つのプロセスが複数の起動中アプリに一致するときは、最も長い bundle id のアプリに割り当てる。そうすれば、結果が起動中アプリの並び順に左右されない。

実際のタップの作成と文字起こしは、モックでテストしなかった。モックで通しても、実際の API がそう動くことの確認にはならないからだ。そちらは手順を README に書き、人の実機確認に回した。

**実機が要る処理は、判断の部分を純粋関数に切り出して細かくテストし、OS の呼び出しはモックせずに実機の確認へ回す**。

### 3. 実行ファイルの最上位に書いた配線はテストできないので、薄い関数に切り出す

最初の実装では、STT の結果をイベントにして WebSocket に流すループが `main.swift` に直接書かれていた。Swift の実行ターゲットの最上位のコードは、テストから呼べない。takt の伴走役（コンパニオン）が、ここを「テストできない経路」と指摘した。

対応は、ループを `HelperCore`（ライブラリ側）の関数に移すだけだった。

```swift
public func relay<Results: AsyncSequence>(
    _ results: Results, track: Track, to server: WebSocketServer
) async throws where Results.Element == TranscriptionResult {
    for try await result in results {
        await server.broadcast(try event(from: result, track: track).jsonString())
    }
}
```

テストは、結果の流れを直接渡し、本物の WebSocket クライアントに `partial`、`remark` の順で届くことを確かめる。STT 全体の偽物は作らなかった。確かめたい受け渡しが `relay` の内側に収まるからだ。`main.swift` が `relay` を呼んでいるかどうかだけは、自動テストの外に残る。

**テストできない場所に置いたコードは、偽物を作り込む前に、テストできる場所へ移せないかを考える**。

### 4. 観点を分けた並行レビューは、テストが通った後の「失敗の経路」を拾う

実装の工程が終わった時点で、テストは 23 件すべて通っていた。そのあと 5 つの観点（セキュリティ・コーディング・AI 生成コードの癖・アーキテクチャ・テスト）のレビューを並行で回すと、5 観点すべてが差し戻した。指摘は 9 件あり、裁定の工程がそれを 3 つの問題にまとめた。

| 問題 | どこで見つかったか | 中身 |
| --- | --- | --- |
| A | 3 観点が同じ箇所 | 音声形式の変換器を作れないと `guard let converter else { continue }` でバッファを捨て続ける。タップは動いているのに何も届かず、エラーにもならない |
| B | 2 観点 | 取得から認識までの 2 つのキューに上限がない。認識が遅れると、長い会議でメモリが増え続ける |
| C | 2 観点 | Ctrl-C のシグナルで呼ぶ `stop()` と、`start()` がロックなしで同じ資源を触る。開始の途中でシグナルが来ると、終了の要求が失われる |

どれも正常系のテストでは出てこない。問題 C は、一度 `SIG_IGN` に差し替えたシグナルを受け損なうと、Ctrl-C を押しても止まらなくなる、というところまで裁定に書かれていた。

裁定は、直さない指摘も 2 件決めた。

- **WebSocket に認証がない（セキュリティ）。** 現象は本当にある。`127.0.0.1` に束縛しても、同じ Mac の別ユーザーのプロセスはつなげる。しかし、仕様にも ADR にも「localhost の WebSocket に流す」としか書かれていない。裁定は認証を勝手に足さず、「必要以上の拡張」として別の要求に持ち越した
- **`自分` のトラックが転送で正しく届くかのテストがない（テスト）。** 指摘は「`relay` がトラックを `相手` に固定していたら」という仮定に立っていた。実際のコードはトラックを引数のまま渡している。そのため「根拠なし」として退けた

**レビューの指摘は、仕様に照らして「直す」「別の要求として持ち越す」「前提が成り立たない」に分ける**。現象が本当でも、仕様にない契約をレビューで足すと、作業の範囲が黙って広がる。

### 5. 音声のキューがあふれたら、捨てずにエラーで止める。時刻がずれるから

問題 B の直し方には、選択肢が 2 つあった。あふれた分を捨てて処理を続けるか、エラーで止めるか。リアルタイムの音声なら、古い分を捨てて追いつく案は自然に見える。

止めるほうを選んだ。SpeechAnalyzer が結果に付ける時刻は、「入力に流し込んだ音声の先頭から何秒か」で数えられる。途中でバッファを 1 つ捨てると、その後のすべての発言の時刻が、捨てた長さだけ黙って前にずれる。発言の時刻はマップのノードの根拠として残るので、ずれたまま動き続けるより、止まって気づけるほうがいい。

```swift
// 2048 個: 1 個あたり約 10 ms 前後の IO バッファを想定して約 22 秒分。通常の遅れは吸収し、処理が止まった場合だけ超える。
let (stream, continuation) = AsyncThrowingStream.makeStream(
    of: AVAudioPCMBuffer.self, throwing: Error.self, bufferingPolicy: .bufferingOldest(limit))
// …IOProc の中で
if case .dropped = continuation.yield(copy) {
    continuation.finish(throwing: ProcessTapError.backlogExceeded(limit: limit))
}
```

`AsyncStream` の `yield` には背圧（送り手を待たせる仕組み）がない。上限を決めない限り、既定のキューは無制限に溜まる。上限 2048 という値が実機の IO バッファの大きさに合っているかは、まだ測っていない。

**時刻を「入力の累積」で数える処理の前では、データを間引かない。あふれたらエラーで止める**。

### 6. テストを走らせるコマンドは 1 か所に固定する。工程が変わると、エージェントは素のコマンドに戻る

この Mac には Xcode がなく、Command Line Tools だけが入っている。その環境では、素の `swift test` が swift-testing のマクロを見つけられずに失敗する。

```text
plugin for module 'TestingMacros' not found
```

テストを書く工程のエージェントがこれに気づき、マクロのプラグインの場所を渡す引数を見つけた。実装の工程はそれを `package.json` の test スクリプトに入れ、23 件を通した。

```sh
swift test -Xswiftc -plugin-path -Xswiftc /Library/Developer/CommandLineTools/usr/lib/swift/host/plugins/testing
```

ところが、レビュー後の修正の工程は、素の `swift test` を叩いて同じエラーで失敗した。その結果、問題 C のために足した `stop()` のテストは、この作業の中では一度も実行されなかった。救いは、修正の検証の工程が、それを成功の証拠に数えなかったことだ。「テストは失敗、実行結果は得られていない」と書き、後続の確認に引き継いだ。

同じ引数の不足は、ほかにもあった。音声バッファの型（`AVAudioPCMBuffer`）がスレッド間で安全に渡せる印（`Sendable`）を持たないため、Swift 6 の言語モードではタスク間の受け渡しがエラーになる。これは `Package.swift` で言語モードを 5 にして避けた。テストを書く工程では、もう 1 つつまずきがあった。`stop()` の直後に同じポートで待ち受け直すテストが、OS の都合で不安定になった。そこで「`stop()` の後は新しい接続を受けない」という確かめ方に置き換えた。

**環境に合わせた実行コマンドは、スクリプトに 1 か所だけ書き、どの工程もそれを使うよう指示する**。工程ごとに別のエージェントが動く仕組みでは、前の工程の発見が次の工程に自動では伝わらない。

### 7. 利用上限で止まった実行は、すぐに再試行せず、止まった工程から再開する

最初の実行は 30 分ほど進み、修正の検証の工程で止まった。AI のサービス側の利用上限（rate limit）に当たったためだ。止まった直後に 2 回、再開が試みられた。だが、どちらも 5〜6 秒で同じ理由で失敗した。利用上限は、時間がたたないと解けない。

17 分ほど待ってから、止まった工程を起点に再開した。計画・テスト・実装・レビュー・修正をやり直さず、修正の検証から続けた。そこから 2 回目のレビュー（5 観点すべて承認）と最終判定まで、13 分で終わった。工程に使った時間は、合計で約 43 分だった。

工程ごとに報告書がファイルで残っているので、途中から再開しても、前の工程の判断を読み直せる。再開後の検証の工程は、前の実行の修正報告をそのまま読んでいる。

**利用上限による停止は、間を置いて、止まった工程から再開する**。すぐの再試行は、同じ失敗を重ねるだけだ。

### その後

この作業のあと、マイクを `自分` のトラックとして足す作業で、ここで決めたことのうち 2 つが変わった。

- **発言の時刻の起点。** この作業では「キャプチャ開始からの秒数」とし、SpeechAnalyzer が返す時刻をそのまま使った。トラックが 1 つならそれで足りる。しかし、`相手` と `自分` で SpeechAnalyzer を 2 本並べると、それぞれが自分の最初の入力を 0 秒として数える。そのため、同じ瞬間の発言でも時刻が揃わない。そこで、取得した音声のバッファに取得時点のホスト時刻（OS の単調な時計）を付けるようにした。そのうえで、`run` が取得を始める直前を 0 とする、2 トラック共通の秒数に補正している。5 節の「時刻は入力の累積で数えられる」という性質が、ここでも効いた
- **退けたテスト。** 4 節で「根拠なし」とされた `自分` のトラックの転送も、2 トラックを実際に流すようになった時点で、「自分と相手の結果が、トラック違いの同じ形のイベントとして 1 つの接続先に届く」というテストとして入った。指摘の前提は外れていても、確かめたい振る舞いそのものは、次の作業で必要になった

6 節で一度も実行されなかった `stop()` のテストは、いまの main で `package.json` のコマンドから流すと、ほかと合わせて 40 件すべて通る。

## 自分の声を 2 本目の音声認識で文字起こしし、2 トラックの時刻を揃えた話

Mac 上で動く Swift のヘルパー（音声を取って文字起こしし、localhost の WebSocket でイベントを流す常駐プロセス）に、**自分の声**の文字起こしを足したときの学び。それまでのヘルパーは、会議アプリの音（相手の声）だけを Apple の SpeechAnalyzer（macOS 26 からの端末内の音声認識）で文字にしていた。今回、マイクの音を 2 本目の SpeechAnalyzer に流し、2 つの**トラック**（音声の出どころ。`自分` はマイク、`相手` は会議アプリの音）の結果を、同じ形・同じ時刻の基準で流すようにした。

実装は、AI エージェントのワークフロー実行ツール（takt）が、計画 → テスト → 実装 → 複数の観点のレビュー → 修正、の順に自動で進めた。下の学びのいくつかは、その途中でレビュー役が出した指摘と、計画のやり直しから来ている。

- 決定の記録: [ヘルパー：自分の声を別トラックで文字起こしする](https://github.com/daiki-beppu/live-mindmap/issues/34)、[ADR 0002 音声取得と STT はローカルのヘルパーが行う](../adr/0002-local-stt-helper.md)
- 用語集: [`CONTEXT.md`](../../CONTEXT.md)（発言・途中結果・トラックの語彙）

前提として、次のことが決まっていた。

- ヘルパーが流すイベントは 2 種類。**途中結果**（確定前の暫定の文字列）と、**発言**（STT が確定させた 10〜15 秒程度の 1 区切り。トラック・開始と終了の秒数・本文を持つ）
- Apple のエコーキャンセル（音声処理）は使わない。同じプロセスで有効にすると、会議アプリの音を取るプロセスタップ（Core Audio の、特定のプロセスの音だけを取る仕組み）が止まるため
- スピーカーで聞くと相手の声が自分のマイクにも入る。この二重の文字起こしは、後でサーバー側が時刻と文字列の重なりで見分ける。そのため、2 トラックの `start` / `end` は同じ基準の秒数でなければならない

### 1. 認識器を 2 本にすると時刻の原点も 2 つになるので、共通の時計で先頭の差を 1 回だけ補正する

SpeechAnalyzer が返す結果の時刻は、「そのアナライザに最初に入れた音声を 0 とする秒数」で、入れたサンプル数から計算される。アナライザが 1 本なら、これがそのまま「キャプチャ開始からの秒数」になる。2 本にすると、原点が 2 つになる。プロセスタップとマイクは開始のタイミングが少しずれ、アナライザの準備が終わるまでの待ちもトラックごとに違うからだ。

計画の段階で比べた案は 3 つあった。

| 案 | 採否 | 理由 |
| --- | --- | --- |
| 音声の取得側がバッファに取得時のホスト時刻（Mac の単調な時計）を付け、`run` で 1 回だけ取った基準時刻との差を、結果の時刻に足す | 採用 | 差を足す計算は純粋関数になり、テストできる |
| SpeechAnalyzer の入力に、バッファの開始時刻を渡す API（`AnalyzerInput(buffer:bufferStartTime:)`）を使う | 不採用 | API はあるが、渡した値が結果の時刻にどう反映されるかは、実機でないと確かめられない |
| 補正しない（同時に始めるので差は小さいとみなす） | 不採用 | 準備の待ちがトラックごとに違い、ずれが残る |

採った方式は、次の形になった。

```swift
// main.swift: 2 トラック共通の基準。音声取得を始める直前に 1 回だけ取る
let origin = AudioGetCurrentHostTime()
let theirResults = try await theirTranscriber.transcribe(tap.start(), origin: origin)
let myResults = try await myTranscriber.transcribe(microphone.start(), origin: origin)
```

各トラックは、最初に届いたバッファの取得時刻と `origin` の差を 1 回だけ記録し、以後のすべての結果の `start` と `end` に同じ量を足す。トラックの中の時刻は、これまでどおり SpeechAnalyzer のサンプル数から出る値を使う。補正するのは先頭の差だけで、60 分の間に生じるデバイスのクロックのずれは補正しない（要求にないため）。

テストでは、取得の開始が相手 0.5 秒・自分 1.2 秒とずれた 2 トラックに、共通の基準で 3.0〜4.0 秒にあたる発言を流した。アナライザから見ると、相手は 2.5〜3.5 秒、自分は 1.8〜2.8 秒になる。補正後はどちらも 3.0〜4.0 秒になることを確かめている。

**音声認識を並べるときは、結果の時刻が何を原点にしているかを先に確かめ、共通の時計への変換を 1 か所に置く**。

### 2. 時刻は「読み出した時点」ではなく「取得した時点」のタイムスタンプから取る

補正量を決める「最初のバッファの時刻」には、2 通りの取り方がある。バッファを読み出したときに時計を見るか、取得したときに付いたタイムスタンプを使うかだ。

ヘルパーでは、取得したバッファはいったん上限 2048 個のキューにためてから、文字起こしの側が読み出す。プロセスタップは `transcribe` を呼ぶ前に動き始めるので、最初の数個のバッファは、読み出されるまでキューで待つ。読み出した時刻を使うと、その待ちの分だけ基準がずれる。

そこで、取得のコールバックが受け取るタイムスタンプを使った。

- プロセスタップ: IOProc の第 3 引数 `inInputTime` の `mHostTime`（`mFlags` に `hostTimeValid` があるとき）
- マイク（AVAudioEngine）: `installTap` のブロックが受け取る `AVAudioTime` の `hostTime`（`isHostTimeValid` のとき）

どちらも有効でないときだけ、その場で `AudioGetCurrentHostTime()` を使う。2 つの出どころは同じホスト時刻の時計なので、そのまま比べられる。

**バッファをためて後で処理する経路では、時刻を処理の側で取らず、取得のコールバックで付けて運ぶ**。

### 3. 並行タスクの「最初のエラーで全体を止める」は、`waitForAll()` では書けない

2 トラックの結果は、Swift の `withThrowingTaskGroup` で並行して WebSocket に流す。決めた振る舞いは次の 2 つだった。

- どちらかのトラックがエラーで終わったら、そのエラーを返し、もう一方も止める
- 片方が正常に終わっても、もう一方は止めない

最初の実装は、グループの最後で `try await group.waitForAll()` を呼んでいた。すると、「一方がエラーで終わり、もう一方は終わらない流れ」を渡すテスト 2 件が、どちらも 60 秒のタイムアウトで失敗した。`waitForAll()` は、子のタスクが投げたエラーを受け取ってもグループをキャンセルせず、残りのタスクが終わるまで待つ。会議の音声のように終わらない流れが残っていると、エラーが起きても戻らない。

グループの結果を 1 つずつ受け取る形に直すと、通った。

```swift
try await withThrowingTaskGroup(of: Void.self) { group in
    for (track, results) in tracks {
        group.addTask { try await relay(results, track: track, to: server) }
    }
    // 最初のエラーで抜ける。グループを抜けるときに、残りのタスクはキャンセルされる
    for try await _ in group {}
}
```

テストでは、終わらない側の流れの `onTermination` が呼ばれることまで見ている。キャンセルが伝わって、マイクやプロセスタップの読み出しが本当に止まることの確認になる。

**終わらない流れを並行に扱うときは、「片方が失敗したらもう片方は止まるか」を、終わらない偽の流れでテストする**。

### 4. 規則を確かめていないテストは、規則を private から出して型にすれば書ける

1 の補正には、「補正量は最初のバッファで 1 回だけ決め、2 本目以降で上書きしない」「記録した補正量をすべての結果に足す」という規則がある。最初の実装では、この規則が文字起こしクラスの中の `private` な小さな型と、2 か所の呼び出しに分かれていた。テストは、秒数を出す関数と、時刻をずらす関数に、手で計算した値を渡しているだけだった。

テストを担当するレビュー役が、ここを指摘した。

> 共通時刻のテストは同じ `offsetSeconds` 呼び出しを 2 回比較するだけです。（中略）既存テストはその補正を外しても成功します。

実装役は最初、規則のテストには SpeechAnalyzer を差し替える層の新設が要るとして、テストを純粋関数の組み合わせに書き換えるところで止めた。その後の再計画で、この想定が崩れた。SpeechAnalyzer に依存しているのは結果の流れの元だけで、補正の規則そのものは SpeechAnalyzer がなくても成り立つ。テストできなかった本当の理由は、規則が `private` の中に散らばっていたことだった。

規則を `internal` の型 `TrackTimeline`（`record` で最初の 1 回だけ記録し、`align` で結果をずらす）にまとめ、テストを `@testable import` にした。足したテストは、それぞれ 1 つの誤実装を落とすように選んだ。

| テスト | 落とす誤実装 |
| --- | --- |
| 0.5 秒後のバッファを記録し、2.5〜3.5 秒の結果をずらすと 3.0〜4.0 秒になる | 補正量を結果に足さない |
| 0.5 秒後の次に 0.9 秒後のバッファを記録しても、結果は 3.0〜4.0 秒のまま | 2 本目以降で上書きする（3.4 秒になる） |
| 相手 0.5 秒・自分 1.2 秒の 2 トラックで、同じ瞬間の発言が両方 3.0〜4.0 秒になる | 2 トラックで補正量を共用する |

その後のアーキテクチャのレビューで、秒数を出す関数と時刻をずらす関数に `public` が付いたままだと指摘され、`internal` に戻した。テストは `@testable` で内部の型を呼べるので、公開する必要はなかった。

**「外部への依存があるからテストできない」と判断する前に、確かめたい規則が依存の外で成り立つかを見る。成り立つなら、規則を内部の型に切り出して、公開せずにテストする**。

### 5. 文字列で比較するテストが揺れたら、出力の順序を固定する

イベントは JSON の文字列にして WebSocket に流し、テストは受け取った文字列を期待値と比べている。2 トラックのテストを足したところ、`JSONEncoder` の出力のキーの並びが呼び出しごとに変わり、テストがときどき落ちた。既存のテストの 1 件も、同じ理由で潜在的に不安定だった。

テスト側で JSON を解析して比べる案もあったが、エンコーダに `.sortedKeys` を指定した。キーと値は変わらず、並びだけが決まる。変更後、テストを 3 回続けて流し、38 件すべてが通ることを確かめた。

あわせて、2 トラックの到着順そのものは決まらないので、テストでは「全体の集合が一致すること」と「同じトラックの中の順序が保たれること」を分けて確かめている。

**並行に届くものを比べるテストは、決まらない順序（キーの並び、トラック間の到着順）を、出力の側で固定するか、比較の側で無視するかを、1 つずつ決める**。

### 6. localhost の WebSocket でも、ブラウザの別のサイトからは接続できる

セキュリティのレビュー役は、マイクの文字起こしが流れる WebSocket が、接続元（`Origin`）を確かめていないことを指摘した。待ち受けは `127.0.0.1` に限っているが、それはネットワークの外からの接続を防ぐだけで、利用者のブラウザで開いた別のサイトのページは `ws://127.0.0.1:8765` につなげる。ヘルパーが動いている間、そのページは利用者の発言を受け取れることになる。

自分の声を足したことで、流れる内容は「会議アプリの音」から「マイクに入ったすべての音」に広がった。それでも、今回の修正では扱わず、範囲外とした。接続を受ける部分は今回の変更の対象外のファイルにあり、許可する `Origin` や認証の方式は、まだつないでいないサーバー側の設計と一緒に決める必要があるためだ。この判断は、レビューの裁定として記録に残した。

**localhost で待ち受けるサーバーは「外から届かない」と思いがちだが、ブラウザからは届く。流す内容が広がる変更のときに、接続元の確認があるかを見直す**。

### 7. 自動で確かめられない前提は、人が実機で確かめる手順として残す

今回のテストは、偽の結果の流れと、手で作ったホスト時刻で通している。次のことは、単体テストでは確かめられない。

- 会議アプリの音とマイクを同時に流したとき、2 トラックの発言が実際に届くこと
- SpeechAnalyzer の結果の時刻が「最初に入れた音声を 0 とする秒数」であるという、1 の方式の前提
- 2 本の SpeechAnalyzer を 60 分同時に動かしても止まらないこと、そのときの CPU の負荷

ワークフローの中では実行できないので、ヘルパーの README に手順として書いた。2 つ目の前提は、「2 トラックの近い時刻の発言が、近い `start` / `end` になること」を見ることで確かめる。CPU は、次のコマンドで 1 分ごとに記録する。

```sh
top -pid $(pgrep -f live-mindmap-helper | head -1) -l 0 -s 60 -stats pid,cpu,mem | tee helper-cpu.log
```

自動の実装では、こうした項目は「確認済み」ではなく「環境のため未実証」として報告させ、どの確認で補うかを一緒に書かせた。テストが全部通っても、マイクから `自分` として流れる配線の誤りは検出できない、と報告に明記されている。

**自動で確かめられない受け入れ条件は、確かめ方（見る値とコマンド）まで書いた手順にして、人に渡す**。

## サーバーが落ちても、ログを流し直して直前のマインドマップに戻す機能を作った話

**ログからの復元**を作ったときの学び。ログからの復元とは、サーバーが落ちて再起動したときに、ログに残ったイベントを順に流し直し、落ちる直前のマップに戻すことをいう。LLM は呼び直さない。実装は、AI エージェントのワークフロー実行ツール takt に任せた。takt は計画・テスト作成・実装・複数観点のレビュー・指摘の採否判断・修正を順に回し、途中経過をレポートのファイルに残す。このエントリは、そのレポートと差分を読み直して書いた。

- 決定の記録: [ログからの復元](https://github.com/daiki-beppu/live-mindmap/issues/40)、[ADR 0003 ローカルの Node サーバーがパイプラインを持つ](../adr/0003-local-node-server-owns-pipeline.md)
- 用語集: [`CONTEXT.md`](../../CONTEXT.md)（発言・差分操作・セッションの語彙）

前提として、次のものがすでにあった。

- マップは会議をルートとする木。AI は毎回作り直さず、既存のマップへの**差分操作**（追加・更新・統合・移動・削除・何もしない）を返す
- **セッション**（1 つの会議を追う一続きの作業）は、イベントをログ（JSONL）に追記する。イベントは 2 種類で、`remark`（**発言**＝STT が確定させた 10〜15 秒程度の文字起こしの 1 区切りを受け取った）と `diff`（差分更新の入力の要約・返ってきた操作・捨てた操作・エラー）
- 差分操作を検証して適用する純粋関数 `applyOps` が、新しいノードに `n1`、`n2`… と ID を振る
- 受入条件は 4 つ。「再起動時にログのイベントを順に適用関数へ流してマップを戻す」「復元では LLM を呼ばない」「知らない種類のイベントは読み飛ばせる」「復元したマップが元と一致する（ノードの ID を含む）」

### 1. 復元に要る情報がログに全部あるかを、書く前に棚卸しする

計画の段階で、受入条件の「元のマップと一致する」を、一致させるべき項目に分解した。ノードの ID・親・種別・本文・根拠・状態に加えて、**ルートの本文**（会議のタイトル）も一致しなければならない。ところが、既存のログにタイトルは無かった。タイトルは文字起こしのファイル名から作っていて、ログにもどこにも残っていなかった。

候補は 3 つあった。

| 案 | 採否 | 理由 |
| --- | --- | --- |
| セッションの開始時に `{ type: "start", title }` を最初のイベントとして書く | 採用 | ログだけで戻せる |
| タイトルを書き出し済みの `export.json` から読む | 不採用 | ログだけからの復元にならない |
| ルートの本文を空文字で補う | 不採用 | 元と一致しない |

`start` が無いログはエラーにした。ルートの本文を推測で埋めると、一致しないマップが黙って出来上がる。

一方、ノードの ID はログに書き足さなくても戻せた。`applyOps` の採番は、初期のマップ・操作の列・処理済みの発言の集合が同じなら同じ ID になる。ID を保存するより、採番が決定的であることを確かめるほうが安い。

**イベントソーシング（状態を、起きたことの記録から組み立て直す方式）で復元を作るときは、最初に「一致させるべき項目」を並べ、それぞれがログから導けるかを確かめる**。抜けは、ログの形を決めた時点では気づきにくい。

### 2. 復元では記録された結果を信用せず、元と同じ順で適用関数を通し直す

ログの `diff` には、捨てた操作とその理由まで残っている。これを使えば、適用関数を通さずに結果を組み立てられそうに見える。しかし受入条件は「適用関数へ流す」と言っており、近道は採らなかった。

注意が要ったのは、適用関数が見る「処理済みの発言の集合」だ。根拠の検証（根拠に指定できるのは差分更新に渡した発言だけ）と採番は、この集合に左右される。元のセッションは、差分更新を**呼ぶ前に**渡す発言を集合に加えていた。呼び出しが失敗した回も加わっている。復元でも、`error` 付きの `diff` を含めて、同じ順で加えてから `applyOps` を呼ぶ。

```ts
case "diff": {
  if (!map) throw new Error("ログの diff より前に start がありません");
  for (const id of e.input.fresh) {
    const r = remarks.find((x) => x.id === id);
    if (!r) throw new Error(`ログに発言がありません: ${id}`);
    known.add(id);
    processed.push(r);
  }
  map = applyOps(map, e.ops, known).map;
  break;
}
```

テストの元になるセッションには、すべての種類の操作・捨てられる操作・差分更新の失敗・重複の印（スピーカーの音を自分のマイクが二重に拾った発言に付ける印）の付いた発言を、わざと起こさせた。そのうえで、ログを JSON に書いて読み直した形で復元し、`snapshot()`（その時点のマップ全体）を `toEqual` で比べる。実装の `known.add` を消すと、復元のテストが 4 本落ちることも確かめた。

**ログから状態を戻すときは、記録された結果ではなく、適用関数が見ていた入力を元と同じ順で組み立て直す**。失敗した回の副作用も、入力の一部になる。

### 3. 復元の結果は「止まったマップ」ではなく、続きを受け取れるセッションで返す

マップだけを戻せば、受入条件は満たせる。しかし、再起動の後も会議は続く。そこで、既存の `createSession` を、開始のイベントを書く部分と、状態を受け取ってセッションを組み立てる `openSession` に分けた。`restoreSession` はログから状態を組み立てて、同じ `openSession` に渡す。

戻す状態はマップだけではない。

- 受け取ったすべての発言（重複の印つきも含む）
- 差分更新に渡した発言（直前の発言として、最後の 3 つを次の呼び出しに渡すため）
- まだ渡していない発言（重複の印がなく、どの `diff` の入力にも含まれない発言）

最後のものの扱いが分かれ目だった。復元の終わりにすぐ差分更新を呼ぶと「復元では LLM を呼ばない」に反する。捨てると、会議の最後の発言を取りこぼす。たまった発言として戻しておき、次の発言が来たときに一緒に流すことにした。

テストでは、元のセッションをそのまま続けた場合と、途中で落として復元してから続けた場合で、次の差分更新に渡る入力（直前の発言・新しい発言・マップ）が `toEqual` で一致することを確かめた。

**復元の正しさは、戻した状態の見た目ではなく、「落ちなかった場合と同じ次の一手になるか」で確かめる**。

### 4. 読み飛ばすのは「読めて、種類を知らない行」だけにし、壊れた行では止める

「知らない種類のイベントを読み飛ばせる」は、後でイベントの種類を足すための条件だ。これを「読めないものは全部飛ばす」と広げると、ログの欠けに気づかないまま違うマップが出来上がる。

そこで、2 つを分けた。

- JSON として読めて、`type` が知らない値の行 → 読み飛ばす
- JSON として読めない行 → `log.jsonl の 2 行目が JSON として読めません` のように、行番号付きのエラーにする

読み飛ばしのテストには、知っている種類のフィールド名を持つ未知のイベントも混ぜた。`{ type: "future", remark: {…}, ops: [{ op: "delete", … }] }` のような行だ。`remark` や `ops` という欄があるかで解釈する実装なら、これを誤って適用してしまう。判別は `type` だけで行う。

**前方互換のための読み飛ばしは「種類を知らない」に限り、「形が壊れている」とは区別する**。

### 5. 生成の途中でイベントを書くようにすると、コールバックが戻り値より先に呼ばれる

`createSession` が開始のイベントを書くようにすると、既存の CLI が壊れることを、計画の段階で見つけていた。CLI はログのコールバックの中で、作ったセッションを参照してエクスポートを書き出していた。

```ts
// 変更前の CLI（要点だけ抜き出したもの）
const session = createSession({
  title, updater,
  log: (event) => {
    appendFileSync(logPath, JSON.stringify(event) + "\n");
    writeFileSync(exportPath, JSON.stringify(session.exportJson())); // start の時点では session がまだ無い
  },
});
```

`start` は `createSession` の中で書かれるので、`session` に代入される前にコールバックが走る。ログへの追記は常に行い、エクスポートの書き出しは代入の後だけにした。

**ファクトリの中でコールバックを呼ぶようにしたら、呼び出し側のコールバックが戻り値を参照していないかを確かめる**。外から見える関数の形は変わらないので、型チェックでは気づけない。

### 6. 理由を指定しない「例外が出ること」のテストは、実装が無くても通る

テストを先に書いた段階で、新しいテストのうち 10 本が想定どおり落ち、18 本が通った。通ったものの中に、「`start` が無いログはエラーにする」のテストがあった。

```ts
expect(() => restoreSession(withoutStart, options)).toThrow();
```

このとき `restoreSession` はまだ存在せず、呼ぶと `TypeError`（関数ではない）が出る。`toThrow()` は理由を問わないので、それで通っていた。テストを書いた側がこれを申し送り、実装の後に、意図したエラー文で例外が出ることをコードで確かめた。ほかのテストも、実装を 1 か所壊して落ちることを確かめている。

| 壊した箇所 | 結果 |
| --- | --- |
| 復元で処理済みの発言を集合に加える `known.add` を消す | 復元のテストが 4 本落ちる |
| 最新のセッションを選ぶ `.at(-1)` を `.at(0)`（最古）にする | 複数セッションのテストが落ちる |

**赤を経ずに緑になったテストは、何が投げられて通ったのかを確かめる**。例外のテストは、エラー文か型まで指定しておくと、この取り違えが起きない。

### 7. レビューの指摘は、守る契約が受入条件から来ているかで採否を分ける

実装の後、アーキテクチャ・テスト・コーディング・AI 特有の書き癖の 4 観点で、並行してレビューさせた。差し戻しは 2 件あった。

| 指摘 | 採否 | 理由 |
| --- | --- | --- |
| ログを持つ最新のセッションを選ぶ処理に、セッションが複数あるときのテストが無い | 採用 | 「進行中だったセッションのログを読む」という受入条件そのもの。今回、選ぶ処理を `export` と共用の関数に抜き出したことで生まれた、まだ誰も確かめていない契約だった |
| ログ全体を一度に読み込んでいる。長い会議でメモリを超えうるので、1 行ずつ流すべき | 不採用 | 復元したセッションは、エクスポートのためにすべての発言を持ち続ける。読み込みを 1 行ずつにしても、全体を持つことは避けられない。受入条件にもない |

1 件目は、テストだけを足して直した。新旧 2 つのセッションを作って新しい方が選ばれることと、ログの無い、より新しいフォルダがあっても飛ばされることを確かめる 2 本だ。

2 件目の指摘は、事実としては正しい。しかし採用すると、元の要求に無い「ログがメモリを超えても復元できる」という契約を新しく背負うことになる。

**「直すべきか」は指摘の正しさではなく、守ろうとしている契約がどこから来たかで決める**。共通の関数に抜き出したときは、呼び出し元ごとの契約が、それぞれテストされているかを見直す。

### 8. エージェントのワークフローは、途中経過をファイルに残しておくと、止まっても続きから回せる

最初の実行は、計画から修正まで進んだところで、使っていたコーディングエージェントの利用上限に当たって止まった。直後に 2 回再実行したが、どちらも 5 秒ほどで同じ理由で止まった。上限が戻るまで約 30 分待ち、修正の検証から再開した。

| 実行 | 時間 | 進んだところ |
| --- | --- | --- |
| 1 回目 | 約 29 分 | 計画 → テスト作成 → 実装 → レビュー 4 観点（ここだけで約 15 分）→ 指摘の採否 → 修正 → 修正の検証で停止 |
| 2・3 回目 | 各約 5 秒 | 利用上限のまま、すぐ停止 |
| 4 回目 | 約 9 分 | 修正の検証 → レビュー 5 観点（セキュリティを追加）→ 指摘の採否 → 最終確認で完了 |

再開できたのは、各段の結果（計画・テストの対応表・決定の記録・レビュー・採否）がレポートのファイルとして残っていて、次の段がそれを入力に読むからだ。止まって失ったのは待ち時間だけで、やり直した段はなかった。このエントリの「判断が変わった瞬間」も、すべてこのレポートから拾えた。

**エージェントに長い手順を任せるときは、段ごとの結果を会話ではなくファイルに残させる**。利用上限で止まったときは、すぐに再実行せず、上限が戻るのを待ってから続きを回す。

## 会議のマップを md・json・Drawnix に書き出す処理を、AI エージェントのワークフローに実装させた話

**エクスポート**を実装したときの学び。エクスポートとは、その時点のマップを、人とエージェントが使える形でセッションの外へ書き出すことをいう。何をどの形式で出すかは、[前のエントリ](#export-formats)で決めてあった。今回は、その決定どおりに作ったときに分かったことを書く。決定どおりにはいかなかった点や、決定には書かれていなかった点、はまりどころが中心になる。実装は、AI エージェントのワークフロー実行ツール takt に任せた。takt は、計画 → テストを書く → 実装 → 観点別のレビュー → 指摘の裁定 → 修正 → 再レビュー → 最終確認、という手順でエージェントを順に動かす。手順は全部で 16 段になった。途中で利用上限に当たって約 45 分止まり、再開してから完了した。

- 決定の記録: [エクスポート（md・json・drawnix）](https://github.com/daiki-beppu/live-mindmap/issues/41)、[エクスポート：会議の後に何をどの形式で取り出すか](https://github.com/daiki-beppu/live-mindmap/issues/23)
- 用語集: [`CONTEXT.md`](../../CONTEXT.md)（ノードの種別・根拠・セッション・再生の語彙）
- 形式を決めたときのエントリ: [会議のマインドマップを会議の後に何の形で取り出すか決めた話](#export-formats)

前提として、次のことが決まっていた。

- 出力は、人が読む `map.md`、エージェントが加工する `map.json`、Drawnix（ブラウザで動くホワイトボード・マインドマップのツール）で開いて直す `map.drawnix`、マップの画像 `map.png` の 4 つ。すべて同じスナップショット（その時点のマップ全体）から作る。今回の範囲は画像を除く 3 つ
- **セッション**（1 つの会議を追う一続きの作業）の終了時には、ログと同じフォルダに自動で書き出す。会議の途中の `export` は、ファイルにせず標準出力に出す
- `map.md` の根拠（ノードの元になった発言への参照）は、会議の中の時刻だけで示す。却下した案は取り消し線で元の位置に残す
- 同じ時間帯に、ブラウザの表示・ログからの復元・回帰評価も、別のエージェントが並行して実装していた

### 1. 「同じスナップショットから作る」は、スナップショットを 1 回だけ取る書き出し口を 1 つ置いて守る

「4 つの出力はすべて同じスナップショットから作る」は、形式ごとに書き出し関数を作ると簡単に崩れる。形式ごとにセッションからマップを取り直すと、その間に差分更新が入ったとき、md と json の中身が食い違う。

実装では、書き出しの入口を 1 つの関数にまとめた。スナップショットを 1 回だけ取り、3 形式すべてに同じ値を渡す。

```ts
// セッション終了時の書き出し。スナップショットは 1 回だけ取り、3 形式に同じものを渡す。
export function writeSessionExports(dir: string, exp: JsonExport): string[] {
  return Object.entries(exportFiles(exp)).map(([name, content]) => {
    const path = join(dir, name);
    writeFileSync(path, content.endsWith("\n") ? content : content + "\n");
    return path;
  });
}
```

形式への変換（`exportFiles`）は Node に依存しない中核に置き、ファイルに書くのは CLI の側だけにした。中核に `node:*` の import が無いことは、中核だけを対象にした型チェックで確かめている。

この 1 か所にまとめる形は、後から別の理由でも効いた。受入条件には「再生・ライブの**両方**の終了時に書き出す」とあった。しかし、ライブのセッションはまだ作られていなかった（後続のチケットの範囲）。最初のレビューでは、4 観点のうち 3 観点がライブ側が無いことを、そのうち 2 観点は画像が無いことも、差し戻しの理由に挙げた。裁定の段はこれらを範囲外と判断し、人も「ライブと画像は後続のチケットで作る。そのとき同じスナップショットから出力を足せるよう、書き出しの入口は 1 か所にしておく」と範囲を補足した。ライブの終了処理は、後でこの関数を呼ぶだけでよい。

**「全部を同じ元から作る」という決定は、元を取る場所を 1 つの関数に閉じ込めて守る**。まだ無い呼び出し元があっても、入口が 1 つなら後から足せる。

### 2. 「時刻だけ付ける」と決めても、根拠が複数あるときと 1 時間を超えるときの表記は、実装で初めて決まる

形式を決めたときは「ノードごとに会議の中の時刻を付ける（例：`（12:34）`）」と決めた。実装に入ると、決めていない場合が 2 つ出てきた。

- 根拠の発言が複数あるノードは、どの時刻を出すか
- 会議が 1 時間を超えたとき、`1:01:40` と書くか、`61:40` と書くか

前者は「最も早い発言の開始時刻」にした。ノードの話が最初に出た時刻なので、録音をたどる起点になる。後者は分を 60 以上のまま出し、`61:40` とした。書式が 1 種類で済み、並べたときに桁が揃う。

ほかにも、決めていなかった細部をテストで固定した。項目の無い一覧は見出しだけにせず `- なし` と書く。TODO の担当者と期限は、あるものだけを出す。冒頭の決定の一覧は、どの論点への決定かが分かるよう `面接は何回か → 2 回にする` の形にする。テストは、全部の状態を含むマップを 1 つ組み、`map.md` の全文と一致するかを見た。根拠が 3725 秒と 3700 秒の 2 つある TODO が `（61:40）` になる行も、その中に入れた。

```text
## TODO
- 求人票を直す（担当：佐藤・期限：来週）（00:28）
- 日程を決める（61:40）
```

**「時刻を付ける」「件数を出す」のような表記の決定は、値が複数あるとき・空のとき・桁が上がるときの 3 つを、実装の前に決めておく**。決めていなければ、全文一致のテストに入れて、実装の判断を見える形で残す。

### 3. 「同じ内容」を文字列で比べるなら、末尾の改行を足す場所を 1 か所に決める

テストを書く段のエージェントは、次の 2 つのテストを書いた。

- `map.json` のファイルの中身は、直後の `export --format json` の標準出力と文字列で一致する（標準出力は末尾に改行が付く）
- 中核の `exportFiles` が返す `map.json` の文字列は、`JSON.stringify` の結果そのもの（末尾に改行が無い）

どちらも単独では正しい。しかし、同じものを片方は改行あり、片方は改行なしで求めている。実装の段のエージェントは、ファイルに書く直前に「末尾に改行が無ければ足す」ことで両立させた（1 節のコードの `content.endsWith("\n")`）。

これで動くが、改行を付ける場所が、標準出力の側とファイルの側の 2 か所に分かれた。後で 3 か所目の出力を足すときにも、同じ判断をもう一度することになる。

**出力どうしを文字列一致で比べる契約を置くなら、末尾の改行を付ける層を 1 つに決めてから書く**。中身を作る関数は改行を付けず、ファイルや標準出力に書く層で付ける、のように揃える。

### 4. 「途中で」の契約は、途中で止めた状態を作ってテストする

`export` は会議の途中に呼ばれる。CLI の再生は、ログを書くたびに `export.json` へ最新のマップを書いておき、別のプロセスの `export` がそれを読む。最初のテストは、どれも再生が終わってから `export` を呼んでいた。

テストのレビューが、これを差し戻した。再生の終わった後は、`export.json` と終了時に書く `map.*` の中身が一致する。そのため、`export` が誤って `map.md` を読むように変わっても、完了後のテストでは気づけない。

直したテストは、2 回目の差分更新の中で処理を止め、その間に `export` を呼ぶ。止めるのに固定の待ち時間は使わず、Promise を 2 つ使った。1 つは止まった所に着いたことを知らせ、もう 1 つは止まった処理を再開させる。

```ts
let reachedSecond!: () => void;
const secondCallReached = new Promise<void>((resolve) => (reachedSecond = resolve));
let release!: () => void;
const released = new Promise<void>((resolve) => (release = resolve));
const updater = async () => {
  const ops = script[calls++] ?? [];
  if (calls === 2) {
    reachedSecond();
    await released; // 2 回目の更新が終わらない、進行中の状態で止める
  }
  return { ops };
};
const playing = runCli(["play", fixture], { updater, sessionsDir, ... });
await secondCallReached;
// ここで export を呼ぶ。論点は（未決）のままで、「→ 決定」はまだ出ない
release();
await playing;
```

止めている間に見るのは 3 つ。Markdown に `面接は何回か（未決）` があって `→ 決定` が無いこと、JSON の論点の子が空であること、フォルダのファイルが `export.json` と `log.jsonl` の 2 つのまま増えないことだ。`map.md` を読む実装にすると、この時点ではまだファイルが無いので落ちる。

**「途中でも」「完了する前に」という契約は、完了後の状態では区別がつかない。処理を止める口を差し替え口に作り、その状態でテストする**。

### 5. 読み込みの検査を通ることと、ツールで描けることは別

形式を決めたときに Drawnix のソースを読み、ファイルを開くときに確かめられるのは `type` が `"drawnix"`・`elements` が配列・`viewport` がオブジェクトの 3 点だけだと分かっていた。受入条件のテストも、この 3 点と木の形を見る。

しかし、この 3 点は開けるかどうかの検査で、マインドマップとして描けるかは別の話だった。計画の段のエージェントは、描画を担うライブラリ（Plait）のソースまで読んだ。そして、次の形に合わせる必要があると判断した。

- ルートの要素は `type: "mindmap"` で、置く位置の `points` と、枝を伸ばす向きの `layout` を持つ
- 子の要素は `mindmap` ではなく `type: "mind_child"`
- 本文は `data.topic.children[0].text` に入れる

3 点の検査だけを満たすなら、子の型が違っていても、テストは通ってファイルも開ける。描けるかどうかは、実際に drawnix.com で開くまで分からない。この確認は人の手作業として受入条件に残したが、自動でマージされたときにはまだ済んでいなかった（人の作業が閉じた issue に取り残される話は、[回帰評価のエントリ](#regression-eval-recall)の 7 節を参照）。

**ファイルの形式を自前で組むときは、読み込みの検査と描画が要求する形を分けて調べる**。自動テストで確かめられるのは前者だけなので、後者は実物で開く手順として残す。

### 6. 並行の作業が使っている出力の形を変えると、マージで壊れる

再生のコマンド `play` は、終わるとセッションのフォルダのパスを 1 行だけ標準出力に出していた。今回、受入条件に従って、書き出した 3 ファイルのパスを 1 行ずつ出す形に変えた。

```text
変更前: <セッションのフォルダ>
変更後: <セッションのフォルダ>/map.md
        <セッションのフォルダ>/map.json
        <セッションのフォルダ>/map.drawnix
```

エージェントが作業している間に、ブラウザへの配信・ログからの復元・回帰評価の 3 つが先に main に入っていた。どれも、テストで `play` の出力をそのままセッションのフォルダとして使っていた。takt の作業ブランチは古い main から切られていたので、レビューも最終確認も通った。マージの前に main を取り込むと、CLI 本体とそのテストのファイルが衝突した。衝突を解いたうえで、3 か所のテストを「1 行目のパスの親フォルダを使う」形に直した。

```ts
const dir = dirname(out.join("").split("\n")[0]!); // play は書き出したファイルのパスを出す
```

CLI の標準出力は、エージェントが Bash から読む前提の出力なので、テストや別の機能も同じように頼る。並行するチケットのどれかが形を変えると、残りはマージのときに初めて気づく。

**並行して作業させるときは、CLI の標準出力のような「みんなが読む出力」の形を変えるチケットを、先に入れるか単独で回す**。出力を読む処理を 1 つの関数にまとめておけば、直す場所も 1 か所で済む。

### 7. エージェントに渡すのはそのチケットだけなので、別のチケットに書かれた共有の値は見えない

Drawnix の要素には、表示と揃えた種別の色を付ける決まりだった。ところが計画の段のエージェントは、「表示はまだ作られていない」と判断した。作業ブランチの起点の main には表示が無かったからだ。表示は、この作業の途中で main に入っていた。

エージェントが参照できたのは、自分のチケットと過去の開発ログだけだった。過去の開発ログから読み取れた「議題 青・論点 黄・課題 赤・案 紫・決定 緑」の 5 色はそのまま使った。しかし TODO の色はどこにも書かれていなかったので、自分で橙を選んだ。TODO を青緑と決めていたのは、表示のチケットの本文だった。

| 種別 | 表示（ブラウザ） | `map.drawnix` |
| --- | --- | --- |
| 議題・論点・課題・案・決定 | 同じ 5 色 | 同じ 5 色 |
| TODO | `#14b8a6`（青緑） | `#f97316`（橙） |

このエントリを書いた時点でも、main の 2 つの色の表は別々に定義されていて、TODO の色は食い違ったままだ。エージェントは「表示との一致は、表示を作るときに確かめる」と未確認の項目に書き残していた。しかし、表示のほうが先に入ったので、確かめる場面が来なかった。

**複数のチケットで使う値（色・ラベル・ファイル名）は、どちらかのチケットの本文ではなく、コードの 1 か所に置いて両方から参照させる**。エージェントは自分のチケットの外を読まないので、「別のチケットで決まっている」は伝わらない。

## LLM が組み立てたマップを、正解の決定・TODO と時刻で突き合わせて採点した話

プロンプトやモデルを変えたときにマップの出来が良くなったか悪くなったかを比べる**回帰評価**の仕組みを作ったときの学び。作ったのは、録音サンプルを流し直した結果を読んで、ノード数・深さ・種別ごとの数と、人が書いた正解の決定・TODO に対する再現率を、1 ラン 1 行の表で出す CLI のコマンドだ。実装は、AI エージェントのワークフロー実行ツール takt が、計画・テスト作成・実装・4 観点のレビュー・修正までを約 25 分で自動で回した。

- 決定の記録: [回帰評価](https://github.com/daiki-beppu/live-mindmap/issues/44)、[ADR 0003 ローカルの Node サーバーがパイプラインを持つ](../adr/0003-local-node-server-owns-pipeline.md)
- 用語集: [`CONTEXT.md`](../../CONTEXT.md)
- 評価に使う録音サンプルを選んだ話: [会議 AI の回帰評価用に、公開会議の音声サンプルを 1 時間で揃えた話](./2026-09-30.md#meeting-samples-for-regression)

前提として、次のものが揃っていた。

- **再生**: 録音済みの会議の文字起こしを、発言の流れとして待ち時間なしで流し直す CLI の `play`。終わるとセッションのフォルダにその時点のマップ（JSON）を書き出す
- マップの**ノード**は議題・論点・案・決定・課題・TODO の 6 種別のどれかで、**根拠**として元になった**発言**（STT が確定させた文字起こしの 1 区切り）を 1 つ以上持つ。発言は会議の中の開始・終了の秒を持つ
- 録音サンプルは、収束型と発散型の公開会議 2 本（各 60 分）。第三者の著作物なので、リポジトリの外に置く

### 1. 正解との照合は、本文ではなく「種別 + 時刻の区間」で行う

再現率を出すには、AI が作ったノードと人が書いた正解を対応付ける規則が要る。候補は 3 つあった。

| 照合の方法 | 採否 | 理由 |
| --- | --- | --- |
| 本文の類似度 | 不採用 | 日本語の言い回しはランごとに変わる。同じ決定でも、ランが変われば別の言葉で書かれる |
| LLM に判定させる | 不採用 | 判定そのものがぶれ、評価のたびに費用がかかる。評価の物差しが評価対象と同じくらい揺れる |
| 同じ種別のノードの根拠の発言が、正解の時刻の区間と重なるか | 採用 | 同じ入力からは必ず同じ結果が出る |

正解のファイルは、種別名をキーにした JSON にした。

```text
{ "決定": [{ text, from, to }], "TODO": [{ text, from, to }] }
```

`from` / `to` は会議の中の秒で、発言の開始・終了と同じ単位にした。変換せずにそのまま比べられる。`text` は人が読み返すための欄で、照合には使わない。判定は「同じ種別のノードの根拠のどれか 1 つが区間と重なれば再現できた」で、端が接するのも重なりとして数える（`r.start <= to && r.end >= from`）。

**採点を毎回同じにしたいなら、言葉ではなく、入力の側にある動かない座標（ここでは時刻）で突き合わせる**。

### 2. 時刻で照合した再現率は「当たりの上限」なので、ノード数と同じ行に並べる

この照合規則には弱点がある。自動レビューでは、4 つの観点のうち 3 つが同じ点を指摘して差し戻した。

- 正解と違う内容の決定でも、同じ時間帯の発言を根拠にしていれば当たりになる
- 根拠の発言 1 つが複数の正解の区間に重なれば、1 つのノードで複数の正解を満たす

後者は、このプロジェクトでは特に起きやすい。録音サンプルの文字起こしは、60 分で 196〜220 発言、1 発言あたり平均約 17 秒と粗い。17 秒のあいだに決まったことが 2 つあれば、どちらの正解も 1 つのノードで当たりになる。

それでも照合規則は変えなかった。内容まで照合するには、結局 1. で捨てた本文の類似度か LLM の判定が要るからだ。代わりに、この再現率を「取りこぼしていないか」を見る指標として扱い、誤りや水増しは同じ行の別の列で見る。

```text
| ラン | 会議 | ノード | 深さ | 議題 | 論点 | 案 | 決定 | 課題 | TODO | 決定の再現率 | TODO の再現率 |
```

何でも決定にしてしまうプロンプトは再現率が上がるが、同じ行の「決定」の数も跳ね上がるので気づける。

**安く決定的に測れる指標は、甘く出る方向を自覚して、それを打ち消す数と同じ行に並べる**。

### 3. 比較は統計値を出さず、1 ラン 1 行の表を標準出力に出すだけにする

「複数回の結果を並べて、ランごとのぶれを見る」という要求には、次の形で応えた。

```sh
node src/cli.ts eval [--truth <正解ファイル>] <セッションのフォルダ>...
```

- 渡した順に 1 ラン 1 行の Markdown の表を出す。行を並べればぶれは見えるので、平均や標準偏差は出さない
- 結果はファイルに書かず、標準出力だけに出す。評価結果には第三者の会議の内容が入りうるので、リポジトリの中に何も書かなければ、誤って git に入れることがない
- モデル名やプロンプトの版をセッションに記録する仕組みも作らない。比べたいランのフォルダを並べて渡せば比較は成り立つ

計算（指標・再現率・表の整形）は Node に依存しない中核のモジュールに純粋関数として置き、ファイルの読み込みは CLI の側に置いた。前のエントリで書いた「実行環境に触る出口は中核の外に出す」という分け方に、そのまま乗っている。

1 つだけ、レビューの指摘で直した。会議名は文字起こしのファイル名から、ランの名前はフォルダ名から来るので、`|` や改行が入りうる。そのまま ` | ` で連結すると、指標が隣の列にずれ、1 ラン 1 行も崩れる。セルごとに `\` と `|` をエスケープし、改行を空白 1 つにしてから連結した。テストでは、会議名 `会議|A\B<改行>C`、ランの名前 `run|x\` という意地の悪い名前で流し、各行のセル数が見出しと一致することを確かめている。

**人が後で目で比べる出力は、集計を足すより、1 行 1 件で並べてそのまま貼れる形にする。そして、外から来る名前は表の区切りを壊すものとして扱う**。

### 4. 人が書く入力は、照合に使う欄だけを厳しく検証する

正解は人が手で書くので、形が崩れていても計算が黙って進むと、再現率が気づかないうちに誤る。読み込みの境界で検証し、不正ならファイルのパスを含むエラーで止めるようにした。テストでは次の 8 通りを止めている。

- JSON として読めない / オブジェクトでない
- `決定` か `TODO` のキーが無い / 配列でない
- `from` か `to` が数でない
- `from` が `to` より大きい

一方、`text` は検証せず、文字列でなければ空文字にした。自動レビューは「必須の欄なのに書き忘れを通す」と指摘したが、`text` は照合にも出力にも使わない。書き忘れで止めても人の手間が増えるだけで、再現率の正しさは `from` / `to` の検証で守れている。

**入力の検証の厳しさは、その欄が結果にどう効くかで決める**。結果に効かない欄で止めるのは、正しさではなく手間を増やす。

### 5. 自動レビューの指摘は「元の要求にある契約か」で採否を分ける

takt のワークフローでは、4 つの観点（コーディング・アーキテクチャ・テスト・AI 生成コードにありがちな問題）のレビューが並行に走り、その後で裁定の担当が指摘ごとに直すかどうかを決める。1 回目は 3 観点が差し戻し、指摘は重複を除いて 3 件だった。

| 指摘 | 裁定 | 理由 |
| --- | --- | --- |
| 再現率が内容を照合しない（2. の弱点） | 直さない | 要求は「正解の形を決め、再現率を出す」まで。内容の照合や 1 対 1 の対応は要求にない契約の追加になる |
| 正解の `text` の書き忘れを通す（4.） | 直さない | 照合にも出力にも使わず、観測できる誤った結果がない |
| 表のセルに `|` や改行が入ると崩れる（3.） | 直す | 要求の「1 ラン 1 行で並べて比べる」が実際に破れる |

2 回目のレビューは 4 観点とも承認し、直さなかった 2 件は「要求が変わる、新しい証拠が出る、などの条件を満たせば再び開く」として残った。

レビューの担当は、親切心から要求を広げる方向に指摘を出しがちだ。どれも筋は通っているので、全部直すと、要求にない照合規則や入力制約が積み上がる。**指摘は「元の要求のどの条件が破れるか」を示せたものだけ直し、示せなかったものは既知の限界として記録に残す**。2. の弱点がこのエントリに書けているのは、それが捨てられずに記録に残っていたからだ。

### 6. テストを先に別の担当が書くと、計画の細部まで契約になる

ワークフローでは、テストを書く担当と実装する担当が分かれている。テストの担当は計画にあった列の見出し `決定の再現率` / `TODO の再現率` をそのまま期待値にした。実装の担当が見出しを `${種別}の再現率` と組み立てたところ、`TODOの再現率`（空白なし）になり、テストが 3 件落ちた。

実装は、種別ごとに見出しを持つ対応表に直した（テストの側を合わせるのではなく）。対応表にしておくと、正解の種別を増やしたときに型検査で見出しの書き漏れに気づける。

テストを先に書くのは、同じ人がやっても別の担当がやっても、計画の文字列を固定する効果がある。別の担当だと、実装の担当が「このくらい揃っていればいい」と丸めた細部が、そのまま落ちたテストとして返ってくる。**表示の文字列は、組み立てずに表として持つ**。

### 7. 人がやる受け入れ条件は、自動でマージされると閉じた issue の中に取り残される

要求には「サンプル 2 本分の正解（決定・TODO の一覧）を人が作る」という条件があった。エージェントは計画の段階でこれを自分の範囲外と判断し、レビューもマージを止める理由にはしなかった。それ自体は正しい。

ところが、PR の本文に issue を閉じる記述（`Closes #44`）が入っていたので、マージと同時に issue も閉じた。人がやる条件のチェックボックスは未チェックのまま閉じている。このエントリを書いた時点でも、サンプルの置き場に正解のファイルはまだない。つまり、指標の表は出せるが、再現率の列はまだ一度も実データで埋まっていない。

**エージェントに渡す issue に人の作業が混ざるなら、人の作業は別の issue に切り出してから渡す**。同じ issue に入れておくと、コードの完了がそのまま issue の完了として扱われる。
