## 共有画面の取り込みで、利用者に許可と選択をどう求めるかを決め、断られても音声だけで続けることにした話

共有画面（選んだ会議アプリのウィンドウに映る、相手が共有している画面）を、発言を読み解く文脈として AI に渡すことは、前日の試作で決まっていた。今回は、その画面を Mac からどう取り込むかと、利用者にどんな許可と操作を求めるかを決めた。やり方は、設計者（利用者本人）に質問を並べて答えてもらう形で、2 往復で決まった。結論は 3 つある。システムのウィンドウピッカーは使わず、選んだ会議アプリのウィンドウを直接取り込む。許可はセッションを始めるたびに確かめる。許可が無いときや断られたときは、止めずに音声だけで続ける。

- 決定の記録: [共有画面の取り込みで、利用者に権限と選択をどう求めるか](https://github.com/daiki-beppu/live-mindmap/issues/185)、[ADR 0011](../adr/0011-capture-shared-screen-directly.md)、地図は [共有画面を発言の文脈としてマップに使う](https://github.com/daiki-beppu/live-mindmap/issues/179)

前提として、今の作りでは、ヘルパー（会議の音を取る Swift の CLI）をローカルのサーバーが子プロセスとして起動する。マイクとシステム音声の許可は、ヘルパーを起動したターミナルのアプリに付く。調べて分かっていたのは次の 4 点だ。

- 会議アプリのウィンドウは、ScreenCaptureKit で、アプリの bundle id と突き合わせて特定できる
- 画面を取るには「画面収録」の許可が要る。音声の許可とは別の許可になる
- ピッカーを使わずに直接取ると、macOS 15 以降は OS が月に 1 回「システムのプライベートウィンドウピッカーを回避しようとしています」と確認を出す
- ピッカーは、候補を会議アプリのウィンドウだけに絞る指定を持たない（除外の指定だけ）

### 1. 「新しい前提を課さない」方針の下では、月に 1 回の OS の確認より、毎回の選択のほうが重い

選択肢は 2 つあった。直接取り込むと、許可が 1 つ増え、月に 1 回確認が出る。ピッカーを使うと、確認は出ない代わりに、セッションを始めるたびに利用者がウィンドウを選ぶ。

この利用者には「イヤホン必須のような使い方の条件を課すより、自動で判定してどのケースでも動く案を選ぶ」という方針がある。この方針に照らして、2 つの負担を次の 2 点で比べた。

- **頻度:** 月に 1 回か、毎回か
- **間違える余地があるか:** OS の確認は「許可」を押すだけだ。ピッカーは候補を絞れないので、ブラウザの別のウィンドウなど、違うものを選べてしまう

もう 1 つ、調査には「画面を持たない CLI からピッカーを出せるかは未確認」とあった。ピッカーを選ぶと、この確認も先に要る。

決めたことは、ピッカーを選ばなかった理由と一緒に ADR に残した。コードだけを読むと、毎月確認が出る方式をわざわざ選んだように見えて、「なぜピッカーを使わないのか」と思われやすいからだ。

**許可や確認の負担を比べるときは、頻度と、利用者が間違える余地があるかを並べる。** OS が出す確認は、頻度が低く間違えようがないので、手順としては軽い。

### 2. 入力が欠けたときに止めるかどうかは、その入力が無いと製品の出力が成り立たないかで決める

マイクの許可が無いと、ヘルパーはエラーで終わる。画面も同じ扱いにするかを決めた。

結論は、画面はマイクとは逆で、許可が無くても止めないことにした。マイクが無ければ `自分` の発言が取れず、マップの半分が欠ける。共有画面は「この数字」が何を指すかを補う文脈で、ノードの根拠にはならない。画面が無くても、マップは今まで通り作れる。

止めない代わりに、知らせ方を 2 つ決めた。

- **画面:** セッションの開始時に、目立たない一文を 1 回だけ出す（例:「共有画面は使っていません（画面収録の許可がありません）」）
- **ログ:** 共有画面なしで動いたことと、その理由を 1 件残す。後で再生や評価をするときに、画面なしの回と区別できるようにする。この区別が無いと、画面を指す発言が取れなかった回が、許可が無かったせいなのか、読み解きが外れたせいなのか分からなくなる

**同じ「許可が無い」でも、入力ごとに止めるか続けるかを決める。続けるなら、利用者への一言と、後で区別するためのログの記録を対にする。**

### 3. 用語を広げるかどうかは、見た目が似ているかではなく、その用語が約束している帰結で決める

用語集には「取り込みの途切れ」という語がある。音声を取り込めず、発言が届かない区間のことで、「マップはその間の話を含まない」という帰結が付いている。途中で画面収録の許可を取り消されて画面だけが取れなくなったときも、この語で呼ぶかを決めた。

どちらも「取り込みが止まった」ように見えるが、帰結が違う。画面だけが取れないなら、話は今まで通りマップに入る。同じ語で呼ぶと、ログや画面で「途切れ」を見た人が、その間の話が抜けていると読み違える。そこで、途切れには含めないことにした。用語集の「取り込みの途切れ」の説明には、「共有画面だけが取れないときは、話はマップに入るので途切れではない」と一文を足した。

**新しい事象を既存の語に含めるときは、その語の定義に付いている帰結（ここでは「その間の話が無い」）が、新しい事象でも成り立つかを確かめる。**

### 4. 結果がどうなっても決定が変わらない事実の確認は、仕様を止めずに実装の完了条件に回す

実機でしか確かめられない点が 3 つ残った。

- 画面収録の許可も、音声と同じくターミナルに付くか
- 月に 1 回の確認に、誰の名前が出るか
- 許可した後、ターミナルを開き直さないと効かないか

3 つ目は、質問の中で「macOS の画面収録は、許可した後もアプリを開き直すまで効かないことが多い」と書いた。これは一般的な知識として書いたもので、このヘルパーで確かめたわけではなかった。もし正しければ、初めてのセッションは画面なしで進むことになる。

どれも OS のダイアログを人が操作しないと確かめられない。地図に「人が実機で確かめる」チケットを立て、それが済むまで仕様をまとめるのを止める案もあった。ただ、どの結果が出ても、直接取り込むことと、断られたら音声だけで続けることは変わらない。変わるのは、利用者に出す一文の文言（どのアプリに許可を与え、何を開き直すか）だけだ。そこで、仕様には「未確認」と書いておき、確認は実装 issue の完了条件にした。

**未確認の事実を、決定を待たせるものとそうでないものに分ける。** 答えによって選ぶ案が変わるなら、先に確かめる。変わるのが文言や数字だけなら、実装の完了条件に回し、仕様は先に進める。

### 5. 1 つ決めたら、霧の中で問いの形になったものをチケットに切り出し、次に着手できるものを残す

この地図では、まだ問いの形にできない論点を「Not yet specified（霧）」の節に書いておく。今回の決定が閉じた時点で、地図の子チケットのうち開いているものが無くなった。そのままだと、次のセッションが手を付けられるものが無い。

霧を読み直すと、3 つは問いとして既に十分はっきりしていた。共有画面を差分更新の呼び出しのどこに・いつ載せるか、画面の中身が変わったことをどう判定するか、利用者がセッションごとに切れるようにするか、の 3 つだ。この 3 つを、霧から外してチケットにした。前日の試作で分かったことや調査で分かった制約は、霧の節に書き足してあった。それをチケットの本文に移すだけで、問いの形になった。

一方、「ログへの残し方と、再生で共有画面を流す形」は霧に残した。画像をいつ送るかが決まらないと、ログに何を残すかも決まらないからだ。

**チケットにするかどうかは、今答えられるかではなく、今問いを正確に書けるかで決める。** 他の決定を待つ論点は、問いの形が決まらないので霧に残す。

### 6. エージェントに送った最初の指示は、画面が空に見えても、数秒待って読み直してから送り直す

次のチケットは、Orca（git worktree ごとにエージェントのターミナルを管理するアプリ）で新しいワークツリーを作り、そこで別の Claude Code のセッションに進めてもらった。`orca worktree create --agent claude --prompt "/wayfinder #179"` で作り、起動が落ち着くのを待って（`terminal wait --for tui-idle`）、画面を読んだ。入力欄が空で、指示が届いていないように見えたので、同じ指示をもう一度送った。

実際には、最初の指示は届いていて、エージェントは作業を始めていた。2 通目は「実行中のターンの後に送るメッセージ」としてキューに入った。送ったときの結果にも、「入力は受け付けたが、ターンの開始は観測できなかった」という警告が出ていた。そのまま放っておくと、エージェントが質問を出して止まったときに、2 通目が利用者の答えとして渡ってしまう。上矢印キーを送ってキューから下ろしたところ、画面からは消えた。ただ、実行中のターンに追加の指示として入った可能性は消せていない。中身が同じ指示だったので、実害は無かった。

**起動直後のエージェントに送った指示は、届いたかを、作業の表示が出るまで数秒待って確かめる。** 送り直すのは、それでも始まっていないと分かってからにする。

## 共有画面を、変わったときだけ時刻つきで AI への呼び出しに載せると決めた話

共有画面（選んだ会議アプリのウィンドウに映る、相手が共有している画面）を画像のまま AI に渡すことは、前日の試作で決まっていた。今回は、その画像を AI への呼び出しの「どこに・いつ」載せるかを決めた。やり方は、設計者（利用者本人）に 7 つの質問を推奨案つきで並べる形で、1 往復で全部推奨どおりに決まった。

- 決定の記録: [共有画面を差分更新の呼び出しのどこに・いつ載せるか](https://github.com/daiki-beppu/live-mindmap/issues/251)、関連する判断は [ADR 0006](../adr/0006-send-map-changes-within-a-query.md)、地図は [共有画面を発言の文脈としてマップに使う](https://github.com/daiki-beppu/live-mindmap/issues/179)

前提として、マップの差分更新（新しい発言を読んで、既存のマップに足す・直すなどの操作を返させる呼び出し）は、Claude Agent SDK の query を開いたまま 14 回使い回す。query の中では、前に送ったメッセージが会話の履歴として残り、プロンプトキャッシュで安く読み直される。14 回目の後や失敗の後には query を開き直し、履歴は消える。ADR 0006 では、この開いた query の中で、2 回目からはマップの変更だけを送ると決めてあり、実装は進行中だ。

試作で分かっていたのは次のことだ。

- 画面を「変わったときだけ」添え、開き直したら今の画面を送り直す形で、画面を指す発言（「この数字」など）が 20 件中 0 件から 12〜13 件、正しい中身でマップに入った。費用は 1 時間あたり約 +$0.2 だった
- 開き直すと前の画面が履歴から消え、「さっきの表」のように前の画面を指す発言は 2 件とも取れなかった
- 画像は 1280×720 で 1 枚 1,196 トークンになる

### 1. 会話の履歴に残る入力は、毎回添えず、変わったときだけ添える

候補は、毎回の呼び出しに最新の画面を 1 枚添えるか、変わったときだけ添えるかの 2 つだった。毎回添えるほうが作りは単純で、AI も「今の画面はこれ」と迷わない。

ただ、開いた query では、添えた画像は開き直すまで履歴から消せない。途中で消すと、キャッシュが前から一致しなくなって効かなくなる。毎回添えると、14 回で約 1.7 万トークンが履歴に積もる。キャッシュの読み出しは安いが、画面が変わっていない呼び出しにまで払うことになる。変わったときだけ添えれば、費用は呼び出しの回数ではなく、画面が変わった回数で決まる。これは ADR 0006 の「マップは変更だけ送る」と同じ考え方で、試作で効くことも確かめてあった。

**履歴に残る入力は、状態そのものではなく、状態の変化として送る。** 履歴から消せない作り（開いた query とキャッシュ）では、毎回の再送はそのまま積もる。

### 2. 「添えていなければ前のものが続く」と決めたら、「無くなった」も明示的に送る

変わったときだけ添えると、添えていない呼び出しでは「前に添えた最新の画面が今も映っている」と AI に読ませることになる。すると、共有が終わって参加者の顔だけになったとき、何も送らなければ、AI は最後のスライドがまだ映っていると思い込む。黙っていることが「続いている」の意味になったので、「終わった」は黙っていては伝わらない。

そこで、共有が終わったときは画像を付けずに `## 共有画面：なし（[12:34] から）` と送ることにした。終わったことをどう見分けるかは、画面の変化を判定する別のチケットで決める。こちらで決めたのは、伝え方だけだ。

**差分で状態を伝える形にしたら、「無くなった」を表す送り方を最初から用意する。** 差分の中で、何も送らないことは「変わらない」の意味になってしまうからだ。

### 3. 1 回の呼び出しでまとめて送る入力は、時刻で突き合わせられるようにする

差分更新の 1 回の呼び出しには、前回からの「新しい発言」がまとめて入る。その間にスライドが 3 から 4 に変わると、最後の 1 枚だけ添えた場合、スライド 3 を指した発言をスライド 4 で読んでしまう。

発言にはもともと `id [12:34] 本文` の形で時刻が付いている。そこで、新しい発言の時間帯に映っていた画面をすべて、映り始めた時刻つきで時刻順に添えることにした。見出しは `## 共有画面 [12:34] から` にし、上限は 3 枚（超えたら新しい 3 枚）にした。system プロンプトには「時刻つきで複数あれば、発言の時刻に映っていたものを使う」と書く。

**まとめて送る入力どうしの対応は、並び順ではなく、両方に付けた時刻で取らせる。** 一方（発言）にもう時刻があれば、もう一方（画面）に同じ形の時刻を付けるだけで済む。

### 4. 履歴が消える区切りでは、全部を送り直さず、さかのぼれる最低限を決めて送り直す

query を開き直すと、それまでの画像は消える。試作は今の画面だけを送り直していたので、「さっきの表」は取れなかった。かといって、それまでの画面を全部送り直すと、開き直すたびに費用が会議の長さに比例して伸びる。ADR 0006 で避けたのと同じ形になる。

決めたのは、開き直したときに、今の画面と、その前に映っていた 1 枚を、時刻つきで送り直すことだ。増えるのは開き直すたびに約 1,200 トークンだけになる。これで、「少なくとも直前の 1 枚までは必ずさかのぼれる」と言える。それより古い画面は、query が開いている間に履歴に残っていればさかのぼれる、という扱いにした。

**さかのぼれる範囲は「最大でどこまで」ではなく「最低でもどこまで」で決める。** 履歴が残っていれば偶然それより前も見えるが、仕様として約束するのは、開き直した直後でも成り立つ範囲だけにする。

### 5. 同じプロンプトの節を書き換える 2 つの変更は、並行させずに積む

system プロンプトの「会話の扱い」には、今は「毎回のメッセージは独立した依頼」と書いてある。試作では、ここを「共有画面だけは前に添えた最も新しいものが続く」と書き換えていた。一方、進行中の「変更だけ送る」実装も、同じ節を「2 通目からは前回からの変更だけが載る」と書き換える。

2 つを並行して進めると、同じ節を別々に書き換えて、マージするときにぶつかる。しかも共有画面の「前のものが続く」という読ませ方は、「会話は続いている」という前提の上に乗っている。そこで、「会話の扱い」の書き換えは変更だけ送る実装に任せ、共有画面の側は新しい「# 共有画面」の節だけを足すことにした。実装の順番も、変更だけ送る実装がマージされてから、その上に積む。

**同じ前提に乗る 2 つの変更は、前提を書き換える側を先に入れ、乗る側は自分の節だけを足す。**

### 6. 前の決定を待って霧に残していた論点は、その決定が出たらすぐチケットにする

この地図では、まだ問いの形にできない論点を「Not yet specified（霧）」の節に書いておく。同じ日の[前のエントリ](#shared-screen-permission)では、「ログへの残し方と、再生で共有画面を流す形」を、載せ方が決まらないと問いにできないとして霧に残していた。

今回、載せ方が決まり、ログに残すべきもの（変わった画面と映り始めた時刻、「なし」とその時刻、開き直したときの送り直し）がはっきりした。そこで、この論点を「共有画面をセッションのログに残し、再生で流す形」というチケットにして、霧から外した。あわせて、画面の変化を判定するチケットには、送る側に必要なもの（映り始めた時刻と、共有の終わり）をコメントで伝えた。

**霧に残すときに「何の決定を待つか」を書いておくと、その決定が閉じた時点で、チケットにする論点をすぐ見つけられる。**

## 共有画面の「中身が変わった」を、台本ページを取り込んで判定の規則を詰めた話

共有画面は、変わったときだけ、映り始めた時刻つきで AI に渡すと決まっていた（[前のエントリ](#shared-screen-placement)）。今回は、その「変わった」をどう判定するかを決めた。台本どおりに動く会議アプリ風のページを作り、そのウィンドウを実際に取り込んで、判定の規則を当てながら詰めた。規則は 8 回ほど書き直した。

- 決定の記録: [共有画面の中身が変わったことをどう判定するか](https://github.com/daiki-beppu/live-mindmap/issues/252)、地図は [共有画面を発言の文脈としてマップに使う](https://github.com/daiki-beppu/live-mindmap/issues/179)

試作は 3 つの部品でできている。

- **台本ページ（HTML、166 秒）**: 会議アプリのウィンドウを真似て、次の場面を順に流す。参加者の顔だけ（カメラオフ・オン）、スライドの切り替え、フェード、カーソル、縦長の資料のスクロール、スライドの中の動画、項目を 1 行ずつ出す、表のセルの書き換え、共有の停止、別のタブへの切り替え。右の小窓には動く顔を描き、話している人の枠は 4 秒ごとに移る
- **取り込み（Swift）**: ScreenCaptureKit（macOS の画面取り込みの API）で Chrome のウィンドウを 4 fps で取る。フレームごとに、OS が付ける状態・`dirtyRects`（描き直された範囲）・縮小した輝度・サムネイル・ウィンドウのタイトルを記録する
- **判定とビューア（JS）**: 判定は DOM に触れない関数にした。ビューアのつまみでしきい値を変えると、どこで送るかがその場で出し直され、「送ってほしい時間の幅」との照合の結果も出る

台本ページは、隠れても描き続けるよう `--disable-backgrounding-occluded-windows` を付けた別の Chrome で開いた。タブの切り替えは DevTools プロトコルから行った。こうすると、利用者の画面を奪わずに、同じ場面を何度でも取り直せる。

### 1. OS が出す「変わっていない」は、描き直し続けるアプリでは出ない。頼る前に、1 本取り込んで中身を見る

調べた段階では、ScreenCaptureKit のフレームには「変わっていない」を表す `SCFrameStatus.idle` と、変わった範囲の `dirtyRects` が付き、これで変わったときだけ取れる見込みだった。

最初の取り込みの 20 秒で、81 枚がすべて新しいフレーム（`complete`）だった。`idle` は 1 枚も出ない。`dirtyRects` も、場面に関係なく常にウィンドウ全体（100%）だった。顔だけで、話している人の枠しか動かない場面でもそうだった。Chrome はアニメーションのたびにウィンドウ全体を描き直すので、OS から見ると毎回すべてが変わっている。判定は、取り込んだ画像を自分で比べることになった。

**OS やライブラリが出す「変化の手がかり」は、文書に書いてあっても、対象のアプリで実際に出るかを 1 本取り込んで確かめてから設計に入れる。** 本物の会議アプリ（Zoom など）で `idle` が出るかは、まだ確かめていない。出るなら前段の間引きに使うが、判定の根拠にはしない。

### 2. 比べる相手は前のフレームではなく、最後に送った画面にする

最初の規則は、前のフレームと比べて変わったマスが多ければ「変わり始め」とし、止まったら送る、というものだった。顔だけでなくスライドを映している間も、2〜3 秒ごとに送ってしまった。

数字を出すと、前のフレームとの差は 0.1% 程度で「止まっている」のに、送った画面との差は 0.6% → 1.1% → 1.9% と毎フレーム増えていた。右の小窓の顔がゆっくり揺れていて、1 フレームではしきい値に届かないが、積み上がるとしきい値を超える。前のフレームと比べると「止まっている」に見え、送った画面と比べると「変わった」に見える。

そこで、判定の基準を「最後に送った画面との差」に固定した。前のフレームとの差は、「いま動いているか」を見ることだけに使う。

**ゆっくり進む変化は、隣どうしの差では見えず、基準との差で初めて見える。** 送るかどうかの判定は、送ったものと比べる。

### 3. しきい値で分けられない 2 つの変化は、場所と時間で分ける。外すのを一時的にすれば、見落としは遅れに変わる

スライドに文字を 1 行足すと、ウィンドウの約 1% のマスが変わる。顔の縁の揺れも、ちょうど同じくらいの約 1% だった。しきい値を 1.5% にすると 1 行の追加を見落とし、0.5% に下げると顔の揺れで送る。大きさでは分けられなかった。

分けられたのは、場所と時間だった。顔や動画のマスは動き続け、追加された行のマスは 1 回変わったら止まる。そこで、「いま動いているマス」（直近 1 秒に動いた、または直近 10 秒のうち 25% を超えるフレームで動いた）を、比べる対象から外すことにした。

途中で一度、外し方を間違えた。動いたマスを長く覚えておく作りにしたところ、3 回スクロールした資料の場所が「よく動く場所」として残った。その後、同じ場所に出た行やセルの書き換えを見落とした。

直したのは、外すのを一時的にしたことだ。2 の「送った画面と比べる」と組み合わせると、外していた間の変化も、止まった時点で送った画面との差として残っている。外していた時間の分だけ遅れて送るが、見落としにはならない。

**判定から一部を外すときは、外している間の変化が後で拾える形（基準との差）にしておく。** そうすれば、外しすぎても失敗は「見落とし」ではなく「遅れ」になり、しきい値を緩く選べる。

### 4. 縮小の粒度は、拾いたい最小の変化の大きさから決める

最初は、ウィンドウを 64×36 のマス（1280 幅で 1 マス約 20px）に縮めて比べていた。表のセルを「1,580」から「1,620」に書き換える場面は、どうしても拾えなかった。マスごとの差を文字で描いてみると、変わった数字の上のマスは、輝度の差が 3〜8 程度しかなかった。20px 四方の平均の中では、細い数字の線が変わっても薄まってしまう。

128×72（1 マス約 10px）で取り直すと、同じ書き換えで比べたマスの約 2% が変わり、拾えた。マスの数は 4 倍だが、1 フレーム 9,216 個の比較なので、4 fps でも負担は無いに等しい。

**画像の比較の粒度は、見逃したくない最小の変化（ここでは表の数字 3 桁）を実際に描き分けられるかで決める。** 大きな変化（スライドの切り替え）で試すと、どの粒度でも拾えてしまい、差が見えない。

### 5. 「前と同じ状態に戻っただけ」の判定は、部品ごとではなく 1 枚単位で取る

話している人が替わると、枠が移る。共有中も右の小窓の枠が移るので、そのたびに送ると、話者が替わるたびに画像を送ることになる。

規則は、「違うマスが前に送った画面と同じ値なら、枠が移っただけとみなして送らない」とした。最初は、マスごとに「前に送ったどれか 1 枚と同じ」かを見ていた。これで枠の移動は抑えられたが、セルの書き換えまで抑えてしまった。変わった数字のマスが、マスごとに見ると、昔の別の画面のどれかと近い値になっていたからだ。30 枚もあれば、マス 1 つが偶然どれかに当たるのは珍しくない。

直したのは、違うマスが**1 枚の同じ画面**とそろって一致することを条件にしたことだ。枠の移動なら、「枠がその位置にあったときの 1 枚」が必ずある。書き換えた数字には、そろって一致する 1 枚は無い。あわせて、範囲が広い（全体の 10% 以上）なら、前の画面と同じでも送ることにした。前のスライドに戻ったときは、戻ったこと自体を AI に伝えたいからだ。

**「前に見たものか」を部品ごとに調べると、部品の数だけ偶然の一致が増える。** 一致は、まとまり（ここでは 1 枚の画面）で取る。

### 6. 外す範囲は、一律の幅ではなく、動いているものの大きさに合わせる

128×72 では、顔の縁の揺れが外す範囲（動いているマスの周り 1 マス）からはみ出し、話している人の枠の移動を再び送るようになった。周り 2 マスに広げると、今度はセルの書き換えを見落とした。書き換えたセルの隣ではキャレット（文字入力のカーソル）が点滅していて、その巻き添えで数字のマスまで外れたのだ。

結局、動いているマスの周り 5×5 に、動いているマスがいくつあるかで幅を変えた。8 個以上なら「広く動く場所」（顔・動画）として 2 マス、それ未満は「点のように動くもの」（キャレット・カーソル）として 1 マスだけ外す。

**同じ「動いている」でも、顔のような面とキャレットのような点では、巻き添えにしてよい範囲が違う。** 一律の幅で決めると、どちらか一方に必ず合わない。

### 7. 試作の正解表も間違える。判定が外れたら、まず台本と正解表を疑う

ビューアには「送ってほしい時間の幅」を正解として書いておき、判定と照合した。s8（項目を 1 行ずつ出すスライド）の 4 行目と 3 行目が、続けて「漏れ」になった。

実際には、s8 の項目はもともと 3 行で、4 行目は存在しなかった。台本の隠し方の計算から、114 秒の時点ですでに 3 行とも見えていた。判定は 108・111・114 秒に正しく送っていた。私は 2 回とも、まず判定の規則を疑ってマスの差を調べた。サムネイルを並べて見るまで、正解表の誤りに気づかなかった。

**判定が外れたら、規則を直す前に、その時刻のサムネイルを見て、正解表が正しいかを確かめる。** 試作では、台本も正解表も同じ人が急いで書くので、規則と同じくらい間違える。

### 8. 確実に見分けられないものは見分けず、受け取る側が読み分けられるように送る

共有が終わって参加者の顔だけになったとき、「共有画面なし」を送れるかも試した。動いているマスが全体の 7 割を超えたら顔だけとみなす規則は、場面の切り替えの瞬間を「顔だけ」と誤った。3 秒続いたら、と条件を足すと、今度は合成の顔の動きが小さすぎて一度も成り立たなかった。そもそもカメラオフのアイコンの並びは、動きで見るとスライドと区別がつかない。

利用者に選んでもらった結論は、見分けないことだった。顔の並びも 1 枚の画面として送り、AI への指示（system プロンプト）に「顔の一覧なら共有なし」と書いて読ませる。動く顔は 3 のとおり比べる対象から外れるので、送るのは並びが変わったときだけになり、費用は数枚分で済む。「なし」を送るのは、確実に分かるとき（ブラウザのタイトルが会議のタブでない）だけにした。

**手元で確実に見分けられないことは、誤りうる判定を足すより、受け取る側が読み分けられる形で渡す。** その形で費用が膨らまないかは、別に確かめておく。

### 9. 1 回だけの失敗は、決めてある逃げ道で受け止められるかを確かめてから先に進む

128×72 で取り直そうとしたとき、取り込みの開始が「画面収録の TCC（macOS の権限の仕組み）を拒否しました」で失敗した。ウィンドウの一覧は取れていたので、開始だけが断られていた。利用者に確認のダイアログが出ていないか尋ねたが、見当たらなかった。もう一度流すと通り、原因は分からないままになった。

追いかける手もあったが、許可が無い・断られたときは止めずに音声だけで続けると、同じ日の[最初のエントリ](#shared-screen-permission)で決めてある。この失敗も、その作りでそのまま受け止められる。そこで、起きたことを試作の結果に書いておき、本物の会議アプリでの確認（実装の完了条件）のときに、もう一度出ないかを見ることにした。

**再現しない失敗は、決めてある失敗時の振る舞いで受け止められるなら、記録して先に進む。** 受け止められないなら、そこで止めて原因を追う。

## 共有画面を使うかを、セッションの開始時だけ切れるようにした話

共有画面は既定で AI に渡す。それを利用者が会議ごとにオフにできるようにするかを、設計者（利用者本人）に質問を並べて答えてもらう形で決めた。2 往復で、すべて推奨どおりに決まった。セッションの開始時に `cli start --app <bundle id> --no-screen` で切れるようにし、途中では切れないようにした。切ったときは、画面の取り込みも「画面収録」の許可の要求もしない。ログには、許可が無いときとは別の理由として「使わない（指定）」を残す。ヘルパー（会議の音と画面を取る Swift の CLI）が起動し直しても、オフのままにする。

- 決定の記録: [共有画面を使うかを利用者がセッションごとに切れるようにするか](https://github.com/daiki-beppu/live-mindmap/issues/253)、地図は [共有画面を発言の文脈としてマップに使う](https://github.com/daiki-beppu/live-mindmap/issues/179)

### 1. 切り替えを用意する理由を分けてみて、実測の数字で消える理由を先に消す

切りたくなる理由は 2 つ考えられた。1 つは費用を抑えたいこと、もう 1 つは、Claude に送りたくない画面（社外秘の資料など）が映ることだ。費用のほうは、前日までの調査と試作で、変わったときだけ画像を送れば 1 時間あたり +$0.2〜0.25 と分かっていた。この額では、切る理由にほとんどならない。

理由が「送りたくないもの」だけになると、設計の問いも変わる。どれだけ細かく切れるかより、送る前に確実に切れるかが大事になる。

**切り替えを設計する前に、切る理由を並べ、すでに測った数字で消せるものは消す。** 残った理由が、どこで・いつ切るかを決める。

### 2. 既にある逃げ道で代わりになるかは、効く範囲で判断する

新しい切り替えを作らなくても、「画面収録」の許可を出さなければ、画面は使われない。同じ日の[最初のエントリ](#shared-screen-permission)で、許可が無ければ音声だけで続けると決めてあるからだ。

ただし、この許可は macOS の設定で、アプリ全体に効く。一度許可した後に 1 回の会議だけ切るには、システム設定を開いて許可を外し、終わったら戻すことになる。欲しいのは会議ごとに切ることなので、効く範囲が合わない。

**「それなら○○すれば済む」という代わりの手は、欲しい範囲（ここではセッションごと）で効くかで判断する。** 効く範囲がずれる手は、手順を利用者に押し付けるだけになる。

### 3. 前例のある形に合わせ、意味が増える途中の切り替えは後に回す

セッションの開始には、もともと `--no-audio`（会議の録音ファイルを残さない）がある。既定はオンで、フラグで外す形だ。これに並べて `--no-screen` にすれば、利用者に新しい前提も手順も増えない。

会議の途中で切ったり戻したりできるようにする案も比べた。ところが途中で切ると、切る前にもう送ってしまった画面の扱いが問題になる。「切った」が、これから送らないことなのか、送った分も無かったことにするのかを決めなければならない。「送りたくないかどうか」はたいてい会議の性質で始める前に分かるので、途中の切り替えは必要になってから足すことにした。

**切り替えは、新しい意味を生まない地点（開始時）から入れる。** 途中で切ると「それまでの分」の意味が増え、決めることが一段増える。

### 4. フラグが何を切るのかを、既定オンのほかの設定と照らして 1 つにする

この地図の方針には、もう 1 つ既定オンのものがある。AI に渡した共有画面の中身をセッションのログに残し、再生と回帰評価に使うことだ。すると `--no-screen` が切るのは「AI に送ること」か「ログに残すこと」か、別々に切れるべきか、という問いが出た。

照らしてみると、ログに残すのは「AI に渡した中身」と決まっていた。送らなければ、残す中身もそもそも無い。そこで、フラグは共有画面を使うこと自体（取り込まない・送らない・ログにも中身が残らない）を切る 1 本にした。一方で、`--no-screen` は「画面を録画しない」と読み違えられやすい。そこで CLI の説明文に「共有画面を AI に渡さない（取り込まない）」と書くことにした。

**オフにするフラグを足すときは、同じ対象に関わるほかの既定オンの設定を並べ、片方がもう片方を前提にしていないかを確かめる。** 前提になっているなら、フラグは 1 本で足りる。

### 5. 結果が同じでも、理由が違えばログでは分けて残す

`--no-screen` で切ったときと、許可が無いときは、どちらも「画面なしで音声だけ」で動く。それでもログには別の理由として残す。回帰評価では「画面を指した発言が正しい中身でノード（マップの項目）になったか」を数えるので、画面が無かったセッションの扱いが結果を左右する。利用者が自分で切ったのか、取りたかったのに取れなかったのかが混ざると、取れなかった割合を測れなくなる。

あわせて、自分で選んだことなので、表示に通知は出さない。許可が無いときは一文の通知を出すので、通知でも 2 つは分かれる。

**同じ振る舞いに行き着く 2 つの経路は、ログでは理由を分けて記録する。** 後で数えたいのは、たいてい「意図して」と「意図せず」の違いだからだ。

## ヘルパーが黙って止まる・何度も止まる 2 件の報告を、既にある起動し直しに寄せて切り分けた話

前日の実際の会議で見つかった、ヘルパー（会議の音を取る Swift の CLI。ローカルのサーバーが子プロセスとして起動する）の不具合 2 件をトリアージした。トリアージでは、報告をコードと照らし、エージェントが一人で進められる形に整えるか、人の判断や実機の確認に回すかを決める。1 件目は、会議の途中で入力の機器を内蔵マイクから AirPods に切り替えると、`自分`（利用者のマイク）の取り込みが黙って止まるもの。2 件目は、最適化なしのビルドのヘルパーが、Mac の負荷が高いときに入力の滞留で数分おきに止まるものだ。設計者（利用者本人）にまとめて 2 問を聞き、どちらも推奨どおりに決まった。1 件目は、機器が変わったらヘルパーを止め、既にある起動し直しに任せる。2 件目は、release ビルドで起動するところまでをエージェントに渡し、負荷をかけた計測と止まり方の見直しを人の作業として別の issue に切り出した。

- 決定の記録: [入力の機器を切り替えると、自分のマイクの取り込みが黙って止まる](https://github.com/daiki-beppu/live-mindmap/issues/232)、[最適化なしのビルドだと、負荷が高いときにヘルパーが入力の滞留で数分おきに止まる](https://github.com/daiki-beppu/live-mindmap/issues/233)、切り出した [release ビルドで止まらないかを測り、止まり方を変えるかを決める](https://github.com/daiki-beppu/live-mindmap/issues/284)

前提として、このプロジェクトには前から「起動し直し」がある。ヘルパーが予期せず終わると、サーバーは 1 秒ほどで新しいヘルパーを起動し、同じセッションを続ける。起動し直すたびに、録音ファイルは起動回ごとに分かれる。60 秒以内に続けて失敗すると、一定の回数で起動し直しを諦める。

### 1. 直し方の候補は、報告に書かれていない依存をコードで探してから比べる

1 件目の報告には、直し方の候補が 3 つ並んでいた。(a) ヘルパーの中でマイクの取り込みを作り直す。(b) ヘルパーを終了コード付きで止め、起動し直しに任せる。(c) 取り込みが一定時間届かないことを見張る。報告を読んだ時点では、音が抜けない (a) がいちばん良く見えた。

コードを読むと、報告に無い依存が見つかった。録音ファイルは、最初に届いた音声バッファの形式（サンプルレートとチャンネル数）で作られる。AirPods と内蔵マイクは、サンプルレートが違うことが多い。マイクの取り込みだけを作り直すと、途中から別の形式のバッファが同じファイルに流れ込む。エコーキャンセルの参照の流れも、開始時に判定した出力先を前提にしている。(a) を正しく実装するには、取り込み・録音・エコーキャンセル・出力先の判定をまとめて作り直す必要がある。

(b) なら、それらはすべて起動し直しの中で最初から作り直される。新しい形式で録音ファイルが分かれ、出力先も判定し直される。代わりに 1 秒弱の音が抜けるが、既にテストされた経路だけで済む。

**直し方を比べる前に、作り直す対象が「開始時に 1 回だけ決めている」ものに依存していないかを探す。** 依存が多いほど、プロセスごと作り直す既存の経路に乗るほうが安く、確かになる。

### 2. 報告が挙げた直し方が、今の設計が意図して避けた形ではないかを確かめる

2 件目の報告は、直し方の 1 つに「入力が上限を超えたら止まらず、古い入力を捨てて追いつく」を挙げていた。止まるたびに録音ファイルが分かれる（71 分の会議で 15 回止まり、16 本に分かれた）のを避けたいからだ。

ところが、ヘルパーのマイク・システム音声の取り込み・文字起こしの各段には、「満杯で入らなかったバッファは捨てずに、エラーで流れを終わらせる（時刻の意味を保つため）」というコメントがあった。音声を黙って捨てると、録音の何秒目と会議の何秒目が合わなくなる。そうなるくらいなら止めて起動し直す、という意図した設計だ。捨てる方式に変えるには、捨てた区間を録音と文字起こしの時刻でどう扱うかを決め直す必要がある。これは、エージェントに実装だけを頼める範囲を超えている。

**報告にある直し方は、コードのコメントや判断の記録と照らし、今の設計の逆になっていないかを先に見る。** 逆になっているなら、それは実装ではなく判断のチケットになる。

### 3. 1 つの報告の中で、機械的に進められる部分と、計測や判断が要る部分を分ける

2 件目には、性質の違う作業が 2 つ混ざっていた。測った数字は次のとおり。

| ビルド | ヘルパーの CPU | セッション | Mac の負荷（load average の 1 分値） | 止まった回数 |
|---|---|---|---|---|
| 最適化なし（debug） | 約 60% | セミナー 71 分 | 13〜104 | 15 |
| 最適化あり（release） | 3〜12% | 会議 87 分 | 2.6〜25 | 0 |

負荷の条件が違うので、ビルドの違いだけの効果とは言えない。それでも、会議で使う起動の手順を release ビルドにするのは、数字を見れば迷わない機械的な変更だ。一方で、「負荷 80 前後で 30 分流して止まらないか」の計測には実機が要る。止まり方を変えるかどうかは、前節の判断になる。

そこで、元の issue は release ビルドで起動するところまでにしてエージェントに渡した。計測と判断は新しい issue に切り出し、人の作業にした。エージェント向けの説明には、release の実行ファイルが無いときに黙って debug を使ってはいけない、とも書いた。会議の最中に、遅いビルドで動いていることに気付けないからだ。

**1 つの報告の完了条件に、実機の計測や設計の判断が混ざっていたら、そこだけを切り出す。** 残った部分はエージェントがすぐ進められ、切り出した側は、残した部分の結果を見てから測れる。

### 4. 実機でしか再現できない不具合は、テストで確かめられる約束に言い換えて渡す

1 件目は、実際に AirPods に切り替えないと再現できない。トリアージでは再現できず、エージェントも実機を触れない。それでもエージェントに渡せたのは、完了条件を次の約束に言い換えたからだ。マイクの取り込みが「機器の構成が変わった」という OS の通知を受けたら、音声の流れが理由付きのエラーで終わる。手で止めた後に通知が来ても、エラーにはならない。流れがそのエラーで終わったら、ヘルパーは 0 以外の終了コードで終わり、標準エラーに理由が出る。どれも、通知をテストから送れるようにすれば確かめられる。

内蔵マイクから AirPods へ、AirPods から内蔵マイクへの両方向の実機確認は、マージ後に人が行う作業として説明に残した。

**実機が要る不具合は、「OS からこの合図が来たら、こう振る舞う」という境界の約束に言い換える。** 合図の先（ここでは起動し直し）が既にテスト済みなら、新しく確かめるのは合図を受けるところだけになる。

### 5. 同じ方針を強める 2 つの修正は、互いの代償を大きくしないかを並べて見る

2 件を並べると、引っ張り合いがあった。1 件目を (b) で直すと、機器を切り替えるたびにヘルパーが止まり、録音ファイルが 1 本増える。2 件目が困っていたのは、まさにこの録音ファイルの分割だ。「流れが乱れたら止めて起動し直す」という方針を、片方は強め、片方はその代償に困っている。

今回は、機器の切り替えは 1 回の会議で数回程度なので、(b) を選んだ。分割が実際にどれくらい起きるかは、切り出した計測の issue で、release ビルドで負荷をかけて数えることにした。分割が少ないと分かれば、止め方は今のままでよい。また、60 秒以内に何度も切り替えると、起動し直しを諦める上限に達する。この境界は、今回は対象外として説明に明記した。

**複数の報告を一度にトリアージするときは、それぞれの直し方が、もう片方の報告の困りごとを増やさないかを確かめる。** 増やすなら、その量を測る作業を、どちらかのチケットに含めておく。

### 6. 共有の作業場所でほかの版のコードを読むときは、作業場所を動かさずに読む

トリアージの途中で、最新の main のコードを読もうとして、作業中のブランチから `git checkout origin/main` で切り替えた。読み終えて戻ろうとすると、元のブランチ名が見つからなかった。この作業場所（worktree）を管理するツールが、その間にブランチ名を変えていたからだ。`git reflog` で名前の変更を見つけて戻れたので、ファイルは失っていない。

トリアージは読むだけの作業なので、作業場所を動かす必要はなかった。`git show origin/main:<パス>` や `git grep <語> origin/main` なら、手元のブランチのまま、ほかの版を読める。

**読むだけのときは、checkout せずに `git show <版>:<パス>` で読む。** 作業場所はほかの道具も触っているので、動かすと戻る先が変わっていることがある。

## 画面を人が動かす操作を、自動のカメラとの関係から地図にした話

利用者から「画面を縦横のスクロールやドラッグで動かしたい、ショートカットキーも整えたい」という要望が出ていた。この要望を、すぐ実装に入らず、決めることを並べた地図（親の issue の下に、決めることを 1 つずつ子の issue として置き、ブロック関係でつないだもの）にした。設計者（利用者本人）に推奨つきの質問を並べ、2 往復で範囲が決まった。結論は次のとおり。見る位置の操作はブラウザの中だけで完結させる。決めることは、試作 1 枚・調査 1 枚・話し合い 1 枚に分ける。人による議題の開閉とキーでのノード選択は、範囲には入れるが、チケットにするのは後に回す。

- 決定の記録: 地図 [画面を人が動かす操作：スクロール・ドラッグでの移動とショートカットキー](https://github.com/daiki-beppu/live-mindmap/issues/153)、[ADR 0003](../adr/0003-local-node-server-owns-pipeline.md) への追記

前提として、今の画面（React Flow で描くマインドマップ）は、スクロール・ズーム・ドラッグをすべて止めてある。反映のたびに、マップ全体を画面に収め直す。別の地図では、長い会議に向けて「全体は見せず、常に**今の議題**（直近の更新が当たった議題）に寄る」カメラに変えると決めてあった。ただ、その実装はまだ入っていない。また、ブラウザのコードにはキー操作の処理が一つも無かった。

### 1. 「表示専用」は、何を変えないのかで切り分ける

この構成には「ブラウザは表示だけ。操作は AI エージェントがサーバーの CLI から行う」という判断の記録（ADR）がある。文字どおりに読むと、ブラウザで画面を動かすこと自体がこの判断に反するように見える。

そこで、この判断が守りたかったものを確かめた。それは、マップの状態をサーバー 1 か所だけが持ち、変更をすべてログに残して、復元と再生で同じマップを作り直せることだった。画面を動かしてもマップのデータは変わらない。見る位置は人ごと・画面ごとに違うもので、再生で同じ見え方を再現する価値も低い。このため、見る位置の操作はサーバーに送らず、ログにも残さないことにした。ADR には「表示だけ＝マップのデータを変えない」の 1 行を足した。

**「〜だけ」「〜専用」という制約は、守りたかった性質（ここでは復元と再生の再現性）に戻して読む。** その性質に触れない操作なら、制約の外に出してよい。読み方を広げたときは、後の人が同じところで迷わないように、元の記録へ 1 行足しておく。

### 2. 自動の決定と人の操作は、別々の決定として扱う

長い会議の地図では「全体は見せない」と決めていた。161 分の会議では、全体を収めると文字が読めなかったからだ。一方で今回は、人が一時的に「全体を見る」操作を範囲に入れた。

この 2 つは矛盾しない。前の決定が決めたのは、自動のカメラが何を映すかだった。人が自分で遠くの議題を探しに行く場面は、その決定の前提に入っていなかった。前の決定が何を対象にしていたかを確かめずに読むと、「全体は見せないと決めたから、全体を見る操作は入れない」と、決定を必要以上に広く当てはめてしまう。

**前の決定を引くときは、その決定が「誰の・どの振る舞い」を決めたものかを確かめる。** 自動で起きることについての決定を、人が明示的に行う操作にそのまま当てはめない。

### 3. 一緒に触らないと判断できない問いは、1 枚の試作にまとめる

洗い出すと、決めることが 4 つ出た。人が動かした後、自動のカメラにいつ戻るか（一定時間で戻る／議題が変わったら戻る／キーで戻る）。動かしている間であることを画面に出すか。人がどこまで縮められるか。全体を見たときにどう映すか。

4 つは互いに絡んでいる。戻る秒数は、動かしている間の見せ方が控えめなら長くてよく、何も出さないなら短くしたい。全体を見たときの見え方も、議題を畳んで描く機能を前提にしないと評価できない。どれも互いの答えに左右されるので、長い会議のログを再生しながら案を切り替えて触る試作を 1 枚にまとめた。土台には、カメラと畳む描き方の試作で作った既存のブランチを使う。こうすれば、まだ入っていない本実装を待たずに始められる。

**チケットは、答えが互いに左右し合う問いどうしをまとめ、独立に決められる問いだけを分ける。** 実装がまだ無い機能の上で決めるときは、前の試作を土台に指定して、実装待ちで止めないようにする。

### 4. 利用者が先に決めたことは、調査の問いを「選ぶ」から「使うときの注意」に変える

ショートカットキーには「TanStack Hotkeys のようなライブラリを使う」と、利用者がその場で決めた。そのため、調査のチケットはライブラリを白紙から選ぶものではなくなった。中心は、使うときにぶつかるものの確認になった。具体的には、React Flow 自身のキー操作との重なり、ブラウザ既定のキー（`⌘+` によるページ拡大など）を奪ってよいか、画面共有中の会議アプリのキーとの衝突だ。比べる候補も、同じ役の別のライブラリを 1 つ挙げる程度にとどめた。

キーの一覧を決める話し合いのチケットは、この調査と、前の節の試作（戻るキーを置くかが決まる）の両方の後に置いた。

**決まったことが出たら、それに依存する調査の問いを書き直す。** 決まったことを調べ直す調査は、手間がかかるうえに、結論をひっくり返す材料を探すだけになりやすい。

### 5. 範囲に入れることと、チケットにすることは別に決める

人が畳んだ議題を開く操作と、矢印キーでノードを選んで根拠を出す操作も、利用者の要望の延長として範囲に入れた。ただし、どちらもまだチケットにはしていない。開いた議題がいつ自動で畳まれ直すかは、自動のカメラへ戻る条件と同じ考え方で決まる見込みだ。矢印キーは移動のキーと取り合いになる。どちらも前の問いの答えが出ないと、問い自体を正確に書けない。

そこで地図には「まだ詰めていないこと」の欄を作り、見えている範囲で書いておいた。もう一方で、マップのデータを変える人の修正（ノードの削除・本文の修正など）は、入口を CLI にすると決めてある別の取り組みの範囲なので、「範囲外」として分けた。

**チケットにするかどうかの基準は、今その問いを正確に書けるか。答えられるかではない。** 範囲内でも書けない問いは、粗いまま「まだ詰めていないこと」に置く。前の答えが出たときに、1 枚のチケットになるとは限らず、何枚かに分かれることも、要らなくなることもある。

## ショートカットキーのライブラリを調べ、「止めたつもりのキー」が動いていたと分かった話

前のエントリで作った地図の調査チケットを、サブエージェント（調査を任せた別のエージェント）が一次情報で片づけた。ブラウザのショートカットキーに使うライブラリについて、使うときにぶつかるものを確かめる調査だ。結論は 3 つある。TanStack Hotkeys（`@tanstack/react-hotkeys` 0.13.0）を版を固定して使う。React Flow（マップの描画に使っているライブラリ）の使わないキーは明示して止める。ページ拡大のキーを奪うかは仕様の判断として残す。

- 決定の記録: [ショートカットキーのライブラリの調査](https://github.com/daiki-beppu/live-mindmap/issues/286)、地図は [画面を人が動かす操作](https://github.com/daiki-beppu/live-mindmap/issues/153)

### 1. 操作を止めた設定でも、ライブラリのキーの監視は動いている

前のエントリでは「ブラウザのコードにはキー操作の処理が一つも無い」と書いた。これは自分たちのコードを grep した結果としては正しかった。画面は `panOnDrag={false}`・`zoomOnScroll={false}`・`elementsSelectable={false}` などで操作を止めてあり、キーもすべて止まっていると思っていた。

ところが React Flow 12 のソースを読むと、キーの監視は別の prop（`deleteKeyCode`・`selectionKeyCode`・`panActivationKeyCode`・`zoomActivationKeyCode` など）で決まっていた。今の画面はそれらを 1 つも渡していないので、既定のキーの監視がすべて動いている。具体的には `Backspace`・`Shift`・`Space`・`⌘`（Windows では Ctrl）で、どれも単独で押されると `preventDefault` を呼ぶ。止めるには、使わないものに `null` を渡す。監視を付けるのは値が `null` でないときだけだ。

**「操作を止めた」を確かめるときは、自分のコードではなく、ライブラリが既定で何を聞いているかを見る。** 機能ごとの無効化（ドラッグしない・選ばない）と、イベントの監視を止めることは、別の設定になっていることがある。

### 2. 同じキーを 2 つのライブラリが聞くときは、監視をどこに付けているかで届くかが決まる

TanStack Hotkeys は、既定で `document` に監視を付け、`stopPropagation` する。React Flow は `Shift`・`Space`・`⌘` を `window` で聞いている。キーのイベントは document から window の順に伝わるので、同じキーを TanStack に登録すると React Flow には届かなくなる。逆に、同じ document に付いた監視どうしは `stopPropagation` では止まらない。

このため、「Space を押している間はドラッグで移動」のような操作は、React Flow 側のキーを `null` にして、TanStack の `useKeyHold('Space')` で押している間を取り、React Flow の `panOnDrag` を切り替える形にする。1 つのキーは片方だけが扱う。

**キーを二重に聞く可能性があるときは、それぞれが監視を付ける先（document か window か要素か）と、伝わりを止めるかの既定を並べてから割り当てる。**

### 3. alpha の印は、ダウンロード数より重く読む

TanStack Hotkeys は、週に約 112 万ダウンロードされている。一方で README の冒頭には alpha と書かれ、0.11 では型と既定の動作、0.12 では ESM だけへの切り替えと、短い間に互換性のない変更が 2 回入っていた。比べた react-hotkeys-hook 5.3.3 は 2019 年からの安定版で、依存が無く、大きさは min+gzip で約 2.9 KB だ。TanStack は約 10.7 KB で、依存が 3 つある。

それでも TanStack を推したのは、地図で要るもの（押している間の状態、ヘルプに出すキー一覧と `⌘ S` のような表示、入力欄の扱いの既定）が組み込みで、自分で書く部分が少ないからだ。その代わり、条件として版を固定し（`^` を付けない）、上げるときは CHANGELOG を読むことにした。この repo では、Effect の安定でないモジュールを使うときも同じように版を固定していて、それと揃えた。

**ダウンロード数は「使われている」ことしか示さず、API が安定していることは示さない。** alpha の依存を入れるときは、版の固定と、上げるときの手順を決めておく。

### 4. 「奪えるキー」と「奪ってよいキー」は別の問いにする

Chromium のソース（`IsReservedCommandOrKey`）で、ページに渡さずブラウザが先に取るキーを確かめた。予約されているのは、タブとウィンドウの開閉と切り替え、終了（`⌘W`・`⌘T`・`⌘Q` など）だけだった。ページ拡大の `⌘+`・`⌘-`・`⌘0` は予約されておらず、`preventDefault` で奪える。Safari と Firefox は確かめていない。

ただ、奪えることと奪ってよいことは別だ。奪うと、見ている人はブラウザの拡大（文字も含めてページ全体を大きくする手段）を使えなくなる。単独の文字キーのショートカットにも、WCAG 2.1.4 で「無効にできる・割り当てを変えられる・その部品に focus があるときだけ効く」のどれかが求められる。そこで調査では奪えるという事実だけを確かめ、奪うかどうかは、キーの一覧を決めるチケットで利用者に判断してもらう問いとして残した。

もう 1 つ分かったことがある。キーは focus のあるウィンドウにしか届かないので、会議アプリを触っている間は、このページのショートカットは効かない。

**調査では「できるか」を確かめ、「やるか」は仕様の問いとして次のチケットに渡す。** できることが分かると、そのまま採る方向に流れやすいからだ。

## 人が画面を動かした後に自動のカメラへ戻る条件を、試作を触りながら決めた話

前のエントリで作った地図の試作チケットを、設計者（利用者本人）と試作を触りながら決めた。問いは、人が画面を動かした後、**自動のカメラ**（反映のたびに今の議題へ寄る動き）にいつ・どう戻すかだ。あわせて、動かしている間の見せ方、人が縮められる下限、全体を見る操作の見え方も決めた。試作は、長い会議の画面を試したときの既存の試作ブランチの上に作った。161 分の合成会議のログを再生しながら、戻り方の 3 案（一定時間触らなければ戻る／今の議題が変わったら戻る／`Esc` を押すまで戻らない）を切り替えられるようにした。

結論は次のとおり。今の議題が変わるか `Esc` で戻り、時間では戻らない。動かしている間は、左下に控えめな文字を出し、画面の外で変わったノードの方向に縁の点を出す。人が縮められるのは 0.5 倍まで。全体を見る `F` は、**畳んだ**（済んだ議題の子孫を隠して 1 つにまとめた）まま全体を収める。右の列（変わったこと・根拠）は、マップを狭めて出す。

- 決定の記録: [人が動かした後に自動のカメラへ戻る条件と見せ方](https://github.com/daiki-beppu/live-mindmap/issues/285)、地図は [画面を人が動かす操作](https://github.com/daiki-beppu/live-mindmap/issues/153)

### 1. 戻るきっかけは、時間ではなく意味のある出来事に結びつける

初めは「10 秒触らなければ戻る」を既定にしていた。手を離せば必ず戻るので、共有画面が古い場所に留まり続けることがない。ただ、遠くの議題を読んでいる途中でも、10 秒たてば引き戻される。触っていないことと、読み終えたことは同じではない。

選ばれたのは「今の議題が変わったら戻る」だった。話が次の議題に移ったときは、共有画面を見ている参加者にとっても、映すべきものが変わったときだ。人が動かしている理由が残っている間は、引き戻さない。

**自動の振る舞いへ戻すきっかけは、経過時間ではなく、映すべきものが変わったという出来事にする。** 時間は「人が何をしているか」を表さない。

### 2. 動くものを狙うときは、補間中の位置ではなく目標の位置で測る

全体を見る `F` を押すと「挙動が怪しい」と言われた。再現すると、倍率が 1.1 → 0.63 → 0.10 → 0.07 と 4 段で跳ね、途中では 233 ノードのうち 203 個が画面の外にあった。原因は、React Flow の `fitView` が、新しい配置へ動いている途中の実際の位置で全体の箱を測っていたことだ。ノードの寸法が測れるたびに測り直していた。

自動のカメラは、もともと配置の目標の位置で狙っていた。全体を見るときだけ `fitView` に任せていたので、ここだけが崩れていた。目標の位置で箱を測るように揃えると、0.7 秒で一度に収まるようになった。

同じ確認で、もう 2 つ見つかった。全体を見ている最中にも「10 秒で戻る」が効いて勝手に戻っていた。左下には「動かしています」と出ていた。人が動かした状態と全体を見ている状態を 1 つの「自動ではない」状態として扱っていたためで、全体を見ている状態を別にした。

**アニメーションする配置にカメラを合わせるときは、描画中の位置ではなく目標の位置を使う。** ライブラリの「全体を収める」は、描画中の位置を測るものが多い。

### 3. 共有される画面では、手元の切り替えで他の人が読んでいるものを動かさない

右の列を出し隠しするキー `E` を足したところで、「隠したときに字幕がずれる」と言われた。字幕はマップの領域の中央に置いていたので、列（300px）を隠すと中央が 150px ずれて字幕が跳んでいた。この画面は会議アプリで共有され、参加者も字幕を読んでいる。

ここから 3 回やり直した。

1. 列をマップに重ねて出す形にした。マップの幅が変わらないので字幕は動かない。ただし、列で隠れる分を避けるため、自動のカメラが寄り直していた
2. 「`E` を押したらマップが動くようになった」と言われた。列の出し入れだけでは寄り直さず、列が今の議題を隠すときだけずらすようにした
3. 「列がマップに被る」と言われた。重ねるのをやめ、マップを狭めて出す形に戻した。そのうえで、字幕をウィンドウの中央に固定し、列にかからない幅に抑えた

重ねる案は、私が推した案だった。字幕が動かないことだけを見て、列の下にマップが隠れることを軽く見ていた。触って初めて分かった。

**共有画面の UI では、切り替えのたびに「何が動くか」を要素ごとに書き出し、他の人が読んでいるもの（字幕・マップ）は動かさない。** 1 つを止めると別のものが動き出すことがあるので、直すたびに全部を見直す。

### 4. キー入力は、日本語入力をオンにした実機で確かめる

キー一覧を出す `?` を足した。ブラウザの開発ツールから送ったキー入力（US 配列）では動いていた。ところが利用者の Mac（JIS 配列）では出なかった。日本語入力がオンのとき、`?` は全角の `？` か、入力の途中を表す `Process`（`code` は `Slash`）として届く。キーの値だけで判定していたので、どちらも素通りしていた。

全角の記号・英字と `Process` を半角のキーに直して解決した。原因を探しやすくするため、試作のバーに「最後に届いたキーの値」を出すようにした。もう 1 つ、試作のバーの選択欄を操作した後はフォーカスがそこに残り、キーがページに届かなくなっていた。操作の後にフォーカスを外すようにした。

**キーの処理は、日本語入力をオンにした実機で確かめる。** 開発ツールから送ったキー入力は、入力方式を通らない。届いたキーの値を画面に出しておくと、相手の環境で何が起きているかを一往復で切り分けられる。

### 5. 問題を解く新しい UI を足す前に、その操作がそもそも要るかを聞く

`F` の見え方には、どちらにも欠点があった。畳んだ議題も開いて収めると、161 分の会議では 0.07 倍になり、文字は約 1px で読めない。畳んだまま収めると、90 分時点で見えるノードは 13 個しかなく、今の議題に寄った画面とほとんど変わらない。そこで私は、第 3 の案として「議題名だけの縮図」を推した。

作ると、150 分時点の 84 件の議題が 1.05 倍で収まり、議題名を読めた。ところが利用者からは「これはおかしくない？」と言われた。議題を作られた順に並べていたため、一番上の階層の議題が、入れ子の議題（60 件ほどの写真の振り返り）の並びに割り込んでいた。親の議題は 1 列目の最後にあり、2〜5 列目は何の子かが分からなかった。木の順に並べ直している途中で、「縮図はいらないかな」と言われた。`F` は、最初の作りどおり畳んだまま収めることになった。

両案の欠点を埋める新しい画面は、それ自体の設計の問いを新しく抱える。今回なら、並べる順、親の見せ方、押したときの動きだ。私は欠点を埋めることばかり考えて、全体を見る操作にそこまで求められているかを確かめていなかった。

**既存の案の欠点を埋める新しい UI を推す前に、その操作がどれくらい要るかを先に聞く。** 欠点のある簡素な案で足りることがある。

### 6. 軸を固定するスクロールは、キーを分けずに動かし始めの向きで決める

「⌘＋Shift＋スクロールで、縦か横に固定できるか」と聞かれ、縦用と横用でキーを分けるべきかも相談された。分けずに 1 つの組み合わせにして、動かし始めの向き（縦と横の量の大きい方）で固定する形を勧め、その形でチケットの結論に入れた。250ms 指を止めたら向きを決め直す。

理由は 2 つある。覚えるキーが 1 組で済む。そして、縦のホイールしかないマウスで横に動かす手段は、「Shift＋ホイールで横」というブラウザと OS で広く使われている決まりで足りる。縦と横のキーを別に作ると、この決まりとぶつかるおそれがある。

**押す前に覚えてもらう割り当てより、操作から自動で判断する形を先に考える。** 判断の材料（ここでは指の動きの向き）が操作の中にあるなら、キーを増やさずに済む。

## ショートカットキーの一覧を決め、日本語入力でキーが捨てられる理由をライブラリの中で確かめた話

地図の次のチケットで、画面を人が動かす操作のショートカットキーの一覧を、設計者（利用者本人）との問答で決めた。土台は、前のエントリの試作で触ったキーの表だ。そこに、スクロールとドラッグの割り当て、後のチケットのために空けておくキー、ブラウザの拡大を奪うかを足した。問答の途中で、前のエントリで「未確認」として残していた点を、サブエージェント（調査を任せた別のエージェント）に TanStack Hotkeys（ショートカットキーのライブラリ）のビルド済みのソースで確かめさせた。日本語入力がオンのとき、キーがどう扱われるかという点だ。

- 決定の記録: [ショートカットキーの一覧](https://github.com/daiki-beppu/live-mindmap/issues/287)、地図は [画面を人が動かす操作](https://github.com/daiki-beppu/live-mindmap/issues/153)

### 1. 日本語入力でキーが効かないのは、ライブラリが意図して捨てているからのことがある。設定を探す前に、判定の流れを読む

前のエントリの試作では、日本語入力がオンの Mac で `?` が `Process` として届き、効かなかった。自前の処理で半角に直して解決した。ライブラリに載せ替えたらどうなるかは確かめずに残していた。

`@tanstack/react-hotkeys` 0.13.0 が依存するコア（`@tanstack/hotkeys` 0.11.0。npm の tarball には dist しか入っていない）を読んで、次のことが分かった。

- `event.key` が `Process` か `Unidentified` なら、変換中とみなす（`_keyboard-event.js:20`）
- 変換中のイベントは、1 文字のキーの登録とも、物理キー指定の `[KeyF]` の登録とも一致させない（`_match.js:14`）。上流のテストに「ignores printable hotkeys during composition」があり、意図した仕様だ
- この挙動を変えるオプションも、キーを正規化するフックも無い

試作では `?` だけの問題に見えていた。実際には、一覧の `F` `E` `C` `Z` `=` `-` `0` も、日本語入力がオンなら全部効かない。`Esc` と `Shift`＋矢印は 1 文字のキーではないので判定に進み、効く。

回避策は、ライブラリが聞いている `document` の手前で手を打つことだ。`window` の capture 段階で `Process`・変換中・全角（U+FF01〜FF5E）のキーを拾い、元のイベントを止める。そして `code`（`KeyF`・`Slash` など）から半角のキーを作った `KeyboardEvent` を、元の target に送り直す。ライブラリは `isTrusted` を確かめないので、これで受け付ける。ライブラリを替える案は採らなかった。変換中のキーを捨てるのは、文字を入力している最中にショートカットが誤って発火するのを防ぐための作りだ。他のライブラリは確かめていないが、替えても同じ問題に当たる見込みが高く、直す場所は変わらない。

**入力方式で効かないキーは、まずライブラリがそれを「捨てる」と決めているかを読む。** 意図した仕様なら、オプションを探しても見つからない。そのときは、ライブラリの外（イベントが届く前）で直す。

### 2. ライブラリの「救済」が生む余計な一致は、配列ごとに意味を確かめてから止めるかを決める

TanStack Hotkeys は、`event.key` が登録と合わないとき、`code` から作った文字で一致を取り直す（`_match.js:25-26`）。このため `=` の登録は、JIS 配列の `^` キーでも発火する。`^` キーの `code` が `Equal` だからだ。US 配列の `+`（`Shift`＋`=`）でも同じ理由で発火する。

初めは止めるべき副作用に見えた。ところが JIS 配列では `-` の隣が `^` で、US 配列では `-` の隣が `=` だ。どちらの配列でも、隣り合う 2 つのキーで縮小・拡大の組になる。止めると、JIS では拡大に `Shift` が要る。

そのまま使うことにした。キー一覧には `=` / `-` と書き、JIS では `^` でも効くと添える。

**ライブラリが意図せず生む一致は、すぐ止めずに、各配列でどのキーに当たるかを並べてから決める。** 物理的な位置で見ると、筋が通っていることがある。

### 3. 「修飾キー付きは一切受けない」という 1 本の規則で、ブラウザと会議アプリとの衝突がまとめて片づく

チケットには、ぶつかってはいけないものが並んでいた。ブラウザの既定のキーと、画面共有中の会議アプリのキー（Meet の `⌘D` など）だ。1 つずつ照らし合わせる代わりに、「⌘・Ctrl・Option と一緒に押したキーは受けない」と決めた。

- ブラウザの `⌘F`（検索）・`⌘C`（コピー）・`⌘+`（拡大）などは、そのままブラウザに残る。前のエントリで「奪えるか」を確かめたページ拡大も奪わない。奪うと、見る人が字幕や右の列まで含めて全体を大きくする手段が無くなる。代わりに、マップだけを拡大する `=` `-` `0` を自前で持つ
- 会議アプリのキーはどれも ⌘ 付きだ。そもそもキーは focus のあるウィンドウにしか届かないので、会議アプリを触っている間はこちらのキーは効かない

ライブラリも、押された修飾キーと登録の修飾キーを厳密に比べる（`_match.js:43-44`）。`F` の登録は、`⌘F` でも `Shift`＋`F` でも発火しない。規則をそのまま実装に写せる。

**衝突しうるキーを 1 つずつ数える前に、衝突の側がどんな形のキーを使うかを見て、その形を丸ごと避ける規則を立てる。**

### 4. 今の操作の割り当ては、後で来る操作が自然に使うキーやジェスチャを先に空けて決める

後のチケットで決める操作が 2 つある。キーでのノード選択と、人による議題の開閉だ。そのキーは今は決めず、空けておくかだけを決めた。矢印キー（Shift なし）は選択に、`Enter` は選んだ議題の開閉に空けた。画面の移動は `Shift`＋矢印にした。今どこかに割り当てると、後で外すことになり、覚えた人の手を裏切る。

同じ考えで、私の推しが外れた場面があった。ノードの上で始めたドラッグをどうするかだ。私は「ノードの上でも画面を動かす」を推した。長い会議ではノードが画面の大半を占め、ノードを避けて何もないところをつかむのは手間だからだ。ノードを動かすのはマップのデータを変える操作で、今回の範囲外だということも理由にした。利用者は「人間が編集できる機能を考えると」と言い、ノードの上のドラッグは何もしない形を選んだ。範囲外なのは今回の地図の話で、人がマップを直す操作は別のチケットで先に控えている。ノードをつかんで動かすのは、そのとき一番自然な形になる。今それを画面の移動に使うと、後で意味を変えることになる。ノードの上でもスクロールと ⌘＋クリックは効くので、移動に困ることはない。

**「範囲外」はその地図の外というだけで、製品から消えたわけではない。** 割り当てを決めるときは、範囲外にした操作が将来使いそうなキーやジェスチャも空けておく。

### 5. 共有される画面では、操作の手がかりを常には出さず、既にある表示に相乗りさせる

キー一覧（`?`）があることを、どう知らせるかも決めた。画面の隅に常に小さく `?` を出す案もあった。ただ、この画面は会議の参加者にも映る。そこで、前のエントリで決めた「動かしている間に左下に出す控えめな文字」に「`?` でキー一覧」を足すだけにした。一度でも画面を動かせば気づける。キー一覧そのものには、見つけにくいマウス側の操作（⌘＋スクロール、⌘＋クリックなど）も載せる。

**他の人にも映る画面では、手がかりを新しい常設の表示にせず、それが要る瞬間に出ている表示に混ぜる。**

## 見返しで時刻を動かす操作を、試作 3 案から YouTube 風に決め、シークバーを Video.js 10 に載せた話

**見返し**（会議の後に、マップがどう組み上がったかを、時刻を動かしながら見直すこと）のために、エクスポートに 1 ファイルの HTML を足す地図を進めている。今回はその試作チケットで、時刻を動かす操作（▶、コマ送り、シークバー、速さ、キー）を、設計者（利用者本人）と試作を触りながら決めた。素材は 161 分の合成会議のログで、AI がマップを差分更新した**反映**は 255 回、その中の**差分操作**（ノード 1 つの追加・更新など）は 574 件ある。

途中で 2 回、方向が変わった。自作で 3 案を作って見せたところ「このあたりはコンポーネントライブラリを使おう」と言われ、調査してシークバーを Video.js 10 の部品に載せ替えた。3 案から A（会議の時刻の軸）が選ばれた後には、「一般的な UI の方が認知負荷が少ない」として YouTube 風の並びに作り直した。結論は、A を元にした YouTube 風だ。議題ごとに区切った全幅のシークバー、反映 1 つ戻る・進むのボタン、会議の時刻の 10〜120 倍で進む ▶、YouTube に寄せたキー（Space・K／J・L／`,` `.`／`<` `>`／C）にした。

- 決定の記録: [見返し用のマップで時刻を動かす操作](https://github.com/daiki-beppu/live-mindmap/issues/300)、[見返しの操作に使うコンポーネントライブラリ](https://github.com/daiki-beppu/live-mindmap/issues/308)、地図は [会議の経過を見返せる HTML をエクスポートに足す](https://github.com/daiki-beppu/live-mindmap/issues/297)

### 1. 試作の案は「何を軸にするか」で分けると、選ぶ理由が数字で出る

3 案は、見た目ではなく、時刻を何で数えるかで分けた。

| 案 | シークバーの軸 | コマ送りの単位 | ▶ の進み方 |
|---|---|---|---|
| A 動画のように | 会議の時刻 | 反映 1 回 | 会議の時刻に比例（10〜120 倍） |
| B 反映の目盛り | 反映の回数 | 差分操作 1 件 | 1 件ずつ一定の間隔 |
| C 議題の章立て | 会議の時刻（議題ごとの帯） | 反映 1 回 | 反映 1 回ずつ一定の間隔 |

軸で分けたので、各案の弱いところが数字で見えた。B のコマ送りは、反映 1 回の中の 1 件ずつまで刻める。ただ、1 回の反映に入る差分操作は平均 2.25 件（574 ÷ 255）しかない。反映ずつのコマ送りと比べて、得るものが少なかった。C は議題を章として帯に並べた。前半は写真 1 枚ごとの振り返りで議題が 1〜2 分ずつ変わるため、帯は 66 本になった。幅 1,400px ほどの帯では、ほとんどの名前が読めなかった。A は、反映の無い時間（7 分の休憩など）も進む。それでも、後で録音を付けたときに `<audio>` の再生位置をそのまま使えるのは、この軸だけだった。

C を作る途中で、もう 1 つ外れがあった。「今の議題」（直近の反映で変わったノードが属する議題）で帯を切ると、話が議題を行き来するたびに数秒の切れ端ができた。45 秒未満の切れ端を前の章に含めて、ようやく帯の形になった。

**試作の案は、見た目の違いではなく、データのどの量を軸にするかで分ける。** そうすると、案の良し悪しを、実データの件数や長さで説明できる。

### 2. 操作の部品を自作し始める前に、ライブラリで作るかを先に決める

最初の試作では、シークバーも目盛りも帯も、`pointerdown` から位置を割り出す自作の部品で作った。見せたところ、返ってきたのは案の選択ではなく「このあたりはコンポーネントライブラリを使おう」だった。案を比べる前に、作り方の前提が違っていた。

調査（サブエージェントに任せた）の要点は次のとおり。Vite 8 と React 19 で、1 ファイルの HTML に部品だけを入れたページを作り、React だけのページとの差を測った。

| 入れたもの | 増えた量（gzip 後） |
|---|---|
| Radix の Slider だけ | +9.4 KB |
| Video.js 10 の汎用 Slider ＋ホバーの表示 | +18.6 KB |
| Video.js 10 のプレイヤー一式（`<audio>`・章つきのシークバー・再生・速さ） | +30.1 KB |
| 汎用の部品集（Radix・Ark・Base UI・React Aria）で選択メニューまで | +33〜64 KB |
| media-chrome（音声つき） | +43.5 KB |
| Vidstack（音声つき） | +97.5 KB |

選んだのは Video.js 10 の React 版（`@videojs/react` 10.0.1）だ。シークバーに要る、ポインタの位置の値を出す `Preview` と、章の帯 `Chapters` を持っている。見た目は持たない。もとは別々だった Vidstack・media-chrome・Plyr・Video.js の作り手がここに集まっていて、Vidstack は npm で非推奨になり、移行先として Video.js 10 を案内している（`npm view @vidstack/react deprecated` で確かめた）。選択メニューは部品集から入れると 20〜50 KB 増え、Video.js の速さの部品は 0.2〜2 倍に固定されている。そのため、▶・コマ送り・速さは素の `<button>` と自前のメニューのままにした。

Video.js 10 の 10.0.0 が出たのは、この 6 日前（2026-10-01）だ。版を固定して入れた。

**操作の部品は、自作で試作を作り込む前に、ライブラリで作るかどうかを決める。** 案を比べるのはその後でよい。

### 3. 見た目を持たない部品なら、同じ 1 つの部品で、まったく違う見た目の案を描ける

Video.js の汎用 Slider は、つまみの位置を `--media-slider-fill`、ポインタの位置を `--media-slider-pointer` という CSS 変数（%）で渡すだけで、何も描かない。そのため、3 案のシークバーを同じ部品で置き換えられた。A は細い線と点、B は反映ごとに差分操作を積んだ棒、C は章の帯で、違いは CSS と、トラックの中に置いた自前の要素だけだ。音声の無い今は、プレイヤーにつながない汎用の Slider に、自前の時刻を値として渡している。

YouTube 風にしたときも、部品はそのままだった。議題ごとに 2px のすき間で区切った区間と、決定・TODO の点を自前で置いた。ポインタを乗せたときにバーを太くしてつまみを出すのは、部品が付ける `data-pointing` の属性に CSS を当てるだけで済んだ。

**見た目を持たない部品は、試作で見た目の案を比べる段階と相性が良い。** 案を変えても、操作の作り（キー・ドラッグ・読み上げ）は変わらない。

### 4. スライダーを押した後はフォーカスを外し、矢印キーを画面の操作に返す

WAI-ARIA のスライダーは、つまみにフォーカスがある間、矢印キー・Home・End を受け取る。この画面では、矢印キーはノードの選択に空けてある（前のエントリのキー一覧で決めたこと）。シークバーを押した後にフォーカスがつまみに残ると、次に押した矢印でノードの選択ではなく時刻が動いてしまう。

シークバーの外枠の `onPointerUp` でフォーカスを外すようにした。Tab でつまみに来たときは、これまでどおり矢印で時刻を動かせる。

確かめる途中で、一度だまされた。開発ツールから `PointerEvent` を組み立てて送ると、25% の位置を押したはずが時刻が動かず、その後のポインタの移動で 60% の位置へ動いた。部品は、押した後の `pointerup` を別の要素で聞いているらしく、こちらが送った `pointerup` を受け取っていなかった。ドラッグが続いたままになっていた。Playwright の `page.mouse` で実際のマウス操作を流すと、3 案とも次のとおりに動いた。

- 25% を押すと 40:10 へ跳ぶ
- 50% から 75% へ引くと 120:30 になる
- 押した後のフォーカスは外れ、ただの矢印では時刻が動かない

**ポインタの操作は、組み立てたイベントではなく、実際のマウス操作（Playwright の `mouse` など）で確かめる。** 部品がどの要素で `pointerup` を聞いているかまでは、外から合わせられない。

### 5. 覚えることを減らしたいなら、みんなが知っている UI の並びとキーをそのまま借りる

A が選ばれた後、利用者は「一般的な UI が認知負荷が少なくていいかと思うので YouTube 風で」と言った。試作の A は、時刻とボタンを 1 行に詰めた独自の並びだった。YouTube 風に変えたのは次の点だ。

- シークバーを全幅にして、その下に操作の行を置く
- 章ごとにすき間で区切る
- ポインタを乗せると、上に「議題名／時刻」を出す
- 時刻は `2:40:42` のように時・分・秒で出す
- 速さは歯車のメニューにする

キーも YouTube に合わせた。Space・K で進める・止める、J・L で 10 秒戻る・進む、`,` `.` でコマ送り（ここでは反映 1 つ）、`<` `>` で速さ、C で字幕。C は、ライブの画面で既に字幕の出し入れに使っていたキーで、偶然そろっていた。矢印キーは YouTube なら 5 秒の移動だが、ここではノードの選択に空けたままにした。日本語入力がオンでも効くように、`、` `。` `＜` `＞` と入力中の `Comma`・`Period` も半角のキーに直している。

借りられないところもあった。YouTube の速さは 0.25〜2 倍だが、ここでは会議の時刻の 10〜120 倍で進める。161 分を 1 倍で見返す人はいないからだ。見慣れない単位なので、メニューの各項目に「60 倍（161 分を 2.7 分で）」のように、かかる時間を添えた。

**覚えることを減らすなら、独自の並びを工夫するより、多くの人が既に覚えている UI の並びとキーを借りる。** 意味がずれるところ（ここでは速さの単位）だけ、言葉を添えて補う。

### 6. 別の部品に同じ情報を出すときは、近似で作り直さず、マップと同じ値を使う

YouTube 風の操作の行には、今の議題名を出した。初めは、シークバーの区切りに使う章（短い切れ端を前の章に含めたもの）から名前を引いていた。確かめると、3:06 の時点で操作の行は「冒頭の雑談」、マップは「参加者紹介」の下の人の議題に寄っていた。章は帯を描くために切れ端を前の章へ寄せた近似で、マップのカメラが使う今の議題とは別物だった。

操作の行の名前は、マップと同じ今の議題から引くように直した。章は、シークバーの区切りとホバーの表示だけに使う。

**画面の別の場所に同じ意味の情報を出すときは、表示用に作った近似ではなく、主役の表示（ここではマップのカメラ）と同じ値を使う。** 近似は、ずれても気づきにくい。
