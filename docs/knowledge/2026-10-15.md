## 重い結合テストのどれを重いまま残すかを決めたとき、「何を使うか」で書いた層の定義が 36 件の取り違えを生んでいて、「確かめる値がどこで決まるか」に言い直し、終了コードは値ごとではなく仕組みごとに 1 件で足りた話

このプロジェクトのテストは 3 つの層に分かれている。unit（直接の依存がすべて偽物）、軽い IT（本物のファイルシステムや localhost の通信を使う結合テスト）、重い IT（本物の子プロセス・Chromium・音声処理のネイティブライブラリを通す結合テスト）だ。重い IT は遅く、手元で全件を流すと server だけで約 170 秒、web で約 94 秒かかる。一番重いのは CLI を子プロセスで 48 回起動するファイル（32 秒）で、HTTP の入口のファイル（24 秒）が続く。速くする地図を引き、最初のチケットで「何を重い IT に残し、何を下の層に移すか、消すか」を利用者と決めた。推奨を付けた問いを 2 巡で 9 問出し、利用者はすべて推奨どおりに選んだ。

- 決定の記録: チケット [heavy に残す契約の線引きと、移す・削るテストの振り分けを決める](https://github.com/daiki-beppu/live-mindmap/issues/1119)、地図 [heavy IT を、契約が越える境界だけに絞って速くする](https://github.com/daiki-beppu/live-mindmap/issues/1118)

### 1. 層の定義を「何を使うか」で書くと、準備に本物を使うだけのテストが重い層に流れ込む。「確かめる値がどこで決まるか」で書く

コーディング規約には、もともと「層は、テストが実際に越える依存の境界で決める」と書いてあった。ところが、層を作ったときの仕様とテストの手引きは、重い IT を「本物の子プロセス・Chromium・ネイティブの音声処理を**使う**テスト」と定義していた。HTTP の入口の 36 件はこの定義に従って重い IT に置かれた。準備の段で本物のサーバーと、偽のヘルパー（音声を取り込む別プロセスの代役）を子プロセスとして起動するからだ。

監査で中身を読むと、確かめているのは 400・403・404・409・500 の status、Origin の制限、argv の組み立てだけだった。どれも子プロセスに届く前に、server の中で値が決まる。4 件は子プロセスを 1 度も起動していなかった。偽のヘルパーで同じ入口を動かす準備は、軽い IT の側にすでにあった。

線引きは次の文に言い直した。

> 重い IT に置くのは、確かめる値が、子プロセス・OS のコマンド・ブラウザの描画やイベント・ネイティブの音声処理の境界を越えた後で初めて決まるものだけ。本物を準備に使っていても、確かめる値が境界の手前で決まるもの（HTTP の status、argv の組み立て、失敗型への写像、文面）は軽い IT か unit に置く。

原則が正しく書いてあっても、定義が「使うもの」の一覧になっていると、書く人はその一覧を見て層を決める。そこで、規約の側にも「準備に本物を使うだけでは重い IT にしない」の 1 文を足し、HTTP の 36 件を悪い例として名指しすることにした。**層の定義は、テストの準備ではなく、合否を決める値がどこで決まるかで書く。** 原則があっても取り違えが起きたら、迷う所を名指しで書き足す。

### 2. プロセスにしか無い契約は、値ごとではなく仕組みごとに代表 1 件で足りる

CLI を子プロセスで起動してしか確かめられないのは、終了コード、stdout と stderr への振り分け、色や改行を含む実際のバイト列、出力が 1 行にまとまることだけだ。文面は、同じプロセスの中で `runCli(argv)` を呼ぶ軽い IT で確かめられる。重い IT に残す代表は、`--help`（exit 0、stdout だけに出る）、引数の誤り（exit 1、help とエラーが一度だけ出る）、実行時の誤り（exit 1、stderr に 1 行）の 3 件にした。

1 巡目では、4 件目として「exit 3（開始に要るものが未導入）も子プロセスで確かめるべきか」を保留にしていた。0 と 1 があるなら 3 も要りそうに見えたからだ。調べると、終了コード 3 の値と stderr の全文は、軽い IT がすでに 5 つのファイルで確かめていた。CLI は `process.exitCode` に値を入れるだけで、プロセスの境界で起きるのは「その値がそのまま本物の終了コードになる」ことだけだ。この仕組みは 0 と 1 の代表がすでに通っている。

**境界をまたぐテストの代表は、出力される値の種類ごとではなく、境界で働く仕組みごとに数える。** 値の網羅は、境界の手前の層に任せる。

### 3. 同じ契約を 2 つの層で確かめていたら、上の層を消し、下の層に無い部分だけを移す

監査では、CLI の正解ファイル（評価に使う、正しいマップを書いたファイル）の誤り 12 件が、軽い IT でも確かめている文面を子プロセスで見ていた。web の Mount（画面と DOM の監視をつなぐ部品）のテストのうち 3 件は、純粋な関数の unit と同じ契約を Chromium で見直していた。どちらを残すかは、「一番小さい層に 1 つだけ置く」という規約の原則どおり、上の層を消すことにした。ただし、誤りが重なったときにどれを先に報告するかの順番は、子プロセスの側にしか無かった。これだけは軽い IT に移す。

下の層に移すときは、テストを足すときの基準（なぜ既存のテストでは捕まらないか）を当て直す。同じ分岐を入力だけ変えて繰り返すケースは 1 件にまとめる。ただし、サブコマンドごとの help のように、文面そのものが CLI の契約で、ケースごとに出力が違うものは残す。**層を移すときに、そのテストが今も足す基準を満たすかを確かめる。** 層だけ変えて全件を運ぶと、遅さは減っても重複が残る。

### 4. 本物のブラウザの中で合成のイベントを投げても、ブラウザは確かめられていない

web の重い IT には、マップの拡大縮小のジェスチャーを確かめる 2 件があった。どちらも Chromium と Vite を起動していたが、やっていたのは `new Event` で作ったイベントを要素に dispatch することだけだった。値は自前のハンドラの中で決まり、ブラウザがジェスチャーをどう届けるかは通らない。偽の要素で同じハンドラを動かす unit がすでにあった。その unit のコメントには「実ブラウザでの動作は未確認」と書いてある。

2 件は unit に移すことにした。そうすると「本物のブラウザでの確認」が無くなるように見えるが、もともと合成イベントでは確認できていなかった。本物のジェスチャーを確かめたいなら、それはブラウザを人のように操作する E2E の仕事になる。**重い道具を起動していることと、その道具の振る舞いを確かめていることは別だ。** 合否を決める値がどこで生まれたかで見分ける。

## 重い結合テストで Chromium と Vite を共有する単位を決めたとき、高い起動はファイルで 1 回にして独立は安い境界で保ち、製品の作りやテスト対象の経路はテストの都合で曲げなかった話

前のエントリで、重い IT（本物の子プロセス・Chromium・ネイティブの音声処理を通る結合テスト）に何を残すかを決めた。同じ地図の次のチケットでは、残ったテストが Chromium と Vite（web の画面を配る開発サーバー）を何回起動しているかを扱った。web の Mount のテストは、テストごとに Chromium を起動し直していた。会議中の画面で 24 回、見返しの画面で 13 回になる。server 側では、ローカルモードの表示のテストが Vite と Chromium の組を 5 回、マップの PNG を撮るテストが 8 回起動していた。推奨を付けた問いを 1 巡で 6 問出し、利用者はすべて推奨どおりに選んだ。

- 決定の記録: チケット [Chromium と Vite を共有する単位と、テストの独立の保ち方を決める](https://github.com/daiki-beppu/live-mindmap/issues/1120)、地図 [heavy IT を、契約が越える境界だけに絞って速くする](https://github.com/daiki-beppu/live-mindmap/issues/1118)

### 1. 高い資源はファイルで 1 回だけ起動し、テストどうしの独立は、その内側にある安い境界で保つ

Playwright には、ブラウザの起動（数百 ms〜1 秒）とは別に、`newContext`（cookie・storage・WebSocket の差し替えを分けた、ブラウザの中の独立した区画）がある。web の各テストは、もともと context を分けて作っていた。つまり、テストごとにブラウザを起動し直しても、独立はそれ以上強くなっていなかった。そこで、ブラウザはファイルの `beforeAll` で 1 回だけ起動し、テストごとに context を作って `finally` で閉じることにした。監査では、context を閉じる処理が `finally` の外にあることも見つかっていた。共有すると、この漏れがテストどうしの干渉になる。

共有の範囲をプロセス全体に広げる案（vitest の globalSetup で起動し、各ファイルから接続する）も比べた。重い IT のファイルは数本しかないので、上乗せで減るのは数秒にとどまる。その代わり、製品が使う起動の部品とは別の起動経路が、テストのためだけにできる。この案は採らなかった。

ブラウザが落ちると、そのファイルの残りのテストが連鎖して落ちる。これは許容した。落ちたこと自体は最初のテストで分かる。**独立は、一番高い資源ではなく、それより内側にある安い境界で保つ。** 内側の境界がすでにあるなら、外側を毎回作り直しても独立は強くならない。

### 2. 製品が呼び出しごとに起動して閉じる作りなら、テストのために共有の口は足さず、テストの数を減らす

マップの PNG を撮る製品の関数は、撮るたびに Vite と Chromium を起動して閉じる。会議の終わりに 1 回だけ撮るので、資源を持ち続けないのは製品として正しい。テストには「続けて 2 回撮れる」という 1 件があり、まさにこの、起動して閉じる作りを確かめている。

ブラウザを外から渡す口を製品に足せば、テストの起動は 1 回にできる。ただ、その口を使うのはテストだけだ。そのうえ、口を使ったテストは、製品が実際に通る「毎回起動する」経路を通らなくなる。そこで、口は足さずに、重複するテストを消すことにした。同じスナップショットを撮り直すテスト、別のテストに包含されるテスト、前のチケットで下の層に移すと決めた 2 件を外すと、起動は 8 回から 3 回ほどに減る。**資源の持ち方が製品の仕様なら、テストを速くする手は、その持ち方を変えることではなく、起動するテストの数を減らすことだ。**

### 3. 共有したサーバーの向き先をテストごとに変えるときは、確かめる経路の中にテストの書いた部品を挟まない

ローカルモードの表示の 2 本目と 3 本目は、テストごとに別の本物のサーバーを立てる。ブラウザは Vite の proxy を通して、そのサーバーの WebSocket につなぐ。Vite を共有するには、テストごとに向き先を変える必要がある。候補は 2 つあった。

| 案 | ブラウザからサーバーまでの経路 |
|---|---|
| Vite の proxy の向き先を、テストの頭で差し替える | ブラウザ → Vite の proxy → 本物のサーバー（今と同じ） |
| Playwright の `routeWebSocket` で、テストが書いた中継を挟む | ブラウザ → テストの中継 → 本物のサーバー |

3 本目は「WebSocket を閉じると張り直し、表示が戻る」ことを確かめている。中継を挟むと、張り直しを正しく扱うかどうかが、テストの書いた中継の出来に左右される。テストが落ちたときに、製品の誤りなのか中継の誤りなのかが分からない。前者を選んだ。Vite と Chromium の組は 5 から 1 になる。

共有したものにテストが状態を残すと、次のテストに漏れる。proxy の向き先がその例だ。そこで「テストが残す状態は、テストの頭で必ず設定し直す」をコーディング規約に足すことにした。後始末で戻す書き方だと、途中で落ちたテストが戻し損ねる。頭で設定する書き方なら、前のテストが何を残していても関係ない。**共有のために足す部品は、確かめる経路の外に置く。** 経路の中に置くと、テストが確かめる対象そのものが変わってしまう。

### 4. テストは、どのパッケージで書かれたかではなく、何を要するかで置く。移す前に、移す先の重なりを読む

server 側には、サーバーを 1 つも立てずに、`routeWebSocket` で画面に frame（server から届く 1 通のメッセージ）を送るだけのテストが 2 本あった。ローカルモードの線の色と文言、更新の一時停止の通知だ。web 側の会議中の画面のテストは、まったく同じ手法を使っていて、Vite も共有済みだった。server に置かれていたのは、server の機能を作ったときに一緒に書かれたからにすぎない。2 本は web へ移し、そこの Vite とブラウザを共有することにした。

移す前に、移す先のテストのコードを読んだ。web 側のテストは、ローカルモードの線の「再開中」と「停止」の色をすでに確かめていた。コメントには「線の色は server 側のテストが running を見る」とある。server 側の 1 本目で web 側に無いのは、running の色と文言だけだった。そこで、移すのは移す先に無い分だけにし、重なる部分は消すことにした。**置き場所を変えるときは、移す先をまず読む。** 重なりは、別々の場所に置かれていた間は見えにくい。

## 重い結合テストの実時間の待ちを縮めるとき、時計ではなく上限の値を差し替え、経過時間は上下で挟み、時間で隠していた製品の取りこぼしは別の issue に切り出した話

同じ地図の 3 つ目のチケットで、重い IT が実時間を待っている所を扱った。server で一番遅い 1 件（11.5 秒）は、ヘルパー（音声を取り込むネイティブの子プロセス）が SIGTERM を無視したときに、5 秒の上限の後で SIGKILL へ上げることを、stop と close の 2 つの経路で直列に確かめていた。ほかに、WebSocket の close の上限 3 秒、ヘルパーへの接続の再試行の 200ms、偽のヘルパーが録音を書き終えるまでの 300ms、見返しの画面のテストに 5 か所ある `waitForTimeout` が、待ちとして上乗せされていた。推奨を付けた問いを 1 巡で 7 問出し、利用者はすべて推奨どおりに選んだ。

- 決定の記録: チケット [実時間を待つテストの縮め方と、時間を注入する口の要否を決める](https://github.com/daiki-beppu/live-mindmap/issues/1121)、地図 [heavy IT を、契約が越える境界だけに絞って速くする](https://github.com/daiki-beppu/live-mindmap/issues/1118)、切り出した issue [見返しで、ノードを選んだ直後の Enter が開閉に効かない](https://github.com/daiki-beppu/live-mindmap/issues/1133)

### 1. 偽の時計で進まない待ちは、時計ではなく上限の値を差し替える。確かめる契約は値ではなく「上限の後に上げる」こと

server は Effect で書かれていて、テストでは TestClock（テストが時刻を進める偽の時計）が使える。それでも SIGKILL の待ちは縮められなかった。子プロセスを止める `forceKillAfter` は、Effect の時計ではなく Node のタイマーで測るからだ。テストのコメントにも「TestClock では進まない」とあり、このテストは実時間で 5 秒×2 回を待っていた。

候補は 3 つあった。上限の値を差し替えられるようにする、2 つの経路を並行に流して 6 秒ほどにする、今のまま残す、の 3 つだ。値を差し替える案を選んだ。上限は既定値つきの `Context.Reference`（Effect の、既定値を持ち、必要なときだけ外から上書きできる依存）にする。製品の配線は既定値のままで変わらず、テストだけが 300ms ほどを与える。WebSocket の close の上限 3 秒も同じ形にする。

この案で決め手になったのは、テストが確かめたい契約が何かだ。契約は「SIGTERM を無視されたら、上限の時間の後に SIGKILL へ上げる」で、5 秒という値そのものではない。値は定数で、読めば分かる。**偽の時計が届かない待ちは、時計を偽るのではなく、待つ長さを差し替える。** 確かめるべきは、長さではなく、その長さの後で何が起きるかだ。

### 2. 待ちの長さを縮めたら、経過時間は上と下の両方で挟む

元のテストは、経過時間が「上限＋3 秒未満」であることだけを見ていた。上限が 5 秒あると、上の側だけでも意味がある。待たずにすぐ SIGKILL する誤りがあっても、それはそれで早く終わるので、上の側の検査では落ちない。上限を 300ms に縮めると、この見逃しが目立つ。300ms 待ったのか、すぐに殺したのかは、上の側だけでは区別できない。

そこで、「上限以上」と「上限＋2 秒未満」の両方で挟むことにした。下の側で、待たずに上げる誤りを落とす。上の側で、いつまでも待つ誤りを落とす。経過時間の検査を外して vitest の時間切れに任せる案もあったが、それだと下の側の誤りを見逃す。**待ちを縮めるときは、縮めた値が「待った」ことの証拠として足りるかを見直す。** 長い待ちの間は暗黙に成り立っていた区別が、短くすると消える。

### 3. テストのための口を増やす前に、製品の値そのものを、本物にとっても良い形にできないか見る

ヘルパーへの接続の再試行は、製品のコードに `Schedule.spaced("200 millis")` と書かれていた。偽のヘルパーはすぐに待ち受けを始めるので、ほとんどのテストで、初回の失敗のたびに 200ms が上乗せされる。上限と同じように差し替える口を足す案もあったが、選ばなかった。10ms から始めて 200ms で頭打ちになる、指数で間隔を広げる再試行に変えることにした。本物のヘルパーも、準備ができた直後に早くつながる分だけ得をする。テストのための口も増えない。

偽のヘルパーが録音を書き終えるまでの 300ms は、テストの中の値なので、50ms ほどに縮めるだけにした。この待ちは「サーバーが録音の書き終わりを待ってから読む」ことを確かめるためにある。遅れて書き終わるという形は残す。長さは、待たずに読む誤りが偶然通らない程度があれば足りる。

### 4. 「待っても変わらない」を時間で確かめているテストは、変わらないことを保証しているのが誰かを見る

見返しの画面のテストには、待っても変わらないことを合格の条件にしている所が 2 か所あった。1 つは、一時停止の後に 500ms 待って、音声の再生位置が進まないことを確かめていた。一時停止中の `<audio>` の再生位置が進まないのは、ブラウザの責務だ。製品の契約は「Space で一時停止する」までで、それは直前の `paused` を待つ行ですでに確かめている。500ms の待ちは消し、`paused` を見るだけにした。

もう 1 つは、操作の後に 300ms 待って、点滅（変わったノードを知らせるアニメーション）が再生し直されないことを確かめていた。その直前に、画面の表示範囲が落ち着くまで待つ処理と、動いているアニメーションが無いことの確認があり、それで足りる。この 300ms も消した。**変わらないことを時間で確かめるテストは、待ちを短くするほど弱くなる。** 縮める前に、その不変を守っているのが製品なのか、ブラウザなのか、すでにある別の確認なのかを見る。

逆に、何かが起きるのを時間で待っている所は、起きたことを観測できる値を待つ形に変える。点滅が最初から再生し直されるのを 500ms 待っていた 2 か所は、新しい Animation が始まった、または再生位置が巻き戻った、を待つ形にする。表示範囲が落ち着くまで待つ処理は、50ms 間隔で 4 回同じ値を読むまで待っていて、1 回で最低 200ms かかった。同じ実装が 3 か所にあった。これも 1 つにまとめ、`requestAnimationFrame` の数フレームで安定を見る形にする。見たいのは補間が止まったことなので、描画のフレームが単位として実態に合う。

### 5. 時間の待ちが製品の取りこぼしを隠しているなら、テストの側で繰り返して隠さず、別の issue に切り出す

最後の 1 か所は、ノードをクリックで選んだ後に 500ms 待ってから Enter を押していた。コメントには「キーの Subscription（キー入力を受け取る購読）が、選択ありの設定で張り直されるのを待つ。直後の Enter は選択なしの設定で流れて、開閉にならない」とある。

テストを速くするだけなら、Enter を押して畳まれるまで繰り返す形にもできた。しかし、コメントが書いているのは製品の振る舞いだ。人がノードを選んだ直後に押した Enter が、古い設定のまま解釈されて効かない。テストの側で繰り返すと、この取りこぼしを見えなくする。そこで、これはテストの問題ではなく製品の問題として、地図の外に issue を切り出した。テストは、製品が直るまで今のまま残す。直ったら待ちを消す。

ただし、この issue はコードのコメントを根拠にした疑いの段階で、実機ではまだ確かめていない。issue にもそう書いた。**テストの中の固定の待ちは、何を待っているのかをコメントから読む。** 待っている相手が製品の内部の遅れなら、それは利用者も踏む遅れかもしれない。

<a id="heavy-it-screen-compare"></a>

## 移行の受け入れのために作った画面の照合テストを、移行が終わった後にどうするか決めたとき、比べる相手が消えたテストは自分どうしの比較になっていて、消す前に「おまけで見ていたこと」と「ほかのテストが任せていたこと」を拾った話

同じ地図の 4 つ目のチケットで、web の重い IT のうち 2 番目に遅いファイル（約 29 秒）を扱った。見返しの画面（会議の後にマップと録音を振り返る画面）を headless Chromium で 2 枚開き、同じ操作を 20 ステップ流して、表示範囲・`<audio>` の状態・スクリーンショットのピクセルが全ステップで一致するかを比べるテストだ。比べる道具（2 つのページに同じ操作を流して差を報告する関数と、操作の列）を使うのはこのファイルだけだった。問いは「消すか、1 本に縮めるか」。推奨を付けた問いを 1 巡で 2 問出し、利用者は推奨どおりに選んだ。

- 決定の記録: チケット [画面の照合の heavy IT を消すか縮めるか決める](https://github.com/daiki-beppu/live-mindmap/issues/1122)、地図 [heavy IT を、契約が越える境界だけに絞って速くする](https://github.com/daiki-beppu/live-mindmap/issues/1118)

### 1. 残すか決める前に、そのテストを作った issue の受け入れ条件を読み、守っていた相手がまだいるかを見る

テストの冒頭のコメントは「同じ操作が同じ値になること（揺れない）と、道具がスタイルの差・ビューポートの差を見逃さないことを保つ」と書いていた。これだけ読むと、決定性を守るテストに見える。起点の issue を読むと、目的は違った。画面を React から Foldkit（Effect の上に作られた UI フレームワーク）へ書き換えるときに、各画面を切り替える段の受け入れに使うテストだった。受け入れ条件は「React 版どうしを比べて一致する（違うピクセルが 0.05% 以下）」「わざと違えた版で不一致を報告する」。比べる相手は、移行前の版だった。

移行が終わって React 版が消えた後、テストは比べる相手を Foldkit 版自身に差し替えて生き残っていた。同じビルドを 2 枚開いて比べるので、確かめているのは「同じ入力で同じ出力になる」ことだけだ。この性質を頼りにしている契約は、製品のどこにも無かった。**移行のために作ったテストは、移行が終わると、比べる相手を自分に差し替えて残りやすい。** コメントは差し替えた後に書き直されるので、元の目的は起点の issue の受け入れ条件にしか残っていない。

1 本に縮める案も比べたが、選ばなかった。縮めても、守る相手のいない性質を 1 本分の時間で確かめ続けるだけだからだ。また照合が要る移行が来たら、道具は git の履歴から戻せる。道具がわざと違えたページを見逃さないかの自己点検 2 件も、道具と一緒に消える。

### 2. 消す前に、比較のおまけで確かめていたことを洗い出し、ほかの層に無いものだけを拾う

このテストは一致を見るだけでなく、「何も起きなくても通るテストにしない」ために、操作の前後で表示範囲が実際に変わったことも確かめていた。ホイールでパンすると位置が動く、⌘＋クリックで倍率が上がる、Ctrl＋ホイールのピンチで倍率がさらに上がる、ドラッグで動く、Space で再生が始まる、といった検査だ。本物のブラウザに本物の入力を送って、値が動くことを見ている。前のチケットで決めた線引き（確かめる値が、ブラウザの描画やイベントの境界を越えた後で初めて決まるものだけを重い IT に置く）に当たるのは、比較ではなく、こちらの付けたしの方だった。

そこで、消す前に、付けたしの検査をほかのテストと 1 つずつ突き合わせた。ホイールのパン・Ctrl＋ホイールのピンチ・ドラッグ・キー入力は、会議中の画面の重い IT が、見返しと同じ表示面の部品で確かめていた。再生・停止と End で終わりへ飛ぶことは、見返しの重い IT にあった。ほかに無かったのは ⌘＋クリックの拡大だけだった。これを 1 件、会議中の画面の重い IT に足すことにした。表示面は 2 つの画面で共有なので、置き場所は見返しでなくてよい。

`<audio>` の速さ・ミュート・シークも、このテストにしか無かった。それでも足さないことにした。playbackRate と muted は、製品のコードが書いた値をブラウザから読み返しているだけで、値は境界の手前で決まる。**ほかに無いことは、拾う理由の半分でしかない。** 拾うのは、ほかに無く、しかも境界の向こうで決まる値だけにした。

### 3. ほかのテストのコメントが「それはあのテストが見る」と任せていないかを grep する

道具やテストの名前でリポジトリを検索すると、テスト自身のほかに 2 か所、コメントで名前が出てきた。ポインタの購読の unit テストは「ドラッグで表示範囲が実際に動くことは、画面の照合の heavy IT が見る」と書き、操作の行の軽い IT は「実ブラウザでの見た目は、画面の照合の heavy IT が見る」と書いていた。どちらも、自分が確かめない部分を、消そうとしているテストに任せていた。

ドラッグは、会議中の画面の重い IT がすでに見ていたので、穴にはならない。ただ、コメントを残したまま消すと、次に読む人が、存在しないテストを探すことになる。2 か所のコメントは、実際に見ているテストの名前に書き直す。**テストを消すときは、そのテストが確かめていたことに加えて、ほかのテストがそのテストに任せていたことも消える。** 任せていた側は import ではなくコメントでつながっているので、型の検査では見つからない。名前で grep して見つける。

道具を書いたファイルにも、同じ形のつながりがあった。2 つの画面の重い IT は、比較の関数は使わず、ブラウザを起動する関数と型だけをこのファイルから import していた。題材のログのファイル名も、照合の名前のまま、ほかのテストが使っていた。比較の部分は消し、ほかが使う部分は残す。残す型の置き場所や、ログの名前を変えるかは、実装のチケットに任せた。

<a id="heavy-it-real-install"></a>

## 本物の導入を通す重い結合テストを縮めるとき、遅そうな 3 本のうち実際に遅いのは 1 本だけで、CI のステップも確かめの 1 つに数え、「重複だから消す」は下の層が本物を使っているかまで見て 1 つ前の決定を改めた話

同じ地図の 5 つ目のチケットで、本物の導入を通す重い IT を扱った。このアプリは、重い依存（差分更新に使う Claude Agent SDK と、map.png を撮る Chromium）を通常の依存から外している。利用者の手元の管理ディレクトリに、アプリが固定した版を、使うときだけ入れる作りだ。この導入を本物の `npm ci` や Playwright で確かめる重い IT が 3 本ある。Chromium の導入（2 件）、開発用の `pnpm install` で SDK のプラットフォーム別バイナリが入らないことの確認、SDK の導入だ。問いは「契約を落とさずに、導入の回数と範囲をどこまで減らすか」。推奨を付けた問いを 1 巡で 4 問出し、利用者はすべて推奨どおりに選んだ。

- 決定の記録: チケット [本物の導入を通す heavy IT の導入回数と範囲を決める](https://github.com/daiki-beppu/live-mindmap/issues/1123)、地図 [heavy IT を、契約が越える境界だけに絞って速くする](https://github.com/daiki-beppu/live-mindmap/issues/1118)

### 1. 「本物の導入」という名前で遅いと決めつけず、問いを立てる前に 1 本ずつ測る

監査は 3 本を「本物の導入」として 1 つの節にまとめ、それぞれに縮める案を添えていた。`pnpm install` はワークスペース全体ではなく `--filter @live-mindmap/server...` に絞る、といった案だ。ファイルごとの時間が分かっていたのは、Chromium のファイル（約 25 秒）だけだった。

問いを出す前に、残りの 2 本を手元で流した。

```sh
pnpm exec vitest run --project heavy test/sdkDevelopmentInstall.heavy.test.ts test/managedClaude.heavy.test.ts --reporter=verbose
```

`pnpm install` のテストは 1.7 秒、SDK の導入は 3.3 秒だった。pnpm のストアと npm のキャッシュが温まっていれば、導入はほとんどリンクを張るだけで終わる。`--filter` の案も、一時ディレクトリに lock と各 `package.json` を写して比べた。入るパッケージは 235 から 169 に減ったが、時間はどちらも約 1 秒だった。遅いのは、Chromium を別々の一時ディレクトリに 2 回ダウンロードしていることだけだった。

測ったので、絞る案は「速くならないから取らない」と、数字を添えて推奨できた。**名前が同じ種類のテストでも、遅さの原因は 1 本ずつ違う。** 縮める案を出す前に測り、遅くないものは範囲の話だけにする。

### 2. CI のステップも確かめの 1 つに数える。ただし、キャッシュに当たって何もしない日がいつかを見ておく

Chromium の 2 件のうち、1 件は開発用のスクリプトで導入し、再実行しても実体が変わらないことを見ていた。もう 1 件は、常駐サーバー経由の `cli install` で導入して、固定版と headless shell が入ったことを見たうえで、会議を止めて map.png を撮る。

CI の重い IT のジョブを読むと、テストより前に、同じ開発用スクリプトで Chromium と SDK を入れるステップがあった。入れた結果は `actions/cache` に残し、キャッシュのキーは同梱の lock のハッシュにしてある。lock が変わればキャッシュに当たらず、ステップが本物の導入を流す。版を上げて導入が一番壊れやすいのは、ちょうどその時だ。さらに、再実行で再導入しないことは、偽の npm を使う軽い IT が確かめていた。そこで、開発用スクリプトの重い IT は消し、本物の導入は利用者の経路の 1 回だけにした。

一方で、キャッシュのキーに入っていないもの、たとえば導入のコードだけを変えた日には、ステップはキャッシュに当たって何もしない。その日にも本物の導入を通すのが、残した 1 件だ。毎回新しい一時ディレクトリに入れるので、キャッシュに左右されない。**CI のステップはテストの代わりになるが、キャッシュのキーに入っていない変更に対しては空振りする。** どの変更で空振りするかを見たうえで、テストを消すか決める。

### 3. 「下の層と重複するから消す」と決める前に、下の層が本物と偽物のどちらを使っているかを読む

この地図の最初のチケットで、SDK の導入テストの後半は「軽い IT と重複する」として消すと決めていた。後半は、導入した実体から `deps.load("claude")` で SDK を読み込み、`query` が関数であることを見る。軽い IT も同じ関数を呼んで同じことを見ているので、名前と呼び出しだけを見れば重複だった。

今回、その軽い IT を読み直すと、読み込んでいたのは、テストが書き出した数行の偽の `sdk.mjs` だった。本物の SDK のパッケージ（exports の書き方、ESM かどうか、依存）を管理ディレクトリから評価できることを確かめているのは、消すことにした後半の数行だけだった。このプロジェクトには前例もあった。Chromium の読み込みで、vitest が CJS の default を名前付き export として補ってしまい、本番では落ちる不具合が隠れたことがある。そのため Chromium の読み込みは、素の Node プロセスで確かめる重い IT にしてある。

そこで前の決定を一部改めた。本物の SDK を読み込む 2 行は残し、消すのは、SDK をアプリのサービスに組み込む所だけにした。改めたことは、前のチケットにもコメントで追記した。後から仕様を書く人が、古い決定だけを読んで消さないようにするためだ。**同じ関数を呼んでいても、下の層が偽物を読み込んでいるなら、本物の形を確かめる部分は重複ではない。** 重複かどうかは、何を呼ぶかではなく、何を通して値が決まるかで見る。

同じ見方で、逆向きの例もあった。`pnpm install` のテストの後半は、SDK の型を使う小さなファイルを `tsc` で型検査していた。こちらは、本物のインストールの上で流す `pnpm typecheck` が、製品のコードで同じ型を使っている。下の層も本物を通しているので、本当に重複していた。消した。

<a id="heavy-it-helper-audio"></a>

## ネイティブの音声処理の重い結合テストを縮めるとき、並行に流れる中では一番長い 1 本だけが壁時計を決め、因果的な処理は使う窓の後ろを切っても結果が変わらず、既定の引数はテストで守らずに外した話

同じ地図の 6 つ目のチケットで、helper の重い IT を扱った。helper は、会議の音声を取り込んで文字にする macOS のネイティブのプログラム（Swift）だ。重い IT では本物の音声処理を通す。WebRTC のエコーキャンセラ AEC3（スピーカーから出てマイクに回り込んだ相手の声を消す）、Sortformer（誰が話したかを分ける話者分離のモデル）、Apple の SpeechAnalyzer（音声認識）の 3 つだ。監査の指摘は 3 つあった。AEC3 で合計約 166 秒分の音声を処理していること、モデルをテストごとに読み直していること、既定の引数を AEC3 の出力の一致で確かめている 1 件があること。推奨を付けた問いを 1 巡で 4 問出し、利用者はすべて推奨どおりに選んだ。

- 決定の記録: チケット [helper の heavy で処理する音声の長さとモデルの読み込みを決める](https://github.com/daiki-beppu/live-mindmap/issues/1124)、地図 [heavy IT を、契約が越える境界だけに絞って速くする](https://github.com/daiki-beppu/live-mindmap/issues/1118)

### 1. テストが並行に流れるなら、壁時計は一番長い 1 本で決まる。共有で全体を削るより、その 1 本を割る

手元で流す前に、CI の main の helper ジョブのログから、テストごとの時間を取り出した。Swift Testing は、テストの開始と終了をそれぞれ 1 行ずつ出すので、grep で拾える。

```sh
gh run view --job <job-id> --log | grep -E "✔ (Test|Suite)|Test run with"
```

重い IT は全体で 58 秒だった。ほかのテストが 33 秒以内に終わる中、AEC3 の「開始直後の残り方」の 1 件だけが 58 秒かかっていた。このテストは、発話が始まる秒を 1・2・3・5 と変えて、20 秒の音声を 4 回直列に処理していた。Swift Testing は既定でテストを並行に流すので、ほかのテストはこの 1 件の裏で終わっている。

これで、監査のもう 1 つの指摘の重みが変わった。Sortformer のモデルを 2 件のテストで 1 回の読み込みにまとめても、その 2 件はもともと並行に流れていて、壁時計はほとんど縮まない。代わりに、テストの間に状態の結びつきができ、読み込みに失敗したときにどのテストのせいかが見えにくくなる。そこで、読み込みは共有しないことにした。一番長い 1 本は、発話の開始秒ごとに別のテスト（`@Test(arguments:)`）に分けて並行に流す。**並行に流れるテスト群で遅さの原因を探すときは、合計の時間ではなく、一番長い 1 本を見る。** 合計の時間を減らす共有は、CPU は節約できても、壁時計にはほとんど効かない。

ただし、CI の macOS ランナーはコア数が少ないので、4 つに分けても 4 倍速くはならないかもしれない。58 秒が 15〜20 秒程度になるという見込みはまだ測っていない。実装の PR で、変更の前後の時間を同じ条件で測ることにした。

### 2. 因果的な処理なら、使う窓より後ろの入力を切っても結果は変わらない。縮めても判定が変わらない根拠を、処理の性質から出す

このテストは、発話が始まった直後の 1 秒の残り方を、定常（15〜16 秒目の 1 秒）の残り方と比べる。20 秒の音声を処理しているが、使うのは 16 秒目までだ。AEC3 は過去の入力だけを使って出力を決める（因果的）。だから、16 秒＋出力の遅れの分（最大 20 ms）で処理を止めても、比べる 2 つの窓の出力は 20 秒流したときと同じになるはずだ。長さを縮めても、テストの判定はそのまま保てる。これは推論なので、実装のときに前後の出力が一致することを確かめる。

一方で、定常の窓を 15 秒から 5 秒に前倒しする案は取らなかった。前倒しすれば処理はもっと短くなるが、「定常」として比べる基準そのものが変わってしまう。このテストは、AEC3 の既定の設定が話し始めの声まで削ってしまう問題（初期のバグ）を、設定を変えて直したことの回帰を見ている。**縮めるときは、判定に使う入力の範囲を変えずに、使わない部分だけを削る。** 使う範囲まで動かすと、速くなった代わりに物差しが変わり、何を守っているテストなのかが曖昧になる。

同じファイルでは、出力の遅れ（`measureOutputDelay`）を、処理のたびに 2 秒分の音声で測り直していた。入力が決まっている決定的な計算なので、ファイルで 1 回だけ測って使い回す。

### 3. 既定の引数が正しい値に届くことをテストで守るより、既定の引数を外して、呼び出し側で値を明示する

監査が「unit にするか削除」と書いていた 1 件は、`WebRTCEchoCanceller()`（引数なし）と `WebRTCEchoCanceller(settings: .production)` に同じ 20 秒の音声を流し、出力が一致することを確かめていた。守りたいのは「本番の経路が本番の設定で AEC3 を作る」ことだ。本番の経路では、引数を省いて既定の値に任せていた。

コードを読むと、引数を省いて呼んでいるのは本番の経路の 1 か所だけだった。そこで第 3 の案を出した。既定の値を外し、本番の経路で `.production` と書く。こうすれば、設定を書き忘れた呼び出しはコンパイルで止まる。テストは、確かめる対象（既定の引数）がなくなるので消せる。unit に移す案は取れなかった。設定は AEC3 の中に渡ったきりで外から読めないうえ、この repo の層の検査は、unit のファイルが本物の `WebRTCEchoCanceller(` を作ると失敗させる。**テストが既定の値の正しさを守っているなら、まず既定の値をなくせないかを見る。** 型やコンパイラが守れることをテストで守ると、遅いうえに、守れるのは書いたケースだけになる。

## テストの層の取り違えを機械的な点検で防げるか考えたとき、きっかけの取り違えをその点検にかけると通ってしまい、「使ってはいけない」は点検できても「使っていなければならない」は点検しにくいと分かって、点検を広げなかった話

同じ地図の 7 つ目のチケットで、層の取り違えがまた入らないように、型検査（`pnpm typecheck`）の中で動く層の点検を広げるかを決めた。今の点検は 2 つある。server と web の点検は、unit のテストファイルが本物の資源（`node:fs`・`node:net`・`ws`・`playwright` など）を import していたら失敗させる。helper（Swift）の点検は、unit のファイルに本物の音声処理を作るコードが書かれていないか、テストの型名とファイル名の層が合っているかを見る。重い IT に重くないテストが入ることは、どちらも検出しない。1 つ目のエントリで決めた線引きは「確かめる値が、子プロセス・OS のコマンド・ブラウザ・ネイティブの音声処理の境界を越えた後で初めて決まるものだけを重い IT に置く」だ。これを機械的に検出できないかを考えた。推奨を付けた問いを 1 巡で 3 問出し、利用者はすべて推奨どおりに選んだ。

- 決定の記録: チケット [層の取り違えを防ぐ点検を広げるか決める](https://github.com/daiki-beppu/live-mindmap/issues/1125)、地図 [heavy IT を、契約が越える境界だけに絞って速くする](https://github.com/daiki-beppu/live-mindmap/issues/1118)

### 1. 点検を足す前に、きっかけになった取り違えをその点検にかけてみる

チケットの手がかりには、点検の案が 1 つ書いてあった。「重い IT のファイルが、子プロセス・Chromium・OS のコマンドのどれも使わなければ失敗させる」。この地図を引くきっかけは、HTTP の入口の重い IT にあった 36 件の取り違えだった。どれも、HTTP の status や引数の組み立てのように、境界の手前で決まる値を確かめていた。ところがこのファイルは、本物の Helpers（helper の子プロセスを立てる部品）とサーバーの起動を準備に使っていて、子プロセスにはちゃんと届いている。つまり、案の点検にかけても通ってしまう。

取り違えは、ファイルの単位ではなく、テスト 1 件ごとに起きていた。同じファイルの中に、境界を越えた後の値を見るテストと、手前の値を見るテストが混ざっている。「確かめる値がどこで決まるか」は、import の字面からは読めない。**点検を足すときは、まずその点検を作るきっかけになった実例を手でかけてみる。** その実例が通ってしまう点検は、保守の手間がかかるうえに、守りたいものを守らない。

### 2. 「使ってはいけない」はファイルの中だけで判定できるが、「使っていなければならない」はたどる先が広がる

今の unit の点検がうまく働いているのは、規則の向きのおかげだ。「本物の資源を import してはいけない」なら、そのファイルの import を 1 つ見つければ違反だと言える。ほかのファイルを読む必要はない（間接の利用は拾わないと割り切っている）。

逆向きの「境界を使っていなければならない」は、そうはいかない。重い IT が境界に届く道を数えると、3 通りあった。

| 届き方 | 例 |
|---|---|
| テストのファイルが直接 import する | `node:child_process`・`ws` |
| 製品のコード（`src`）を通す | 画像を JPEG にするモジュールが macOS の `sips` を、音声を混ぜるモジュールが `ffmpeg` を呼ぶ |
| テストの実行設定で届く | web の重い IT は vitest のブラウザモードで動くので、ファイルは `vitest` しか import していない |

これを検出するには、import をたどって境界に届く `src` のモジュールの一覧を持つか、ファイルごとの除外の一覧を持つしかない。どちらも、このプロジェクトのテスト規約が避けている「import やファイルの置き場所を契約にする」ことにあたる。`src` の作りを変えるたびに、一覧も直すことになる。**禁止の規則はファイルの中だけで判定できるが、必須の規則は依存をたどる範囲を決めないと判定できない。** 点検にしやすいのは前者だ。

### 3. 点検に頼らない守りには、すでにあるゲートの言い直しを足さない

点検の代わりに、重い IT を足すときは PR の本文に「境界を越えた後で決まる値」を 1 行書かせる、という案も出した。しかし、このプロジェクトのテスト規約には、テストを足す前に示す 5 つの証拠（Evidence gate）がすでにあり、その 1 つが「その契約を持てる最も小さい層」だ。重い IT のときだけ同じことを別の場所で求めても、言い直しにしかならない。守りは、1 つ目のエントリで決めた文書の変更に任せる。層の定義を「確かめる値がどこで決まるか」で書き直し、テスト規約に「準備に本物を使うだけでは重い IT にしない」を足して、HTTP の入口の 36 件を悪い例に挙げる。あとはレビューで見る。**機械で守れない規則は、規則を書く場所を 1 か所に保ち、悪い例を添えて、読む人に届く形にする。**
