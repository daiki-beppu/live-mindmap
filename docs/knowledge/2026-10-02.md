## 会議の音声を流しっぱなしにする「ライブのセッション」を、AI エージェントのワークフローに実装させた話

本物の会議でマップを組み立てる経路をつないだときの学び。それまでは、録音済みの文字起こしを流し直す**再生**でしかマップを作れなかった。今回、`pnpm dev` の 1 コマンドでサーバーが音声文字起こしのヘルパー（Swift の常駐プロセス）を子プロセスとして起動し、CLI の `start --app <会議アプリ>` / `stop` で、会議の音声を**発言**（音声認識が確定させた文字起こしの 1 区切り）として再生と同じ経路に流すようにした。**セッション**は、1 つの会議について開始から終了までマップを組み立てる一続きの作業のこと。終了時には md・json・Drawnix の 3 形式で書き出す。

- 決定の記録: [ライブのセッション](https://github.com/daiki-beppu/live-mindmap/issues/35)、[音が出ないままセッションを終えると、cli stop が戻らない](https://github.com/daiki-beppu/live-mindmap/issues/70)、[ADR 0003 ローカルの Node サーバーがパイプラインを持つ](../adr/0003-local-node-server-owns-pipeline.md)

takt の実行は 56 分、工程の数で 19 回、レビューでの差し戻しは 2 周だった。

### 1. 取り消せない副作用は、成功が確定するまで外に出さない

1 回目のレビューで、5 件の指摘のうち 3 件が採用された。そのうち 1 件は、**開始に失敗すると、前の会議のマップが空のマップで上書きされる**というものだった。

実装は、セッションを作った時点で、ルートだけの空のマップをブラウザへ配信していた。そのあとでヘルパーへの接続に失敗すると、セッションのフォルダは消して元に戻す。しかし、ブラウザに一度送ったフレームは取り消せない。画面には空のマップが残り、直前の会議のマップは見えなくなる。

実装したエージェントは、計画の段で「接続の後にセッションを作ると、その間の発言を取りこぼす」として、接続を先にする案を退けていた。直し方は、セッションを作る順はそのままにして、**最初のマップを配信する時点だけ**を接続の成功の後ろへ移すことだった。

| 副作用 | 失敗したら戻せるか | 置き場所 |
| --- | --- | --- |
| セッションのフォルダを作る | 消せば戻る | 接続の前でよい |
| ブラウザへマップを配信する | 戻せない | 接続の成功の後 |

**失敗時の後始末を書くときは、副作用を「消せば戻るもの」と「一度出たら戻らないもの」に分ける。後者は、成功が確定するまで出さない**。

### 2. 「テストが通る」と「テストが結果を見ている」は別。2 周目のレビューは、1 周目で足したテストを疑う

1 周目の指摘の 1 つは、「ヘルパーの空きポートを探している間に `close()` されると、子プロセスが残る」だった。修正の段は、この経路のテストを足した。2 周目のレビューのテストの観点は、その足したテストを差し戻した。テストは `await started;` で開始を待つだけで、開始が失敗したかどうかを見ていなかった。開始が成功しても通る。

テストを足したのも、そのテストを差し戻したのもエージェントだ。修正のために足したテストは、レビューを一度も受けていない。差し戻しが 2 周になったのは、この 1 件のためだった。3 周目でテストは 98 件になり、6 観点すべてが通した。

**修正で足したテストは、次の周のレビューで「失敗する実装でも通らないか」を見る対象にする**。

### 3. 子プロセスの終了待ちには、時間の上限と強制終了を必ず付ける

`stop` は、ヘルパーの終了と WebSocket が閉じるのを `Promise.all([helper.exited, wsClosed])` で待っていた。上限は付いていない。6 観点 × 3 周のレビューでも、ここは指摘されなかった。

翌日、人が実機で確かめていて `stop` が戻らなくなった。会議アプリの代わりに QuickTime で音声ファイルを開き、**再生しないまま**セッションを止めたときだった。`sample` コマンドでヘルパーのスタックを見ると、メインスレッドが音声認識の終了処理 `finalizeAndFinishThroughEndOfInput()` の中で止まっていた。音声を 1 度も渡していない認識器にこれを呼ぶと、戻ってこない。それまでの実機の確認は、60 分の連続稼働も含めて、すべて音が出ている状態で行っていた。

直したのは 2 か所だ（[#70](https://github.com/daiki-beppu/live-mindmap/issues/70)、takt で約 18 分）。

- ヘルパー: 音声を受け取ったかを覚えておき、0 件なら `cancelAndFinishNow()` で終える
- サーバー: SIGTERM から `HELPER_STOP_TIMEOUT_MS = 5_000` 待っても終わらなければ SIGKILL し、そのことを標準エラーに出す

テストでは、SIGTERM を無視する偽のヘルパーを用意し、実時間で 5 秒待って強制終了に至ることを確かめた。

**子プロセスを止める処理は、相手が正しく終わる前提で書かない。上限を付けて、超えたら強制終了する。原因の側を直しても、上限は残す**。

### 4. 実機での確認は「入力が 0 件」の場合を 1 回入れる

3 節の不具合は、テストでもレビューでも、音が出ている前提の確認でも見つからなかった。入力が無い場合は、入力がある場合の特別な形ではなく、別の終了の経路を通る。

**音声やストリームを扱う機能の実機確認では、「つないだが何も流れない」状態で開始から終了までを 1 回通す**。

## マップの「変わったところ」の強調を、AI エージェントに実装させてから人の目で 3 回作り直した話

AI がマップを差分更新するたびに、どこが変わったかを画面で分かるようにしたときの学び。サーバーは反映の前後のマップを比べて「追加・更新・決定済み化・却下・移動・統合」を割り出す。ブラウザは変わったノードを強調し、右側に変わったことの一覧を出す。最初の形（赤い枠）は takt に実装させ、利用者の「ハイライトは最高だが、赤が見にくい」という評価を受けて、takt でもう 1 回、人の手で 2 回作り直した。

- 決定の記録: [「変わったこと」と赤い枠](https://github.com/daiki-beppu/live-mindmap/issues/37)、[変わったノードの強調を塗りに変え、ルートの文字を中央揃えにする](https://github.com/daiki-beppu/live-mindmap/issues/67)

### 1. 時刻で動くアニメーションは、テストが通っても、実機で座標を数値で採るまで壊れ方が見えない

新しい枝は、親の位置から伸びて出てくる。位置の補間は純粋な関数で、テストは web だけで 41 件通っていた。

実装の段のエージェントは、そのあとブラウザでノードの位置を数値で採った。すると、ノードが出発点より逆の方向へ `x = -19.25px` まで戻ってから進んでいた。`requestAnimationFrame` が渡す時刻は**そのフレームの開始時刻**で、アニメーションを始めた時刻より前になることがある。そのため、進み具合 `t` が負になっていた。補間の中で `t` を 0〜1 に収める 1 行で直し、3303 サンプルすべてで `x` の最小が 0 になることを確かめた。

テストは `t` に 0〜1 の値しか渡していなかった。負の `t` は、実際のフレームの時刻からしか出てこない。

**時刻を入力にするアニメーションは、実機で全フレームの座標を採って、範囲の外に出ていないかを数で見る**。

### 2. 前後の比較だけでは、統合と削除が区別できない場合がある。裁定は受入条件で切る

5 観点のレビューのうち、設計・コーディング・AI 生成コードの 3 つが、同じ欠陥を挙げて差し戻した。**子がなく、相手のノードが根拠をすでに全部持っている統合**は、前後のマップを比べただけでは削除と区別できない。消えたノードの痕跡が、残ったノードに何も残らないからだ。

3 つとも、差分操作（AI が出した追加・統合などの指示）の記録を比較に渡せば判定できる、という修正案を付けていた。裁定の段は 3 件とも退けた。受入条件が「前後のマップを比べて導く」と決めていて、修正案はその条件に反するからだ。この判定は、今も main にそのまま残っている。

3 観点が揃って差し戻すと、直したくなる。しかし、受入条件が手段まで決めている場合、それを変えるのは実装の工程ではなく、条件を書いた人の判断になる。

**レビューが揃って同じ欠陥を挙げても、直すと受入条件に反するなら、その場で直さず、条件を書き直すかどうかを人に返す**。

### 3. 見た目の受入条件は、エージェントが満たしても正解とは限らない。人の目視を完了の条件に入れる

赤い枠の評価を受けて、[#67](https://github.com/daiki-beppu/live-mindmap/issues/67) で強調を塗りに変えた。受入条件は「変わったノードを薄い黄色で塗り、約 3 秒で元に戻す」「枠は足さない」「ルート（会議の名前）の文字を中央揃えにする」だった。

takt は 11 分、差し戻しなしで通した。計画の段では色を比べていた。より薄い黄 `#fef9c3` は**論点**（会議で答えを出すべき問い）のノードの塗りと見分けにくいとして退け、`#fef08a` を選んでいる。ただし、色の見分け、塗りの戻り方、中央揃えの 3 点は、ブラウザで見ないまま承認された。

人が画面で見てから、2 回作り直した。

| 段階 | 形 | 評価・理由 |
| --- | --- | --- |
| #37（takt） | 赤い枠 3px | 「赤が見にくい」。種別「課題」の赤とも混ざる |
| #67（takt） | 黄色の塗りが 3 秒で戻る＋ルートを中央揃え | 3 秒で戻るのは違和感。中央揃えは見て取りやめ |
| #67 に人が追加 | 黄色の塗りが 1 秒周期で 3 回点滅 | まだ違う |
| 候補 | ノード全体の不透明度で点滅 | 文字まで薄くなるので採らない |
| #71（人） | 背景と枠の色だけを 1 秒周期で 3 回薄くし、細い黄色の枠（1.5px）を次の反映まで残す | 「いい感じ」 |

最後の形は、受入条件の「枠は足さない」に反している。点滅が終わった後も、どれが変わったのかを残しておく必要があったからだ。issue の受入条件は、この経緯を書いて改めた。

**見た目の受入条件は、書いた人も実物を見る前に書いている。エージェントに満たさせた後、人が一目見るまでは完了にしない**。

## ノードの根拠になった発言を出す画面を、ブラウザ操作のツールが固まったまま作りきった話

ノード、または「変わったこと」の一覧の項目をクリックすると、そのノードの種別・本文と、**根拠**（ノードの元になった発言）の時刻・トラック・本文を右の列に出す機能を takt に実装させたときの学び。**トラック**は発言の出どころで、`自分`（マイク）か `相手`（会議アプリの音）のどちらか。実行は 58 分で、そのうち約 32 分はブラウザ操作のツールが応答しないまま失われた。

- 決定の記録: [根拠の表示](https://github.com/daiki-beppu/live-mindmap/issues/38)

### 1. ブラウザ操作のツールが固まったら、同じ呼び出しを繰り返さず、確認の手段を替えて計画をやり直す

実装のやり直しの段で、Chrome DevTools の MCP サーバーの `new_page`（新しいタブを開く）が 1800 秒応答しなかった。エージェントは「関数を直接呼ぶテストで代わりにする」案を考えたが、退けた。実際のクリックや Tab キーでのフォーカスの止まり方は、関数を呼んでも確かめられないからだ。未確認のまま、計画のやり直しの段へ渡した。

計画のやり直しの段は、確認の手段を「ヘッドレスの Chrome を DevTools Protocol で直接操作する一時スクリプト」に替えた。これで、約 5 分で全項目を確かめられた。

**ツールが固まったときに替えるべきなのは、確認の対象ではなく手段のほう。確かめたいこと（実際のクリック・フォーカス）は残し、同じことを確かめられる別の経路を探す**。

### 2. 「Tab が 2 回止まる」の原因は、ライブラリの既定値のソースを読んで特定する

キーボードで操作すると、Tab がノードの外枠と、その中のボタンの 2 か所で止まっていた。計画のやり直しの段は、React Flow の配布物のソースを読み、`nodesFocusable` の既定値が `true` であることを見つけた。ノードの外枠をフォーカスできるのはこのためで、`nodesFocusable={false}` を渡して直した。

### 3. 計測の数字が仕様に反して見えたら、まず計測の側を疑う

確認のスクリプトでは、2 回、仕様に反するように見える結果が出た。どちらも、製品のコードの問題ではなかった。

| 見えたこと | 本当の原因 |
| --- | --- |
| クリックがノードを外れて、背景に落ちる | スクリプトが先に呼んだ `scrollIntoView` で位置がずれた |
| ブラウザから WebSocket の送信が 1 件ある（「ブラウザはマップを変えない」に反する） | URL ごとに分けると、開発サーバー Vite のホットリロードの接続だった。アプリの `/ws` への送信は 0 件 |

2 つ目は、数字を宛先で分けなければ「仕様違反」として直しにいくところだった。

**ブラウザの通信を数えるときは、宛先ごとに分けて数える。開発サーバー自身の接続が混ざる**。

### 4. レビューが受入条件の外を指摘したら、別チケットに切り出す

レビューでは 4 観点が同じ点で差し戻した。削除や**統合**（同じ種別の 2 ノードを 1 つにまとめる差分操作）で消えたノードを指す一覧の項目をクリックしても、根拠に移れない。裁定の段は、受入条件に定めがないとして全件退け、「選んだノードは今のマップにありません」と出すだけにした。裁定の記録には「別チケットで決める」とある。しかし、そのチケットは起票されていなかった。

**裁定で「別チケットで」と退けたものは、その場で起票まで済ませる。そうしないと、レビューで見つかったことが記録の中に埋もれる**。

## 話し終わりからマップに出るまでの待ちを、区間に分けて測って縮めた話

実機で話してから、マップにノードが出るまでが遅かった。それを 2 回に分けて takt に直させ、最後に人が設定 1 行で大きく縮めたときの学び。

- 決定の記録: [差分更新を、発言が 1 つでも一定時間で呼ぶ](https://github.com/daiki-beppu/live-mindmap/issues/66)、[発言が 1 つのときの待ちを 1.5 秒に縮める](https://github.com/daiki-beppu/live-mindmap/issues/74)

前提として、**差分更新**（AI がマップを作り直さずに、追加・更新などの操作を当てること）は、発言が 2 つたまるまで呼ばない作りだった。1 つずつ渡すと、文脈が足りずに読み違えることが、試作で分かっていたからだ。

### 1. 「N 個ごとに呼ぶ」には、最後の 1 個が来ないときの時間の上限を付ける

実機で確かめると、最初の発言は開始 11 秒で確定していたのに、マップへの反映は 39 秒だった。2 つ目の発言が来るまで、1 つ目は呼ばれずに待っていた。

[#66](https://github.com/daiki-beppu/live-mindmap/issues/66) で、最後の発言から `QUIET_MS` の間、次の発言が来なければ、1 つでも呼ぶようにした（最初は 5 秒）。

### 2. 取り消せない待ちしか使えないときは、世代の番号で古い待ちを無視する

差分更新の中核は、Node のタイマーに依存させない方針で、待ちは `sleep(ms)` という関数を外から受け取っている。外から渡された `sleep` は、`clearTimeout` のように取り消せない。そこで、発言を受け取るたびに世代の番号を進め、待ちが明けたときに番号が変わっていたら何もしないようにした。

```ts
let gen = 0; // 新しい発言を受け取るたびに進める。古い待ちの解決を無視するための世代

const g = gen;
void sleep(QUIET_MS).then(() => {
  if (g !== gen) return;
  quiet = true;
  // ...
});
```

差分更新の呼び出し中に待ちが明けた場合は、`quiet` のフラグに残しておき、呼び出しが終わった時点で 1 つで流す。

**待ちを取り消せない環境では、待ちの側を止めるのではなく、明けたときに「まだ有効か」を確かめる**。

### 3. 配線のテストは、外すと落ちることを確かめてから残す

1 回目のレビューで、テストの観点が差し戻した。ライブの経路で、サーバーが中核に `sleep` を渡していることを確かめるテストがない。既存のテストは発言を 3 つまとめて送るので、待ちの経路を 1 度も通らない。修正の段は、発言を 1 つだけ送るテストを足した。そして、`sleep` を渡す 1 行を一時的に外すと、そのテストだけが落ち、戻すと通ることを記録した。

### 4. 遅れの内訳でいちばん大きい区間を、前提として扱わない

#66 の後も遅かったので、セッションのログの時刻から、話し終わりからノードが出るまでの 13〜18 秒を区間に分けた。

| 区間 | 時間 |
| --- | --- |
| 話し終わり → 発言の確定 | 4〜9 秒 |
| `QUIET_MS` の待ち | 5 秒 |
| AI の差分更新 | 3〜4 秒 |

ここで「確定そのものが区切りを待っているので、5 秒の待ちは二重になっている」と考え、[#74](https://github.com/daiki-beppu/live-mindmap/issues/74) で 1.5 秒に縮めた。takt では定数とテストの期待値の 3 行の変更で、11 分で済んだ。#66 のテストが値を直接書かずに `QUIET_MS` を参照していたので、変更がここで止まった。

しかし、いちばん大きい「確定まで 4〜9 秒」の区間は、音声認識がそういうものだと考えて、手を付けていなかった。その約 30 分後、人が Apple の SpeechAnalyzer の設定を見直し、`reportingOptions` に `.fastResults` を足した。これが付いていないと、認識器は約 11.5 秒分の音声をまとめて処理していた。

| | 付ける前 | 付けた後 |
| --- | --- | --- |
| 途中結果が届く間隔 | 約 11.5 秒おきに塊で | ほぼ毎秒 |
| 話し終わり → 発言の確定 | 4〜10 秒 | 0.2〜1 秒 |
| 話し終わり → マップに出る | 10〜15 秒 | 5〜7 秒 |

認識の精度は同程度だった。

**遅れを区間に分けたら、いちばん大きい区間を「そういうもの」として外さない。自分で決めた待ちを削る前に、外部の部品の設定を疑う**。

## 話している文字の仮表示を、仕様どおりに作ってから字幕に作り直した話

AI がマップに反映するまでの数秒〜十数秒の間、画面が止まって見える問題を埋める機能を作ったときの学び。音声認識は、発言が確定する前に**途中結果**（後で書き換わる暫定の文字列）を出している。これを使って、話している文字を破線の枠の「仮のノード」としてマップに出し、反映で正式なノードに置き換える形を takt に実装させた。画面で見た後、仮のノードはやめて、文ごとの字幕に作り直した。

- 決定の記録: [話している文字を仮のノードとして出し、反映で正式なノードにする](https://github.com/daiki-beppu/live-mindmap/issues/39)

### 1. 待ち時間を埋める表示は、AI の判定を足す前に、すでに流れているデータで足りないかを見る

最初の案は、小さな AI モデルで約 0.2 秒ごとに「いまどのノードの話をしているか」を判定し、そのノードを点滅させるものだった。試作では、判定の一致率が 86%、60 分の会議で約 0.05 ドルと見積もっていた。

実装の前に、利用者が実機で試した評価は「リアルタイムで文字が出力されて、ある一定のところで構造化されるのが理想」だった。欲しいのは「どのノードの話か」ではなく、「話した文字が出ていること」だった。それなら、ヘルパーがすでに配っている途中結果をそのまま出せばよい。追加の AI 呼び出しはやめた。

### 2. 途中結果の表示は、文字単位で前から削らず、文の単位で入れ替える

takt の実装は、受入条件の「末尾の数十文字だけを出す」に沿って、仮のノードに途中結果の末尾 40 文字を出した。テストはすべて通った。

2 人が掛け合う合成音声を流して画面で見ると、利用者の評価は「どんどん前から消えていくのは目が滑る」だった。話が進むたびに文の頭が削れ、読んでいる位置が左へ流れていく。

作り直した形は、マップの下端の中央に重ねる字幕だ。

- 文の区切り（。？！）ごとに 1 行にする
- トラックごとに直近の 2 文だけを出す
- 古い文は、文字ではなく行ごと消す

サーバーの側は何も変えず、ブラウザの表示だけを差し替えた（+133 / −279 行）。評価は「字幕のほうがわかりやすかった」「だいぶいい」だった。

**流れ続ける文字は、読む単位（文）で入れ替える。文字数で切ると、読み手の目が文の頭を追いかけ続ける**。

### 3. 「止まって見える」の原因は、表示の形ではなく、データの届き方にもある

仮のノードが止まって見えた理由の 1 つは、途中結果が 50〜60 件ずつ塊で届いていたことだった。前のエントリの [.fastResults の設定](#reflect-latency) を足すまで、認識器は約 11.5 秒分をまとめて処理していた。表示をどう作り直しても、届くのが 11 秒おきなら、11 秒止まって見える。

**表示の形を評価する前に、データが実際にどの間隔で届いているかをログの時刻で確かめる**。

## 会議の終わりにマップの画像を書き出す機能を、AI エージェントに実装させた話

セッションを終えたとき、md・json・Drawnix に加えて、マップ全体の画像 `map.png` を書き出す機能を takt に実装させたときの学び。ブラウザを開いていなくても、サーバーが自分で撮る。サーバーは web の開発サーバーを起動し、Playwright の Chromium でマップを開いて撮る。マップの中身はページを開く前に変数として埋め込み、web の側は描き終えたことを `data-capture-ready` の属性で知らせる。撮るときは強調のアニメーションを切る。

- 決定の記録: [エクスポートの画像（map.png）](https://github.com/daiki-beppu/live-mindmap/issues/42)、[前日のエントリ「画像の撮り方は、『いつ撮るか』の決定から逆算する」](./2026-10-01.md#export-formats)

### 1. 付属の成果物の失敗で、主の処理を失敗させない。どちらが主かは仕様に書く

takt の実装は、撮影に失敗したら、テキストの 3 ファイルは残したうえで、`stop` をエラーで終える設計だった。それを固定するテストまで書かれていた。失敗を黙って握りつぶさず伝えるのは、エージェントにとって安全側の判断に見える。

人が見ると逆だった。会議の記録の本体は md・json・Drawnix で、画像はおまけだ。Chromium が入っていないだけで、会議の終了が失敗扱いになる。直した後は、撮影に失敗したら標準エラーに「map.png を書き出せませんでした: …」と出し、書き出せた 3 ファイルのパスを返して正常に終える。テストも「失敗する」から「成功し、標準エラーに出る」に書き換えた。

仕様には「map.png も書き出す」とだけあり、ほかの 3 ファイルとの重みの違いは書いていなかった。

**成果物が複数あるときは、どれが失敗したら全体を失敗にするかを仕様に書く。書かなければ、エージェントは全部を同じ重みで扱う**。

### 2. 画像を出す機能は、実物を 1 回開いて見るまで完了にしない

疎通のテスト「map.png が書き出される」は通っていた。人が短い文字起こしを再生して出た画像を開くと、画面全体（3200×2000）を撮っていて、小さなマップの周りは余白だらけだった。ノードの範囲に余白 32px を足して切り抜くように直し、3040×238 になった。テストには、PNG のヘッダーから実際の幅と高さを読んで確かめる 1 本を足した。

**画像のテストは「ファイルがある」で止めず、大きさを読んで確かめる。そのテストを書く前に、実物を 1 回開いて見る**。

<a id="filler-remarks"></a>

## 誰も話していないのに確定する「あ」を、文字数ではなくフィラーの語で外した話

合成音声のデモで、マップの最初の反映だけが遅れる原因を追って、中身のない発言を差分更新に渡さないようにしたときの学び。実装は takt に任せた。

- 決定の記録: [誰も話していないのに「自分」の「あ」が確定し、最初の反映が遅れる](https://github.com/daiki-beppu/live-mindmap/issues/81)

**発言**は、音声認識が確定させた文字起こしの 1 区切りのこと。会議アプリの音（`相手`）と自分のマイク（`自分`）の 2 トラックで別々に確定する。

### 1. 1 回目だけ遅いときは、その前に余計な 1 回が挟まっていないかを見る

デモのたびに、1 つ目の議題だけ、話し終わりから反映まで約 12 秒かかっていた。ほかの発言は約 5〜7 秒だった。最初の呼び出しは立ち上げで約 9 秒かかるので、はじめは「コールドスタートだから仕方ない」と見ていた。

セッションのログを見ると、マイクの入力音量を 0 にしていても、開始から約 12 秒で `自分` の発言「あ」が確定していた（5 回とも同じ）。この 1 文字で差分更新が 1 回呼ばれ、結果は「何もしない」（noop）。1 つ目の議題は、この空振りの呼び出しが終わるのを後ろで待っていた。

**最初の 1 回だけ遅いときは、遅い理由を立ち上げのせいにする前に、その前に何が呼ばれたかをログで確かめる**。

### 2. 中身のない発言は、文字数でも前方一致でもなく、「語がすべてフィラーか」で判定する

「1〜2 文字なら捨てる」は簡単だが、「賛成」「了解」のような短い同意まで消える。「はい」で始まる発言を捨てると、「はい。では次の議題です」まで消える。

そこで、発言を空白・句読点で語に分け、長音（ー〜~）を除いた各語が**すべて**フィラーの集合に入っているときだけ、中身なしとした。

```ts
export const FILLERS: ReadonlySet<string> = new Set([
  "あ", "え", "う", "お", "ん", "うん", "ふん", "ええ", "はあ", "へえ", "ほう",
  "あの", "えっと", "えと", "その", "まあ", "はい",
]);

export function hasContent(text: string): boolean {
  const words = text.replace(/[ー〜~]/g, "").split(/[\s\p{P}\p{S}]+/u).filter((w) => w !== "");
  return words.some((w) => !FILLERS.has(w));
}
```

「えー」「あの、えっと」は外し、「賛成」「はい。では次へ」は渡す。この境目の例を、そのままテストにした。

**機械的な足切りは、捨てる側の例と、捨ててはいけない側の例を両方テストで固定してから入れる**。この足切りは最低限のものにとどめ、雑談かどうかのような判断は、次のエントリで測る別のモデル（Jev）に任せる設計にしている。

### 3. 捨てた入力もログには残し、「どこで捨てたか」の印を付ける

中身のない発言は、差分更新にも、画面の字幕（まだマップに反映していない発言）にも出さない。ただしログには `noContent: true` を付けて残す。捨て方の基準が間違っていたとき、ログを見れば何が消えたかが分かる。

ログからセッションを復元する処理にも、同じ判定を入れた。この修正より前のログには「あ」が渡された記録が残っている。復元の側で判定しないと、続きの差分更新に「直前の発言」として「あ」が渡ってしまう。

**入力を捨てる規則を足したら、リアルタイムの経路だけでなく、古いログを読む経路にも同じ規則を通す**。

## 差分更新の AI 呼び出しを速くする案を、6 つの場面で測り比べた話

話し終わりからマップに出るまでが約 5〜7 秒まで縮んだ後、残る大きな区間である AI 呼び出し（Claude の差分更新、1 回約 3〜4 秒）を速くする案と、呼び出しの回数を減らす案を、同じ入力で測り比べたときの学び。この記事を書いた時点では 1 本目の計測（6 案）が終わったところで、2 本目（変更分だけ送る案など）は実行中。

- 決定の記録: [差分更新の AI 呼び出しを速くする案を測る](https://github.com/daiki-beppu/live-mindmap/issues/75)、[Claude に渡す前に Jev で判定し、雑談は後回しにして呼び出しを減らす](https://github.com/daiki-beppu/live-mindmap/issues/84)

Claude は Claude Agent SDK の `query()` で呼んでいる。**Jev** は、選択肢から選ぶだけで文章を作らない判断専用のモデル（TypeSafe AI の System One）で、1 回約 0.2 秒、入力 100 万トークンあたり $0.042 と安い。

### 1. 案を比べる前に、台本と正解のある「場面」を複数作り、実時間で流す

1 本の録音で比べると、その会議の性格で結論が決まってしまう。そこで台本から合成音声を作り、性格の違う 6 つの場面を用意した。

| 場面 | 長さ | 性格 |
|---|---|---|
| converge | 89 秒 | 収束型の定例 |
| brainstorm | 62 秒 | 発散型のブレスト |
| chitchat | 64 秒 | 雑談が多い |
| agree | 36 秒 | 短い同意が続く |
| rapid | 28 秒 | 早口の掛け合い |
| monologue | 53 秒 | 長い独り語り |

台本から、決定・TODO の正解（どの時刻の発言が決定か）も同時に書き出した。文字起こしは 1 回だけ取り、どの案にも同じ発言を同じ時刻で流す（実時間での再生）。こうすると、違いは AI の呼び方だけになる。1 案を 6 場面に流すのに約 13 分かかる。

### 2. 呼び出しごとに CLI を立ち上げる作りでは、時間の半分以上が立ち上げだった

Agent SDK の `query()` は、呼ぶたびに Claude Code の CLI をプロセスとして立ち上げる。試しに、`prompt` に AsyncIterable を渡して 1 つのセッションを開いたまま使い回すと、1 回が 3.4〜8.5 秒から 1.4〜2.3 秒になった。

6 場面の計測でも同じ傾向だった（stream が使い回し）。

| 案 | 呼び出し 1 回 p50 | 話し終わり→ノード p50 / p90 | 決定・TODO の発言 p50 | 決定・TODO の再現 | 反映されなかった発言 | 費用（6 場面計） |
|---|---|---|---|---|---|---|
| sonnet（今の作り） | 3.6 秒 | 5.2 / 7.3 秒 | 6.0 秒 | 13/15 | 0 | 記録できていない |
| stream-sonnet | 1.7 秒 | 3.2 / 8.2 秒 | 3.2 秒 | 14/15 | 0 | $0.31 |
| jev-sonnet | 4.0 秒 | 6.0 / 12.2 秒 | 6.1 秒 | 14/15 | 1 | $0.44 |
| jev-stream-sonnet | 1.8 秒 | 3.4 / 9.7 秒 | 3.2 秒 | 14/15 | 3 | $0.26 |
| haiku | 12.8 秒 | 51.7 / 143.6 秒 | 72.4 秒 | 11/15 | 0 | 記録できていない |
| stream-haiku | 5.6 秒 | 28.3 / 86.4 秒 | 69.7 秒 | 13/15 | 0 | $0.51 |

使い回しは、モデルも入力も変えずに、話し終わり → ノードの p50 を約 2 秒縮めた。

**SDK や CLI 経由でモデルを呼ぶときは、モデルを替える前に、1 回の時間のうち立ち上げが何割かを測る**。

### 3. 「小さいモデルなら速い」は、自分の入力で測るまで前提にしない

Haiku に替えれば速くなると考えていたが、逆だった。1 回の呼び出しが 60 秒を超えることがあり、話し終わり → ノードの p50 は約 52 秒になった。呼ぶ回数も Sonnet の約半分になった。1 回が遅いあいだに次の発言がたまり、まとめて渡されたためだ。決定・TODO の再現も 11/15 と落ちた。

遅い理由は、出力が長くなったのか、利用枠の側で待たされたのかを、まだ切り分けていない。ただ、この入力と呼び方では使えないことは分かった。

もう 1 つの候補だった Gemini 3.8 Flash は、サブスクリプションで使える Antigravity CLI（`agy`）から JSON スキーマ付きで呼ぶと、1 回 13〜19 秒かかった（CLI の中で 2 ターン回っていた）。こちらも見送った。API で直接呼ぶ場合は、料金の見積もり（60 分の会議で約 $1.5、2027 年からは約 $3.0）までで、時間はまだ測っていない。

**モデルの「速い・遅い」は一般論ではなく、自分のプロンプトの長さと出力の形で測る**。

### 4. 呼び出しを減らすゲートは、1 回が安く速くなった後では得が小さい

雑談の多い場面（chitchat）では、Jev のゲートで Claude の呼び出しが 12 回から 7 回に減った。雑談は捨てずにためておき、次に中身のある発言で呼ぶときに一緒に渡す。それでも 6 場面の合計では、使い回しどうしの比較で費用が $0.31 から $0.26 に下がっただけだった。一方で、反映されなかった発言が 3 件出た。後回しにした発言は、反映が最大 31 秒遅れた（当初は 25 秒と書いていた。2026-10-06 に数え直すと、25 秒は 2 番目の値だった）。Jev 自体の費用は 6 場面で $0.002 だった。

9/30 の試作で「1 発言ごとに呼ぶ形に近づけば、ゲートの価値が出る」と見込んでいた。実際に 1 発言ごとに近づいたが、先に使い回しで 1 回の費用（前置きがキャッシュに乗る）と時間が下がったので、減らす回数の価値も小さくなった。

**回数を減らす最適化と、1 回を安くする最適化は、後から入れる方の効き目が小さくなる。両方を同じ入力で一緒に測ってから選ぶ**。

### 5. 集計の数字が案の差に見えたら、まず集計の側を疑う

最初の集計では、Jev の案で「後回しにした発言」が、話し終わり → ノードの時間にも、反映されたかどうかにも数えられていなかった。後回しにした発言は次の呼び出しの入力に「持ち越し」として入るが、集計は呼び出しの入力のうち「新しい発言」だけを見ていたからだ。持ち越した発言の ID を数えるように直すと、Jev の案の遅れ（最大 31 秒）が初めて表に出た。

また、決定・TODO の再現が 13/15 と 14/15 で違っても、それが案の差とは言えない。同じ案でも AI の判断は毎回少し揺れるので、2 本目の計測では、今の作りをもう 1 回流してばらつきを見ている。

**新しい仕組みに有利な数字が出たら、その仕組みだけが通る経路を集計が数えているかを先に確かめる**。

| jevprio-stream-diff-sonnet | 38 | 3.7 / 10.6 秒 | 3.4 秒 | 14/15 | 3 | $0.21 |

- 今の作りは 1 本目で 13/15、2 本目で 14/15 だった。この差は同じ案の揺れの範囲で、再現率で案を選ぶことはできない（5 節の見立てどおり）
- 使い回し（stream）は、今の作りより話し終わり → ノードを約 1.7 秒縮め、費用を約 3 割下げた。p90 も 7.2 秒から 4.6 秒になった
- 変更分だけ送っても、費用は下がらなかった。1〜2 分の場面ではマップが小さく、全体を送っても入力がほとんど増えないからだ。マップが大きくなる 60 分の会議では効く可能性があるので、長い会議で測り直す
- 急ぐ発言だけすぐ呼ぶ案は、呼び出しを約 35% 減らし、使い回しと組み合わせて最も安かった（$0.21）。ただし反映されなかった発言が 3 件出て、p90 も 10 秒台に延びた

結論として、まず使い回しを入れ（[差分更新の Claude 呼び出しを、開いたまま使い回して速くする](https://github.com/daiki-beppu/live-mindmap/issues/87)）、Jev による振り分けと変更分だけ送る案は、60 分の会議で費用の差が大きくなるかを見てから決める。使い回しには、計測では出なかった課題が 1 つ残る。計測した場面は最長 14 回の呼び出しだったが、60 分の会議では数百回になり、会話の履歴がたまり続ける。決まった回数ごとに開き直す前提で実装する。

## AI エージェントのワークフローが、起動した側の時間の上限で止められ、止まった工程から積み直した話

スピーカーで会議を聞くときに二重に入る自分の発言へ印を付ける作業を、takt に実装させている途中で、実行が外から止められたときの学び。takt は、計画 → テストを書く → 実装 → レビュー → 修正 → 最終判定の工程を、別々のエージェントに順に受け持たせて回すツールで、この作業では全体で 51 工程の予算を持っていた。

- 決定の記録: [スピーカーで聞くときの重複の印](https://github.com/daiki-beppu/live-mindmap/issues/36)
- 前に利用上限で止まった実行を再開した話: [ヘルパーの文字起こしを AI エージェントに実装させた話の 7 節](./2026-10-01.md#helper-transcription-by-agent)

### 1. 長い処理を別のエージェントから起動するときは、起動した側の時間の上限を先に確かめる

takt は、コーディング用のエージェント（Claude Code）から、バックグラウンドのコマンドとして起動していた。このバックグラウンド実行には、既定で 30 分の時間の上限がある。takt の実行は 1 件で 1 時間近くかかることがあり（この日の「ライブのセッション」は 56 分）、ちょうど 30 分で、実装のやり直しの工程（5/51）の途中で止められた。

takt の側にも、実装の側にも、失敗はなかった。止めたのは、起動した側の時間の上限だった。それまでの実行は上限に当たらずに済んでいたか、別の起動のしかたをしていたので、気づかなかった。

再開するときは、時間の上限を最大の 2 時間にして起動し直した。

**エージェントに長い処理を起動させるときは、その処理の時間ではなく、起動した側の上限の時間を基準にする。上限より長くなり得るなら、上限を明示する**。

### 2. 「途中で止められた」と「ある工程で失敗した」は別の状態で、自動の再試行は前者を拾わない

takt には、失敗したタスクを自動で積み直す設定がある（このリポジトリでは 2 回まで）。しかし、次に `takt run` を起動すると、こうなった。

```text
[INFO] Marked 1 interrupted running task(s) as failed.
[INFO] Task "issue-36-..." was not auto-requeued: failed step is missing (0/2)
[INFO] No pending tasks in .takt/tasks.yaml
```

実行中のまま持ち主のプロセスがいなくなったタスクは、「失敗」に書き換えられる。ただし、どの工程で失敗したかの記録がない。自動の積み直しは「失敗した工程」から再開する仕組みなので、工程の記録がないタスクは対象から外れる。エラーの文面も「明示的に積み直せ」（`Requeue it explicitly to run again.`）と言っていた。

前日の利用上限による停止では、工程の中でエラーになったので、失敗した工程が記録され、再開の手がかりがあった。外から止められた今回は、その記録がない。

**外からプロセスを止められたタスクは、自動の再試行に任せず、自分で積み直す**。

### 3. 対話でしか選べない操作は、ツールのソースを読み、同じ関数を同じ順に呼んで非対話で行う

明示的に積み直す手段は、`takt list` の対話の画面しかなかった。前の workflow を使うかの確認と、どこから始めるかの選択の 2 問が出る。エージェントからは端末の対話を操作できない。

そこで takt のソース（`taskRetryActions.js` の `requeueFailedTask`）を読み、対話の 2 問を、既定の答えに置き換えて同じ関数を順に呼んだ。

```js
const task = runner.listFailedTasks().find((t) => t.name.startsWith("issue-36"));
const prep = prepareFailedTaskRetry(task, cwd);
const ctx = buildFailedTaskRetryStartContext(prep, cwd, prep.previousWorkflow); // 前の workflow を使う
const sel = resolveTaskRetryStartOption(ctx.workflowConfig, ctx.options, "resume-checkpoint"); // 止まった位置から
const own = resolveTaskRetryStartOwnership(sel.selection, ctx.workflowConfig);
persistFailedTaskRetry({ task, projectDir: cwd, worktreePath: prep.worktreePath, /* ... */
  resumePoint: own.resumePoint, sourceRunSlug: prep.matchedRunSlug, restartPoint: own.restartPoint });
```

始める位置の選択肢には、「止まった位置から再開」（`resume-checkpoint`）が既定として用意されていた。工程の失敗としては記録されていなくても、どの工程まで進んだかのチェックポイントは残っていた。これで実装のやり直しの工程（5/51）から続きが走り、計画とテストを書く工程はやり直さずに済んだ。

**対話の画面しかない操作も、中の関数は非対話で呼べることが多い。呼ぶ順と、対話で選ばれる既定の答えを、ソースから写す**。

### その後

翌日、同じ手順で積み直すと、「止まった位置から再開」の選択肢が出ず、既定が最初の計画の工程になった。並列のレビューの途中で止まると、止まった位置を今のワークフローの定義でたどり直せないためだった。また、2 時間の上限でも足りない実行が出たので、takt の実行は起動した側から切り離して動かすようにした。経緯は [長い処理が起動した側と一緒に止まるのを、3 回繰り返してから切り離した話](./2026-10-03.md#detach-long-runs) にある。

<a id="mit-license-publish"></a>

## 公開前にライセンスと有料の線引きを決めるつもりが、収益化をやめて MIT にした話

private のリポジトリを GitHub で公開する前に、ライセンスと「無料 / 有料の線引き」を決めようとしたときの学び。当初の方向は、本体を AGPL-3.0 で公開し、有料の機能やホスト版（こちらで運用する SaaS）で収益化するオープンコアだった。最終的には収益化をやめ、リポジトリ全体を MIT で公開することにした。公開前の点検もこのとき済ませた。

- 決定の記録: [ADR 0004 収益化せず、全体を MIT で公開する](../adr/0004-mit-license-no-monetization.md)、[公開の手順](../publishing.md)

### 1. ライセンスは「何を守りたいか」から決める。守るものが無ければ、問いはまとめて消える

最初に挙げた「公開前に決めること」は 8 つあった。

- 本体を AGPL だけにするか、商用ライセンスと併売するか
- 有料の機能を、公開リポジトリの `ee/` に置くか、非公開のリポジトリに置くか
- 外部の貢献者に CLA（著作権の扱いへの同意）を求めるか
- フォークがこの名前でホスト版を出すことを、どこまで許すか
- 会議に参加する Bot について、Zoom / Google Meet の規約がどうなっているか
- ほかに、プロンプトや評価データを公開するかどうか、など

これを、問題を分解して 1 つずつ決めていく道具（決定のチケットを親子と依存でつなぐ「マップ」）に載せようとしていた。その途中で、「オープンソースでもいい気がしてきた」「収益は気にせず」と方針が変わった。

8 つのうち 6 つは、収益を守るためだけの問いだった。CLA が要るのは、デュアルライセンスや有料版に貢献を流用するときだけ。`ee/` の置き場所や商標の範囲も、有料の層があるときだけ意味を持つ。残ったのは、ライセンスの種類・公開前の点検・公開する資料の範囲の 3 つで、1 回の作業で片付いた。マップは作らずに済んだ。

**ライセンスの問いを並べる前に、守りたいもの（収益・改変の還元・名前）を先に決める。守るものが無いと決まれば、それに付いてくる問いはまとめて消える**。

### 2. ライセンスを変えたときの戻しやすさは、変える向きで違う

AGPL と MIT のどちらにするかを迷っている間は、AGPL で出しておくほうが選択肢が残る。

| 変える向き | 戻せるか |
|---|---|
| MIT → AGPL | 新しい版からしか変えられない。MIT で出した版は MIT のまま使われ続ける |
| AGPL → MIT | 著作権者が自分 1 人なら（または CLA で権利を集めていれば）、いつでも緩められる |

今回は、迷った末に「広まることを優先する」と決めたので MIT にした。そのため、「MIT で出した版は取り消せない」ことを ADR の「戻しにくい点」として書いた。収益化に戻すなら、新しく書くコードや運用でしか作れない。

もう 1 つの軸は思想だった。「ギブすればいずれ返ってくる」と考えるなら MIT、「返ってくる仕組みを作りたい」なら AGPL になる。MIT は返すかどうかを相手の善意に任せるライセンスで、AGPL は、改変したものをネットワーク越しに使わせる場合にもソースの公開を求める互恵のライセンスだからだ。

**ライセンスを迷ったときは、どちらが良いかより、後からどちらへ動けるかで比べる**。

### 3. プロプライエタリな依存で効いてくるのは、ライセンスより利用規約のほうだった

依存パッケージのライセンスを `pnpm licenses list` で並べると、1 つだけ例外があった。

```text
Unknown: @anthropic-ai/claude-agent-sdk, @anthropic-ai/claude-agent-sdk-darwin-arm64
MIT: ...
Apache-2.0: ...
```

差分更新（会議の新しい発言を見て、AI が既存のマップに追加・更新などの操作を出す処理）で Claude を呼ぶための SDK だ。パッケージに入っている LICENSE は「© Anthropic PBC. All rights reserved.」で、利用は Anthropic の規約に従う。

最初は、これが AGPL と両立するかを一番の論点だと思っていた。しかし、MIT にすると決まった時点で、ライセンスの衝突はなくなった。私たちはこのパッケージを同梱せず、利用者が npm から自分で入れるからだ。

問題は別のところにあった。Anthropic の規約（Claude Code の [Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)）は、Agent SDK を使ってプロダクトを作る開発者に、API キーでの認証を求めている。さらに、第三者の開発者が利用者に代わって、Free / Pro / Max のサブスクの認証で要求を送ることも認めていない。

このプロジェクトでは、費用を抑えるために、自分のサブスクの認証で SDK を呼んでいた。以前の ADR には、「配布するときは、API キーで API を直接呼ぶ実装に差し替える」と書いていた。

規約を読み直すと、問われているのは**どの認証で呼ぶか**で、SDK を使うかどうかではなかった。SDK は環境変数 `ANTHROPIC_API_KEY` があればそれを使う。そこで、README で API キーの設定を必須の手順として案内し、サブスクの認証は案内しないことにした。実装の差し替えは、公開の前提条件から外した。コードは 1 行も変えていない。

**同梱しない依存なら、ライセンスの互換性より、利用規約が「誰の資格で、どう呼ぶか」をどう縛っているかを先に読む**。

### 4. 公開前の点検は、コードの履歴だけでなく、issue・PR・コミットのメタデータまで見る

リポジトリを public にすると、コードの全履歴に加えて、issue・PR のやり取りと、コミットの author も一緒に公開される。点検したことと結果は次のとおり。

```sh
# 全ブランチの履歴をシークレットの規則で走査する（78 コミット、0 件）
nix run nixpkgs#gitleaks -- git --log-opts="--all" --redact .
# 一度でも入ったことのあるファイル名から、音声や文字起こしらしいものを探す
git log --all --format= --name-only | sort -u | grep -iE 'transcript|audio|\.wav|\.m4a|\.env|secret|key'
# issue の本文とコメントを書き出し、社外秘・メールアドレス・トークンらしい文字列を探す
gh issue list --state all --limit 200 --json number,title,body,comments > issues.json
```

- 見つかったのは、削除済みの試作に残っていた環境変数のファイル 1 つだけだった。中身はパスワード管理ツールの参照で、値は含まれていなかった
- 「社外秘」は issue で 8 か所に出てきた。どれも「社外秘の会議は使わない」という運用方針の記述だった
- 音声と文字起こしは、履歴に 1 つも無かった。最初の試作のときから、評価用の録音（第三者の公開会議）とその実行結果を git の外のフォルダに置き、コミットのメッセージにも理由を書いていた。そのおかげで、点検は確かめるだけで済んだ

残ったのは、25 コミットの author が個人のメールアドレスだったことだ。履歴を書き換えれば隠せる。しかし、全コミットの SHA が変わり、issue・PR・開発ログからのコミットへの参照が切れる。そこで、書き換えずに公開し、この先のコミットだけ GitHub の noreply のアドレスに切り替えることにした。

**公開の点検は、コード・issue・コミットのメタデータの 3 つを見る。履歴を書き換えるかどうかは、隠したいものの重さと、切れる参照の多さで比べる。録音のような生のデータは、最初のコミットから git の外に置いておくのが一番安い対策になる**。

<a id="duplicate-mark"></a>

## スピーカーで聞くと二重に入る自分の声を、捨てずに印を付ける形で AI エージェントに実装させた話

会議をイヤホンではなくスピーカーで聞くと、相手の声がマイクにも入り、`自分` のトラックにも同じ発言が文字起こしされる。この二重の発言に印を付ける作業を takt に実装させたときの学び。途中で実行が外から止められ、止まった工程から積み直した経緯は [9 のエントリ](#takt-interrupted-requeue) に書いた。再開後は 14 工程・約 35 分で、2 回目のレビューは全観点が承認した。takt の工程ごとの報告書は、マージ後に作業用のクローンごと消したので、この記録はセッション中に読んだ範囲と、マージされた差分から書いている。

- 決定の記録: [スピーカーで聞くときの重複の印](https://github.com/daiki-beppu/live-mindmap/issues/36)

ヘルパー（会議の音声を文字起こしする Swift の常駐プロセス）は、会議アプリの音を `相手`、マイクを `自分` という 2 本のトラックで、別々に文字起こししている。

### 1. 自動の判定で入力を消すときは、捨てずに印を付けて流し、使うかどうかは後段で決める

重複と判定した `自分` の発言は、捨てずに `duplicate` の印を付けてサーバーへ流す。サーバーは印の付いた発言を差分更新（AI がマップに追加・更新の操作を当てること）に渡さないが、ログには残す。判定が外れて自分の本当の発言に印が付いても、ログから何が消えたかを追える。

[7 のエントリ](#filler-remarks) のフィラーの足切りも、同じ形にしている。**判定を間違えたときに取り返せることを、判定の精度より先に設計する**。

### 2. 判定のしきい値は、実測した分布から余裕を取って決め、根拠をコードに書く

判定は、`自分` の発言の文字 3-gram（3 文字ずつの断片）が、前後 8 秒の `相手` の発言にどれだけ含まれるか（被覆率）で行う。9/30 の試作で、スピーカーから漏れた発言 12 件の被覆率は 0.68〜1.00 だった。しきい値はそれより下に余裕を取って 0.6 にし、この数字の出どころをコメントに残した。

```swift
/// 漏れた発言の実測（12 件）は 0.68〜1.00（docs/knowledge/2026-09-30.md）。それより下に余裕を取りつつ、
let duplicateThreshold: Double = 0.6
```

**しきい値は、数字そのものより「なぜその数字か」を残す。後で実機の結果と比べて動かすときの起点になる**。

### 3. 「後の入力を見てから決める」判定は、待つ上限と、上限を数え始める時点をセットで決める

「前後 8 秒」の「後」を見るには、`自分` の発言を、後から来る `相手` の発言を待って保留しなければならない。保留を解くのは、後 8 秒の `相手` の発言が届いたとき、`相手` の流れが終わったとき、保留の上限（8 秒）に達したときのどれかにした。

設計の観点のレビューは「入力が判定より速い状態が続くと、保留の列が際限なく伸びる」と指摘した。裁定の工程は、上限を「保留に入れた時刻」から数えているので、8 秒を過ぎた発言は待たずに判定され、列は約 8 秒分に収まる、とコードの行を挙げて退けた。

**待つ処理のレビューでは、上限があるかだけでなく、上限をどの時点から数えるかを確かめる**。前の発言の待ちで遅れた分を引かずに数えると、列は伸び続ける。

### 4. 守りたい振る舞いのテストは、守っている行を外すと落ちることまで確かめる

1 回目のレビューで差し戻されたのは、テストの観点の 1 件だった。片方のトラックがエラーで止まったら、保留中の `自分` の発言は送らない。この契約を確かめるテストが、保留の状態に入ったことを待たずに確かめていた。`相手` の流れが起動直後に失敗するので、保留に入る前に全体が止まっても通る。守っている行（`Task.isCancelled` の確認）を外しても、テストは落ちなかった。

修正では、保留に入ったことを確かめてから、もう片方を失敗させる順にした。

**「〜しないこと」を確かめるテストは、何も起きなければ通る。「〜しない」状態に確かに入ったことを先に確かめる**。

### 5. 機器の分類で決めきれない所は、実機の確認に回して人が決める

出力先は Core Audio で、内蔵スピーカー・イヤホン（内蔵の差し口）・Bluetooth・その他の 4 つに分けた。判定をかけるのは内蔵スピーカーとその他（USB・HDMI・AirPlay）で、イヤホンと Bluetooth にはかけない。

ここで 2 つ、仕様が決めていない所が残った。

- Bluetooth スピーカーは「Bluetooth」なので判定されない。AirPods と区別できない
- USB のヘッドセットは「その他」なので判定され、漏れていない自分の発言に印が付くことがある

レビューもこの挙動を指摘したが、裁定は「受入条件は 3 種類の分類しか求めていない。USB ヘッドセットを Core Audio で区別できるかも確かめていない」として持ち越した。どちらも、実機の確認で人が決める項目として、確認用の issue に書き写した。

**機器や環境の種類で分ける処理は、分類の表にない機器がどこに落ちるかを書き出し、決めきれない所を人の確認に回す**。

## AI の呼び出しを開いたまま使い回す実装で、レビューが持ち越した懸念を本物の API で確かめた話

[8 のエントリ](#call-latency-bench) の計測で選んだ「Claude の呼び出しを開いたまま使い回す」案を、takt に実装させたときの学び。実行は 11 工程・約 41 分。こちらも、工程ごとの報告書はマージ後に消したので、セッション中に読んだレビューの指摘と、マージされた差分から書いている。

- 決定の記録: [差分更新の Claude 呼び出しを、開いたまま使い回して速くする](https://github.com/daiki-beppu/live-mindmap/issues/87)

Claude は Claude Agent SDK の `query()` で呼んでいる。これまでは呼ぶたびに `query()` を作り、そのたびに CLI のプロセスが立ち上がっていた。新しい作りでは、`prompt` に AsyncIterable を渡した 1 つの `query()` を開いたままにし、発言のたびにメッセージを流し込む。

### 1. 計測用のコードを本番に移すときは、設定値の意味が呼び方で変わっていないかを確かめる

計測のコードでは `maxTurns`（1 つの `query()` で許すやり取りの回数）を 10000 にしていた。本番の実装は、それまでの 1 回ずつ呼ぶ作りの値 `maxTurns: 4` をそのまま残した。

コードの観点のレビューは、これを重要度・高で指摘した。開いたままの `query()` で 4 が通算の上限なら、5 回目の呼び出しで `error_max_turns` になり、その回の発言がマップに反映されない。裁定の工程は「この値は前からある。SDK が通算するかは確かめていない。失敗しても開き直すのでマップは壊れない」として、実機の確認に持ち越した。

### 2. レビューが「未確認」で持ち越した懸念は、マージ前に実物で 1 回確かめる

持ち越したままマージすると、実機の確認で 5 回目に失敗して初めて分かる。そこでマージの前に、PR のコードで本物の Claude を 7 回続けて呼んだ。

| 回 | 時間 | 結果 |
|---|---|---|
| 1 | 7.8 秒 | 成功（立ち上げを含む） |
| 2〜7 | 1.8〜2.9 秒 | すべて成功 |

`maxTurns` は 1 回のメッセージの中のやり取りに付く上限で、通算ではなかった。値はそのままでマージした。2 回目以降の時間は、計測の 1.4〜2.3 秒とほぼ同じだった。

**レビューの懸念が「SDK の挙動しだい」なら、議論で決めずに、数十秒の実験で確かめる**。この確認は 1 分かからなかった。

### 3. 開き直す回数は、計測で品質を確かめた範囲に置く

開いたままにすると、会話の履歴がたまり続ける。60 分の会議では数百回の呼び出しになる。そこで、決まった回数ごとに `query()` を開き直す。

```ts
// 1 つの query を開いたまま使い回す回数。会話の履歴がたまり続けないよう、この回数ごとに開き直す。
// 14 は、計測（#75）で品質を確かめた最長の回数
export const QUERY_RENEW_CALLS = 14;
```

もっと大きくすれば立ち上げの回数は減るが、14 回を超えて履歴がたまったときの品質は測っていない。**測った範囲の外に出る値は、測るまで使わない**。毎回マップ全体を送っているので、開き直しても答えは履歴に依存しない。

### 4. 資源を開く処理は、失敗の経路でも閉じることを、その経路を実際に通るテストで確かめる

テストの観点のレビューは、「会議の開始に失敗したら、開いた `query()` を閉じる」テストを差し戻した。テストの失敗のさせ方が、`query()` を開く前の段階で失敗していた。開いた数も閉じた数も 0 で、「開いた数 = 閉じた数」が成り立ってしまう。閉じる処理を消しても通る。

修正では、`query()` を開いた後で失敗させる経路をテストにした。[11 のエントリ](#duplicate-mark) の 4 節と同じく、**確かめたい状態に入ったことを、テストの中で先に作る**。

### その後

この直後の録音の作業（次のエントリ）で、開始の順番が変わった。録音の保存先をヘルパーに渡すため、セッションのフォルダをヘルパーの起動より前に作るようになった。フォルダを作れずに失敗する経路では、`query()` はまだ開かれない。そのため、ここで足したテスト（「ヘルパーにつないだ後にフォルダを作れず失敗しても、開いた updater は閉じる」）は、「フォルダを作れず失敗したら、ヘルパーも updater も起動しない」に書き換えられた。開いた後の失敗で閉じることは、`stop` の途中の失敗とサーバーの終了のテストで確かめている。

## 会議の録音を発言の時刻にそろえて残す機能を、AI エージェントの思い込みをほどきながら実装させた話

会議の音声を、`相手` と `自分` のトラックごとに録音ファイルとしてセッションのフォルダに残す機能を、takt に実装させたときの学び。録音の 0 秒を発言の時刻の基準とそろえ、議事録の時刻から音声を聞き返せるようにする。実行は途中で 1 回自動で積み直され、再開後は 21 工程・約 42 分だった。工程ごとの報告書はマージ後に消したので、セッション中に読んだ計画・レビュー・実行の出力と、マージされた差分から書いている。

- 決定の記録: [録音の保存](https://github.com/daiki-beppu/live-mindmap/issues/43)

**セッション**は、1 つの会議について開始から終了までマップを組み立てる一続きの作業のこと。

### 1. 録音と発言の時刻をそろえるには、両方の「空白の数え方」を同じ規則にする

発言の時刻は、ヘルパーが取得を始める直前を 0 秒とした、2 トラック共通の秒数で数えている。録音の側は、最初の音声が届くまでの差の分だけ、先頭に無音を書き込む。一方で、取得の途中の空白は無音で埋めない。

```swift
/// 途中の取得の空白は無音で埋めない。発言の時刻（`TrackTimeline`）も空白を数えないので、同じ規則にそろえることで
/// 発言の時刻と録音の位置が一致する。
```

途中の空白も埋めるほうが「実時間の録音」としては自然に見える。しかし、発言の時刻は届いた音声の量で数えているので、録音だけ空白を埋めると、空白の後ろで発言の時刻と録音の位置がずれる。**2 つの記録を同じ時間軸に乗せるときは、片方を「正しい時刻」に合わせるのではなく、もう片方と同じ数え方にそろえる**。テストも、録音の位置と発言の時刻が一致することを確かめる形にした。

### 2. 後で使う予定の処理は、今のうちに入力の条件を要件に書いておく

計画の段階で、録音はモノラル（会議アプリの音はステレオなので左右を混ぜる）と決まっていた。人から「モノラルにすると、後で話者分離するときに邪魔にならないか」という問いが出た。

調べると、会議アプリは全員の声を 1 本に混ぜて左右に同じ音を出しているので、チャンネルに話者の情報はない。pyannote などの話者分離も、入力を最初にモノラル 16 kHz にする。効くのはチャンネル数ではなく音質だった。そこで、実行中の takt に追加の指示を送り、同じ内容を issue にもコメントで残した。

> 後で話者分離にかけられるよう、AAC は 64kbps 以上、サンプルレートは 16kHz 以上を保つこと。値は名前付きの定数にし、テストで形式を確かめる。

実装は 48 kHz・64 kbps・モノラルの定数になり、コメントにこの理由が残った。**今は使わない後段の処理（話者分離）があるなら、その入力の条件だけは今の要件に入れる**。録音し直すことはできない。

### 3. エージェントが環境について思い込んだら、議論させずに事実を渡す

実装の途中で、実装と計画のやり直しが 4 回続いた。実行の出力を見ると、エージェントは「この環境には Xcode がなく、Swift のテストをビルドできない」と考え、テストを XCTest に移すか省くかで計画を立て直していた。

実際には、ヘルパーのテストは `cd helper && pnpm test` で流れる。package.json の script が、Command Line Tools に入っているテストのプラグインの場所を渡しているからだ。同じ日の [11 のエントリ](#duplicate-mark) の作業では 70 件が通っていた。この事実を、実行中のタスクへの追加の指示として送ると、やり直しは止まり、レビューまで進んだ。最終的にヘルパーのテストは 85 件すべて通った。

指示を送るときに、1 つつまずいた。送り先の run（1 回の実行）を指定したら「実行中のタスクにない」と断られた。計画のやり直しが途中で止まり、takt が新しい run を立てて自動で再開していた。新しい run を指定して送り直した。

**工程ごとに別のエージェントが動く仕組みでは、ある工程の思い込みが、次の工程にも引き継がれる。環境の事実は、気づいた時点で外から渡す**。前日のエントリ（[ヘルパーの文字起こしの話の 6 節](./2026-10-01.md#helper-transcription-by-agent)）で「環境に合わせた実行コマンドは、スクリプトに 1 か所だけ書く」とした。スクリプトはあったが、それを使えばよいと知らないエージェントには届かなかった。

### 4. 終わりの処理の失敗も、呼んだ側に返す

レビューでは、3 つの観点が同じ 1 件を指摘した。会議の終わりに、サンプルレートの変換器に残った末尾の音声を書き出す。ここで失敗しても、トラックはエラーにならず、ヘルパーは終了コード 0 で終わっていた。録音が壊れていても、誰も気づかない。

修正では、末尾の書き出しに失敗してもファイルは閉じたうえで、その失敗を投げるようにした。**後片付けの処理は「最後までやる」ことと「失敗を返す」ことを両立させる。失敗したから途中でやめる、でも、失敗を黙って飲み込む、でもない**。

### 5. 待ち時間の長い作業ブランチは、マージの前に main とのずれを確かめる

PR ができた時点で、main と衝突していた。takt が動いていた約 1 時間の間に、別の作業で README にライセンスと認証の節が入っていた。録音の確認手順の追記とぶつかっただけなので、両方を残してつなぎ直し、マージした。

自動のマージは、PR が衝突していると止まる。**長く走る自動の実装は、PR ができたらまず main との衝突を確かめる**。
