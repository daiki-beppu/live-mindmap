# Haiku 5.5 と Sonnet 5.5 を同じ素材で cli eval にかける（issue #614）

2026-10-09 に、16GB の M4 で計測した。2 つのモデルを交互に 1 本ずつ流した。使い捨てのブランチで、main には入れない。

## 条件

- 素材: 「ローカルの候補モデルを 16GB の M4 で回帰評価にかける」（#380）と同じ `synth/screen`（23 分・78 発言・画面 15 回、正解は決定 5・TODO 7、共有画面の正解あり）と `synth/facilitators`（55 分・171 発言、正解は決定 4・TODO 5）。`play` は待ち時間なし（#380 と同じ）
- モデルは `claude-sonnet-5-5` と `claude-haiku-5-5`。effort は両方とも `options.effort: "medium"` で明示した（今の Sonnet 5.5 が実際に使っている値）。プロンプト・開き直し（14 回ごと）・5 分 TTL のキャッシュは今のまま
- 差し替えは評価用の一時的なパッチ（[eval-only.patch](eval-only.patch)）で行った。`LM_EVAL_MODEL`・`LM_EVAL_EFFORT` を読み、差分更新 1 回ごとに result の `usage`・`modelUsage`・API の要求ごとの usage を JSONL に書く
- 認証は Claude Code のサブスク（`env -u ANTHROPIC_API_KEY`）。流し方は [run.sh](run.sh)
- 各モデル・各素材 2 本ずつ、計 8 本

## トークンと料金の数え方

- 料金は `total_cost_usd` ではなく、トークン数に公式の料金表の単価を掛けて出した（$/MTok）
  - Sonnet 5.5: 入力 2・出力 10・書き込み（5 分）2.50・読み出し 0.10
  - Haiku 5.5: 入力 0.10・出力 0.50・書き込み 0.125・読み出し 0.01。入力（キャッシュの読み書きを含む）が 10 万を超えた要求は、5 倍の表
- **result の `usage` は、差分更新 1 回の最後の API の要求の分しか持たない。** 構造化出力をやり直した回（`num_turns` が 3）では要求が 2 回走るが、`usage.iterations` には 1 つしか入らない。そこで次のように数えた（[cost.mjs](cost.mjs)）
  - 要求ごとの入力側（input・cache_read・cache_creation）は、assistant メッセージの `message.usage`（要求の始まりの値）を `message.id` で重複を除いて取る。10 万トークン超の判定もこの値で行う
  - 出力は、最後の要求の分を `iterations` から取る。それより前の要求の分は、`modelUsage`（query ごとの累計）の差分から、最後の要求の分を引いた残りとする
  - 入力側の合計が `modelUsage` の差分と合うことを、全回で検算した（ずれは 0 回）
- `total_cost_usd` は使えない。Haiku 5.5 でも Sonnet 5.5 より高く出る（screen で $2.7〜3.2）。同梱の Claude Code が Haiku 5.5 の単価を知らないためとみられる。Sonnet 5.5 でも 1〜2 割高く出る
- Claude Code は query を開くたびに、補助の呼び出し（`claude-haiku-4-5-20251001`、入力 1〜3k・出力 20 前後）を 1 回する。差分更新のモデルによらず同じなので、本体とは別の列に分けた（Haiku 4.5 の $1 / $5 で計算）
- 呼び出しごとの内訳: `<ラン>.calls.tsv`（列は 差分更新の番号・要求の番号・秒・input・cache_read・cache_write・output・入力の合計・10 万超・料金）

## 分かったこと

1. **品質は下限（Sonnet 5.5 から落ちないこと）を満たさない。** screen では、決定の再現率が Sonnet 4/5・4/5 に対し、Haiku は 2/5・3/5 だった。facilitators では、TODO が 3/5・3/5 に対し 2/5・1/5 だった。画面を指す発言も 4・2 に対し 2・0 と少ない。捨てた操作は screen で 4〜6 倍（Sonnet 2・5、Haiku 20・29）。スキーマ違反・失敗は、どちらも 0
2. **effort を medium に揃えると、Haiku 5.5 のほうが遅い。** thinking が Sonnet の約 8〜9 倍出る（1 会議の合計で、screen は 7.0k・8.7k に対し 59.6k・64.1k、facilitators は 7.9k・7.7k に対し 74.2k・71.9k）。1 回の秒数の中央は、screen で 5.1・5.7 秒に対し 10.3・10.5 秒、facilitators で 5.3・5.6 秒に対し 6.5・6.9 秒だった。最大は 10〜18 秒に対し 20〜30 秒
3. **料金は 1/7〜1/10 で、公表単価の比（1/20）ほどは下がらない。** 1 会議あたり、screen は $0.58〜0.64 に対し $0.08〜0.09、facilitators は $1.07〜1.12 に対し $0.11 だった。出力（thinking）が 3.5 倍、読み出しが 1.2〜1.7 倍に増えたため
4. **10 万トークンを超えた要求は 0 回。** ただし、Haiku の screen 2 は最大 91.7k まで行った。画像つきの会議で、開き直しの直前の回が 10 万に近づく。facilitators（画像なし・55 分）は最大 56.6k
5. **`total_cost_usd` は Haiku 5.5 の料金を表さない**（実際の 30〜40 倍）。`usage` も、構造化出力をやり直した回は最後の要求の分しか無い。料金を出すときは、要求ごとの usage と `modelUsage` の差分を使う

## 追加: 等速（`--realtime`）での反映までの遅れ

上の 8 本は待ち時間なしで流したので、発言が届いてからマップに反映されるまでの遅れは測れていない。そこで screen を `--realtime` で、2 つのモデルを同時に 1 本ずつ流した（[run2.sh](run2.sh)、条件はほかと同じ）。遅れは、ログの発言の `at`（届いた時刻）から、その発言を `input.fresh` に含む `diff` の `at`（反映してログに書いた時刻）までとした（[lagReal.mjs](lagReal.mjs)）。呼び出しごとの内訳は `*-rt1.calls.tsv`。

| ラン | 差分更新 | 反映までの遅れ（中央 / p90 / 最大） | 1 回の秒数（中央 / 最大） | 出力（うち thinking） | 10 万超の要求（入力の最大） | 料金（usage×単価） | 捨てた操作 / 操作 | 決定 | TODO |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Sonnet screen 等速 | 78 | 5.5 / 8.0 / 10.5 秒 | 4.0 / 9.0 秒 | 30.1k（8.3k） | 0（41.4k） | $0.892 | 2 / 202 | 4/5 | 5/7 |
| Haiku screen 等速 | 78 | 7.0 / 11.5 / 23.7 秒 | 5.4 / 22.2 秒 | 87.9k（60.0k） | 0（59.2k） | $0.096 | 25 / 187 | 3/5 | 3/7 |

- 等速では、発言の間隔（中央 17 秒、最短 9 秒）が無音の判定（1.5 秒）より長いので、78 回すべてが 1 発言ずつの呼び出しになった。待ち行列はできなかった
- 遅れは、ふだん（中央）は 1.5 秒の差、裾（p90・最大）は Haiku が 1.4〜2.3 倍
- 1 発言ずつなので 1 回の入力が小さく、Haiku の 1 回の中央は 5.4 秒まで縮んだ（待ち時間なしでは 2 発言ずつで 10.3・10.5 秒）
- 呼び出しが 2 倍になるので、料金は待ち時間なしより上がった（Sonnet $0.58〜0.64 → $0.89、Haiku $0.08〜0.09 → $0.10）。比は 1/9.3
- 失敗・不正な出力は、どちらも 0
