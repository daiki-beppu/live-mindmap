## 画面のカメラの決め方を 1 つの表に集めたら、直したかった 3 つの食い違いは本体の 2〜8 行で直ったが、そのうち 2 つは表の外にも手が要り、「1 回だけ呼ぶ」は 2 通りに読まれた話

画面のマップには「カメラ」がある。マップのどこを、どの倍率で映すかを決めるもので、見方は 4 つある。今の議題（直近の差分更新で変わったノードが属する議題）に追従する「自動」、人が動かした位置を保つ「手動」、マップ全体を収める「全体」、最後の反映（AI の差分をマップに当てること）で変わったノードへ寄る「変わったところ」だ。この見方と見る位置を決める所が、web の 3 か所（キーやクリックを受ける見方の reducer、そこが出す「カメラの命令」の振り分け、表示面）に分かれていた。仕様 [#1702](https://github.com/daiki-beppu/live-mindmap/issues/1702)（親 [#1709](https://github.com/daiki-beppu/live-mindmap/issues/1709)）で、これをカメラの module 1 つの状態と遷移（`stepCamera`）に集め、残っていた 3 つの食い違いを直した。子は 5 本で、順に [#1710](https://github.com/daiki-beppu/live-mindmap/issues/1710)（畳んだ結果を 1 回だけ作る下ごしらえ）、[#1712](https://github.com/daiki-beppu/live-mindmap/issues/1712)（振る舞いを変えずに表へ集める）、[#1713](https://github.com/daiki-beppu/live-mindmap/issues/1713)・[#1715](https://github.com/daiki-beppu/live-mindmap/issues/1715)・[#1717](https://github.com/daiki-beppu/live-mindmap/issues/1717)（食い違いを 1 つずつ直す）。どれも takt（issue を計画・テスト・実装・レビューまで自動で回すワークフロー）で実装した。

### 1. 「1 回だけ呼ぶ」と書いた完了条件は、「呼ぶ所が 1 か所」とも「評価が 1 回」とも読める。数えるものを書かないと、run は止まり、レビューは別の読み方で差し戻す

画面では、済んだ議題などを畳んで（子孫を隠して 1 つにまとめて）見せる。何をどう畳むかは畳む module の `foldView` が決める。#1710 は、マップ面の 1 回の更新で `foldView` を 1 回だけ呼び、その値から見方の reducer に渡す木と、カメラが読む「見えているもの」（`seen`）の両方を作る、という作り替えだった。2 つが別々に畳み直していると、見方が使った見せ方とカメラが寄せ先を決めた見せ方が食い違いうるからだ。

10/28 に takt が #1710 を 3 回流し、3 回とも止まった。「1 回だけ」が更新前の状態を畳む所にも及ぶのか、決められなかったのだ。人の開閉は、更新前の見せ方を見て「どのノードを開閉したか」を決めるので、更新前にも畳む必要がある。10/30 14:51（日本時間、以下同じ）に issue へ「数えるのは更新後の状態の `FoldView` だけ。更新前の状態から作るものは数えない」とコメントし、3 分後に始めた run は 38 分で通った。この run は先に、更新後の引数で畳んだ回数を数えるテストを書き、実装の前に開閉の後は 4 回、選択を変えた後は 3 回で落ちることを確かめてから、畳む所を 1 つの関数に集めた。レビューの 4 観点も、指摘 0 件で通した。

ところが PR を作った後のマージの run で、裁定役（レビューの指摘をまとめて判定する役）が P1 を立てた。反映で選択が移ると、更新先のスナップショットを畳んだ後に、同じスナップショットをもう一度畳む、という指摘だ。takt の直しの段は、本番のコードを変えずに止まった。消せない理由は依存の循環だった。

1. 反映で消えたノードを選んでいたら、選択の移し先を決める。候補には、更新先を畳んだときにできる「議題 N 件」のまとめも入る。だから先に、更新先を今の選択で畳む（1 回目）
2. 反映の結果、選択が移るか、人の畳みが解ける
3. `foldView` は選択と人の開閉を引数に取るので、2. で引数が変わったら畳み直す（2 回目）

1 回目を省くとまとめが移し先の候補から外れ、1 回目の結果を使い回すと、選んだノードまでの鎖が開かれない。どちらも利用者に見える動きが変わる。直しの担当は「完了条件を『呼ぶ所が 1 か所』と読んで受け入れる」か、「畳む module の interface を変えてでも評価を 1 回にする」かを人に返した。人は前者を選び、「2 回目の評価は、振る舞いとして正しいので残す」とした。

10/28 の 3 回の停止と、10/30 の P1 は、同じ曖昧さの表と裏だった。run は「更新前も数えるのか」で迷い、裁定役は「呼ぶ所は 1 つでも、評価は 2 回ある」と数えた。「N 回だけ」を完了条件に書くときは、数えるのが呼ぶ所の数か評価の回数か、どの状態から作るものを数えるかまで書く。そのうえで、評価の回数を減らしたいなら、2 回目が要る理由（ここでは選択の移し先と畳み方の循環）が無いかを先に確かめる。

### 2. 直したい食い違いを「表のセル」として残す作り替えを先に入れると、直しの子は本体の数行で済む。ただし、表の外に手が要るかは直してみるまで分からない

#1712 は、利用者から見た振る舞いを変えずに、カメラの決め方を `stepCamera` の中の 1 つの表に集めた。行が入力（反映・Esc・測り直し・カメラに関わらない入力など）、列が前の見方で、セルに「後の見方・見る位置の決め方・何を外すか」を置く。変更は 23 ファイルで +1087 −1832 行だった。命令の型を消したので、命令が出たかを見ていた見方の reducer のテストは 897 行が消え、最後の見る位置と見方を見る `it.each` の表に移った。

仕様が残した食い違いは 3 つあった。

- 何も変わらない反映ではカメラを動かさない、という門が、画面の大きさの変化・ノードの高さの測り直し・Esc にも効き、自動が今の議題に寄り直さない（#1713）
- 右の列を出した後、幅を測る前に `?`（キーの一覧）や C（字幕）を押すと、横にずらす保留が消える（#1715）
- 手動などで議題を開閉した後、500ms の動きの途中で `?` などを押すと、開閉したノードを画面の同じ点に残す錨が外れる（#1717）

#1712 の本文は「この 3 つが表の 1 か所の変更で直せる形にしておく」と書いた。直しの子の差分は、カメラの module だけ見ると次のとおりで、テストの方がずっと大きい。

| 子 | `camera.ts` | 表の story のテスト |
|---|---|---|
| #1715（列のずらしの保留） | +3 −2 | +73 −23 |
| #1713（門を反映にだけ効かせる） | +8 −5 | +39 −17 |
| #1717（錨を外す入力を絞る） | +2 −2 | +163 −20 |

ただ「表の 1 か所」で済んだのは #1715 だけだった。#1713 は、門の判定そのもの（表の外の、見る位置を決める関数）に「反映のときだけ」の条件を足し、見る位置の決め方に新しい種類（`refocus`）を 1 つ足した。「選択で畳み方が変わった」はカメラに関わらない入力として届くので、前後の `seen` でノードの位置が変わったかを比べて寄り直すかを決める関数も要った。

#1717 はもっと手間取った。issue は「直すのは `stepCamera` の表のこの決まりだけ」と縛っていたが、表を直すだけでは、開閉したノードが「議題 N 件」のまとめに吸われたとき、見えている先を同じ点に残せなかった。錨の位置を探す関数が、吸われたノードの id のまま位置を引いていたからだ。takt の run は 20:57 から 56 分走って失敗し、自動の再投入の 2 回も 4 分ずつで失敗した（失敗の中身は run の記録に残っていない）。翌 0:47 に issue へ「錨の位置を探す関数は、既にある `shownIdOf` で読み替えて直してよい」という例外を足すと、4 回目の run が通った。縛りが仕様から写したものだと、takt の計画の段はそれを外せない。人が issue を書き換えるまで、run は止まり続ける。

その読み替えも、1 回では足りなかった。`shownIdOf` は、隠れたノードの id を見えているまとめの id に読み替え、もう無いまとめの id はその先頭の議題に戻す。開閉の前のまとめ `run:A` は、1 回目で先頭の議題 `A` に戻り、`A` が今は別のまとめ `run:X` に入っていれば、2 回目で `run:X` になる。だから実装は `seen.shownIdOf(seen.shownIdOf(id))` と 2 回かけている。読み替えの関数が「別の種類の id」を返しうるなら、もう 1 回かけて止まるかを確かめる。

作り替えで直しを小さくする狙いは当たった。けれども「1 か所で直せる」は、直しを書いてみる前の見込みだった。食い違いを直す子に「表のこの決まりだけ」と縛りを書くなら、表が呼ぶ関数にも手が要るかを、作り替えの PR で一度直してみて確かめる。確かめないなら、縛りに「表が呼ぶ関数は、この約束を満たすのに要る分だけ直してよい」と逃げ道を書いておく。

### 3. 振る舞いを変えない作り替えは、既知の食い違いを「今の動き」としてテストに固定する。直す子は、行を足すだけでなく固定した行を書き換える

命令を返す形をやめた理由は、テストが命令しか見ていなかったことにある。命令は `follow`・`hold`・`fitAll`・`fitChanged` の 4 つで、どれも中身を運ばず、表示面が見方を読み直して実際の動きを決めていた。`hold`（保つ）という名前なのに、全体と変わったところでは収め直していた。見方のテストは「どの命令が出たか」を見るので、何もしない命令や、表示面の読み直しの誤りでは落ちない。以前、F キーを押しても変わったところに寄らない不具合（#1223）を直したときは、4 ファイルとテスト 257 行を一緒に変えた。

#1712 は振る舞いを変えないので、3 つの食い違いも今の動きのまま表のテストに入る。マージの run のレビューは、3 つを「範囲外なので指摘にしない懸念」として挙げ、後の子に回した。実際、#1717 は「開閉の後にクリックで選ぶと錨が外れる」を期待していたテストを消して、「外れない」に書き換えている。直す子の issue は「行を足して赤を確かめてから直す」と書いていたが、今の動きを固定した行が反転することは書いていなかった。作り替えの PR で食い違いを固定するなら、どの行が後で反転するかを、直す子の本文に名前で書いておく。

### 4. 「直す前に落ちたこと」を報告に求めても、takt の PR の本文には残らない。補うなら、テストは今の版のまま、本体だけを直す前の版に戻して比べる

#1713・#1715・#1717 の issue は、足した行が直す前に落ちたことを実装の報告に書くよう求めていた。takt の PR の本文は 3 本とも「Workflow `default` completed successfully.」だけで、その証拠は無い（1 回で通った run の報告は本文に写らない）。マージの run の扱いは分かれた。#1742（#1715）・#1757（#1717）の裁定は「未確認」として通し、#1743（#1713）の裁定だけが「issue が報告への記載を明示している」として直す対象にした。同じモデル・同じワークフローで、裁定の時刻が 1 分しか違わない 2 本の判断だ。

#1743 の直しの段は、過去の順序を推測で書かないことにして、事後の比較を取った。別の worktree で、テスト・依存・設定は PR の版のまま、`camera.ts` だけを直す前の版に置き換え、足した 4 行を名前で絞って流した。

```sh
pnpm --filter @live-mindmap/web test test/mapSurfaceCamera.story.test.ts -t '空の反映の後の(画面サイズ変更|ノードの高さ変更|選択による畳み変更| Esc)'
```

直す前の版では 4 件とも落ちた。高さ・選択・Esc の 3 件は、見る位置の y が 3 件とも 87.8 のまま（期待はそれぞれ −28.8・−31.0・48.2）で、カメラが動いていないことがそのまま数字に出た。PR の版では 4 件とも通った。この比較は 1 回目、手元に報告を作っただけで PR に載らず、検証の段に差し戻されてから PR のコメントに公開された。run は 24 段・49 分で、ほかの 3 本（11 段・12〜20 分）の倍以上かかった。

「テストを先に足して赤を見た」順序は、後からは証明できない。けれども、テストを今の版に固定して本体だけを戻した比較は、「このテストは直したことを捉えている」の証拠としては同じ働きをする。takt の報告が本文に写らない以上、赤の証拠が要る子では、この比較を完了条件に書く方が確実だ。

### 5. takt のマージの run が動いている PR に手で push すると、同じ直しが 2 つ作られ、run の push が落ちる

#1732（#1710 の PR）を作った後、main に別の PR（#1731）が先に入った。#1731 は、#1732 が消した関数を使う行を足していて、合わせると型チェックが落ちる。人は 15:42 にその行を `seen` の比較に移すコミットを手で push した。同じころ、takt のマージの run も同じ指摘で差し戻され、15:51〜16:01 に同じ直し（2 行の追加と 2 行の削除）を作り直していた。run の push は `! [rejected] ... (fetch first)` で落ち、そのレビューは失敗として終わった。

害は無駄な 1 周で済んだが、マージの run は PR の head を取り込んでから直しを作るので、その間に人が push すると必ずこうなる。手で直すなら、先にその PR のマージの run が動いていないかを見る。

## CI を PR・main への push・Nightly・Weekly の段に分けたら、最長ジョブは 150 秒から 88 秒に縮んだが 60 秒には届かず、仕様の「今と同じく」は 2 か所で今と違い、Nightly は 1 晩目にテストの揺れを拾った話

この repo の CI（GitHub Actions）は、PR ごとに必須チェック `check` が green になるのを待ってからマージする。PR を出すのは人だけでなく、takt（issue を計画・テスト・実装・レビューまで自動で回し、PR を作るワークフロー）も 1 本ずつ直列に出すので、`check` の待ちはそのまま開発の速さになる。その待ちが、通常時でも最長のジョブで 128 秒（2026-10-24〜28 の 100 本の p50）かかり、10/28 には Node の取得が遅れて 1 時間 56 分かかったジョブもあった。仕様 [#1706](https://github.com/daiki-beppu/live-mindmap/issues/1706)（親 [#1711](https://github.com/daiki-beppu/live-mindmap/issues/1711)）で、CI を「PR」「main への push」「Nightly」「Weekly」の 4 つの段に分け、helper（音声と画面を取り込む macOS の Swift のプロセス）を触らない PR で最長ジョブの稼働を 60 秒以内にすることを目指した。子は 7 本で、時間切れと古い run の取り消し（[#1714](https://github.com/daiki-beppu/live-mindmap/issues/1714)）、helper のテストの時間制限（[#1716](https://github.com/daiki-beppu/live-mindmap/issues/1716)）、外部から取得するテストの切り分け（[#1718](https://github.com/daiki-beppu/live-mindmap/issues/1718)）、ジョブ定義の共有（[#1719](https://github.com/daiki-beppu/live-mindmap/issues/1719)）、ジョブの分割（[#1720](https://github.com/daiki-beppu/live-mindmap/issues/1720)）、Nightly・Weekly の追加（[#1721](https://github.com/daiki-beppu/live-mindmap/issues/1721)）と失敗の知らせ（[#1722](https://github.com/daiki-beppu/live-mindmap/issues/1722)）。あわせて、helper の IT がときどき時間切れになる件（[#1681](https://github.com/daiki-beppu/live-mindmap/issues/1681)）も直した。

### 1. テストを段に振り分ける軸は、テストの層ではなく「結果を何が決めるか」で切る

この repo のテストには、unit・light IT（軽い結合テスト）・heavy IT（本物の子プロセスやブラウザを立てる重い結合テスト）という層がある。段を決めるときに、まず「heavy は夜だけ」のように層で切りたくなる。だが、マージを止めてよいかを決めるのは重さではない。そのテストの結果が、PR のコードだけで決まるかどうかだ。仕様では、層とは別の軸として次の 3 つに分けた。

| 結果を決めるもの | PR | main への push | Nightly | Weekly |
|---|---|---|---|---|
| コードだけ（型検査・unit・light IT・heavy IT・e2e の記録の再生） | 全件 | 全件 | 全件 | 全件・キャッシュなし |
| 外部からの取得（本物の `deps:install`・`npm ci`） | 管理する依存のパスに当たるときだけ | 走らせない | 走らせる | 走らせる |
| キャッシュで隠れる準備（音声処理ライブラリのビルド、話者分離のモデルの取得など） | キャッシュを使う | 使い、保存する | 使う | 使わず、保存もしない |

きっかけは 10/28 の障害だった。Chromium と Claude の SDK を本物の手順で入れて確かめる heavy IT の 2 本（`managedClaude.heavy`・`managedDeps.heavy`）が、配布元の遅さで、コードと関係なく落ちた。この 2 本は heavy の定義を満たすので、層で切る限り PR に残る。そこで `*.external.test.ts` に改名し、vitest の project `external` に移して、PR ではその依存のパス（`server/managed-deps/**` など）に当たるときだけ流すようにした（[PR #1740](https://github.com/daiki-beppu/live-mindmap/pull/1740)）。#1740 自身は依存の README を変えたので external のジョブが走って 35 秒で通り、当たらない後続の PR 4 本ではどれも skipped になった。

逆に、e2e（画面を操作する端から端のテスト）は重いが、記録した応答を `--strict-cache` で再生するだけでモデルも資格情報も使わないので、「コードだけ」の側に入れて PR に残した。main への push の段に外部取得のテストを置かないのも同じ理由で、外の障害で main が赤くなると、「main が赤くなったら原因の PR を revert する」という手順を誤って踏むことになる。

### 2. 時間切れは「通常時の p90 の約 3 倍を 5 分単位で切り上げ、最小 5 分」と決め方で持つ。外から取るステップには、ジョブとは別に 5 分を付ける

10/28 に 2 時間近く待ったのは、ubuntu のジョブに `timeout-minutes` が無く、遅い取得を最後まで待ち続けたからだ。値を 1 つずつ考えると揺れで落ちる値を選びがちなので、仕様では決め方を書いた。今は、ほとんどのジョブが 5 分、外部取得のテストが 10 分、helper が 20 分（以前の 30 分から下げた）になっている。そのうえで、Node・pnpm の用意、`pnpm install`、キャッシュの復元、依存の導入、モデルの取得などの外から取るステップに、各 5 分の時間切れを付けた（[PR #1730](https://github.com/daiki-beppu/live-mindmap/pull/1730)）。止まったときに、どのステップの取得で止まったかがログに出る。

Node は、`pnpm/setup` に nodejs.org から落とさせるのをやめ、`actions/setup-node` でランナーにあらかじめ入っている版（toolcache）を使うようにした。効いたかどうかは、ジョブのログの `Found in cache @ /opt/hostedtoolcache/node/24.22.1/x64` の行で確かめた。

helper の Swift のテストは、止まると suite の名前も出ずにジョブの時間切れまで待っていた。IT の suite に `.timeLimit(.minutes(1))`、heavy の suite に `.timeLimit(.minutes(2))` を付け、付いていない suite があれば helper の型検査の段で `path:line` つきで落とす点検を足した（[PR #1724](https://github.com/daiki-beppu/live-mindmap/pull/1724)）。規則を文書に書くだけでは、次に足す人が忘れる。

### 3. ジョブを割っても 60 秒には届かなかった。偏りの元は、所要時間を見ずにファイルの並び順で配っていることと、1 本で 60 秒近いテストが残っていること

ts のジョブは、型検査・unit・light IT を 1 つのジョブで直列に流していた。これを「型検査と静的検査（fallow）」「unit」「light IT（server を 2 つに割る）」に分け、heavy は server を 2 つ、web を 3 つの runner に割った（[PR #1760](https://github.com/daiki-beppu/live-mindmap/pull/1760)）。影響のあるテストだけを選ぶ仕組みは入れず、全件を走らせたまま割っている。下は main への push の run の各ジョブの稼働時間（秒）で、before は割る前の 5 本、after は 10/31 の 6 本から取った。

| ジョブ | before（範囲 / p50） | after（範囲 / p50） |
|---|---|---|
| ts（型検査・unit・light IT を直列） | 145〜156 / 148 | — |
| 型検査・fallow | — | 22〜31 / 28 |
| unit | — | 39〜65 / 57 |
| light IT runner 0（server の半分と web の全件） | — | 54〜88 / 88 |
| light IT runner 1（server の残り半分） | — | 48〜72 / 61 |
| heavy server（割る前は 1 runner） | 98〜113 / 104 | — |
| heavy server 0/2（起動時間を測る 1 本だけ） | — | 57〜72 / 67 |
| heavy server 1/2（残り全部） | — | 60〜95 / 83 |
| heavy web（割る前は 2 runner） | 67〜89 | 43〜76（3 runner、p50 は 60・65・72） |
| e2e | 54〜60 / 55 | 53〜60 / 57 |

最長は 148 秒から 88 秒に縮んだが、60 秒には届いていない。いちばん長い light IT の runner 0 は、web の light IT を載せた分（約 2 秒）を引いても、runner 1 より 25 秒ほど長い。配り方は、テストの一覧を取ってファイル名の順に番号を振り、その剰余で runner を決めている。新しいファイルを足しても設定を書き換えずに済む代わりに、所要時間を見ないので、長いファイルが片方に寄れば寄ったままになる。heavy server の 0/2 は、bootstrap の時間を測る 1 本（`measureBootstrap.heavy`）だけを受け持って 67 秒かかる。1 本のテストを runner に分けることはできないので、この 1 本は割り方では 60 秒に収まらない。

仕様は、目標に届かなかったときに選択の仕組み（変えたファイルに関係するテストだけを流す `vitest related`）を入れ直す条件を、「割った後もファイルの中まで割れずに 60 秒を超えるとき」と書いている。light IT はまだ所要時間で配り直す余地があるので、この条件には当たらない。#1720 の「マージ後に人が確かめること」にあった after の表は、10/31 の時点で PR の本文に足されておらず、親 #1711 は開いたままだ。

### 4. 必須チェックを再利用できる workflow の外に残すと、中のジョブの結果が見えない。結果を出力で運び、欠けていたら落とす

段ごとにテストの流し方や時間切れが食い違わないよう、テストを流すジョブを 1 つの再利用できる workflow（`workflow_call`）にまとめ、PR・push・Nightly・Weekly がそれを入力つきで呼ぶ形にした（[PR #1756](https://github.com/daiki-beppu/live-mindmap/pull/1756)）。ここで必須チェック `check` は呼ぶ側の最上位に残した。再利用の中に入れるとチェックの名前が変わり、マージの規則（ruleset）を書き換えることになるからだ。

すると、呼ぶ側の `check` からは、呼び出し 1 つ分の結果しか見えない。再利用の側の最後に、7 つのテストのジョブの結果を JSON にまとめて出力する `results` のジョブを置き、`check` はその JSON のキーが 7 つちょうどあるか、どれも success か skipped かを確かめる。出力が欠けていたり壊れていたりしたときも落とす。「呼び出しは成功したが、中身の報告が無い」を通さないためだ。ジョブを増やしたら、集める側と確かめる側の両方に足す必要がある。

同じ PR に push し直したときの古い run の取り消しは、`concurrency` の group を `github.head_ref || github.run_id` にして入れた。PR では同じブランチの古い run が取り消され、main への push では run ごとに group が分かれるので取り消されない。取り消された run でも `check` は `if: always()` で走り、古い head の SHA に failure を付ける。空のコミットを push して確かめると、古い run は後のジョブがすべて cancelled になり、新しい head の run だけが green になった。ruleset が見るのは新しい head なので、マージは止まらない。

### 5. 仕様が「今と同じく」と書いた所を 2 か所、今の動きで確かめていなかった。形式仕様の検証は、表の中の矛盾は見つけても、表と今の workflow の食い違いは見つけない

仕様は 2 か所で、今の CI の動きを述べていた。どちらも違っていた。

- 「main への push では、helper は今と同じくパスで振り分ける」。実際の `check.yml` は、push のときは helper を常に流していた。
- 「キャッシュの保存は main への push だけ、今の方針のまま」。実際は、Playwright・音声処理ライブラリのビルド・話者モデルのキャッシュは PR でも保存していた。

仕様には、Quint（状態機械を書いて全状態を調べる形式仕様の言語）で書いた 13 本の不変条件のコメントが付いていて、検証は通っていた。ただし、モデルが写しているのは仕様の振り分け表で、今の workflow ではない。表の中で「push で外部取得を流す」のような矛盾があれば見つかるが、表の前提そのものが今と違っても気づけない。

食い違いが表に出たのは、ジョブ定義をまとめる #1719 だった。この子は「CI の振る舞いを変えない」作り替えで、仕様の「保存は push だけ」に合わせると振る舞いが変わる。takt の run が ABORT（自分で続けられないと判断して止まる）した後、issue に「この ticket では振る舞いを変えないを優先する」と決定を書き足してから流し直すと通った。今の `docs/agents/checks.md` には、振り分け表の下に「現行の `check.yml` は main への push では helper を常時実行する」と注記がある。仕様に「今と同じく」と書くなら、その行を書く前に今の設定ファイルを開いて確かめる。

### 6. Actions の上の結果は、takt の run の中からは観察できない。完了条件に入れると、run は止まる

#1714 と #1718 の takt の run は、どちらも実装と手元の確かめまで済ませたうえで止まった。完了条件の「同じ PR の古い run が取り消される」「管理する依存を変える PR でだけ external が走る」は、PR を作って Actions が動かないと見えない。takt が PR を作るのは run が終わった後なので、run の中からは確かめようがない。2 本とも人が手で引き取って PR にし、PR の CI の結果をコメントに残した。

残りの 4 本（#1719〜#1722）には、流す前に「run の中で確かめないこと（takt 用）」の節を足した。Actions の上の結果は完了条件にせず、run では `actionlint`・条件式の手元での判定・各層のテストまでを済ませ、Actions で確かめることは実装の報告に「PR の CI で確かめること」として書けば完了とする。#1720・#1721・#1722 については、ABORT を知らせる案内役（issue の流れを見張り、止まったら Discord で人に判断を頼む常駐のスクリプト）の記録が無く、そのまま PR になった。#1719 は止まったが、それは前の節の食い違いのためだ。

代わりに、観察は「マージ後に人が確かめること」として人の側に残る。そして、それは忘れられやすい。10/31 の時点で、Nightly・Weekly を `workflow_dispatch` で 1 回ずつ流す確かめも、#1720 の after の表も済んでいない。親の完了条件に書いてあるので、親が閉じないことで残っていることは見える。

### 7. Nightly は 1 晩目にテストの揺れを拾い、知らせの issue は設計どおりに立った。ただし schedule は 18:17 UTC の予定に対して 4 時間遅れて始まった

Nightly は、main の最新のコミットに対して、全件と helper と外部取得のテストを毎晩流す。落ちたら、段ごとに固定の題名（`Nightly の CI が落ちている`）の issue を探し、無ければ立て、あればコメントを足す（[PR #1766](https://github.com/daiki-beppu/live-mindmap/pull/1766)）。手で起動した run では立てない。次の run が通っても自動では閉じず、原因を書いた人が閉じる。

最初の schedule の run は、web の heavy IT の 1 つの runner で落ち、[#1768](https://github.com/daiki-beppu/live-mindmap/issues/1768) が立った。落ちたジョブだけを 1 回流し直すと通ったので、手順どおりテストの揺れとして調べた。画面のテストが議題のノードをクリックした直後に Enter を押していて、選択が画面の状態に届く前に Enter が来ると議題が開かない。選択が出る（`aria-pressed=true`）のを待ってから Enter を押すよう [#1783](https://github.com/daiki-beppu/live-mindmap/pull/1783) で直し、原因を書いて issue を閉じた。知らせの issue から、流し直し 1 回、原因の特定、直しの PR、原因を書いて閉じるまでが、文書に書いた手順どおりに約 5 時間で回った。

時刻は、PR の混む時間と、GitHub の schedule が遅れやすい毎時 0 分を避けて、18:17 UTC（03:17 JST）にしていた。それでも最初の run の作成は 22:26 UTC で、約 4 時間遅れた。定期段の結果を朝に見る前提で何かを組むなら、この遅れは見込んでおく。

### 8. CI の混み合いでだけ落ちる helper の IT は、CPU を埋めて手元で再現できた。原因は、並列のテストが 1 本の直列キューに並び、期限だけが一斉に数え始めていたこと

helper の IT は、手元（10 コアの Mac）では全体が約 9 秒で、何度流しても落ちないのに、CI ではたまに 30 秒の待ちの期限切れで落ち、流し直すと通っていた（#1681）。[PR #1820](https://github.com/daiki-beppu/live-mindmap/pull/1820) は、まず CI の混み合いを手元に持ち込む道具を作った。CPU のコア数の 1.6 倍の `yes` を走らせたまま IT を流すスクリプトだ。

```sh
cd helper && swift build --build-tests
bash scripts/stress-it.sh 3   # yes を 16 本（10 コアの場合）走らせて、IT を 3 回流す
```

直す前の main では 3 回とも落ち、毎回、CI と同じ 3 つのテストが同じ文言で落ちた。原因は製品のコードではなくテストの側にあった。録画の映像を読んで文字を読み取る処理は、プロセスに 1 本の直列キューを通る。並列に走る IT がみな同じキューに並び、30 秒の期限だけが並んだ時点から一斉に数え始めていた。負荷をかけた全体の実行では、キューが 44.2 秒のうち 43.5 秒ふさがり、1 件の待ちは最大 10.6 秒だった。映像を読む suite を `.serialized`（suite の中のテストを 1 本ずつ流す）にすると、9 回流して 1 度も落ちなかった。

もう 1 つの `pausedPairDoesNotAdvance` は、止めてから 500ms 寝た位置を写し、さらに 500ms 後に同じかを比べていた。キューで遅れた「止める前の読み」が写しの後に記録され、止まっている間に進んだように見えていた。固定の sleep をやめ、止まったことを期限つきで待ってから写す形に直した。直したテストが本当に止まることを確かめているかは、製品側の門の待ち（`waitOpen`）を空にすると直した後も 3/3 で赤になることで確かめた。

キューを読み手ごとに分ける製品側の試作も作ったが、負荷ありでは 3 回中 1 回、22 件が時間切れになったので退けた。代償もある。直列にした suite が IT の一番長い道になり、CI の helper の IT は 72.4 秒と、それまでの 28〜41 秒から 30〜40 秒伸びた。helper のジョブは 60 秒の目標の外にあるが、短くするなら直列にした suite の中の長いテストから手を付けることになる。
