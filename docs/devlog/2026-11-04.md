## 会議の画面と見返しが別々に書いていたマップ面のつなぎ方を 1 か所に集めたら、待っていた別の整理では重複が消えず、「落ちるテストが出たら守りを戻す」という逃げ道は素通りされた話

この Web アプリには、マップを描く部品（以下、マップ面）を使う画面が 2 つある。会議中に見る「会議の画面」と、会議の後に時刻を動かして組み上がりを見直す「見返し」だ。UI は Foldkit（Elm と同じ、Model・Message・update で組む TypeScript のフレームワーク）で書いている。2 つの画面は、マップ面の状態の持ち方、ノードの点滅の始め直し、見方（自動・手動・全体・変わったところ）が変わったときの知らせを、それぞれ自分で書いていた。利用者に見える振る舞いを変えずに、これを 1 か所へ集めた。決定は仕様 [#1876](https://github.com/daiki-beppu/live-mindmap/issues/1876) と、その元の [#1556](https://github.com/daiki-beppu/live-mindmap/issues/1556)・[#1557](https://github.com/daiki-beppu/live-mindmap/issues/1557)・[#1864](https://github.com/daiki-beppu/live-mindmap/issues/1864) にある。実装は AI エージェントの実行基盤 takt に 4 つのチケットとして流し、PR [#1902](https://github.com/daiki-beppu/live-mindmap/pull/1902)・[#1903](https://github.com/daiki-beppu/live-mindmap/pull/1903)・[#1904](https://github.com/daiki-beppu/live-mindmap/pull/1904)・[#1905](https://github.com/daiki-beppu/live-mindmap/pull/1905) で入った。この記事は issue と PR の差分を素材にし、takt の実行記録は読んでいない。実装者が途中で何を考えたかは分からないので、差分から言えることだけを書く。

### 1. 重複が別の整理の後に消えるかは、減った数ではなく「足すときに何か所直すか」で判断する

この作業は「画面のカメラの整理」と「畳む規則の整理」の 2 つの後に始めるほうがよいかもしれない、という待ちを抱えて保留していた。マップ面の Model のうち 14 個のフィールドを、2 つの画面が 1 行ずつ写していたからだ。先の 2 つで状態がまとまれば、写す量が減って作業そのものが要らなくなるかもしれない。

両方が入った後に数えると、14 個は 12 個になった。カメラの整理が 4 個を 1 個にまとめて 3 減り、畳む規則の整理が `foldingContext` を足して 1 増えた。

減ったのは数だけで、形は同じだった。しかも、増えた 1 個がそのまま反例になっている。`foldingContext` を足すときに、マップ面に加えて 2 つの画面にも同じ 1 行を足す必要があった。待ちは「数が減るかもしれない」という見立てだったが、問うべきは「フィールドを 1 つ足すと何か所直すか」で、答えは 3 か所のままだった。

直し方は 1 行に収まった。マップ面が、外から入る 3 つを除いた schema を自分で出す。

```ts
export const Stored = Model.mapFields(Struct.omit(["mode", "snapshot", "speakerNames"]));
```

2 つの画面の 12 行は `mapSurface: MapSurface.Stored` の 1 行になった。Model を組み立てる側の `surfaceOf` は共通にしなかった。スナップショットの出どころが、会議の画面は受信した feed、見返しは再生の時刻と画面ごとに違い、そこが 2 つの画面の役目の違いそのものだからだ。

### 2. 2 つの実装を 1 つにする前に、違いを「役目から来るもの」と「偶然のもの」に分け、偶然のものは画面で確かめる

まとめる前に、2 つの画面で違う所を 15 行の表にし、1 行ずつ意図か偶然かを決めた。抜粋するとこうなる。表の「反映」は AI の差分更新をマップに当てること、「測る」は描く前にマップの大きさを測ることを指す。

| 所 | 会議の画面 | 見返し | 判定 |
|---|---|---|---|
| スナップショットの出どころ | 受信した feed | 再生の時刻から求める | 意図 |
| Escape で先に閉じるもの | キーの一覧 | 速さのメニュー → キーの一覧 | 意図（会議の画面にメニューが無いだけ） |
| マップ面に渡す話者の名前 | feed の名前 | 空の `{}` | 偶然（不具合） |
| 測る前に反映を飛ばす守り | 無い | ある | 偶然（理由の記録が無い） |
| 点滅と知らせの順 | 点滅 → 知らせ | 知らせ → 点滅 | 偶然（互いに読み書きしない） |

意図の行は画面に残し、偶然の行はまとめて消す。この表があると、「1 か所に集める」が「全部を共通にする」にならない。Escape の順や再生のキーを無理に共通化すると、引数で分岐するだけの共通関数ができる。

話者の名前の行は、設計レビューの時点では「漏れかもしれない（画面では未確認）」だった。実物で見返しを開くと、字幕には付けた名前が出ているのに、同じ人のノードは `相手 A` のままだった。意図ではなく不具合と確定できたので、別のチケットに切り出して先に直した。

### 3. 同じ「変わったら何かする」でも、置き場所は Command の持ち主と届け先で分かれる

スナップショットが変わったときの処理のうち、点滅の始め直しと見方の知らせは、どちらも前後を比べて何かを足す手順で、形はよく似ている。それでも置き場所は分けた。

- **点滅の始め直しはマップ面の update の中。** Command の `RestartBlink` も、条件が読む点滅中のノードも、マップ面の内側にある。外の入口は「新しいスナップショットを渡す」1 本のままで、後ろの仕事だけが増える
- **知らせは親の前後比較。** 知らせを出す部品はマップ面の兄弟で、マップ面の外にある。子から兄弟へは OutMessage で親を通すのが Foldkit の形だが、1 回の返り値に OutMessage は 1 つしか持てない。クリックでノードを選ぶと、選択の OutMessage と見方の変化が同じ返り値に重なる

前後比較には、もう 1 つ利点がある。見方を変える Message が今後増えても、親の比較は変えなくてよい。`surfaceFolds`（2 つの画面が使う共通の手順）が返す包みは、こうなった。

```ts
withViewingNotice: (before, result) => {
  const was = parent.read(before);
  const now = parent.read(result.model);
  if (Option.isNone(was) || Option.isNone(now) || was.value.camera.mode === now.value.camera.mode) return result;
  return Update.combine(before, [() => result, (model) => parent.onViewingMode(model, now.value.camera.mode)]);
},
```

見返しの update の末尾は、この包みをかける 1 行になった。行数は会議の画面が 185 → 151、見返しが 326 → 303 で、その間に写しと外す手順と比べる手順が消えた。行数そのものより、3 つ目の画面が 4 つの値（`read`・`write`・`toParentMessage`・`onViewingMode`）を渡すだけでつなげる形になったことが大きい。

### 4. 形式仕様が通っても、抽象化で落とした順序とフィールド名は確かめられていない

仕様には Quint の形式仕様があり、点滅・知らせ・Escape の順の不変条件を全状態で調べて通っていた。各性質は、1 か所だけ壊した mutant（わざと壊した版）で赤くなることも確かめてある。

ところが、チケットを切る段で実コードを読むと、形式仕様が見ていない落とし穴が 4 つ出てきた。

- **無いフィールド。** 仕様は「`viewing.mode` を比べる」と書いていたが、そのフィールドは無く、比べるべきは `camera.mode` だった。仕様の元の決定を書いた後に、カメラの整理が入っていた。形式仕様は `viewMode` という抽象の変数なので、名前のずれには関係なく通る
- **早く返す分岐。** スナップショットを受ける update には、判断軸（ノードに付く、選ぶときの観点）だけの変化などで早く返す分岐がいくつもある。前の実装は分岐と関係なく前後の Model で決めていたので、分岐の中に点滅を足すと漏れる。実装は本体を `replaceSnapshot` に切り出し、その外側で 1 回だけ判定する形になった
- **渡す順序。** `read` は feed や再生の時刻から「前」のスナップショットを組み立てる。feed を新しい値に置き換えた後の Model を渡すと、前と後が同じになる
- **最初の frame。** 会議の画面はセッションができる前は `read` が None を返す。比べる片方が無いときは足さない

形式仕様が悪いのではない。抽象化は順序や名前を落とすから全状態を調べられるのであって、これは役割の違いだ。形式仕様が守るのは「何が成り立つべきか」で、「コードのどこで間違えやすいか」は、コードを読まないと書けない。

3 つ目の落とし穴を契約テスト（後述）が捕まえるかは、この記事を書くときに試した。見返しで置き換えた後の Model を渡すように書き換えると、12 件中 1 件（見返しの点滅）が落ちた。

### 5. 「落ちるテストが出たら守りを戻す」という逃げ道は、どんなテストかまで書かないと素通りされる

見返しだけが持っていた、測る前に反映を飛ばす守りには、要る理由の記録が無かった。git で辿ると、別の変更のついでに入ったものだった。そこで仕様にこう書いた。

> `size` が無いときに `changedSnapshot` を飛ばす守りは外す。測る前は map surface の条件が `RestartBlink` を出さないので、点滅の振る舞いは変わらない。外して落ちるテストが出たときだけ、両方の画面に同じ守りを置く。

PR は守りを外し、CI も通っていた。ただ、差分を読むと既存のテストが書き換わっている。

```diff
-  it("移動は時刻だけを変える。playing・rate・muted・volume と表示面の実測は変わらず、Command も無い", () => {
+  it("時刻を動かしても playing・rate・muted・volume と表示面の実測は変わらず、未測定なら Command も無い", () => {
...
-    expect(result.model.mapSurface).toEqual(start.mapSurface);
+    expect(result.model.mapSurface.size).toEqual(start.mapSurface.size);
+    expect(result.model.mapSurface.nodeHeights).toEqual(start.mapSurface.nodeHeights);
```

この記事を書くときに、古いテストを今の実装で流して確かめた。やはり落ちた。測る前に時刻を動かすと、今の議題・畳みの文脈の時刻（30 → 10）・`idleStamp`（触らずに待つ時間の計り直しの印、0 → 1）が動く。つまり「外して落ちるテスト」は実際に出ていて、守りは戻らず、テストのほうが狭められた。チケットの「書き直すテスト」の一覧に、このテストは無い。PR の本文やコメントにも記録が無い。

結論として、書き換えは妥当だと思う。落ちたテストは守りの効果そのものを確かめていて、害を示していない。会議の画面は守り無しで動いてきたし、測る前の画面には何も描かれていない。受け入れ条件も「守りが無い」と求めていた。

問題は結論ではなく、文の書き方にある。「落ちるテストが出たら」は、害を示すテストと、消す仕組みの効果を確かめるだけのテストを区別しない。そのため実装者は、どちらに読んでも説明が付く。書くなら次のようにする。

- 落ちると分かっているテストを先に調べ、「書き直すテスト」の一覧に載せる
- 逃げ道の条件は、テストの有無ではなく振る舞いで書く（「測った後の表示や点滅が変わるテストが落ちたら」）
- 判断が要ったら、PR の本文に書かせる

### 6. 「2 回かけている」の害は、呼ぶ回数ではなく受け手で確かめる

会議の画面は、知らせの比較を `update` と、その内側の `received` の 2 か所でかけていた。3 つの文書がこれを違う言葉で書いている。

- 違いの表（#1556）: 「2 回目は差が無く何もしない」
- 形式仕様の mutant の表: 「今の会議の画面の二重がけ」を、知らせが 2 回になる壊れた形として扱う
- チケット: 「今の二重がけはこれを破る形」

コードを読むと、最初の説明は少し違っていた。どちらも同じ「更新前の Model」と比べるので、2 回目にも差はあり、知らせの手順は確かに 2 回呼ばれていた。それでも見えなかったのは、受け手の Toast が「今出している文と同じなら何もしない」からだ。

```ts
onSome: (text) => (Option.contains(shown, text) ? { model } : swapNotice(fold, text, options)(model)),
```

呼び出しは二重、利用者への知らせは 1 回。だから二重がけを消しても振る舞いは変わらない。逆に言えば、テストはこの二重がけを捕まえられない。試しに今の実装を二重がけに戻すと、契約テストと会議の画面のテスト、計 32 件は全部通った。テストは呼ぶ回数ではなく、画面に出る文言を見ているからだ。完了条件の「包みを 1 回だけかけている」を守っているのは、レビューだけになる。

これは欠陥ではないと判断している。見える結果が同じものをテストで縛ると、内部の構造を縛ることになる。ただ、形式仕様の「知らせが 1 回」と、実コードの「呼び出しが 1 回」は同じものではない。

### 7. 2 つの画面の契約は、1 本のテストを `describe.each` で当て、Command を子に移すならそれを通る既存のテストも解決する

点滅と知らせの契約は 2 つの画面で同じなのに、テストも別々に重なっていた。`mapSurfaceSnapshot.contract.story.test.ts` の 1 本にまとめ、`describe.each` で会議の画面と見返しの公開の `update` に当てた（6 件 × 2 画面で 12 件）。画面ごとに渡すのは初期の Model と、スナップショットを変える Message・変えない Message、知らせの読み方だけで、確かめるのは返る Command の名前と知らせの文言だけにした。

重なった分は消した。見返しの組み立てのテストは差し引き 32 行減った。画面ごとに残したのは、いつ渡すかの違いだ。見返しのシーク・時計・ボタン、会議の画面の取り込みの frame、見方を変える入口の違いが該当する。

想定に入っていなかったのは、テストの書き換えの範囲だ。チケットの「書き直すテスト」は `blinkRestartsOf` を直接呼ぶ story テストだけを挙げていた。実際には、マップ面に直接スナップショットを流す scene テスト（story テストが update だけを通すのに対し、画面の状態まで見るテスト）にも 9 か所の追記が要った。update が Command を返すようになると、Foldkit のテストは未解決の Command を残したまま次の Message を送ると例外を投げる（`I found unresolved Commands`）。

```ts
Subscription.emit(Message.ChangedSnapshot({ snapshot: after })),
Command.resolveAll([RestartBlink, Message.CompletedRestartBlink()]),
```

親が足していた Command を子へ移すと、親を通らないテストにまで新しい Command が現れる。利用者に見える振る舞いを変えない作り替えでも、テストの差分がゼロとは限らない。

## 改名の候補を 20 個出してどれも選ばれず、「変えない」と決まって README の 4 行だけが残った話

このツールの名前を、短い再帰的頭字語（GNU のように、頭文字の 1 つが名前自身を指す略語）に変えようとした。問いは map（大きな問いを子のチケットに分けて進める親の issue）[#1857](https://github.com/daiki-beppu/live-mindmap/issues/1857) に立てた。候補の案出しと衝突調査を重ねた末に、利用者は `live-mindmap` のまま前半の LIVE を **L**IVE **I**nstantly **V**isualizes **E**xchanges と読むことを選んだ（[#1861](https://github.com/daiki-beppu/live-mindmap/issues/1861)）。実装は仕様 [#1896](https://github.com/daiki-beppu/live-mindmap/issues/1896) のとおり、2 つの README への追記だけで、AI エージェントの実行基盤 takt に流して [PR #1909](https://github.com/daiki-beppu/live-mindmap/pull/1909) で入った。この記事は issue・その編集履歴・PR の差分を素材にし、takt の実行記録は読んでいない。

### 1. 依頼文の欠けた条件を「分かったら足す」で保留すると、候補をいくら出しても的を外す

map を立てた最初の版に、すでに次の 1 行があった。

> 依頼文にもう 1 つ条件があったようだが、欠けていた（「◯◯と再帰的頭字語であること」）。分かったらここに足す。

この行は、日本時間 11 月 3 日 0 時 14 分の作成から、名前が決まる 11 月 4 日 12 時 59 分の編集まで、約 37 時間そのまま残った。その間に絞った候補は 20 個になる。issue に残る 3 回の問いにも、この条件を尋ねたものは無い。

最後の編集で、この行は次のように解消された。答えは「〇〇map で考えて」から「live-mindmap のまま、それを基に再帰的頭字語にする」に変わった、と。20 個のうち `map` を含むのは `lmap` の 1 個だけで、他は `hum` や `vine` のように、map と関係のない語から探していた。

答えがいつ返ったかの時刻は残っていない。先に答えを聞いていれば 20 個が要らなかったとまでは言えない。それでも、探す範囲を決める条件が欠けていると気づいた時点で、候補を出す前に 1 問聞くのは安い。欠けに気づいて書き留めたのに、書き留めただけで先へ進んでいた。

### 2. 「新しい名前を決める」という問いには、「変えない」という答えが入らない

map の目的地は「新しい名前を 1 つに決め、改名が及ぶ範囲とその順序まで決める」だった。この時点で、変えないという答えが選択肢から消えている。

| 回 | 出した案 | 推奨 | 返事 |
|---|---|---|---|
| 1 | hum・lmap・vine・said | hum | 「全然そそらない」 |
| 2 | yak・limb・frond | yak | 「別のパターンで考えて」 |
| 3 | jinn・finn・wit・jin | jinn | 選ばれず、deep-research に回す |
| 4 | tidod・widod・odoti・edoti・udoti | tidod | 「live-mindmap のままでもいい気がしてきた」 |

どの回の表にも、今の名前の行が無い。改名の費用は [#1859](https://github.com/daiki-beppu/live-mindmap/issues/1859) で最初に調べてあったのに、後で決める互換の材料としてしか扱っていなかった。候補を選ぶ表と、費用の調査がつながっていなかった。

決まった後に振り返ると、今の名前には比べるだけの強みがあった。保存先や環境変数を移す手間も、移した後の互換も要らない。素の npm 名 `live-mindmap` は空いていて（`npm view` が E404）、短い略称の `live`・`lmm`・`lmap`・`livemap` はすべて取られていた。この比較は、最初の表に 1 行足せばできた。

改名や移行を問うときは、今のままを候補の 1 行に入れ、新しい候補と同じ物差しで並べる。

### 3. 衝突調査は候補を落とせるが、選ばせることはできない

1 回目は丁寧に調べた。8 個の候補について npm・GitHub・Homebrew・既存のコマンド・同じ分野の製品・無料で引ける商標を当たり、深刻さを 3 段に分けた。4 個が「重い」で落ち、残った 4 個を推奨つきで出して、返事は「全然そそらない」だった。

衝突が軽いことと、その名前を使いたくなることは別の軸だ。調査が保証するのは必要条件で、好みには何も言わない。名前を探した条件に「わかりやすく、キャッチーであること」はあったが、機械的に確かめられるのは衝突のほうだけなので、調べやすい軸に労力が寄った。

反応を受けて作り方は変えていった。1 回目と 2 回目は「意味のある単語に展開形を後付けする」型、3 回目は GNU や WINE の「◯◯ではない」型、4 回目は言いたい文を先に決めて先頭の語を造語に置き換える型だ。どの型も外れた。3 回目で deep-research に回すと決めたのも、4 回目の後に問いそのものをひっくり返したのも、案を出していたエージェントではなく利用者だった。エージェントは毎回、次の案と推奨を出すことを続けていた。

### 4. 改名で壊れる場所は、回数ではなく、その文字列が約束として使われているかで数える

洗い出しの数字だけを見ると大ごとに見える。追跡中のファイルに `live-mindmap` が 2,157 回、`LIVE_MINDMAP` が 341 回ある（`git grep -Io`）。しかし 2,157 回のうち 1,661 回は GitHub の URL で、GitHub のリダイレクトが残るので、置き換えなくても壊れない。

壊れるのは回数の少ない 5 か所だった。

- 保存先 `~/.live-mindmap/`。既定を変えると、過去のセッションと導入済みの依存が見えなくなる
- 環境変数 `LIVE_MINDMAP_*` の 18 種。名前を変えると、設定が黙って効かなくなる
- helper（Mac で音声を取り込む Swift のプログラム）の実行ファイル名。server が固定のパスで起動する
- 画面のタイトルと、helper の自画面の除外の対
- 手元のパスや引数で照合するもの（ghq のパス、エージェントのメモリのフォルダ、常駐スクリプトの引数）

4 つ目が分かりやすい。web のタイトルが helper 側の文字列と黙って対になっている。

```swift
return !normalized.isEmpty && !["live-mindmap", "about:blank", "新しいタブ", "New Tab"].contains(normalized)
```

型もテストもこの対を結んでいない。片方だけ変えると、自分のマップを会議のタブとして覚えてしまう。置換の回数を見積もるより、文字列がプロセスやファイルシステムをまたぐ約束になっている場所を探すほうが、費用の見積もりとして当たる。

### 5. 選んだ名前が条件から外れる点は、決定の中に書き、「蒸し返さない」と仕様まで運ぶ

選ばれた名前は、map の条件を 2 つ満たしていない。12 文字で記号も入るので「短く打ちやすい」から外れ、再帰するのは名前全体ではなく LIVE の部分だけだ。

どちらも見落としではなく、承知の上の選択である。放っておくと、後のセッションが条件と照らして「外れている」と指摘し直しかねない。そこで #1861 の答えに「外れる点」の節を立て、仕様と子のチケットにも「蒸し返さない（#1861 の決定）」と書き写した。

人の好みで条件を破るのは、条件を緩めるのとは違う。文字数は「緩める順」まで決めてあったが、再帰の範囲を緩める段取りは無かった。決まった事実として残さないと、次の読み手には条件違反にしか見えない。

なお、PR #1909 に差し戻しの記録は無い。ただ takt の実行記録を読んでいないので、この一文が効いたのかどうかは分からない。

### 6. 前提が崩れたチケットは、閉じるときに「触らないものの一覧」を答えに残す

名前が変わらないと決まると、「改名する範囲と順序を決める」[#1862](https://github.com/daiki-beppu/live-mindmap/issues/1862) は問う意味を失った。ここで「不要」とだけ書いて閉じず、「決めることがない」と答えたうえで、今のまま触らないもの（リポジトリ、CLI の bin、パッケージ、保存先、環境変数、helper の実行ファイル名、画面タイトルの照合、手元の登録）を並べた。

この一覧はそのまま仕様 #1896 の Out of Scope になり、子のチケット [#1908](https://github.com/daiki-beppu/live-mindmap/issues/1908) の「やらないこと」にも写った。改名の map から生まれた作業なので、「改名の作業を誤って始める」のが現実の事故の形だった。子のチケットは受け入れ条件でも退路を塞いでいる。

- 展開形の字句は Markdown のまま（`**L**IVE **I**nstantly **V**isualizes **E**xchanges`）指定する
- 2 つの README の最初の見出しより前に 1 か所ずつ
- `main` との差分は追記だけで、削除行も他のファイルの変更も無い

入った差分は `README.ja.md` と `README.md` に 2 行ずつ、削除は 0 だった。

### 7. 4 行の変更でも、流れに乗せれば 38 分かかる。ただし省いた工程には理由が残る

この 4 行は、いつもの大きな機能と同じ流れを通った。

| 段 | 日本時間 | 記録 |
|---|---|---|
| 形式仕様の判断 | 13:19:33 → 13:19:47 | 14 秒で「対象外」と理由をコメント |
| takt の起動 | 22:19 | 子のチケットを 1 本渡す |
| PR の作成 | 22:45 | 起動から 26 分 |
| レビューの完了とマージ | 22:57 | 起動から 38 分 |

38 分のうち、人の手は承認だけで済んでいる。形式仕様を書かない判断も、黙って飛ばしたのではなく「状態遷移・排他・順序・権限のような常に成り立つべき性質が無い」とコメントに残った。このくらいの変更で流れに乗せることが得かどうかは、1 回では判断できない。
