## main の ruleset の strict を外したら、先に閉じた blocker の issue が後の作業を 20 秒で走らせ、「揃えずにマージされた」は head の SHA と出来事の列で示すことになった話

この repo の `main` は、GitHub の ruleset で「マージの前に最新の main を取り込んでおくこと」（strict）を必須にしていた。自動マージを予約した PR が main より遅れる（BEHIND）と、手元の Mac に常駐するスクリプト `align-behind.mjs` が予約の古い順に 1 件ずつ main を取り込み、その 1 件がマージされるか落ちるまで次を取り込まなかった。takt（issue を計画・テスト・実装・レビューまで自動で回すワークフロー）を複数並べて回す takt-sequence を入れても、出口でマージが 1 件ずつに戻る。そこで strict を外し、マージ後の main の CI を dotfiles の案内役（手元に常駐して issue・PR・CI を見張るスクリプト）が見張って直す形にした。落ちたら、落ちた job を 1 回だけ再実行し、また落ちたら main-fix（main から切った修正のセッション）が修正の PR を出し、それでも直らなければ Discord で人に判断を頼む。決めたのは仕様 [#1682](https://github.com/daiki-beppu/live-mindmap/issues/1682)（親 [#1703](https://github.com/daiki-beppu/live-mindmap/issues/1703)）で、子は 3 本。案内役の修復が動くことを確かめてから ruleset を変える [#1704](https://github.com/daiki-beppu/live-mindmap/issues/1704)、ADR と手順書を書き換える [#1705](https://github.com/daiki-beppu/live-mindmap/issues/1705)（[ADR 0026](../adr/0026-verify-main-after-merge-without-strict.md)）、strict でない repo で `align-behind.mjs` を立てない dotfiles 側の [daiki-beppu/dotfiles#410](https://github.com/daiki-beppu/dotfiles/issues/410) だ。コードの変更はほとんど無く、設定と文書の作業だった。それでも、作業の順で 2 回、判断が揺れた。

### 1. blocker の issue が「閉じた」ことは、その実装が「入った」ことではない。issue の状態を合図に次を始める仕組みがあるなら、閉じる前にマージを確かめる

#1704 は「dotfiles#407（案内役が main を直す仕組みの仕様）の実装がマージされてから」と書き、GitHub の blocked by でつないでいた。壊れた main を見張る者がいないまま門を外さないためだ。ところが #407 は、実装の PR も子の issue も無いまま、10/28 22:11:06（日本時間、以下同じ）に閉じられた。takt-sequence は blocked by が外れた issue から取るので、20 秒後の 22:11:26 に #1704 の takt の run が始まった。

run の側は踏みとどまった。計画の段が「#407 が閉じていること」ではなく「実装のマージと、案内役が main の `check` を読めること」を前提に置き、実装の段が #407 の状態・子の数・timeline を API で読み直した。子は 0 件で、結びつく PR も無い。そこで ruleset の書き換え（`gh api -X PUT`）を実行せず、「前提が成り立っていない」と証拠を添えて計画に返した。実装の報告には、こう残っている。

> CLOSED や担当者の API 成功だけで解除する誤りを避けた。

#407 は 22:16 に開き直された。実装の PR（dotfiles#420・#422・#423・#424）が作られたのは 23:00 から 23:15 で、23:17 までに全部マージされた。

ここで、後から書いたコメントの方が言い過ぎになった。翌 10/29 の朝、#407 には「開き直したのは誤りだった。実装は #420・#422・#423・#424 で main に入っている」、#1704 には「前のコメントの見送りは取り消す」と書いた。だが 22:16 に開き直した時点では、4 本の PR はまだ 1 本も作られていない。開き直したことも、ruleset の変更を見送ったことも、その時点では正しかった。誤りだったのは 22:11 に閉じたことの方だ。「今は入っている」と「あのときも入っていた」を取り違えると、正しかった判断を取り消したことになり、なぜ止めたのかが記録から読めなくなる。

基準は 2 つにした。

- 「この実装が入ってから」を blocked by で表すなら、blocker は実装の PR がマージされてから閉じる。仕様の issue のように子を持つものは、子がすべて閉じてから閉じる
- 後の作業の前提を確かめるときは、issue の状態ではなく、その実装の PR がマージされているか、main にそのコードがあるかを見る

### 2. 人が引き取るための ABORT の指示も、自動の再投入には「失敗」に見える。同じ指示を読んで同じ ABORT が 2 回繰り返された

#407 を開き直した後、#1704 は人が引き取ることにした。takt の run には実行中に指示を送れるので、22:24:30 に「人が引き取ることになった。これ以上変更を加えず、PR を作らずに ABORT して終わること。ruleset など GitHub の設定にも触れないこと」と送った。1 本目の run は次の再計画でこれを読み、22:25:32 に ABORT した。

takt は、ABORT で終わったタスクを自動で再投入する（この設定では 2 回まで）。2 本目は 22:25:35 に、3 本目は 22:27:19 に始まった。どちらも再計画の段で同じ指示を読み、約 2 分で同じ ABORT を出した。3 本目の再投入のメモには `"error":"Workflow aborted by step transition","attempt":2,"maxAttempts":2` とある。再投入の仕組みからは、人の指示による ABORT も、要件が足りずに止まった ABORT も、同じ失敗に見える。

害は 4 分ほどで済んだ。ただ、ABORT の指示は run を 1 本止めるだけで、タスクを終わらせはしない。人が引き取ると決めたら、run に ABORT を頼むだけでなく、タスクそのものを列から外す。外すまでの間は、再投入で同じ ABORT が上限の回数だけ繰り返されると見込んでおく。

### 3. 常駐スクリプトは、起動した時点のコードで動き続ける。前提のコードがマージされたかに加えて、常駐を起動した時刻とも比べる

10/29 に #1704 を手で再開し、まず案内役が live-mindmap の main を読めるかを確かめた。動いていた案内役は 10/27 23:14 に起動したもので、前提の実装（10/28 23:17 にマージ）より前のコードだった。dotfiles の main にコードがあっても、常駐しているプロセスはそれを読み込んでいない。PID を名指しで止め、同じペインで 10/29 8:25 に起動し直した。

読めることの確かめ方にも一工夫が要った。案内役の状況の一覧は、main が赤いときだけ main の行を出す。このときの main は緑だったので、一覧に何も出ないことは「読めた」の証拠にならない。代わりに、案内役が使っている読み取りの関数（`readMain`・`requiredChecks`・`mainState`）をそのまま呼んで、結果を残した。

```json
{
 "sha": "dedd277bb3aa25374a949c1a9bcc5f170ac4c014",
 "required": ["check"],
 "requiredRuns": [{ "name": "check", "status": "completed", "conclusion": "success" }],
 "state": { "state": "green", "failed": [] }
}
```

必須チェックの名前 `check` を ruleset から読めていて、main を緑と判定している。「何も出ない」が正常な状態を確かめるときは、出力の画面ではなく、その画面を作る関数の戻り値を見る。

ruleset の変更そのものは、`strict_required_status_checks_policy` を `true` から `false` に変えるだけにした。変更前後の `required_status_checks` を両方残し、必須チェック（`check`）と、名前・適用の状態・条件・例外の利用者が変わっていないことを確かめた。

### 4. strict を外すと、遅れている PR の `mergeStateStatus` は `BEHIND` ではなく `CLEAN` になる。「揃えずにマージされた」は、揃える者を止めたうえで、head の SHA と出来事の列で示す

完了条件の 1 つは「BEHIND の予約済みの PR が、揃えられずに `check` の通過でマージされた」ことだった。開いている PR が 0 件だったので、docs だけの訓練の PR を 2 本出した（#1725・#1726）。

- #1725 を予約し、10/29 21:54:38 にマージされた
- この時点で #1726（head `7986d7f`）は、`compare/main...<branch>` が `behind_by: 1` だった。`check` は古い base の上で通っている
- ところが `gh pr view` の `mergeStateStatus` は `BEHIND` ではなく `CLEAN` を返した。GitHub は、ruleset が最新の取り込みを求めていなければ、遅れていても「マージできる」と答える。BEHIND かどうかは、`compare` の `behind_by` で見るしかない
- #1726 を予約すると、19 秒後の 21:54:57 にマージされた。head は `7986d7f` のままで、timeline の出来事は `committed`・`closed`・`merged` の 3 つだけ。ブランチの更新も force push も無い

「揃えられずに」は、起きなかったことの証明だ。そこで、揃える者だった `align-behind.mjs` を先に止めておき、そのうえで head の SHA が予約からマージまで変わらなかったこと、出来事の列に取り込みが無いことを示した。訓練で足したファイルは #1727 で消した。

### 5. 仕様が名指しした関連の ADR は、番号ではなく中身で確かめる。置き換えた ADR を「今の決まり」として指している文書も探す

仕様 #1682 は「0020（BEHIND の判定の扱い）が不要になるなら、同じ ADR で扱う」と書いていた。子の #1705 を起票するときに ADR 0020 を開くと、中身は差分更新の判定のモデル（選択肢から選ぶだけの答えを返す軽いモデル）の口の決定で、BEHIND の PR とは関係が無かった。仕様を書いた時点で、番号の記憶が別の ADR と混ざっていたことになる。#1705 には「0020 は変えない」と書き、置き換えるのは 0021（GitHub Actions が App のトークンで揃える）と 0022（手元の常駐スクリプトが揃える）の 2 本にした。

置き換えの側でも 1 つ見つかった。takt の run の読み方をまとめた知識文書 `docs/knowledge/takt-runs.md` が、マージの流れの参照先として ADR 0022 を今の決まりのように指していた。#1705 の PR（[#1728](https://github.com/daiki-beppu/live-mindmap/pull/1728)）で ADR 0026 に差し替えた。ADR を置き換えるときは、置き換えられる ADR の冒頭に新しい ADR への参照を足すだけでなく、`git grep` でその番号を指す文書を探す。開発ログのような過去の記録は、その時点の事実なので書き換えない。

### 6. 設定で決まる振る舞いは、repo の名前で分けずに設定そのものを読む。読めなければ推測しない

dotfiles#410 では、desk（案内役や `align-behind.mjs` を Orca のペインに並べて起動するスクリプト）が、strict でない repo で `align-behind.mjs` を立てないようにした。案は 2 つあった。live-mindmap の起動から外すか、repo の main の ruleset を読んで strict の repo でだけ立てるか。desk には repo ごとの設定が無いので、前者は repo 名の分岐を書き込むことになる。後者なら、strict の repo が増えても、strict を戻しても、desk を直さずに効く。後者を選び、`gh api repos/<repo>/rules/branches/main` の応答から「必須チェックのどれかが strict か」を返す純粋な関数を足した。

`gh api` が失敗したときは、desk を例外で止める。strict かどうかを既定値で推測すると、strict の repo で揃える者がいなくなるか、strict でない repo に役目の無い常駐が残るかのどちらかになり、どちらも気づきにくい。実データで確かめると dotfiles 自身も strict でなかったので、dotfiles でも `align-behind.mjs` は立たなくなった。repo 名で分けていたら、この 2 つ目の repo は見落としていた。
