## 保存したセッションのログの読み側を 1 つの module にまとめたとき、読み手を「ファイルを開く所」で数えたせいで、読んだ値を後から decode する 5 つ目の読み手を見落とした話

live-mindmap は、会議を 1 回取り込むごとにセッションのフォルダを作る。中身は、出来事を 1 行 1 JSON で追記した `log.jsonl`、書き出しの `export.json`、共有画面の画像の `screens/`、録音のファイルだ。CLI には、このフォルダを後から読むコマンドがいくつもある。ログを流し直す `cli play`、マップを復元する `cli restore`、差分更新の出来を測る `cli eval`、見返し用の HTML（`map.html`）を作る `cli review`、それを Cloudflare に置く `cli publish` だ。フォルダを書く側は `sessionFiles` という module 1 つにまとまっていたが、読む側には持ち主がいなかった。そこで、読み側を書き側と同じ module に入れ、ログの壊れた行の失敗を 1 つの型にまとめ、どのコマンドでも同じ文で知らせるようにした。決めたのは仕様 [#1438](https://github.com/daiki-beppu/live-mindmap/issues/1438)（決定の一次資料は [#1427](https://github.com/daiki-beppu/live-mindmap/issues/1427)）で、実装は 3 本のチケット [#1444](https://github.com/daiki-beppu/live-mindmap/issues/1444)・[#1445](https://github.com/daiki-beppu/live-mindmap/issues/1445)・[#1446](https://github.com/daiki-beppu/live-mindmap/issues/1446) に分け、takt（issue を計画・実装・レビューまで自動で回すワークフロー）で 1 本ずつ流した。

### 1. 同じ失敗の文がコマンドごとに違うのは、読み側を写した数だけ言い換えがあるからだ

始める前に数えると、ログを読む所は 8 か所あった。CLI の 6 つの関数、`review`、それに計測用の bench の 2 つだ。`log.jsonl` が無いときの失敗は 2 か所に写され、壊れた行を行番号に直す処理は 4 通りあった。4 通りとも、空行を除いた配列の index から元の行番号を引く `lines[i]?.no ?? 1` を書き写していた。

その結果、同じ壊れたログを渡しても、コマンドによって標準エラーの文が違った。パスが付くものと付かないものがあり、`cli eval` は汎用の失敗に包み直して言い換え、`cli review` は書き出しの失敗に言い換えていた。直すべき場所がどのファイルの何行目か、という利用者の知りたいことは同じなのに、文から読み取れる手がかりがコマンドで違っていた。

失敗はタグ付きのエラー `BrokenLogLine { path, line, kind, reason }` の 1 つにし、日本語の文を作るのは CLI の入口の表 1 か所だけにした。`kind` は、JSON として読めない（`json`）か、JSON としては読めても出来事の Schema に合わない（`event`）かを分ける。文は次の 2 つだけになる。

```text
json:  <パス> の <行> 行目が JSON として読めません: <理由>
event: <パス> の <行> 行目が読めません: <理由>
```

行番号は、空行も数えた、エディタで開いたときの行番号にした。index から行番号へ直す仕事は読み側の内側に閉じ、呼び出し側には出さない。

### 2. 全部を先に decode する口は、呼び出し側が今は許している壊れまで失敗にする

読み側の interface は 2 案を並べて比べた（design-it-twice）。

- A: 全部入りの記録。`read(dir)` が `{ start, remarks, screens, vocab, diffs, events }` を先に全部 decode して返す
- B: 種類で絞る口。`readSessionLog(dir)` は JSON として読んだだけの `events` を返し、`select([RemarkEvent, ScreenEvent])` のように欲しい種類だけを decode させる

A の方が呼び出し側は楽に見える。しかし `cli play` は今、再生に使わない差分更新の記録（diff の行）が壊れていても流せる。A では全部を先に decode するので、その壊れで play が止まるようになる。ログの種類が増えるたびに、戻り値の記録も大きくなる。B を採った。

この比較で効いたのは「今の呼び出し側は、何を読み飛ばしているか」を先に数えたことだ。読み飛ばしは、壊れに対する寛容さという、目に見えない契約になっている。全部を decode する口は、その寛容さを黙って取り上げる。

### 3. 循環を解く段を先に切ると、間の 1 本は重複を一時的に増やす

読み側を `sessionFiles` に入れるには障害が 1 つあった。`sessionFiles` は見返しの HTML を作る `review` を import し、`review` はログを読む。読み側を `sessionFiles` に置くと循環する。ログの行を読む関数は、この循環を避けるためだけに `logLines` という別ファイルに分けてあった。

順番は 3 段にした。まず `review` を、ログのパスではなく読んだ出来事を受け取る形にして循環を解く（#1444）。次に読み側を `sessionFiles` に入れ、`logLines` を消す（#1445）。最後に CLI を新しい口へ差し替えて、文をそろえる（#1446）。

1 段目は「振る舞いを変えない」と決めていた。そのため、`review` が内側でしていた「壊れた行を文にする」処理は、呼び出し側の 3 か所（`writeReviews`、`cli review --self-only`、`cli publish`）へ写すことになった。この仕様が消そうとしていた行番号の書き写しを、間の 1 本が 3 つ増やしたことになる。3 段目で消えたので最終形には残っていないが、段に分けるときは、間の状態が最初より悪くなることがある。それを承知で順番を決めた方がよい。

### 4. 生の値を渡す口を残すなら、読み手は「ファイルを開く所」ではなく「その値を decode する所」で数える

B の口は、`review` の埋め込みや復元のために、decode しない生の `events` も返す。最後の #1446 のレビューで、ここに穴が見つかった。

`cli publish --content map` は、発言の文字を消したマップだけの見返しを公開する。文字を消すために、`review` の奥にある `mapOnlyReviewEvents` が、生の `events` から発言と共有画面の行を自分で decode していた。壊れていると、そこで次の文を投げる。

```ts
throw new Error(`出来事 ${index} 行目を読めません: ...`);
```

`index` は空行を除いた配列の 0 始まりの番号で、パスも無い。これが `review` の失敗に包まれ、さらに CLI の汎用の失敗に包まれて出ていた。つまり行番号の対応づけは、仕様が数えた 4 通りではなく 5 通りあった。仕様は読み手を「`log.jsonl` を開く所」で数えていて、開いたあとの値を別の場所で decode する所は数えていなかった。

見つけたのは、takt のレビューの 5 人のうち AI 由来の書き方を見る担当 1 人だけだった。設計・バックエンド・セキュリティ・テストの担当は通していた。裁定の段がテスト担当の見落としもこの指摘にまとめ、修正の計画は次のようにした。

- `publish` の map の版では、描画の前に `log.select([RemarkEvent, ScreenEvent])` を呼んで検証だけをする。失敗は `BrokenLogLine` のまま入口へ届く
- 描画には、検証した値ではなく元の `events` を渡す。描画の失敗を包む処理の外で検証するので、壊れた行が書き出しの失敗に言い換えられない

不正な発言を空行 2 つの後の 4 行目に置いたログで、`<パス> の 4 行目が読めません: …` が出て終了コード 1 になることを、公開の入口から確かめた。takt の run は 11 回の段を 82 分で回り、そのうち、裁定から修正の計画・修正・確認・再レビューを経て最後の確認までの 7 段が、この指摘のやり直しの分だった。

### 5. interface の下書きは、呼び出し側の文に要る値までは見通せない。足す余地を残しておく

仕様の interface の下書きには、もう 1 つ足りないものがあった。`cli play` は、共有画面の行が指す画像が無いと、その行の行番号を付けて失敗する。この行番号は、`select` が decode した値から元の行へ戻れないと作れない。下書きには `brokenAt`（復元が返す index を行番号に直す口）しかなく、decode に成功した値の行番号を引く口が無かった。

仕様は「名前は実装で整えてよい」としていたので、実装の計画の段が `lineOf(event)` を足した。そのとき、decode の前と後のオブジェクトが同じ参照だという確かめていない仮定には頼らず、`select` が decode した値をキーにして行番号を覚えておく形にした。下書きで隠すと決めた「空行を除く前の行番号」は、失敗のときだけでなく、成功した値の検証で呼び出し側が自分の文を作るときにも要る。

### 6. 境界が FileSystem だけなら、読み側の契約は偽の FileSystem の unit に下ろし、IT からは同じ失敗を消す

読み側の契約は、偽の `FileSystem` を Layer で差し込む unit で確かめた。Effect の `FileSystem.makeNoop` に、試したい関数だけを上書きして渡す。

```ts
const fileSystem = (overrides: Partial<FileSystem.FileSystem>) =>
  Layer.succeed(FileSystem.FileSystem, FileSystem.makeNoop(overrides));
```

確かめる契約は仕様の段で 7 つに決めておいた。JSON として壊れた行が空行込みの行番号の `kind: json` になる、選んだ種類の壊れが `kind: event` になる、選んでいない種類の壊れでは失敗しない、`log.jsonl` が無いときの失敗、最新のフォルダの選び方、`brokenAt` の行番号、start の有無とローカルモードの判定だ。実装ではこれに、読み取りの権限エラーを「ログが無い」に変えないこと、存在を確かめた直後にファイルが消えた場合も足された。

同じ失敗を、CLI を argv から動かす IT でも確かめていた 2 件は消した。IT に残したのは、標準エラーの文の完全一致を、文の形（json・event）ごとに 1 つずつだ。CLI の出力そのものは契約なので IT で守り、行番号の数え方は unit で守る。層ごとに確かめるものを分けた結果、`cli.it.test` からは 53 行を消して 12 行を足し、新しい unit は 188 行になった。

### その後

この仕様の 3 本は 2026-10-24 に main に入った。4 節の `mapOnlyReviewEvents` の、index で数えてパスの無い文はまだ残っている。CLI の `publish` からは先に `select` で検証するので届かないが、生の `events` を受け取る別の呼び出し側が増えれば、また同じ形で漏れる。発言と画面の行を decode する所が `select` と `mapOnlyReviewEvents` の 2 つある状態だ。
