## 差分更新の結果を状態に当てる手順を、ライブ・復元・計測の 3 か所の写しから 1 つの純粋な畳み込みにまとめたとき、往復の照合テストを 1 本に減らせた理由と、全員 APPROVE のレビューが見なかった所の話

live-mindmap は、会議の発言がたまるたびに AI にマップの差分（ノードの追加・更新などの操作の列）を出させ、それを今のマップに当てる。この 1 回を差分更新と呼ぶ。セッション（1 つの会議を追う一続きの作業）の出来事は、1 行 1 JSON の `log.jsonl` に追記する。差分更新の結果はその中の `diff` の行で、AI に渡した新しい発言の id（`fresh`）、帰属済みの操作（`ops`）、AI が処理し終えた発言の数（`processedRemarks`、一部だけ処理した回にだけ付く）、失敗した回なら `error` を持つ。この行をセッションの状態に当てる手順が、3 か所に別々に書かれていた。会議中に AI の応答を当てる「ライブ」、保存したログからセッションを戻す「復元」、ログからマップの形の数字を出す「計測」だ。その手順を 1 つの関数にまとめ、3 つともそれを通るようにした。決めたのは仕様 [#1593](https://github.com/daiki-beppu/live-mindmap/issues/1593)（親 [#1594](https://github.com/daiki-beppu/live-mindmap/issues/1594)）で、実装は 3 本のチケットに分けた。関数を作って復元を載せる [#1595](https://github.com/daiki-beppu/live-mindmap/issues/1595)、ライブを載せる [#1596](https://github.com/daiki-beppu/live-mindmap/issues/1596)、計測を載せる [#1597](https://github.com/daiki-beppu/live-mindmap/issues/1597) だ。takt（issue を計画・テスト・実装・レビューまで自動で回すワークフロー）で 1 本ずつ流した。

### 1. 同じ手順の写しは、もう食い違っている。関数の入力は「ログに書く行そのもの」にすると、書く側と読む側が同じ値を見る

3 か所の手順はどれも同じ形だった。処理した発言を `processedRemarks ?? fresh.length` で数え、round（何回目の反映か）と時刻の印を付け、操作を当て、エラーの無い回だけ反映の履歴を進める。それでも、仕様を書く段で読み比べると、もう食い違いがあった。処理した数が `fresh` の数より多い行を、復元は不正なログとして止める。計測は黙って `fresh` の数に切り詰め、そのまま数字を出していた。壊れたログからでも、計測はもっともらしい数字を返していたことになる。

3 つがそろっていることは、`restore.test.ts` の「ライブで組んだマップと、そのログから復元したマップが一致する」という往復の照合だけで確かめていた。git の履歴では、`session.ts` と `restore.test.ts` は 16 回一緒に変わっていた。反映の規則を 1 つ変えるたびに 3 か所を直し、往復で食い違いを探していたことになる。

まとめた関数は、前の状態と `diff` の行 1 件を受けて、次の状態を返す同期の純粋な関数（畳み込み）にした。用語集に「**反映**」として足した。持つ状態は、マップ・反映の履歴（round・変わったこと・今の議題）・発言の台帳（全発言・既知・処理済み）の 3 つだ。

決めどころは入力の型だった。復元用に簡単な入力の型を作る案もあった。それを捨て、`log.jsonl` に書く `diff` の行の型（`DiffEvent`）をそのまま受けることにした。ライブは、AI の出力から行を組み、その行を畳み、同じ行をログに書く。復元と計測はその行を読んで同じ関数で畳む。書く値と読む値が同じものなので、「復元 = 元」は照合で探すものではなく、作りで成り立つ。

### 2. 書く側と読む側が同じ関数を通ると、往復の照合では関数の誤りを見つけられない。中身は期待値の unit で、外は往復 1 本で確かめる

作りで一致するようになると、往復のテストの意味が変わる。反映に誤りがあっても、ライブも復元も同じように間違えるので、往復は一致して通る。往復で落ちるのは、反映の外（行の組み立て・書き込み・読み戻し）の誤りだけになる。

そこで仕様は、テストを 2 層に分けた。反映の中身は、新しい `reflection.test.ts` で期待値を書いて確かめる。成功の回・エラーの回・一部だけ処理した回・処理数の超過・台帳に無い id・中身の無い発言（「えー」「あの」だけの発言）の 6 つの契約だ。前例は、操作を当てる純粋な関数 `applyOps` の unit テストにした。往復は、エラーの回・捨てた操作・未反映の発言を含む 1 本だけを残した。

`restore.test.ts` からは 3 本を消した。今の議題・今の時刻・ノードの印（`touchedAt`・`evidenceRound`）が元と一致するかを見るテストで、どれも往復 1 本と同じ層で同じ契約を見ていた。値そのものは別の unit テストが期待値で持っている。2 本目（#1596）のテストを書く段は、新しいテストを 1 本も書かず、この 3 本（49 行）を消しただけだった。

逆に 1 本足したものがある。ログに `diff-update-state` の `stopped`（AI を動かす子プロセスが止まったこと）があっても、復元したセッションは差分更新が動く状態で戻る、というテストだ。復元がこの行を読まないことは前から同じだったが、意図かどうかがどこにも書かれていなかった。仕様の段で、意図だと決めた。`stopped` はその回の子プロセスの状態で、セッションの中身ではない。しかも、状態を `stopped` から出さない作りなので、`stopped` で戻すと、再開したセッションは二度と差分更新しない。理由の書かれていない「しない」は、決定なのか漏れなのかが後から分からない。決定ならテストで固定する。

### 3. 純粋な関数は失敗を値で返し、位置を付けるのは呼ぶ側にする。ライブでは、自分で組んだ行が落ちたら defect にする

反映は Effect（このリポジトリが使う Effect 4 の、副作用と失敗を型で持つ値）を返さず、`Result`（成功か失敗の理由）を返す。ライブはセッションの状態を `Ref`（割り込まれずに読み書きできる入れ物）に持ち、`Ref.modify` のコールバックの中で反映を呼ぶ。コールバックの中では Effect を実行できないので、同期の値で返す必要があった。

失敗の理由は文字列だけにし、ログの何行目かは付けない。復元と計測は、それぞれ `Effect.fromResult(...).pipe(Effect.mapError(invalid))` で、行の位置つきのエラー（`InvalidLogEvent`）に包む。同じ失敗でも、ログを読む側には位置が要り、反映そのものは位置を知らない。

ライブだけは扱いが違う。AI が `fresh` より大きな処理数を返したときは、反映より前にエラーの回に直してある。だからライブが組んだ行が反映の検査に落ちたら、それはライブが自分の約束を破ったことになる。型付きのエラーを足さず、`Result.getOrThrowWith` で例外にして defect（直せない不具合として扱う失敗）にした。`Ref` はコールバックが戻ってから状態を書くので、例外のときに半端な状態は残らない。

`Ref.get` で先に状態を読んでから反映する案は、計画の段で捨てた。`Ref` の操作の間には別の Fiber（Effect の軽量スレッド）が割り込める。読むのと書くのを分けると割り込みの境目が 1 つ増え、古い状態で畳むおそれがある。差分更新の呼び出しの順序は TLA+ でモデルにしてあり、モデルの 1 つの遷移が `Ref` の操作 1 回に当たる。既存の `Ref.modify` と `Ref.update` の中に入れたので、操作の回数も順序も変わらない。モデルの変更は注釈の行番号の 2 か所だけで、TLC は 6 つの性質を 11 の構成ですべて通した（調べた状態の数は、クラウドのモデルの構成で 318,363、Apple の端末内モデルの構成で 17,037）。

### 4. 検査をすべて済ませてから新しい値を作ると、「失敗したら前の状態のまま」が作りで守られる。ただし分けた関数どうしは、呼ぶ順に頼ることがある

前の復元の `consumeFresh` は、台帳の Set と配列をその場で書き換えながら進んでいた。途中で検査に落ちると、半分だけ書き換わった台帳が残りうる。反映は、`fresh` の id をすべて台帳で引き、処理数を確かめてから、新しい Set と配列を作る。失敗の回は何も作らない。unit テストは、成功でも失敗でも、入力の状態と行を `structuredClone` で取っておき、呼んだ後に変わっていないことを確かめている。

時刻が 2 種類あることも、計画の段で先に名指しした。共有画面の画像を選ぶ境の時刻は `fresh` 全体の終わりの最大、反映の印の時刻は処理し終えた発言だけの終わりの最大だ。一部だけ処理した回には、この 2 つが違う。テストは、処理しない側の発言に遅い時刻（90 秒）を置き、取り違えたら落ちるようにした。

一方で、分けたことで順序に頼る所が 1 つできた。復元は、共有画面の持ち越しを再生する部分を `replayScreens` として切り出し、反映と並べて呼ぶ。`replayScreens` は台帳を `ledger.byId.get(id)!` と非 null の表明つきで引く。台帳に無い id は直前の反映が先に弾くので安全だが、その安全は型ではなく呼ぶ順で守られている。レビューは「指摘にしなかった懸念」として挙げ、呼び出しが 1 か所なので問題なしとした。

### 5. 黙った切り詰めを失敗に変えるときは、変える前の実装が何を返していたかを赤いテストで残す

計測（3 本目、#1597）は、処理数が `fresh` を超えるログで `InvalidLogEvent` を返すようにした。テストを先に書く段で、変える前の計測にそのログを渡すと、`{"remarks":1,"rewrites":0,...}` と数字を返して落ちた。fixture の不備で落ちたのではなく、弾く処理が無いから落ちたことを確かめ、報告に残している。「壊れたログから数字が出ていた」ことの証拠がそのまま残った。

計測の載せ方は 3 案を比べた。今の手順に処理数の検査だけを足す案は、数え方の写しが残るので捨てた。反映の出力に印や処理した発言を足して計測に渡す案は、計測のために共通の関数の出力を広げることになるので捨てた。採ったのは、計測の側だけが持つ「1 回の応答の中で本文が何回書き換わったか」の数え方（`rewrittenIds`）の中でも反映を呼ぶ案だ。操作の列の先頭から 1 件、2 件、と区切った列を、反映前の同じ状態から反映にかけ、前後で本文が変わったノードを数える。反映の出力の型は変わらない。

正しいログに対する計測の数字は、既存のテストの期待値を変えずに通った。過去の計測と比べられることが条件だったので、ここが崩れていないことは期待値を変えなかったことで示せる。

### 6. 仕様が置き場所・失敗の扱い・消すテストまで決めていると、レビューは確認になり、差し戻しは 0 になる。レビューの観点の外にあったものは別に見る

3 本とも、計画 → テスト → 実装 → レビュー → 裁定 → 最終確認を 1 回ずつ通り、差し戻しは 0 だった。並列のレビュー（設計・バックエンド・テスト・AI 由来の書き方など 5〜6 観点）は全員 APPROVE で、ブロッキングの指摘は 1 件も無かった。仕様が、関数の型、呼ぶ場所（`Ref.modify` の中）、失敗の扱い（ライブは defect）、消すテストの名前まで書いていたので、計画は迷わず、レビューはそれに合っているかを確かめる作業になった。

ただ、APPROVE の外に残ったものもある。開発ログを書くために差分を読み直して気づいた所で、どれも run の中では話題になっていない。

- 計測の `rewrittenIds` は、操作の列の区切りごとに反映を呼ぶ。反映は処理数と台帳しか検査せず、操作の中身は見ないので、行全体の反映が先に通っていれば、区切りの反映は失敗しない。`rewrittenIds` が `Result` で失敗を返す経路は、実際には通らない。
- 区切りごとの反映は、そのたびに反映の履歴の連結と既知の Set の複製を行う。区切りごとにマップへ操作を当て直すこと自体は前から同じだったが、1 行あたりの仕事は増えた。
- ライブのエラーの回は、仕様の「`Ref.update` の中で」に字面どおり従い、コールバックの外に置いた `let dropped` に中から書き込んでいる。`Ref.modify` で値を返せば、`Ref` の操作の回数を変えずに外の変数を無くせる。

時間の使い方も偏っていた。2 本目は 79 分のうちレビューが 38 分、3 本目は 82 分のうち 45 分だった。3 本目では、バックエンドのレビューのレポートを書く段が、AI の提供元から `status "error"` が返るまで 36 分止まり、やり直すと 25 秒で通った。コードの難しさより、待ちが所要時間を決めていた。
