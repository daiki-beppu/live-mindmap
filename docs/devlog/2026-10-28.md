## helper のライブのセッションを差し替えられる module にしたら、止める直前のイベントの欠けが直り、CI の時間切れの 1 つはテスト自身が協調スレッドを塞いでいた話

live-mindmap の helper は、会議アプリの音とマイクを取り込み、文字起こし・話者分離・共有画面（会議で映っていた画面）の判定をする Swift のプロセスだ。結果はイベント（発言・話者の区間・画面など）として WebSocket で server に送る。会議の最中に取り込む「ライブのセッション」の組み立ては、`main.swift` の `run` という約 200 行の関数がすべて持っていて、テストは 1 本も無かった。これを HelperCore の module `LiveSession` に移し、機器（音の tap・マイク・認識・話者分離・入力の使用・共有画面・時計）を偽物に差し替えられる形にした。決めたのは仕様 [#1639](https://github.com/daiki-beppu/live-mindmap/issues/1639)（親 [#1658](https://github.com/daiki-beppu/live-mindmap/issues/1658)）で、実装は 3 本のチケットに分けた。イベントの送り口を 1 つにする [#1665](https://github.com/daiki-beppu/live-mindmap/issues/1665)、module に移して終わらせ方を 5 段にする [#1666](https://github.com/daiki-beppu/live-mindmap/issues/1666)、片付けで `tap-silent` を待つ [#1667](https://github.com/daiki-beppu/live-mindmap/issues/1667) だ。3 本とも takt（issue を計画・テスト・実装・レビューまで自動で回すワークフロー）で流した。コードを書く前に、仕様の「常に成り立つべき性質」を Quint で書いて TLC で全状態を調べてある（仕様のコメント）。

### 1. 「ついでに待っている」順は、待つ側がいない構成で壊れる。守る順は段の並びとしてコードに置き、段の中は順不同と書く

止める直前のイベントが server に届くのは、送り終わりを待ってから server を閉じるからだ。ところが、その待ち（`waitUntilSent`）を呼んでいたのは共有画面の Task の末尾だけだった。共有画面を送り終えるついでに、全部の送り終わりを待っていたことになる。`--no-screen` で取り込んだときや、画面収録の許可が無い Mac では、この Task が無い。誰も待たずに server を閉じるので、止める直前の発言や話者の区間が落ちうる。共有画面があっても、休止の監視が最後に出す `self-pause-state`（自分の休止の状態。`自分` のトラックを取らない間かどうか）は待たれていなかった。これが落ちると、マイクの機器が変わって helper を起動し直したとき、古い休止の状態から始まる。

片付けは 11 段あった。守らないと壊れる順と、たまたまの順が混ざっていて、その区別はコメントにしか無かった。破っても失敗としては出ない。片付けがハングし、server が SIGTERM の 5 秒後に SIGKILL を送るだけだ。録音のファイルは閉じられずに残る。

仕様はこれを 5 段に束ねた。

1. 止める（音声・休止の監視と入力の通知・共有画面）
2. 流し切る（話者の流れ・共有画面の Task・休止の監視の Task・`tap-silent` の送信・録音の `finish`）
3. 送り終わりを待ってから server を閉じる。共有画面の有無によらない
4. 指示の Task を待つ（server の受け取りの流れは、server を閉じたときにしか終わらない）
5. 失敗を選ぶ（本処理 → `相手` の録音 → `自分` の録音の順に、最初の失敗を投げる）

段の中は順不同で、並べて待ってよいと書いた。順を確かめるテストも、段の中については書かないと決めた。形式仕様では、モデルを 1 か所だけ壊した mutant で各性質が赤くなることを確かめた。「段 3 は共有画面があるときだけ送り終わりを待つ」、つまり今の形の mutant で、「閉じた時点で全部届いている」という性質が赤くなる。今の欠けが、性質の言葉でそのまま再現できたことになる。

### 2. 残すかどうかを呼ぶ側に書かせない。種類の網羅の `switch` に `default` を書かなければ、種類を足したときの決め忘れがコンパイルで止まる

server は helper に後から接続することがある。そこで helper は、一部のイベント（原点・最新の画面・休止の状態など）の最新の 1 件を覚えておき、接続した直後に送り直す。どれを覚えるかは、呼ぶ側が `broadcastRetained(_:key:)` に文字列の key を渡して決めていた。その手書きの key が 9 か所にあり、`speakerOff`（話者分離が使えない知らせ）を覚えるかどうかを決める閉包は、2 か所に写されていた。新しい種類を足して覚えるかどうかを決め忘れても、何も落ちない。

#1665 は送り口を `WebSocketServer.send(_ event: HelperEvent)` の 1 つにし、扱いを `HelperEvent` の側の純粋な関数 1 つに置いた。

```swift
func delivery(retained: HelperEvent?) -> HelperEventDelivery {
    switch self {
    case .origin: return .retain(.origin)
    case let .screen(start, _, _, _, _):
        if case let .screen(previousStart, _, _, _, _) = retained, start < previousStart {
            return .connectedOnly
        }
        return .retain(.screen)
    // …覚える種類が続く
    case .remark, .partial, .speaker, .speakerSettled, .speakerMixed, .speakerCentroid:
        return .bufferUntilFirstClient
    }
}
```

`default` が無いので、`HelperEvent` に case を足すと、この関数に行を書くまでコンパイルが通らない。server がブラウザへ送る frame の表で前にやったのと同じ考え方だ。socket なしで全種類を確かめられるので、表のテストは unit に置けた。

ついでに 2 つの欠けが消えた。

- 前の時刻の画像を覚えないという規則は、画面を送る呼び出し側が `latestStart` を持って守っていた。今はこの表の `screen` の行にある。覚える枠を、エンコードした文字列ではなく `HelperEvent` のまま持つことにしたので、`start` を比べられるようになった。
- server が最初に接続するまでの数 ms〜数百 ms に出た発言は、前は黙って落ちていた。今は、最初の接続までは流すだけのイベントも送った順に溜める。接続したら、覚えた枠を表の順（`origin` が先頭）に送り、その後に溜めた分を送る。起動の段取りが変わっても、届く順は変わらない。

エンコードに失敗したイベントの扱いも、経路ごとにばらばらだった（黙って捨てる・セッションごと落ちる・書いて捨てる）。これは「標準エラーに種類の名前だけを書き、その 1 件を送らない」にそろえた。種類の名前だけにしたのは、`EncodingError` の文に発言の本文や画像が入りうるからだ。

### 3. 投げっぱなしの Task は、片付けからは待てない送り手になる。送り手を 1 本の流れに束ねると、流し切る段で待てる

相手の音が届いていないことの知らせ（`tap-silent`）は、無音の判定の閉包が `Task { await server.send(event) }` で送っていた。この Task は誰も持っていないので、片付けからは待てない。止める直前に判定が重なると、server を閉じた後に送られて落ちる。

#1667 は、この知らせを話者のイベントと同じ `AsyncStream` に入れた。流し切る段は、すでにこの流れを閉じて、読み終わるまで待っている。だから送り手を新しく待つ仕組みは要らなかった。直したのは、`LiveCapture` に `server` を渡すのをやめ、`emitEvent: { continuation.yield($0) }` を渡すところだけだ。待てない送り手を見つけたら、待つ仕組みを足す前に、すでに待っている流れに合流させられないかを見る。

### 4. 「送り終わった」は「相手が受け取った」ではない。ただし、その反例が現実に起きる根拠が無い入力なら、要件に上げずに記録だけ残す

#1666 の実装の run は、一度ここで止まった。「共有画面が無くても、止める直前の発言が届く」を確かめるテストが、10 秒の期限で落ち続けたのだ。

切り分けで分かったことは次のとおり。

| 試したこと | 結果 |
|---|---|
| `LiveSession` 経由。送信の完了待ちの数と完了のコールバックを、同じ実行で受信と照らす | 未完了の送信は 0 件、完了のコールバックにも失敗が無い。それでも発言だけが届かない |
| `LiveSession` を外し、server だけで「`origin` → 同じ発言 → `waitUntilSent` → `stop`」 | `origin` しか届かない |
| 同じ入力で、発言を受け取った後に `stop` | 届く |

つまり、送信の完了のコールバックが返った直後に接続を閉じると、受け手はまだ読み終えていないことがある。実装の担当は「`waitUntilSent` の後に閉じれば届く」という計画の前提が崩れたと報告し、server の接続の閉じ方を変える再計画を求めた。

ところが、落ちていた発言は、テストが作った 524,288 文字の `x` だった。JSON にすると 1,573,025 バイトになる。再計画の段は、この量が現実に起きる根拠を探した。本物の認識（`SpeechAnalyzerTranscriber`）がこの長さの反復を作る根拠は、要求にもコードにも無かった。そこで、この量を必須の条件に上げないと決め、テストの発言を「こんにちは」に替えた。止める時点も、期限も、確かめる中身も変えていない。この条件では全部通った。巨大な発言で落ちた記録と、比べたコードは消さずに残した。直したとは扱っていない。

判断の基準は 2 つあった。反例を見つけたら、その入力が現実の経路で起きるかを先に確かめる。起きないなら、反例を消したことにも、直したことにもせずに、記録を残す。

1 つ気がかりが残る。共有画面のイベントは JPEG の画像を base64 で載せるので、発言よりずっと大きなフレームになる。どの大きさから受け手の読み残しが起きるかは、測っていない。

### 5. 関係のないテストが時間切れで落ちたら、まず自分が足したテストが協調スレッドを塞いでいないかを疑う。`LIBDISPATCH_COOPERATIVE_POOL_STRICT=1` で手元でも再現できる

#1667 の PR は、CI の helper の IT で落ちた。落ちたのは `FileReadingAlignment` と `invNoReadWhilePaused` の 2 つの suite で、どちらも録画からのセッションのテストだ。PR が触ったのは `LiveSession.swift` とそのテストだけだった。CI を流し直しても、同じ 2 つが落ちた。

takt の CI の調査は「証拠が足りない」で止まった。調査は、PR が足したテストの `LiveSessionITTests.swift:354` にある同期のセマフォの待ちに気づいていた。それでも「これが他のテストの失敗を引き起こした証拠はない」と書いて、先へ進まなかった。

その後の直しのセッションが、原因を突き止めた。足したテスト「無音の判定中に stop が重なっても、知らせを届けてから接続を閉じる」は、判定のフックの中で `DispatchSemaphore.wait` していた。フックは Swift concurrency の協調スレッドの上で動く。セマフォを解くのはテスト本体で、テスト本体も協調スレッドで動く。協調スレッドの数はコア数なので、スレッドの少ない CI のランナーでは、解く側が走れない。`waitFor` の期限の 10 秒まで止まり、並んで走っていた時刻に頼る IT まで巻き添えにしていた。

切り分けには、協調スレッドのプールを 1 本に絞る環境変数を使った。

```sh
LIBDISPATCH_COOPERATIVE_POOL_STRICT=1 swift test --skip-build --filter 'ITTests/'
```

PR の版のテストでは 28 件落ちた。製品コードはそのままで、`LiveSessionITTests.swift` だけを main の版に戻すと、2 回とも全件通った。直し方は、停止の要求とその待ち合わせを `Thread.detachNewThread` に出すことだ。フックが待つのは、そのスレッドが停止を要求するまでになり、テスト本体の進みは待たない。直した後、同じ環境変数で 3 回流して、3 回とも 162 件が通った。

この罠は 2 回目だ。10 月 16 日の [#1197](https://github.com/daiki-beppu/live-mindmap/issues/1197) では、Vision の OCR が中でセマフォを待っていて、協調スレッドの上から同期で 3 つ同時に呼ぶと、3 コアのランナーで helper の IT が丸ごと止まった。そのときも、同じ環境変数で手元で再現している。どちらも、コア数の多い手元では通り、CI でだけ落ちた。そして、落ちたのは塞いだテストではなく、隣のテストだった。

## 取り込みの終わらせ方を sink に 1 回で渡す形にしたら、4 通りの終わり方が 2 種類で足り、終わらせる手順を 2 段に分けた理由は呼ぶ側の手順を間に挟むためだった話

live-mindmap の server では、helper から届く発言や共有画面をセッションに入れることを「取り込み」と呼ぶ。セッションの開始・停止と状態は `Sessions` という Service が持つ。1 つのセッションに届いたものをログ（`log.jsonl`）・マップ・書き出しのファイルへつなぐ組み立ては、sink（`SessionSinks` が作る）が持つ。取り込みの終わらせ方は 4 通りある。会議の最中に取り込む「ライブのセッション」を利用者が止めたとき。会議の録音ファイルから組み立てる「録画からのセッション」を利用者が止めたとき、読み終えたとき、helper の起動し直しの上限に達して諦めたとき。この 4 通りごとに、`Sessions` が sink の 6 つの口（`drain`・`discardBacklog`・`finishBacklog`・`flush`・`exports`・`ocrSummary`）を、決まった順で並べて呼んでいた。これを、sink に終わり方を 1 回渡すだけの形に変えた。決めたのは仕様 [#1636](https://github.com/daiki-beppu/live-mindmap/issues/1636)（親 [#1662](https://github.com/daiki-beppu/live-mindmap/issues/1662)）だ。その元になった設計の地図 [#1534](https://github.com/daiki-beppu/live-mindmap/issues/1534) で、3 つの問いを順に決めた。終わり方の種類（[#1536](https://github.com/daiki-beppu/live-mindmap/issues/1536)）、規則の置き場所と interface（[#1537](https://github.com/daiki-beppu/live-mindmap/issues/1537)）、テストの置き換え（[#1538](https://github.com/daiki-beppu/live-mindmap/issues/1538)）だ。実装は 2 本のチケットに分け、takt（issue を計画から実装・レビューまで自動で回すワークフロー）で流した。ライブが落ちたときの口を 1 つにする [#1663](https://github.com/daiki-beppu/live-mindmap/issues/1663) と、終わりの口を `end(ending)` と `writeOut` にする [#1664](https://github.com/daiki-beppu/live-mindmap/issues/1664) だ。コードを書く前に、仕様の性質を Quint で書いて TLC で全状態を調べてある（31,256 状態）。HTTP の stop の応答、CLI へ流す終了の知らせ、`log.jsonl` の行、書き出すファイルは、どれも変えていない。

先に、この節で使う sink の内側の言葉を 3 つ説明しておく。

- **settling**: 認識がまだ確定していない発言（途中結果）を、確定を待つ間持っておく段。止めた瞬間に残っている途中結果を、発言として締めて入れるかどうかが、終わり方で変わる
- **feed**: 締めた発言をマップへ入れる入口。ライブではそのまま入れる。録画からのセッションでは、2 本のトラック（相手と自分）の発言を時刻の順に並べ替え、溜まりに積んでから入れる
- **溜まり**: 録画からのセッションで、まだマップに入れていない発言の列。別の fiber の worker が 1 件ずつ入れる

### 1. 終わり方は「何が起きたか」ではなく「受け手が何を変えるか」で数える。4 通りの終わり方は、sink から見ると 2 種類だった

#1536 では、まず 4 通りの終わり方ごとに、sink を呼ぶ順を表にした。

| 終わり方 | 溜まりの扱い | 呼ぶ順（`[ ]` は sink 以外の手順） |
|---|---|---|
| ライブ・止めた | 入れ切る（溜まりは無い） | `[helper を止めて終わりを待つ]` → `drain` → `[SIGKILL の注意]` → `flush` → `exports` → `ocrSummary` |
| 録画・止めた | 捨てる | `discardBacklog` → `[helper を止めて終わりを待つ]` → `finishBacklog` → `flush` → `exports` → `ocrSummary` → `[finished]` |
| 録画・読み終えた | 入れ切る | `drain` → `finishBacklog` → `[claim]` → `flush` → `exports` → `ocrSummary` → `[finished]` |
| 録画・諦めた | 捨てる | `[intake-gave-up の行]` → `discardBacklog` → `finishBacklog` → `[claim]` → `flush` → `exports` → `ocrSummary` → `[finished{failure}]` |

並べてみると、「諦めた」と「利用者が止めた」の違いは、CLI に流す終了の知らせ（`finished`）に `failure` が付くかどうかだけだった。それは `Sessions` が CLI と結んでいる契約で、sink の仕事ではない。sink がやることは「待っている発言を全部入れる（入れ切る）」か「捨てる」かの 2 つしかない。ライブには溜まりが無いので、ライブの stop も「入れ切る」と同じ型で表せる。ライブの feed では、終えるのも捨てるのも何もしない（`Effect.void`）だけだ。

```ts
export type Ending =
  | { kind: "入れ切る" }
  | { kind: "捨てる"; quiesce: Effect.Effect<void> };
```

起きた出来事で種類を作ると、4 つの種類と、それぞれの手順の写しができる。受け手が振る舞いを変える軸で数えれば 2 つで済み、残りの違いは、それを気にする側（ここでは CLI への契約を持つ `Sessions`）に置いておける。

### 2. 落ちたときの口は終わり方に入れない。ただし、終わった sink を型で閉じたわけではない

helper が予期せず落ちても、セッションは終わらない。用語集の「取り込みの途切れ」で、取り込みが戻れば同じマップに続けて組み立てる。落ちたとき、ライブの `Sessions` は `drain` と字幕を消す `clearSpeaking` を続けて呼んでいた。#1663 はこれを `LiveSink.interrupted` の 1 つにした。録画からのセッションには、もとから `drainForRestart`（settling を流し、起動し直す位置を数える）の 1 つがある。

```ts
return { ...sink, interrupted: Effect.andThen(flow.drainForRestart, flow.clearSpeaking) };
```

（`flow.drainForRestart` は、`remarkFlow` の中では settling を流すだけの口だ。）

この 2 つを `Ending` の 3 つ目・4 つ目の種類にしなかったのは、終わった後に使わない sink と、落ちても使い続ける sink の区別を interface に残すためだ。ライブの型には `interrupted` だけがあり、録画の型には `drainForRestart` だけがある。それぞれの口だけを持つことは、型のテストで確かめている。

一方で、`end` を呼んだ後の sink が使えなくなるわけではない。`end` は何も閉じないので、その後も sink の口は呼べる。実際、話者の名前のテスト（`speakerNames.it`）は、地図なしの録画からのセッションで `end({ kind: "入れ切る" })` を呼んだ後に、`nameSpeaker` で話者に名前を付けている。区別が残っているのは、口の名前と `Sessions` がどこでそれを呼ぶかにであって、型が後から呼ぶことを止めているわけではない。

### 3. 途中に呼ぶ側の手順が挟まる終わり方では、その手順を引数で受ける。順を呼ぶ側に返さずに済む

一番難しかったのは「録画・止めた」だった。待っている発言を捨てるのは、helper を止める**前**でなければならない。前の決定（[#1238](https://github.com/daiki-beppu/live-mindmap/issues/1238)）で、「server が stop を受けた時点で待っている発言を捨てる」と決めてあるからだ。一方で、溜まりの worker を終えるのは、helper の終わりを待った**後**だ。そして helper を止めて終わりを待つ手順は、`Sessions` が持つと #1238 で決めてある。sink に 1 回で渡したいのに、sink の手順の真ん中に `Sessions` の手順が入る。

#1537 では 3 つの案を比べた。

| 案 | 中身 | 結果 |
|---|---|---|
| A | `end` は待たずに返す。片付けと書き出しを 1 回だけ走る Deferred として持つ | 退けた。1 回だけ走る状態と、`end` が 2 回重なったときの約束が sink に増える。それでも「helper を止める前に `end` を呼ぶ」という順は `Sessions` に残る |
| B | `Sessions` の手順を引数で受ける。状態の claim も受ける | claim を受けるのはやめた（5 節）。手順だけを受ける部分は C に取り込んだ |
| C | 新しい module `sessionEnding` を作る | 退けた（4 節） |

残った形は、「捨てた後、終える前に走らせる手順」を `quiesce` として `Ending` に持たせるものだ。

```ts
const { writeOut } = yield* recorded.sink.end({ kind: "捨てる", quiesce: Effect.gen(function* () {
  yield* recorded.controller.stop;
  const running = yield* Ref.get(recorded.running);
  if (running !== undefined) yield* running.end;
}) });
```

helper を止める手順は `Sessions` の Effect のままで、sink はそれを**走らせる位置**だけを持つ。「諦めた」ときは helper がもう止まっているので、`quiesce: Effect.void` を渡す。同じ「捨てる」の口で、止めたときと諦めたときの両方を表せる。

### 4. 新しい module を作るかは削除テストで決める。消すと十数行が元の場所に戻るだけなら作らない

C 案の `sessionEnding` は、削除テストで pass-through だった。削除テストとは、その module を消したら複雑さがどこへ行くかを考えることだ。消すと、15 行ほどの並べ方が `remarkFlow`（発言の流れの module）に戻るだけだった。しかも `sessionEnding` を作ると、`remarkFlow` の 2 つの半分（settling と feed）を別々の関数として渡す必要があり、interface がかえって広がる。録画の feed の module（`recordedFeed`）は settling も書き出しも見えないので、置き場所にならない。

そこで、片付けの順は `remarkFlow` の `settle` に置いた。「settling の後に feed」という順は、`remarkFlow` がもともと持っていたからだ。

```ts
settle: Effect.fnUntraced(function* (ending: Ending) {
  if (ending.kind === "入れ切る") yield* settling.drain;
  else {
    yield* feed.discard;
    yield* ending.quiesce;
  }
  yield* feed.finish;
}),
```

「捨てる」では settling を流さない。止めた瞬間の途中結果は、待っている発言として捨てる側に入る。

### 5. 2 段に分けたのは、片付けと書き出しの間に呼ぶ側の手順を挟むためだった。「片付ける前に書き出す」も型の上で書けなくなる

sink の終わりの口は、`end(ending)` が `{ writeOut }` を返す 2 段にした。

```ts
end: (ending: Ending) => Effect.Effect<{ writeOut: Effect.Effect<Written> }>;
```

`writeOut` は `end` の結果からしか取れないので、片付ける前に書き出すコードは書けない。これは仕様が最初に挙げた理由だった。けれども、比べた案を振り返ると、2 段にした決め手はもう 1 つの理由のほうにある。`end` と `writeOut` の間に、`Sessions` が自分の手順を挟めることだ。

録画からのセッションを読み終えたとき、`Sessions` は `end` の Exit を受け取ってから状態を claim する（stop と取り合いになったときに、どちらが書き出すかを決める）。claim を片付けの**後**に置くのは、録画を実時間の速さで入れているときの「入れ切る」に数分かかることがあり、その間も stop で割り込めるようにするためだ。割り込んだ stop の「捨てる」が溜まりの待ちを解くと、走っていた「入れ切る」も抜ける。その後の claim は stop の側が取っているので、読み終えた側は何もしない。ライブの stop では、helper を SIGKILL で止めたときの注意を、`end` の後・`writeOut` の前に出す。

B 案は、claim まで sink に渡して 1 回の呼び出しで全部の順を持たせようとした。ところが、claim に勝ったときだけ書き出し、その書き出しは別の fiber で走らせる必要がある。そのため、書き出しをコールバックで受ける形になり、claim → fork → 終了の知らせ → 閉じる、という順は結局 `Sessions` に残った。「1 回の呼び出しで全部の順を持つ」は、型の上でしか成り立たなかった。呼ぶ側の手順を挟む場所が要るなら、無理に 1 回にせず、その場所で区切って結果を返すほうが素直だ。

`writeOut` は結果を覚えずに、呼ぶたびにその時点の状態を書き出す。テストには、`end` の後に `writeOut` を 2 回呼ぶと 2 回撮影すること、`end` だけでは何も書き出さないことを確かめるもの（「endの後もwriteOutを実行するまで書き出さず、実行ごとに撮影する」）がある。書き出しに話者の名前が出ることを確かめるテスト（`people.it`）は、`end` の後に名前を付け替えるたびに同じ `writeOut` を呼び、3 回書き出している。2 節で書いたとおり、`end` の後も sink を使えることに頼っている。

### 6. 「害の無い 2 回目」は、呼ぶ側が中身を知りすぎている印だった

録画からのセッションを読み終えたとき、`Sessions` は `drain` → `finishBacklog` の順に呼んでいた。ところが `finishBacklog` の中身は「feed の drain（並べ替えの保留を溜まりへ出す）→ 溜まりを終える」だった。feed の drain が 2 回走っていたことになる。2 回目は空なので、害は無い。

#1536 はこれを、直す価値のある不具合ではなく、浅さの印として扱った。呼ぶ側が「`drain` には settling が要る」「`finishBacklog` には feed の drain が入っている」と知っていないと、正しく並べられない、という印だ。単独では直さず、終わり方を 1 回で渡す形にすれば消える、とした。#1664 では、`Feed` の `drain` を `finish` と `discard` の 2 つに置き換え、録画の feed の `finish` に drain を含めた。形式仕様にも「入れ切るの feed の drain は 1 回だけ」（`invFullDrainOnce`）を入れた。

同じ印は、テストにもあった。`recordedFeed.test` には `const finish = (r) => Effect.andThen(r.feed.drain, r.feed.finish)` という手伝いがあり、27 か所で使われていた。テスト自身が「drain してから finish」という順を写し持っていたわけだ。#1664 で、27 か所はすべて `r.feed.finish` 1 つになった。

### 7. 両側の unit がそれぞれ相手を偽物にしているとき、つなぎ目は誰も見ていない。組み立てに IT を 1 本だけ足す

前は、`Sessions` の unit（`sessions.test`）が、偽の sink への呼ぶ順を確かめていた。たとえば諦めたときは `["gave-up","discard","finish","flush","exports"]` だ。この順の半分は `remarkFlow` の規則で、同じ規則が 2 か所に書かれていた。#1538 で、`sessions.test` が見るのは `Sessions` が持つ順だけにした。渡した終わり方、`quiesce` の中で helper を止めること、`writeOut` が 1 回で閉じる前に済むこと、`intake-gave-up` の行が `end` の前に書かれること、の 4 つだ。テストの名前も「stopは溜まりを捨ててからヘルパーを止め、finish後に書き出す」から「録画のstopは捨てるを渡し、quiesceでヘルパーの終了を待ってから書き出す」に変わった。偽の sink が真似るのは、「捨てる」で `quiesce` を走らせることだけだ。走らせないと helper が止まらず、テストが進まない。settling と feed の順は、それ自身が約束である `remarkFlow.test` で見る。

こうすると、`remarkFlow.test` は偽の feed を使い、`sessions.test` は偽の sink を使うことになる。どちらも相手を偽物にしているので、組み立て（録画の sink を作るところ）で feed の `finish` を `settle` につなぎ忘れても、どちらも落ちない。つなぎ忘れれば並べ替えの保留に残った発言が落ち、2 回つなげば二重に入る道ができる。それまでの「読み終えた」道の IT は、音声ファイルと題名しか見ていなかった。

そこで、本物の流れのテストを 1 本だけ足した。`sessionsRecorded.it` の「録画が済んだら、台本の発言がすべて1回ずつ入る」だ。

```ts
expect(remarksOf(logLines(dir)).map(({ id, end }) => ({ id, end }))).toEqual([
  { id: "r1", end: 600 }, { id: "r2", end: 660 }, { id: "r3", end: 750 },
]);
```

足す前に、このリポジトリのテストの規約にある「証拠の 5 つ」を書いた。義務（組み立てが変わる）、約束（読み終えたら作った発言をすべて 1 回ずつ入れる）、落ちる道（つなぎ忘れ・二重につなぐ）、今のテストが拾わない理由（両側が偽物）、最小の層（実物の sink の組み立てとファイルシステムを通るので light IT）の 5 つだ。逆に、「最後の差分更新が終わってから閉じる」を `sessions.test` で見ていたテストは消した。`Sessions` の側の約束は `["writeOut","close"]` の順を見る別のテストが、sink の側の約束は `sessionSinks.it` が、もう見ていたからだ。

## マップの「畳めるノード」の規則を 1 つの module に集めたら、押せる点と効き方が同じ値から出るようになり、呼ぶ側から移した分岐が出来事の名前で決めていた待機の計り直しを連れてきた話

live-mindmap の web の画面は、マップのノードを「畳む」。畳むとは、ノードの子孫を隠して 1 つにまとめて見せることで、マップのデータではなく見せ方の話だ。既定では、`済み` の議題・論点と、`話し中` でも最後に触れてから 15 分たった議題を畳む。今の議題（会議でいま話されている議題）とその祖先は畳まない。人も議題・論点を Enter か、ノードに付く畳みの点で開け閉めでき、そのときは人の操作を優先する。畳んだ議題が兄弟として続くと、「議題 N 件」という 1 つのまとめ（一続きのまとめ）になり、これは開け閉めではなく「解く」対象だ。振る舞いは正しかったが、「どのノードを畳めるか」の規則が web の 3 か所に写されていて、人の開閉の記録をどう変えるかも、見せ方の reducer（キー・クリック・反映などの出来事から選択とカメラを決める関数）に散っていた。これを畳む module（`web/src/folding.ts`）1 つに集めた。決めたのは仕様 [#1615](https://github.com/daiki-beppu/live-mindmap/issues/1615)（親 [#1659](https://github.com/daiki-beppu/live-mindmap/issues/1659)）で、元になった設計の地図 [#1551](https://github.com/daiki-beppu/live-mindmap/issues/1551) で、写しの扱い（#1552）・値の置き場所（#1553）・テストの置き換え（#1554）・interface（#1608）を順に決めた。実装は 2 本のチケットに分け、takt（issue を計画から実装・レビューまで自動で回すワークフロー）で流した。ノードごとの開閉の値を出す [#1660](https://github.com/daiki-beppu/live-mindmap/issues/1660) と、人の開閉の記録とその変え方を移す [#1661](https://github.com/daiki-beppu/live-mindmap/issues/1661) だ。コードを書く前に、仕様の性質を Quint で書いて TLC で全状態（228,349 状態）を調べてある。利用者から見た振る舞いは変えていない。

### 1. 写しがどの入力でも同じ結果を出していても、写しがある限り「押せる点と効き方の食い違い」は書けてしまう。判定と描き分けを 1 つの値から出すと、食い違いそのものが書けなくなる

写しは 3 つあった。畳む module の `isFolded`（スナップショット上の今の議題の鎖、議題・論点か、人が開いたか、人が畳んだか、選択の祖先か、`済み`・15 分か、の順に見る）。見せ方の reducer の `foldToggle` で、Enter が効くかを決めるために、今の議題から見えている木の親をたどり直していたところ。マップ面の木を作る関数 `treeOf` で、「議題か論点なら開閉の欄を持つ」と種別を写していたところ。テストの中にも、`treeOf` を写した `visibleOf` があった。

#1552 で 3 つを突き合わせ、どの入力でも同じ結果を出していて、意図した差は無いと確かめた。だから今は壊れていない。それでも直す理由になったのは、どれか 1 つを誤って変えても、テストが落ちないまま「点は出ているのに押しても効かない」画面が出うることだった。テストの `visibleOf` も同じ写しなので、本番の写しと一緒に間違えれば、テストも一緒に通る。

#1660 では、畳む module がノードごとの開閉を 4 値で返すようにした。

```ts
export type Openness =
  | { state: "folded"; hint: string | null; hidden: number }  // 畳んだ（押すと開く）
  | { state: "open"; byHuman: boolean }                        // 開いた（byHuman のときだけ「畳む」の点を出す）
  | { state: "bundle"; hint: string | null; hidden: number }   // 解ける（一続きのまとめ）
  | { state: "fixed" };                                        // 開閉できない
```

マップ面のノードの描き分けも、Enter で何をするかも、まとめをクリックしても選ばないことも、この値 1 つだけを見る。`foldToggle` は `switch (tree.fold?.openness[id]?.state)` の 4 行になり、`treeOf` の種別の写しは `fold: view` の 1 行になった。

値をまとめると、起きない分岐も見える。前の描き分けには「畳んであるが開閉できない（数だけを出す）」という分岐があった。けれども、開閉できないのは今の議題とその祖先と議題・論点以外のノードで、そのどれも畳まれない。4 値にすると、この組み合わせは表せず、分岐ごと消えた。

### 2. 見せ方に「自分を作った材料」を外から見えない形で持たせると、遷移に古い見せ方や別の材料を渡せなくなる。代わりに、写した見せ方では遷移が効かない

人の操作で人の開閉を変える関数は `refold(view, action)` にした。スナップショットを別に受け取らない。見せ方（`FoldView`）が、自分を作ったスナップショット・人の開閉・選択を持っているからだ。仕様の interface を比べた #1608 は、3 案を作って比べ（design-it-twice）、この形を軸にした。スナップショットを別に受け取る形だと、呼ぶ側が「今のスナップショット」と「前の人の開閉で作った見せ方」を組み合わせて渡せてしまい、見せた開閉と違う計算で遷移を判定する誤りが型の上で書ける。

実装では、材料を `FoldView` の型には足さず、`WeakMap<FoldView, Basis>` に入れた。`FoldView` は見た目には `nodes`・`openness`・`blink`・`shownAs` だけのただのデータのままで、呼ぶ側は材料を読めない。#1660 の段階では、まとめの中の議題の並びだけをこの形で隠し、`bundleMembers` という関数で引かせていた。#1661 で、それを材料全体（`Basis`）に広げ、`bundleMembers` は消えた。2 本に分けたチケットの間の足場として、隠し場所だけ先に作ったことになる。

この形には、はまりどころが 1 つある。材料は見せ方のオブジェクトそのものに紐づくので、`{ ...view }` で写したり、テストで手組みしたりした見せ方には材料が無い。そのとき `refold` は例外を投げずに `null`（効かない）を返す。カメラや矢印を位置で確かめるテストの手組みの木は、もともと `fold: null` にして開閉を効かせない約束にしたので困らない。けれども、見せ方を写してから `refold` に渡すと、黙って何も起きない。

### 3. 呼ぶ側にあった分岐を中へ移すときは、呼ぶ側が出来事の「名前」で決めていた副作用を確かめる。今回は、見返しで自動のカメラに戻るまでの待機の計り直しだった

前は、マップ面が変更一覧（右の列の「変わったこと」）のクリックを受けると、まず指した ID がスナップショットにあるかを調べていた。無ければ（統合で消えたノードなど）、見せ方の reducer には `select`（ノードを選ぶ）の出来事として渡していた。仕様は、この分岐を見せ方の reducer に移すと決めた。マップ面は `pointChange` を渡すだけになり、reducer が `refold` の `null` を見て「ただの選択」として扱う。

選択の結果は同じになった。けれども、マップ面にはもう 1 つ、出来事の名前で決めていることがあった。見返しでは、人が触ってから 10 秒たつと、カメラが手動から自動に戻る。その待機を計り直すかどうかを、マップ面は `keepsIdleTimer` で、出来事の種類が `select`・`deselect` などかどうかで決めていた。前は消えた ID のクリックが `select` として届いたので、待機は計り直されなかった。移した後は `pointChange` として届くので、そのままだと計り直してしまう。

#1661 は、reducer の戻り値に `preserveIdleTimer` を足し、消えた ID の `pointChange` のときだけ立てて、計り直さない前の振る舞いを保った。あわせて、カメラの Story テストに「見返しの manual で不存在 ID の変更項目を選んでも待機を計り直さず、有効な対象なら寄せて計り直す」を足した。分岐の結果（何を選ぶか）は仕様の表に載っていたが、出来事の名前に付いていた副作用は、どの表にも載っていなかった。

### 4. 「2 回目の計算」は消すのではなく、module の中へ入れる。祖先を開くかどうかは、形式仕様で「足さなくても必ず見える」と確かめてから決める

変更一覧のクリックの中身は、「指したノードの祖先に付いた人の畳みを外し、選んだ状態でなお畳まれるなら、指したノードを開く」だ。前は、マップ面が `pointedNode` という関数で畳む計算をもう 1 回走らせ、その結果（祖先の一覧と、開くかどうか）を出来事に載せて reducer に渡していた。#1661 では、この 2 回目の計算をそのまま `refold` の `point` の中へ入れた。人の畳みを外した材料と、選択を指したノードに移した状態で `foldView` を作り直し、指したノードが `folded` なら開く。2 回目を走らせること自体は規則なので、消さずに置き場所だけ変えた。出来事の `pointChange` は ID だけを運ぶ。

ここで迷いうるのが、祖先が既定の理由（`済み`・15 分）で畳まれているときに、祖先も人が開いた集合に足すかどうかだ。足さないと指したノードが隠れたままになりそうに見える。形式仕様は、これを性質 `invPointShows`（指したノードは選ばれ、見えて、畳まれていない）として書き、全状態で確かめた。結論は、足す必要がない、だった。指したノードに選択が移るので、その祖先は「選択の祖先は既定では畳まない」の規則で開く。人の畳みだけを外せば、残る畳む理由は既定の理由だけで、それは選択の保護に負ける。テストにも「隠れた決定を point すると祖先が選択で開くが、人が開いた扱いにはならない」が 1 件ある。祖先を開いた集合に足していたら、選択を外したときに、人が開いた覚えのないノードが開いたまま残っていた。

### 5. テストの期待値から内部の集合を外すと、同じ失敗を 2 か所で見ていたテストがまとめて消える。見せ方の reducer のテストは 728 行減った

仕様は、畳む規則の契約を「スナップショットと人の操作の列の後に、何が見え、どのノードがどう開閉できるか」と書いた。人の開閉の集合（開いた・畳んだ・解いた）の中身は内部の値なので、期待値に書かない。前のテストは、見せ方の reducer のテストが `humanOpened` などの集合を、畳む module のテストが見せるノードを、それぞれ確かめていて、同じ規則の失敗を 2 か所で拾っていた。

#1661 では、テスト用の手伝い `foldingActions(snapshot, actions)` を足した。`FoldAction` の列を `refold` で畳み込み、最後の `foldView` を返す。途中の操作が効かずに `null` を返したら、そこで失敗にする。畳む module のテストはこれで書き直し、見るのは見せるノードの ID と `openness` だけにした。見せ方の reducer のテストには、選択とカメラの期待値だけを残した。差分は、`viewing.test.ts` が 102 行足して 728 行消し、`folding.test.ts` が 314 行足して 281 行消した。web の unit テストの件数は、#1660 の報告の 1,884 件から #1661 の報告の 1,823 件になった（この間に main に入った PR は server と文書だけ）。

仕様の約束と実装が 1 か所だけずれている。仕様は `refold` が `null` を返すのを、`toggle` の見せていない ID・`fixed` の ID と、`point` のスナップショットに無い ID の 2 つに限っていた。実装は、`reflect`（反映で今の議題に付いた人の畳みを解く）も、解く畳みが無いときに `null` を返す。呼ぶ側は `null` を「人の開閉はそのまま」と読むので振る舞いは同じで、`foldingActions` も `reflect` の `null` だけは失敗にしない。

### 6. 規則を 1 か所に集めると、用語集の言い足りなさも見える。直すのは文言で、振る舞いではない

用語集の「畳む」は「人も議題を開いたり畳んだりでき」と書いていた。けれども、#320 で決めて出荷した振る舞いでは、人は論点も開け閉めできる。`isFolded` の「議題・論点か」の条件を正にすると決めたとき、この食い違いが表に出た。仕様は、規則を変えずに、用語集を「人も議題・論点を開いたり畳んだりでき」に直すと決め、#1661 で直した。一方で、`HumanFolds`・`Openness` や module の名前は用語集に足していない。利用者に見える概念が増えないので、「畳む」の説明で足りる、とした。
