## helper のライブのセッションを差し替えられる module にしたら、止める直前のイベントの欠けが直り、CI の時間切れの 1 つはテスト自身が協調スレッドを塞いでいた話

live-mindmap の helper は、会議アプリの音とマイクを取り込み、文字起こし・話者分離・共有画面（会議で映っていた画面）の判定をする Swift のプロセスだ。結果はイベント（発言・話者の区間・画面など）として WebSocket で server に送る。会議の最中に取り込む「ライブのセッション」の組み立ては、`main.swift` の `run` という約 200 行の関数がすべて持っていて、テストは 1 本も無かった。これを HelperCore の module `LiveSession` に移し、機器（音の tap・マイク・認識・話者分離・入力の使用・共有画面・時計）を偽物に差し替えられる形にした。決めたのは仕様 [#1639](https://github.com/daiki-beppu/live-mindmap/issues/1639)（親 [#1658](https://github.com/daiki-beppu/live-mindmap/issues/1658)）で、実装は 3 本のチケットに分けた。イベントの送り口を 1 つにする [#1665](https://github.com/daiki-beppu/live-mindmap/issues/1665)、module に移して終わらせ方を 5 段にする [#1666](https://github.com/daiki-beppu/live-mindmap/issues/1666)、片付けで `tap-silent` を待つ [#1667](https://github.com/daiki-beppu/live-mindmap/issues/1667) だ。3 本とも takt（issue を計画・テスト・実装・レビューまで自動で回すワークフロー）で流した。コードを書く前に、仕様の「常に成り立つべき性質」を Quint で書いて TLC で全状態を調べてある（仕様のコメント）。

### 1. 「ついでに待っている」順は、待つ側がいない構成で壊れる。守る順は段の並びとしてコードに置き、段の中は順不同と書く

止める直前のイベントが server に届くのは、送り終わりを待ってから server を閉じるからだ。ところが、その待ち（`waitUntilSent`）を呼んでいたのは共有画面の Task の末尾だけだった。共有画面を送り終えるついでに、全部の送り終わりを待っていたことになる。`--no-screen` で取り込んだときや、画面収録の許可が無い Mac では、この Task が無い。誰も待たずに server を閉じるので、止める直前の発言や話者の区間が落ちうる。共有画面があっても、休止の監視が最後に出す `self-pause-state`（自分の休止の状態。`自分` のトラックを取らない間かどうか）は待たれていなかった。これが落ちると、マイクの機器が変わって helper を起動し直したとき、古い休止の状態から始まる。

片付けは 11 段あった。守らないと壊れる順と、たまたまの順が混ざっていて、その区別はコメントにしか無かった。破っても失敗としては出ない。片付けがハングし、server が SIGTERM の 5 秒後に SIGKILL を送るだけだ。録音のファイルは閉じられずに残る。

仕様はこれを 5 段に束ねた。

1. 止める（音声・休止の監視と入力の通知・共有画面）
2. 流し切る（話者の流れ・共有画面の Task・休止の監視の Task・`tap-silent` の送信・録音の `finish`）
3. 送り終わりを待ってから server を閉じる。共有画面の有無によらない
4. 指示の Task を待つ（server の受け取りの流れは、server を閉じたときにしか終わらない）
5. 失敗を選ぶ（本処理 → `相手` の録音 → `自分` の録音の順に、最初の失敗を投げる）

段の中は順不同で、並べて待ってよいと書いた。順を確かめるテストも、段の中については書かないと決めた。形式仕様では、モデルを 1 か所だけ壊した mutant で各性質が赤くなることを確かめた。「段 3 は共有画面があるときだけ送り終わりを待つ」、つまり今の形の mutant で、「閉じた時点で全部届いている」という性質が赤くなる。今の欠けが、性質の言葉でそのまま再現できたことになる。

### 2. 残すかどうかを呼ぶ側に書かせない。種類の網羅の `switch` に `default` を書かなければ、種類を足したときの決め忘れがコンパイルで止まる

server は helper に後から接続することがある。そこで helper は、一部のイベント（原点・最新の画面・休止の状態など）の最新の 1 件を覚えておき、接続した直後に送り直す。どれを覚えるかは、呼ぶ側が `broadcastRetained(_:key:)` に文字列の key を渡して決めていた。その手書きの key が 9 か所にあり、`speakerOff`（話者分離が使えない知らせ）を覚えるかどうかを決める閉包は、2 か所に写されていた。新しい種類を足して覚えるかどうかを決め忘れても、何も落ちない。

#1665 は送り口を `WebSocketServer.send(_ event: HelperEvent)` の 1 つにし、扱いを `HelperEvent` の側の純粋な関数 1 つに置いた。

```swift
func delivery(retained: HelperEvent?) -> HelperEventDelivery {
    switch self {
    case .origin: return .retain(.origin)
    case let .screen(start, _, _, _, _):
        if case let .screen(previousStart, _, _, _, _) = retained, start < previousStart {
            return .connectedOnly
        }
        return .retain(.screen)
    // …覚える種類が続く
    case .remark, .partial, .speaker, .speakerSettled, .speakerMixed, .speakerCentroid:
        return .bufferUntilFirstClient
    }
}
```

`default` が無いので、`HelperEvent` に case を足すと、この関数に行を書くまでコンパイルが通らない。server がブラウザへ送る frame の表で前にやったのと同じ考え方だ。socket なしで全種類を確かめられるので、表のテストは unit に置けた。

ついでに 2 つの欠けが消えた。

- 前の時刻の画像を覚えないという規則は、画面を送る呼び出し側が `latestStart` を持って守っていた。今はこの表の `screen` の行にある。覚える枠を、エンコードした文字列ではなく `HelperEvent` のまま持つことにしたので、`start` を比べられるようになった。
- server が最初に接続するまでの数 ms〜数百 ms に出た発言は、前は黙って落ちていた。今は、最初の接続までは流すだけのイベントも送った順に溜める。接続したら、覚えた枠を表の順（`origin` が先頭）に送り、その後に溜めた分を送る。起動の段取りが変わっても、届く順は変わらない。

エンコードに失敗したイベントの扱いも、経路ごとにばらばらだった（黙って捨てる・セッションごと落ちる・書いて捨てる）。これは「標準エラーに種類の名前だけを書き、その 1 件を送らない」にそろえた。種類の名前だけにしたのは、`EncodingError` の文に発言の本文や画像が入りうるからだ。

### 3. 投げっぱなしの Task は、片付けからは待てない送り手になる。送り手を 1 本の流れに束ねると、流し切る段で待てる

相手の音が届いていないことの知らせ（`tap-silent`）は、無音の判定の閉包が `Task { await server.send(event) }` で送っていた。この Task は誰も持っていないので、片付けからは待てない。止める直前に判定が重なると、server を閉じた後に送られて落ちる。

#1667 は、この知らせを話者のイベントと同じ `AsyncStream` に入れた。流し切る段は、すでにこの流れを閉じて、読み終わるまで待っている。だから送り手を新しく待つ仕組みは要らなかった。直したのは、`LiveCapture` に `server` を渡すのをやめ、`emitEvent: { continuation.yield($0) }` を渡すところだけだ。待てない送り手を見つけたら、待つ仕組みを足す前に、すでに待っている流れに合流させられないかを見る。

### 4. 「送り終わった」は「相手が受け取った」ではない。ただし、その反例が現実に起きる根拠が無い入力なら、要件に上げずに記録だけ残す

#1666 の実装の run は、一度ここで止まった。「共有画面が無くても、止める直前の発言が届く」を確かめるテストが、10 秒の期限で落ち続けたのだ。

切り分けで分かったことは次のとおり。

| 試したこと | 結果 |
|---|---|
| `LiveSession` 経由。送信の完了待ちの数と完了のコールバックを、同じ実行で受信と照らす | 未完了の送信は 0 件、完了のコールバックにも失敗が無い。それでも発言だけが届かない |
| `LiveSession` を外し、server だけで「`origin` → 同じ発言 → `waitUntilSent` → `stop`」 | `origin` しか届かない |
| 同じ入力で、発言を受け取った後に `stop` | 届く |

つまり、送信の完了のコールバックが返った直後に接続を閉じると、受け手はまだ読み終えていないことがある。実装の担当は「`waitUntilSent` の後に閉じれば届く」という計画の前提が崩れたと報告し、server の接続の閉じ方を変える再計画を求めた。

ところが、落ちていた発言は、テストが作った 524,288 文字の `x` だった。JSON にすると 1,573,025 バイトになる。再計画の段は、この量が現実に起きる根拠を探した。本物の認識（`SpeechAnalyzerTranscriber`）がこの長さの反復を作る根拠は、要求にもコードにも無かった。そこで、この量を必須の条件に上げないと決め、テストの発言を「こんにちは」に替えた。止める時点も、期限も、確かめる中身も変えていない。この条件では全部通った。巨大な発言で落ちた記録と、比べたコードは消さずに残した。直したとは扱っていない。

判断の基準は 2 つあった。反例を見つけたら、その入力が現実の経路で起きるかを先に確かめる。起きないなら、反例を消したことにも、直したことにもせずに、記録を残す。

1 つ気がかりが残る。共有画面のイベントは JPEG の画像を base64 で載せるので、発言よりずっと大きなフレームになる。どの大きさから受け手の読み残しが起きるかは、測っていない。

### 5. 関係のないテストが時間切れで落ちたら、まず自分が足したテストが協調スレッドを塞いでいないかを疑う。`LIBDISPATCH_COOPERATIVE_POOL_STRICT=1` で手元でも再現できる

#1667 の PR は、CI の helper の IT で落ちた。落ちたのは `FileReadingAlignment` と `invNoReadWhilePaused` の 2 つの suite で、どちらも録画からのセッションのテストだ。PR が触ったのは `LiveSession.swift` とそのテストだけだった。CI を流し直しても、同じ 2 つが落ちた。

takt の CI の調査は「証拠が足りない」で止まった。調査は、PR が足したテストの `LiveSessionITTests.swift:354` にある同期のセマフォの待ちに気づいていた。それでも「これが他のテストの失敗を引き起こした証拠はない」と書いて、先へ進まなかった。

その後の直しのセッションが、原因を突き止めた。足したテスト「無音の判定中に stop が重なっても、知らせを届けてから接続を閉じる」は、判定のフックの中で `DispatchSemaphore.wait` していた。フックは Swift concurrency の協調スレッドの上で動く。セマフォを解くのはテスト本体で、テスト本体も協調スレッドで動く。協調スレッドの数はコア数なので、スレッドの少ない CI のランナーでは、解く側が走れない。`waitFor` の期限の 10 秒まで止まり、並んで走っていた時刻に頼る IT まで巻き添えにしていた。

切り分けには、協調スレッドのプールを 1 本に絞る環境変数を使った。

```sh
LIBDISPATCH_COOPERATIVE_POOL_STRICT=1 swift test --skip-build --filter 'ITTests/'
```

PR の版のテストでは 28 件落ちた。製品コードはそのままで、`LiveSessionITTests.swift` だけを main の版に戻すと、2 回とも全件通った。直し方は、停止の要求とその待ち合わせを `Thread.detachNewThread` に出すことだ。フックが待つのは、そのスレッドが停止を要求するまでになり、テスト本体の進みは待たない。直した後、同じ環境変数で 3 回流して、3 回とも 162 件が通った。

この罠は 2 回目だ。10 月 16 日の [#1197](https://github.com/daiki-beppu/live-mindmap/issues/1197) では、Vision の OCR が中でセマフォを待っていて、協調スレッドの上から同期で 3 つ同時に呼ぶと、3 コアのランナーで helper の IT が丸ごと止まった。そのときも、同じ環境変数で手元で再現している。どちらも、コア数の多い手元では通り、CI でだけ落ちた。そして、落ちたのは塞いだテストではなく、隣のテストだった。

### 6. PR の差分に直す対象が無い CI の赤は、期限の延長で隠さず、止めて別の issue に出す

#1666 の PR も、CI の helper の IT で落ちた。こちらは、本当に PR と関係が無かった。

| run | 落ちたテスト |
|---|---|
| main の `fe0304b`（この PR の base。#1665 のマージ） | `FileSessionRelayITTests` の 3 テスト・5 件。待っていた条件が 30 秒で成り立たない |
| PR の 1 回目 | 同じ 3 テスト・4 件 |
| PR の 2 回目（流し直し） | `FileSessionRelayITTests` は通り、`FileReadingPauseITTests` が 1 件落ちた |

手元（macOS）では 169 件が 2 回とも通った。直しのセッションは、期限の延長・テストの除外・assertion を緩めることを、根拠が無いという理由でどれもせず、「この PR では直せない」と書いて止まった。人が判断して流し直すと、3 回目で通り、マージされた。時間切れそのものは [#1681](https://github.com/daiki-beppu/live-mindmap/issues/1681) に分けた。#1681 には、ランナーの image が替わった頃から helper の IT 全体が 27 秒から 43〜55 秒に延びていることと、固定の 500ms の sleep で位置を写すテストがあることを書いてある。

5 節の赤と 6 節の赤は、見た目が同じだった。どちらも録画の経路の IT が、待ちの期限切れで落ちた。違いは、片方には PR が足した塞ぐ待ちがあり、もう片方には無かったことだ。「関係のないテストだから PR のせいではない」とも、「流し直せば通るからフレークだ」とも、見た目だけでは決められない。
