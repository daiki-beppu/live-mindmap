## 話者分離を前日の会議の記録で確かめたら、見返しが開くまで 39 秒かかるのに気づき、「埋め込みが大きい」という見立ては外れて、原因はイベント 1 件ごとの再計算だった話

話者分離は、相手側の音声（`相手` のトラック）の中を声で区別し、「相手 A」「相手 B」のような匿名のラベルを発言に付ける機能だ。実装の最後に、人が実際の会議で確かめる項目が残っていた（[#1412](https://github.com/daiki-beppu/live-mindmap/issues/1412)、親 [#1018](https://github.com/daiki-beppu/live-mindmap/issues/1018)）。これを前日の会議の記録で済ませる途中で、見返し（会議の後にマップの組み上がりを時刻を動かして見直す、1 ファイルの HTML）がとても重いことに気づいた。原因を [#1778](https://github.com/daiki-beppu/live-mindmap/issues/1778) に起票して [PR #1835](https://github.com/daiki-beppu/live-mindmap/pull/1835) で直し、二次的な要因の [#1779](https://github.com/daiki-beppu/live-mindmap/issues/1779) は測り直して閉じた。

### 1. 「人が実際の会議で確かめる」項目は、新しく会議を開かなくても、手元の記録で済むことがある。数から出せるものは先に出し、人には「どのラベルが誰か」だけを聞く

#1412 の手順は「相手 2〜4 人の会議を 1 本取り込んで見る」だった。何をすればよいかを聞かれて手順を説明したところ、利用者から「昨日のデータとか使えるんじゃない？」と返ってきた。前日の会議（約 3 時間 20 分）は、録音とログ（`log.jsonl`、出来事を 1 行ずつ書いたもの）が残っていた。

確かめる 4 項目のうち、ログの数だけで出せるものと、人にしか分からないものがあった。

| 項目 | 数から出せること | 人に聞いたこと |
|---|---|---|
| 字幕の相手のラベルが合っているか | ラベルごとの発言数（B が 67%、ラベルなしが 28%） | A・B・C・D がそれぞれ誰か |
| 案の出した人・TODO の担当者 | 担当が付いた数（17 件中 13 件）、付き先の内訳 | 一覧を見て妥当か |
| 名前が合っているか | 付いた名前の種類（2 つ） | その人で合っているか |
| 字幕が遅れないか | 発言を書いた時刻から、音声上の終わりの位置を引いた差 | なし |

字幕の遅れは、専用の計測をしなくても、ログに記録された時刻と発言の終わりの位置（`remark.end`）の差で出せた。中央値 2.4 秒・90% で 5 秒前後で、1 時間ごとに分けても 3 時間を超えても増えていなかった。

人に聞く項目では、見返しの HTML が重すぎて開けない、と言われた。そこで、相手 D の 8 発言だけを ffmpeg で録音から切り出し、1 本の音声にして渡した。

```sh
ffmpeg -ss <start-0.5> -to <end+0.5> -i 相手.m4a -ac 1 -ar 24000 d1.wav   # 発言ごと
ffmpeg -f concat -safe 0 -i list.txt -c:a aac 相手D_8件.m4a               # 1 秒の無音を挟んでつなぐ
```

聞くと、D は途中で抜けた 4 人目の人で、発言が少ないのは実際どおりだった。4 項目とも合格で、#1412 は閉じた。なお、途中の報告で TODO の担当が付いた数を 15 件と言い、issue へのコメントを書く段で数え直して 13 件に直した。数を報告するときは、数えた表から写す。

### 2. 「HTML が重い」の見立ては、ファイルの大きさから立てると外れる。測ると、時間はデータの読み込みではなく計算に使われていた

見返しの HTML は、`map.html` が 18MB、音声つきの `map-audio.html` が 81MB あった。中身を数えると、`map.html` はほぼすべてがログを丸ごと埋め込んだ部分で、その半分以上（約 9.8MB）が話者分離の途中経過の記録だった。見返しの画面のコードは、この 3 種類の記録を読んでいない。そこで「要らない記録まで埋め込んで大きくなっている」として、#1778 を「HTML が重い」で起票した。

triage（起票された issue を評価して、次の状態を決めること）の段で、headless の Chrome でプロファイルを取った。

| 計測 | 結果 |
|---|---|
| `map.html` の表示まで（LCP） | 38,764 ms |
| そのうち 1 本の処理で画面が固まっている時間 | 35,614 ms |
| Node で同じ関数（`reviewSnapshot`）に全イベントを渡す | 18,467 ms |
| 話者分離の途中経過を除いて渡す | 3,944 ms |

17MB の JSON の読み込みはほとんど時間を使っていなかった。時間の大半は、ログを頭から読み直して状態を戻す計算に入っていた。話者分離の記録を除くと速くなるが、それは記録が大きいからではなく、記録の件数が多いからだった。issue の題名と本文は、原因に合わせて「ログの復元が遅い」に書き直した。

プロファイルは最小化されたコードの名前（`wO`・`rk`・`ik`）で出る。今回のビルドは Foldkit の変換が関数の返り値をすべて `n(value, "../server/src/core/map.ts#children")` のように包んでいた。そのため、行と列の位置のコードを抜き出すと、元の関数名がそのまま読めた。

### 3. イベント 1 件ごとに全体を計算し直す処理は、関係の無いイベントが増えるだけで掛け算で遅くなる

ログから状態を戻す関数（`restoreState`）は、イベントをどの種類でも 1 件読むたびに、論点（会議の中で答えを出すべき問い）の状態を計算し直していた。1 回の計算では、全発言から表を作り直し、論点ごとにマップの全ノードをなめて子を探していた。時間はおおよそ「イベント数 × 論点数 × ノード数」に比例する。

この会議のログは 62,338 件で、そのうち約 5.4 万件が話者分離の途中経過の記録だった。話者を後から付け直した記録などで、どれもマップにも発言にも触れない。話者分離が入って、イベントは約 9 倍に増えていた。論点の計算は増えた記録とは無関係なのに、記録の件数の分だけ回っていた。

直し方は 2 つだった。論点の計算は、マップ・発言の数・時刻のどれかが前回から動いたときだけにする。1 回の計算では、親から子への索引を 1 度だけ作って引く。直す前と後で同じ結果になることは、話者分離の記録や論点の通知を挟んだログで固定するテストを先に足し、わざと壊した 2 通りの実装で落ちることで確かめた。

| 空いた状態、交互に計測 | 直す前（中央値） | 直した後（中央値） |
|---|---|---|
| Node の `reviewSnapshot`（5 回ずつ） | 24,508 ms | 976 ms |
| Chrome の LCP（3 回ずつ） | 52,588 ms | 1,328 ms |

10 回とも、復元の結果のハッシュは直す前と後で一致した。索引は「作り終えたマップは書き換えない」ことに頼っている。後からマップを書き換える処理を足すと、古い索引を引くことになる。

### 4. 受け入れ条件の時間は、空いたマシンで測った値で判定すると先に決める。混んだマシンの値は前後の差を言えても、目標を満たしたかは言えない

修正はワーカー（pstack の poteto-mode で動かした別の Claude Code）に任せた。最初の計測は、並行する別の作業の Swift のビルドとかち合った。直した後の Node の時間は 980〜3,122 ms と大きく揺れ、受け入れ条件の「1,000 ms 未満」は速い回だけが満たしていた。直す前の Chrome の LCP も、triage で測った 38.8 秒に対して 62 秒と出た。

利用者に聞き、空いているときの値を正とすることにした。ワーカーは空くのを待つ背景の処理を立てたが、待っている間にマシン全体のメモリが足りなくなり、Claude Code がその処理を止めた。このときの load は 76〜89（10 コア）だった。ワーカーは止まった理由を報告して、自分では立て直さなかった。ビルドが終わった後に、測る直前に load と重いプロセスを確かめ、数十秒おきに `uptime` を見るだけの待ち方で再開させた。各回の直前に Swift のビルドのプロセスが 0 で、1 分平均の load が 3〜5 であることを確かめてから測った値が、3. の表だ。

空いた状態でも、直した後は 900 ms 前後と 1,100〜1,200 ms の 2 つの山に分かれた。この機械は P コア 4・E コア 6 なので、E コアに載った回が遅い山だと見ている（推測）。

### 5. 二次的な要因は、主な原因を直してから測り直して決める。呼ぶ回数に比例する手間は、主な原因と一緒に消えることがある

triage のプロファイルでは、37 秒のうち約 6 秒が Foldkit の vite プラグインの変換が足した包み関数に使われていた。この変換は画面の部品を見分けるためのものだが、web がバンドルする `server/src/core` のコードにも掛かっていた。別の issue（#1779）に分け、#1778 を直した後に測ると決めた。

修正の後に同じログで見返しを作り直して測ると、包み関数の時間は約 26 ms で、表示まで（1.29〜1.34 秒）の 2% ほどだった。包み関数は返り値 1 つごとに一定の手間を足すだけなので、core の関数を呼ぶ回数が減ると一緒に減る。プラグインの設定で対象を絞る手間（Foldkit の開発時の機能を壊さないかの確認を含む）に見合わないので、`wontfix` で閉じた。見返しがまた重くなったら、まずプロファイルを取り、包み関数の割合が大きければ開き直す。

## clone 直後の初回の準備を `pnpm bootstrap` にまとめ、helper のビルドを 1 回に減らしたが、最初の計測ではビルドが基準より 90 秒長く、表は PR の本文に残らなかった話

live-mindmap は、音声認識と話者分離（相手側の声を話者ごとに分けること）を Swift の常駐プロセス「helper」に任せている。clone したばかりの Mac で README の手順をたどると、使い始めるまでに約 300 秒かかり、その 65% がビルドだった。仕様 [#1423](https://github.com/daiki-beppu/live-mindmap/issues/1423)（親 [#1431](https://github.com/daiki-beppu/live-mindmap/issues/1431)）では、ビルドを 140 秒以下、準備の計を 240 秒以下にすると決め、4 つの子に分けた。モデルの取得を release の実行ファイルで行う [#1432](https://github.com/daiki-beppu/live-mindmap/issues/1432)（[PR #1464](https://github.com/daiki-beppu/live-mindmap/pull/1464)）、入口の `pnpm bootstrap` を足す [#1433](https://github.com/daiki-beppu/live-mindmap/issues/1433)（[PR #1490](https://github.com/daiki-beppu/live-mindmap/pull/1490)）、モデルの保存先を環境変数で上書きできるようにする [#1434](https://github.com/daiki-beppu/live-mindmap/issues/1434)（[PR #1513](https://github.com/daiki-beppu/live-mindmap/pull/1513)）、計測スクリプトを置く [#1435](https://github.com/daiki-beppu/live-mindmap/issues/1435)（[PR #1519](https://github.com/daiki-beppu/live-mindmap/pull/1519)）だ。4 つとも takt（GitHub の issue をエージェントに実装させ、レビューまで回す仕組み）で実装した。

### 1. 初回の時間を縮めるには、まず同じものを違う構成で 2 回ビルドしていないかを見る

段ごとに測ると（[#1416](https://github.com/daiki-beppu/live-mindmap/issues/1416)、Apple M4・10 コア・16GB・Command Line Tools・Swift 6.4）、helper は初回の手順の中で 2 回ビルドされていた。話者分離のモデルを取るスクリプト（`fetch-speaker-models.sh`）の `swift run` が debug で 1 回（59.4 秒）、`pnpm dev` の `swift build -c release` が release で 1 回（113.7 秒）。会議で使うのは release だけなので、debug の 1 回は使わない構成のために待っている時間だった。時間の大半は helper の依存の FluidAudio（話者分離のライブラリ）のコンパイルで、構成が違えば作り直しになる。

`-Osize`・デバッグ情報を切る・依存の機能を絞る、といったコンパイラの設定の手も負荷の低い時間帯に測り直したが、揺れを超える差は出なかった。効いたのは、ビルドを 1 回減らすことだった。

直し方は、モデルの取得を `pnpm dev` が作った release の実行ファイルで直接動かすことにした。

```sh
HELPER="$HELPER_DIR/.build/release/live-mindmap-helper"
if [ ! -x "$HELPER" ]; then
  swift build -c release --package-path "$HELPER_DIR"
fi
"$HELPER" install-speaker-models
```

README の順序も、「`pnpm dev` を起動したまま、別のターミナルで」モデルを取る形に入れ替えた。

### 2. 無いときの代わりのビルドは、後で必ず走るビルドと引数を 1 文字もずらさない

古い順序で、`pnpm dev` より前にモデルを取る人もいる。そのときだけ release をビルドするが、引数は `pnpm dev` と同じにし、`--product` も付けない。#1416 で次の 2 つの SwiftPM の振る舞いが見えていたからだ。

- `--product` で 1 つの製品だけを作った後に、製品を指定せずに `swift build` すると作り直す。製品を絞って縮むのは約 3 秒（計測用の製品 1 つを外した分）だけで、作り直しの損のほうがずっと大きい
- `swift build` を 1 回増やすだけで、約半分の確率で release を作り直す。6 回中 4 回で中間生成物の名前が変わった（[#502](https://github.com/daiki-beppu/live-mindmap/issues/502)、原因は追えていない）

このため、初回の準備の中で `swift build` を呼ぶのは `pnpm dev` の 1 回だけにする、を設計の縛りにした。入口の `pnpm bootstrap` も、依存の解決（`swift package resolve`）までにとどめ、ビルドはしない。

### 3. 互いに依存しない段は並べて流し、1 つが落ちても残りを最後まで待つ。段の名前を行の頭に付ける

`pnpm bootstrap` は、パッケージの取得（`[install]`）、AEC3（WebRTC のエコー除去のライブラリ）のビルド（`[aec3]`）、Swift の依存の解決（`[resolve]`）を並べて流す。中身は依存を使わない bash で、`node_modules` の無い clone 直後でも動く。

```bash
run_stage() {
  local name="$1"; shift
  "$@" 2>&1 | while IFS= read -r line || [ -n "$line" ]; do
    printf '[%s] %s\n' "$name" "$line"
  done
}
run_stage install pnpm install & pids+=("$!")
run_stage aec3 bash helper/scripts/build-webrtc-apm.sh & pids+=("$!")
run_stage resolve swift package resolve --package-path helper & pids+=("$!")
for i in "${!pids[@]}"; do wait "${pids[$i]}" || failed+=("${names[$i]}"); done
```

1 つが落ちたときにほかを止めないのは、途中で止めると AEC3 のビルド（meson）の作業ディレクトリが中途半端に残るからだ。全部が終わってから、落ちた段の名前を並べて 0 以外で終える。

はまりどころが 1 つあった。pnpm 12 は script を流す前に依存がそろっているかを確かめる。`pnpm bootstrap` の中で install を並べて流すために、ワークスペースの設定に `verifyDepsBeforeRun: false` を足した。この設定はリポジトリのすべての script に効く。

### 4. 「並べて流れること」は時間ではなく、全段が揃うまで先へ進まない偽のコマンドで確かめる

並列のテストを「全体が直列の合計より短い」で書くと、遅い機械でだけ落ちる。#1433 のテストは、`pnpm`・`swift`・AEC3 のスクリプトを PATH の先頭の偽物に差し替えた。偽物は起動すると自分の印のファイルを書き、3 つの印が揃うまで先へ進まない。直列に流すと 1 段目が 8 秒の期限で落ちるので、並べて流したことが時間に頼らず分かる。

失敗の契約も同じ形で確かめた。落ちる役の段は 3 つが揃った直後に終わり、成功する段は、落ちた段のプロセスが実際に消えたのを `kill(pid, 0)` で確かめてから終わる。そのうえで、出力の最後の完了の行より後に、落ちた段の名前の行が出ることを見る。確かめているのは終了コードと出力だけで、スクリプトの書き方には触れていない。

### 5. 計測を利用者のキャッシュから切り離すには、環境変数で足りない道具を PATH の先頭の包みで包む

計測スクリプト `scripts/measure-bootstrap.sh` は、指定したコミットを一時ディレクトリへ clone し、README の手順どおりに流して段ごとの秒を出す。まっさらな状態を毎回作るため、利用者のキャッシュ（SwiftPM・pnpm の store・uv・依存の置き場・話者分離のモデル）に書かないことが条件だった。ここで 2 つの道具が環境変数では向け先を変えられなかった。

- pnpm 12 は `npm_config_store_dir` も `--cache-dir` も受け付けず、`--store-dir` の引数しか効かない
- helper のモデルの保存先は Foundation の Application Support で、`$HOME` を差し替えても動かない

前者は、`pnpm`・`swift`・`uvx`・`bash` の包みを一時ディレクトリの `bin` に置き、PATH の先頭に足して解決した。包みは `--store-dir` や `--cache-path` などの引数を足し、段の始めと終わりの時刻をファイルに書く。`pnpm bootstrap` の並列を崩さずに中の段ごとの秒が取れるのも、この包みのおかげだ。ただし pnpm は script の PATH の先頭に自分の bin を戻すので、script を流すシェル（`scriptShell`）の入口でも、包みを先頭に戻し直す必要があった。後者は helper の側に開発用の環境変数 `LIVE_MINDMAP_HELPER_SPEAKER_MODEL_DIR` を足し（#1434）、取得と会議中の読み込みが同じ解決の関数を通るようにした。

仕様は「bash のスクリプト」と書いていたが、できたものは bash の 1 行目から Node に渡す 300 行ほどのプログラムになった。プロセスのグループごとの後始末、計測中のサーバーが自分の子孫かの確認、中断のシグナルでも一時ディレクトリ（約 5GB）を消す処理が、bash では書き切れなかった。

### 6. 段ごとの計測を足し合わせた見込みは、まとめた形で 1 度測るまで当てにしない

仕様の見込みは、ビルド約 136 秒・準備の計約 205〜220 秒だった。#1416 の段ごとの値から debug の 59 秒を引き、残りを足したものだ。#1435 の実装の途中で、できたスクリプトで main と作業中の HEAD を続けて測った（2026-10-24）。clone した対象はどちらも同じコミットで、同じ入力の 2 回の観測になる。

| 段 | 基準（#1416、秒） | 1 回目（秒） | 2 回目（秒） |
|---|---:|---:|---:|
| AEC3 の compile | 22.7 | 63.1 | 58.7 |
| Swift の依存の解決 | 31.2 | 51.8 | 52.1 |
| helper の release ビルド | 113.7 | 166.1 | 164.1 |
| モデルの取得 | 45.0 | 39.2 | 31.0 |
| ビルドの計 | 136.4 | 229.2 | 222.8 |
| 初回の計 | 約 300 | 299.6 | 284.1 |

debug のビルドは消えたのに、準備の計はほとんど縮まず、ビルドは目標の 140 秒を 60% ほど超えた。AEC3 と helper のビルドがどちらも基準の 1.5〜2.8 倍になっている。計測を始める条件（空き 10GB 以上、1 分の load average 4 未満、ほかの `swift-build` 0 本）は満たしていたが、load average は 3.63 と 3.76 で、上限の手前だった。#1416 から OS・ツール・電源・負荷のどれが変わったのかは、まだ確かめていない。

この結果は、AGENTS.md に足した「目標を揺れ（±20%）より大きく超えたら、その PR で直すか issue を立てる」の最初の当てはまりになり、[#1518](https://github.com/daiki-beppu/live-mindmap/issues/1518) が立った。その triage では、手元では takt や他のセッションが並行していて、load average が 4.64 と開始の条件を満たせなかった。run の中で測ると run 自身の負荷が混ざる。そこで、この切り分けはエージェントに渡さず、並行する作業が空いたときに人が手元で流すことにした。

### 7. takt に測らせた表は、PR の本文ではなく issue に書かせる

4 つの子の受け入れ条件は、どれも「実装の報告に、流した結果と表を書く（PR の本文に写される）」だった。実際に PR の本文に報告が残ったのは #1513 だけで、#1464・#1490・#1519 は issue の写しと「Workflow `default` completed successfully.」の 1 行だった。takt は、1 回で通った run の実装の報告を PR の本文に写さない。6. の表が読めるのは、計測の値で立てた #1518 の本文に書かれていたからだ。#1513 の報告も、「上書き先への実取得・実モデル読込は未確認」と後に送っている。

計測の値のように、後で比べるために残したい数字は、takt の報告に頼らず、issue のコメントに書くことを完了条件にする。
