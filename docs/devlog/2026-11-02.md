## 話者分離を前日の会議の記録で確かめたら、見返しが開くまで 39 秒かかるのに気づき、「埋め込みが大きい」という見立ては外れて、原因はイベント 1 件ごとの再計算だった話

話者分離は、相手側の音声（`相手` のトラック）の中を声で区別し、「相手 A」「相手 B」のような匿名のラベルを発言に付ける機能だ。実装の最後に、人が実際の会議で確かめる項目が残っていた（[#1412](https://github.com/daiki-beppu/live-mindmap/issues/1412)、親 [#1018](https://github.com/daiki-beppu/live-mindmap/issues/1018)）。これを前日の会議の記録で済ませる途中で、見返し（会議の後にマップの組み上がりを時刻を動かして見直す、1 ファイルの HTML）がとても重いことに気づいた。原因を [#1778](https://github.com/daiki-beppu/live-mindmap/issues/1778) に起票して [PR #1835](https://github.com/daiki-beppu/live-mindmap/pull/1835) で直し、二次的な要因の [#1779](https://github.com/daiki-beppu/live-mindmap/issues/1779) は測り直して閉じた。

### 1. 「人が実際の会議で確かめる」項目は、新しく会議を開かなくても、手元の記録で済むことがある。数から出せるものは先に出し、人には「どのラベルが誰か」だけを聞く

#1412 の手順は「相手 2〜4 人の会議を 1 本取り込んで見る」だった。何をすればよいかを聞かれて手順を説明したところ、利用者から「昨日のデータとか使えるんじゃない？」と返ってきた。前日の会議（約 3 時間 20 分）は、録音とログ（`log.jsonl`、出来事を 1 行ずつ書いたもの）が残っていた。

確かめる 4 項目のうち、ログの数だけで出せるものと、人にしか分からないものがあった。

| 項目 | 数から出せること | 人に聞いたこと |
|---|---|---|
| 字幕の相手のラベルが合っているか | ラベルごとの発言数（B が 67%、ラベルなしが 28%） | A・B・C・D がそれぞれ誰か |
| 案の出した人・TODO の担当者 | 担当が付いた数（17 件中 13 件）、付き先の内訳 | 一覧を見て妥当か |
| 名前が合っているか | 付いた名前の種類（2 つ） | その人で合っているか |
| 字幕が遅れないか | 発言を書いた時刻から、音声上の終わりの位置を引いた差 | なし |

字幕の遅れは、専用の計測をしなくても、ログに記録された時刻と発言の終わりの位置（`remark.end`）の差で出せた。中央値 2.4 秒・90% で 5 秒前後で、1 時間ごとに分けても 3 時間を超えても増えていなかった。

人に聞く項目では、見返しの HTML が重すぎて開けない、と言われた。そこで、相手 D の 8 発言だけを ffmpeg で録音から切り出し、1 本の音声にして渡した。

```sh
ffmpeg -ss <start-0.5> -to <end+0.5> -i 相手.m4a -ac 1 -ar 24000 d1.wav   # 発言ごと
ffmpeg -f concat -safe 0 -i list.txt -c:a aac 相手D_8件.m4a               # 1 秒の無音を挟んでつなぐ
```

聞くと、D は途中で抜けた 4 人目の人で、発言が少ないのは実際どおりだった。4 項目とも合格で、#1412 は閉じた。なお、途中の報告で TODO の担当が付いた数を 15 件と言い、issue へのコメントを書く段で数え直して 13 件に直した。数を報告するときは、数えた表から写す。

### 2. 「HTML が重い」の見立ては、ファイルの大きさから立てると外れる。測ると、時間はデータの読み込みではなく計算に使われていた

見返しの HTML は、`map.html` が 18MB、音声つきの `map-audio.html` が 81MB あった。中身を数えると、`map.html` はほぼすべてがログを丸ごと埋め込んだ部分で、その半分以上（約 9.8MB）が話者分離の途中経過の記録だった。見返しの画面のコードは、この 3 種類の記録を読んでいない。そこで「要らない記録まで埋め込んで大きくなっている」として、#1778 を「HTML が重い」で起票した。

triage（起票された issue を評価して、次の状態を決めること）の段で、headless の Chrome でプロファイルを取った。

| 計測 | 結果 |
|---|---|
| `map.html` の表示まで（LCP） | 38,764 ms |
| そのうち 1 本の処理で画面が固まっている時間 | 35,614 ms |
| Node で同じ関数（`reviewSnapshot`）に全イベントを渡す | 18,467 ms |
| 話者分離の途中経過を除いて渡す | 3,944 ms |

17MB の JSON の読み込みはほとんど時間を使っていなかった。時間の大半は、ログを頭から読み直して状態を戻す計算に入っていた。話者分離の記録を除くと速くなるが、それは記録が大きいからではなく、記録の件数が多いからだった。issue の題名と本文は、原因に合わせて「ログの復元が遅い」に書き直した。

プロファイルは最小化されたコードの名前（`wO`・`rk`・`ik`）で出る。今回のビルドは Foldkit の変換が関数の返り値をすべて `n(value, "../server/src/core/map.ts#children")` のように包んでいた。そのため、行と列の位置のコードを抜き出すと、元の関数名がそのまま読めた。

### 3. イベント 1 件ごとに全体を計算し直す処理は、関係の無いイベントが増えるだけで掛け算で遅くなる

ログから状態を戻す関数（`restoreState`）は、イベントをどの種類でも 1 件読むたびに、論点（会議の中で答えを出すべき問い）の状態を計算し直していた。1 回の計算では、全発言から表を作り直し、論点ごとにマップの全ノードをなめて子を探していた。時間はおおよそ「イベント数 × 論点数 × ノード数」に比例する。

この会議のログは 62,338 件で、そのうち約 5.4 万件が話者分離の途中経過の記録だった。話者を後から付け直した記録などで、どれもマップにも発言にも触れない。話者分離が入って、イベントは約 9 倍に増えていた。論点の計算は増えた記録とは無関係なのに、記録の件数の分だけ回っていた。

直し方は 2 つだった。論点の計算は、マップ・発言の数・時刻のどれかが前回から動いたときだけにする。1 回の計算では、親から子への索引を 1 度だけ作って引く。直す前と後で同じ結果になることは、話者分離の記録や論点の通知を挟んだログで固定するテストを先に足し、わざと壊した 2 通りの実装で落ちることで確かめた。

| 空いた状態、交互に計測 | 直す前（中央値） | 直した後（中央値） |
|---|---|---|
| Node の `reviewSnapshot`（5 回ずつ） | 24,508 ms | 976 ms |
| Chrome の LCP（3 回ずつ） | 52,588 ms | 1,328 ms |

10 回とも、復元の結果のハッシュは直す前と後で一致した。索引は「作り終えたマップは書き換えない」ことに頼っている。後からマップを書き換える処理を足すと、古い索引を引くことになる。

### 4. 受け入れ条件の時間は、空いたマシンで測った値で判定すると先に決める。混んだマシンの値は前後の差を言えても、目標を満たしたかは言えない

修正はワーカー（pstack の poteto-mode で動かした別の Claude Code）に任せた。最初の計測は、並行する別の作業の Swift のビルドとかち合った。直した後の Node の時間は 980〜3,122 ms と大きく揺れ、受け入れ条件の「1,000 ms 未満」は速い回だけが満たしていた。直す前の Chrome の LCP も、triage で測った 38.8 秒に対して 62 秒と出た。

利用者に聞き、空いているときの値を正とすることにした。ワーカーは空くのを待つ背景の処理を立てたが、待っている間にマシン全体のメモリが足りなくなり、Claude Code がその処理を止めた。このときの load は 76〜89（10 コア）だった。ワーカーは止まった理由を報告して、自分では立て直さなかった。ビルドが終わった後に、測る直前に load と重いプロセスを確かめ、数十秒おきに `uptime` を見るだけの待ち方で再開させた。各回の直前に Swift のビルドのプロセスが 0 で、1 分平均の load が 3〜5 であることを確かめてから測った値が、3. の表だ。

空いた状態でも、直した後は 900 ms 前後と 1,100〜1,200 ms の 2 つの山に分かれた。この機械は P コア 4・E コア 6 なので、E コアに載った回が遅い山だと見ている（推測）。

### 5. 二次的な要因は、主な原因を直してから測り直して決める。呼ぶ回数に比例する手間は、主な原因と一緒に消えることがある

triage のプロファイルでは、37 秒のうち約 6 秒が Foldkit の vite プラグインの変換が足した包み関数に使われていた。この変換は画面の部品を見分けるためのものだが、web がバンドルする `server/src/core` のコードにも掛かっていた。別の issue（#1779）に分け、#1778 を直した後に測ると決めた。

修正の後に同じログで見返しを作り直して測ると、包み関数の時間は約 26 ms で、表示まで（1.29〜1.34 秒）の 2% ほどだった。包み関数は返り値 1 つごとに一定の手間を足すだけなので、core の関数を呼ぶ回数が減ると一緒に減る。プラグインの設定で対象を絞る手間（Foldkit の開発時の機能を壊さないかの確認を含む）に見合わないので、`wontfix` で閉じた。見返しがまた重くなったら、まずプロファイルを取り、包み関数の割合が大きければ開き直す。

## 聞かれる前に AI が答える「補足」を作ったら、形式仕様の検査と「何もしない応答」の扱いで守り方が決まり、初回の計測では引き金の狭さが見えた話

補足は、会議で出そうな質問（用語や略語の意味、決定の理由、議題の背景など）に、聞かれる前に AI が答えておくノードだ。添える先のノードの子としてマップに置き、出どころとして `会議の中`（発言から分かること）か `会議の外`（AI の一般知識）を持つ。仕様 [#1755](https://github.com/daiki-beppu/live-mindmap/issues/1755)（親 [#1769](https://github.com/daiki-beppu/live-mindmap/issues/1769)、判断は [ADR 0027](../adr/0027-supplement-is-a-node-kind-with-origin.md)）を 7 つの issue に分け、[#1770](https://github.com/daiki-beppu/live-mindmap/issues/1770)〜[#1775](https://github.com/daiki-beppu/live-mindmap/issues/1775) は takt（issue を計画・テスト・実装・レビューの段で順に流す自動実装の道具）が [PR #1777](https://github.com/daiki-beppu/live-mindmap/pull/1777)・[#1781](https://github.com/daiki-beppu/live-mindmap/pull/1781)・[#1782](https://github.com/daiki-beppu/live-mindmap/pull/1782)・[#1805](https://github.com/daiki-beppu/live-mindmap/pull/1805)・[#1818](https://github.com/daiki-beppu/live-mindmap/pull/1818)・[#1840](https://github.com/daiki-beppu/live-mindmap/pull/1840) で実装した。最後の [#1776](https://github.com/daiki-beppu/live-mindmap/issues/1776) は、評価用の正解データを足して初回の値を測る作業で、PR を作らずに閉じた。

出しすぎを防ぐ約束が仕様の中心にある。1 つのノードに補足は 1 つまで、同じ語の説明は 1 つの会議で 1 回だけにする。前の補足を画面に足してから 60 秒は次を足さず、補足だけで共有画面のマップを動かさない。補足は差分更新（発言が入るたびに AI がマップへの変更を返す呼び出し）とは別の呼び出しで作り、結果をログの 1 行として書いてから反映する。

### 1. 形式仕様の検査で破れた約束は、「プロンプトが守らなくても成り立つか」を基準に守り方を決める

仕様を issue に分ける前に、約束を Quint（状態の移り変わりを書いて、全部の道筋を検査できる仕様言語）で書いて検査した。初回は 2 つの不変条件が破れた。60 秒の間隔（`invAddGap`）と、同じ語は 1 回だけ（`invTermOnce`）だ。どちらも、補足の呼び出しが返るのを待つ間に次の呼び出しが走ると破れた。

60 秒は「呼び出した時刻」ではなく「`supplement` 行を畳んで画面に足した時刻」から測り、待っている補足が 2 件以上たまったら新しい 1 件だけを残す、と決め直した。

同じ語の約束には、守り方が 2 通りあった。

- 入力で守る: 呼び出しに渡す「説明済みの語」に、まだ画面に足していない補足の語も入れる
- 反映で守る: 行を畳むときに、すでに説明した語の追加を落とす

決め手は「プロンプトが守らなくても必ず 1 回になるか」だった。モデルが入力を無視すれば、入力だけでは破れる。そこで両方を採った。再検査では、この検査のモデルの上で、入力側の決まりが安全性に効かないことも分かった。反映側だけで約束は成り立ち、入力側は無駄な呼び出しを減らすだけだ。そこで、安全性は形式仕様の検査で、無駄を減らす決まりはセッションのテストで確かめる、と分けた。7 つの不変条件それぞれで、仕様を 1 か所だけ壊した版が検査に落ちることも確かめた。

### 2. 「新しい 1 件だけを残す」と書くなら、何もしない応答を数えるかまで決める

補足の呼び出しは、「足す・言い直す・消す」のどれか 1 つか、何もしない（`op: null`）を返す。takt の最初の実装は、何もしない応答でも、待っている補足を上書きしていた。60 秒の間隔待ちで保留していた補足が、後から来た「何もしない」に消される。仕様の「新しい 1 件だけを残す」を「新しい応答」と読むと、こうなる。

PR #1818 のレビューで見つかり、保留を置き換えるのは操作がある応答だけにした。

```ts
if (decoded.op !== null) yield* Ref.update(retained, (s) => ({ ...s, pending: result }));
```

テストは、仮想の時計（Effect の `TestClock`）を 59,999 ms 進めて、「何もしない応答の後も保留が残り、次の反映か停止のときに書かれる」ことを固定した。保留と上書きのある仕様では、受け入れ条件に「何もしない応答のとき」を 1 行書いておくと、この穴は計画の段で塞がる。

### 3. 計測の列の説明は、後から入った修正で嘘になる。費用は「記録された分」と書く

評価のコマンド（`cli eval`）に補足の列を足した PR #1805 は、補足のトークン数を「`supplement` 行の usage の合計。何もしない・失敗の呼び出しも含む」と説明した。その後にマージされた #1818 では、何もしない応答は保留にならず、行も書かれない。反映を断られた呼び出しと失敗した呼び出しも、行を残さない。2 つの PR はそれぞれレビューを通ったが、組み合わせると説明が事実と合わなくなった。

#1776 で実際に測って気づいた。ある回は補足 0 件で、トークンの列は欠測になった。別の回では「この語は説明済み」で反映を断った警告が 2 件出たが、その呼び出しの usage はログに無かった。計測の表は、欠測を `-` のまま残し、トークンの列は「記録された分で、全呼び出しの総費用ではない」と断った。

### 4. 計画の段の「情報不足」は、自動の積み直しでは直らない。完了条件を run の中で満たせるかを、積む前に確かめる

#1776 の takt は、計画の段で 3 回続けて止まった（ABORT）。issue の完了条件は「正解をサンプル側のリポジトリにコミットする」だった。ところがサンプルを置いたディレクトリは git のリポジトリではなく、takt の実行の決まりも `git commit` を禁じていた。計画のエージェントは毎回 `git rev-parse --show-toplevel` を流して `not a git repository` を確かめ、「必要な情報が足りない」と判定した。

takt には失敗したタスクを自動で積み直す設定がある（`auto_requeue_max_attempts: 2`）。2 回目と 3 回目は、前の run の 3〜5 秒後に始まった。前の計画を読み、同じ確認をし直し、それぞれ約 3 分で同じ結論に着いた。3 回の計画で、入力は合わせて約 200 万トークンだった。

| run | 所要 | 入力トークン | 判定 |
|---|---:|---:|---|
| 1 回目 | 約 3.6 分 | 777,650 | 情報不足で ABORT |
| 2 回目（自動の積み直し） | 約 3.5 分 | 639,152 | 同じ |
| 3 回目（自動の積み直し） | 約 2.8 分 | 589,596 | 同じ |
| 4 回目（本文を直して投入） | 約 91 分 | 1,573,690（計画の段） | 完了、差し戻し 0 回 |

直したのは issue の本文だった。「git のリポジトリではないので、ファイルに書くだけでよい。コミットは要らない」と書き、結果の置き場所を「issue のコメント」から「実装レポート（PR の本文に写る）」に変えた。正解の形の正本も、別の issue の決定ではなく、読み込むコードのファイル名で指した。直した後の 4 回目は、一度も差し戻されずに通った。

計画の段で「情報不足」と判定した ABORT は、もう一度流しても入力が同じなので結論も同じになる。積み直しは使用量の上限や一時的な失敗に効くもので、この種の止まり方は人に回すほうが安い。

なお、この作業はリポジトリの差分が 0 だったので、takt は PR を作らなかった。結果を issue にコメントで写し、手で閉じた。外のデータだけを変える issue は、どう閉じるかも本文に書いておく。

### 5. 評価の正解は、生成を見る前に台本から作る。少ない回数の結果は、分子と分母を合算して書く

正解は、合成会議（台本を音声合成で読ませた評価用の会議）2 本に 8 件ずつ、計 16 件足した。補足が出るべき場面の時刻の範囲とキーワードだ。生成された補足から正解を逆算すると、生成されなかった場面（取りこぼし）を数えられない。そこで、生成の前に台本と発言の時刻表から作り、16 件すべてで範囲の両端が発言の時刻と一致することを確かめた。

既存の正解ファイルに足すときは、読み込み関数を通さずに元の JSON の値で比べた。読み込み関数は知らないキーを捨てるので、読み込んで保存し直すと、決定の担当者や案の提案者の情報が消える。

生成と判定は Claude Sonnet 5.5 で、会議ごとに 2 回、等速で再生した。

| 会議 | 回 | 補足の数 | 再現率 | 遅れ p50 / p90 |
|---|---|---:|---|---|
| 略語の多い会議 | 1 | 5 | 2/8 | 33.3 / 40.6 秒 |
| 略語の多い会議 | 2 | 3 | 1/8 | 15.8 / 19.5 秒 |
| 進行役の会議 | 1 | 4 | 0/8 | 17.6 / 27.2 秒 |
| 進行役の会議 | 2 | 0 | 0/8 | - |

再現率は回ごとの割合を平均せず、件数を合算して 3/32（9.4%）とした。百分位どうしも平均しない。4 回は並行して流したので、遅れは単独で流したときの値ではないと断った。出た補足 12 件は、判定器（`supplementJudge`、補足ごとに「要る・要らない・誤り・根拠なし・出どころ違い」の 5 ラベルを付ける）にかけた。要る 9 件（75%）、誤り 1 件、根拠なし 2 件だった。

評価の CLI では 1 度つまずいた。`pnpm cli` は中で `cd server` するので、相対パスで渡したセッションのフォルダが見つからず、「セッションのマップがありません」で落ちた。絶対パスで渡し直して通った。

### 6. 再現率が低いときは、モデルより先に、何が呼び出しの引き金になるかを疑う

補足を作る呼び出しの引き金は、議題・論点・決定の追加と、案の却下だけだった。略語の多い会議では、正解の場面に合う要点（議題の中で共有された中身の記述）が 1 回目に 6 件、2 回目に 5 件あったが、補足は 1 つも付かなかった。要点は引き金に入っていないので、そこに出た略語は呼び出しに一度も渡されない。一方、正解の場面に合った議題には、2 回とも補足が付いた。

再現率 9.4% は「モデルが説明できない」ではなく、「説明を頼んでいない」が大半だと見ている。60 秒の間隔と 1 回に 0〜1 件の目安は、誤りと根拠なしが 25% あるので緩めずに保ち、引き金の見直しを先にする、と所見に書いた。

### 7. takt のレビューは、受け入れ条件の「前後の表」の抜けを止めない

差分更新のプロンプトに補足の約束を教えた PR #1782 は、受け入れ条件に「評価を前後に回して表を書く」があった。PR の本文は takt の完了の 1 行だけで、表も実行した検査の層も無いまま、レビューを通って自動でマージされた。takt のレビューはコードの差分を見るが、PR の本文が受け入れ条件の成果物を揃えているかは見ていない。プロンプトを変える PR は、マージを予約する前に、人が本文を受け入れ条件と突き合わせる。

もう 1 つ、受け入れ条件の画面写しが takt の最初の実装に無く、レビューの修正で足された PR が 2 本あった（#1777・#1781）。画面写しや表のような、コードの外の成果物ほど落ちやすい。

### その後

補足のコードは、最後の PR #1840 のマージ後に main で変わっていない。この記録をまとめる PR で、説明の食い違いを 2 つ直した。

- 評価の手順書（`server/bench/README.md`）のトークンの列の説明を、3. の「何もしない・失敗の呼び出しも含む」から「記録された行の合計で、何もしない応答・捨てた結果・失敗した呼び出しは含まない」に直した
- README の「前の反映から 60 秒空け」を、仕様どおり「前の補足を画面に足してから 60 秒空け」に直した

コードの側の食い違いが 1 つ残っている。用語集の補足は「案が `却下` になったら、補足も言い直すか消す」とする。一方、引き金の関数は、補足がすでに付いたノードは本文が変わったときしか呼ばない。補足の付いた案が、本文を変えずに却下になると、補足はそのまま残る。6. の引き金の見直しと合わせて直す。
