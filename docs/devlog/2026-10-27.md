## 録画を読む経路を 1 本にしたとき、「判定の済んだ時刻」がフレームの時刻ではなかった話

live-mindmap には、会議の後に録画のファイルからマップを組む「録画からのセッション」（`cli recorded`）がある。ファイルを読むのは helper（音声の文字起こしと共有画面の判定をする Swift のプロセス）で、結果を WebSocket で server に送る。音声のトラックは 2 つあり、`相手` は会議の相手の声が入る録音、`自分` は自分のマイクだ。録画からのセッションでは、`--self` を付けたときだけ `自分` のファイルも渡す。helper の中では、この有無で経路が 2 本に分かれていた。その 2 本を 1 本にした。決めたのは仕様 [#1612](https://github.com/daiki-beppu/live-mindmap/issues/1612)（親 [#1623](https://github.com/daiki-beppu/live-mindmap/issues/1623)）で、実装は 2 本のチケットに分けた。画面の判定器の作り方を名前で分ける [#1624](https://github.com/daiki-beppu/live-mindmap/issues/1624) と、入口を 1 つにする [#1625](https://github.com/daiki-beppu/live-mindmap/issues/1625) だ。どちらも takt（issue を計画・テスト・実装・レビューまで自動で回すワークフロー）で流した。#1624 は 44 分で 1 周で通り、#1625 はレビューの差し戻しと再計画を挟んで 1 時間 51 分かかった。

### 1. 出す順の決まりは、受け手が実際に頼っている一番弱い条件で書く。強い条件を契約だと思うと、経路が割れたまま残る

2 本の経路は、共有画面（会議で映っていた画面）と発言を出す順が違っていた。

- `相手` だけ: 映像を最後まで判定して共有画面をすべて送り、それから溜めておいた文字起こしの結果を送る
- `相手` と `自分`: 「時刻 t の共有画面は、終わりが t より後の途中結果・発言より先」になるように、映像の判定の進みに音声の読み手を合わせて交互に送る

1 本目の注には「サーバーは画面の変化を発言より先に受け取る前提」とあった。この注を契約と読むと、2 本目のほうが条件を破っているように見え、まとめられない。仕様を書く段で server の側（録画の待ち行列 `recordedFeed`）を読むと、server が頼っていたのは 2 本目の弱い条件だけだった。届いた画面を積んでおき、発言が来るたびに「時刻 < その発言の終わり」の画面を先に出す。全部の画面が先に来ることには頼っていない。

条件を弱いほうにそろえると、server を 1 行も変えずに経路を 1 本にできた。利用者から見える差も出た。`--self` なしで長い動画を渡すと、前は映像を最後まで判定し終えるまで、字幕にも発言にも 1 件も出なかった。今は判定の進みに合わせて画面と発言が交互に流れ、helper と server が溜めるものも「判定の済んだ時刻の少し先」までになる。

代わりに 1 つ受け入れたことがある。共有画面に映った語で発言の聞き違いを直す補正が、画面の直後の発言に間に合わないことがある。`--self` ありの経路とライブではもともとそうだったので、仕様はそちらにそろえ、読みを待つ仕組みは足さなかった。

### 2. 「判定の済んだ時刻」はフレームの時刻ではない。画面の始まりを過去にさかのぼって決める判定器では、まだ出していない画面の始まりの下限が進みになる

順を守る仕組みは単純に見えた。映像の読み手が「判定の済んだ時刻」を進め、音声の読み手はその時刻を越えて入力を渡さない。計画の段は、ここを 2 つの前提で組んでいた。

- 進みを動かすのは、画面のイベントを出したフレームだけ（2 本目の経路の元の作り）
- 判定器が画面の始まり（`start`）を決めるやり方は変えない

1 つ目は、1 回目のレビューで崩れた。backend の観点が REJECT を出した。画面が変わらない動画では進みが 0 のまま止まり、最初の発言が映像の終わりまで待たされる。直したかった「最初の発言が遅い」が、`相手` だけの経路でそのまま残っていた。

直し方には注意が付いた。単純に毎フレーム、そのフレームの時刻まで進めると順が壊れる。判定器は、変化を確かめてから送る。送る画面の `start` は、変わったマスがそれぞれ変わり始めた時刻の中央値になるので、送ると決めたフレームの時刻より前になりうる。進みをフレームの時刻まで動かした後に過去の `start` の画面が出ると、その間に終わった発言のほうが先に届いてしまう。

1 回目の直しは、送った画面とまだ違うマスのうち一番古い変わり始めの時刻を、進みの上限にした。黒い固定画面と全面が変わる画面では通った。ところが別の観点が、反例を出した。0.25 秒に 40 マスだけ変わってその後固定すると、変化が送る閾値に届かないまま、進みは 0.25 秒で止まる。この差分を無視して進みを 2 秒まで進めると、3 秒で変わったマスが 47 に増えたとき、`start` が 0.25 の画面が作られて順が壊れる。2 つ目の前提を守る限り、早く出すことと順を守ることは両立しなかった。直しの担当は「完了」の報告を取り消し、本番のコードに手を入れないまま計画へ差し戻した。

再計画で 2 つ目の前提を外した。判定器が、録画のときだけ「ここまでなら音声を進めてよい」時刻（`fileProgress`）を持つ。そして、一度その時刻まで進めたら、後から作る画面の `start` もその時刻を下限にする。進みを先に約束し、画面の側をその約束に合わせる。ライブの判定器ではこの値を持たないので、ライブの振る舞いは変わらない。

仕様には Quint の形式仕様があり、「時刻 t の画面は、終わりが t より後の発言より先」も性質として検証していた。それでもこの穴は捕まえられなかった。モデルでは、映像を 1 フレーム進めるたびに、そのフレームの時刻を `start` とした画面を出していた。`start` が判定の時刻より前になる、という判定器の性質を抽象化で落としていた。順の性質を形式で確かめるときは、時刻を誰が決めるのかをモデルに残す。

### 3. 「早く出る」を約束する作り替えは、門を全部開けてから見るテストでは確かめられない

仕様が指定した順のテスト（`screenPrecedesLaterRemarksWhenVideoIsDelayed`）は、読み手 1 つと 2 つの両方で回すように引数を足した。けれども実装の後、testing の観点がこう指摘した。このテストは映像の門（読み進めてよいかを server が決める栓）を最後に全部開けてから届いた順を見る。だから、映像が終わるまで発言を溜める古い作りでも通る。

足したのは、映像を途中で止めたまま、発言が届くことを見るテストだ（`remarksArriveBeforeVideoFinishes`）。ここでもつまずいた。映像を 2 秒で止めても、音声は塊で渡るので、そこまでに渡った音声の終わりは 1.536 秒だった。発言が 1.6 秒で終わる台本では発言が出ず、時間切れになった。終わりを 1.2 秒に下げて通した。

順のテストは「遅く出しても順は守れる」ので、早さの契約を確かめない。早さを約束したら、「全部終わる前に届く」ことを、止めた状態で見る。

### 4. 画面の変化を試す動画は、ProRes 4444 で作る。H.264 では圧縮の揺れが「動き」に見える

2 回目の直しで、小さな変化の場面を作る IT が通らなかった。fixture の動画は H.264 で書き出していた。圧縮で輝度がフレームごとに揺れ、判定器はそのマスを「動いている場所」とみなして比較から外し続けた。狙った小さな変化が判定に入らなかった。fixture を ProRes 4444 に変えると、揺れが消えて通った。

判定器はスクロール・動画の再生・顔の小窓のような動く場所を比べる対象から外す。そのため、人が見て止まっている画面でも、圧縮のノイズが「動き」として判定を変える。試す動画は、まず劣化の無い形式で作る。

### 5. 今は空の保留を流す約束は、入口の IT では落とせない。作り方の名前と単体テストで守り、動かしていないことを書いて持ち越す

#1624 では、録画の映像を読み終えたときに、判定器の保留（タブの判定のために溜めた画面）を確定して流すようにした。ライブの経路は閉じるときに必ずそうしていて、録画の経路だけが呼んでいなかった。ただし、録画ではタブの判定をしないので、保留はいつも空だ。入口から何を入れても、この約束が破れたテストは落ちない。

仕様は、入口の IT を足さないと決めていた。代わりに、意図を名前に出した。前は `ScreenChangeDetector(bundleID: "")` の空文字で、「空文字がブラウザの bundle id の一覧に無い」ことを使ってタブの判定を止めていた。これを `ScreenChangeDetector.withoutTabDetection()` にし、中では bundle id を持たない（`nil`）。単体テストは、ブラウザ風のタイトルが来ても保留せずに送ることを確かめる。そのテストの red は、作り方が無いことによるコンパイルエラーだけだった。

5 つの観点のレビューは全員 APPROVE で、うち 4 つが同じ懸念を「指摘にしなかった懸念」に書いた。空でない保留を流す道を、実際に動かして確かめていないことだ。裁定は「今の入力では保留を作れず、仕様も入口の IT を禁じているので、直しの根拠にしない」として持ち越した。落とせない約束を無理にテストで覆うより、守っていない状態を名前と注で読めなくすることと、動かしていないことを報告に残すことを選んだ。

## 開始前の確かめを入口の表 1 つにまとめたら、PR の本文の 1 行で takt が 4 回止まった話

live-mindmap には、セッションや再生を始める入口がいくつかある。会議を始める `start`、止めた会議を再開する `resume`、録画のファイルから組む `recorded`、文字起こしやログを流し直す `cli play`、ログを別のモデルで流し直して評価する `cli eval --model` だ。どの入口も、始める前に要るものがそろっているかを見る。これを「開始前の確かめ」と呼んでいる。見る相手は、音声認識をする Swift の常駐プロセス（helper）、日本語の音声認識モデル（speech-ja）、差分更新に使う Claude の SDK（claude）、マップの画像を書き出す Chromium、マイクと画面収録の許可だ。この確かめを 1 つの module にまとめた。決めたのは仕様 [#1611](https://github.com/daiki-beppu/live-mindmap/issues/1611)（親 [#1622](https://github.com/daiki-beppu/live-mindmap/issues/1622)）で、実装は 4 本のチケットに分けた。helper の確かめの口を 1 つにする [#1626](https://github.com/daiki-beppu/live-mindmap/issues/1626)、module を作って server の入口を載せ替える [#1627](https://github.com/daiki-beppu/live-mindmap/issues/1627)、CLI の再生と評価を載せる [#1628](https://github.com/daiki-beppu/live-mindmap/issues/1628)、録画を始めずに確かめる口を足す [#1629](https://github.com/daiki-beppu/live-mindmap/issues/1629) だ。足りないものを入れるのは利用者で、確かめは確かめるだけ、という決まりは [ADR 0017](../adr/0017-heavy-deps-in-managed-dir-cli-stops-at-check.md) のまま変えていない。4 本とも takt（issue を計画・テスト・実装・レビューまで自動で回すワークフロー）で流した。

### 1. 手順を入口ごとに並べさせると、1 段抜けた入口ができる。入口の行を決める鍵だけを受け取り、要らない鍵は型で渡せなくする

前は、どの入口も同じ手順を自分で並べていた。共有画面を取るかどうかで helper の確かめ方を選ぶ。確かめる。差分更新のモデルの計画から updater（差分更新を呼ぶ部品）を準備する。準備の失敗を「要るものが無い」という開始の拒否に読み替える。判定のモデルの鍵が無いときの知らせを警告に足す。この 5 段を 5 か所以上で書いていた。

1 段抜けた入口が実際にあった（[#1524](https://github.com/daiki-beppu/live-mindmap/issues/1524)）。`cli eval --model` は確かめを通らずに差分更新を始めていた。Chromium が無く claude はある環境で、`cli play` は始める前に Chromium の警告を出す。`cli eval --model` は何も言わずに評価を最後まで回し、最後の map.png の書き出しで初めて失敗した。

仕様は、入口ごとに「要る」「あれば足りる（警告して始める）」「確かめない」を 1 枚の表にした。たとえば `cli play` は claude（経路が claude のとき）だけが要り、Chromium はあれば足りる。helper・speech-ja・マイク・画面収録は確かめない。`cli eval --model` は `cli play` の行をそのまま使う。module が受け取るのは、表の行を決める 4 つの鍵だけだ。入口、差分更新の経路、共有画面の有無、マップを作らないか（`noMap`）。

鍵の組み合わせは型で縛った。共有画面の有無は `start` と `resume` だけが持ち、`noMap` は `recorded` だけが持つ。updater を準備しない行（`resume` と、`recorded` の `noMap`）の準備の口は、戻り値に `updaterLayer` を持たない。単体テストには、`recorded` に `screen` を渡す呼び出しなどを 5 つ並べ、どれも型検査で落ちることを `@ts-expect-error` で固定した。

Effect の要求する環境（`R`）でも縛った。`play` の行で呼ぶときの型は `Helpers` を要求しない。だから helper の layer を持たない CLI のプロセスからも、そのまま呼べる。「`play` は helper を呼ばない」という表の 1 マスが、呼び出しの型にそのまま出ている。

### 2. 「確かめない」は、その資源を壊した状態を入れても何も出てこないことで確かめる。何回呼んだかは数えない

前のテストは、偽の helper を 2 束用意していた。そろった状態を返す束と、呼ばれたら落ちる束（`forbiddenHelperChecks`）だ。後者は「この入口では helper を呼ばない」を、呼び出しの有無で確かめていた。

これを、状態を受け取る 1 つの fixture にした。「helper が失敗する」か「マイク・画面収録・speech-ja がどうなっているか」を渡すと、`check({ screen })` が `screen` に応じた形を返す。「確かめない」は、その資源が無い・壊れている状態を入れても、項目にも警告にも出ず、始められることで確かめる。`play` は helper が失敗しても通る。共有画面を取らない `start` は、画面収録の許可が無くても画面収録の項目を出さない。経路が claude 以外なら、claude が無くても警告しない。

呼んだ回数で確かめると、実装が「念のため呼んで結果を捨てる」形に変わっただけで落ちる。利用者に見えるのは出てくるものだけなので、テストもそこを見る。

同じ考えで、報告の口（始めずに `ready` と項目を返す）と準備の口（始める）が食い違わないことも、出てくるもので確かめた。speech-ja の 5 つの状態ごとに、報告の `ready` と準備が成功するかどうかが一致することを見ている。web の画面は報告の口を使い、開始は準備の口を使う。2 つの答えがずれると、「確かめでは大丈夫と言われたのに始まらない」が起きる。

### 3. 準備の口は、層を組むときにサービスを捕まえ、呼ぶときに Scope を受け取る。updater の寿命はセッションのもの

updater の準備（`prepareUpdater`）には、HTTP のクライアントやファイルシステムなどのサービスが要る。前は、セッションの書き出し先を作る部品（`SessionSinks`）がこれを抱えていた。仕様はそれを確かめの module の layer に移した。サービスは layer を組むときに捕まえておき、準備を呼ぶときに、呼び手の Scope を足して渡す。

Scope まで layer を組むときに捕まえると、updater は server が生きている間ずっと開いたままになる。テストでは、準備で開いた資源を数えた。layer を組んだだけでは 0 回開く。呼び手の Scope の中で 1 回開き、その Scope を抜けると 1 回閉じる。2 回目も同じになる。

この移し替えは、server の層の組み立てを作る全部のテストに響いた。#1627 は 42 ファイル・+676/−493 になった。その多くは IT の fixture で、層の組に `startupChecks` の欄を 1 つ足しただけの変更だ。

### 4. 古い関数を消すと、知らなかった呼び手が出てくる。関数を再公開して逃がさず、同じ口に載せる

#1628 は、旧来の確かめの関数（`requireStartupDeps` と、準備の失敗を読み替える `startupPreparationFailure`）を消すことも完了条件にしていた。ファイルを消すと、評価用の bench（`server/bench/sttReplay.ts`）が読み込みの段で落ちた。bench も読み替えの関数を直接使っていた。チケットの本文には出てこない呼び手だった。

1 回目の run は、bench の import 先を、関数の残っている内側のファイル（`startupItems.ts`）に向け替えて通した。2 回目の run の計画は、これを採らなかった。module の中の関数を bench のために外へ出すと、「確かめの関数を module の外に出さない」という仕様の線が崩れるからだ。bench も、`cli play` と同じく準備の口を `play` の行で呼ぶ形にした。

ここで想定外が 1 つあった。CLI と同じ汎用の準備（`planLayer`）を渡すと、型検査が、bench に Apple Intelligence と HTTP の依存が増えたことを検出した。`planLayer` はどの経路にも対応するので、すべての経路の依存を要求する。bench は claude しか使わない。そこで、claude の updater を先に組み、その結果を返すだけの準備を渡した。

fixture の直し方でも 2 回の run の差が出た。1 回目は、評価用の偽の依存の fixture の引数をオブジェクトに変え、10 ファイルに手が入った。2 回目は、Chromium の状態を第 2 引数に足して既定値を `"ready"` にするだけにした。既存の呼び出しは触らずに済み、8 ファイル・+57/−63 で収まった。

### 5. run の中から確かめられないこと（PR の本文の 1 行）を完了条件に入れると、レビューが全員 APPROVE でも止まる

#1524 は単独では流さず、#1628 の PR で `Closes #1524` を書いて閉じることにした。GitHub は PR の本文に `Closes #N` があれば、マージのときにその issue を閉じる。#1628 の完了条件には、最初「PR の本文に `Closes #1524` を書く」と入れていた。

けれども、takt が PR を作るのは実装の run が終わった後だ。1 回目の run は 36 分で、計画・テスト・実装・5 観点のレビューまで進んだ。レビューは全員 APPROVE で、裁定も「直すものなし」だった。それでも最終の関門が BLOCKED を出した。理由は「PR の本文の `Closes #1524` を確かめられない」。続く再計画は、「同じ実装・同じ証跡で、外を待つだけ」と判断して ABORT した。自動の再投入が 2 回続き、どちらも再計画から始まって約 2.5 分で同じ理由で ABORT した。合わせて約 42 分、ABORT が 3 回だった。

チケットの本文を「実装の報告に `Closes #1524` を載せる（PR の本文に写る）。確かめるのは実装の報告まででよい」に書き換えると、2 回目の run は 30 分で、一度も戻らずに通った。

ところが、括弧の中の「PR の本文に写る」が外れていた。PR を作った後のレビューの run が、「PR の本文の実行報告は定型の完了文と `Closes #1628` だけ」として、もう一度止まった（4 回目）。takt は、1 回で通った run の実装の報告を PR の本文に写さない。修正のセッションが PR の本文を手で直し、`Closes #1524` と検査の層の表を足した。コードは 1 行も変えていない。レビューのやり直しで通り、#1628 と #1524 は一緒に閉じた。

この「写らない」は、すでにこのリポジトリの知識文書に書いてあった（[takt の run](../knowledge/takt-runs.md)）。それでも、チケットを起こす段も、#1524 を #1628 で閉じると決めた triage のコメントも、「写る」と書いた。知っていることが文書にあっても、別の段がそれを前提に書くとは限らない。

完了条件に入れてよいのは、run が自分で満たして確かめられるもの（テストや検査の終了コード、grep で残りが無いこと）だけだ。PR の本文、ほかの issue を閉じること、実モデルでの評価は、PR を作る側か人の手順に書く。

## 共有画面の持ち越しを 1 つのキューにしたら、ログの行とキューの操作の順がずれる隙間が形式検証で見つかった話

live-mindmap の差分更新（新しい発言を AI に渡し、マップへの操作を返してもらう 1 回の呼び出し）には、共有画面（会議で相手が映している画面）の画像を添える。どの画像をどの回に添えるかには規則がいくつもある。発言の締め切りまでの画面を時刻順に選ぶ。前に添えた画像から 10 秒未満の画像は添えず、最新の 1 枚を次の回に持ち越す。1 回に添えるのは新しい 3 件まで。ただし一時停止（モデルの利用上限で差分更新が待っている状態）から戻った最初の回は、停止中にたまった画面を上限なしで全部添える（追いつき）。この規則が、会議中のライブの Session と、ログ（`log.jsonl`）を読み直してセッションを組み直す復元（`restoreState`）に、別々に書かれていた。突き合わせると違いが 8 つあり、そのうち 4 つは偶然の食い違いだった。これを pure で同期の 1 つの module「共有画面のキュー」（`ScreenQueue`）に集めた。決めたのは仕様 [#1638](https://github.com/daiki-beppu/live-mindmap/issues/1638)（親 [#1651](https://github.com/daiki-beppu/live-mindmap/issues/1651)）で、実装は 3 本に分けた。キューを作って復元を載せ替える [#1652](https://github.com/daiki-beppu/live-mindmap/issues/1652)、ライブを載せ替える [#1653](https://github.com/daiki-beppu/live-mindmap/issues/1653)、画面の受け取りと呼び出しの結末を直列化する [#1654](https://github.com/daiki-beppu/live-mindmap/issues/1654) だ。前の日に、差分更新の結果をマップに当てる処理を 1 つの純粋な関数にした（[ADR 0024](../adr/0024-reflect-diff-row-in-one-pure-fold.md)、[その開発ログ](./2026-10-26.md#reflect-fold)）。今回はその隣にある共有画面を同じ形にした。3 本とも takt（issue を計画・テスト・実装・レビューまで自動で回すワークフロー）で流し、実装の run はどれも差し戻し 0 回で、49 分・48 分・31.5 分だった。

### 1. 「選ぶ」を状態を変えない操作にし、消費は書いたログの行を入力に 1 回だけ行う。そうすると巻き戻しの手順がそもそも要らなくなる

前のライブは、呼び出しの最初に添える画面を選び、その場でキューから外していた。呼び出しが一時停止で終わると、外した画面を戻す。戻すために、選ぶ前の数（`before`）と残した数（`keptUnsent`）を覚えておき、呼び出し中に届いた画面を失わないように巻き戻していた。復元の側は、ログの `diff` の行（1 回の差分更新の入力と結果）を読んで同じことを別の手順で再現していた。

キューの操作は 5 つにした。受け取る・選ぶ・消費する・一時停止の印を付ける・画像を添えないにする。「確定する」と「巻き戻す」は持たない。

- **選ぶ**は締め切りを受け取り、この回に添える画面と、ここまでに受けた画面の数（`screenCount`）を返す。キューは変えない
- **消費する**は、書いた `diff` の行そのものを入力にする。受けた順の番号（`seq`）が `screenCount` より小さく、締め切りまでの画面だけを外す。持ち越しの画像は残す

選んでも状態が変わらないので、一時停止で終わった回に戻すものが無い。差分更新が止まった回は `diff` の行を書かないので、消費もしない。ライブは書いた行で消費し、復元は読んだ行で消費する。同じ行を同じ関数に入れるので、「ライブ = 復元」は照合のテストではなく作りで成り立つ。

偶然の食い違いの 1 つは、これで消えた。一時停止で終わるログを復元すると、追いつきの印が戻らなかった。その結果、復元した続きの最初の回が 3 件に切られていた。#1652 は実装の前に、これを落ちるテストとして再現した。停止中に 5 件たまったログを復元すると、続きの最初の回に 3 件しか添えない。画像を添えない設定の会議を復元すると、復元の後に受けた画像を添える（復元が常に `images: true` で開いていた）。実装の後、どちらも通った。

`seq` で区切る理由もある。呼び出しの間にも画面は届く。結末で「締め切りまでの画面を外す」とだけ書くと、呼び出し中に届いた古い時刻の画面まで、添えていないのに外してしまう。#1653 のテストは、これを見分けられる条件を選んだ。最初の回の締め切りを 30 にし、呼び出し中に時刻 10・20 の画像と 21 の「なし」（共有の終了）を届ける。次の回の入力が `[10, 20, 21]` になることを見る。

復元のテストは 42 件から 37 件に減った。持ち越しや 10 秒の起点が元と一致するかを見る 4 件と、一時停止で選んだ画面が戻るかを見る 2 件を消した。前者の規則はキューの単体テスト（23 件、Session も偽の更新器も通さない）が期待値で確かめる。後者は、戻す操作そのものが無くなった。

### 2. 「ログに書く → 状態を変える」と「状態を変える → ログに書く」が並ぶ場所は、順をそろえるだけでは足りない。両側を同じ区間に入れる

前の `pushScreen`（helper から共有画面の変化を受ける口）は、受けた数を増やしてから `screen` の行を書いていた。その間に呼び出しが数を読んで、`screen` の行より先に `diff` の行を書くと、`screenCount` がその行より前の `screen` の行の数を超える。そのログは復元で `InvalidLogEvent` になる。偶然の食い違いの 3 つ目だ。

仕様の最初の案は、順を入れ替えるだけだった。`screen` の行を書いてから受け取る。仕様の要件を Quint / Alloy で書いて検証器にかける段（formal-spec）が、この案を通さなかった。TLC（TLA+ のモデル検査器）は、「復元したキュー = ライブのキュー」が破れる 6 手の反例を出した。

1. `pushScreen` が `screen` の行を書く（受け取りはまだ）
2. 差分更新の呼び出しが始まる
3. 一時停止で終わり、`diff-update-paused` の行を書く。ライブのキューは空なので、追いつきの印は付かない
4. 再試行の呼び出しが始まる
5. `diff` の行を書いて終わる。状態は「動いている」に戻る
6. ここで `pushScreen` が画面を受け取る。動いている状態で受けるので、印は付かない

復元はログを `screen` → `diff-update-paused` → `diff` の順に読む。画面を受けてから一時停止の印を付けるので、印がその画面に付く。続く `diff` は `screenCount` が 0 なので消費しない。復元の側にだけ追いつきの印が残る。

直したモデルでは、2 つの区間を同じ排他に入れた。1 つは `pushScreen` の「行を書く → 受け取る」。もう 1 つは、呼び出しの結末の「消費する → `diff` の行」と「印を付ける → `diff-update-paused` の行」だ。TLC は 591,236 状態をすべて通した。そのうえで、どちらか片方だけを囲んでも反例が残ることを示した。

#1654 の計画は 4 案を比べた。

| 案 | 判断 |
|---|---|
| 順を入れ替えるだけ | 上の反例が残る |
| ログの書き込みだけをロックする | キューの更新を守れない |
| 呼び出し全体を囲む | AI の応答を待つ間、画面を受け取れなくなる |
| Session ごとに `Semaphore.make(1)` を 1 つ作り、両側の区間を同じ permit で囲む | 採用 |

採った形には、このリポジトリに前例があった。ログの書き込みの直列化（`sessionFiles.ts`）だ。選ぶこと・画像の読み戻し・応答の待ちは区間の外に置いた。選ぶ操作は状態を変えないので、囲む必要が無い。

結末は 3 種類ある。成功、エラーで終わった回、一時停止だ。仕様は「消費する → `diff` の行」としか書いていなかった。#1654 の計画は、エラーで終わった回も消費して `diff` の行を書くことから、これも区間に入れる要件を導いた。成功の回だけを囲んでも、約束は成り立たない。

### 3. 排他と、中断されないことは別の性質。行を書いた後・状態に反映する前の中断で、ログとライブがずれる

#1654 は、仕様に無いものを 1 つ足した。画面側の区間を `Effect.uninterruptible` で包むことだ。計画の段で「排他と中断不可を区別する」と書き、実装でそうした。排他だけでは、`screen` の行を書いた直後に Fiber が中断されると、その画面は「ログにはあるが、ライブのキューには無い」状態になる。次に復元すると、ライブには無かった画面が添えられる。形式検証のモデルは中断を扱わないので、反例には出てこない。実装の段で、中断のテストを 1 件足した。

モデルが守るのは、モデルに書いた遷移の間だけだ。中断・defect・プロセスの終了は、モデルの外から来る。排他の区間を作るときは、その区間の途中で止まったら何が残るかも別に問う。

### 4. 上限の内側の入力では、印の違いが結果に表れない。反例を写しただけのテストは、実装の前から緑だった

#1654 のテストは、偽のログの書き込みを `Deferred` で止め、更新器の応答も止めて、上の割り込みを作る。比べるのは、ライブの続きが添える画面と、`restoreSession` で組み直した続きが添える画面だ。時刻・ファイル名・画像のバイト列を見る。Semaphore があるかどうかは見ていない。

画面は 4 枚使った。追いつきの印の有無で変わるのは「3 件上限を外すかどうか」だけだ。3 枚以下なら、印があってもなくても同じ画面が添えられる。

テストを書く段で足した 6 件のうち 5 件は、狙いどおり実装の前に落ちた（中断のテストは実装の段で足し、全部で 7 件になった）。

- `screen` の行より先に `screenCount: 1` の `diff` の行が書かれる（2 件）
- 再試行の後、ライブは 3 枚、復元は 4 枚を添える（2 件）
- 停止の行と画面の行の順が逆になる（1 件）

ところが、formal-spec の反例の筋書きをそのまま写した 1 件は、実装の前から緑だった。この反例が狙うのは、順を入れ替えただけの誤った実装だ。実装の前のコードは、順を入れ替えていない。だから、実装の前に緑だったことは、このテストが効かない証拠にはならない。かといって、効いている証拠も無い。確かめるには、順だけを入れ替えた実装（mutation）に対して落ちるかを見る必要がある。この run はそれをしていない。

### 5. 積み重ねた仕様の「消すファイル」「移す件数」は、前のチケットのマージで古くなる。件数ではなく規則ごとに今の配置と照合する

仕様は、テストの行き先を件数で書いていた。`sessionScreen.test.ts` の 44 件のうち、14 件をキューへ移して 30 件を残す、といった具合だ。#1652 がキューと復元を先に入れたので、#1653 の計画の時点で `screenSelection.ts`（旧来の選び方の関数）はもう無く、テストも 36 件になっていた。#1653 の計画は件数を当てはめず、規則ごとに「キューのテストにあるか」を照合して 6 件を消した。結果は 30 件で、仕様の数と一致した。

#1652 と #1653 の間には、選び方の規則が 2 か所にある時間があった。仕様はキューの内側の関数を外に出さないと決めていた。そのため #1652 は、ライブの旧来の選び方を `session.ts` の中に非公開で写した。この写しは、リポジトリの重複検査（fallow）に 1 件の重複として見つかった。#1652 は抑制を使わず、キューの側の書き方を `filter` に変えて検査を通した。書き方の重複は消えたが、規則の重複は残った。重複検査が見るのは形だけだ。規則の重複は、次のチケットで消すことがチケットに書いてあったから追えた。#1653 で写しは消えている。

### 6. 対象のファイルだけでテストを回すと、id の形のような横断的な前提を見落とす

#1653 は、更新器へ渡す画像の id を、helper の id からファイル名（`0005.0.jpg` など）に変えた。今の復元と同じ形にそろえるためだ。テストを書く段で、対象の 5 ファイルの 124 件はすべて通った。ところが、リポジトリのルートで `pnpm test` を回すと、仕様が触れていない `remarkFlow.test.ts` の 2 件が落ちた。「画像の id は連続し、画像なしの変化は番号を消費しない」を見るテストで、helper の id の形を前提にしていた。

直し方は 2 つあった。期待値をファイル名の id に書き換える案と、feed を通って画像のバイト列が届くことを見る案だ。後者を採った。ファイル名の id は、Session のテストがすでに確かめている。このテストが守りたかったのは「画像が届くこと」で、id の形ではない。

### 7. 実装の run の証跡は、PR のレビューの worktree から見えない。結果を PR の本文に書かないと、全部やり直しになる

#1654 の実装の run は、レビュアー 5 人が全員 APPROVE だった。PR を作った後、takt の PR レビューの run が別の worktree で走った。コードのレビューは APPROVE だったが、裁定は 2 件の指摘を採った。どちらも中程度だ。

- TLC の結果が PR に書かれていない
- 必須の検査の層と結果が PR に書かれていない

PR の本文の実行報告は「Workflow `default` completed successfully.」の 1 行だけだった。実装の run が残した検査のログ（`.takt/issue-1654-*.log`）は、レビューの worktree からは見えない。fix の段は、TLC と全部の検査を回し直した。PR レビューの run は 16 イテレーション・42 分で、その大半がこのやり直しだった。

同じ日の[前のエントリ](#startup-checks-module)の 5 節と同じ根を持つ。takt は、1 回で通った run の実装の報告を PR の本文に写さない。チケットの完了条件にあった「実装の報告に、実行した層と結果を書く」は、run の中では満たされていた。それでも、PR の本文の読み手には届かなかった。

ついでに、TLA+ のモデル（`server/formal/DiffUpdateScheduler.tla`）の注釈も直した。遷移ごとに `session.ts` の行番号を書いた注釈が、前に合わせた #1501 の後の変更で 80 行前後ずれていた。`startDiffIfReady` は `:393–409` ではなく `:312–328` だった。このモデルは差分更新の呼び出しの段取りだけを持ち、共有画面もログも復元も含まない。だから #1653・#1654 で TLC（11 検査がすべて通った）が示したのは、段取りを変えていないことだけだ。順の約束の証拠は、Session のテストだけにある。

## helper・server・web の受け渡しの形のずれを、見本と型で CI に捕まえさせた話

live-mindmap は 3 つのプロセスでできている。helper（音声の文字起こしと共有画面の判定をする Swift のプロセス）は、結果を 1 行 1 件の JSON（helper のイベント）にして server（Node.js）へ送る。server はブラウザの画面（web）へ、WebSocket の `/ws` で frame（画面の更新 1 件の JSON）を送る。この 2 つの継ぎ目では、両側がそれぞれ自分の思う形だけをテストしていた。形がずれても CI は通り、会議の最中に字幕や共有画面の更新が理由を残さず消える。仕様 [#1609](https://github.com/daiki-beppu/live-mindmap/issues/1609)（親 [#1616](https://github.com/daiki-beppu/live-mindmap/issues/1616)）で、形の正を 1 か所に決め、反対側がそれを読んで確かめるようにした。実装は 5 本のチケットに分けた。helper のイベントの見本（[#1617](https://github.com/daiki-beppu/live-mindmap/issues/1617)）、server の知らないイベントの知らせ（[#1618](https://github.com/daiki-beppu/live-mindmap/issues/1618)）、frame の union を 1 か所にする（[#1619](https://github.com/daiki-beppu/live-mindmap/issues/1619)）、web のパスを型で縛る（[#1620](https://github.com/daiki-beppu/live-mindmap/issues/1620)）、web の読めない frame の警告（[#1621](https://github.com/daiki-beppu/live-mindmap/issues/1621)）だ。どれも takt（issue を計画・テスト・実装・レビューまで自動で回すワークフロー）で流し、5 本とも 1 回の run で通った。かかった時間は 21 分から 62 分だった。

### 1. 形の正は送る側に置く。見本は送る側のコードに書き出させ、受ける側はそれを読むだけにする

前は、どちらの側も手書きの形でテストしていた。helper の Swift のテストは、エンコードした辞書のキーを確かめる。server のテストは、helper を偽る `fake-helper.ts` に手で書いた JSON を流す。それぞれのテストは自分の思う形が正しいことしか言えない。両側で一致していなければならない規則もいくつかあった。`screen` の `image` は欄が常にあって `null` もありうる。OCR に失敗した `screen` は `lines` を欄ごと落とす。`origin` の `hostTime` は数字だけの文字列にする。どの規則も、両側を通すテストは無かった。

決めたのは、送る側の Swift が書き出した JSON を正とすることだ。helper のテストの下に `helper-events.jsonl` を置き、Swift の `HelperEvent.jsonString()`（キーを並べ替えるので毎回同じ文字列になる）が出す 19 行を並べた。Swift のテストは、見本の一覧から作った JSONL と置いてあるファイルを比べる。違えば落ち、メッセージに書き直し方（`UPDATE_HELPER_EVENTS=1 pnpm --filter @live-mindmap/helper test`）を出す。見本の一覧の隣には、`HelperEvent` への `switch` を `default` 無しで置いた。case を足すと、見本を足すまでコンパイルが通らない。

server のテストは見本を読んで 2 つを確かめる。どの行も `decodeHelperEvent` で既知のイベントとして読めること。server の union のどの `type` も見本に 1 回以上出てくること。後者が無いと、helper がもう送らない type を server が受け続けていても気づけない。両方向を確かめて、初めて契約になる。

見本の行には、規則が変わると差分に出る形を 1 件ずつ選んで入れた。`hostTime` の値は `9007199254740993`（2^53 + 1）にした。JavaScript の数では正確に表せない最小の整数で、文字列で送る理由そのものになっている。

手書きの `fake-helper.ts` は消さなかった。場面ごとのテストの入力としてはそのほうが書きやすい。両側の形の一致は見本が受け持ち、場面の振る舞いは手書きの入力が受け持つ、と役を分けた。

### 2. 両側が読む見本は、受ける側のテストの層と CI の経路の両方に乗せないと、片側でしか走らない

見本を置いただけでは、2 か所で片側に閉じた。

1 つ目はテストの層だ。このリポジトリでは、unit テストが本物の資源を開かないことを `check-test-layers` という検査で強いている。`node:fs` を import したテストは unit として通らない。server のテストは、見本を Vite の `?raw` の import（ファイルの中身を文字列として取り込む）で読み、unit のまま `pnpm test` で毎回走るようにした。

2 つ目は CI の経路だ。CI の `changes` ジョブは、変わったパスで走らせるジョブを選ぶ。`helper/` の下だけが変わった PR では、TypeScript の `ts` ジョブを走らせない。見本は `helper/` の下にあるので、そのままでは見本だけを書き直した PR で server のテストが走らない。前例が 1 つあった。`helper/package.json` は server のテストが読むので、`helper/` の中でもこのファイルだけは `ts=true` にしていた。見本のパスを同じ例外に足した。

```sh
if printf '%s\n' "$code" | grep -Fqx -e 'helper/package.json' -e 'helper/Tests/HelperCoreTests/Fixtures/helper-events.jsonl'; then ts=true; fi
```

継ぎ目の両側が同じファイルを読むなら、そのファイルが変わったときに両側のテストが走ることまでを、契約の一部として作る。

### 3. 走っている最中の「知らない形」は 1 度だけ知らせて続ける。「1 度」の寿命は、直す手段の寿命に合わせる

CI で捕まえても、走っている最中に知らない形が届くことはある。手元の helper を作り直し忘れて古いままだったり、server を更新したのに画面を読み込み直していなかったりする。前はどちらも跡なく捨てていた。server の取り込みのテストには「未知typeは診断せず」という名前のものまであり、標準エラーが空であることを確かめていた。これを「1 度だけ知らせて、読み飛ばして続ける」に変えた。会議やセッションは止めない。

難しかったのは「1 度」を数える集合の寿命だ。仕様は 2 つの側で別の寿命を選んだ。

- **server**: helper の起動 1 回（attempt）ごと・type ごとに 1 度、標準エラーに出す。直す手段は helper を作り直して起動し直すことなので、起動し直したら空から数える。集合（`Ref`）は、取り込みの試行を開く `openIntake` の中で、起動のたびに作る
- **web**: ページを開いてから type ごとに 1 度、ブラウザの console に出す。直す手段は画面の読み込み直しなので、集合はページと同じ寿命にする。WebSocket の接続ごとに作ると、切れて 1 秒後につなぎ直す（`RECONNECT_MS`）たびに同じ警告が出る。字幕の frame は 1 秒に何度も届くので、console が埋まる

web の集合は、Subscription（Foldkit で外からの出来事を受ける口）のモジュールに 1 つだけ置いた。テストでは `vi.resetModules()` でモジュールを読み直して「新しいページ」を作り、1 つのテストの中では同じモジュールのまま切断とつなぎ直しを挟んで、警告が増えないことを見る。

type の読めない frame（JSON が壊れている、`type` が無い、数字や `null`）は、まとめて 1 つの組として 1 度だけ警告する。分類に使うのは最上位の文字列の `type` だけにした。`{"payload":{"type":"future-a"}}` のような入れ子の `type` で分類すると、本文の中身で警告が分かれてしまう。server の `decodeHelperEvent` も同じ規則にし、最上位に文字列の `type` が無い入力は「知らない type」ではなく形の誤り（`SchemaError`）として扱う。

1 つ、仕様と違う層に置いたテストがある。仕様は server の知らせを、`intakeAttempts` の unit テスト（偽の helper で試す層）で確かめると決めていた。実装の PR は、それを heavy IT（本物の子プロセスをまたぐ層）の `server.heavy.test.ts` に置いた。helper の偽のスクリプトを `SIGKILL` で落とし、起動し直した後に同じ type でもう 1 度知らせが出ることを見ている。unit の `intakeAttempts.test` からは、前の「未知typeは診断せず」のテストの未知 type の部分を外しただけになった。

### 4. 型で起こらなくできることは型に任せ、そのことを確かめていたテストは消す

web の `applyFrame`（frame を受けて画面の状態を変える関数）は `if` の連なりで、最後の `return state` で知らない frame を黙って無視していた。それを確かめるテストもあった。「知らない type のフレームは何も変えない」というテストで、union に無い値を `as unknown as` で型を外して渡していた。

frame の union を、Schema として共有の core（server と web の両方が値として import してよい module）に 1 つだけ置いた（`ViewerFrame`）。server の送る型も web の受ける型もそこから導く。`applyFrame` は Effect の `Match.discriminatorsExhaustive("type")` で 9 種類を書き、足りない case は `pnpm typecheck` が落とす。知らない frame は、もう `applyFrame` まで来ない。手前の decode で止まり、そこで 3 節の警告になる。型を外して入れていたテストは、ありえない入力を試すだけになったので消した。

パスも同じ考え方で縛った。web が直書きしていた `/session/self-pause`・`/session/speaker-name`・`/ws` は文字列のまま残し、server の経路の定義 `ServerRoutes` を `import type` で取って型を付けた。

```ts
type PostPath = Extract<(typeof ServerRoutes)[keyof typeof ServerRoutes], { readonly method: "POST" }>["path"];
export const postToServer = (path: PostPath, body: unknown) => /* … */;

const liveFeedUrl = () => `…${"/ws" satisfies typeof ServerRoutes.feed.path}`;
```

呼び出し側ごとに `satisfies` を書くより、`postToServer` の引数の型で POST の経路のパスに限るほうが、新しい呼び出しでも縛りが漏れない。`import type` なので、17 本の経路の Schema は web の bundle に入らない。

型に任せた所でも、送るときの形は変えなかった。server は frame を union の Schema で encode せず、`JSON.stringify` のまま送る。9 つの frame は Schema の上の型と JSON の形が同じで、encode しても得が無い。逆に、`optionalKey`（省ける欄）に `undefined` が入っていると `null` として書き出され、wire（流れる JSON）の形が変わる危険があった。

### 5. 警告に本文を出さないなら、Schema の失敗から「位置」だけを取り出す。失敗の文には値が入る

web の警告には、frame の type と Schema の失敗の位置だけを出し、本文（字幕の発言・マップの文）は出さない、と仕様が決めた。会議の中身を console に残さないためだ。Schema の失敗をそのまま文にすると、合わなかった値が文に入る。そこで、Effect の `SchemaIssue.makeFormatterStandardSchemaV1()` で失敗を形式化し、各失敗の `path` だけを `$.bubbles.0.track`（字幕の吹き出しの話し手の欄）のような形にして渡した。テストは、字幕・マップ・不正な値に見分けのつく文字列を入れ、logger に渡った message・cause・annotations のどこにもそれが無いことを確かめる。

ここでテストの前提が 1 つ外れた。テストを先に書く段は、知らない type の frame の失敗の位置を `type` の欄だと仮定していた。実装の段で、固定版の `ViewerFrame` が返す位置を見ると、ルート（`path: []`）だった。union のどの候補にも合わないとき、失敗は特定の欄ではなく値全体に付く。実装の担当は、位置を補うコードを足さず、テストを実際の位置に合わせた。仕様が求めたのは「Schema の失敗の位置」で、`type` の欄ではないからだ。

もう 1 つ、decode をする場所を動かした。前は WebSocket の `onmessage` の中で decode していた。このコールバックは Effect の外で呼ばれるので、そこで警告を書いても、テストで差し替えた logger に届かない。警告のためだけに別の runtime を起こすと、logger の環境も受け取った順も分かれる。`onmessage` は受け取った文字列を queue に入れるだけにし、decode と警告は Subscription の stream の中（Effect の中）に移した。読めなかった frame はそこで `undefined` にして、Message にする前に落とす。

## 話者の名前の表を「ログを開く口」からセッションへ移し直したら、復元で名前が消える不具合が復元の側の配線なしで直った話

live-mindmap は、会議の相手の声を「相手 A」「相手 B」のようなラベル（話者）で区別し、ラベルに人の名前（話者の名前）を添えられる。名前は画面で手入力するか、相手が「田中です」と名乗ったのを差分更新（発言が届くたびに AI がマップへの操作だけを返す仕組み）の AI が拾って推定する。付いた名前は `log.jsonl`（出来事を 1 行 1 JSON で追記するセッションのログ）に `speaker-name` の行として残り、会議の終わりに書く `export.json` にも `speakerNames` として載る。2 日前（[前のエントリ](./2026-10-25.md#speaker-name-wrap)）に、この名前の表を「セッションのログを開く口」（`sessionFiles` の `openLogged`）の中へ集めた。今回はそれを開き直し、表を core のセッションの状態に移した。保存したログからセッションを組み直す `cli restore` を流すと `export.json` から名前が消える不具合 [#1523](https://github.com/daiki-beppu/live-mindmap/issues/1523) が、これで直った。決めたのは地図 [#1530](https://github.com/daiki-beppu/live-mindmap/issues/1530) の 3 つの決定（[#1531](https://github.com/daiki-beppu/live-mindmap/issues/1531)・[#1532](https://github.com/daiki-beppu/live-mindmap/issues/1532)・[#1630](https://github.com/daiki-beppu/live-mindmap/issues/1630)）と、それをまとめた仕様 [#1637](https://github.com/daiki-beppu/live-mindmap/issues/1637)（親 [#1655](https://github.com/daiki-beppu/live-mindmap/issues/1655)）。実装は、表を移す [#1656](https://github.com/daiki-beppu/live-mindmap/issues/1656) と、復元で名前の行を読む [#1657](https://github.com/daiki-beppu/live-mindmap/issues/1657) の 2 本に分け、takt（issue を計画・テスト・実装・レビューまで自動で回すワークフロー）で 1 本ずつ流した。どちらも 38 分で、6 人のレビュー役が全員 APPROVE の 1 周で通った。

### 1. 状態の置き場所を「書き手がみな通る口」で決めると、ログを読み戻す側を数え落とす。持ち主は読み戻す側に置く

2 日前に `openLogged` を選んだ理由は、名前を受ける 3 つの経路（ライブと録画、過去のログを流し直す再生と評価、計測用の bench）がどれも `openLogged` を通ることだった。数えたのは名前を「書く」経路だけで、ログを「読んで状態に戻す」経路は数えていなかった。

読み戻す経路は 3 つある。`cli restore`、core の `restoreSession`、見返しの画面を作る `reviewSnapshot` で、どれも `openLogged` を通らず、core の `restoreState`（ログの行を順に畳んで状態に戻す関数）を直に呼ぶ。その `restoreState` は `speaker-name` の行だけを読み飛ばしていた。一方、web の見返しは同じ行を自前で畳んで名前を出していた。ログの読み手が 2 つあり、片方だけが名前を知っていた。

包みを `openLogged` に残したまま復元でも名前を保つ案（B）と、表を core に移す案（A）を並べた。

| | A: core のセッションの状態（採用） | B: `openLogged` の包みのまま、復元にも通す |
|---|---|---|
| 呼び出し側が知ること | `session.nameSpeaker(change)` だけ | `openLogged` が返す `nameSpeaker`。復元のときは、それとは別の、行を畳む読み手 |
| ログの読み手 | `restoreState` の 1 つ | `restoreState` と、名前の行の読み手の 2 つ |
| 復元の 3 経路 | 何もしなくても名前を保つ | 経路ごとに配線が要る |

B で `cli restore` に `openLogged` を通すと、開くときの副作用（`export.json` を書く、画面へ通知を送る、ログの書き先を持つ）が付いてくる。どれも復元には要らない。A にすると `restoreState` に分岐を 1 つ足すだけで、3 経路がまとめて名前を保つ。ほかにも、推定名が core から `openLogged` へ callback で戻ってまた core の規則を通る往復と、`export.json` に名前を足すための包みが消えた。#1656 の本番コードの差分は `sessionFiles.ts` が +10 −38 で、表を移した分だけ減った。

2 日前の決定は「`openLogged` の中の配線なので後から戻せる」と書いていた。実際、外へ出る形（ログの行・`export.json`・画面への通知）を 1 つも変えずに移せた。置き場所を選ぶときの数え方は、書き手と読み手の両方を並べること。状態をログから組み直せる作りなら、ログを読む関数が持ち主の第一候補になる。

### 2. 継ぎ当てですぐ直る不具合でも、持ち主を増やす直し方なら、構造の直しを待つ

#1523 は設計の見直しの中でコードを読んで見つけ、2026-10-27 の triage で実物でも再現した（名前を付けた会議のフォルダで `cli restore` を流すと、`export.json` の `speakerNames` が `null` になる）。直すだけなら、`cli restore` の中で `speaker-name` の行を拾って `exportJson` に足せば数行で済む。triage はそれをしないと決めた。名前の持ち主がもう 1 つ増え、地図で決めていた「持ち主は core のセッション 1 つ」と食い違うからだ。#1523 は単独で流さず、実装のチケット（#1657）の PR が閉じることにした。

地図の調べでは、もう 1 つの抜けも見つかった。`cli play`（再生）が、md・html の書き出しに名前の表として空の `Map` を渡していた。地図の段では「別の作業の途中かもしれない」としていたが、#1531 で確かめると単なる抜けだった。ライブの書き出しは `exportJson` の `speakerNames` から表を作っていて、再生だけが別の所から（何も無い所から）読んでいた。これも、2 つの呼び出し側が同じ所（セッション）から読むようにしたら、それだけで直った。

### 3. ログの行が規則を通った後の結果なら、復元では規則を通し直さず、ラベルごとの後勝ちで畳む

名前の付け方には規則がある。手入力の名前は推定で変えない。推定の名前どうしの付け替えは、相手が名乗ったときだけ受け入れる。復元の後もこの規則が効くには、何を戻せばよいか（#1532）。

最初に思いつくのは、ログの行を 1 つずつ規則に通し直すことだ。けれども通し直せない。規則が「名乗りかどうか」（`basis`）を読むのは入ってくる変更の側だけで、行には `basis` が書かれていない。逆に言えば、通し直す必要も無い。行は表が変わったときにだけ、変わった後の 1 件（trim 済みの名前と、手入力・推定の別 `source`）を書く。だから行をラベルごとに後の行で上書きして畳めば、書いた時点の表とぴったり同じになる。戻した表は `source` を持つので、復元の後に名前を付けても、ふだんのセッションと同じ規則がその表に対して効く。

この畳み方は、web の見返しが前からしていた畳み方と同じだ。#1657 で足した関数は 2 行だった。

```ts
export const restoreSpeakerName = (current: SpeakerNameTable, event: SpeakerNameLogEvent): SpeakerNameTable =>
  new Map(current).set(event.label, { name: event.name, source: event.source });
```

もう 1 つ前提がある。名前の行は、表を書き換えるのと同じ中断されない区間で書く。途中で止まっても、ログは表と同じか一歩先にあり、戻した表が「書いていない名前」を持つことは無い。命令（「この名前を付けて」）ではなく結果（「この名前になった」）をログに書いておくと、復元は検証の無い畳み込みで済む。

形の崩れた `speaker-name` の行は、ほかの行と同じく、何行目で壊れたかを付けて復元を止める。名前の行だけ黙って捨てると、名前が消えたことに気づけない。それはまさに #1523 の症状だった。

### 4. 用語集の定義が、畳み込みに何を入れるかの境界になる

前日に、差分更新の「反映」（`reflectDiff`）を 1 つの畳み込みにしていた（仕様 #1593）。名前の行もそこで畳めば、復元の分岐が 1 つで済むように見える。#1630 はこれを採らなかった。

用語集（`GLOSSARY.md`）は「反映」を「ログの `diff` の行 1 件を、マップ・反映の履歴・発言の台帳に畳むこと」と定義している。名前の表はこの 3 つのどれでもない。反映の結果も名前に依らない。マップの提案者・担当者の割り当ては、反映より前に発言のラベルで済んでいる。名前が効くのは「次の差分更新の入力」と「`export.json`」で、どちらも反映の外にある。入れると、反映の入力が「`diff` の行 1 件」から「ログの行 1 件」に変わり、名前を使わない計測の状態まで名前を運ぶことになる。

そこで `restoreState` の振り分けに、`diff` の分岐と並ぶ `speaker-name` の分岐を足した。2 つの行は互いの結果を読まないので、ログの中のどこに名前の行があっても、同じ表とマップに戻る。#1657 のテストは、名前の行を `diff` の行の前後に動かしても元と同じに戻ることを確かめている。ライブでは推定名の行が必ず `diff` の行の後に来るが、復元はその順に頼らない。

### 5. 専用のロックを消して既存の区間に相乗りしたら、その区間の中から同じ区間を取らない

2 日前の包みには、名前のためだけのロックと「名前 → ログ」の順で取る決まりがあった（[前のエントリの 3 節](./2026-10-25.md#speaker-name-wrap)）。表を core に移したので、名前の操作は core が共有画面の出し入れと差分の反映に使っている区間（同時に 1 つしか入れない semaphore）に相乗りした。ロックが 1 つになり、取る順の決まりは要らなくなった。

代わりに、1 か所だけ気をつける所ができた。推定名は差分の反映の区間の中で受け入れが決まる。ところが名前の操作も同じ区間を取る。Effect の semaphore は取り直せない（同じ Fiber でも、もう一度取ろうとすると待ち続ける）。実装は、受け入れた推定名を区間の戻り値として外へ出し、区間を抜けてから名前の操作に渡した。名前の行が `diff` の行の後になるという仕様の順も、これで自然に守られる。ロックの数を減らしても、「区間の中から、同じ区間を取る関数を呼ばない」という前回の学びはそのまま残る。

### 6. 今の振る舞いを確かめていたテストは、正しい直しで落ちる。入力が経路に届いているかも疑う

`speakerNames.it.test.ts` には、「`restoreState` は名前の行を読み飛ばす」ことを確かめるテストが 2 つあった（手入力と推定）。守りたかったのは「名前の行があってもマップと発言は元どおりに戻る」ことだったが、書き方は「表が空で戻る」ことまで固定していた。#1523 を直すと、このテストは落ちる。仕様の段で消すと決め、守っていたことは復元の往復のテスト（元のセッションと、そのログから戻したセッションの見え方・`export.json`・次の差分更新の入力が等しい）に含めた。

core に移った契約（次の差分更新の入力に名前が載る、`export.json` に名前が入る、推定名の受け入れ）は、偽の差分更新と偽のログを使う core の単体テストに移し、同じことを確かめていた IT は消した。`speakerNames.it.test.ts` は #1656 で +22 −259 行になった。

単体テストを書く段で、もう 1 つ見つかった。元のテストは推定名の根拠の発言に「はい」を使っていた。「はい」は中身の無い発言として差分更新の対象から外れるので、推定名の根拠にならない。テストは推定名が付かない理由を、確かめたい規則とは別の所で得ていた。入力を「田中です」に直して、規則の側で受け入れ・拒否が決まるようにした。テストが緑でも、入力が確かめたい分岐まで届いているとは限らない。

### 7. 複雑度の上限は、同じ値になる条件分岐を見つけさせる

#1657 で `restoreState` に分岐を 1 つ足すと、fallow（未使用・重複・複雑度を見る検査）が認知的複雑度 16 で落ちた（上限 15）。関数を分けて逃がす案もあったが、実装は既存の条件式を読み直した。`diff` の行の後で差分更新の状態を「一時停止なら動作中に、そうでなければそのまま」にしていた。復元の中で作られる状態は動作中か一時停止のどちらかしかないので、どちらも動作中になる。条件式を「動作中にする」の代入 1 つにまとめ、上限の内側に戻った。

上限を超えたときは、分割の前に、その関数の中に結果の変わらない分岐が無いかを見る。分割は複雑さを移すだけだが、同じ値になる分岐は消せる。

### 8. 実物の確かめは、合成のセッションと分けた HOME で回すと、本物の会議を読まずに済む

#1657 の受け入れ条件には、#1523 の再現手順を手で流すことがあった。実装の run は、手元にある本物の会議のフォルダを使わなかった。実物の `openLogged` とファイルシステムで、名前の付いた合成のセッションを保存し、それをライブの書いた `export.json` の比較元にした。そのうえで、専用の HOME とセッションの置き場所で 2 つのコマンドを流した。

```sh
env HOME="$PWD/.takt/issue-1657-cli/home" \
  LIVE_MINDMAP_SESSIONS="$PWD/.takt/issue-1657-cli/sessions" \
  pnpm cli restore

env HOME="$PWD/.takt/issue-1657-cli/home" \
  LIVE_MINDMAP_SESSIONS="$PWD/.takt/issue-1657-cli/sessions" \
  pnpm cli export --format json
```

ライブの保存・restore の後の `export.json`・JSON の書き出しの標準出力の 3 つで、`speakerNames` は `{"相手 A":"佐藤","相手 B":"田中"}` に揃い、JSON 全体も一致し、`log.jsonl` は変わらなかった。会議の中身を読まずに、利用者と同じコマンドの端から端までを確かめられる。
