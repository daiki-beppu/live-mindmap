# ロックの中から呼ぶ send がログを書かないことを、型や構造で守る

SessionLog は、書き込みのロックの中でフレームを送ります。この send がログを書かないという決まりは、`LoggedSessionOptions.send` のコメントで守っています。型や構造の検査は足しません。

## 背景

#2050 で、diff-update と speaker-names の送信を、SessionLog の書き込みのロックの中に移しました。送る順とログに書く順をそろえるためです。

ロックは再入できない `Semaphore(1)` です。そのため、ロックの中で呼ぶ send がログを書くと、ロックを待ち合って止まります。今の send は `Viewers.send` で、ログを書きません。

## なぜ足さないか

挙がった案は、どれもこの決まりを守れないか、守る代わりに大事なものを壊します。

- **型で禁じる**: 守れません。send がログの書き込みを closure で捕まえれば、Effect の要件（`R`）は `never` のままです。そのため型はこれを区別できません。

  ```ts
  // 型は通る。要件にログは現れない
  const send: SendFrame<NotIntakeFrame> = (frame) => appendLog(toLogEvent(frame));
  ```

- **send をロックの外に出し、順序を別の仕組みで決める**: #2050 が揃えた「送る順とログに書く順」を、もう一度作り直すことになります。直したい危険より、作り直す手間と危険のほうが大きくなります。

この決まりが破られると、ロックを待ち合って止まります。止まれば、diff-update を送る今のテストが止まったまま終わらないので、黙って通ることはないと見込んでいます（試してはいません）。

AGENTS.md の「Rules and what enforces them」は、同じ決まりがまた破られたときに、文章ではなく検査を足すとしています。この決まりは、まだ一度も破られていません。

## 考え直すとき

ロックの中の send からログを書く変更が実際に入りかけたら、考え直します。そのときは、型よりも見張りを足します。たとえば、ロックの中からもう一度ロックを取ろうとしたら、止まったままにせず、名前の付いた defect で落とします。
