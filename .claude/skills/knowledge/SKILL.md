`docs/knowledge/` の記事は、社外への発信（ブログ・登壇）の素材になる。読み手はこのプロジェクトを知らない開発者で、リポジトリは private なので issue や PR のリンク先も読めない。**本文だけで話が通じる**ことを最優先にする。

## 手順

1. **main を最新にしてブランチを切る。** `git fetch` して `origin/main` から `docs/knowledge-<slug>` を作る。完了条件: 既存の `docs/knowledge/*.md` と、最新の `CONTEXT.md`・`docs/adr/` を読み終えている。

2. **素材を集める。** 対象の作業について、チケットの本文と resolution コメント、関連 PR の差分、このセッションのやり取りを読む。完了条件: 次の 2 つが分かっている。
   - 作業の中で**判断が変わった瞬間**（候補を比べて選んだ、想定と違う結果が出た、決めたことどうしが矛盾した）
   - その判断が**その後の main で直されたかどうか**。直されていたら、記事の最後に「その後」の節を立てて経緯を書く。本文が最新の `CONTEXT.md` と食い違ったままにならないようにする

3. **学びを選ぶ。** 学びとは、他のプロジェクトでも使える判断の基準、はまりどころ、再現できるコマンド、実測した数字のこと。決定の中身そのもの（何に決めたか）はチケットにあるので、記事では、なぜそう決めたかと、どんな基準で決めたかを書く。完了条件: 学びのそれぞれに、このプロジェクトでの具体例（実際の発言・数字・失敗）が 1 つ以上ある。

4. **書く。** `docs/knowledge/<ファイル名>` に、既存の記事と同じ形で書く。
   - ファイル名は、書いた日（日本時間）を付けて `YYYY-MM-DD-<slug>.md` にする。同じ日付の記事が既にある場合は、その日の記事すべてに書いた順の 3 桁の番号を付ける（`YYYY-MM-DD-001-<slug>.md`、`YYYY-MM-DD-002-<slug>.md`）。番号のない既存の記事は `git mv` で `-001-` に改名する
   - タイトルは「〜した話」。導入の 1 段落で live-mindmap が何か（会議の音声から AI がマインドマップを差分更新し続ける Web アプリ）と、何をしたときの学びかを書き、決定の記録（チケット・ADR）へのリンクを並べる
   - 節は番号付きで、**見出しを学びの主張そのもの**にする（「種別は『答えを出す対象か』という 1 本の軸で切る」のように）。見出しだけを拾い読みしても学びが伝わる
   - プロジェクトの用語（`CONTEXT.md` の語）は、初めて出てくるときに一言で説明する
   - 表・コマンド・数字は、実際に使ったものだけを載せる

   完了条件: 社外秘の会議の内容、第三者の音声や文字起こしの長い引用、認証情報が含まれていない。

5. **PR にしてマージする。** タイトルは `docs: <何をしたとき>の学びを記録（issue #<n>）`。本文に節の見出しを箇条書きで並べる。squash でマージし、PR の URL と節の一覧を報告する。
