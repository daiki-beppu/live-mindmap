`docs/knowledge/` は 1 日 1 ファイルの開発ログで、作業ごとに 1 エントリを追記する。日付ファイルは、そのまま技術記事や個人ブログの 1 本として公開する前提で書く。読み手はこのプロジェクトを知らない開発者で、リポジトリは private なので issue や PR のリンク先も読めない。**本文だけで話が通じる**ことを最優先にする。

## 手順

1. **main を最新にしてブランチを切る。** `git fetch` して `origin/main` から `docs/knowledge-<slug>` を作る。完了条件: 既存の開発ログ（`docs/knowledge/*.md`）と、最新の `CONTEXT.md`・`docs/adr/` を読み終えている。

2. **素材を集める。** 対象の作業について、チケットの本文と resolution コメント、関連 PR の差分、このセッションのやり取りを読む。完了条件: 次の 2 つが分かっている。
   - 作業の中で**判断が変わった瞬間**（候補を比べて選んだ、想定と違う結果が出た、決めたことどうしが矛盾した）
   - その判断が**その後の main で直されたかどうか**。直されていたら、エントリの最後に「その後」の節を立てて経緯を書く。本文が最新の `CONTEXT.md` と食い違ったままにならないようにする

3. **学びを選ぶ。** 学びとは、他のプロジェクトでも使える判断の基準、はまりどころ、再現できるコマンド、実測した数字のこと。決定の中身そのもの（何に決めたか）はチケットにあるので、エントリでは、なぜそう決めたかと、どんな基準で決めたかを書く。完了条件: 学びのそれぞれに、このプロジェクトでの具体例（実際の発言・数字・失敗）が 1 つ以上ある。

4. **書く。** 書いた日（日本時間）の `docs/knowledge/YYYY-MM-DD.md` の末尾に、エントリを 1 つ追記する。既存の日付ファイルと同じ形にする。
   - その日のファイルが無ければ作る。冒頭は `# 開発ログ YYYY-MM-DD`、live-mindmap が何か（会議の音声から AI がマインドマップを差分更新し続ける Web アプリ）を 1 段落、「この日のエントリ:」の番号付きの目次の順に置く。プロジェクトの説明はファイル冒頭の 1 回だけにし、エントリごとには書かない
   - 目次に、追記したエントリへのリンクを 1 行足す
   - エントリは `<a id="<slug>"></a>` の行と、`## <タイトル>` の見出しで始める。タイトルは「〜した話」。他のエントリへのリンクは、同じ日なら `#<slug>`、別の日なら `./YYYY-MM-DD.md#<slug>` にする（見出しから自動で作られるアンカーは日本語で崩れやすいので使わない）
   - 見出しの直後の 1 段落で、何をしたときの学びかを書き、決定の記録（チケット・ADR）へのリンクを並べる。同じ日の直前のエントリは時系列で並んでいるので、「前のエントリ」へのリンクは要らない
   - 節は `###` の番号付きで、**見出しを学びの主張そのもの**にする（「種別は『答えを出す対象か』という 1 本の軸で切る」のように）。見出しだけを拾い読みしても学びが伝わる
   - プロジェクトの用語（`CONTEXT.md` の語）は、エントリの中で初めて出てくるときに一言で説明する。日付ファイルを 1 本だけ読んでも通じるようにする
   - 表・コマンド・数字は、実際に使ったものだけを載せる

   完了条件: 社外秘の会議の内容、第三者の音声や文字起こしの長い引用、認証情報が含まれていない。

5. **PR にしてマージする。** タイトルは `docs: <何をしたとき>の学びを記録（issue #<n>）`。本文に、追記した日付ファイルとエントリのタイトル、節の見出しを箇条書きで並べる。squash でマージし、PR の URL と節の一覧を報告する。同じ日に複数の作業のエントリを並行で書くと、同じ日付ファイルの末尾と目次で衝突しやすい。並行で書くときは 1 つのブランチにまとめるか、先にマージされたものを取り込んでから追記する。
